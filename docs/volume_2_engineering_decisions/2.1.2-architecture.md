## 2.1.2.1 Service data under `/opt/<svc>` or `/var/lib/fabric/<svc>`

- **Decision:** `/var/lib/fabric` for new installs; keep `/opt` paths on existing hosts.
- **Shapes:** 1.2
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** the product design (2.3.1.4 maps where it went).
- **Status:** Replaced by 2.1.2.5 (2026-10-03: installed under `/opt`). It was never followed: every install used `/opt/fabric` and `/opt/<svc>`.

## 2.1.2.2 Docker privilege

- **Decision:** Harden all containers + daemon; userns-remap on by default; rootless opt-in with stated limits ([1.3.2.1](../volume_1_description_and_architecture/1.3.2-setup-design.md#1321-setup-secure-by-default-fully-scriptable), [1.2.6.1](../volume_1_description_and_architecture/1.2.6-targets-and-hardening.md#1261-targets-and-hardening)).
- **Shapes:** 1.2
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** least privilege for every container (global Rule 10); user-namespace remapping stays the isolation path (2.3.2.2.1).
- **Status:** In force. Built: container and daemon hardening; not built: userns-remap, rootless.

## 2.1.2.12 The host firewall when its management is declined but ufw is already on

- **Decision:** fabric's firewall step **secures the host to fabric's own ports only**; when the host already has firewall rules, setup says so and lists the ports fabric will open beside them, instead of offering to take the firewall over.
- **Shapes:** 1.2, 3.3
- **Made:** 2026-10-08, by the owner, for 0.6.2, after the owner's own run of setup on the test Pi: Keycloak could not reach the DC through ufw, and setup failed late as "UnknownError".
- **Why:** 2.3.6.2.11.
- **Status:** Revised 2026-10-08 by 2.1.2.13 (separate questions).

## 2.1.2.13 The host firewall's questions

- **Decision:** **Separate questions:** first *open the ports fabric needs* (`ports`; declined while ufw is on, setup stops at once with the reason); then, only if yes, *secure the host* (`firewall`: deny incoming by default, only what fabric needs plus SSH); then, only if yes and the host has ufw rules fabric did not add, *remove them* (`own_rules`: listed one by one; yes removes them, recorded and put back by uninstall; no keeps them).
- **Shapes:** 1.2, 3.3
- **Made:** 2026-10-08, by the owner, for 0.6.2. Revises 2.1.2.12.
- **Why:** opening ports and taking over a firewall are different consents; a person keeps rules of their own unless they choose otherwise (2.3.6.2.11).
- **Status:** In force.

## 2.1.2.14 Consent carried over when a group is split

- **Decision:** An earlier yes to a group later split answers the groups it covered (0.6.1's `firewall` answers `ports` and `firewall`); a genuinely new group (`own_rules`) is still asked. Each split records its mapping.
- **Shapes:** 1.2, 3.3
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** found by the upgrade test (2.3.5.3.17, 2.3.1.11.3).
- **Status:** In force; **built 2026-10-08** for 0.6.3.

## 2.1.2.15 Traffic stays on the host

- **Decision:** Whenever possible, traffic does not leave the host, and above all traffic between fabric's own
  services: containers talk over `fabric_net` (by alias or `fabric_net` address) or unix sockets, never through the
  host's LAN address or a public name. A service on the host network that containers must reach (the domain
  controller) also listens on `fabric_net`'s gateway (`ip_fabric_gateway`, the host's address on the bridge), and
  containers use that. Traffic leaves the host only where it must: LAN clients and machines (DNS, DHCP, 802.1X, ACME
  for LAN machines, the web pages), sites of a federation, and upstreams (registries, Sigstore, the internet's DNS).
- **Shapes:** 1.2, 1.6, 1.7, every chapter that connects one service to another
- **Made:** 2026-10-08, by the owner ("whenever possible we do not want traffic to leave the host, especially true for
  container to container interactions"; the DC on the bridge the same day).
- **Why:** fewer paths through the host's firewall and NAT, nothing of fabric's own on the wire, and no dependence on
  the LAN address for what happens inside the host.
- **Status:** In force. Applied 2026-10-08: Keycloak's and FreeRADIUS's LDAPS to the DC moved from the LAN address to
  `ip_fabric_gateway` (the DC listens there too, its DNS records still name the LAN address only: `samba_dnsupdate
  --current-ip`); OpenBao reaches Postgres by its alias (2.1.7.4); Postgres's unused name `postgres.<domain>` left its
  certificate. Audited the same day: everything else between containers already used `fabric_net` or a socket.

## 2.1.2.16 Setup asks only what cannot be changed later

- **Decision:** setup asks what is permanent once installed (the DNS domain, the host name, which is the domain
  controller's name, the organisation's name, which names the CA, and the AD domain), what it needs to install at
  all (the network, found and confirmed; the first admin and their password, 2.1.6.33) and the host changes it may
  make (global Rule 12). Everything else takes a default and is changed later: the password policy (2.1.6.35), the
  memory fabric may use (all of it), Kerberos sign-in (off, 2.1.6.32), the firewall and Docker hardening, Keycloak and
  the web console, the DNS filter, DHCP, RADIUS and log forwarding. The plan is still shown, with Proceed as the
  default; **Advanced** keeps only permanent choices: the CA root's lifetime (2.1.5.6) and, from the release after 0.7 (2.1.1.42), leaving the host
  out of its domain (2.1.6.34). The host name is refused by the vars editor, as `ad_domain` is.
- **Shapes:** 1.3, 3.3, 1.6, 1.2
- **Made:** 2026-10-09, by the owner ("Can't we ask only the immutable changes during install and leave the rest to
  the ui? … This also means advanced largely goes away"; the lighter policy chosen the same day).
- **Why:** a first install should be short; choices that can be changed later belong where they are changed
  (the command line and vars editor now, the settings page after 0.7: 2.1.8.4, 2.1.1.42).
- **Status:** In force; **built 2026-10-09** for 0.6.4 (2.1.1.41). Revises 2.1.2.3, 2.1.6.13 and 2.1.6.32.
  **Revised by 2.1.6.45 on 2026-10-11:** the host's name is no longer permanent; the DC's own name
  (`dc_name`) is asked in its place (0.7.0).

## 2.1.2.17 Advanced is a numbered menu of settings, the optional parts among them

- **Decision:** setup's Advanced is a numbered text menu: every setting worth choosing before the install, each with
  its current value (the CA root's lifetime, this host as a member of its domain, and the optional parts: DHCP with
  Kea, 802.1X with FreeRADIUS, log forwarding with Fluent Bit, the DNS filter); a number changes one (turning a part on
  asks what it needs, such as DHCP's interface), Enter goes back to the plan. A part left off is not installed at all
  (nothing pulled, written or started: 1.1.9). A plain menu, not a dialog box: it works over any SSH session and with
  answers given on standard input ([1.2.9.10](../volume_1_description_and_architecture/1.2.9-host-consent.md#12911-setups-start-guided-or-a-menu-of-every-setting-one-confirmation)).
- **Shapes:** 1.2, 3.3
- **Made:** 2026-10-11, by the owner, seeing rc.2's Advanced ask one question with no overview ("advanced should be a
  selection window"; "if users don't want DHCP or FreeRadius, leave the packages away … and don't start their
  containers"): a numbered text menu over a dialog (whiptail); the parts in it.
- **Why:** one screen shows what Advanced can change; the parts are the choices most worth making up front.
- **Status:** In force; **built 2026-10-12 for 0.7.1** (2.1.2.21; moved from 0.9 by 2.1.1.51). Refines 2.1.2.16 (what Advanced holds). Revised by 2.1.2.19 on 2026-10-11:
  Advanced is the whole of setup's menu, reached from setup's start or the plan.

## 2.1.2.18 One confirmation for every host change; the recommended ones are opted out in Advanced

- **Decision:** setup's plan lists every host change fabric would make, by group, with what each changes: the
  required ones (packages, fabric's own services, its service accounts) and the recommended and choice ones (Docker's
  hardening, the firewall's three, the host trust store, time, the resolver, domain membership). **Proceed** is the one
  yes that approves all of them. The recommended and choice groups are items of the Advanced menu (2.1.2.17), on by
  default: turning one off shows what declining it means and records it declined (a relaxation, shown as today); a
  group another needs takes it along (the firewall needs ports, the host's own rules need the firewall). No separate
  consent question is asked in an interactive run; an unattended run's `--approve`/`--decline` are unchanged.
- **Shapes:** 1.2, 3.3
- **Made:** 2026-10-11, by the owner, at rc.2's test install: first "mandatory stuff can all be combined", then "some
  recommended changes (such as firewall rules, such as securing) can be placed in the advanced menu … host trust store.
  Should be in advanced". Supersedes the same day's "the required changes take one yes".
- **Why:** global Rule 12 asks for every host change up front with one confirmation for the list shown; the
  recommended changes are what almost everyone wants, so declining one is an Advanced choice, not a question each time.
- **Status:** In force; **built 2026-10-12 for 0.7.1** (2.1.2.21; moved from 0.9 by 2.1.1.51). Revises how 2.1.2.13's questions are asked, not what fabric changes.

## 2.1.2.19 Setup starts with a choice: guided, or a menu of every setting

- **Decision:** an interactive setup on a new install starts with a choice: **[G]uided** asks the questions setup needs,
  one at a time (as today), then shows the plan; **[A]dvanced** is one numbered menu of every setting, the required ones
  first (each shown as "needs an answer" until it has a value; Proceed waits for them), then what is best chosen before
  the install, then the host changes; the plan offers the same menu (`[M]enu`) to change anything before Proceed
  ([1.2.9.11](../volume_1_description_and_architecture/1.2.9-host-consent.md#12911-setups-start-guided-or-a-menu-of-every-setting-one-confirmation)).
- **Shapes:** 1.2, 3.3
- **Made:** 2026-10-11, by the owner ("advanced should be presented at the beginning, and all other interactive
  discussions should be there too … the whole thing should become a selection, with [g] being guided mode, and [a]
  being a menu option and advanced mode"), the layout confirmed from a preview.
- **Why:** one screen holds every choice, in any order, for those who want it; the guided path stays for those who do
  not.
- **Status:** In force; **built 2026-10-12 for 0.7.1** (2.1.2.21; moved from 0.9 by 2.1.1.51). Revises 2.1.2.17.

## 2.1.2.22 The console's fixes from the 0.7.0 test install, in 0.7.1

- **Decision:** built in 0.7.1 with the installer's improvements (2.1.2.21, 2.1.1.51):
  1. **The DNS filter tab updates itself** while a fresh install's first fetch runs (the lists and AdGuard's
     catalogue arrive a minute or so after setup): it refreshes until every ticked list has a copy, then stops.
  2. **The password policy is edited in the console** (Directory, Domain), behind the domain admin's permission and
     the same checks as `fabricctl domain password-policy`, not only shown.
  3. **Adding a DNS record asks only what its type needs:** type, name, value; priority for MX, priority, weight
     and port for SRV, shown only for those types.
  4. **The landing page's links leave the record form.** The landing page is fabric's start page,
     `info.<domain>`, with a link to each of your services; which records it links to is set on its own page
     (a "Landing page" section listing the links, each naming a record), not with every record.
  5. **The Domain tab names the roles plainly:** "This controller holds all five roles" (or which it holds and
     which another does), not each role's DN.
  6. **Deleting one of fabric's own names works, or says why it cannot.** The owner deleted `info.<domain>` in the
     DNS tab and the apply kept it: fabric's own names (the landing page's `info`, `ca`, `dns`, `sso`, `vault`, `ntp`,
     the console's) are added back from their settings on every render (`templates/vars.yaml.j2`, `default_cnames`).
     The DNS tab marks them as fabric's ("provided by fabric", as 2.1.10.14's options), and removing one either turns
     its service's name off through its setting (the landing page's `info`) or is refused, naming the setting.
- **Shapes:** 1.8, 1.4, 1.6, 1.12
- **Made:** 2026-10-12, by the owner at the 0.7.0 candidate's test install (item 6: "apply did not remove the
  info.home.arpa page when deleted. Trying to test the record for deletion and it didn't work"): "page did not automatically refresh and

  record adder is kind of unnecessarily complicated, normally you only have 4 values at most"; "What's the
  "landing" page? wouldn't that be set on some other device or tab?"; earlier "just put all the ui install fixes in
  0.8". Item 5 was seen in the same screenshots.
- **Why:** each is what the owner met first on a real install.
- **Status:** In force; built in 0.7.1 on 2026-10-12 (branch `dev/0.7.1-console`): item 1 in 1.12.2.17, items 2 and
  5 in 1.6.5.25 (the new permission `domain:admin`, admins only), item 3 in 1.4.1.4, item 4 in 1.4.2.4, item 6 in
  1.4.1.4. Item 6 is built as "refused, naming the setting" for every one of fabric's names, `info` included: turning
  the landing page's name off needs more than its setting (2.3.1.19.5), which waits for the owner.
  **Revised by 2.1.4.6 on 2026-10-12 for `info`:** the landing page is served at `http://<host_ip>/info/` and on

## 2.1.2.23 The console waits as long as an apply may run

- **Decision:** Every console change that saves and applies at once (DHCP, RADIUS, DNS zones, log-on policies, DNS
  filter changes) waits for fabric-agent up to 960 s, as Apply changes does, and the reverse proxy in front of the
  console waits 990 s. The wait is only how long the console waits for an answer before giving up. It does not slow
  a change down: a DNS record is live after the zone's reload (no restart), a DHCP change after Kea's restart and
  health check.
- **Shapes:** 1.8, 1.4, 1.10, 1.11
- **Made:** 2026-10-12, by Claude, after a log-on change's apply outlived the console's 30 s wait (2.3.1.20.6); the
  owner asked only whether it slows quick changes (it does not).
- **Why:** since 0.7.0 an apply restarts one service at a time, each health-gated (2.1.14.15), so it can run for
  minutes; a console that gives up first shows an error while the change goes on.
- **Status:** In force; built 2026-10-12 for 0.7.1.

## 2.1.2.24 The host's own firewall rules are said apart before setup removes them

  explicit statement of any custom removals and allow users to opt out of resetting custom firewall rules".
- **Why:** the opt-out existed (2.1.2.13) but read as one plan line among many, and Proceed allows them all at once.
- **Status:** In force; built for 0.7.1.

## 2.1.2.25 Setup says it is ready only once what a person reaches first answers

- **Decision:** a setup step `ready`, after `verify`, gates *fabric is ready* and the first steps: it waits (up to 5
  minutes) until the landing page by address, sign-in (Keycloak's realm through nginx, certificate checked), the web
  console, and Keycloak's database (no refused sign-in in Postgres's log for 30 s) answer in the same round, and
  otherwise stops, naming what did not (3.3.3).
- **Shapes:** 3.3.3 (the steps), 3.3.2 (the first steps follow it).
- **Date and who:** 2026-10-14, the owner, after the 0.7.1 rehearsal: "let's put that 40 seconds as a gated health
  check before showing users the final setup instructions".
- **Why:** setup's last words send a person to the landing page and the console; they should work when read. The
  40 seconds of refusals turned out to be Postgres's health probe, not Keycloak (2.3.1.21.4), and is fixed apart;
  the gate stays so any such settling is waited for, or said.
- **Status:** In force; built for 0.7.1.

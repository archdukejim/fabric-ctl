### 2.3.5.3.1 What the owner asked

On 2026-10-08, for a 0.6.3 of small items before the 0.7/0.8 work that needs isolated networks or hardware:

- **Upgrade in place, tested**, as 2.1.1.32 requires from 0.6.1 on (0.6.2 shipped without it).
- **Image updates, tested:** each container one small version back, then updated.
- **Certificate renewal.** Service certificates live **90 days** and are renewed with **30 days left** (overlap well
  inside the browsers' shrinking limits: 200 days from March 2026, 100 from 2027, 47 by 2029). Certificates fabric
  cannot renew itself are **warned about ahead**. Upgrading to 0.6.3 **re-issues** today's long-lived service
  certificates. The **CA's lifetime is asked at install** (in Advanced; the root's, default **10 years**; the
  intermediate follows it).
- **The instructions page** (today the landing page at `<domain>`) moves to **`info.<domain>`**, always reachable
  over **plain HTTP** as well as HTTPS, with the CA download and the root's fingerprint; `<domain>` and the host's own
  name redirect to it.

### 2.3.5.3.2 How it works today

- **Service certificates** (the table in `setup/mint_service_certs.py`: nginx's hosts, BIND, OpenBao, Keycloak and
  Postgres, the DC, FreeRADIUS) are minted from Step-CA by `pki/mint_cert.py` with `cert_service_days`: 365 in
  `vars.yaml.j2`, a 5475-day fallback in code. They are renewed only when `fabricctl setup` or `fabricctl certs` runs;
  `pki/needs_renewal.py` already renews one with under 30 days left, missing, not from the CA, or without a SAN. A
  renewal **restarts** each affected service. **Nothing runs on a schedule** (1.5.1.2 says so).
- **The CA:** `setup/init_pki.py` makes the root with a hard-coded 10 years (`--not-after 87600h`) and lets `step ca
  init` choose the intermediate's lifetime. `cert_root_ca_days` (1825) and `cert_intermediate_days` (1095) exist in
  the settings, but the root does not read them; `cert_intermediate_days` is used only for federation site CAs.
- **Certificates fabric cannot renew:** device and people certificates (the PKI page already marks those with under
  30 days "expires soon"), the web UI's admin client certificate (365 days, renewed only by setup), and the CA's root
  and intermediate. `fabricctl status`, `fabricctl doctor` and the web UI's overview show no expiry today.
- **The landing page** is HTTPS only, at `hostname_landing` (`<domain>` unless `landing_page_cname` is set) and the
  host's own name; plain HTTP redirects everything to HTTPS except `/certs/` and the certs host, which answers on both.
- **Upgrades:** the `.deb`'s postinst only asks for `sudo fabricctl setup`; `setup/upgrade_vars.py` migrates settings.
  The sandbox upgrades a package built from the same source onto itself; nothing upgrades from an actual previous
  release.
- **Image updates:** `fabricctl images status/update/rollback` work (health-gated, restoring on failure); the sandbox
  tests update and rollback for nginx only.

### 2.3.5.3.3 Service certificates: 47 days, renewed at 30 days old

(Title and values as revised by 2.3.5.3.13; first proposed as 90 days, renewed with 30 left.)

- `cert_service_days` defaults to **47**, in the settings and in code (one default); a new setting,
  `cert_renew_after_days` (default **30**), is the age at which a certificate is renewed, so with the defaults a
  certificate is renewed with 17 days left. Both are checked: the renewal age is at least 1 day and leaves at least
  7 days. Step-CA's maximum (`stepca_cert_max_lifetime_hours`) follows `cert_service_days`, as now.
- **A daily timer**, `fabric-certs.timer` (fabric's own unit, under `fabric.target`, in the `services` consent group
  like the others), runs `fabricctl certs --scheduled` at a quiet hour with a random delay. It renews only what
  `needs_renewal` says (30 days old, so a failed night is retried every night for 17 days).
- **Picked up without downtime where the service allows it:** nginx and Postgres **reload**; OpenBao gets **SIGHUP**
  (it re-reads its listener certificate; a restart would leave it sealed on a host unlocked only by a USB stick or a
  security key); Keycloak re-reads its certificate by itself (`https-certificates-reload-period`); BIND, the DC and
  FreeRADIUS **restart** (seconds). Which applies is a table beside the certificates table, tested per service.
- **Failure is loud:** each run records its result (`/var/lib/fabric/certs/last-renewal.json`). A failed run, or any
  service certificate under **7 days**, is a warning in `fabricctl status`, a failure in `fabricctl doctor` and a
  banner on the web UI's overview. The timer's journal holds the detail.
- **A certificate longer-lived than the setting is re-issued** (a new `needs_renewal` reason): this is how the
  upgrade to 0.6.3 replaces today's 365-day and 5475-day certificates, and how a lowered setting takes effect.
- `needs_renewal`'s fixed "30 days left" becomes the renewal age above; the issued-certificate list keeps its own
  30-day "expires soon" mark (2.3.5.3.4).
- `fabricctl certs` without `--scheduled` stays as it is (renews what needs it; `--force` renews everything), now
  with the same reload table.

### 2.3.5.3.4 Certificates fabric cannot renew: warned ahead

- **The root and intermediate CA:** warned **180 days** before either expires (status, doctor, the web UI's
  overview); replacing them stays a manual procedure (3.5).
- **The web UI's admin client certificate** (when that layer is on): warned 30 days ahead; renewed by `fabricctl
  setup`, as now.
- **Device and people certificates:** the PKI page keeps its "expires soon" mark (30 days); the overview gains a
  count of those expiring soon and expired, linking to the page.

### 2.3.5.3.5 The CA's lifetime, asked at install

- **One question, the root's lifetime** (`cert_root_ca_days`, default **3650**, i.e. 10 years), shown on setup's plan
  with its default and changed in **Advanced**; at least 365 days. `init_pki` uses it instead of the hard-coded
  10 years.
- **The intermediate follows:** its lifetime is the root's **less one year** (9 years by default), passed to `step ca
  init`, so it never outlives the root and leaves a year to replace it before the root ends. `cert_intermediate_days`
  keeps its one use, federation site CAs (capped at the root, as now).
- **Fixed once the CA exists:** on an existing install the question is not asked, and a changed value is refused
  with the reason (a CA's lifetime cannot change once it is made). Existing installs keep their CA.

### 2.3.5.3.6 The info page at info.\<domain\>, over HTTP too

- `landing_page_cname` defaults to **`info`**, so `hostname_landing` is `info.<domain>` (a value already set is
  kept). BIND gets the record like any other name.
- **`info.<domain>` answers on HTTP and HTTPS, with no forced redirect:** the instructions, the CA files and the
  **root's SHA-256 fingerprint**, so a person on a new device can fetch the CA over plain HTTP and check it before
  trusting it. Everything else stays HTTPS-only: the manual (`/manual/`) and the "This network" links stay on HTTPS,
  and the plain-HTTP page links to them there.
- **`<domain>` and `<hostname>.<domain>` redirect** (301) to `info.<domain>`: HTTP to its HTTP page, HTTPS to its
  HTTPS page, so old bookmarks keep working. The page's service certificate covers all three names.
- The certs host (`certs.<domain>`) stays as it is.

### 2.3.5.3.7 Upgrade-in-place test, every release

A host test, `tests/host/upgrade.sh`, run on the test Pi before each release from 0.6.3 on:

1. remove fabric (purge), install the **previous release** from apt `stable` and set it up non-interactively;
2. **seed state:** a person with a password, a DNS record marked for the info page, an issued device certificate, an
   AdGuard filter setting, an application secret in OpenBao, a raised sign-in layer;
3. **upgrade** to the candidate from apt `testing` and run `fabricctl setup`, as an operator would;
4. **check it survived:** the person signs in with the same password; the CA's root is the same file; the record, the
   certificate (still valid against the CA), the AdGuard setting, the secret and the layer are all still there; then
   the whole host suite.

First run: **0.6.1 → 0.6.2**, to catch up on the release that skipped it; then 0.6.2 → 0.6.3 for this release. The
results go in the release's notes, and the procedure goes in 3.1 as a step of every release.

### 2.3.5.3.8 Image-update test, one version back for every image

- A test, `tests/images/update.sh`, run in the sandbox (amd64) and once on the test Pi (arm64), for **every image**
  in the lock: the upstream ones (nginx, Step-CA's base, Keycloak, Postgres, OpenBao, Fluent Bit, AdGuard,
  oauth2-proxy, cosign) and fabric's own published ones (adguard, bind9, freeradius, kea, keycloak, samba, stepca,
  webui).
- For each: pin the **previous version**, by digest (the previous patch release on the image's tracked line for an
  upstream image, the previous published build for fabric's own), and deploy. Then check that `fabricctl images
  status` shows the update, `fabricctl images update` applies it, the service is healthy and the running digest is
  the lock's; then that **rollback** returns the previous one; then update again.
- The previous versions are listed in a test fixture (`tests/images/previous.yaml`), each pinned by digest and
  refreshed when the lock moves. An image whose track has no earlier patch is listed as skipped, with the reason.

### 2.3.5.3.11 Impact assessment

- **Architecture:** a scheduled job for the first time (one systemd timer, fabric's own); a reload table beside the
  certificates table; one new setting asked (`cert_root_ca_days`, now used); `landing_page_cname` gets a default;
  for public certificates, one new container (lego) and no new port.
- **Breaking changes:**
  - **Short certificates make renewal load-bearing:** if the timer stops, services fail within 47 days. Mitigated by
    17 days of nightly retries, warnings from 7 days left, a failure in `fabricctl doctor`, and the upgrade and
    sandbox tests renewing for real. Renewing every 30 days means every service reloads or restarts about once a
    month, at night.
  - **The info page moves:** `<domain>` now redirects; anything that used the page there still reaches it.
  - **Upgrading re-issues every service certificate once** and reloads or restarts their services: a few seconds per
    service during `fabricctl setup`, as any certificate change today.
  - **Public certificates** (2.3.5.3.15): a new container (lego, pinned), a Cloudflare token and an ACME account
    key in OpenBao, an HTTPS fetch endpoint for machines, and a relaxation while any machine holds the shared
    wildcard. Off by default: nothing changes for an install that does not turn it on.
  - **ACME on the LAN** (2.3.5.3.14): one more path into the CA; its names are limited to the
    domain, its certificates are short, and every issue is in the CA's log.
  - Changed defaults: `cert_service_days` 365 → 47 (and `cert_renew_after_days`, new, 30); `cert_acme_lifetime_hours`
    720 → 1128 (47 days); the root's lifetime from a fixed 10 years to the setting (the
    same default); `cert_root_ca_days` 1825 → 3650 (unused until now, so nothing changes for existing installs).
  - Design chapters changed: 1.5.1 (renewal, lifetimes), 1.5.2 (the settings), 1.4.2 (the info page), 1.2.9 (the
    timer under `services`), 1.14.2 (the update test), 3.1 (the release procedure), 3.3.2 and 4.4.4 (where the
    instructions are).
- **Scope creep risk:** low to moderate. The pieces are separate and each is small; the risk is in the tests (an
  upgrade run on the Pi takes about an hour, and finding a previous digest for seventeen images is fiddly). Not in
  scope: email alerts, automatic CA replacement, per-user certificates. **Public certificates (2.3.5.3.15) make
  0.6.3 noticeably larger:** a new container, a secret, a fetch endpoint and its tests; they come last in the order
  of work so the rest can be released without them if they slip.

### 2.3.5.3.12 Order of work and how it is tested

1. The upgrade test, run first as **0.6.1 → 0.6.2** (the catch-up), so a broken upgrade path is known before
   anything else changes.
2. Certificate lifetimes, renewal, the timer and the reload table; the warnings; the CA question. Positive and
   negative tests for each entry point (global Rule 9): `fabricctl certs --scheduled`, the Advanced question (a value
   too short; a change on an existing CA, refused), the status, doctor and web UI warnings, and a forced near-expiry
   renewal per service with its reload checked.
3. The info page: nginx, the record, the redirects, HTTP with no redirect; render tests and the sandbox's page
   checks.
4. ACME for the LAN: the provisioner's names and lifetime, the `acme.<domain>` zone and its keys, the commands;
   tested with a real ACME client in the sandbox over http-01 and dns-01, and refused for a name outside the domain,
   a name the client does not control, and a key used for another machine's name.
5. The image-update test and its fixture, run in the sandbox, then on the Pi.
6. Public certificates (2.3.5.3.15): the client container and its plug-in interface, the per-service switch, the
   machine fetch; tested against Pebble in the sandbox (positive and refusal cases), then once against Let's
   Encrypt's staging on the test Pi with the owner's token and test name.
7. The riding-along items; the full sandbox; then the release candidate on the test Pi, with the upgrade test
   0.6.2 → 0.6.3, the image-update test (arm64) and the host suite.

### 2.3.5.3.13 Revised: the 47-day cadence (owner, 2026-10-08)

The owner wants fabric ready for the CA/Browser Forum's schedule for publicly trusted certificates: at most 200
days from 15 March 2026, 100 days from 15 March 2027 and 47 days from 15 March 2029 (domain validation reused for
10 days by then), with a 30-day renewal cycle under full ACME automation as the industry's advice. That schedule
binds public CAs; certificates from fabric's own CA, trusted because a person installed its root, are not held to
it, but fabric follows it anyway so renewal is exercised all the time and nothing changes in 2029. For all three
kinds of certificate the owner named:

- **fabric's own service certificates:** 47 days, renewed at 30 days old (2.3.5.3.3, replacing the first proposal's
  90 days with 30 left);
- **other machines on the LAN:** ACME from fabric's CA, in 0.6.3 (2.3.5.3.14);
- **public certificates for a public address:** in 0.6.3 too (2.3.5.3.15, pulled forward the same day). The
  owner's roots stay offline as they are.

### 2.3.5.3.14 ACME for other machines on the LAN

Machines fabric does not run — a Proxmox host, a NAS, a printer, a server — get certificates from fabric's CA
automatically, with any standard ACME client (certbot, acme.sh, lego, Proxmox's own).

- **The provisioner:** Step-CA's ACME provisioner (already configured) at `https://<hostname_stepca>/acme/acme/directory`,
  issuing **47-day** certificates (`cert_acme_lifetime_hours` 1128) for names **under fabric's domain only** (a
  Step-CA name policy), RSA or EC as the client asks. Clients renew at 30 days old, as their defaults allow.
- **http-01** for machines with a web server on port 80: nothing to set up beyond trusting fabric's root.
- **dns-01** for machines without one: a dynamic zone **`acme.<domain>`** (like the DHCP subzone, never a rendered
  zone, 2.1.4.1). `fabricctl acme enroll <name>` adds `_acme-challenge.<name>.<domain> CNAME
  <name>.acme.<domain>` to the rendered zone and makes a TSIG key that may change only `<name>.acme.<domain>`'s TXT
  record; `fabricctl acme list` and `fabricctl acme remove <name>` show and undo it, and the web UI's PKI page does the
  same (permission `pki:issue`). The key is shown once, for the client's settings.
- **Instructions** per client in Volume 4 (4.5): certbot, acme.sh, Proxmox; the info page links to them.
- **Seen and warned like the others:** certificates issued over ACME are listed on the PKI page from the CA's
  database, marked "renewed by its machine", with the same 30-day "expires soon" mark — a machine whose client stopped
  renewing shows up there.
- Not in 0.6.3: EAB (external account binding) and per-client limits beyond the name policy; Step-CA's ACME accepts
  any client on the LAN that proves control of a name, which is ACME's model.

### 2.3.5.3.15 Public certificates: a public wildcard beside the private CA, in 0.6.3

First proposed as designed now and built at its milestone; **the owner pulled it into 0.6.3 the same day**, and
chose what it covers (2026-10-08).

- **Two chains, side by side.** Step-CA stays fabric's **private** CA (under fabric's own root, or as an
  intermediate under the owner's offline root, 3.5): everything internal keeps using it — the DC's LDAPS, Postgres,
  OpenBao's listener, FreeRADIUS and 802.1X, device and people certificates, ACME for LAN machines (2.3.5.3.14).
  It does **not** become a public intermediate: public CAs issue subordinate CAs only to audited operators, so no
  chain from a public root to fabric's CA is possible. **Public** certificates come from Let's Encrypt (or any ACME
  CA) through an ACME client fabric runs.
- **The name: one wildcard**, `*.<domain>` and `<domain>` (for example `*.lan.j-j.family`), when fabric's domain sits
  under a public zone the owner controls. Every public certificate is published in Certificate Transparency logs; a
  wildcard shows only itself, never the host names under it. One renewal covers every service.
- **How:** an ACME client in its own pinned container (lego), **DNS-01 through Cloudflare's API** (the owner's DNS
  provider; others as plug-ins behind one interface), so no port is opened to the internet and the names need not
  resolve publicly. The API token — a Cloudflare token limited to DNS edits on that one zone — is asked once and kept
  in OpenBao, never on a command line. The ACME account key is kept the same way.
- **Off by default; asked in setup's Advanced**, and turned on or off later from the web console (admins) or
  `fabricctl certs public`. Until it is on, the private CA covers everything, as today. Turning it off goes back to
  the private CA for every service, at once.
- **Which services use it — customizable:** each browser-facing service (the web UI, Keycloak's sign-in, AdGuard,
  OpenBao's UI, the info page, the certs host (gone since 0.7.0: the CA is on the info page, 1.5.1.5), Step-CA's
  front page) has a setting, `public` or `private`, default
  `public` once public certificates are on. Internal-only services (LDAPS, Postgres, RADIUS, the federation endpoint's
  mutual TLS) are always `private`: they are not offered the choice.
- **Renewal:** on the same timer and cadence as the service certificates (2.3.5.3.3): at 30 days old, which holds
  whether the public CA issues 90, 47 or fewer days; the same reload table, the same warnings (7 days left, a failed
  run) in status, doctor and the web UI. Let's Encrypt's rate limits are far above one wildcard a month; a failed
  attempt backs off to the next night.
- **Other machines on the LAN — customizable per machine** (`fabricctl acme enroll <name> --cert private|public|wildcard`,
  and on the PKI page):
  - `private` (the default): fabric's CA over ACME, as 2.3.5.3.14;
  - `public`: fabric obtains that machine's **own public certificate** (`<name>.<domain>`) through the same client;
    its name appears in the public CT logs, which the enroll command and page say before it is chosen;
  - `wildcard`: the machine gets **the shared wildcard** — the same private key as fabric's own pages, so a machine
    that leaks it exposes them all; shown as a relaxation (status, the web UI) for as long as any machine has it.
  - For `public` and `wildcard`, the machine **fetches** its current certificate and key from fabric over HTTPS with
    its own token (`https://<hostname_certs>/machine/<name>/` as proposed; `hostname_certs` is gone since 0.7.0
    (1.5.1.5), so the host for this path is settled when 2.1.5.9 is built, mutual-TLS or bearer token, its own only), using a
    small script fabric provides (with instructions for Proxmox's `pveproxy`, a NAS, nginx and Apache in 4.5); fabric
    never logs in to the machine. A fetch is logged; a machine that stops fetching shows on the PKI page as its
    certificate ages.
- **Also for hosts outside the LAN** (the edge machine, 2.1.9.10): the same per-name fetch, so the edge stack can use
  a public certificate fabric renews, without fabric running it.
- **Tests without the owner's domain:** in the sandbox against **Pebble**, Let's Encrypt's test ACME server, with its
  test DNS server standing in for Cloudflare behind the same plug-in interface: issue, renew, the per-service switch,
  the machine fetch, and the refusals — a token for another zone, a token without DNS edit rights, a machine fetching
  another's certificate, a name outside the domain, Cloudflare unreachable (the private certificate stays in use and
  the failure is shown). **On the test Pi**, once, against **Let's Encrypt's staging** environment with a real
  Cloudflare token for a test name under the owner's zone; the owner provides the token (typed into setup, never into
  a command line) and the name.

### 2.3.5.3.16 Dynamic DNS for public records at Cloudflare, in 0.6.3

Added by the owner the same day (2026-10-08): the house's public address is dynamic, and the owner hides it behind
Cloudflare's proxy. Today a dynamic-DNS client on the edge machine keeps the records current, outside fabric
(2.3.1.10); fabric takes this over, with the same Cloudflare token as public certificates (DNS edit on one zone).

- **What is kept current: a list the owner sets** — each entry a name in the public zone, its **proxy setting**
  (`proxied` for web services behind Cloudflare, `dns-only` for anything Cloudflare cannot proxy, such as the
  WireGuard endpoint) and an optional TTL. fabric creates a missing record and changes only the **address** of an
  existing one; it never changes a record's proxy setting on its own (a difference from the list is reported, and
  fixed only when the owner applies the list). A `dns-only` record is shown, in the list and in status, as exposing
  the house's address. Records not in the list are never touched.
- **IPv4 only for now** (A records), like the rest of fabric (2.1.6.29); AAAA with the IPv6 design.
- **Finding the address:** every **5 minutes**, from Cloudflare's trace (`https://1.1.1.1/cdn-cgi/trace`), cross-checked
  with a second source before anything is changed (an address that is private, or that the two sources disagree on,
  changes nothing and is reported). A record is written only when the address really changed.
- **Where it runs — selectable, the core host by default** (`ddns_runner: core | external`):
  - `core`: a timer on the fabric host (`fabric-ddns.timer`, fabric's own unit like the certificate timer);
  - `external`: another host (the edge machine) runs a small updater fabric provides (a pinned container or a
    script, 4.4), which fetches its list from fabric over HTTPS with its own token (the machine fetch of
    2.3.5.3.15) and reports each run back, so fabric still shows the state. The token for that host is its own,
    scoped the same way; fabric never logs in to it. Only one runner is active at a time: switching moves it.
- **Seen and warned:** the current address, the last check and the last change per record in `fabricctl status`,
  the web console (a DNS page section) and `fabricctl ddns status`; a failed update, a token refused, or no report
  from an external runner for 30 minutes is a warning; `fabricctl doctor` fails while any listed record points at an
  old address. Changes are in the audit log.
- **Commands and pages:** `fabricctl ddns list | add <name> --proxied|--dns-only | remove <name> | status | run`
  and the same on the web console (admins, a new permission `dns:public`); off until the first record is added.
- **Tests:** in the sandbox against a stand-in for Cloudflare's API (the same plug-in interface as DNS-01) and a
  stand-in trace: a changed address updates only listed records, keeps each proxy setting, writes nothing when
  unchanged, refuses on disagreeing or private addresses, reports a refused token, and an external runner's reports
  arrive; on the test Pi once against the real API with the owner's token on a test record.
- **Decision this records:** 2.1.4.4 — fabric keeps a list of public records at Cloudflare pointed at the house's
  current IPv4 address, proxy setting per record, checked every 5 minutes, run on the core host by default or on
  another host the owner selects. It ends the edge machine's own DDNS client (2.3.1.10 updated when built).
- **Impact:** one more timer, one more use of the Cloudflare token (still one token, DNS edit on one zone), one new
  permission; nothing changes until a record is added. Order of work: with the public certificates (step 6 of
  2.3.5.3.12), since both use the same Cloudflare plug-in.

### 2.3.5.4.2 Vendor facts, and where they come from

- **Step-CA's SCEP provisioner** ([smallstep: provisioners, SCEP](https://smallstep.com/docs/step-ca/provisioners/#scep)):
  the fields `challenge`, `forceCN`, `minimumPublicKeyLength`, `includeRoot`, `excludeIntermediate`,
  `encryptionAlgorithmIdentifier` (0 DES by default, 2 AES-256-CBC), `decrypterCertificate`, `decrypterKeyPEM`,
  `decrypterKey` (a KMS URI), `decrypterKeyPassword`; "most SCEP clients use HTTP", hence `insecureAddress`; the
  endpoint `/scep/<provisioner>`. The page says the CA needs an RSA intermediate; the source of the pinned 0.30.2
  ([authority/provisioner/scep.go](https://github.com/smallstep/certificates/blob/v0.30.2/authority/provisioner/scep.go),
  [scep/authority.go](https://github.com/smallstep/certificates/blob/v0.30.2/scep/authority.go)) shows that a
  provisioner with its own decrypter key uses it to decrypt and to sign its answers (one key for both) and returns its
  certificate first in `GetCACert`: so fabric's EC intermediate stays, with an RSA "RA" beside it. That reading is the
  code's, not a documented promise; the `pki` suite's Step-CA run is what proves it.
- **Webhooks** ([smallstep: webhooks](https://smallstep.com/docs/step-ca/webhooks/); source
  [authority/provisioner/webhook.go](https://github.com/smallstep/certificates/blob/v0.30.2/authority/provisioner/webhook.go),
  [webhook/types.go](https://github.com/smallstep/certificates/blob/v0.30.2/webhook/types.go)): kinds `SCEPCHALLENGE`
  (body `scepChallenge`, `scepTransactionID`, `x509CertificateRequest`; answer `{"allow": true}`) and `NOTIFYING`
  (body `x509Certificate` with `raw`, and `scepTransactionID`); the URL must be `https`; each call has 10 seconds and
  is retried once on a transport error or a 5xx; the signing secret, bearer token and basic auth are `json:"-"`, so a
  webhook written in `ca.json` carries none of them (they live in Step-CA's admin database only); Step-CA's webhook
  client presents the CA's own TLS certificate when the server asks for one (`ca/ca.go`: the webhook transport takes
  the CA's client TLS configuration).
- **Android and PKCS#12 ciphers:** Android added PBES2 (AES) PKCS#12 keystores through a Mainline update
  ([AOSP change, bug 230750823](https://android.googlesource.com/platform/libcore/+/feeff5ff784%5E%21/)); Android 11
  and older are reported to refuse OpenSSL 3's default PKCS#12 with a misleading "wrong password"
  ([IPFire community](https://community.ipfire.org/t/openvpn-android-certificate-p12-password-wrong/10384),
  [openssl-users, 2023-03](https://mta.openssl.org/pipermail/openssl-users/2023-March/015987.html)). No official
  version table was found: the cut-off at Android 12 is the best reading, to be confirmed on real phones.
- **Apple's profile payloads** (`com.apple.security.scep`, `com.apple.security.root`, `com.apple.wifi.managed`,
  `com.apple.firstactiveethernet.managed`): Apple's Device Management pages could not be read by the tools at hand
  (they render by script); the keys used are the long-standing ones. `CAFingerprint` is left out for that reason
  (2.3.5.4.4).

### 2.3.5.4.3 Choices made while building

- **The hook's authentication is Step-CA's client certificate**, checked by nginx against this CA and by the hook for
  Step-CA's own names (`hostname_stepca`, `localhost`, `127.0.0.1`), because a webhook in `ca.json` has no secret
  (2.3.5.4.2). Running Step-CA's admin database to get one was rejected: another stateful part, and remote
  provisioner management turned on for one secret.
- **A root service on a unix socket behind nginx** (`fabric-scep-hook`), as `fabric-federation` is, not fabric-agent:
  the agent serves only the web console and every call carries a person's token; the hook is called by Step-CA and
  carries none.
- **The web console is required**: the hooks are on its nginx server, which already asks for client certificates.
- **A challenge is spent on first use, whatever the answer**: a request refused for its name does not leave the
  challenge usable for a second try with another.
- **The CN of an Apple enrolment is the name the person types** (a device-style label, `a-z 0-9 -`); the person is
  recorded in the ledger and the audit, not in the certificate.
- **The RA key is RSA-3072**, 730 days, issued again by setup under 90 days left: long enough not to need a timer of
  its own, short enough to be exercised.

### 2.3.5.4.4 Open points for the owner

1. **Pinning the CA in the Apple profile (`CAFingerprint`).** Without it, a device on a network someone controls during
   enrolment could be answered by a forged SCEP server (which would spend the one-time challenge; it could not issue a
   fabric certificate). Options: (a) leave it out (built); (b) pin it once a lab run shows which certificate Apple
   compares it with. Recommendation: (b), after the lab run.
2. **Signing the profile**, so iOS shows it as verified: (a) unsigned (built); (b) signed with the console's
   certificate. Recommendation: (b) in a later release; it changes nothing in what the profile does.
3. **The legacy PKCS#12 cipher** for Android 11 and older, offered per file (built, said on the form). Options: keep
   it, or drop it and refuse old phones. Recommendation: keep it while such phones are in use; revisit with MDM.

## 2.3.12.1 Proposal: 0.7 — BIND filters DNS, managed in fabric's web console, and AdGuard Home goes

Status: **approved by the owner on 2026-10-08** by answering every question of 2.3.12.1.11 the same day it was
proposed; recorded as 2.1.12.3. The spike (Q8) comes first and its findings are recorded here (global Rules 4 and 5.5). Also
decided: it is **release 0.7**, a milestone of its own (owner 2026-10-08: "it is a new feature and a major
milestone"; first proposed for 0.6.3, moved the same day, and the releases after it moved up one, 1.1.4.6), DoT moves from AdGuard to the resolver (2.1.12.2), and the query log is kept 7 days for
admins only (2.1.12.4). Volume 1's 1.12 takes the design when it is built.

### 2.3.12.1.1 What the owner asked

On 2026-10-08, after weighing AdGuard Home against BIND: BIND stays for authority (TSIG/RFC2136 updates for ACME and
Kea, zone transfers between sites, the AD zone through DLZ, 1.4.1), and the owner is "considering that bind9
replaces adguard with our ui handling" — the filter's engine becomes BIND (response policy zones), and the lists,
rules, per-client policy, query log and statistics move into fabric's web console. Target: 0.6.3 at first, then **0.7** (owner, the same day).

### 2.3.12.1.2 How it works today

AdGuard Home answers clients on `host_ip:53`, filters, sends fabric's domains to BIND (`bind_dns_port`, 5053 with the
filter on) and internet names to Cloudflare over DoH (1.12.1, 2.1.12.1). Its own UI, behind oauth2-proxy and the
`dns:filter` permission, owns the lists, upstreams, rules and clients after the first deploy. BIND is
authoritative-only; nginx sends DoH (`dns.<domain>/dns-query`) to BIND, so DoH answers fabric's names only.

### 2.3.12.1.3 The resolver: a second BIND

- **A second BIND instance, `bind9-resolver`**, from the same `fabric/bind9` image with its own config: recursion on,
  for `dns.allowed_clients`' equivalent (`lan_cidr`, `fabric_subnet`, `security.firewall_allow`) only. The
  authoritative BIND stays authoritative-only (1.4.1.1): one server answering both is the cache-poisoning
  anti-pattern, and keeping them apart means a bad list or a resolver restart never touches the zones ACME, Kea,
  federation and AD depend on.
- On `fabric_net` with a fixed address (`ip_resolver`), its own unit under `fabric.target`, no capabilities
  (unprivileged ports inside, Docker publishes `host_ip:53` TCP/UDP), read-only root, memory limit
  `resolver_mem_limit` (budget: AdGuard's 256 MB, measured in the spike, 2.3.12.1.11 Q8).
- **Fabric's zones** are forwarded to the authoritative BIND (`forward only` per zone: this site's domain, the
  organisation's, linked sites' secondaries, the reverse zones, the AD zone) — the same set AdGuard is given today
  (`fabriclib/dns_filter`). Answers for them are never filtered (RPZ `passthru` for each fabric zone, as AdGuard's
  `$important` allow rules do now).
- `bind_dns_port` keeps its meaning (the authoritative BIND, 5053 with the filter on), so federation links,
  RFC2136 clients and their settings do not change.
- With `dns_filter: none`, the resolver is still not run: the authoritative BIND takes `host_ip:53` as before 0.6.0
  and internet names are the router's business (unchanged behaviour).

### 2.3.12.1.4 Block lists as response policy zones

- A list is a **response policy zone** (RPZ) in the resolver, made by fabric from the list as published.
- **The catalogue is AdGuard's** (owner 2026-10-08: "all the filter lists that adguard comes with, added and
  downloaded on demand"): the console reads AdGuard's HostlistsRegistry index (`filters.json`) live when it is
  opened, and shows every list with its name, description, category and home page from the registry's metadata (the
  registry carries no licence: 2.3.12.1.16). Adding one downloads it at once; any other URL can be added by hand. New lists in the registry appear
  without a fabric release. Offline, the catalogue is unavailable and lists already added keep working (Q13).
- **Formats, converted to RPZ:** RPZ as is; hosts files (`0.0.0.0 name`, `127.0.0.1 name`); plain domain lists;
  adblock-style DNS rules — `||name^` blocks the name and every name below it, `@@||name^` allows it (an RPZ
  `passthru` that wins over the list's own blocks). Rules RPZ cannot express are **skipped and counted**, never
  guessed: regular expressions, AdGuard's modifiers (`$dnsrewrite`, `$client`, `$denyallow`, `$dnstype`,
  `$badfilter`, `$ctag`...) and cosmetic rules. `$important` is dropped: in RPZ fabric's own rules already win. The
  console shows, per list, rules converted and rules skipped.
- Lists are fetched over HTTPS by a fabric timer (`fabric-dns-lists.timer`, daily, and on demand from the console),
  converted, checked (`named-checkzone`, a size limit, a minimum entry count so a truncated download never empties a
  list), written atomically and reloaded only when changed. A failed fetch keeps the last good copy and shows on
  Overview.
- Order of evaluation: **fabric's zones (passthru) → the owner's allow rules → the owner's block rules → lists**,
  first match wins (BIND's RPZ order).
- A blocked name answers **NXDOMAIN** (Q5).
- Default list: the **AdGuard DNS filter** (Q2), as on 0.6.x, so an upgrade blocks what it blocked before.

### 2.3.12.1.5 Policy per client

RPZ matches on the client's address (`rpz-client-ip`), so a policy is: a **client group** (addresses or subnets,
named in the console), the lists that apply to it, and its own allow/block rules. One built-in group, *everyone*,
takes the default lists. In 0.7 groups are by address and subnet (2.3.12.1.11 Q4); groups from fabric's device
inventory, 802.1X roles and DHCP scopes follow with Kea in 0.8, which is where this design gains on AdGuard's
separate client list.

### 2.3.12.1.6 Upstreams, DoT and DoH

- **Upstream:** BIND forwards over **DoT** (BIND 9.20 ESV, 2.1.1.5) to Cloudflare by address
  (`1.1.1.1`, `1.0.0.1`, name `cloudflare-dns.com` verified), replacing DoH by address — the same privacy, no
  bootstrap resolver. BIND does not forward over DoH. To be proven in the spike (2.3.12.1.11 Q3). `[]` = no
  forwarders (full recursion from the root servers) is offered as a setting; offline installs set the resolver to
  answer fabric's zones only.
- **DoT for clients (2.1.12.2, moved):** the resolver listens on 853 with the DNS name's service certificate, or
  the public wildcard when that is on (2.1.5.9). 853 joins `ports` (consent) only with the filter on, as decided.
- **DoH for clients:** nginx's `dns.<domain>/dns-query` moves from the authoritative BIND to the resolver, so DoH
  clients get internet names and filtering too. Doctor's DoH check (2.3.1.11.6) is unchanged.

### 2.3.12.1.7 The query log and statistics

- The resolver logs queries and RPZ hits (`querylog`, category `rpz`) to a log file on its data volume.
  `fabric-agent` reads it incrementally into fabric's Postgres (a `dnslog` database: time, client, name, type,
  answer, policy and list that matched). Fluent Bit forwarding (1.15.1) sees the same lines, unchanged.
- **Retention (2.1.12.4):** entries 7 days, then deleted hourly. Statistics (per hour: queries, blocked, by list;
  top blocked names) are kept without client addresses, 90 days (Q6).
- **Who reads it:** the query log names who looked up what, so it needs a new permission, `dns:querylog`, in the
  admin bundle only. `dns:filter` (network operators) manages lists, rules and groups and sees the statistics.

### 2.3.12.1.8 The web console's DNS filter tab

Replaces AdGuard's UI and its sign-in (`adguard.<domain>`, oauth2-proxy `adguard-auth`, client `fabric-adguard`):

- **Overview:** queries and blocked per hour, top blocked names, top clients (counts), each list's last fetch.
- **Lists:** add (RPZ URL), enable per group, fetch now, remove.
- **Rules:** allow and block names per group; from a query-log line, one click *allow* or *block*.
- **Groups:** name, addresses and subnets, lists, rules.
- **Query log** (`dns:querylog`): search by client, name, blocked only; each blocked line names the list or rule.
- **Settings:** upstreams.

Every change is a fabriclib function the route calls (global Rule 1), validated there, audited, and applied with a
resolver reload (`rndc reload <zone>` for a rules zone; no full Apply). Settings live in vars (`dns_filter_*`) and
rules/groups in vars too, so a reinstall keeps them.

### 2.3.12.1.9 Moving off AdGuard Home

- An upgrade from 0.6.x with `dns_filter: adguard` **imports** AdGuard's settings from its YAML: upstreams (DoH by
  address mapped to DoT by address where the provider offers it, else reported), user rules that are plain domain
  allow/block rules, persistent clients as groups, safe search per client, and every list by its URL (the same lists,
  now converted, 2.3.12.1.4). Anything that cannot move (blocked services, AdGuard's parental service, rules RPZ
  cannot express) is listed in the upgrade's report and kept in a file beside the backup — never dropped silently.
- Then AdGuard's unit, container, oauth2-proxy unit, Keycloak client and OpenBao secrets are removed, and the
  `fabric/adguard` image is no longer published. `dns_filter` takes `bind` (new default) or `none`; `adguard` is
  read once, as the upgrade's input. The `adguard_*` vars are retired (2.3.12.1.11 Q1 decides whether `adguard`
  stays selectable for one release).
- The upgrade test (2.1.1.36) gains the case: the release before 0.7, with AdGuard and owner rules → 0.7, rules present, filtering
  works, nothing of AdGuard left.

### 2.3.12.1.10 Impact assessment

- **Architectural:** one DNS engine (BIND) in two roles, one sign-in and one UI. Removed: AdGuard's image (and its
  file-capabilities rebuild), oauth2-proxy for it, its Keycloak client, the YAML merge of fabric's and AdGuard's
  keys. Added: the resolver unit, the list fetcher, query-log ingestion and a Postgres database, a console tab,
  a permission.
- **Breaking:** installs on 0.6.x with the filter on (the default) — handled by the import (2.3.12.1.9).
  Lost against AdGuard: regex rules and AdGuard's DNS modifiers (skipped and counted, 2.3.12.1.4), blocked
  services, AdGuard's parental service, DoH upstreams. `dns:filter` changes from "open AdGuard's UI" to "manage the filter in the console". DoH moves from
  the authoritative BIND to the resolver (clients gain internet names). Decisions changed: 2.1.12.1 (revised:
  engine and upstream transport), 2.1.12.2 (paused, then moved to the resolver), 1.12 rewritten.
- **Scope creep: high.** The resolver and lists are small; the query log, statistics and the console tab are the
  bulk — the reason it became 0.7, a release of its own, instead of joining 0.6.3. Order of work: build in this order, each testable on WSL and
  the test Pi — (1) spike, (2) resolver + lists + rules in vars, (3) import from AdGuard, (4) query log and
  statistics, (5) the console tab, (6) safe search (2.3.12.1.14). 0.7 is not
  cut with AdGuard removed and no UI to replace it.

### 2.3.12.1.14 Safe search and adult-content lists

In 0.7 with the filter (owner 2026-10-08). The owner does **not** want services blocked (YouTube and the like), so
there is no blocked-services catalogue, and no schedules (Q9, Q10). Set per client group (2.3.12.1.5): address
groups in 0.7, device groups in 0.8.

- **Safe search: one switch per group, off by default** (owner 2026-10-08: "no sense in limiting one"). Switched on,
  it enforces **every engine below at once, in strict mode**; there are no per-engine switches. The only special
  case is **YouTube**, which can be set to **moderate** instead of strict for that group (Q12). An RPZ zone kept by
  fabric rewrites each engine's search names to the provider's enforced name.
- **The console names every site it affects:** the switch reads *Strict safe search* and, beside it, lists each
  engine it enforces (Google, Bing, DuckDuckGo, YouTube, Yandex, Pixabay, Ecosia), with YouTube's
  strict/moderate choice next to it — generated from the same table fabric enforces, so the label can never drift
  from what the zone does. Engines that cannot be forced (below) are named there too, as not covered.

  | Engine | When the switch is on | Enforced name |
  |---|---|---|
  | YouTube | strict, or moderate per group (Q12) | `restrictmoderate.youtube.com`, `restrict.youtube.com` |
  | Google | strict | `forcesafesearch.google.com` |
  | Bing | strict | `strict.bing.com` |
  | DuckDuckGo | strict | `safe.duckduckgo.com` |
  | Yandex | strict (family search) | the address `213.180.193.56` (52 names) |
  | Pixabay | strict | `safesearch.pixabay.com` |
  | Ecosia | strict | `strict-safe-search.ecosia.org` (confirmed by the spike, 2.3.12.1.16) |

  Google's names are its 267 `www.google.<country domain>` sites; YouTube's are five (2.3.12.1.16). Engines with no DNS
  mechanism (Brave Search, Startpage) cannot be forced; a group that must not use them blocks them with a rule. It
  works for HTTPS: the browser still talks to the provider, with the provider's real certificate.
- **Adult content** is a list like any other, chosen from the catalogue for a group (Q11). AdGuard's own parental
  service (a hashed lookup at AdGuard's servers) has no BIND equivalent and is not copied.
- **Import:** AdGuard's per-client safe search maps to the group's switch (2.3.12.1.9).
- **Tests:** with the switch on for a group, every engine's name answers its strict enforced name, and YouTube's
  the moderate one when the group chose it; with it off, or for another group, every name is unchanged; the
  console's list of affected sites equals the enforced table. Refused: safe search on an unknown group, a YouTube
  level other than strict or moderate.

### 2.3.12.1.16 The spike's findings (WSL)

Run 2026-10-09 in WSL (Docker, amd64), `spikes/dns-filter/`: Debian 13's **BIND 9.20.29** on the base fabric's BIND
image is built on, 4 worker threads (the test Pi's cores). Every check passes in both view modes (22 in
`run.sh`). The test Pi (arm64, 4 GB) is still to run (Q8's memory and SD-card questions).

**What works as designed**

- Cloudflare over **DoT** by address with the certificate's name verified (`tls` with `remote-hostname` and
  `ca-file`); DNSSEC still validated through it (the `ad` flag).
- **DoT (853) and DoH (`/dns-query`) towards clients** from BIND itself, filtered like plain DNS.
- fabric's zone forwarded to the authoritative BIND and **never filtered**: a list naming a fabric name is beaten by
  the `fabric.rpz` passthru zone listed first. The resolver needs `validate-except` for fabric's zones, or a
  private zone fails DNSSEC validation (true of a real domain's unpublished subdomain too).
- The owner's allow beats a list; the owner's block; a client outside the allowed networks is REFUSED.
- **Safe search** by RPZ rewrites, for one group only. AdGuard Home's own rule files give the names: Google 267
  (`www.google.<country domain>`, the list Google publishes as `google.com/supported_domains`), YouTube 5 (`www`,
  `m`, `youtubei.googleapis.com`, `youtube.googleapis.com`, `www.youtube-nocookie.com`), Yandex 52 (answered with an
  address, `213.180.193.56`, not a name: RPZ local data does that too), Bing, DuckDuckGo, Pixabay, and **Ecosia**
  (`www.ecosia.org` → `strict-safe-search.ecosia.org`, so it joins the table, 2.3.12.1.14). fabric keeps its own
  table, built from the providers' published names.
- **The logs carry what the console needs:** the query log names the client and its **view** (= the group); the RPZ
  log names the rule's **zone** (= the list or rule set) — `view kids: rpz QNAME NXDOMAIN rewrite doubleclick.com/A/IN
  via doubleclick.com.list1.rpz`. named must run with `-f`, not `-g` (which ignores the logging statement).

**Lists: the converter**

All 64 lists of AdGuard's catalogue fetched and converted. AdGuard republishes every list in its own DNS syntax, so
one converter covers the catalogue. Beyond 2.3.12.1.4's formats, these map exactly to RPZ and are converted:
`||*.name^` and `||tld^` (a whole TLD), `$denyallow=a|b` (the block plus passthru for the exceptions),
`$dnsrewrite=<name>` (a block: AdGuard points it at its block page), `$badfilter` (cancels the rule), `||1.2.3.4^`
(an `rpz-ip` trigger on the answer's address). Still skipped and counted: wildcards inside a name, regular
expressions, `$dnstype`, unanchored patterns.

- The **AdGuard DNS filter**: 179,717 lines → 178,896 names blocked, 11 allowed, **714 skipped (0.4%)**.
- 51 of the 64 lists convert with nothing skipped; the most skipped is HaGeZi's DNS Rebind Protection (all regex:
  it could become fabric's own `rpz-ip` setting for private ranges, later).
- The registry's metadata has **no licence field** (name, description, home page, tags, languages, URLs only); the
  console shows the home page, and 2.3.12.1.4 and Q2 are corrected accordingly.

**Memory: the finding that changes the design**

BIND accepts neither RPZ zones nor forward zones through `in-view`: a view (a client group) must load its own copy
of every list it applies. About **0.53 KB per RPZ record** (`||name^` is two records: the name and `*.name`):

| Views : lists | RPZ records | Load | Memory |
|---|---|---|---|
| 1 : none | 0 | 0.8 s | 8 MiB |
| 1 : AdGuard DNS filter | 358k | 1.5 s | 193 MiB |
| 2 : AdGuard DNS filter | 716k | 1.6 s | 380 MiB |
| 4 : AdGuard DNS filter | 1.43M | 1.6 s | 754 MiB |
| 1 : OISD small | 116k | 1.0 s | 70 MiB |
| 1 : HaGeZi Pro | 389k | 1.5 s | 206 MiB |
| 1 : OISD big | 480k | 1.7 s | 262 MiB |
| 1 : AdGuard DNS filter + HaGeZi Pro | 747k | 2.3 s | 388 MiB |

So a group as a full view costs a whole copy of the lists. **Chained views** fix it (`MODE=chain`, every check
passes, 2 groups in **194 MiB** instead of 381): a group's view holds only its own policy — safe search, its own
rules, its own extra lists — and forwards everything else to the main view, which holds the shared lists once.
- A group's **allow** is a forward zone for that name straight to the upstream, past the main view's lists
  (`@@||name^` semantics: the name and below).
- A group view must **not validate DNSSEC** (`dnssec-validation no`): its DS lookups for a listed name are blocked by
  the main view and the trust chain breaks (SERVFAIL). The main view validates what it answers; the upstream what a
  group's allows send it.
- A group **cannot switch a shared list off**, only allow names past it (Q14).
- The console shows each list's estimated memory before it is added (records × 0.53 KB, measured again on arm64) and
  refuses one that would pass the resolver's memory limit (Q15).

With Q14 and Q15 answered (2026-10-09), this replaces what 2.3.12.1.3 and 2.3.12.1.5 say about groups: **the
resolver runs chained views** — the main view (*everyone*) holds fabric's zones, the owner's rules and every list on
*everyone*; each group's view holds its safe search, its own rules and extra lists, and forward zones for the names
it allows, and forwards the rest to the main view; a group never switches a shared list off. `resolver_mem_limit`
is **384 MiB**, and the console shows each list's estimated cost and refuses one past it. Volume 1's 1.12 takes

### 2.3.12.1.18 Step 2 built: the resolver, its lists and the owner's rules

Built 2026-10-09 on `rc/0.7.0` (design 1.12.2): `bind9-resolver` with its own account (`fabric-resolver`, 613),
`dns_filter/convert_list` (the spike's converter, which gives the same result on the AdGuard DNS filter: 357,872

Choices made in building it, within the recorded decisions:

- **The resolver's own account** rather than BIND's: it never reads the authoritative BIND's keys, zones or the AD
  zone's database.
- **The host's CA bundle**, mounted read-only, verifies the upstream's DoT certificate: fabric's bind9 image carries

- **A list's zone is named from its URL** (`<id>.list.rpz`), so reordering or renaming lists never reloads one.
- **`rndc reload`, not `reconfig`**, after an apply: reconfig loads only new zones; reload also rereads the changed
  rules zones.
- **A list with no good copy is left out of the configuration**, so the resolver never starts on a missing file.

### 2.3.12.1.19 Step 3 built: the move from AdGuard Home

### 2.3.12.1.20 Step 4 built: the query log and statistics

Built 2026-10-09 on `rc/0.7.0` (design 1.12.2.13, decisions 2.1.12.4 and 2.1.12.5). The owner kept Postgres when a
SQLite file on the host was offered, and chose the 5-minute timer with reads on demand.

Choices made in building it, within those decisions:

- **No client library:** fabric's Python reaches Postgres as its other Postgres work does, `psql` in the container
  over the local socket with the SQL on stdin; the host gains no package, the query log no password. Search terms
  are checked, then bound as `psql` variables and quoted by `psql` (`:'name'`), never formatted into SQL — the
  suite sends SQL as a client address and finds it refused and the table intact.
- **Its own role and database:** `fabric_dnslog` owns `dnslog`, `CONNECT` revoked from `PUBLIC`, so Keycloak's role
  (and any other) cannot read who looked up what; made by `fabric_admin`, Postgres's own admin.
- **One row per query**, the RPZ line marking it (same client, port and name within 2 seconds), rather than two
  tables joined at read time: the searches and "blocked only" stay one index scan.
- **Statistics recomputed** for each hour and day a run touched, from the rows, instead of counters added up: a
  rewrite line read a run after its query cannot leave a count wrong.
- **The place in the files** (inode and offset) is root's, beside the resolver's folders, and moves only after
  Postgres took the lines: a refusal re-reads them; nothing is lost or counted twice.

`tests/resolver/querylog.py` (22 checks) passes against the pinned Postgres 18, and `tests/resolver/run.py` checks
that the job parses every line the real BIND wrote. Left for step 5: the web console's tab on `GET /v1/dns-filter`
and `POST /v1/dns-filter/querylog`.

### 2.3.12.1.21 Step 5 built: the web console's tab

Built 2026-10-09 on `rc/0.7.0` (design 1.12.2.14): the *DNS filter* tab with the overview (statistics), lists (AdGuard's
catalogue by group, a list by URL, fetch now), rules, the query log (search; *Allow* on a blocked line, *Block* on
another) and settings (upstreams). Each change is saved and applied at once, like the DHCP tab's.

Found while building it, and solved within the design:

- **fabric-agent cannot fetch.** Its unit allows only localhost and fabric's subnet (by design), and an apply it starts
  runs in that sandbox: a list added in the console could not be downloaded until the nightly job. The agent now
  starts the lists job's own unit (`systemctl start fabric-dns-lists.service`), and the job applies when a list it
  fetched is not in the running configuration yet (`refresh_lists`).
- **The catalogue is read by that job too** (daily and on demand) and kept beside the lists, instead of "live when the
  console is opened" (2.3.12.1.4): the agent cannot reach AdGuard's registry. It is still never shipped with a release

### 2.3.12.1.22 Client addresses through Docker's port mapping (test Pi)

Checked 2026-10-10 on the test Pi (fabric 0.6.3-rc.64), before groups were built (step 6): groups match a client by its
address (2.3.12.1.5), so the resolver must see the client's real address, not Docker's gateway. A throwaway BIND
container (fabric's bind9 image, `-p <host_ip>:5354:53` for UDP and TCP, query logging on) was queried from a PC on
the LAN and removed afterwards.

- **Result:** both UDP and TCP queries were logged from the PC's own address (`192.168.4.106`), not from `docker0`'s
  `172.17.0.1`. Groups by address work through the port mapping.
- **Why:** fabric's hardened `daemon.json` sets `userland-proxy: false` (1.2.6), so the mapping is kernel NAT and keeps
  the source address. With the userland proxy (Docker's default), every query would come from the gateway.
- **The gap:** the hardening is the `runtime` host change, which the owner can decline at setup or undo later. Then
  every client falls into the default policy and the query log shows one address. Step 6 therefore lists
  "client addresses hidden: Docker's userland proxy is on" among the relaxed settings (Rule 10: status and the
  console show it) when groups exist and `userland-proxy` is not `false`. Rootless Docker hides them the same way
  (1.2.6), and is not built.

### 2.3.12.1.23 Step 6 built: client groups and safe search

Built 2026-10-10 on `rc/0.7.0` (design 1.12.2.15): client groups as chained views, strict safe search for everyone and
per group, AdGuard's persistent clients and safe search imported, the console's **Groups** section. DoT and DoH towards
clients are the rest of step 6, still to build.

Choices made while building it, within the design (none changes a decision):

- **The most specific address wins** when a client is in one group's subnet and another group's address (AdGuard Home
  did the same, so imported clients behave as before). Each group's `match-clients` excludes the more specific entries
  of the others; the same address or subnet in two groups is refused.
- **Everyone has safe search too** (`dns_filter_safe_search`), in the main view after the owner's rules: *everyone* is
  the built-in group of 2.3.12.1.5, and AdGuard's global switch needed a place to go. It reaches every group through
  the chain; a group's own YouTube level is applied first.
- **A group's allow above fabric's zones is refused** (`test` when the domain is `lan.test`, anything under `.arpa`):
  it is a forward zone in the group's view, which does not hold fabric's zones, so it would send them to the internet.
- **`max-ncache-ttl 0` in a group's view**, found needed: a blocked answer from the main view would otherwise be cached
  there, answered again without passing the main view, and logged as a plain query instead of a block. BIND 9.20 takes
  0 (checked: a second blocked query passes the main view again).
- **The query log through the chain:** the main view's copy of a group's query (client `127.0.0.1`) is dropped, and its
  rewrite is put on the group's query (1.12.2.15).
- **A memory guard instead of a refusal at add time** (Q15 asked the console to refuse a list past the limit): a list's
  size is known only after it is fetched, which the agent cannot do. The apply counts every view's lists against 90% of
  `resolver_mem_limit` and leaves out a list that would pass it; the console marks it "left out". (Confirmed by the
  owner on 2026-10-10, with the line at 80%: 2.3.12.1.25.)
- **Docker's userland proxy** listed as a relaxed setting while groups exist and it is not off (2.3.12.1.22).

Corrections found on the way:

- **Google publishes 187 search domains** (`google.com/supported_domains`, 2026-10-10), not 267 as 2.3.12.1.14 and
  2.3.12.1.16 say (that count came from AdGuard Home's rule files, which also hold names Google no longer lists).
  fabric's table follows Google's list. Yandex has 52 names (24 country domains, `ya.ru`, `яндекс.рф`, each with
  `www.`), as the spike found.
- **Every apply removed AdGuard's catalogue** (`lists/catalogue.json`, step 5): the apply's clean-up of the lists folder
  kept only the converted lists and their state, so the console's catalogue was empty again until the next nightly
  fetch. Fixed: the clean-up keeps the catalogue and the memory guard's record.

Tested: `tests/resolver/groups.py` (54 checks, real containers: three clients on their own addresses; strict safe
search answered by Google, Bing, DuckDuckGo, YouTube and Yandex over the internet), `querylog.py` (the group lines in a

### 2.3.12.1.24 Step 6 built: DoT and DoH for clients

Built 2026-10-10 on `rc/0.7.0` (design 1.12.2.16, decision 2.1.12.2): the resolver answers DoT on `host_ip:853` and
DoH behind nginx (`dns.<domain>/dns-query` → `resolver:8053`), both with the DNS name's Step-CA certificate, which
`mint_service_certs` now also copies to `<base>/resolver/tls`. With that, the DNS filter's design is built.

Found while building it, and solved within the design:

- **Setup deploys before it issues certificates**, so a first install rendered the resolver without its TLS listeners.
  The start step renders once more when the certificate has arrived but the configuration does not use it yet
  (`dns_filter/resolver_tls_pending`), before the resolver starts.
- **An upgrade's DNS certificate is current**, so its new copy for the resolver would have waited for the next renewal
  (up to 30 days). The certificates step now issues a certificate when one of its destinations has no copy.
- **DoH clients are answered as everyone**: nginx terminates TLS, so the resolver sees nginx's address. BIND 9.20 can
  read a client's address from the PROXY protocol, but nginx's HTTP proxying (grpc_pass) cannot send it; DoT and plain
  DNS keep the client's address. Recorded in 1.12.2.16, so a group's device is pointed at DoT or plain DNS.
- **Clients must trust fabric's root CA** for DoT and DoH, as for every service. Not checked yet: whether phones'
  built-in encrypted DNS (Android's Private DNS) accepts a certificate from a user-installed root; if not, those
  clients need the public wildcard (2.1.5.9, in the release after 0.7: 2.1.1.42). To test on a phone.

Tested: `tests/resolver/run.py` (DoT with the certificate verified and filtered, DoH as nginx passes it, doctor's DoT
client and its refusal of a certificate for another name), `tests/render.py` (the listeners only with the certificate,
nginx's DoH to the resolver, or to BIND with the filter off).

### 2.3.12.1.25 The memory guard confirmed, at 80% of the limit (owner)

Q15 asked the console to refuse a list that would pass the resolver's memory limit; what was built leaves such a list
out at apply instead (2.3.12.1.23). Asked on 2026-10-10, the owner kept the guard and lowered its line from 90% to 80%

## 2.3.12.2 fabric's own queries hidden from the query log (0.9.5)

What the owner saw on 2026-10-17: a page of the query log filled by `10.255.0.1`, the DC's `samba_dnsupdate`
checking its AD records every ten minutes (the DC runs in the host's network, so it reaches the resolver from the
host's gateway address on fabric's Docker network). Decided as 2.1.12.12, designed in 1.12.3.16, the operator's side
in 4.12.1.6.

Choices made while building (recorded in 2.1.12.12):

- **A search by client shows fabric's own when it lies within one of fabric's own networks.** Within, not overlapping:
  a search for the LAN's `/24` overlaps the host's address but asks for the LAN's devices, so it still hides the host
  (tick the box for both). `0.0.0.0/0` overlaps everything and is not a request for fabric's own either.
- **The totals keep everything; the most blocked names leave fabric's own out.** The statistics never hold client
  addresses (2.1.12.4), so there is no "top clients" list; the one top list is the most blocked names. Its counts come
  from `stats_blocked`, which the collector now fills only from other clients' blocks (the alternative, counting the
  top list from `queries` at each read, would have left `stats_blocked` unread). The own count is read from `queries`
  at each read (7 days kept, the same 7 days shown), so it needs no new table and follows a change of `fabric_subnet`
  at once.
- **Days counted before the upgrade** keep their own blocks in `stats_blocked` until they pass the 7 days shown (a
  day is recounted only when the collector touches it); not migrated, as it fades by itself within a week.
- **The switch is strict:** the agent takes `own` as a JSON boolean only (`"yes"`, `1` refused, saying so), the
  console's box sends `on` or nothing (any other value refused in place of the results), the CLI's `--own` takes no
  value. The older `blocked` term stays as lenient as it was.

Tested: `tests/resolver/querylog.py` (a real Postgres: own hidden by default, shown with the switch, a LAN client
still shown, a search by an own address, the host's address, the statistics' own count and the most blocked names
without fabric's own, the CLI's `--own` and its refusals, a bad switch refused), `tests/resolver/console.py` (the
agent route passes `own` and refuses a non-boolean; the page's box, its note and a bad value), `tests/webui` (the dev
preview: the box hides and shows the sample's own line).

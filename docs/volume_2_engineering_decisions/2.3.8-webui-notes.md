### 2.3.8.3.1 Step 1: the frame and the navigation (2026-10-22)

Step 1 of [1.8.6.8](../volume_1_description_and_architecture/1.8.6-console-redo.md#1868-build-order), as built:

- **The dev preview rewritten:** it had its own copy of every route (`dev_get_page`, `dev_post_*`), which drifted from
  production. It now runs the production `get_page` and `post_action` with a fake agent connection
  (`FakeConnection` in place of the unix socket), so a route or a permission changed in production is what the preview
  shows. Its `--as <bundle>` sets the person's permissions.
- **`tests/webui/test_devserver.py`** checks, among the rest: each bundle's navigation entries against a table written
  out in the test (the oracle), every navigation page opened with its permission and refused (403) without it, every
  old address redirected to its new one, no `<script>`, inline `style=` or `on…=` handler on any page (the strict CSP;
  the pages work with JavaScript off), a form's message shown once and never taken from the address.
- **`tests/webui/test_container.py`** reads a form's message from the page the form goes to (its `_said` helper), and
  takes its container, network, image and mock-Keycloak names from `WEBUI_TEST_ID`, `WEBUI_TEST_NET` and
  `WEBUI_TEST_KC_PORT`, so two worktrees can run it side by side.
- **The inventory** (`scripts/docs/entrypoints.py`) also lists a page per name (`_rest(path, "/x/")` in `get_page`:
  `web:get.x.*`).
- **Checked in the running preview** (the browser pane): the frame at desktop width; at 375 px the navigation folded
  behind Menu, opened with it, and `document.documentElement.scrollWidth` was 375. A zone's records table still
  scrolls inside its card: the lists become cards under 768 px in step 2 (1.8.6.3).
- **Not yet automated:** the 375 px width check; it needs a browser, 2.1.8.15 (built in step 2: 2.3.8.3.2).

### 2.3.8.3.3 Step 3: Apply per page (2026-10-22)

As built: [1.8.6.11.3](../volume_1_description_and_architecture/1.8.6-console-redo.md#18611-as-built).

- **Two changes on one thing in one apply:** the first build checked every change's version at Apply, so a second
  change to the same person (enable, then a group) was refused as "changed since", the first change having changed
  them. A thing an earlier change of the same apply changed is now not checked again (`pending_thing.thing_key`).
- **A person's version missed their details:** the People list's row has no title, department and the rest, so
  another person editing them went unseen at Apply (`tests/samba/domain.py` found it). A person's read is now the row
  and their details (the DC's `get_person` returns them, `person_record.py`, shared with `edit_person`).
- **A thing that cannot be read is a refusal:** the webui container suite has no DC, and holding a machine's change
  there answered 500 (the read of the machines failed on a setting the suite leaves out). Every failure to read what
  a change changes, when it is held or applied, is now a refusal that says why: fail closed, nothing held or run. The
  password policy's version is fabric's own setting (`ad_password_policy`), which Apply writes into the domain.
- **Refusals move to Apply:** a form's values are checked when the change runs (the password policy's checks, a
  removal's name typed back), so a refusal is shown in the queue on the Review, with the change still pending to drop
  or fix; a missing permission is refused at once, when the change is held.
- **Tested:** `tests/samba/domain.py` (fabric-agent's own store and routes against a real DC: held and applied, the
  DC untouched until Apply; discarded; refused when another person changed the thing first, then applied once
  reviewed; a failing change stopping the job with the one after it not run; another page's change untouched;
  refused at Apply without the permission; held per person; a change done at once never held); the webui
  container suite (the real agent over its socket and tokens: the top bar, an Apply refused by fabric-agent without
  a DC to check the caller, fail closed; the policy's own refusals at Apply; holds refused without the change's
  permission); `tests/webui/test_devserver.py` (the flow in the preview, which runs the agent's own store over the
  samples: the bar, the navigation's count, Review, Apply, Drop, Discard, two changes on one person, a one-time
  password shown once on the Review and never again).
- **The webui container suite hung half-way:** it started fabric-agent with its output on a pipe it never read; each
  page now also asks the agent for the person's pending counts, so the log passed the pipe's 64 KiB and every request
  that logged blocked (the next 15 minutes' sessions then expired). The agent's log now goes to a file.
- **Suites that drove the console's route code directly** (`tests/samba/hostgroups.py`, `tests/resolver/console.py`,
  `tests/settings/console.py`) had stand-in handlers without the session message of step 1; they now have `back`,
  and the host-groups forms are applied at once there (the store is the webui suite's).

## 2.3.8.6 Design question: what must follow a person, group or machine moved out of fabric's folders (0.9.1)

**Answered 2026-11-03, option (a): 2.1.6.106.** *Raised 2026-11-02 while building 1.8.8.5 (decisions 2.1.6.98 to
2.1.6.102).* 1.8.8.5's table lists what must follow
an object to any OU; building it found three more things that read only fabric's own folders, none in the table, so
moves are kept inside each kind's folder for now (1.8.8.9.3):

1. **Keycloak** federates the domain's people from `OU=people` (`usersDn`, `keycloak/ensure_ldap_federation`) and maps
   groups from `OU=groups` (`keycloak/ensure_group_mapper`). A person moved to an OU outside `OU=people` disappears
   from Keycloak: no console or SSO sign-in. A group outside `OU=groups` loses its role bundle's mapping.
2. **fabric's own finders**: a person is found under `OU=people` only (`find_person`, `list_people`, FreeRADIUS's
   `check_person` for 802.1X), and a group outside `OU=groups` is taken for one of AD's own (`group_kind`), so fabric
   would refuse to manage it.
3. **The site's Windows baseline GPO and its two admin GPOs** (the 802.1X profile, the SSO allowlist, the ADMX
   editor's settings and controls) are linked at `OU=machines` (2.1.6.84). A Windows machine moved outside it loses
   them; only the access GPOs and the default deny moved to the root (2.1.6.98).

Options, for the owner:

- **(a) Everything follows** (recommended): Keycloak's users from the domain's root with a filter (people only:
  `objectCategory=person`, not fabric's service accounts, not AD's own), its group mapping from the root likewise;
  fabric's finders search the whole domain with the same rules; the baseline and admin GPOs linked at the root,
  denied to the DCs and the fabric hosts as the default deny is (2.1.6.98's pattern). Then any person, group or
  machine moves to any OU, as 1.8.8.5 asks. *Trade-offs:* Keycloak's federation changed on every install (an upgrade
  step, tested both ways); a wider search per sign-in (small at fabric's sizes); the console's move form offers every
  OU.
- **(b) Each kind within its own folder's tree** (what is built now, machines included): an admin's OUs under `OU=people`, `OU=groups`
  and `OU=machines` hold that kind; nothing else changes. *Trade-offs:* not RSAT's "anything anywhere"; an OU at the
  root can only hold other OUs.
- **(c) Machines anywhere, people and groups in their trees:** the GPO part of (a) only. *Trade-offs:* a middle
  that still does not match 1.8.8.5 (a).

### 2.3.8.9.6 Pressure readings, and the thresholds chosen (2026-11-07)

Read on gaming-23's WSL kernel (`6.6.87.2-microsoft-standard-WSL2`, 24 cores, 31 GB) while the sandbox backed off:

| Reading | Value |
|---|---|
| load average, 1 min | 215.9 |
| `/proc/pressure/cpu` some avg60 | 0.08% |
| `/proc/pressure/memory` some avg60 | 0.02% |
| `/proc/pressure/io` some avg60 | 0.37% |
| `MemAvailable` | 86% of `MemTotal` |

The load stays above 200 whatever this distribution runs. Another system sharing the kernel holds it there, while nothing
here waits. The load average also counts tasks waiting on disk. So it cannot say whether this host has room. Pressure
stall information (PSI) measures the share of time at least one task actually waited: for a core, or on memory reclaim
and swap.

- **CPU "some" avg60 at 50%:** a host that is busy but coping shows short waits. Half of each minute with something
  runnable kept off a core means the cores are saturated. A refresh takes 2 to 10% of one core (1.8.9.3), so backing off
  for less would give up freshness for nothing.
- **Memory "some" avg60 at 10%:** a healthy host reads about 0 (above). A tenth of each minute stalled on memory means
  reclaim is already slowing real work, and a refresh's reads add to it. This is far below the point where the kernel or
  an OOM daemon acts, so the cache backs off first.
- **avg60, not avg10 or avg300:** the decision is taken once per refresh, 30 s to 5 min apart. avg10 would follow a
  passing spike, and avg300 would keep a refresh backing off minutes after pressure ends.
- **I/O pressure is not used:** a refresh reads from the DC's memory-mapped database, not much from disk. Disk waits from
  other systems would bring back the load average's fault. Not requested; can be added if a host shows the need.
- **MemAvailable under 15% stays** as a second test. It is the only one a kernel without PSI has. Some Raspberry Pi
  kernels ship PSI off unless `psi=1` is on their command line, and then `/proc/pressure` is absent.

**Results with PSI (2026-11-07, sandbox on gaming-23, `tests/sandbox/read_cache.py --load`, all PASS):** the agent's status line
read `kept reads: this host is medium, 4 held processes; pressure from the kernel's CPU and memory readings (PSI) and available
memory`. With the load average still about 215, CPU pressure read 0.0% and the refresher did not back off: a group added with
`samba-tool` showed after 24 s (161 s and 300 s with the load average, 2.3.8.9.4). Under the test's load, CPU pressure reached
74.67%, the refresher backed off (`under pressure, next in 91 s: CPU pressure 56.7% (from 50%)`), the slowest `/directory/sites`
took 136 ms, every page answered, and nothing was killed. A kernel without PSI is covered by unit tests only: none was at hand.

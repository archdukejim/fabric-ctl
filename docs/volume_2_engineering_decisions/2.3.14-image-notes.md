## 2.3.14.1 Proposal: publishing fabric's own images (2.1.1.21)

Status: **approved by the owner on 2026-10-03, with P1–P4 as proposed** (2.1.14.5, 2.1.14.6, 2.1.14.7, 2.1.14.8; global Rule 5.5: it changes 2.1.14.1,
2.1.14.2 and 2.1.14.3). The owner decided C5 (2.1.1.21) on 2026-10-03: "we will release a container package and
manage its updates".

### 2.3.14.1.1 What changes

Today every host builds eight images itself, from a pinned base and Debian packages: `adguard`, `bind9`,
`dirsrv`, `freeradius`, `kea`, `keycloak`, `stepca` and the web UI (`fabric-web`). That costs the Pi time and
memory at setup, makes hosts differ (each installs whatever packages the archive had that day) and needs the
network at build time. With 2.1.1.21 they are built once, in CI, tested, published and pinned by digest like every
other image; hosts only pull them.

### 2.3.14.1.2 How it works

- **Packaging:** each image's Dockerfile and build files in `packaging/images/<name>/` (2.3.2.1); code that runs
  inside it stays in `src/containers/<name>/`. One build matrix, `packaging/docker-bake.hcl`, lists the eight
  images × amd64 and arm64 (2.1.1.11). Each also builds with a plain `docker build` (global Rule 7.2), documented in
  Volume 3.
- **Publishing:** GitHub Actions builds the matrix on every release and when a base image changes (the watcher
  of 1.14.2), runs a smoke test per image (it starts and reports healthy), and pushes multi-arch images to the
  GitHub Container Registry (`ghcr.io/archdukejim/open-fabric/<name>`, 2.1.1.19), tagged with fabric's version.
- **Pinning:** the published digests go into `images.lock.yaml` through a reviewed commit (2.1.14.4, 2.1.14.3), so a host
  runs exactly what CI tested.
- **Hosts:** compose files name the pinned image instead of a `build:` section; setup pulls; `fabricctl images
  update` (4.14.1) keeps managing updates and rollbacks. Offline installs carry the images in the bundle (2.1.1.22).

### 2.3.14.1.4 Impact assessment

- **Architecture:** 2.1.14.1 (fabric updater, local registry) and 2.1.14.2 (a signed channel on GitHub Pages) are replaced
  by the registry and the lock file; 2.1.14.3's pipeline gains the build and publish steps. Hosts no longer build
  images except for custom ids (P1).
- **Breaking changes:** an existing install switches from its locally built image to the published one at its
  next `fabricctl images update` or setup (same image content, different digest); the rollback record keeps the
  local one until pruned. CI needs package-write permission to GHCR.
- **Scope creep risk:** medium: the CI pipeline (watcher, regression, issues) of 1.14.2 is larger than this; only
  build, smoke test, sign, publish and the lock update are in scope here.

### 2.3.14.1.5 Follow-up decisions 2.1.14.9, 2.1.14.10, 2.1.14.11

Asked while designing the host side (1.14.3) on 2026-10-03; the owner chose:

- **2.1.14.9, which refs publish.** Publishing only from main would leave no way to test hosts against fabric's own
  signed images before a merge, and a release would rebuild images nobody tested. The owner made an exception:
  release-candidate branches (`rc/<version>`) publish too, and a release tag promotes the candidate's digests instead
  of rebuilding (1.14.3.6). Rejected: publishing from any branch (unreviewed images in the public registry).
- **2.1.14.10, an unverifiable signature.** Refusing keeps 2.1.14.6 meaningful: a check that silently passes when it cannot run
  protects nothing. Air-gapped hosts turn it off explicitly, and the relaxation is visible (Rule 10). Rejected:
  warn and continue (weakens 2.1.14.6 silently); verify only when pinning (would change 2.1.14.6).
- **2.1.14.11, running cosign.** Ubuntu 24.04's archive has no cosign; a pinned image needs nothing installed on the host
  and is updated like every other image. Rejected: a host package from GitHub releases (a second pin and update
  path).

## 2.3.14.3 Offline install bundles: building the images part (2.1.14.14)

Built 2026-10-22 on `dev/0.13.0-bundles` (first `dev/0.12.0-bundles`, renamed when the owner renumbered the
releases), for 0.13.0. Design: 1.14.4; procedure: 3.14.2.

### 2.3.14.3.1 What was found

Probed on WSL (Docker 29.8.1) and in a systemd + Docker box with Ubuntu 24.04's `docker.io`:

- **Offline signature checks work with cosign 3.0.6.** fabric's images are signed in the new bundle format: an OCI
  referrer holding a Sigstore bundle (v0.3) whose DSSE envelope is an in-toto statement (`predicateType`
  `https://sigstore.dev/cosign/sign/v1`) naming the image index's digest. `cosign verify --offline --local-image`
  finds no signature in a `cosign save` layout, and `cosign verify` has no `--bundle`; what works is
  `cosign verify-blob-attestation --new-bundle-format --bundle <sig> --trusted-root <root> --type
  https://sigstore.dev/cosign/sign/v1 <index blob>` with `--network none`: "Verified OK"; another signer and another
  blob are refused with cosign's reason.
- **`cosign save`** writes the whole multi-arch index (134 MB for bind9) and none of the new-format signatures:
  not usable for a one-architecture bundle.
- **Docker's image store decides whether a loaded image keeps its digest.** On the containerd store, a
  one-architecture OCI layout whose `index.json` points to the image's own index (the other platform's blobs
  absent) loads, `docker image inspect repo:tag@digest` resolves, and compose runs it with `--pull never`.
  The classic store refuses an OCI layout without a `manifest.json` and, loaded from `docker save`, would not know
  the digest. `docker compose pull --policy missing` skips an image that is present ("Skipped - Image is already
  present locally").
- **Ubuntu 24.04's `docker.io` 29.1.3 uses the containerd store on a new install** (`driver-type
  io.containerd.snapshotter.v1`). Nested in a container it can unpack layers only with `/var/lib/containerd` on a
  volume (on the box's overlay root: "failed to convert whiteout file … operation not permitted"); the sandbox's
  move to the classic store (tests/sandbox/run.sh) is about the same thing.
- Fetching from the registries with Python's standard library took 9 s for nginx and bind9 (130 MB); a registry's
  blob redirect is followed without its token (to the CDN that stores it).

[BUNDLE]` and its `bundle` step, the shipped trusted root, the launcher running export and import from the package;
the deploy pulls with `--policy missing` and `images update` pulls only an image not present; the export of

`--ubuntu` and `--deb` (2.1.14.16, 2.1.14.17, 2.1.14.23; 1.14.4.10), installed by setup's `host` and `member`
steps. Not built: 2.1.14.22.

  (it needs an image this Docker lacks), proven in `offline.sh`.
- 2026-10-22, the export of unpublished images on request (2.1.14.21, 1.14.4.9) added; `tests/images/bundle.py`
  then 26 passed, 0 failed (the space refusal skipped there, as before).
- 2026-10-22, the packages (2.1.14.16, 2.1.14.17, 2.1.14.23; 1.14.4.10) added; `tests/images/bundle.py` then

  packages, about 150 MiB, resolved from the release's `.deb` Depends and setup's host, Docker and member packages.

### 2.3.14.3.4 Open after the build

- **`--deb` (2.1.14.23, Open)**: built so a version not released (this branch, 0.13.0 before its release) can be
  bundled and tested; the owner to confirm it, or have it removed so that only released versions can be bundled.
- **The bootstrap trusts the carried bundle**: before `fabricctl` is installed, the offline host has no fabric key
  to check the `.deb` with (the release's was checked at export; the Ubuntu packages apt checks itself). A bundle
  could also carry the apt repository's signed `InRelease` and `Packages` for an admin to check by hand with the
  key's published fingerprint; not built.
- **The web UI's Overview** does not show the bundle relaxations (`--allow-unpublished`, `--deb`): fabric-agent
  cannot read root's record (`/etc/fabric/images/bundle.json`); status and doctor do.
- **Ubuntu 26.04's codename** is taken as `resolute` (`images/bundle/ubuntu_release`); check it when 26.04 hosts
  are tested.

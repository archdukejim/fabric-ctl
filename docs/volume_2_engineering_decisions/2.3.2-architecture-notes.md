## 2.3.2.1 Proposal: the repository layout of Rule 7

Status: **approved by the owner on 2026-10-03; built the same day (2.3.1.3.8)** (global Rule 5.5: it replaces 2.1.1.7 and the layout in 1.2.2;
decision 2.1.1.30). Container image publishing (2.1.1.21) is a separate proposal, 2.3.14.1.

### 2.3.2.1.1 What changes and what does not

Only where files sit in the repository changes. **The installed tree on hosts stays exactly as it is**
(`/usr/lib/fabricctl/fabric/…`, `/opt/fabric/…`, 2.1.2.5): the package build (`assemble-tree.sh`, which already maps
the repository onto the installed tree) maps the new locations onto the same installed paths. Nothing that runs
on a host sees a different path; no migration code is needed.

Every folder keeps its `README.md` index (1.1.5.2). `HANDOFF.md` goes when the alignment ends (2.3.1.3.3).

### 2.3.2.1.3 One decision: package names

The Python packages keep their names (`fabriclib`, `webui`): renaming them would change the installed tree and
every import on every host. So the web UI's code sits in `src/webui/` and `src/ux/web/` holds only the thin entry
that starts it, rather than moving all of the web UI under `src/ux/web/`. The alternative — the whole web UI under
`src/ux/web/` with imports renamed — needs migration code on upgrade (against 2.1.1.20's spirit) for no behaviour
gain. **Decided: keep the names** (2.1.1.30).

### 2.3.2.1.4 Impact assessment

- **Architecture:** none at run time (installed tree unchanged). 2.1.1.7 (repository layout) is superseded; 1.2.2
  is replaced by the new layout (old topics kept as `[DELETED]` placeholders, 5.7).
- **Breaking changes:** for people working on the code only: every path in the repository moves; the tests,
  the docs tools, CI (`package.yml`), `assemble-tree.sh`, the dev preview's paths and the folder READMEs are
  updated in the same change. Old commits and the section map (2.3.1.4) keep the old paths.
- **Scope creep risk:** high if mixed with other changes, so: moves and path updates only, no refactoring;
  `git mv` so history follows each file.

### 2.3.2.1.5 How it is checked

Against the baseline taken at `b64302c` (2.3.1.3.6): the installed tree built by the package script must hash the
same, file for file, apart from the files whose text this branch changed on purpose (references rewritten in
step 4); the rendered templates must hash the same; every suite and the sandbox must give the same results.

## 2.3.2.2 Options considered and rejected

### 2.3.2.2.1 Podman and a Cockpit bridge

Considered 2026-10-02 so fabric's stacks would show in Cockpit's Podman view, with a separate bridge package
joining Cockpit and fabric. Rejected by the owner the same day: a community Cockpit plugin for Docker Compose
(`cockpit-compose`) already shows every fabric stack, so a runtime switch gained little. Docker stays the runtime
(2.1.2.2's user-namespace remapping remains the isolation path); no fabric Cockpit package is planned (2.1.1.23). Reopen
only if the owner asks.

### 2.3.2.2.2 Docker's own apt repository

fabric first installed Docker from Docker's repository. A release upgrade (`do-release-upgrade`) disables
third-party sources, which left the test Pi's `docker-ce` without updates; the owner decided on 2026-10-02 that
fabric adds no apt sources (2.1.1.24): Docker comes from Ubuntu's archive (`docker.io`, 3.2.2).

## 2.3.2.3 Known gaps

Moved from the README on 2026-10-03 (global Rule 7.1: the README holds no design).

- IPv6: zones can hold AAAA records (with ULA reverse zones), but `fabric_net` and the published ports are IPv4

## 2.3.2.4 Setup's work as fabric-setup.service (0.8.0)

Decision 2.1.2.26, design [1.3.2.3](../volume_1_description_and_architecture/1.3.2-setup-design.md#1323-setups-work-survives-a-dropped-session-080),
procedure [3.3.1.1.6](../volume_3_installation/3.3.1-running-setup.md#33116-a-dropped-connection-the-work-goes-on-080).
Built 2026-10-15 on `dev/0.8.0-setup-detach`.

### 2.3.2.4.1 What was built

- `fabriclib/setup/detach/`: `choose_start` (attach / resume / new), `read_run` and `write_run` (the run record,
  `<config>/setup-run.yaml`, 0600, atomic), `write_handoff` and `read_handoff` (the secrets' file in `/run/fabric-setup`, 0700),
  `unit_running`, `can_detach`, `launch_worker` (`systemd-run --unit fabric-setup.service --collect -p Type=exec`, the
  log appended by systemd itself so a traceback at start is in it too), `follow_run`, `hand_over`, `resume_run`,
  `run_worker` (`setup --worker <run>`, hidden).
- `setup/run_steps.py`: the step loop, out of `run_setup.main`, shared by the unit, the no-systemd fallback and
  `--step`; with a record it saves progress after each step.
- `run_setup.main`: a full run checks the unit and the record before any question; after the plan it hands over
  instead of running the loop. New option `--restart`.
- `uninstall` stops a running `fabric-setup.service` first and removes left hand-off files; `restore_install` (restore
  and reinstall) removes a copied run record.
- The log is written with systemd's `StandardOutput=append:`, with `PYTHONUNBUFFERED=1` so it grows line by line,
  and `PYTHONIOENCODING=utf-8` (the unit has no locale; setup prints ✓ and ·).

### 2.3.2.4.2 How setup held its answers, and what moved

Read in the code before building: after the questions, setup kept these between its questions and its steps.

| What | Where it was | In the unit |
|---|---|---|
| The settings (`ctx.vars`, the plan's defaults applied after `fabric.yaml` was first written) | memory; `deploy` wrote them to `fabric.yaml` | written to `fabric.yaml` at the hand-off (as `deploy` does first); the unit reads them there |
| The consent answers | `consent.yaml` (saved by `ask_consent`) | unchanged: the steps read the file |
| The first admin's password | memory only (2.1.6.33) | the hand-off file, removed once read |
| The join invitation | memory only | the hand-off file, removed once read |
| `--offline`, `--yes`, Guided, `--admin-password-file` (a path) | options | the run record's `options` |
| `SUDO_USER` (`~/fabric-admin`'s owner), `SSH_CONNECTION` (the firewall's lockout guard) | the environment | `--setenv` (names, not secrets) |
| The services whose config changed (`restart_services`) | memory, from `deploy`/`pki`/`certs` to `start` | the run record, after each step |

Every other secret was already in fabric's secrets file or OpenBao (`ctx.secrets` is read on first use), so nothing
else crosses. No setup secret went on a command line before either; the hand-off file keeps it that way (1.2.8.4).

### 2.3.2.4.3 Idempotency across a stop: the review

The steps were already run again whole by every `sudo fabricctl setup`, so each is idempotent by itself (3.3.1.1); a
resume adds one thing a re-run did not have: **state one step left in memory for a later one**. Reviewed step by
step (`steps.py`, every `ctx.` write in the step files):

- `restart_services` (deploy, pki, certs, start): lost on a stop, a resumed `start` would not restart services whose
  configuration changed. **Fixed**: kept in the run record after each step and restored on resume.
- `join` adds the organisation's settings to `ctx.vars` before `deploy` saves them: lost on a stop between them.
  **Fixed**: before deploy, the settings are saved to `fabric.yaml` after each step.
- The first admin's password and the join invitation (memory only): **asked again** on resume when their step is
  ahead (the password only when that run had one).
- `ctx.secrets` (a cache, re-read): nothing to keep.

Where a step is still not idempotent across a stop (inside one step, as before this change: a re-run had the same
exposure):

- `join`: the invitation is single-use; a stop after the upstream accepted it but before the step ended leaves a
  resume (or a re-run) with an invitation the upstream refuses as used. The step reuses what it staged (its Notes),
  so the gap is the moment between the upstream's answer and the staging: ask the upstream for a new invitation.
- `vault`: OpenBao's init writes the recovery keys once; a stop between init and their writing to `~/fabric-admin`
  loses them (the vault works; new recovery keys need a rekey).
- `dbrotation`: Keycloak's database password is handed to OpenBao once; a stop between the rotation and Keycloak's
  restart leaves Keycloak with the old password until the step runs again (the resume runs it).
- The site's number (`start`) and the first admin (`admin`) were asked *inside* their step: in the unit they take
  their unattended answers (1.3.2.3.1), see 2.3.2.4.5.

### 2.3.2.4.4 Tests and results

- Pure, in the `consent` suite (`tests/setup/run_steps_test.py`, `run_setup_test.py`, `tests/setup/detach/*_test.py`,
  one per unit): the start decision, the record, the hand-off file (refusals: an existing file, a symlink, a loose
  mode, another owner, a second read), the unit's command line and environment (no secret), following (result,
  Ctrl-C, a killed unit), the hand-over (no secret left when the unit cannot start; no systemd), the resume (secrets
  asked again only when needed; refused unattended without the password file), the worker (another run refused).
- The sandbox suite (`tests/sandbox/run.sh`, real systemd): the first install through the unit (recorded, collected,
  no hand-off file or password left); a re-run whose session (its own process group) is killed with SIGHUP in the
  certificates step, the unit going on, then `fabricctl setup` re-attaching and ending ready with exit 0.
- The installer test (`tests/host/installer.py`, on the test host): the same over SSH, the client killed in the
  certificates step, then an interactive `sudo fabricctl setup` re-attaching without a question.
- Results, 2026-10-15:
  - `consent` suite (WSL Ubuntu 24.04): PASS, 332 checks passed, 0 failed (99 new); rerun after the folder move: PASS,
    333 passed, 0 failed (100 new).
  - Sandbox suite (WSL Docker, the package built from `af7b9b3a`): 219 passed, 7 failed. Every setup check passed,
    the five new ones among them (the install through the unit, no secret left, the session killed in `[certs]` with

### 2.3.2.4.5 Open

For the owner (the build takes the first answer until then):

1. **The site's number** (2.1.10.16) was asked inside the `start` step once the DC answered. The unit has no
   terminal, so an interactive setup now takes the suggestion and says how to change it, as unattended always did.
   Options: (A) keep that; (B) ask it in the session before the hand-over when the DC already answers (an upgrade or
   a re-run: the main case, moving 0.7's subnets), taking the suggestion only on a fresh install; (C) ask it in the
   session from the suggestion alone, before the DC exists.
2. **`--step` runs stay in the session** (they are repairs, short, and fabric's own programs run them, e.g.
   `refresh_firewall`): a dropped connection still stops one. Detach them too?
3. **Ctrl-C while following exits 130** (following interrupted, the work going on), not the run's result, which is
   not known yet.

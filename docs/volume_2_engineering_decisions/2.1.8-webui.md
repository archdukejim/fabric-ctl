## 2.1.8.1 The web UI from a domain device

- **Decision:** Signed in by the domain, then asks for TOTP by default.
- **Shapes:** 1.8, 1.6
- **Made:** 2026-10-07, by the owner.
- **Why:** 2.3.6.2.
- **Status:** Revised 2026-10-07 by 2.1.6.23: no second factor by default; TOTP or a passkey is raised from the web console.

## 2.1.8.2 The web UI's client certificate

- **Decision:** An **option, off by default**, easy to turn on after the first standup; status output and the web UI show whether it is on. (Before: always required, 2.1.6.2.)
- **Shapes:** 1.8, 1.5
- **Made:** 2026-10-07, by the owner.
- **Why:** the certificate made a first standup hard to use; it stays as a layer to raise (2.3.6.2).
- **Status:** In force; built in 0.6.1 (`webui_client_cert`).

## 2.1.8.3 Doctor and image updates on the web console

- **Decision:** The Overview runs the doctor checks on demand (`status:read`); an Updates section shows image status and applies update or rollback per service as a job (`images:update`, new, admin, behind the admin tools' second factor when raised).
- **Shapes:** 1.8, 1.14
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** 2.3.1.11.5.
- **Status:** In force; **built 2026-10-08** ([1.8.4.2](../volume_1_description_and_architecture/1.8.4-webui.md#1842-doctor-and-image-updates-on-the-overview)); the ACME page with it (Step-CA → ACME, 1.5.1.4). The pages for public certificates, dynamic DNS and the Linux join's leftovers move to 0.7 with those features (2.1.1.39), then to the release after it (2.1.1.42).

## 2.1.8.4 A settings page for setup's choices

- **Decision:** the web console gets a settings page where everything setup decided that is not permanent can be
  changed: the network and host name, the memory fabric may use, the optional services, the password policy,
  Kerberos sign-in, the host changes setup was allowed to make (undone or allowed again), and sign-in security,
  lowering included. Each change asks again for the password of the first admin (2.1.6.33), or later of a
  `fabric-admins` member (2.3.6.4). The permanent ones are shown, read only: the domain, the AD domain, the CA, the
  site and the organisation.
- **Replaced by 2.1.8.7 on 2026-10-14** (the owner, with its impact assessment): a wizard instead of a page, built in
  0.8.0 instead of 0.11, with the network, the host's name, the host changes and lowering sign-in security kept on the
  host's console.
- **Shapes:** 1.8, 1.3, 4.2
- **Made:** 2026-10-09, by the owner ("a menu to the web ui, that requires host password to change these things …
  it could be frustrating if they can't change them later"; everything not permanent; the first admin's password).
- **Why:** setup asks many questions once; each answer must be easy to change later, and changing the host's
  settings is worth proving again who is at the keyboard.
- **Status:** In force; to build in the release after 0.7 (moved by 2.1.1.42 on 2026-10-10; it was set for 0.7); **placed in 0.11 by 2.1.1.45 on 2026-10-10**. Revises 2.1.6.24 (lowering, today only on the host's command line). Its
  page layout and how each change is applied are designed with that work.

## 2.1.8.5 The console's navigation runs down the left, as Cockpit's

- **Decision:** the web console's frame mirrors Cockpit's: a top bar (the install, its host and version, the person
  signed in) and a navigation down the left, one entry per part with its pages below it, replacing the row of tabs;
  the pages' contents and routes stay ([1.8.3.2](../volume_1_description_and_architecture/1.8.3-single-pane.md#1832-the-consoles-frame-a-navigation-down-the-left-as-cockpit-has-it)).
- **Shapes:** 1.8
- **Made:** 2026-10-11, by the owner, reviewing `v0.8.0-rc.2` ("I really like the cockpit layout, could mirror that
  layout instead?"), for 0.9.
- **Why:** the parts outgrew a row of tabs; a navigation down the side holds them and their pages.
- **Status:** In force; to build in 0.9. **Moved to 0.8.0 by 2.1.8.8 on 2026-10-17.**

## 2.1.8.6 DNS is one entry with two pages: Zones and the DNS filter

- **Decision:** the console's DNS has one navigation entry with two pages, Zones (BIND9: zones, records, TSIG, ACLs)
  and the DNS filter; each page keeps its own permission, and the entry shows for anyone who may see either ([1.8.3.2](../volume_1_description_and_architecture/1.8.3-single-pane.md#1832-the-consoles-frame-a-navigation-down-the-left-as-cockpit-has-it)).
  The "optional" badges on the tabs go (already in 0.8.0-rc.3).
- **Shapes:** 1.8, 1.12
- **Made:** 2026-10-11, by the owner ("combine DNS filter into Bind9 DNS … two different top level tabs, so
  permissions are easier to manage"; one entry with two pages, over two separate entries).
- **Why:** one place for names, two permissions as today.
- **Status:** In force; to build in 0.9 with 2.1.8.5. **Moved to 0.8.0 with it (2.1.8.8, 2026-10-17).**

## 2.1.8.7 A setup wizard in the console, with a settings file; sensitive settings stay on the host's console

- **Decision:** setup's choices that are not sensitive are changed in a wizard in the web console (*Settings*), first
  after install and later to reconfigure, through one plan and one apply; the same settings export to and import
  from one file format, in the console and with `sudo fabricctl settings export|import` (owner: "same files, just
  two different methods"); an import ignores what is not the wizard's — secrets, console-only settings — listing it.
  The console-only set: the permanent identity, the network and the host's name, the first admin, every host change,
  OpenBao's unlock and recovery, lowering sign-in security, client certificates and every secret
  ([1.8.5.2](../volume_1_description_and_architecture/1.8.5-setup-wizard.md#1852-what-the-wizard-changes-and-what-stays-on-the-hosts-console)).
- **Shapes:** 1.8 (1.8.5), 1.6.8 (`settings:admin`), 1.3.2 (setup's last words), 1.1.4 (0.8.0).
- **Made:** 2026-10-14, by the owner: "for things that can get changed via the web ui (aka the non-permanent stuff)
  should we move that to a setup wizard in the webui and use that wizard to reconfigure the system in the future as
  well. Within limitation, certain sensitive items should be limited to the console"; then: replace 2.1.8.4 (yes),
  "in line with 0.8.0", the network and host name console-only (yes), headless through file import and export in the
  wizard and a fabricctl command, "certain WebUI fields will be ignored (such as passwords, etc)".
- **Why:** one place to change the site, a file to repeat it on another, and the settings that can cut the console
  off from its host, or touch its operating system, where only someone at the host can change them.
- **Status:** In force; to build in 0.8.0. Replaces 2.1.8.4. **Revised by 2.1.1.58 on 2026-10-17:** on 0.8.0 the
  wizard offers and writes no DHCP or address-manager setting; DHCP joins it with the address manager in 0.9.0.

## 2.1.8.8 0.8.0 redoes the whole console in Cockpit's style

- **Decision:** 0.8.0 builds the frame of 2.1.8.5 (moved from 0.9) and restyles every page to match Cockpit: cards,
  lists that open a detail page, a page's actions along its top. The routes stay.
- **Shapes:** 1.8 ([1.8.6](../volume_1_description_and_architecture/1.8.6-console-redo.md))
- **Made:** 2026-10-17, by the owner ("we are going to completely redo the ui this 0.8.0 release to match the cockpit
  style"; asked whether to restyle every page as well as the frame: "yes").
- **Why:** the console grew a tab at a time and reads that way (the Directory tab most of all: 2.3.8, the survey of
  2026-10-17); 0.8.0 is the console's release (2.1.1.58).
- **Status:** In force; to build in 0.8.0. 2.1.8.5 and 2.1.8.6 are built with it.

## 2.1.8.9 Each page applies its own changes

- **Decision:** a settings change is held as pending on its page (or app) until that page's Apply; Discard drops it.
  One page's Apply never applies another's. Today's three ways to save (a whole-install Apply, a save that applies at
  once, a Group Policy set that is live at once) become this one.
- **Shapes:** 1.8, 1.3 (the agent's routes), 1.6
- **Made:** 2026-10-17, by the owner ("we should have an apply"; one bar for the whole install, or per page: "per
  'page' or app or whatever setup you are in").
- **Why:** a person reviews and applies what they changed where they changed it; changes on other pages are not swept
  in.
  Actions on one object (an admin's password reset, disabling an account, moving a machine) wait for Apply too
  (owner, 2026-10-17: "needs an apply"). Only a person changing their own password is done at once (2.1.8.11).
- **Status:** In force; to build in 0.8.0.

## 2.1.8.10 Devices and device roles move to the 802.1X entry

- **Decision:** the Directory's Devices and device roles (802.1X and its role-based access: MAC addresses, the role
  that decides a device's VLAN) move to the 802.1X entry. Directory is the domain only.
- **Shapes:** 1.8, 1.7
- **Made:** 2026-10-17, by the owner ("even though they are related, if they are 802.1x controls put them there").
- **Why:** "role" then means one thing on each page, and the Directory holds only what a domain admin manages.
- **Status:** In force; to build in 0.8.0. The routes under `/directory/devices` and `/directory/roles` are kept as
  redirects.

## 2.1.8.11 Every person in the domain may sign in to the console and see their own account

- **Decision:** any person in the domain may sign in to the console. With no fabric role they see one
  page, their own account: change their password (it lands in AD), their sign-in factors (TOTP, passkey), their
  certificates and the devices they own. Each fabric role (the bundles of 1.6.8.1, carried in the OIDC token) adds its
  entries to the navigation, as today; the admin bundle sees everything. A password change is its own light form,
  done at once, outside any page's Apply (2.1.8.9).
- **Shapes:** 1.8, 1.6.8, 1.6.2
  A forgotten password is not reset from the sign-in page: the helpdesk resets it (fabric sends no mail).
- **Made:** 2026-10-17, by the owner ("a regular user, they can reset their own password by reaching the site";
  fabric-admin "would see everything"; asked to confirm: yes; a reset from the sign-in page: no).
- **Why:** each person keeps their own sign-in without a helpdesk call, and the roles already carried in the token
  decide everything else; a reset by mail would add a mail service fabric does not need yet.
- **Status:** In force; built 2026-10-23 (1.8.6 step 4).

## 2.1.8.12 The web console's default address is fabric-ctl.<domain> on a new install

- **Decision:** a new install's console answers at `fabric-ctl.<domain>` (`cname_mgr` default `fabric-ctl`); an install
  that has an address keeps it on upgrade. `webui_hostname` still sets any name, checked for collisions
  ([1.2.13.4](../volume_1_description_and_architecture/1.2.13-name-claims.md#12134-the-web-consoles-default-name)).
- **Shapes:** 1.8, 1.2 (1.2.13), 1.4
- **Made:** 2026-10-17, by the owner, after the production install's host named `fabric` hid the console ("I think
  fabric-ctl as the webui ... it stays consistent all the way through").
- **Why:** the product's name (2.1.1.53) as its address; `fabric` alone is a likely host name. Keeping an installed
  address on upgrade follows Rule 9: act only on evidence of the old state, and never move what people use.
- **Status:** In force; the default built 2026-10-23 (1.2.13.4, note 2.3.8.3.4); the collision check of a set
  name is 2.1.2.27's, not built.

## 2.1.8.13 Pending changes are held in fabric-agent's memory

- **Decision:** the pending changes of Apply per page (2.1.8.9, 1.8.6.5) are held in fabric-agent's memory, per
  person and per page, as its jobs and the wizard's plans are; nothing is written to disk. A restart of fabric-agent
  drops them (the person makes them again).
- **Shapes:** 1.8 ([1.8.6.5](../volume_1_description_and_architecture/1.8.6-console-redo.md#1865-apply-per-page)), 1.3
- **Made:** 2026-10-22, by the owner ("yes all recommended", to the question of where the pending changes are held).
- **Why:** the same store as the agent's jobs and plans (one way to hold short-lived state); a change not yet applied
  is a person's draft, so losing it on a restart costs little, and nothing unapplied lingers on the host.
- **Status:** In force; built 2026-10-22 (1.8.6 step 3).

## 2.1.8.14 A pending change's version is a hash of the agent's own read of what it changes

- **Decision:** when a change is made pending, fabric-agent reads the thing it changes (a zone's records, a person, a
  policy) as its own read route returns it and keeps a SHA-256 of that read as the change's version. At Apply it reads
  again; a different hash means someone changed the thing since, and the change is refused and shown again (1.8.6.5).
- **Shapes:** 1.8 (1.8.6.5), 1.3
- **Made:** 2026-10-22, by the owner ("yes all recommended").
- **Why:** it needs no version counter added to every store fabric changes (vars.yaml, AD, Keycloak, OpenBao), and it
  compares exactly what the person saw.
- **Status:** In force; built 2026-10-22 (1.8.6 step 3).

## 2.1.8.15 The console's narrow-screen checks run in a headless Chromium test image

- **Decision:** the checks of 1.8.6.9 that need a browser (every page at 375 px with nothing wider than the screen)
  run in a test-only image: the pinned Debian base of `tests/image_ref.py` with Debian's own `chromium` package,
  driven headless over its DevTools pipe (`--remote-debugging-pipe`) from the test, against the dev preview. It is
  never shipped, and its container gets a unique name per run.
- **Shapes:** 1.8 (1.8.6.9), 1.1 (the tests, 3.1.2)
- **Made:** 2026-10-22, by the owner ("yes all recommended": record the image as a decision before building it).
- **Why:** a page's width can only be measured where it is laid out; Debian's package comes from the source the
  project already pins, and the pipe needs no port and no extra driver (no Selenium, no Node).
- **Status:** In force; built 2026-10-22 (1.8.6 step 2: `tests/webui/test_narrow.py`).

## 2.1.8.16 A page for one thing that is not there answers 404

- **Decision:** a detail page whose thing does not exist (`/8021x/devices/<name>`, `/8021x/roles/<name>`, and every
  later page per name) answers 404 with a plain message, instead of showing the list.
- **Shapes:** 1.8 (1.8.6.3)
- **Made:** 2026-10-22, by the owner ("yes all recommended").
- **Why:** an address names one thing; showing something else at it hides a stale link or a typo.
- **Status:** In force; built 2026-10-22 (1.8.6 step 1).

## 2.1.8.17 Changes that carry a secret are done at once, never held

- **Decision:** a change that carries a secret, typed in or made by fabric and shown once, is done at once and is not
  held for Apply (an exception to 1.8.6.5, beside a person's own password): adding a RADIUS client and its **New
  secret**; OpenBao's unlock methods, unseal and key rotation; PKI's key and certificate issue, CSR signing and
  conversion; Federation's invitations; a TSIG key's creation. Their other changes (removing a client, a group
  mapping, a DNS record) are held as any other.
- **Shapes:** 1.8 (1.8.6.5)
- **Made:** 2026-10-23, by the owner ("all as recommended", to the questions of 2.3.8.3.14 and the step 5i report).
- **Why:** a held change keeps its body in fabric-agent's memory and shows it on the Review; a secret must do neither.
- **Status:** In force; revised 2026-10-23 by 2.1.8.23 (a revocation is done at once too) and 2.1.8.26 (removing an
  unlock method too).

## 2.1.8.18 DNS edits are held on their page; DNS' Apply reloads only BIND

- **Decision:** DNS → Zones' edits (records, zones, ACLs) are held in fabric-agent's pending store per person
  (2.1.8.13), as the Directory's are, instead of being written to `vars.yaml` and published by the whole-install
  Apply. DNS' Apply runs them, then re-renders and reloads BIND alone, health-gated (2.1.14.15).
- **Shapes:** 1.8 (1.8.6.5), 1.4
- **Made:** 2026-10-23, by the owner ("all as recommended", to the questions of 2.3.8.3.14 and the step 5i report).
- **Why:** one page's Apply never applies another's, and a record change should not restart anything but BIND.
- **Status:** In force; how its Apply reloads BIND decided by 2.1.8.24 (2026-10-23); built 2026-10-23 (1.8.6.11.21).

## 2.1.8.19 The wizard's form leaves the password policy and Kerberos sign-in to their pages

- **Decision:** the setup wizard's "Passwords and sign-in" step no longer shows the domain's password policy or
  Kerberos sign-in; it links to Directory → Policies and Directory → Kerberos. The settings file still accepts
  `ad_password_policy` (`policy_*`) and `signin_kerberos`, checked as before.
- **Shapes:** 1.8 (1.8.5, 1.8.6.10)
- **Made:** 2026-10-23, by the owner ("all as recommended", to the questions of 2.3.8.3.14 and the step 5i report).
- **Why:** each setting has one home in the console (1.8.6.10, point 2); the file stays complete for a new install.
- **Status:** In force; it revises 1.8.5's step table for the form only; built 2026-10-23 (1.8.6.11.14).

## 2.1.8.20 Relaxations that are on are shown on both Settings pages and on each one's own page

- **Decision:** the security relaxations that are on (`GET /v1/relaxed-settings`) are listed in a card on Settings →
  Setup wizard and Settings → Sign-in security, and each is also shown on the page it belongs to (a RADIUS client
  without Message-Authenticator on its client's page, a lowered sign-in layer on Sign-in security).
- **Shapes:** 1.8 (1.8.6.4), 1.2.8
- **Made:** 2026-10-23, by the owner ("all as recommended", to the questions of 2.3.8.3.14 and the step 5i report).
- **Why:** a relaxation must be visible where settings are changed and where its effect is (global Rule 10).
- **Status:** In force; the Settings card built 2026-10-23 (1.8.6.11.14); each page's own as that page is rebuilt.

## 2.1.8.21 fabric-agent answers 404 for a person, computer, group or grant that is not there

- **Decision:** fabric-agent's reads of one person, computer, group or grant answer 404 when it is not there (a
  `NotFound` refusal), and 400 only for a refusal of another kind (the DC not running); the console's page for it then
  answers 404 (2.1.8.16).
- **Shapes:** 1.3 (1.3.3), 1.8 (1.8.6.3)
- **Made:** 2026-10-23, by the owner ("all as recommended", to the questions of 2.3.8.3.14 and the step 5i report).
- **Why:** the console must tell "not there" from "cannot be read now" to answer as 2.1.8.16 says.
- **Status:** In force; built 2026-10-23 (1.8.6.11.15).

## 2.1.8.22 A device role's page links its devices; a device's roles are set on the device

- **Decision:** a device role's page lists its devices, each linked to its page, and has no form to add or remove
  one: a device's roles are a field of the device, changed on its page and held on Devices.
- **Shapes:** 1.8 (1.8.6.7)
- **Made:** 2026-10-23, by the owner ("all as recommended", to the questions of 2.3.8.3.14 and the step 5i report).
- **Why:** a member change is the device's change; making it on the role's page would hold it on another page.
- **Status:** In force; built 2026-10-23 (1.8.6.11.13).

## 2.1.8.23 Revoking a certificate is done at once

- **Decision:** PKI's **Revoke certificate** is done at once, a listed exception to Apply per page (1.8.6.5) beside
  the changes that carry a secret (2.1.8.17): the CRLs are published when it is pressed.
- **Shapes:** 1.8 (1.8.6.5, 1.8.6.11.17), 1.5
- **Made:** 2026-10-23, by the owner ("yes", to question 5 of the step 5m report).
- **Why:** a revocation answers a compromised key; waiting for an Apply someone may forget leaves the key trusted.
- **Status:** In force; built 2026-10-23 (1.8.6.11.17).

## 2.1.8.24 DNS' Apply is a BIND-only deploy, and writes the landing page

- **Decision:** DNS' Apply (2.1.8.18) runs its held changes, then renders everything as an apply does and installs only
  BIND's files and the landing page: `rndc reconfig` when BIND's configuration changed and each changed zone swapped in
  under the running BIND, health-gated (it stops at the first part BIND does not take). Another service's changed file
  waits for the next full apply. A TSIG key made or given a new secret at once (2.1.8.17) is given to BIND the same way
  at once.
- **Shapes:** 1.8 (1.8.6.5), 1.4, 1.14 (the deploy engine's render shared)
- **Made:** 2026-10-23, by the owner ("yes" to a BIND-only deploy, and "yes" to the landing page in it: questions 1 and
  2 of the step 5l report).
- **Why:** a record change should reload BIND alone, never another service; the landing page's links are DNS' records.
- **Status:** In force; built 2026-10-23 (1.8.6.11.21).

## 2.1.8.25 Two held record deletes of one type in one zone may refuse the second at Apply (0.8.0)

- **Decision:** a held record delete names its record by type, position and name, as before; when two held deletes
  of one type in one zone run in one Apply, the second can be refused as "changed since it was shown" (fail closed).
  Accepted for 0.8.0 and noted (2.3.8.3.21); naming records by name and value is not built.
- **Shapes:** 1.8 (1.8.6.5), 1.4
- **Made:** 2026-10-23, by the owner ("yes", to question 3 of the step 5l report).
- **Why:** it fails closed (nothing wrong is deleted); the person makes the second delete again.
- **Status:** In force.

## 2.1.8.26 Removing an OpenBao unlock method is done at once

- **Decision:** removing an unlock method on Secrets is done at once, as adding one, testing one and rotating the
  vault key are (2.1.8.17), after a recent sign-in and the host's name typed.
- **Shapes:** 1.8 (1.8.6.5, 1.8.6.11.18), 1.7
- **Made:** 2026-10-23, by the owner ("yes", to question 4 of the step 5l report).
- **Why:** the unlock methods change together; holding one of them would split the kill switch's state over an Apply.
- **Status:** In force; built 2026-10-23 (1.8.6.11.18).

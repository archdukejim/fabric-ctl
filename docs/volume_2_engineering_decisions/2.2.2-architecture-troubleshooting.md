## 2.2.2.1 Known issue of 0.8.0: a fresh install's setup stops at Postgres or Keycloak

*Added 2026-11-01 (found by the lab campaigns, 2.3.10.11.24 and 2.3.1.33).* Applies to fabric **0.8.0** only, and
only to a fresh install's first `sudo fabricctl setup`: a host that is already installed is not affected, because the
bug is in a database's first start. 0.9.0 fixes it (1.2.4.5). In the lab it stopped one fresh 0.8.0 install in three.

**What the operator sees.** Setup stops partway with a failed start of `postgres.service` (or of `keycloak.service`,
which started too early against a Postgres that was not yet listening), for example:

```
Job for postgres.service failed because the control process exited with error code.
See "systemctl status postgres.service" and "journalctl -xeu postgres.service" for details.
```

followed by setup's own error naming `systemctl start postgres` (or `keycloak`). `fabricctl doctor` then fails.
`journalctl -u keycloak` may show `Connection to postgres:5432 refused`.

**Cause.** Postgres's health probe had no start period and asked over the Unix socket, so a first start, which runs
`initdb` and a temporary server before the real one, was either called `unhealthy` too early (a slow disk) or called
healthy too early (the temporary server). See 1.2.4.5.

**Fix.** Run setup again; it resumes where it stopped:

```
sudo fabricctl setup
```

(with the same settings file and flags if the first run was unattended). Then `sudo fabricctl doctor` passes.
Upgrading to 0.9.0 or later removes the cause.

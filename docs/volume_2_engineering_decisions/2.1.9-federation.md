## 2.1.9.1 Can an existing install join, or only a fresh one?

- **Decision:** Proposed: fresh (or an empty directory) at first.
- **Shapes:** 1.9, 3.9
- **Made:** proposed 2026-10-01 to 2026-10-02, with the federation design; decided 2026-10-10 by the owner
  ("probably fresh only, but I want a migration option to keep data users, machines, ssh keys and join them all to
  a new domain easily").
- **Why:** merging two directories' people is a migration project of its own.
- **Status:** In force since 2026-10-10: **fresh only**, with a **migration option** that carries an existing
  install's people, machines and SSH keys into the new domain and guides moving each host
  ([1.9.8.19](../volume_1_description_and_architecture/1.9.8-federation-on-ad.md#19819-moving-an-existing-install-into-a-federation)).

## 2.1.9.2 TOTP at branches: enrolled per site, or through the upstream's Keycloak?

- **Decision:** Proposed: per site first (works offline); brokering to the upstream as an option later, with the local sign-in as fallback.
- **Shapes:** 1.9, 1.6
- **Made:** proposed 2026-10-01 to 2026-10-02, with the federation design; never marked decided.
- **Why:** a branch must sign people in while cut off from its upstream.
- **Status:** In force since 2026-10-10, by the owner: **per site**. Brokering to the upstream stays a later option.

## 2.1.9.3 Roaming devices: which sites hold a site's devices?

- **Decision:** By consent between sites — a site offers its devices and machines to another site, which approves; only then are they replicated there read-only (each pair of sites decides). Each site's part still goes up to its parent.
- **Shapes:** 1.9, 1.11
- **Made:** 2026-10-02, by the owner. The question: replicate every site's devices to every site (read-only), or only upward? (a laptop from branch1 at branch2).
- **Why:** 1.9.
- **Status:** Revised 2026-10-04 by 2.1.9.12: with one AD domain, consent becomes an access grant.

## 2.1.9.4 Site-scoped admin groups: naming and who may create them

- **Decision:** `<site>-<role>` groups, created in the root site's directory (people stay central); they grant rights only at that site; organisation-wide groups apply everywhere.
- **Shapes:** 1.9, 1.6
- **Made:** 2026-10-02, by the owner.
- **Why:** 1.9.
- **Status:** Revised 2026-10-04 by 2.1.9.11: the groups live in the site's own OU.

## 2.1.9.5 May upstream admins manage a site's local items?

- **Decision:** Proposed: site admins only in phases F1–F3; delegated administration from upstream in F4 behind `federation:admin`. (Local items: subnets, switches, through the federation API.)
- **Shapes:** 1.9, 1.6
- **Made:** proposed 2026-10-01 to 2026-10-02, with the federation design; never marked decided.
- **Why:** 1.9.
- **Status:** Decided 2026-10-10 by the owner ("yes, i think it makes sense"): **upstream admins may manage a
  site's local items**, as 2.1.9.13 already gives a parent's roles every site below it. The F1-F3 restriction
  proposed above does not apply.

## 2.1.9.6 HA promote: by hand only, or automatic later?

- **Status:** Revised 2026-10-10 by 2.1.9.16: takeover is by hand, and automatic only where an upstream site

## 2.1.9.13 Who administers a site

- **Decision:** Five **roles**, each its own group in the site's `OU=groups` so each can be given to a different admin group: `<site>-ou-admins` (the site's OU: people, groups, sub-OUs), `<site>-machine-admins` (add, enable and remove the site's machines and devices), `<site>-gpo-admins` (the site's own GPOs, and blocking inheritance of what a parent did not enforce), `<site>-linux-sudo` (any command as root on the site's joined Linux machines), `<site>-windows-admins` (local Administrators on the site's Windows machines). `<site>-admins` is a member of all five by default. A parent site's roles reach every site below it and a child cannot block them (2.1.6.20); no role may change or bypass a parent's enforced controls. Everyone else gets sudo only from rules an admin adds.
- **Shapes:** 1.9, 1.6
- **Made:** 2026-10-05, by the owner (S6.3).
- **Why:** [2.3.6.1.21](2.3.6-identity-notes.md#236121-the-owners-s8-answers).
- **Status:** In force. Revised 2026-10-13 (status only): the role list above still names `<site>-linux-sudo`, which
  2.1.6.37 replaced in 0.9 by `<site>-fabric-admins` (1.6.11.3); the roles are now `<site>-ou-admins`,
  `<site>-machine-admins`, `<site>-gpo-admins`, `<site>-windows-admins` and the host admins `<site>-fabric-admins`.
  Revised 2026-10-13 by 2.1.9.21: `<site>-admins` is no longer a member of the roles by default (it is the site
  helpdesk); a site above grants them.

## 2.1.9.14 Where the Federation tab's overrides and access grants are kept

- **Decision:** A `fabric` database, with its own role, in each site's Postgres (the server Keycloak already uses). Each row is owned by the site that made it and only the owner writes it; every site holds a copy of every row, kept by Postgres's logical replication along the site tree (each site with its parent; a link carries only the rows the other side does not own, so nothing loops). **Postgres is never on the host:** a link reaches it through nginx's stream proxy on one port open to the linked sites' addresses only, mutual TLS with the site's certificate (its name checked against the registry), then a Unix socket nginx and Postgres share (no network on the inner hop: TLS there is not possible, nginx's stream proxy cannot speak Postgres's direct TLS; the owner's "TLS inside if it can be done, not a requirement"), and a per-link replication role whose password is in OpenBao (spike: 2.3.6.1.25). The effects (ACLs, GPOs, FreeRADIUS and Keycloak changes) are written to AD as before. Other fabric state stays where it is; moving any of it is its own decision ([1.9.8.16](../volume_1_description_and_architecture/1.9.8-federation-on-ad.md#19816-where-overrides-and-grants-are-kept)).
- **Shapes:** 1.9, 1.2
- **Made:** 2026-10-05, by the owner (S8.6).
- **Why:** [2.3.6.1.21](2.3.6-identity-notes.md#236121-the-owners-s8-answers).
- **Status:** In force.

## 2.1.9.15 HA scope: independent power, maintenance, tested on the lab only

- **Decision:** A site's HA runs on two independently powered machines with two fabric instances on each (four
  nodes, possibly as a hot standby), so one instance per machine can be in maintenance while the site stays
  redundant. HA is built and tested on the lab, and the owner does not run it on their own network. If it proves
  infeasible or needs significant code, it may never be released
  ([1.9.2.2](../volume_1_description_and_architecture/1.9.2-ha-partners.md#1922-scope-power-how-many-partners-maintenance-owner-2026-10-10)).
- **Shapes:** 1.9
- **Made:** 2026-10-10, by the owner ("two independently powered machines so if one looses power the other
  continues to operate for a site"; "perhaps four to allow maintence modes in either machine"; "I won't be doing
  HA, we will just test it here"; then "two machines with two instances each, this might be a hot standby
  situation, if it's not feasible or requires signficant code, we may never release it"; then "assume HA will
  continue to be worked, features on it may be limited based on technical difficulties").
- **Why:** HA has to survive the failures that happen (power), and maintenance must not remove the redundancy;
  the owner's own resources run one host per house, protected by measured rollout instead (2.1.14.15).
- **Status:** In force. HA's release stays as 2.1.1.45 places it (0.10, after 802.1X: the owner kept the order on
  2026-10-10). Revised the same day by the owner: HA continues to be worked whatever the gate finds; the gate
  limits which HA features are built, not whether HA exists (1.9.2.2). Federation's later phases may still build
  on it (1.1.4.3 item 12).

## 2.1.9.16 HA takeover: by hand, or automatic with the upstream site as witness

- **Decision:** A site's partners take over **by hand** (`fabricctl site promote`, the runbook). Where the site
  has an **upstream site**, the upstream is the witness, and takeover may be automatic with a majority that counts
  it (1.9.2.1.1.1). No separate witness-only agent: federation gates witnesses.
- **Shapes:** 1.9
- **Made:** 2026-10-10, by the owner ("takeover by hand, or if upstream site exists, a witness, federation gates witnesses").
- **Why:** two machines with two VMs each split two against two when a machine loses power or the link breaks
  (1.9.2.2): without a third party, no side may take over safely. The upstream is that third party where it exists;
  elsewhere a person decides.
- **Status:** Revised 2026-10-11 by 2.1.9.20: any linked remote site may witness, and by hand is one promote (and
  demote) step in the CLI and the console. Revises 2.1.9.6 (automatic takeover in every case).

## 2.1.9.17 A removed site's objects go to the Lost OU

- **Decision:** Removing a site moves its people, machines and devices into a default **Lost OU**. Objects there
  lose every connection to the domain's resources; people may still sign in with their cached profiles by default,
  which an admin can restrict in the web console. A site with no DC is a site all the same: its OU, nothing more
  ([1.9.8.17](../volume_1_description_and_architecture/1.9.8-federation-on-ad.md#19817-the-lost-ou)).
- **Shapes:** 1.9, 1.6
- **Made:** 2026-10-10, by the owner ("removal places all objects in OU purgatory, so maybe a default 'Lost OU'"), answering what
  `remove` does with a site's OU (2.3.6.1.26) and whether a site may have no DC (2.3.6.1.23).
- **Why:** nothing is deleted by accident, and nothing removed keeps its access.
- **Status:** In force; revises 1.9.8.12's "moved to the parent's or deleted, as the admin chooses". Not built.

## 2.1.9.18 Joining is a role: Domain-Join

- **Decision:** Joining machines and sites to the domain is a **role, Domain-Join**, which can be delegated to any
  group the admin makes; by default it is held by Domain Admins
  ([1.9.8.18](../volume_1_description_and_architecture/1.9.8-federation-on-ad.md#19818-the-domain-join-role)).
- **Shapes:** 1.9, 1.6, 1.8
- **Made:** 2026-10-10, by the owner ("it would be a Role called Domain-Join, and can be delegated to any custom groups, but default it
  will be domain admins"), answering whether the join account needs less than Domain Admin (2.3.6.1.20).
- **Why:** least privilege where it works, and the admin decides who joins.
- **Status:** In force. Not built. A DC's join may still need Domain Admin rights in Samba (1.9.8.18).

## 2.1.9.19 Each house is a site under the owner's root

- **Decision:** the owner's house and three family houses (both parents', a brother's) are each a fabric site,
  under the owner's site as the root; the owner, at the top, edits every house's settings, its network plan first
  (2.1.10.10). This uses 2.1.9.5 (an upstream's admins manage a site's local items).
- **Shapes:** 1.9, 1.10
- **Made:** 2026-10-11, by the owner: "multiply that by four, for both my parents houses, and my brother"; asked
  whether each house is a site and whether the top edits them: "yes and yes. I will be the top level, editing them".
- **Why:** one person administers four networks.
- **Status:** In force. How an edit reaches a house: 2.1.10.11 (open). Revised 2026-10-12 (status only): 2.1.10.11
  is no longer open; the owner decided it on 2026-10-11, option A ("3 A"): the plan is kept in AD and an edit from
  the top is written on the house's DC and replicates to it.

## 2.1.9.20 HA takeover: any remote site may witness; otherwise one easy promote

- **Decision:** a site's nodes take over automatically when **a linked remote site** can be the witness (any site
  it links to, not only its upstream: the vote that breaks a two-against-two split). With no remote site to
  witness, takeover is **by hand**, and by hand is one step: **promote** (and **demote**, stepping a node back to
  standby) in the CLI (`fabricctl site promote|demote`) and in the web console, each doing the whole runbook
  (Postgres, OpenBao's snapshot, Keycloak, the web UI, nginx, names) and saying what it did.
- **Shapes:** 1.9, 1.8, 4.9
- **Made:** 2026-10-11, by the owner: "promote by hand if no remote sites can serve as witness, if promote by hand,
  should still be an easy button to promote and remote in the cli and hopefully in the web page"; "remote" is
  demote (owner, the same day: "2 demote").
- **Why:** an owner without a remote site still needs takeover to be quick and safe, not a written procedure.
- **Status:** In force; HA is 0.10. Revises 2.1.9.16 (the upstream only as witness; promote as a runbook).

## 2.1.9.21 Layered roles: Central IT everywhere, a site's admins its helpdesk, more granted from above

- **Decision:** Three layers.
  1. **Central IT** is the organisation's groups in `OU=organisation` (`admins`, `network-operators`, ...): full
     rights at every site, unchanged. In AD the organisation's admin group is kept in the root site's AD role groups,
     which reach every site (it held them before through people in `<root>-admins`).
  2. A site's **local admins**, `<site>-admins`, by default may only **unlock and reset passwords, add and disable
     people — of their own site's people only** ("3 b"), never a person who holds a role: in AD exactly those rights
     on the site's `OU=people` (and `<site>-users`' members), instead of membership of the role groups; in the
     console the bundle `fabric-site-helpdesk` (`site:people:read|create|reset|unlock|disable`, with the new
     `people:unlock`), mapped from `<site>-admins` at that site only. The AD role groups (`ou-admins`,
     `machine-admins`, `gpo-admins`, `windows-admins`, and `<site>-fabric-admins`) are empty of `<site>-admins` by
     default.
  3. **Expansion from above:** a site above grants a site below more roles, as that site's groups —
     `<site>-network-operators`, `<site>-equipment-operators`, `<site>-pki-operators`, `<site>-helpdesk`,
     `<site>-auditors` (their bundle in that site's console only: a site's Keycloak maps its own groups and no
     other site's) and the AD role groups — to `<site>-admins` or any group or person, with `fabricctl federation
     roles grant|revoke` or the Federation tab (`federation:admin`). Only a site above may grant: a site never grants
     itself (refused by the DC's operation; in AD its admins and its `ou-admins` are denied its role groups'
     members). Status (`fabricctl federation roles`, `federation status`, the tab) shows each site's granted roles.

  The fabric-agent's own per-site rights are unchanged. Upgrade: nothing released to keep; existing installs'
  `<site>-admins` are narrowed at the next convergence (also from the site above, for a read-only DC's site), and the
  change list says so per group.
- **Shapes:** 1.6.3 (1.6.3.6, 1.6.3.18), 1.6.8 (1.6.8.2), 1.8.2, 1.9.8 (1.9.8.20), 1.9.6, 4.6.1, 4.9.1
- **Made:** 2026-10-13, by the owner: "a traditional company layout of a main IT department managing all site
  installs, device lifecycle, while a local admin might just do user unlocks. Hence the layered permissions. But a site
  might also reach the size to have expanded need like device management, at that point promote DC to read-write and
  expand user roles"; local admins' default limited to their own site's people ("3 b"). Promoting the DC is separate
  work.
- **Impact assessment (global Rule 5.5), approved by the owner 2026-10-13:** *architecture* — Keycloak gets a per-site
  role mapping (a second, read-only group mapper for the site's own groups) and a site's AD rights are redrawn, pulling
  1.0's S8.6 / decision F4 pieces forward into 0.9; *breaking* — local admins lose full control of their site's OU by
  default, acceptable before 1.0 (2.1.1.31); *scope creep* — large (AD ACLs, Keycloak, the agent's permission check,
  the console, the CLI); placed in 0.9.
- **Why:** one central department runs every site; a branch's own staff need only the everyday helpdesk tasks, and a
  site that grows is given more deliberately, from above, never by itself.
- **Status:** In force; built 2026-10-13, untested (2.3.9.2). Revises 2.1.9.13 (`<site>-admins` a member of every
  role by default).
- **Revised 2026-10-13** (owner, through the coordinator; built, untested): (1) convergence keeps `<site>-admins` a
  member of `<site>-users`, so Keycloak admits a site's admins (settles 2.3.9.2.6, option b); (2) below the root the
  site's own `fabric-agent-<site>` is denied, as `<site>-admins` and `<site>-ou-admins` already were, any change to
  the members of its own site's role groups, console role groups and `<site>-admins` — and, with `<site>-ou-admins`,
  every other write on them (name, delete, permissions, owner) — so root on a branch host cannot grant through the
  agent's credentials; grants come only from a site above's agent. A role group the branch deletes and makes again is
  refused by convergence (owned by a branch principal) and replaced by the next grant from above. The agent's other
  per-site rights are unchanged. Fabric's own writes at a branch are unaffected: groups, and 2.1.6.38's
  `<site>-fabric-admins` in `<site>-machine-admins`, are made by convergence as the system (on the parent's DC when
  the site is created, `prepare_site`; on the site's own DC where it is writable). Settles 2.3.9.2.7's first limit;
  manual 1.6.3.18.4.
- **Revised 2026-10-13, second** (owner's choice (b) of 2.3.9.2.5, through the coordinator; built, untested): a role
  granted at a site works at that site **and every site below it**, never a sibling or a site above. In the console,
  each site's Keycloak maps its own groups and the console role groups of every site above it (an ancestor's
  `<site>-admins` stays its own site's helpdesk only); in AD, `<above>-ou-admins` reaches below by inheritance, and
  each site's convergence puts the machine and GPO admins of every site above it on the site's machines, devices and
  OU (windows-admins and fabric-admins already reached below). The fabric-agent needs no change (it takes a bundle as
  any role). Grants still come only from above the site granted. Replaces item 3's "their bundle in that site's
  console only"; manual 1.6.3.18.7, 1.6.8.2.5, 1.9.8.20.6.
- **Revised 2026-10-13, third** (through the coordinator; built, untested): a site above may **remake** a site
  below's role group or `<site>-admins` — replaced empty when the site made it itself, made when missing, left as it
  is when fabric made it — with `fabricctl federation roles remake` or the Roles card; refused at the site itself, a
  sibling or a site above; audited `SITE_GROUP_REMAKE` (settles 2.3.9.2.8, option a).

## 2.1.9.22 Sibling isolation: a site sees itself and the sites below it

- **Decision:** The Federation tab's address plan and overlaps, `fabricctl federation networks` and `fabricctl ipam
  find` show only this site and the sites below it (the same `visible_sites` rule as the Networks tab, 2.1.10.27); the
  top sees all. An overlap with a site not shown is counted, never named. AD itself stays readable domain-wide to
  authenticated accounts (as in any AD), and fabric does not try to hide that.
- **Shapes:** 1.9.8 (1.9.8.20), 1.8.2, 1.10.4
- **Made:** 2026-10-13, by the owner, with 2.1.9.21.
- **Why:** a branch has no business with its siblings' networks; the top runs them all.
- **Status:** In force; built 2026-10-13, untested (2.3.9.2). The checks that refuse overlapping networks (a join, a
  DHCP subnet) still check against every site. Open: whether `fabricctl ipam show <site>` and `export` of a sibling
  follow the same rule (2.3.9.2.4).
- **Revised 2026-10-13** (owner, through the coordinator; built, untested): `fabricctl ipam show <site>` and `ipam
  export [<site>]` follow the same rule — a site not shown is refused before AD is read, `export` without a site writes
  every site shown, the top sees all (settles 2.3.9.2.4, option a). Shapes 1.10.4 and 4.10.2 too.

## 2.1.9.24 An account holds a role only at its own level or below

- **Decision:** An account may hold a role only if it lives at that role's level or above: a role at site S (which
  reaches S's sites below, 2.1.9.21) may be given only to an account whose object lives in S's OU or an ancestor's
  (Central IT's accounts live in the top site's OU; the organisation's fabric groups and the domain's administrators
  count as roles at the top). A grant, and putting a person in a group that gives a role (nested too), is refused
  otherwise, naming where the account must live and how to move it. `fabricctl people move <uid> --site <site>` moves
  an account, from a site above both its place and the target, never below a site where it holds a role; audited
  (`PERSON_MOVE`). A branch's own `fabric-agent-<site>` and `fabric-keycloak-<site>` are denied every write on a person
  of the branch whose role reaches beyond it. Such people change their password at a sign-in page of their own level:
  the branch's Keycloak cannot store it. Existing violators are reported by every convergence, `fabricctl federation
  roles` and the Roles card, and never moved automatically.
- **Shapes:** 1.6.3 (1.6.3.18.8), 1.9.8 (1.9.8.20.3), 4.6.1 (4.6.1.5), 4.9.1 (4.9.1.2)
- **Made:** 2026-10-13, by the owner: option (a) of 2.3.9.2.9, "I agree for privileged accounts".

## 2.1.9.23 Changing a site's DC type: requested from above, carried out at the site with its consent

- **Decision:** a site's DC changes from read-only to writable (a site that has grown) or back, as 1.9.8.12 designed
  it (demote, then join again under the same name), in two steps:
  - **Requested from above:** a site above it in the tree (its parent or any ancestor), with a writable DC, runs
    `fabricctl federation dc-type <site> writable|rodc`. The request is written into AD, in the site's own OU
    (`CN=fabric-dc-type-request`, a `serviceConnectionPoint`, no schema change), where the site and every DC see it,
    as the top's other top-down edits are (2.1.10.11); and the top hands its admin a **one-time change token**
    (one hour, the invitation's form: only a hash kept), which is what lets the site fetch the temporary join account
    the change needs. Refused, saying why and changing nothing: from the site itself, a sibling or a site below
    (not an ancestor); `none` (not built: 1.9.8.12's third type stays open); the root's own DC (always writable,
    1.9.8.3); the site already of that type; the top's own DC read-only (it cannot prepare the join account); the
    top's replication unhealthy; the federation endpoint off.
  - **Carried out at the site, with its consent:** `fabricctl federation dc-type show` lists the request;
    `fabricctl federation dc-type accept` shows the plan, asks for consent (or `--yes`, never a default) and the
    token (pasted at a prompt or from a file, never on the command line), checks again that a writable DC answers
    (the list of 2.1.6.57) and that this DC's replication is healthy (every inbound partner succeeded within the last
    hour, no failures), redeems the token at the top's endpoint for the join account, demotes this DC at the
    writable DC (`samba-tool domain demote --server`), sets the DC aside (its data folder kept for the record), removes
    the demoted DC's leftover computer account, and joins again with the new type under the same name, through
    setup's own join path (`JOIN_ROLE`); the services use the writable DC meanwhile (1.9.8.12). Then the request is
    removed and the change recorded (`<config>/dc-type-change.json`).
- **Idempotent and undo:** every step is checked before it is taken, so `accept` run again after a failure continues
  where it stopped (the record says which step), and once the type is right it only removes the request. There is no
  rollback of a demoted DC (AD has forgotten it: putting its old database back would make a DC the domain does not
  know); **undo is the reverse change**, requested from above the same way. Before the demote nothing has changed and
  a refusal leaves everything as it was.
- **After promotion (read-only → writable):** writes stay local (2.1.6.52's routing follows `ad_dc_type`; the
  writable list of 2.1.6.57 is no longer used); Group Policy edits and per-OU log-on policies are allowed again
  (`refuse_at_read_only_dc`); the site's DC converges its own OU and GPOs. `<site>-rodc-cache` is kept with its
  members and its timer removed (nothing reads it while the DC is writable; a change back reuses it). The fabric host
  keeps its computer account (2.1.6.49, 2.1.6.52): made at the writable DC and replicated, it is the same account
  at the site's own writable DC.
- **After a change to read-only:** the site's join writes the allow list again (`allow_rodc_cache`) and the cache is
  preloaded (2.1.6.55); writes go to the writable list (2.1.6.57); Group Policy edits are refused at the site again.
  Refused as well: a DC holding an FSMO role (move the role first).
- **Shapes:** 1.9 (1.9.8.12, 1.9.8.22), 1.6, 4.9 (4.9.1.4)
- **Made:** 2026-10-13, by the owner: "design: initiated from above (central IT decides a site has grown; the top
  writes a request into AD, like other top-down actions) and executed at the site with the site's consent step";
  the owner's model: "a site might also reach the size to have expanded need like device management, at that point
  promote DC to read-write and expand user roles" (the roles are 2.1.9.21 and 2.1.9.22, built apart). Settled while
  building (2.3.9.3): the token (a DC join needs Domain Admin rights for an hour, 1.9.8.18, and AD must never carry a
  secret), the request object's class, the health rule, the FSMO refusal, undo as the reverse change.
- **Why:** central IT decides a site's size; the site's own admin consents to the downtime of its DC. The request in
  AD is visible to both and to every DC; the token keeps the join account's password off AD and off command lines, and
  only a site above can mint one (only it has the endpoint, the join-account converge and the rights on the site's OU).
- **Status:** In force; **built 2026-10-13** for 0.9; container-free tests run, the `samba` suite's written, **not
  run** (the owner's direction of 2026-10-12: 2.3.9.3.3). Settles 1.9.8.12's "changing the type" for writable and
  read-only; `none` stays open.
  **Revised 2026-10-13 while building (2.3.9.3.3), the order only:** the demoted DC's leftover computer account is
  deleted before the DC is set aside (`ldbdel` from inside the still-running container, where the join account's
  file is mounted), and the join runs as `fabricctl setup --yes` (setup's own join path). The steps are: token,
  demote, leftover, set aside, join, done.
  **Revised 2026-10-14 at the 0.9 integration (the coordinator, settling 2.3.9.3.5 points 1 and 2 by the owner's
  central-IT model, 2.1.9.21):** the request can also be made from the console: the Federation tab's form (a site that
  joined here, the type), for `federation:admin` (central IT's permission, which the roles work added) and a sign-in
  from the last 5 minutes; agent route `POST /v1/federation/dc-type/<site>`, audited from `web`. The change token is
  shown once on the answering page, never put in a URL nor kept by the console (1.9.8.22.4, 4.9.1.4). The rest of the
  decision is unchanged: the same checks (`request_dc_type`), the same consent at the site.

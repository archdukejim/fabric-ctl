## 2.3.9.1 References used in the federation design

- 389 Directory Server: multi-supplier, hub and consumer replication; fractional and certificate-based replication.
- Kea 3.0: the high-availability hook (hot-standby, load-balancing) and TLS for the HA channel.
- BIND 9.20: primaries/secondaries, NOTIFY, TSIG-signed zone transfers, delegation.
- Step-CA: intermediate CAs signed by an external root ("bring your own CA"), path length.
- Keycloak: LDAP user federation; identity brokering (OIDC).
- OpenBao: Raft storage, snapshots (`bao operator raft snapshot save/restore`).
- PostgreSQL: streaming replication and promotion.

Choices made while building:
- **Re-joining through setup.** The join path already lives in setup (`deploy_samba` re-joins when `ad_join_server`
  is set and `samba/data/.fabric-provisioned` is missing; `start_services` runs `allow_rodc_cache` and `finish_join`).
  The change sets the settings and runs `fabricctl setup --yes` rather than copying those steps.
- **Order: leftover before set aside.** The demoted DC's leftover account is deleted with `ldbdel` from inside the
  site's DC container while it still runs (the join account's file is mounted there), then the container is stopped
  and its data set aside.
- **The token** is a separate kind in `federation_invitations` (`kind: dc-type`), revoked and listed with the
  invitations (`fabricctl federation revoke <id>`, `invitations` marks it); `accept_join` refuses any entry with a
  kind, so one can never be used for the other.
- **A site can write its own request** (its agent's rights cover its OU) but gains nothing by it: the token the
  change needs is only made at a site above, and is checked there.
- **Healthy replication**: every inbound partner of every partition succeeded within the last hour with no failure
  since; a DC with no partner is unhealthy (`samba/replication_healthy`, from `read_replication`).

Vendor facts checked:
- `msDS-RevealedUsers`: "Used with RODCs to identify the user objects whose secrets have been disclosed to that
  RODC"; DN-Binary, stored on the RODC's computer object (System-Flags 0x10)
  ([Microsoft: ms-DS-Revealed-Users](https://learn.microsoft.com/en-us/windows/win32/adschema/a-msds-revealedusers)).
- `msDS-RevealedList`: the principals whose secrets have been replicated to the RODC, DN-String, **constructed**
  (System-Flags 0x14 includes the constructed flag 0x4)
  ([Microsoft: ms-DS-Revealed-List](https://learn.microsoft.com/en-us/windows/win32/adschema/a-msds-revealedlist)).
  fabric reads the stored `msDS-RevealedUsers` and adds `msDS-RevealedList` when a DC returns it.
- Samba records disclosures in `msDS-RevealedUsers` since 4.7, the first release it calls secure as or with an RODC
  ([Samba 4.7.0 release notes](https://www.samba.org/samba/history/samba-4.7.0.html)).
- `samba-tool domain demote --remove-other-dead-server=<name>` calls `remove_dc.remove_dc(samdb, logger, name)`
  ([netcmd/domain/demote.py](https://github.com/samba-team/samba/blob/master/python/samba/netcmd/domain/demote.py)),
  which finds the DC by its server object's `cn` and deletes its NTDS Settings and server objects, its computer
  account, the RODC's own krbtgt account (`msDS-KrbTgtLink`), its DNS account and records and its SYSVOL references
  ([remove_dc.py](https://github.com/samba-team/samba/blob/master/python/samba/remove_dc.py)). fabric calls the same
  function inside the writable DC.

Choices made while building:
- **Kinds:** a computer account is a machine; an account in a site's `OU=service-accounts` or with
  `DONT_EXPIRE_PASSWORD` is a service account; any other user a person. The RODC's own account and krbtgt are removed
  with it, never reset; a krbtgt that is not the RODC's is never touched by the command (4.9.1.3 says what to do).
- **The DC enforces the list too:** while the RODC exists, `rodc_lost.py` refuses a reset of an account not in its
  revealed list, so a mistake on the host cannot widen the reset. After the RODC is removed, the host's record is the
  list.
- **The allowance:** the allow list lives on the RODC's computer account (`msDS-RevealOnDemandGroup`); it is cleared
  first and goes with the account. `<site>-rodc-cache` itself is kept (a new read-only DC of the site uses it again).
- **No `--yes`:** the command needs a terminal for the typed site name; there is no unattended form.
- **The console's permission** is the admin bundle (`system:admin`), not a new permission: 2.3.9.3.5 asks whether a
  narrower one is wanted.

### 2.3.9.3.5 Open points (0.9 promote round)

1. **Requesting a DC type change from the console.** Built only at the command line (as invitations are). Options:
   (a) leave it at the command line; (b) a console form under a new `federation:admin` permission, with the token
   shown once. Recommendation: (a) until federation's console actions get their own permission.
2. **The lost-DC action's permission.** Built as `system:admin`. Options: (a) keep it; (b) a new `federation:admin`
   given to central IT's role. Recommendation: (a); (b) with point 1.
3. **A whole DC type change against real DCs.** Not in any suite (the `samba` suite has one writable and one
   read-only DC of different sites, never a DC that changes). Options: (a) a lab run (two hosts) before 0.9 ships;
   (b) a new suite with a second site's DC that is changed both ways. Recommendation: (a) now, (b) later.
4. **`none`** (a site with no DC) stays open (1.9.8.12): the lost-DC command leaves a site DC-less, but no command
   makes one so on purpose.

## 2.1.10.1 Kea in a container (host networking) or native package

- **Decision:** Container, for parity with the other services and easy pinning ([1.10.1.1](../volume_1_description_and_architecture/1.10.1-kea-design.md#11011-kea-dhcp)).
- **Shapes:** 1.10, 1.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** parity with the other services and easy pinning.
- **Status:** In force; built this way.

## 2.1.10.2 Lease backend: memfile or Postgres

- **Decision:** memfile; Postgres only if HA or large lease counts.
- **Shapes:** 1.10
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** nothing more is needed for one site's leases.
- **Status:** In force; built: memfile.

## 2.1.10.3 0.8: DHCP on real networks, and what it adds

- **Decision:** 0.8 makes fabric's DHCP work on networks other than the host's own LAN and proves it on a real one.
  In scope: a **lab suite** on an isolated network (fabric serving a second interface, real Ubuntu clients), a gate
  for the release; **reverse DNS** (PTR) for DHCP clients, with the generated reverse zones leaving the pools out;
  **turning DHCP on and off from the web console**, removing its key and zone when off; the names DHCP registered
  **shown in the DNS tab** (read-only); and the DNS filter's **groups from DHCP** that 0.7 left for Kea (a subnet,
  a device's reserved address, an 802.1X role's VLAN: 2.3.12.1.5). Design: [1.10.3](../volume_1_description_and_architecture/1.10.3-serving-networks.md).
- **Shapes:** 1.10, 1.4, 1.12, 1.8, 3.1
- **Made:** 2026-10-10, by the owner (all four of the gaps offered; the DNS filter's groups from 0.7's plan).
- **Why:** everything else of DHCP is built (1.10.1.1, 1.10.2); what is missing is what a real network shows.
- **Status:** In force; to build in 0.8.

## 2.1.10.4 What a DHCP subnet's clients may reach

- **Decision:** a subnet fabric serves gets fabric's services by default: its clients may use the DNS (fabric's BIND
  and the filtering resolver), NTP and fabric's pages (the landing and certificate pages, the console's sign-in),
  exactly as the host's own LAN does: handing out addresses implies serving them. A subnet marked **guest** (for
  example the VLAN 802.1X puts unknown devices on) gets DNS through the filter and NTP only. SSH to the host stays
  for the host's LAN and `security.firewall_allow`, whatever DHCP serves.
- **Shapes:** 1.10, 1.4, 1.12, 1.2 (the firewall)
- **Made:** 2026-10-10, by the owner ("By default adds them, however, if subnets are created for guest subnets like
  with 802.1x those may be restricted").
- **Why:** a client that gets an address but cannot resolve names is broken; guests should not see management pages.
- **Status:** In force; to build in 0.8.

## 2.1.10.5 The DNS and NTP servers DHCP hands out

- **Decision:** by default a subnet's clients are told to use fabric's own address **on the interface that serves
  that subnet** for DNS and NTP (not `host_ip`, which they may not be able to reach). `dhcp.dns` and `dhcp.ntp`, and a
  subnet's own options, still override it.
- **Shapes:** 1.10
- **Made:** 2026-10-10, by the owner.
- **Why:** on a second interface, `host_ip` is on another network the clients have no route to.
- **Status:** In force; to build in 0.8.

## 2.1.10.6 Changes applied by restarting Kea, through its control socket

- **Decision:** as built: a change renders Kea's configuration, checks it (`kea-dhcp4 -t`) and restarts Kea (a
  second or two; leases kept in memfile), and fabric reads leases through Kea's local control socket. The design's
  first plan, `config-set` over Kea's HTTPS API with client certificates, is not taken: nothing needs it while one
  host runs one Kea. It returns with HA (2.1.10.2).
- **Shapes:** 1.10
- **Made:** 2026-10-10, recorded when 0.8 was scoped (the build since roadmap 3; 1.10.1.1 corrected).
- **Why:** simpler and as safe: the check runs before the restart, and a restart loses no lease.
- **Status:** In force; built.

## 2.1.10.7 DHCP's PTR records live in fabric's reverse zones, kept across applies

- **Decision:** a reverse zone that covers DHCP's pools or reservations is dynamic: Kea's key may write PTR and DHCID
  records there (and nothing else, nowhere else). On every apply fabric freezes the zone, reads what BIND holds, keeps
  Kea's PTR and DHCID records for every address it has no static record of, and swaps in its regenerated file with
  them. Fabric's own PTRs win: a static record never lies in a pool (normalize_dhcp refuses it), and a reservation
  whose address also has a static record keeps the static PTR. A DHCP subnet whose reverse zone has no static record
  still gets the zone.
- **Shapes:** 1.10, 1.4
- **Made:** 2026-10-10, by the agent, while building 0.8's reverse DNS (2.1.10.3), the owner having asked for work
  without waiting for approval; flagged to the owner.
- **Why:** a pool and fabric's static records share their /24 reverse zone (`7.168.192.in-addr.arpa`), so a zone of
  DHCP's own (as `dhcp.<domain>` is for names, 2.1.4.1) is possible only when a pool fills a zone alone. Freezing
  writes BIND's copy, Kea's records included, so keeping them costs one read per apply.
- **Status:** In force; to build in 0.8. Narrows 2.1.4.1 for reverse zones: forward names stay in `dhcp.<domain>`.

## 2.1.10.8 VLAN subnets are relayed to fabric by the router, which routes and enforces policy

- **Decision:** each VLAN has its own subnet, routed by the site's gateway (at the owner's house a UniFi gateway),
  which also enforces the policy between VLANs. fabric does not route, firewall between VLANs, or configure the
  switches and gateway. The gateway relays each VLAN's DHCP to fabric (a DHCP relay, "DHCP helper", per network),
  and Kea picks the subnet by the relay's address (1.10.3.2). fabric's procedure for the relay is the operator's
  step (Volume 4).
- **Shapes:** 1.10, 1.2, 4.10
- **Made:** 2026-10-11, by the owner: "the vlans will have a subnet assigned and it will route through a gateway, a
  dhcp helper rule will be needed on my router to assist"; who routes and enforces: "unifi".
- **Why:** the owner's network is UniFi with 802.1X and VLAN segmentation (2.3.1.10); its gateway already routes.
- **Status:** In force; to build in 0.8.0 ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).

## 2.1.10.9 One /24 per VLAN, the VLAN ID its third octet

- **Decision:** "micro segmentation" is many small subnets, one per VLAN, not client classes inside one subnet. The
  convention fabric suggests: a /24 per VLAN whose third octet is the VLAN ID (VLAN 10, management:
  `10.<site>.10.0/24`; VLAN 255, storage: `10.<site>.255.0/24`). A suggestion, never forced: any subnet may be
  entered.
- **Shapes:** 1.10
- **Made:** 2026-10-11, by the owner: "many subnets e.g. mgmt is 10, 255 is storage (3rd octet with a /24)".
- **Why:** an address names its VLAN at a glance; four houses stay apart by their second octet (2.1.10.12).
- **Status:** In force; to build in 0.8.0 ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).

## 2.1.10.10 0.8.0 is an address manager (IPAM), every address tracked, delivered whole

- **Decision:** fabric's DHCP becomes an address manager: every site's VLANs and subnets, their ranges (the gateway,
  static ranges, DHCP pools, reserved), and **every address**: static ones (with owner, MAC, name, notes, optionally
  published in DNS), reservations and live leases, shown together; an address claimed twice is refused. Subnets
  and the address manager are not split across releases: 0.8.0 carries all of it.
- **Shapes:** 1.10, 1.4, 1.8, 1.9
- **Made:** 2026-10-11, by the owner: "the subnet should not spit between releases, also this should look kind of
  like an IPAM solution so I can track all my IPs including static".
- **Why:** with dozens of VLANs over four houses, a spreadsheet beside fabric would drift.
- **Status:** In force; to build in 0.8.0 ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites); all its points answered 2026-10-11); written into Volume 1 as [1.10.4](../volume_1_description_and_architecture/1.10.4-address-manager.md) on 2026-10-12.

## 2.1.10.11 Where the address plan is kept

- **Decision:** **in AD** (option A of [2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)): each site's VLANs, subnets, ranges, static addresses and DHCP options
  are objects in its own `OU=networks`; every DC holds the whole plan. An edit from the top is written on its DC and
  replicates to the house; each site's fabric watches its own OU (its DC's highest USN, every 30 s) and renders Kea,
  its DNS records and the access lists when it changes. A house cut off keeps serving from its own copy. Each
  site's `vars.yaml` keeps only what is the host's own (the interfaces Kea listens on). Rejected: each site's vars
  with edits sent through the federation endpoint (an offline house cannot be edited); fabric's database (one
  writer per row: an edit from the top would not be the house's).
- **Shapes:** 1.10, 1.9, 1.6
- **Made:** 2026-10-11, by the owner ("3 A").
- **Why:** the owner edits four houses from the top (2.1.9.19); the plan is already in AD (1.10.2.8) and AD already
  replicates it.
- **Status:** In force; to build in 0.8.0.

## 2.1.10.12 Each site's address block, and the default split of a /24

- **Decision:** fabric **suggests** addresses from a class A plan: the second octet is the site (a number per site,
  unique, chosen at install or join), the third the VLAN (2.1.10.9): `10.<site>.<VLAN>.0/24`. Inside a /24 the
  suggested split is gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254`, editable per VLAN.
  **Suggestions only:** a site's admins (and the owner above every site) may enter any subnet, split and routing,
  NAT or another path included; fabric checks only what it must (overlaps across the organisation where networks
  are routed together, `--allow-overlap` as today; one claim per address).
- **Shapes:** 1.10, 1.9
- **Made:** 2026-10-11, by the owner: "default, class A with second octet being site, but site admins (or god admin
  [aka me]) can choose to do anything, including NAT and route traffic some other way"; the split: "yes".
- **Why:** a readable default for four houses that never forces a network into it.
- **Status:** In force; to build in 0.8.0.

## 2.1.10.13 Finding addresses in use that nobody recorded

- **Decision:** Kea pings an address before handing it out and skips one that answers (Kea 3.0's ping-check hook),
  and an admin can **scan a subnet on request** (ping and ARP from fabric's host; a routed VLAN answers what its
  gateway lets through). Neither ever blocks: an address found in use but unrecorded is **shown** ("in use,
  unrecorded", with the MAC when ARP saw it) and the console **asks whether to make it a reservation** for the device
  at that address (or a static record); the admin may also ignore it or register something else there.
- **Shapes:** 1.10
- **Made:** 2026-10-11, by the owner: "B, with the caveat that the it doesn't prevent you from registering, just
  informs and asks if you want to set a reservation for the existing device at that IP".
- **Why:** finding hand-set devices is the point of an IPAM, but the admin decides.
- **Status:** In force; to build in 0.8.0.

## 2.1.10.14 DHCP options are part of the plan, with netboot presets

- **Decision:** 0.8.0's address manager carries DHCP options at every level (organisation, site, subnet, client
  class, address; the most specific wins), any option by name or code with custom definitions, and the options a
  subnet or address ends up with shown with where each came from. Netboot presets (PXE for BIOS and UEFI by client
  architecture, iPXE chain-loading, UEFI HTTP boot) can be switched on per VLAN or address, pointing at a boot
  server ([2.3.10.3.10](2.3.10-dhcp-notes.md#2310310-dhcp-options-and-netboot)).
- **Shapes:** 1.10
- **Made:** 2026-10-11, by the owner: "a critical component to dhcp..... Dhcp options, I will likely want to include
  options for netboot".
- **Why:** options are what make DHCP useful beyond addresses; netboot needs per-architecture answers.
- **Shown by their standard names:** every option appears under its RFC name with its code (option 67
  "boot file name", 66 "TFTP server name", 6 "DNS servers", 42 "NTP servers"), never only a number. Almost all are
  unset. The options fabric itself sets because it provides the service (DNS, NTP, and the domain and search list)
  carry a **"provided by fabric"** marker: fabric runs that service and keeps the option's value with the stack;
  an admin may still override it (the marker then says so). Owner, 2026-10-11: "the options necessary should have
  their default names (e.g. option 67 being bootfile)... we know dns, and ntp will be there and while users can
  change that, we can put a nice little pill or some other indicator that fabric provides that service and manages
  it as a part of the stack".
- **Status:** In force; to build in 0.8.0 with the rest of 2.1.10.10.

## 2.1.10.15 Whether fabric serves the netboot files

- **Decision:** **no**: fabric's DHCP points at a boot server the owner runs (option A of
  [2.3.10.3.10](2.3.10-dhcp-notes.md#2310310-dhcp-options-and-netboot)); 1.10.2.7 stays. A later optional boot
  service is not ruled out.
- **Shapes:** 1.10
- **Made:** 2026-10-11, by the owner ("7 A correct").
- **Why:** one fewer service to secure and update; the owner has a boot server to point at.
- **Status:** In force.

## 2.1.10.16 Where the site's number is asked: at setup and by a command

- **Decision:** both (option C of [2.3.10.4.1](2.3.10-dhcp-notes.md#231041-where-the-sites-number-is-asked)): setup
  asks the site's number once, at its start step after the domain controller runs and before the upgrade moves 0.7's
  subnets (one short line, question `setup.site_number`, the suggestion its default: the site's order in the
  organisation, or the next free number; unattended, the suggestion is taken), and `fabricctl ipam block [<n>]`
  shows or changes it later (`--site` for a site below). A number is 1-255 and unique in the organisation; changing
  it changes only what fabric suggests from then on, never a subnet already in the plan. A site with a read-only DC
  is not asked: it is numbered from the site above (`fabricctl ipam block <n> --site <site>`). This is a question
  setup asks although the answer can be changed later, an exception to 2.1.2.16 the owner chose.
- **Shapes:** 1.10, 3.3, 4.10
- **Made:** 2026-10-12, by the owner ("both").
- **Why:** the number is chosen at install as 2.1.10.12 says, and a house renumbered later needs no reinstall.
- **Status:** In force; built 2026-10-12 on `dev/0.8.0-ipam` ([1.10.4.18](../volume_1_description_and_architecture/1.10.4-address-manager.md#110418-the-owners-answers-of-2026-10-12-as-built)).

## 2.1.10.17 A reservation's name may be published in the site's zone too

- **Decision:** yes (option B of [2.3.10.4.2](2.3.10-dhcp-notes.md#231042-a-reservations-name-in-dns)): a
  reservation with DNS on also gets an A record (and its PTR) in the site's zone, beside the name DHCP registers for
  it in `dhcp.<domain>`. The rules of a published name hold: a name, one DNS label, unique among the site's published
  names and not already in the settings' zone. A reservation inside a DHCP range may carry its A record (Kea gives
  that address only to its MAC).
- **Shapes:** 1.10
- **Made:** 2026-10-12, by the owner ("yes").
- **Why:** a device with a fixed address is reached by the site's own name, as a static one is.
- **Status:** In force; built 2026-10-12 on `dev/0.8.0-ipam`. Which PTR the address keeps when Kea registers its
  own is [2.3.10.4.6](2.3.10-dhcp-notes.md#231046-a-published-reservations-ptr) (open). Revised by 2.1.10.20 on
  2026-10-12: a published reservation's names are only the site zone's (its A and PTR); DHCP registers nothing for
  it, so there is no second name in `dhcp.<domain>`.

## 2.1.10.18 More than one subnet per VLAN

- **Decision:** allowed (option B of [2.3.10.4.3](2.3.10-dhcp-notes.md#231043-more-than-one-subnet-per-vlan)):
  `fabricctl ipam subnet add <vlan> <cidr>|set <subnet>|remove <subnet>` gives a VLAN further subnets (a secondary
  network, e.g. while renumbering), or a first one to a VLAN kept as a record. Every rule still holds: one claim per
  address, no overlap anywhere in the organisation unless `--allow-overlap` gives a reason, ranges inside their
  subnet. `vlan add` still makes a VLAN with one subnet; `vlan set` changes the subnet of a VLAN that has one, and
  refuses its subnet settings on a VLAN with several (naming them). The suggestion of 2.1.10.9 stays one /24 per VLAN.
- **Shapes:** 1.10, 4.10
- **Made:** 2026-10-12, by the owner ("allow more").
- **Why:** renumbering a VLAN, or a network that outgrew its /24, needs two subnets on one VLAN for a while.
- **Status:** In force; built 2026-10-12 on `dev/0.8.0-ipam`.

## 2.1.10.19 The upgrade at a site with a read-only DC waits for the parent's write path

- **Decision:** wait (option C of [2.3.10.4.4](2.3.10-dhcp-notes.md#231044-the-upgrade-at-a-site-with-a-read-only-dc)):
  at a site whose DC is read-only, the 0.7 subnets stay in its `vars.yaml` and Kea keeps serving them from there, as
  phase 1 built it; each apply says so. They move into the plan when the parent's write path (S8, 1.10.2.8) exists.
- **Shapes:** 1.10
- **Made:** 2026-10-12, by the owner ("wait").
- **Why:** nothing breaks while it waits, and a hand procedure would be thrown away once S8 is built.
- **Status:** In force; waits for S8.

## 2.1.10.20 A DNS record set by hand outranks DHCP's updates

- **Decision:** a DNS record set by hand is authoritative: one in fabric's zones (the settings' `dns:`), or a static,
  infrastructure or reservation address of the plan with DNS on. DHCP's dynamic updates (Kea's DDNS) never overwrite or
  replace it, forward or reverse. Settles [2.3.10.4.6](2.3.10-dhcp-notes.md#231046-a-published-reservations-ptr)
  with its option C. As built: a reservation whose address a record set by hand names gets no DNS update from Kea at
  all (Kea 3.0 cannot skip only the reverse one), so its names are the site zone's A and PTR alone; and BIND denies
  Kea's key every reverse name whose PTR fabric generates from a record set by hand.
- **Shapes:** 1.10, 1.4 (BIND's update policy), 4.10
- **Made:** 2026-10-12, by the owner, as a general rule: "Manually set in DNS is strongest authority in my mind, other
  options and automations should be second to that".
- **Why:** what an admin wrote must stay what DNS answers; automation fills in only where nobody did.
- **Status:** In force; built 2026-10-12 on `dev/0.8.0-ipam` ([1.10.4.19](../volume_1_description_and_architecture/1.10.4-address-manager.md#110419-a-name-set-by-hand-outranks-dhcps)).
  Revises 2.1.10.17 (no second name in `dhcp.<domain>`).

## 2.1.10.1 Kea in a container (host networking) or native package

- **Decision:** Container, for parity with the other services and easy pinning ([1.10.1.1](../volume_1_description_and_architecture/1.10.1-kea-design.md#11011-kea-dhcp)).
- **Shapes:** 1.10, 1.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** parity with the other services and easy pinning.
- **Status:** In force; built this way.

## 2.1.10.2 Lease backend: memfile or Postgres

- **Decision:** memfile; Postgres only if HA or large lease counts.
- **Shapes:** 1.10
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** nothing more is needed for one site's leases.
- **Status:** In force; built: memfile.

## 2.1.10.3 0.8: DHCP on real networks, and what it adds

- **Decision:** 0.8 makes fabric's DHCP work on networks other than the host's own LAN and proves it on a real one.
  In scope: a **lab suite** on an isolated network (fabric serving a second interface, real Ubuntu clients), a gate
  for the release; **reverse DNS** (PTR) for DHCP clients, with the generated reverse zones leaving the pools out;
  **turning DHCP on and off from the web console**, removing its key and zone when off; the names DHCP registered
  **shown in the DNS tab** (read-only); and the DNS filter's **groups from DHCP** that 0.7 left for Kea (a subnet,
  a device's reserved address, an 802.1X role's VLAN: 2.3.12.1.5). Design: [1.10.3](../volume_1_description_and_architecture/1.10.3-serving-networks.md).
- **Shapes:** 1.10, 1.4, 1.12, 1.8, 3.1
- **Made:** 2026-10-10, by the owner (all four of the gaps offered; the DNS filter's groups from 0.7's plan).
- **Why:** everything else of DHCP is built (1.10.1.1, 1.10.2); what is missing is what a real network shows.
- **Status:** In force; to build in 0.8.

## 2.1.10.4 What a DHCP subnet's clients may reach

- **Decision:** a subnet fabric serves gets fabric's services by default: its clients may use the DNS (fabric's BIND
  and the filtering resolver), NTP and fabric's pages (the landing and certificate pages, the console's sign-in),
  exactly as the host's own LAN does: handing out addresses implies serving them. A subnet marked **guest** (for
  example the VLAN 802.1X puts unknown devices on) gets DNS through the filter and NTP only. SSH to the host stays
  for the host's LAN and `security.firewall_allow`, whatever DHCP serves.
- **Shapes:** 1.10, 1.4, 1.12, 1.2 (the firewall)
- **Made:** 2026-10-10, by the owner ("By default adds them, however, if subnets are created for guest subnets like
  with 802.1x those may be restricted").
- **Why:** a client that gets an address but cannot resolve names is broken; guests should not see management pages.
- **Status:** In force; to build in 0.8.

## 2.1.10.5 The DNS and NTP servers DHCP hands out

- **Decision:** by default a subnet's clients are told to use fabric's own address **on the interface that serves
  that subnet** for DNS and NTP (not `host_ip`, which they may not be able to reach). `dhcp.dns` and `dhcp.ntp`, and a
  subnet's own options, still override it.
- **Shapes:** 1.10
- **Made:** 2026-10-10, by the owner.
- **Why:** on a second interface, `host_ip` is on another network the clients have no route to.
- **Status:** In force; to build in 0.8.

## 2.1.10.6 Changes applied by restarting Kea, through its control socket

- **Decision:** as built: a change renders Kea's configuration, checks it (`kea-dhcp4 -t`) and restarts Kea (a
  second or two; leases kept in memfile), and fabric reads leases through Kea's local control socket. The design's
  first plan, `config-set` over Kea's HTTPS API with client certificates, is not taken: nothing needs it while one
  host runs one Kea. It returns with HA (2.1.10.2).
- **Shapes:** 1.10
- **Made:** 2026-10-10, recorded when 0.8 was scoped (the build since roadmap 3; 1.10.1.1 corrected).
- **Why:** simpler and as safe: the check runs before the restart, and a restart loses no lease.
- **Status:** In force; built.

## 2.1.10.7 DHCP's PTR records live in fabric's reverse zones, kept across applies

- **Decision:** a reverse zone that covers DHCP's pools or reservations is dynamic: Kea's key may write PTR and DHCID
  records there (and nothing else, nowhere else). On every apply fabric freezes the zone, reads what BIND holds, keeps
  Kea's PTR and DHCID records for every address it has no static record of, and swaps in its regenerated file with
  them. Fabric's own PTRs win: a static record never lies in a pool (normalize_dhcp refuses it), and a reservation
  whose address also has a static record keeps the static PTR. A DHCP subnet whose reverse zone has no static record
  still gets the zone.
- **Shapes:** 1.10, 1.4
- **Made:** 2026-10-10, by the agent, while building 0.8's reverse DNS (2.1.10.3), the owner having asked for work
  without waiting for approval; flagged to the owner.
- **Why:** a pool and fabric's static records share their /24 reverse zone (`7.168.192.in-addr.arpa`), so a zone of
  DHCP's own (as `dhcp.<domain>` is for names, 2.1.4.1) is possible only when a pool fills a zone alone. Freezing
  writes BIND's copy, Kea's records included, so keeping them costs one read per apply.
- **Status:** In force; to build in 0.8. Narrows 2.1.4.1 for reverse zones: forward names stay in `dhcp.<domain>`.

## 2.1.10.8 VLAN subnets are relayed to fabric by the router, which routes and enforces policy

- **Decision:** each VLAN has its own subnet, routed by the site's gateway (at the owner's house a UniFi gateway),
  which also enforces the policy between VLANs. fabric does not route, firewall between VLANs, or configure the
  switches and gateway. The gateway relays each VLAN's DHCP to fabric (a DHCP relay, "DHCP helper", per network),
  and Kea picks the subnet by the relay's address (1.10.3.2). fabric's procedure for the relay is the operator's
  step (Volume 4).
- **Shapes:** 1.10, 1.2, 4.10
- **Made:** 2026-10-11, by the owner: "the vlans will have a subnet assigned and it will route through a gateway, a
  dhcp helper rule will be needed on my router to assist"; who routes and enforces: "unifi".
- **Why:** the owner's network is UniFi with 802.1X and VLAN segmentation (2.3.1.10); its gateway already routes.
- **Status:** In force; to build in 0.8.0 ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).

## 2.1.10.9 One /24 per VLAN, the VLAN ID its third octet

- **Decision:** "micro segmentation" is many small subnets, one per VLAN, not client classes inside one subnet. The
  convention fabric suggests: a /24 per VLAN whose third octet is the VLAN ID (VLAN 10, management:
  `10.<site>.10.0/24`; VLAN 255, storage: `10.<site>.255.0/24`). A suggestion, never forced: any subnet may be
  entered.
- **Shapes:** 1.10
- **Made:** 2026-10-11, by the owner: "many subnets e.g. mgmt is 10, 255 is storage (3rd octet with a /24)".
- **Why:** an address names its VLAN at a glance; four houses stay apart by their second octet (2.1.10.12).
- **Status:** In force; to build in 0.8.0 ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).

## 2.1.10.10 0.8.0 is an address manager (IPAM), every address tracked, delivered whole

- **Decision:** fabric's DHCP becomes an address manager: every site's VLANs and subnets, their ranges (the gateway,
  static ranges, DHCP pools, reserved), and **every address**: static ones (with owner, MAC, name, notes, optionally
  published in DNS), reservations and live leases, shown together; an address claimed twice is refused. Subnets
  and the address manager are not split across releases: 0.8.0 carries all of it.
- **Shapes:** 1.10, 1.4, 1.8, 1.9
- **Made:** 2026-10-11, by the owner: "the subnet should not spit between releases, also this should look kind of
  like an IPAM solution so I can track all my IPs including static".
- **Why:** with dozens of VLANs over four houses, a spreadsheet beside fabric would drift.
- **Status:** In force; to build in 0.8.0 once 2.1.10.11 to 2.1.10.13 are answered ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).

## 2.1.10.11 Where the address plan is kept

- **Decision:** to be made. Options ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)):
  - **A, recommended:** in AD, as today's address plan (1.10.2.8): each site's VLANs, ranges and static addresses
    are objects in its own `OU=networks`; every DC holds the whole plan. The owner, at the top, edits a house's plan
    on any writable DC and it replicates; each site's fabric renders Kea and its DNS from its own OU when it
    changes. No new replication to build.
  - **B:** each site's `vars.yaml` stays the truth for its own Kea; the top edits a house through its federation
    endpoint (an apply at that site); the plan in AD stays a copy.
  - **C:** fabric's database (1.9.8.16), replicated along the site tree; one writer per row, so an edit from the
    top would be the top's row, not the house's.
- **Shapes:** 1.10, 1.9, 1.6
- **Made:** open since 2026-10-11.
- **Why:** the owner edits four houses from the top (2.1.9.5, 2.1.9.19); where the plan lives decides how.
- **Status:** Open: waits for the owner.

## 2.1.10.12 Each site's address block

- **Decision:** to be made. Proposed: each site gets a `/16` block from the organisation's private range (the root
  `10.1.0.0/16`, the next site `10.2.0.0/16`, ...), chosen at install or join, permanent, refused if another
  site's block overlaps; with 2.1.10.9 a VLAN's subnet is suggested from it (`10.<n>.<VLAN>.0/24`). A house whose
  LAN already uses another range keeps it: the block is a suggestion source, not a fence.
- **Shapes:** 1.10, 1.9
- **Made:** open since 2026-10-11 ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).
- **Why:** four houses, one /16 each, never collide and read at a glance.
- **Status:** Open: waits for the owner.

## 2.1.10.13 Finding addresses in use that nobody recorded

- **Decision:** to be made. Options ([2.3.10.3](2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)):
  - **A, recommended:** before Kea hands out an address it pings it, and skips one that answers (Kea's ping-check
    hook, open-source in Kea 3.0); such an address is listed in the plan as "in use, unrecorded" for the owner to
    claim. Nothing scans.
  - **B:** A, plus a scan of a subnet on request (ping and ARP from fabric's host; a routed VLAN only answers
    pings the gateway lets through).
  - **C:** neither: only what is recorded or leased is known.
- **Shapes:** 1.10
- **Made:** open since 2026-10-11.
- **Why:** an IPAM is only as good as what it knows; statics set by hand on devices are the usual conflict.
- **Status:** Open: waits for the owner.

## 2.1.10.14 DHCP options are part of the plan, with netboot presets

- **Decision:** 0.8.0's address manager carries DHCP options at every level (organisation, site, subnet, client
  class, address; the most specific wins), any option by name or code with custom definitions, and the options a
  subnet or address ends up with shown with where each came from. Netboot presets (PXE for BIOS and UEFI by client
  architecture, iPXE chain-loading, UEFI HTTP boot) can be switched on per VLAN or address, pointing at a boot
  server ([2.3.10.3.10](2.3.10-dhcp-notes.md#2310310-dhcp-options-and-netboot)).
- **Shapes:** 1.10
- **Made:** 2026-10-11, by the owner: "a critical component to dhcp..... Dhcp options, I will likely want to include
  options for netboot".
- **Why:** options are what make DHCP useful beyond addresses; netboot needs per-architecture answers.
- **Status:** In force; to build in 0.8.0 with the rest of 2.1.10.10.

## 2.1.10.15 Whether fabric serves the netboot files

- **Decision:** to be made. Options ([2.3.10.3.10](2.3.10-dhcp-notes.md#2310310-dhcp-options-and-netboot)):
  - **A, recommended for 0.8.0:** fabric's DHCP points at a boot server the owner runs (a NAS, a container of
    their own); 1.10.2.7 stays.
  - **B:** fabric adds an optional boot service (TFTP and HTTP in a container, netboot.xyz or the owner's images),
    as its own optional part, in 0.8.0 or after.
- **Shapes:** 1.10, 1.2
- **Made:** open since 2026-10-11.
- **Why:** B is a new service to secure and keep updated; A needs one box the owner may already have.
- **Status:** Open: waits for the owner.

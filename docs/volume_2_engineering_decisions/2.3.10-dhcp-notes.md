## 2.3.10.2 0.8 on the lab: what the baseline showed, and the results

**Baseline (2026-10-10, before any 0.8 change).** Fabric on a Hyper-V Ubuntu 24.04 server serving its second
interface (`eth1`, `10.20.0.10/24`, an isolated switch with no router, 2.3.1.9.6), Ubuntu desktops as clients. Kea
served `eth1` and leases and their names in `dhcp.<domain>` worked; but every client was told to use `host_ip` (on
the server's other network, unreachable) for DNS and time, and fabric neither listened on `10.20.0.10` nor let the
lab's clients in: no DNS, no certificate page. Hence 1.10.3.2 and 1.10.3.3.

**Found while building, on the lab:**
- fabric's names (`info.`, `certs.`, `fabric.`) pointed lab clients at `host_ip`, out of their reach. Answering each
  network with its own address needs BIND's `sortlist` (deprecated in 9.20) or a view per network; instead each
  subnet served from another address gets option 121, `host_ip/32` via fabric's address there (1.10.3.3).
- Kea's lease caching (`cache-threshold`, on by default) reused a recent lease without any DNS update, so a renewal
  never registered the PTR; off (`0.0`: Kea refuses the integer `0`).
- A lookup of a name before its registration was cached "no such name" for the reverse zone's negative TTL, a day;
  DHCP's reverse zones now say 300 s, as `dhcp.<domain>` does.
- An apply left the unit of an optional part turned off running (Kea on its old configuration); and a DHCP subnet
  added from the console waited for the next setup for its firewall rules. Both fixed (1.10.3.5).
- The suite's own helper hid exit codes behind its output filter (a quiet command looked failed, a negated one
  passed); fixed before the results below.

**Results:** `tests/lab/dhcp.sh` on `g23-vm-ub24-1` with `g23-vm-ub22-1` (22.04) and `g23-vm-ub20-1` (20.04) as
clients: a fresh run 25 passed, 2 failed (20.04 has no `curl`; the helper above); after the fixes, **25 passed, 0
failed** on the same install (`REUSE=1`: the two install checks the fresh run passed are skipped). The render, zone,
Kea (real Kea and BIND: the PTR registered, the key refused anything but PTR and DHCID in the reverse zone),
resolver, consent and web suites pass.

**The sandbox on `dev/0.8`:** a first run 181 passed, 2 failed, from one cause: the sandbox's second subnet, behind a
router's relay and on none of the host's interfaces, was refused at apply after `add-subnet` had saved it, so every
later apply failed. Such a subnet is simply relayed (Kea picks it by the relay's address); fixed (1.10.3.2). **Rerun:
183 passed, 0 failed.**

## 2.3.10.3 Proposal: 0.8.0, an address manager for VLAN-segmented sites

Written 2026-10-11 from the owner's answers (2.1.10.8 to 2.1.10.10, 2.1.9.19). Nothing is built from it until its
open points (2.3.10.3.9) are answered and it is written into Volume 1 (a new 1.10.4, revising 1.10.2's settings).

### 2.3.10.3.1 What the owner described

- A UniFi network at home with 802.1X and VLAN segmentation; many small subnets, one /24 per VLAN, the VLAN ID the
  third octet (management 10, storage 255); every VLAN served by fabric's Kea through the gateway's DHCP relay; the
  gateway routes and enforces policy between VLANs.
- The same at both parents' houses and the owner's brother's: four sites, the owner at the top editing all of them.
- An IPAM: every address tracked, static ones too; subnets delivered whole in one release.

### 2.3.10.3.2 What fabric has today

- Kea serves the host's LAN and any subnet behind a relay, picked by the relay's address (1.10.3.2); subnets carry a
  name, VLAN (a record), notes, pools, reservations and any DHCP option (1.10.2.3), all in the site's `vars.yaml`.
- The address plan across sites: each site writes its networks to its own `OU=networks` in AD on every apply, every
  DC holds all of them, overlaps between sites are refused (1.10.2.6, 1.10.2.8). It is a copy, written from vars.
- Static names live in fabric's DNS zones (`dns:` in vars); a static address has no record of its own beyond that.
- Reverse zones are generated, DHCP's PTRs kept across applies (2.1.10.7); a served subnet's clients reach fabric's
  services (1.10.3.3); the DNS filter's groups can name a subnet or a VLAN (1.10.3.7).

What is missing: ranges other than pools, static addresses as records of their own, leases shown beside them, the
VLAN convention, a site's block, finding conflicts, and editing another site's plan.

### 2.3.10.3.3 The model

Per site (each object owned by its site; the top may edit any, 2.1.9.5):

| Object | Holds |
|---|---|
| **Block** | the site's `/16` (2.1.10.12): suggestions come from it |
| **VLAN** | ID (1-4094, unique per site), name (unique per site), purpose and notes, `access` (full or guest, 1.10.3.3) |
| **Subnet** | one per VLAN by default (a VLAN with none is allowed: a record only); CIDR, gateway (the router's address in it), served by DHCP or not, DHCP options |
| **Range** | inside a subnet, never overlapping another: `gateway`, `static` (addresses set by hand), `dhcp` (Kea's pool), `reserved` (kept free) |
| **Address** | one IP: kind (`static`, `reservation`, `infrastructure`), name, MAC, owner, notes, DNS (an A and PTR in fabric's zone, or none) |
| **Lease** | live, from Kea (not stored): shown with the address it holds; its name in `dhcp.<domain>` as today |

Rules: an address in a `dhcp` range may only be a reservation; a `static` address lies in a `static` range (or is
warned about); one IP, one claim (static, reservation or the gateway), a second refused; a subnet overlapping another
anywhere in the organisation is refused (as today; `--allow-overlap` kept). A new VLAN is offered the convention:
VLAN `n` gets `10.<site>.<n>.0/24`, gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254` (the
split editable).

### 2.3.10.3.4 How a VLAN is served

- **Relay:** each VLAN's gateway relays DHCP to fabric's `host_ip` (2.1.10.8); Kea picks the subnet by the relay's
  address (the gateway, inside the subnet). fabric opens 67/udp to the gateways' addresses (the `ports` consent
  group, as 1.10.3.5). The UniFi steps (per network: DHCP mode "relay", server `host_ip`) go in Volume 4.
- **What a VLAN's clients get:** the gateway as router, fabric as DNS and NTP (2.1.10.5), the domain and search
  list; `access: guest` VLANs only DNS and NTP (1.10.3.3). fabric's names stay on `host_ip`, reached through the
  gateway (no option 121 route is needed when the gateway routes to the host's LAN).
- **DNS:** a static address with DNS on gets an A in the site's zone and a PTR in its reverse zone (one reverse zone
  per /24, so per VLAN); leases register in `dhcp.<domain>` and their PTRs as today.
- **802.1X:** a role's VLAN (1.11) names a VLAN of the plan, so the console shows "VLAN 20 (iot, 10.1.20.0/24)".
- **The DNS filter's groups** by VLAN keep working (1.10.3.7).

### 2.3.10.3.5 Editing a house from the top

With 2.1.10.11's option A (recommended), the plan's objects live in AD in each site's `OU=networks`; the owner's
roles at the root already have rights over every site below (2.1.9.13). An edit from the top's console writes the
house's objects on the top's DC; replication carries it to the house (1.9.8.5); the house's fabric sees its OU
change (a poll of its DC's highest USN, every 30 s) and renders and restarts Kea through its control socket
(2.1.10.6), its DNS and the access lists. A house cut off from the top keeps serving from its own copy, and its own
edits merge when the link is back (AD keeps the last writer per attribute; the console names a conflict object if
one appears). A site with a read-only DC has no local writes (1.9.8.3): its plan is edited from a writable DC above.

Under option B instead, the top's console sends each edit to the house's federation endpoint, which applies it
there; a house cut off cannot be edited until it is back.

### 2.3.10.3.6 The console and the command line

- **A Networks tab** (replacing the Kea tab's subnet parts): sites (for the top, every house), then VLANs, then a
  subnet's map (its ranges as a bar, used and free) and its address table (static, reservation, lease, unrecorded,
  free; search by IP, name or MAC; export as CSV). Behind `dhcp:read` and `dhcp:write`; a house's admin sees only
  its own house.
- **`fabricctl ipam`:** `vlan add|set|remove`, `range add|remove`, `address add|set|remove`, `show [<site>]`,
  `find <ip|name|mac>`, `export`; `--site` for the top. Every entry point gets positive and negative tests (Rule 9).
- Today's `fabricctl dhcp add-subnet` and the other subnet commands become aliases of the new ones for one release,
  then go.

### 2.3.10.3.7 Tests

- Unit: the model's rules (overlaps, one claim per IP, ranges inside their subnet, the convention).
- Real containers: Kea rendered from the plan answering a relayed request on each VLAN (a relay container on each
  of three Docker networks), DNS and PTR for a static address, a lease shown beside the plan, a conflict refused.
- Two sites (the `site_join` suite's setup): an edit at the root reaches the site's Kea.
- The Incus test bed (2.1.1.45, after 0.7.0): a routed lab with a relaying gateway and real clients on two VLANs.

### 2.3.10.3.8 Impact assessment

- **Architecture:** under 2.1.10.11 A, the address plan's truth moves from each site's `vars.yaml` to AD; vars keep
  only what is the host's own (the interfaces Kea listens on, global options). An apply reads the plan from AD; a
  site whose DC is down keeps its last rendering. New schema: VLAN, range and address classes in fabric's OID arc
  (the schema-update path fixed in 0.7.0, 1.6.5.24).
- **Breaking:** `dhcp.subnets` in vars is moved into the plan at the upgrade (once, recorded) and stops being read;
  the `fabricctl dhcp` subnet commands change (aliases for one release); the Kea tab is replaced.
- **Scope creep risk:** high if finding addresses grows into network scanning (2.1.10.13 keeps it to Kea's ping
  check), or if fabric starts configuring the UniFi gateway (out of scope: 2.1.10.8).
- **Release:** all of it in 0.8.0 (2.1.10.10), the Incus lab run as its gate once Incus exists.

### 2.3.10.3.10 DHCP options and netboot

Added 2026-10-11 by the owner: "a critical component to dhcp..... Dhcp options, I will likely want to include
options for netboot" (2.1.10.14).

- **Options at every level of the plan:** the organisation (every site), a site, a VLAN's subnet, a client class, an
  address (a reservation). Most specific wins, as in Kea; the console shows, for a subnet or an address, the options
  it ends up with and where each came from. Any option, by name or code, with custom definitions for codes Kea has
  no name for (1.10.2.3 already renders all of this from vars; it moves into the plan).
- **Netboot presets** a VLAN or address can switch on, each a set of client classes and options the owner can edit:
  - **PXE, BIOS and UEFI:** classes on the client's architecture (option 93: 0 BIOS, 7 and 9 x64 UEFI, 11 arm64
    UEFI), each with its own `boot-file-name` and `next-server` (siaddr) and option 66;
  - **iPXE chain-load:** a client already running iPXE (user class `iPXE`, option 77) gets the iPXE script's URL
    instead of the iPXE binary, so it does not loop;
  - **UEFI HTTP boot:** vendor class `HTTPClient` gets an `http://` boot URL and option 60 echoed back.
  The boot server is a setting of the preset (an address, or a name in fabric's DNS).
- **Who serves the files:** fabric's DHCP points at a boot server; whether fabric also runs one (a TFTP and HTTP
  container with netboot.xyz or the owner's images) is 2.1.10.15. 1.10.2.7 keeps serving boot files out of scope
  until then.
- **Tests:** a BIOS, a UEFI and an iPXE client (dhcping or a Kea test client with options 93 and 77 set) each given
  its own boot file; an option set at a subnet overridden at an address; an option with a code Kea does not know,
  defined and sent.

## 2.3.10.4 The address manager, phase 1: open points and results

Phase 1 of [1.10.4](../volume_1_description_and_architecture/1.10.4-address-manager.md) was built 2026-10-12 on
`dev/0.8.0-ipam` (what it holds: 1.10.4.17). Where 1.10.4 left a choice that would have needed new design, the
smallest choice consistent with it was built and the question is here for the owner; nothing below blocks phase 1.

### 2.3.10.4.1 Where the site's number is asked

1.10.4.10 says the site's number "is asked once (the suggestion: its order in the organisation)", and 2.1.10.12 says
it is "chosen at install or join". Setup asks its questions before the domain controller runs, and a joining site
learns the organisation's sites only at its join, so neither is a place where the order (or a free number) is known.
**Built for now:** fabric gives the site the suggestion without asking, the first time it needs one (the upgrade, or
`vlan add` with no `--subnet`), and says so; `show` prints it (1.10.4.13.4). **Open:** A) a question at setup's start
step, after the DC runs and before the upgrade (one short line, the suggestion as its default); B) a command,
`fabricctl ipam block <n>` (and the Networks tab), the number given automatically until then; C) both.
**Settled 2026-10-12 by the owner: C, both** ([2.1.10.16](2.1.10-dhcp.md#211016-where-the-sites-number-is-asked-at-setup-and-by-a-command)).

### 2.3.10.4.2 A reservation's name in DNS

1.10.4.3.1 gives every address "DNS (an A and a PTR in fabric's zone, or none)", while 1.10.4.5 publishes a static
address's name in the site's zone and registers leases (a reservation's among them) in `dhcp.<domain>`. **Built for
now:** DNS on a reservation is refused ("its name is registered by DHCP in dhcp.<domain>"); a reservation's name goes
to Kea as its hostname, as in 0.7. **Open:** A) keep it so; B) a reservation with DNS on also gets an A in the site's
zone (a second name for the same device, under the site's own domain). **Settled 2026-10-12 by the owner: B**
([2.1.10.17](2.1.10-dhcp.md#211017-a-reservations-name-may-be-published-in-the-sites-zone-too)); its PTR:
2.3.10.4.6.

### 2.3.10.4.3 More than one subnet per VLAN

1.10.4.3.1 says "one per VLAN by default", which allows more, but the commands of 1.10.4.9 have no way to add a second
(`vlan add` makes the VLAN's subnet). **Built for now:** at most one subnet per VLAN; `vlan set` changes the subnet's
gateway, DHCP, relay and overlap reason, not its network. **Open:** A) one subnet per VLAN, always (the convention of
2.1.10.9); B) a `subnet add|set|remove <vlan>` command (a secondary network on the same VLAN, e.g. while renumbering).
**Settled 2026-10-12 by the owner: B, allow more** ([2.1.10.18](2.1.10-dhcp.md#211018-more-than-one-subnet-per-vlan)).

### 2.3.10.4.4 The upgrade at a site with a read-only DC

1.10.2.8 says a read-only site writes its networks through its parent's agent over the federation endpoint; that
path is S8 and not built. **Built for now:** at a site whose DC is read-only the upgrade cannot write, so the subnets
stay in its settings and each apply says so (1.10.4.15); Kea keeps serving them from the settings. **Open:** A) build
the parent's write path (S8) in 0.8.0; B) the owner moves such a site's subnets from the top (`fabricctl ipam vlan add
--site`) and removes them from its settings by hand, a procedure in 4.10.2; C) leave it until S8.
**Settled 2026-10-12 by the owner: C, wait** ([2.1.10.19](2.1.10-dhcp.md#211019-the-upgrade-at-a-site-with-a-read-only-dc-waits-for-the-parents-write-path));
nothing more is built for it until S8.

### 2.3.10.4.6 A published reservation's PTR

2.1.10.17 publishes a reservation with DNS on as an A record of the site's zone "and its PTR". The address has one
PTR, and two writers want it: fabric's generated reverse zone (the site's name, `cam3.<domain>`) and Kea, which
registers the lease's PTR (`cam3.dhcp.<domain>`), replacing whatever PTR the address had, at every lease and renewal
(`ddns-update-on-renew` is on in fabric's Kea configuration). **Built for now:** fabric's PTR, as for every static
name: each apply writes it and it wins over a registration kept from DHCP (`merge_dynamic_records`, 2.1.10.7); from
the device's next renewal until the next apply the PTR names `dhcp.<domain>` again. Both forward names are right
throughout. **Open:** A) keep it so; B) the PTR stays DHCP's (no PTR from the site's zone for a reservation); C)
fabric's PTR always, Kea told not to update the reverse zone for such a reservation (a client class with Kea's DDNS
settings, if Kea 3.0 allows them per class: to be checked). **Settled 2026-10-12 by the owner: C**, as a general
rule, "Manually set in DNS is strongest authority" ([2.1.10.20](2.1.10-dhcp.md#211020-a-dns-record-set-by-hand-outranks-dhcps-updates));
how it is built: 2.3.10.4.8.

### 2.3.10.4.8 A name set by hand outranks DHCP's: how Kea is kept off it, and results

2.1.10.20, built 2026-10-12. What Kea 3.0.4 (fabric's pinned image) offers, tried with `kea-dhcp4 -t`:

- DDNS settings in a client class (`"ddns-send-updates": false` on a class a reservation names): **refused**,
  "got unexpected keyword "ddns-send-updates" in client-classes map". Kea 3.0 has DDNS settings globally, per shared
  network and per subnet only; a reservation has none.
- The `SKIP_DDNS` class with the ddns-tuning hook (`libdhcp_ddns_tuning.so`, open source since Kea 3.0 and in
  fabric's image): a reservation names the class in its `client-classes`, and Kea sends no DNS update for that
  client, forward or reverse. Accepted by `-t`, and on a real lease in the `kea` suite the reserved client got its
  address while neither `cam3.dhcp.<domain>` nor the address's PTR was registered (the reservation beside it, not in
  the class, was registered as before). This is what is built. Kea cannot skip the reverse update alone, so such a
  reservation has no name in `dhcp.<domain>` (2.1.10.20 revises 2.1.10.17).

Built: a reservation is `"ddns": false` when the address manager publishes it (DNS on) or when any record set by hand
(an A record of fabric's zones) names its address (`normalize_dhcp`); the Kea template puts it in `SKIP_DDNS` and
loads the hook only then; Kea's reverse zones leave such addresses out. And, in BIND, every reverse name whose PTR
fabric generates from a record set by hand gets `deny "kea-ddns" name <name> ANY` before the zone's grant, so even
a stray update from Kea's key is refused (the `kea` suite's `nsupdate` with Kea's key was refused and the PTR set by
hand stayed).

What else was checked in fabric's DHCP path:
- Forward: Kea's key may write only `dhcp.<domain>` (A, AAAA, DHCID); every zone set by hand is out of its reach
  (the `kea` suite already proves a write to `lan.test` refused).
- Reverse: fabric regenerates its reverse zones at each apply and keeps Kea's records only at names it has no PTR
  for (`merge_dynamic_records`, 2.1.10.7); with the deny rules Kea can no longer replace one between applies.
- Pools: an A record set by hand inside a pool is still refused unless the address is a reservation's (which is then
  kept from Kea as above).
- Two findings recorded as open points: 2.3.10.4.9 and 2.3.10.4.10.

Found while building: the ddns-tuning hook refuses to load without a `parameters` map ("params must not be null")
and Kea then does not start, yet `kea-dhcp4 -t` (fabric's check before it writes Kea's configuration,
`check_kea_config`) accepted the configuration: the config test does not load hook libraries. The first suite run
caught it (Kea did not start); the template now gives the hook an empty map. A hook added later needs the same
proof: the real server started in the `kea` suite, not only `-t`.

Results, WSL Ubuntu 24.04 (x86_64), Docker: `tests/run-all.sh docs ipam render consent kea samba zones` passed all but

### 2.3.10.6.1 Kea's ping_check hook: the vendor's facts

- **Available and open source in the Kea fabric runs (3.0.4, `config/images.lock.yaml`).** ISC's Kea 3.0.0
  Administrator Reference Manual, [Hook Libraries](https://kea.readthedocs.io/en/kea-3.0.0/arm/hooks.html): the hook
  table lists Ping Check as "Kea open source"; its section (libdhcp_ping_check.so) says it was added in Kea 2.5.4,
  first only for ISC's support customers, and is now part of the open-source code; the installed list of open-source
  hooks includes `libdhcp_ping_check.so`. ISC moved most hooks into the open-source packages with 3.0
  ([2.3.10.1](#23101-references)); fabric's image already installs `isc-kea-hooks` (the lease_cmds, stat_cmds and
  ddns_tuning hooks come from it). Not confirmed from a package listing: the `kea` suite's `kea-dhcp4 -t` of a
  configuration that loads the hook (`tests/kea/scan.py`) proves it is in the package; if it were not, Kea's check
  refuses the configuration before anything is written, and `dhcp.ping_check: false` is the way round it.
- **What it does (same page).** `kea-dhcp4` only; the offer is parked while ICMP echo requests go out; an ECHO REPLY
  means the address is in use: the offer is dropped and a DECLINED lease is made for the address; an ICMP
  "unreachable", a send error or a full socket buffer counts as free. Parameters `enable-ping-check`,
  `min-ping-requests` (1), `reply-timeout` (100 ms), `ping-cltt-secs` (60), `ping-channel-threads` (0: as many as
  Kea's own; global only). ISC does not recommend it for high-throughput servers.
- **The per-subnet form is disputed.** The ARM shows the parameters flat in a subnet's `user-context`; a user reported
  on kea-users that the code expects them in a nested `ping-check` map, and ISC called it a documentation error
  (issue #4106): [kea-users, 2025-08](https://lists.isc.org/pipermail/kea-users/2025-August/005728.html),
  [the reply, 2025-09](https://lists.isc.org/pipermail/kea-users/2025-September/005747.html). fabric therefore sets
  only the global parameters, and never writes `user-context` keys for the hook (fabric's subnets already carry
  `name`, `vlan` and `notes` there, which the hook ignores). The defaults of the hook's configuration code:
  [ping_check_config.cc](https://reports.kea.isc.org/dev_guide/d2/df8/ping__check__config_8cc_source.html).

### 2.3.10.9.2 How AD expresses "the parent may, the branch may not"

A site's agent and OU admins hold full control of their own OU, inherited, without the rights to change permissions or
the owner (`FULL`, 2.1.6.20); the sites above hold the same, inherited from their own OUs. An explicit deny entry on the
branch's OU is evaluated before the full control the branch inherits there and before the parent's inherited grant
(Microsoft, [Order of ACEs in a DACL](https://learn.microsoft.com/en-us/windows/win32/secauthz/order-of-aces-in-a-dacl):
explicit entries before inherited ones, deny before allow within each, nearer parents first), and the branch cannot
remove it. So the setting lives on the branch's OU (the brief's first choice); the parent-side store the brief allowed
as a fallback was not needed. The create deny on `OU=networks` is inherited by the subnets' entries (one level nearer
than the branch's grant, so it comes first). A request's owner is its creator, which no account below can change
without the right to take ownership; the branch's poll checks it as well, so a request written by hand with a domain
admin's rights is refused, not run. Siblings: no entry grants a site anything outside its own OU, so a sibling has no
access to the branch at all (the `samba` suite's negative cases prove each of these at a real DC; not run).

Not covered: a site whose DC is read-only converges only winbind's pipe (`converge.py`), so `ensure_site_acl`, and
with it these entries, are not written by that site; where a read-only site's access entries come from was not
checked by this build, and that place needs these too (open point 4). Root on a writable DC's host can change anything in its own replica:
the rule binds fabric-agent and the console, not the host's root.

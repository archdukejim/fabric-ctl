## 2.3.10.2 0.8 on the lab: what the baseline showed, and the results

**Baseline (2026-10-10, before any 0.8 change).** Fabric on a Hyper-V Ubuntu 24.04 server serving its second
interface (`eth1`, `10.20.0.10/24`, an isolated switch with no router, 2.3.1.9.6), Ubuntu desktops as clients. Kea
served `eth1` and leases and their names in `dhcp.<domain>` worked; but every client was told to use `host_ip` (on
the server's other network, unreachable) for DNS and time, and fabric neither listened on `10.20.0.10` nor let the
lab's clients in: no DNS, no certificate page. Hence 1.10.3.2 and 1.10.3.3.

**Found while building, on the lab:**
- fabric's names (`info.`, `certs.`, `fabric.`) pointed lab clients at `host_ip`, out of their reach. Answering each
  network with its own address needs BIND's `sortlist` (deprecated in 9.20) or a view per network; instead each
  subnet served from another address gets option 121, `host_ip/32` via fabric's address there (1.10.3.3).
- Kea's lease caching (`cache-threshold`, on by default) reused a recent lease without any DNS update, so a renewal
  never registered the PTR; off (`0.0`: Kea refuses the integer `0`).
- A lookup of a name before its registration was cached "no such name" for the reverse zone's negative TTL, a day;
  DHCP's reverse zones now say 300 s, as `dhcp.<domain>` does.
- An apply left the unit of an optional part turned off running (Kea on its old configuration); and a DHCP subnet
  added from the console waited for the next setup for its firewall rules. Both fixed (1.10.3.5).
- The suite's own helper hid exit codes behind its output filter (a quiet command looked failed, a negated one
  passed); fixed before the results below.

**Results:** `tests/lab/dhcp.sh` on `g23-vm-ub24-1` with `g23-vm-ub22-1` (22.04) and `g23-vm-ub20-1` (20.04) as
clients: a fresh run 25 passed, 2 failed (20.04 has no `curl`; the helper above); after the fixes, **25 passed, 0
failed** on the same install (`REUSE=1`: the two install checks the fresh run passed are skipped). The render, zone,
Kea (real Kea and BIND: the PTR registered, the key refused anything but PTR and DHCID in the reverse zone),
resolver, consent and web suites pass.

**The sandbox on `dev/0.8`:** a first run 181 passed, 2 failed, from one cause: the sandbox's second subnet, behind a
router's relay and on none of the host's interfaces, was refused at apply after `add-subnet` had saved it, so every
later apply failed. Such a subnet is simply relayed (Kea picks it by the relay's address); fixed (1.10.3.2). **Rerun:
183 passed, 0 failed.**

## 2.3.10.3 Proposal: 0.8.0, an address manager for VLAN-segmented sites

Written 2026-10-11 from the owner's answers (2.1.10.8 to 2.1.10.10, 2.1.9.19). Nothing is built from it until its
open points (2.3.10.3.9) are answered and it is written into Volume 1 (a new 1.10.4, revising 1.10.2's settings).

### 2.3.10.3.1 What the owner described

- A UniFi network at home with 802.1X and VLAN segmentation; many small subnets, one /24 per VLAN, the VLAN ID the
  third octet (management 10, storage 255); every VLAN served by fabric's Kea through the gateway's DHCP relay; the
  gateway routes and enforces policy between VLANs.
- The same at both parents' houses and the owner's brother's: four sites, the owner at the top editing all of them.
- An IPAM: every address tracked, static ones too; subnets delivered whole in one release.

### 2.3.10.3.2 What fabric has today

- Kea serves the host's LAN and any subnet behind a relay, picked by the relay's address (1.10.3.2); subnets carry a
  name, VLAN (a record), notes, pools, reservations and any DHCP option (1.10.2.3), all in the site's `vars.yaml`.
- The address plan across sites: each site writes its networks to its own `OU=networks` in AD on every apply, every
  DC holds all of them, overlaps between sites are refused (1.10.2.6, 1.10.2.8). It is a copy, written from vars.
- Static names live in fabric's DNS zones (`dns:` in vars); a static address has no record of its own beyond that.
- Reverse zones are generated, DHCP's PTRs kept across applies (2.1.10.7); a served subnet's clients reach fabric's
  services (1.10.3.3); the DNS filter's groups can name a subnet or a VLAN (1.10.3.7).

What is missing: ranges other than pools, static addresses as records of their own, leases shown beside them, the
VLAN convention, a site's block, finding conflicts, and editing another site's plan.

### 2.3.10.3.3 The model

Per site (each object owned by its site; the top may edit any, 2.1.9.5):

| Object | Holds |
|---|---|
| **Block** | the site's `/16` (2.1.10.12): suggestions come from it |
| **VLAN** | ID (1-4094, unique per site), name (unique per site), purpose and notes, `access` (full or guest, 1.10.3.3) |
| **Subnet** | one per VLAN by default (a VLAN with none is allowed: a record only); CIDR, gateway (the router's address in it), served by DHCP or not, DHCP options |
| **Range** | inside a subnet, never overlapping another: `gateway`, `static` (addresses set by hand), `dhcp` (Kea's pool), `reserved` (kept free) |
| **Address** | one IP: kind (`static`, `reservation`, `infrastructure`), name, MAC, owner, notes, DNS (an A and PTR in fabric's zone, or none) |
| **Lease** | live, from Kea (not stored): shown with the address it holds; its name in `dhcp.<domain>` as today |

Rules: an address in a `dhcp` range may only be a reservation; a `static` address lies in a `static` range (or is
warned about); one IP, one claim (static, reservation or the gateway), a second refused; a subnet overlapping another
anywhere in the organisation is refused (as today; `--allow-overlap` kept). A new VLAN is offered the convention:
VLAN `n` gets `10.<site>.<n>.0/24`, gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254` (the
split editable).

### 2.3.10.3.4 How a VLAN is served

- **Relay:** each VLAN's gateway relays DHCP to fabric's `host_ip` (2.1.10.8); Kea picks the subnet by the relay's
  address (the gateway, inside the subnet). fabric opens 67/udp to the gateways' addresses (the `ports` consent
  group, as 1.10.3.5). The UniFi steps (per network: DHCP mode "relay", server `host_ip`) go in Volume 4.
- **What a VLAN's clients get:** the gateway as router, fabric as DNS and NTP (2.1.10.5), the domain and search
  list; `access: guest` VLANs only DNS and NTP (1.10.3.3). fabric's names stay on `host_ip`, reached through the
  gateway (no option 121 route is needed when the gateway routes to the host's LAN).
- **DNS:** a static address with DNS on gets an A in the site's zone and a PTR in its reverse zone (one reverse zone
  per /24, so per VLAN); leases register in `dhcp.<domain>` and their PTRs as today.
- **802.1X:** a role's VLAN (1.11) names a VLAN of the plan, so the console shows "VLAN 20 (iot, 10.1.20.0/24)".
- **The DNS filter's groups** by VLAN keep working (1.10.3.7).

### 2.3.10.3.5 Editing a house from the top

With 2.1.10.11's option A (recommended), the plan's objects live in AD in each site's `OU=networks`; the owner's
roles at the root already have rights over every site below (2.1.9.13). An edit from the top's console writes the
house's objects on the top's DC; replication carries it to the house (1.9.8.5); the house's fabric sees its OU
change (a poll of its DC's highest USN, every 30 s) and renders and restarts Kea through its control socket
(2.1.10.6), its DNS and the access lists. A house cut off from the top keeps serving from its own copy, and its own
edits merge when the link is back (AD keeps the last writer per attribute; the console names a conflict object if
one appears). A site with a read-only DC has no local writes (1.9.8.3): its plan is edited from a writable DC above.

Under option B instead, the top's console sends each edit to the house's federation endpoint, which applies it
there; a house cut off cannot be edited until it is back.

### 2.3.10.3.6 The console and the command line

- **A Networks tab** (replacing the Kea tab's subnet parts): sites (for the top, every house), then VLANs, then a
  subnet's map (its ranges as a bar, used and free) and its address table (static, reservation, lease, unrecorded,
  free; search by IP, name or MAC; export as CSV). Behind `dhcp:read` and `dhcp:write`; a house's admin sees only
  its own house.
- **`fabricctl ipam`:** `vlan add|set|remove`, `range add|remove`, `address add|set|remove`, `show [<site>]`,
  `find <ip|name|mac>`, `export`; `--site` for the top. Every entry point gets positive and negative tests (Rule 9).
- Today's `fabricctl dhcp add-subnet` and the other subnet commands become aliases of the new ones for one release,
  then go.

### 2.3.10.3.7 Tests

- Unit: the model's rules (overlaps, one claim per IP, ranges inside their subnet, the convention).
- Real containers: Kea rendered from the plan answering a relayed request on each VLAN (a relay container on each
  of three Docker networks), DNS and PTR for a static address, a lease shown beside the plan, a conflict refused.
- Two sites (the `site_join` suite's setup): an edit at the root reaches the site's Kea.
- The Incus test bed (2.1.1.45, after 0.7.0): a routed lab with a relaying gateway and real clients on two VLANs.

### 2.3.10.3.8 Impact assessment

- **Architecture:** under 2.1.10.11 A, the address plan's truth moves from each site's `vars.yaml` to AD; vars keep
  only what is the host's own (the interfaces Kea listens on, global options). An apply reads the plan from AD; a
  site whose DC is down keeps its last rendering. New schema: VLAN, range and address classes in fabric's OID arc
  (the schema-update path fixed in 0.7.0, 1.6.5.24).
- **Breaking:** `dhcp.subnets` in vars is moved into the plan at the upgrade (once, recorded) and stops being read;
  the `fabricctl dhcp` subnet commands change (aliases for one release); the Kea tab is replaced.
- **Scope creep risk:** high if finding addresses grows into network scanning (2.1.10.13 keeps it to Kea's ping
  check), or if fabric starts configuring the UniFi gateway (out of scope: 2.1.10.8).
- **Release:** all of it in 0.8.0 (2.1.10.10), the Incus lab run as its gate once Incus exists.

### 2.3.10.3.9 For the owner to decide

1. Where the plan is kept: AD (recommended), each site's vars, or fabric's database (2.1.10.11).
2. Each site's `/16` block from `10.0.0.0/8`, chosen at install or join (2.1.10.12).
3. Unrecorded addresses: Kea's ping check (recommended), a scan on request too, or neither (2.1.10.13).
4. The default split of a /24: gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254`.

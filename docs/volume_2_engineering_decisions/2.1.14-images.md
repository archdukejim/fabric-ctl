## 2.1.14.1 Updates

- **Decision:** fabric updater + local registry; no Watchtower ([1.14.1.1](../volume_1_description_and_architecture/1.14.1-image-channels.md#11411-image-channels-tested-versions-decoupled-from-releases)).
- **Shapes:** 1.14, 4.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** updates happen when a person asks, from tested versions, never behind their back.
- **Status:** Revised 2026-10-03 by 2.1.1.21: the updater is built as `fabricctl images update` (2.1.14.3); there is no local registry, since fabric's own images come signed from the GitHub Container Registry, pinned in the lock (1.14.3).

## 2.1.14.2 Image versions

- **Decision:** Signed, CI-tested channel on GitHub Pages, independent of releases; offline export/import + local mirror ([1.14.1.1](../volume_1_description_and_architecture/1.14.1-image-channels.md#11411-image-channels-tested-versions-decoupled-from-releases)).
- **Shapes:** 1.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** image versions tested on their own schedule, apart from fabric's releases.
- **Status:** Replaced by 2.1.1.21 (2026-10-03: fabric's images published to a registry, pinned by digest). Never built: hosts follow the lock shipped with fabric.

## 2.1.14.3 Image updates (validation pipeline and host side)

- **Decision:** Daily watcher → regression on amd64 + arm64 incl. an upgrade test → pass: PR auto-merged, signed list published; fail: GitHub issue. Hosts fetch the list automatically unless offline, apply only on command (or opt-in auto-apply), prune old fabric images ([1.14.2](../volume_1_description_and_architecture/1.14.2-image-updates.md#11421-status)).
- **Shapes:** 1.14, 4.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** 1.14.2.
- **Status:** In force, host side partly built. Since 2.1.1.21 (2026-10-03) fabric's own images are built, smoke tested, signed and published in CI and promoted at release (3.14.1, 1.14.3).

## 2.1.14.4 Image pinning (checklist C4)

- **Decision:** Every image pinned by digest (`images.lock.yaml`); a stale upstream image is built from a pinned base.
- **Shapes:** 1.14
- **Made:** 2026-10-03 (the checklist), by the owner.
- **Why:** digest pinning keeps an upstream push from changing what runs (2.3.1.8.3).
- **Status:** In force.

## 2.1.14.9 Which refs publish images

- **Decision:** An exception for this repository: main and `rc/<version>` branches publish by hand (`<version>`, `<version>-rc.<run>`); a `v<version>` tag publishes `<version>` by promoting the digests its lock pins, after verifying them (1.14.3.6).
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-03, by the owner, while designing step 7b.
- **Why:** a way to test hosts against fabric's own images before a release (2.3.14.1.5).
- **Status:** In force.

## 2.1.14.10 A signature that cannot be verified (offline, air-gapped)

- **Decision:** Refused: the new digest is not used. `image_signature_check: false` turns the check off, and `fabricctl status` and the web UI show it while off (1.14.3.4).
- **Shapes:** 1.14, 1.2
- **Made:** 2026-10-03, by the owner, while designing step 7b.
- **Why:** a check that silently passes when it cannot run proves nothing (2.3.14.1.5).
- **Status:** In force.

## 2.1.14.11 How hosts run cosign

- **Decision:** The official cosign image, pinned by digest in `images.lock.yaml` and run with Docker; nothing installed on the host (1.14.3.2).
- **Shapes:** 1.14
- **Made:** 2026-10-03, by the owner, while designing step 7b.
- **Why:** Ubuntu 24.04's archive has no cosign (2.3.14.1.5).
- **Status:** In force.

## 2.1.14.12 Every image's update and rollback is tested from one version back

- **Decision:** `tests/images/update.sh`, in the sandbox and once on the test Pi, pins each image in the lock one version back by digest (`tests/images/previous.yaml`), then checks status, update, health, rollback and update again; an image with no earlier version on its track is listed as skipped with the reason.
- **Shapes:** 1.14, 3.1
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** the image-update path had been run end to end only for nginx (2.3.5.3.8).
- **Status:** In force; **built 2026-10-08** (`tests/images/update.sh`, `previous.yaml`): run for each release candidate once its images are published and pinned. Fabric's own images go back to the previous release, where only the update path and health are checked; base images and OpenBao (no earlier 2.7 release) are skipped with the reason. Its results are recorded with the candidate's.

## 2.1.14.13 A stale published image is detected

- **Decision:** The lock records each published image's source hash (Dockerfile, staged context, base digest); the images suite and CI refuse a source change without the image marked `pending`.
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** a published image can no longer ship stale (2.3.1.11.6, 2.3.14.2).
- **Status:** In force; **built 2026-10-08** (`scripts/images/source_hash.py`, 1.14.3.2, 3.14.1.4). The hash covers the staged context (which holds the Dockerfile) and the pinned base, not file modes (a Windows-mounted checkout shows every file executable). A pending image is unpinned (empty digest), as before, so hosts build it rather than run the stale one.

## 2.1.14.14 Offline install bundles: everything to install

- **Decision:** `fabricctl images export` makes one bundle per release and architecture (the `.deb`, the Ubuntu packages it installs, every locked image by digest, their signature bundles, a manifest); `setup --offline <bundle>` and `images import` check hashes and signatures offline and fetch nothing; no local registry.
- **Shapes:** 1.14, 3.2
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** carries out 2.1.1.22 (2.3.1.11.8).
- **Status:** In force, **revised 2026-10-22** by the owner's answers 2.1.14.16 to 2.1.14.22 (the images fetched from their registries, not `docker save`: 2.1.14.20). History: moved to 0.7 by the owner on 2026-10-08 (2.1.1.39), not built in 0.6.3; moved again, to the release after 0.7, by 2.1.1.42 on 2026-10-10; placed in 0.11 by 2.1.1.45 on 2026-10-10, which became 0.12.0, the catch-all, on 2026-10-17 (2.1.1.58), and **0.13.0** when the owner renumbered the releases on 2026-10-22. **Images built 2026-10-22** (`images export`, `images import`, `setup --offline <bundle>`; 1.14.4, 2.3.14.3); the packages and the `.deb` not yet (2.1.14.16, 2.1.14.17).

## 2.1.14.15 Measured rollout is the default for every restart

- **Decision:** Every change that restarts fabric's services (image updates, applies, release upgrades) fetches
  everything first, then restarts one service at a time in dependency order, waits for each to be healthy, and
  rolls a failed service back and stops ([1.14.2.11](../volume_1_description_and_architecture/1.14.2-image-updates.md#114211-measured-rollout-for-every-restart-211415)).
  It is the default for one host, HA partners and federated sites alike.
- **Shapes:** 1.14, 1.3, 1.9
- **Made:** 2026-10-10, by the owner ("measured rollout of services ... should be our update defaults, ha,
  federated, doesn't matter, these services are too critical"), choosing it over a temporary second fabric to
  carry the network through upgrades.
- **Why:** the owner runs one fabric host per house (2.3.1.10.1) and will not run HA (2.1.9.15), so an upgrade's
  interruption is cut down by restarting less at once, not by a partner.
- **Status:** In force. Image updates follow it; setup starts in dependency order, health-gated; applies follow it
  from 0.7.0 (owner 2026-10-11, "we should fix roll out gates now for 0.7"): one service at a time, health-gated,
  stopping at a failure (`deploy/restart_changed.py`, 1.14.2.11). Rolling an apply's changed configuration back is
  not built (1.14.2.11).

## 2.1.14.16 Offline bundles carry the Ubuntu packages for one release, through a local apt source

- **Decision:** `images export --ubuntu <release>` (default: the exporting machine's release) carries the Ubuntu
  packages fabric installs for that release, recorded in the manifest and refused on another; the offline host
  installs them from a local, file-based apt source made from the bundle, not with `dpkg` on loose files
  ([1.14.4.7](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11447-decided-not-built-yet)).
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-22, by the owner ("yes all recommended"), answering 2.3.14.3's question 1.
- **Why:** a bundle per fabric release and architecture cannot also fit every Ubuntu release, and apt resolving from
  a local source installs only what that host lacks, in the right order (2.3.14.3).
- **Status:** In force; **not built** (0.13.0).

## 2.1.14.17 fabric's .deb in a bundle comes from its GitHub Release

- **Decision:** the export takes the lock's version's `.deb` from its GitHub Release and checks it against the hash
  the signed apt repository publishes for it ([1.14.4.7](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11447-decided-not-built-yet)).
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-22, by the owner, answering 2.3.14.3's question 2.
- **Why:** the released package is the one the release tested, and the apt repository's signature (2.1.1.2) vouches
  for its hash.
- **Status:** In force; **not built** (0.13.0).

## 2.1.14.18 Sigstore's trusted root ships in the package

- **Decision:** the trusted root an offline host checks signatures against is `config/sigstore-trusted-root.json`,
  in the package beside the lock, refreshed by a reviewed commit (`scripts/images/trusted_root.py`), never carried
  in a bundle ([1.14.4.6](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11446-the-trusted-root-the-package-ships)).
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-22, by the owner, answering 2.3.14.3's question 3.
- **Why:** a bundle that brought its own trusted root could vouch for its own forged signatures; the package's comes
  with the release, like the cosign pin (2.1.14.11).
- **Status:** In force; **built 2026-10-22**, with an images-suite check that it is Sigstore's current one.

## 2.1.14.19 A host on Docker's classic image store is refused an offline import

- **Decision:** `images import` and `setup --offline <bundle>` refuse a host whose Docker uses the classic image
  store, with the reason and the procedure to move it to the containerd store (3.14.2.3); fabric does not switch it
  ([1.14.4.5](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11445-dockers-image-store)).
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-22, by the owner, answering 2.3.14.3's question 4.
- **Why:** the classic store forgets a loaded image's digest, so the digest-pinned services would try to pull it
  offline; switching stores hides the images a host already has, which is the admin's call.
- **Status:** In force; **built 2026-10-22**.

## 2.1.14.20 The export fetches images from their registries, not with docker save

- **Decision:** each image is fetched from its registry by digest, every blob checked, into a one-architecture OCI
  layout holding the image's own index; this replaces 2.1.14.14's `docker save`
  ([1.14.4.2](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11442-making-one-fabricctl-images-export)).
- **Shapes:** 1.14
- **Made:** 2026-10-22, by the owner, answering 2.3.14.3's question 5.
- **Why:** `docker save` on the classic store recomputes manifests (the registry's digests are lost, so the host
  could not check them), and `cosign save` carries both architectures and not cosign 3's signatures (2.3.14.3).
- **Status:** In force; **built 2026-10-22**. Revises 2.1.14.14's "(`docker save`)".

## 2.1.14.21 An unpublished image: refused by default, exported anyway on request

- **Decision:** an export refuses a lock with an image not published; an explicit flag exports anyway, a relaxation
  (global Rule 10): the manifest records the images left out, and the import, `fabricctl status` and doctor show
  it ([1.14.4.7](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11447-decided-not-built-yet)).
- **Shapes:** 1.14, 1.2, 3.14
- **Made:** 2026-10-22, by the owner: "overrideable, if they want to attempt the setup that's on them, but they may
  also have a security concern".
- **Why:** a host builds an unpublished image itself, which needs the internet, so such a bundle may not install;
  whoever wants to try may, and it is visible.
- **Status:** In force; **not built** (0.13.0).

## 2.1.14.22 The DNS filter's lists in a bundle: later

- **Decision:** a bundle will carry the DNS filter's lists, so a fresh offline install has them; not in 0.13.0
  ([1.14.4.7](../volume_1_description_and_architecture/1.14.4-offline-bundles.md#11447-decided-not-built-yet)).
- **Shapes:** 1.12, 1.14
- **Made:** 2026-10-22, by the owner ("yes, later"), answering 2.3.14.3's question 7.
- **Why:** 2.1.1.22 asks a bundle path for everything that downloads; the lists are the next thing setup fetches.
- **Status:** In force; **not built**: today a deploy fetches a missing list from the internet.

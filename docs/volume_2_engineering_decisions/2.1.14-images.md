## 2.1.14.1 Updates

- **Decision:** fabric updater + local registry; no Watchtower ([1.14.1.1](../volume_1_description_and_architecture/1.14.1-image-channels.md#11411-image-channels-tested-versions-decoupled-from-releases)).
- **Shapes:** 1.14, 4.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** updates happen when a person asks, from tested versions, never behind their back.
- **Status:** Revised 2026-10-03 by 2.1.1.21: the updater is built as `fabricctl images update` (2.1.14.3); there is no local registry, since fabric's own images come signed from the GitHub Container Registry, pinned in the lock (1.14.3).

## 2.1.14.2 Image versions

- **Decision:** Signed, CI-tested channel on GitHub Pages, independent of releases; offline export/import + local mirror ([1.14.1.1](../volume_1_description_and_architecture/1.14.1-image-channels.md#11411-image-channels-tested-versions-decoupled-from-releases)).
- **Shapes:** 1.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** image versions tested on their own schedule, apart from fabric's releases.
- **Status:** Replaced by 2.1.1.21 (2026-10-03: fabric's images published to a registry, pinned by digest). Never built: hosts follow the lock shipped with fabric.

## 2.1.14.3 Image updates (validation pipeline and host side)

- **Decision:** Daily watcher → regression on amd64 + arm64 incl. an upgrade test → pass: PR auto-merged, signed list published; fail: GitHub issue. Hosts fetch the list automatically unless offline, apply only on command (or opt-in auto-apply), prune old fabric images ([1.14.2](../volume_1_description_and_architecture/1.14.2-image-updates.md#11421-status)).
- **Shapes:** 1.14, 4.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** 1.14.2.
- **Status:** In force, host side partly built. Since 2.1.1.21 (2026-10-03) fabric's own images are built, smoke tested, signed and published in CI and promoted at release (3.14.1, 1.14.3).

## 2.1.14.4 Image pinning (checklist C4)

- **Decision:** Every image pinned by digest (`images.lock.yaml`); a stale upstream image is built from a pinned base.
- **Shapes:** 1.14
- **Made:** 2026-10-03 (the checklist), by the owner.
- **Why:** digest pinning keeps an upstream push from changing what runs (2.3.1.8.3).
- **Status:** In force.

## 2.1.14.9 Which refs publish images

- **Decision:** An exception for this repository: main and `rc/<version>` branches publish by hand (`<version>`, `<version>-rc.<run>`); a `v<version>` tag publishes `<version>` by promoting the digests its lock pins, after verifying them (1.14.3.6).
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-03, by the owner, while designing step 7b.
- **Why:** a way to test hosts against fabric's own images before a release (2.3.14.1.5).
- **Status:** In force.

## 2.1.14.10 A signature that cannot be verified (offline, air-gapped)

- **Decision:** Refused: the new digest is not used. `image_signature_check: false` turns the check off, and `fabricctl status` and the web UI show it while off (1.14.3.4).
- **Shapes:** 1.14, 1.2
- **Made:** 2026-10-03, by the owner, while designing step 7b.
- **Why:** a check that silently passes when it cannot run proves nothing (2.3.14.1.5).
- **Status:** In force.

## 2.1.14.11 How hosts run cosign

- **Decision:** The official cosign image, pinned by digest in `images.lock.yaml` and run with Docker; nothing installed on the host (1.14.3.2).
- **Shapes:** 1.14
- **Made:** 2026-10-03, by the owner, while designing step 7b.
- **Why:** Ubuntu 24.04's archive has no cosign (2.3.14.1.5).
- **Status:** In force.

## 2.1.14.12 Every image's update and rollback is tested from one version back

- **Decision:** `tests/images/update.sh`, in the sandbox and once on the test Pi, pins each image in the lock one version back by digest (`tests/images/previous.yaml`), then checks status, update, health, rollback and update again; an image with no earlier version on its track is listed as skipped with the reason.
- **Shapes:** 1.14, 3.1
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** the image-update path had been run end to end only for nginx (2.3.5.3.8).
- **Status:** In force; **built 2026-10-08** (`tests/images/update.sh`, `previous.yaml`): run for each release candidate once its images are published and pinned. Fabric's own images go back to the previous release, where only the update path and health are checked; base images and OpenBao (no earlier 2.7 release) are skipped with the reason. Its results are recorded with the candidate's.

## 2.1.14.13 A stale published image is detected

- **Decision:** The lock records each published image's source hash (Dockerfile, staged context, base digest); the images suite and CI refuse a source change without the image marked `pending`.
- **Shapes:** 1.14, 3.14
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** a published image can no longer ship stale (2.3.1.11.6, 2.3.14.2).
- **Status:** In force; **built 2026-10-08** (`scripts/images/source_hash.py`, 1.14.3.2, 3.14.1.4). The hash covers the staged context (which holds the Dockerfile) and the pinned base, not file modes (a Windows-mounted checkout shows every file executable). A pending image is unpinned (empty digest), as before, so hosts build it rather than run the stale one.

## 2.1.14.14 Offline install bundles: everything to install

- **Decision:** `fabricctl images export` makes one bundle per release and architecture (the `.deb`, the Ubuntu packages it installs, every locked image by digest, their signature bundles, a manifest); `setup --offline <bundle>` and `images import` check hashes and signatures offline and fetch nothing; no local registry.
- **Shapes:** 1.14, 3.2
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** carries out 2.1.1.22 (2.3.1.11.8).
- **Status:** In force; **moved to 0.7 by the owner on 2026-10-08** (2.1.1.39): not built in 0.6.3. **Moved again, to the release after 0.7, by 2.1.1.42 on 2026-10-10.** **Placed in 0.11 by 2.1.1.45 on 2026-10-10.**

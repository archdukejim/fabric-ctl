## 2.1.4.1 Where Kea registers DHCP hostnames

- **Decision:** A separate dynamic subzone per DHCP scope (`dhcp.<domain>`, per-VLAN subzones with 802.1X); never the rendered zones ([1.10.1.1](../volume_1_description_and_architecture/1.10.1-kea-design.md#11011-kea-dhcp)).
- **Shapes:** 1.4, 1.10
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** dynamic updates never touch the zones fabric renders from settings, so a render cannot lose a lease's name and a lease cannot overwrite a record.
- **Status:** In force.

## 2.1.4.2 Which of the site's DNS records the landing page links to, and how

- **Decision:** **Only records marked for it**, each with an optional port, path and label (`https://<name>.<domain>[:port][/path]`); shown to everyone on the LAN like the rest of the page.
- **Shapes:** 1.4, 4.4
- **Made:** 2026-10-07, by the owner, in 0.6.1; design: 1.4.2.2.
- **Why:** the owner adds records for the machines on the network (a Proxmox host, say) and wants the landing page to link to them; only some records are worth a link.
- **Status:** In force.

## 2.1.4.3 The instructions page lives at info.<domain>, over HTTP too

- **Decision:** `landing_page_cname` defaults to `info`. `info.<domain>` answers on HTTP and HTTPS with no forced redirect, with the instructions, the CA files and the root's SHA-256 fingerprint; everything else stays HTTPS-only. `<domain>` and the host's own name redirect (301) to it.
- **Shapes:** 1.4, 1.5, 3.3, 4.4
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** a new device can fetch the CA over plain HTTP and check it before trusting it (2.3.5.3.6).
- **Status:** In force; built in 0.6.3 (1.4.2.3). **Revised by 2.1.4.6 on 2026-10-12:** `<domain>` and the host's
  own name serve the page themselves instead of redirecting to `info.<domain>`, which the admin may now rename,
  repoint or delete.

## 2.1.4.4 Dynamic DNS for public records at Cloudflare

- **Decision:** fabric keeps a list of public records at Cloudflare pointed at the house's current IPv4 address, the proxy setting kept per record (never changed by fabric on its own), checked every 5 minutes against Cloudflare's trace and a second source; run on the core host by default or on another host the owner selects. IPv6 later.
- **Shapes:** 1.4, 1.2
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** the house's address is dynamic and hidden behind Cloudflare's proxy; fabric takes over the edge machine's own client (2.3.5.3.16).
- **Status:** In force; **moved to 0.7 by the owner on 2026-10-08** (2.1.1.39): not built in 0.6.3. **Moved again, to the release after 0.7, by 2.1.1.42 on 2026-10-10.** **Placed in 0.11 by 2.1.1.45 on 2026-10-10.**

## 2.1.4.5 Zones added and removed in the console, in seconds

- **Decision:** the console adds and removes forward zones (1.4.1.3), as the menu adds them, through one unit; a change
  reloads BIND's and the resolver's configuration (`rndc reconfig`) instead of a full apply. A name BIND already
  answers for is refused; a public name is accepted only when the owner ticks that it hides the real one; removing a
  zone takes its records, after its name is typed again, and is refused while a TSIG key or ACL policy names it.
- **Shapes:** 1.4, 1.8, 1.12
- **Made:** 2026-10-11, by the owner ("why can't I define more zones? I should be able to"), for 0.7.0 (2.1.1.49);
  the refusals and the reload in seconds proposed by the agent with the design, as defaults the owner may change.
- **Why:** a zone could be added only from the host's menu and never removed; a full apply took minutes on the test Pi
  (2.3.1.18).
- **Status:** In force; built in 0.7.0 on 2026-10-11 (1.4.1.3; operation 4.4.1.2).

## 2.1.4.6 The landing page at a path; `info.<domain>` an ordinary alias; the CRL at the CA's own name

- **Decision:** the landing page (with its `/certs/`) is served by fabric's nginx at a path, **`http://<host_ip>/info/`**,
  and on fabric's own names (`<domain>`, the host's own name, and `hostname_landing`, over HTTP and HTTPS), whatever
  DNS says. `info.<domain>` becomes an **ordinary record** of the site's zone: a new install gets it (to the landing
  page, as before), and the admin may rename, repoint or delete it in the console's DNS tab like their own records;
  fabric never adds it back. Any other name the admin points at the host shows the page over plain HTTP (its `/`
  goes to `/info/`). **Certificates name a CRL point fabric owns:** every leaf issued from 0.7.1 names
  `http://<hostname_stepca>/certs/crl/intermediate.crl` (`ca.<domain>`, the CA's own name, kept by fabric and
  refused in the DNS tab), as do the scripts, the certificate page and the texts that tell people where the CA's
  files are; fabric's own service certificates that name another point (`info.<domain>`) are issued again
  at once, so the upgrade itself moves them. Design: 1.4.2.5, 1.5.1.6.
- **Shapes:** 1.4, 1.5, 1.8, 1.9
- **Made:** 2026-10-12, by the owner: "I just wanted to be able to rename and repoint it, maybe they want to reserve
  .info for a different page. Alternatively, we can just make it [fabric-host ip]/info and then whatever DNS record
  they want is just an alias to that? By default info. goes to ip/info." The CRL point, the path's details and the
  early re-issue of service certificates were designed by the agent the same day, as the most robust reading,
  which the owner may change.
- **Why:** the name was load-bearing (2.3.1.19.5): fabric's certificates, scripts and redirects named it, so it could
  not be given up. Moving everything fabric depends on to names and an address fabric keeps leaves `info` free for
  the admin. **The CRL point:** `ca.<domain>` is fabric's (the DNS tab refuses its delete, 1.4.1.4), is the CA's own
  name, survives a change of the host's address (unlike `http://<host_ip>/…`, rejected for that reason), and already
  answers `/certs/` on plain HTTP (nginx's default server) on every install since 0.6.3, so a site fetching another
  site's CRL there needs nothing new from it. **Certificates already issued** name `http://info.<domain>/certs/crl/…`
  until they are issued again; it keeps answering while `info` points at the host (nginx serves `/certs/` on every
  name that reaches it). Fabric's own service certificates are re-issued by the upgrade (a different CRL point is a
  reason to renew, 1.5.1.2), devices' ACME certificates renew within their 30-day cycle (2.1.5.4), and nothing
  fabric itself checks reads a certificate's CRL point (nginx and FreeRADIUS read the CRL files directly, 1.5.1.3).
- **Status:** In force; built in 0.7.1 on 2026-10-12 (branch `dev/0.7.1-landing`; 1.4.2.5, 1.5.1.6). Revises
  2.1.2.22 item 6 for `info`, 2.1.4.3 (the redirects) and 2.1.5.11 (the CRL point); answers 2.3.1.19.5. Open for the
  owner: 2.3.1.20.7. **Revised by 2.1.4.8 on 2026-10-12:** the landing names are the host's own name, `<domain>` and
  the zone's aliases of the host at each apply; `hostname_landing` is one only while a record of the zone points it
  at the host (it still names the certificate's folder).

## 2.1.4.7 A zone change between applies renders BIND from the apply's checked settings

- **Decision:** `fabricctl dns add-zone` and `remove-zone` (and the console's and the menu's zone forms) render BIND's
  zone list from the same checks as an apply, through one function both call (`deploy/check_rendered`): the settings
  check (`check_settings`, which sets `dhcp_reverse_zones` and Kea's grants), the reverse zones and the federation
  links. Settings the apply's check refuses refuse the zone change too, saying why, before any file is written; only
  the vars change is rolled back. Findings: [2.3.4.3](2.3.4-dns-notes.md#2343-a-zone-change-dropped-dhcps-reverse-zones-071).
- **Shapes:** 1.4 (1.4.1.3, the quick zone path), 1.10
- **Made:** 2026-10-12, by the owner (option A of the same defect found on 0.8.0, where it is decision 2.1.10.21,
  settling 2.3.10.4.10), carried to 0.7.1 by the agent since 0.7.1 has the defect too.
- **Why:** between applies, a zone change dropped the reverse zones that hold only DHCP's PTRs and Kea's grants in
  the others, so DHCP's PTR registrations failed until the next apply. One shared function keeps the apply and the
  quick path from drifting apart again. 0.8.0's version adds the address plan and the denies on PTRs set by hand
  (2.1.10.20), which 0.7.1 does not have.
- **Status:** In force; built in 0.7.1 on 2026-10-12 (1.4.1.3). **Extended in 0.8.0 by 2.1.10.21**
  ([2.1.10.21](2.1.10-dhcp.md#211021-a-zone-change-between-applies-renders-bind-from-the-applys-checked-settings)):
  0.7.1 merged into 0.8.0 on 2026-10-12, where the shared function also reads the address plan and keeps the denies
  on PTRs set by hand.

## 2.1.4.8 The landing certificate follows the zone's aliases of the host; a replaced one is revoked (revised: it expires)

- **Decision:** the landing page's names, and so its certificate's, are fabric's own (the host's own name, its CN, and
  `<domain>`) **plus every record of the site's zone that points at the host** (an A record to `host_ip`, or a CNAME
  to one of the host's names, through other CNAMEs too), computed from the zone at each apply; nothing else: not the
  old name of a renamed alias, not a record pointing at another machine, not a wildcard, not fabric's own records or
  the names of fabric's other services. nginx serves the page at each of them over HTTP and HTTPS. When an apply finds
  the certificate's names differ from these in any way, it **issues the certificate again at once** (not at its
  renewal) and **revokes the one it replaced** through fabric's CA (reason `superseded`, actor `fabric`, the CRLs
  published with it). A revocation that fails is said loudly (the apply fails with the command to run, the renewal
  record holds it for status and doctor) and the new certificate is kept. **Revised 2026-10-12 by the owner: the
  replaced certificate is not revoked; it expires on its own** (no revocation record, not in the CRL; nothing to
  fail, so the apply fails only when the new certificate cannot be issued). The page's own links stay relative; its
  `/manual/` over plain HTTP goes to HTTPS at the same name, which the certificate now names. Design: 1.4.2.6, 1.5.1.7.
- **Shapes:** 1.4 (1.4.2.5, 1.4.2.6), 1.5 (1.5.1.2, 1.5.1.7)
- **Made:** 2026-10-12, by the owner, answering 2.3.1.20.7 with option (b): "B mint a new certificate, probably should
  revoke the old one, and it should have up and only the new url for the landing page." The details (the CN on the
  host's own name, what counts as pointing at the host, what is left out, the apply issuing it at once, a failed
  revocation reported but not undone, the links kept relative) designed by the agent the same day as the most robust
  reading, which the owner may change.
- **Why:** a renamed `info` alias showed the page over plain HTTP but got another name's certificate over HTTPS
  (2.3.1.20.7). Computing the names from the zone needs no new setting and follows every rename; holding exactly the
  current names keeps fabric's CA from vouching for a name that has gone, or now belongs to another machine;
  revoking the replaced certificate means a copy of it cannot be used for the old name. Revocation is the
  clean-up, not the goal, so its failure does not take the new names away. **The revision's why:** the owner chose
  to let the replaced certificate run out (at most `cert_service_days`, 47 days by default, 2.1.5.4): it is fabric's
  own, held only by nginx on this host, and the old name no longer reaches it, so revoking it adds an entry to every
  CRL and a way for the apply to fail for no gain.
- **Status:** In force; built in 0.7.1 on 2026-10-12 (branch `dev/0.7.1-landing-cert`; 1.4.2.6, 1.5.1.7). Revises
  2.1.4.6 (the landing names); settles 2.3.1.20.7. **Revised 2026-10-12 by the owner: the replaced certificate is not
  revoked, it expires** (built the same day: the revocation step removed; 1.5.1.7).

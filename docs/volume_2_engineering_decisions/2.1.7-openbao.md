## 2.1.7.1 Secrets

- **Decision:** OpenBao, all four uses, auto-unseal from a local key file ([1.7.1.1](../volume_1_description_and_architecture/1.7.1-openbao.md#1711-secrets-openbao)).
- **Shapes:** 1.7
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** one place for fabric's and applications' secrets, unlocked without a person at boot.
- **Status:** In force; the unseal part is refined by 2.1.7.2 (the key file is one slot among several). Built: fabric's secrets and apps KV; not built: rotated credentials, SSH CA.

## 2.1.7.2 How OpenBao is unlocked

- **Decision:** Key slots (local file, USB sticks, PKCS#11 security keys, KMIP HSMs); any one enabled slot unlocks; handled on the host by fabric-unlock; vendor-neutral ([1.7.1.1](../volume_1_description_and_architecture/1.7.1-openbao.md#1711-secrets-openbao)).
- **Shapes:** 1.7, 4.7
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** a person chooses how strongly the vault is locked without fabric depending on one vendor's hardware.
- **Status:** In force.

## 2.1.7.3 Secrets (checklist E1)

- **Decision:** OpenBao for fabric's and applications' secrets; mode-0600 files at bootstrap; environment variables into containers; never the command line.
- **Shapes:** 1.7, 1.2
- **Made:** 2026-10-03 (the checklist), by the owner.
- **Why:** 2.3.1.8.5.
- **Status:** In force.

## 2.1.7.4 Keycloak's database password rotates monthly

- **Decision:** Postgres gets its own admin, separate from Keycloak's user; OpenBao's database engine rotates Keycloak's password monthly at night, then Keycloak is re-rendered and restarted; Postgres never depends on OpenBao to start; `fabricctl vault rotate-db` rotates now.
- **Shapes:** 1.7, 1.6
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** fewer long-lived secrets (2.3.1.11.9).
- **Status:** In force; **built 2026-10-08** ([1.7.1.2](../volume_1_description_and_architecture/1.7.1-openbao.md#1712-keycloaks-database-password-rotated-by-openbao)). "Keycloak's user stops being a superuser" is met by moving Keycloak to its own role (`keycloak_db`): the role Postgres was created with is its bootstrap superuser, which Postgres 16+ never demotes; it is locked instead. fabric's monthly timer drives the rotation (so Keycloak always follows it), OpenBao's period only backs it up.

## 2.1.7.5 An SSH certificate authority for the domain's Linux machines

- **Decision:** OpenBao's SSH engine: 8-hour user certificates with the person's AD groups as principals (web console or `bao ssh`, `ssh:sign`), host certificates for joined machines, the join script trusting the user CA and the host CA (an option, on by default).
- **Shapes:** 1.7, 1.6, 4.6
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** 2.3.1.11.9.
- **Status:** In force; **moved to 0.7 by the owner on 2026-10-08** (2.1.1.39) with the host-access model it grew into
  ([2.3.6.4](2.3.6-identity-notes.md#2364-proposal-07-host-access-ssh-and-fabrics-own-admin-groups)), which revises
  it once settled. **Moved again, to the release after 0.7, by 2.1.1.42 on 2026-10-10.** **Revised by 2.1.6.39 on 2026-10-10:** SSH certificates are an option, off by default (Kerberos is the default sign-in); certificates go to fabric admins only, the user name as the one principal (2.3.6.4.2). **Placed in 0.9 by 2.1.1.45 on 2026-10-10.**

## 2.1.7.6 Local admin passwords: OpenBao sets and escrows every managed machine's break-glass account

- **Decision:** OpenBao generates, and keeps, a unique local admin password for every Windows and Linux domain member,
  the fabric host and the network gear fabric manages ([1.7.1.3](../volume_1_description_and_architecture/1.7.1-openbao.md#1713-local-admin-passwords-set-and-escrowed-by-openbao)). Rotation is a policy per kind and per machine: after use
  (the default), on a schedule, at check-in, or manual. Reading one is an audited check-out. Passwords export to
  printed sheets, an encrypted file on USB and Shamir-split sheets, so they can be sealed in envelopes for a safe.
  The fabric host's own break-glass account rotates on a schedule with a sealed envelope required, so the host (and
  OpenBao with it) can be recovered when OpenBao is down.
- **Shapes:** 1.7, 1.6, 1.11, 4.7
- **Made:** 2026-10-10, by the owner ("breakglass local admin passwords, I want openbao to set those", captured and
  exportable "so they can be sealed in an envelop and literally saved in a vault"; rotation "configurable, I prefer
  rotate when used, but that's not how everyone operates, some require yearly rotates"; the owner's own use:
  check-out, "with the exception of the breakglass for fabric, which will rotate on a schedule"; all four kinds; all
  three exports; 0.9).
- **Why:** a shared or never-changed local admin password is the usual way one machine's compromise becomes every
  machine's. Secure sites keep break-glass credentials sealed, which works against rotating after every use: making
  the policy configurable and showing stale envelopes lets each site choose, knowingly ([2.3.7.2](2.3.7-openbao-notes.md#2372-proposal-local-admin-passwords-in-openbao)).
- **Status:** In force; designed, **not built**: 0.9 (2.1.1.45), with the domain work. Its mechanisms: 2.1.7.7 to 2.1.7.10. Revised 2026-10-22 by 2.1.7.16: in 0.8.0 the fabric host's account rotates after use (or is kept until checked out); its schedule and sealed export come with 0.10.0.

## 2.1.7.7 How a member machine signs in to OpenBao

- **Decision:** a machine certificate from fabric's CA (OpenBao's cert auth), the same certificate
  0.9's 802.1X EAP-TLS gives each machine, issued at join. Not chosen: Kerberos with the machine's AD account (no
  new credential, but OpenBao's Kerberos auth must be proven against Samba's KDC); an AppRole secret handed over at
  join (simplest, a long-lived secret on every machine).
- **Shapes:** 1.7, 1.6, 1.11
- **Made:** 2026-10-10, by the owner, the proposed option chosen ([2.3.7.2](2.3.7-openbao-notes.md#2372-proposal-local-admin-passwords-in-openbao)).
- **Why:** the machine must prove which machine it is, so that it can only write its own path.
- **Status:** In force; designed, not built (0.9).

## 2.1.7.8 How Windows members set their password

- **Decision:** fabric's own scheduled task (PowerShell, SYSTEM), installed by the Windows join,
  writing to OpenBao directly. Not chosen: Windows LAPS against Samba AD (Microsoft's own agent rotates, the
  password goes to AD, fabric copies it into OpenBao): a mature agent, but the password lives in AD as well, the
  rotation policies are LAPS's, and Samba's support for the Windows LAPS schema needs a spike first.
- **Shapes:** 1.7, 1.6
- **Made:** 2026-10-10, by the owner, the proposed option chosen ([2.3.7.2](2.3.7-openbao-notes.md#2372-proposal-local-admin-passwords-in-openbao)).
- **Why:** the owner asked for OpenBao to set the passwords; LAPS would make AD the source.
- **Status:** In force; designed, not built (0.9).

## 2.1.7.9 The export's encryption and secret sharing

- **Decision:** `age` (a maintained, audited file-encryption tool) for the encrypted file, for a
  passphrase or an `age` key; Shamir's secret sharing of that key k-of-n, 3 of 5 by default, printed one share per
  sheet with a check so a mistyped share is caught.
- **Shapes:** 1.7, 4.7
- **Made:** 2026-10-10, by the owner, the proposed option chosen ([2.3.7.2](2.3.7-openbao-notes.md#2372-proposal-local-admin-passwords-in-openbao)).
- **Why:** global Rule 11 prefers a maintained tool to fabric's own cryptography.
- **Status:** In force; designed, not built (0.9).

## 2.1.7.10 OpenBao's recovery keys in the host's envelope set

- **Decision:** offered, off by default: the host's export can add OpenBao's recovery key shares,
  one per split sheet, so one envelope set recovers both the host and OpenBao. Today the recovery keys go to
  `~/fabric-admin` at init (1.7.1.1) and are the admin's to store.
- **Shapes:** 1.7, 4.7
- **Made:** 2026-10-10, by the owner, the proposed option chosen ([2.3.7.2](2.3.7-openbao-notes.md#2372-proposal-local-admin-passwords-in-openbao)).
- **Why:** the owner's reason for the host's scheduled break-glass is being able to recover OpenBao; keeping both in
  one set is simpler, keeping them apart means one opened envelope cannot reach both.
- **Status:** In force; designed, not built (0.9).

## 2.1.7.11 The managed account is named `local-admin` everywhere

- **Decision:** the local admin account OpenBao sets and escrows (2.1.7.6) is named **`local-admin`** on every machine
  it manages: Linux members, the fabric host, and Windows members, where fabric's task creates it (the built-in
  Administrator, RID 500, is left as it is). It replaces the design's earlier names (`fabric-local-admin` on Linux,
  `fabric-recovery` on the host, the built-in Administrator on Windows).
- **Shapes:** 1.7, 1.6
- **Made:** 2026-10-10, by the owner ("local-admin should be the user name created for the new openbao managed
  local-admin"; everywhere, over Linux and the host only).
- **Why:** one name an admin finds on any machine, in the vault and on the sealed sheet.
- **Status:** In force; designed, not built (0.9). Revises 2.1.7.6's design (1.7.1.3.1).

## 2.1.7.15 local-admin: hidden from sign-in screens, its rotation adjustable for local break glass, and unmanaged admins found

- **Decision:** three additions to the local admin passwords of 1.7.1.3 (2.1.7.6 to 2.1.7.11):
  1. **Hidden on Windows:** `local-admin` does not appear on the Windows sign-in screen (the `SpecialAccounts\UserList`
     registry value, set by fabric's task at join); it is still used by typing its name.
  2. **Rotation adjustable for local break glass:** besides the policies of 1.7.1.3.4, a machine or a host group may be
     set to keep its current password until it is checked out (no scheduled rotation), so a sealed envelope at that
     site stays valid; rotation after use still applies, so a password once used is never valid again.
  3. **Unmanaged local admins found (optional, off by default):** an inspection lists every local administrator
     account on a managed machine that OpenBao does not manage (Windows: members of the local Administrators group;
     Linux: uid 0 and members of `sudo`, `wheel` or `admin`, and sudoers rules granting `ALL`), each with the machine
     and when it was last used. It reports, never removes; the console's Computers page and `fabricctl doctor` show it.
     The account that ran setup on a fabric host is listed as known, not as a finding (2.1.6.70).
- **Shapes:** 1.7 (1.7.1.3), 1.6 (1.6.5.10, 1.6.7 the joins), 1.8 (Computers), 1.11
- **Made:** 2026-10-18, by the owner: "the new local-admin user as should be done for every new machine (should not
  show on login screens for windows) will have an automatic password that rotates in accordance with the open-bao
  settings as described in the manual, however this should also be able to be adjusted to allow for local break
  glass procedures. We should enable an optional inspection to check for any local administrator accounts that are not
  managed by open-bao."
- **Why:** an account nobody signs in with daily should not invite it on every screen; a site's own break-glass
  envelope needs a password that does not change under it; an admin account outside OpenBao is a way in nobody
  audits.
- **Release** (owner 2026-10-18: "B"): the fabric host's own `local-admin` in **0.8.0** (fabric sets it on the host and
  keeps it in OpenBao, with no machine certificate needed), with the inspection on the fabric host; every other
  machine's, and the inspection across them, in **0.10.0** with 802.1X, whose machine certificates they sign in to
  OpenBao with (2.1.7.7).
- **Status:** In force; to build as above. 1.7.1.3's "designed for 0.9" means 0.10.0 (2.1.1.58), but for the fabric
  host's account.
  Revised 2026-10-18 by 2.1.6.78: on a host that runs a DC the inspection is on and reminds the administrators daily
  until each account is removed or approved by the Enterprise Admin; that host's local-admin password is released only
  to the Enterprise Admin.
  Revised 2026-10-22 by 2.1.7.16 to 2.1.7.20: how the fabric host's account is rotated, seen used, checked out, let in
  over SSH and kept while OpenBao is locked, in 0.8.0.

## 2.1.7.16 The fabric host's local-admin in 0.8.0: rotated after each use, or kept until checked out

- **Decision:** in 0.8.0 the fabric host's `local-admin` (2.1.7.15) gets a new password after each use, by default,
  or is set to keep its password until it is checked out (2.1.7.15 item 2). The scheduled rotation, the sealed exports
  (the printed sheet, the `age` file, the Shamir sheets) and the two-step rotation confirmed by the envelope's serial
  (1.7.1.3.6, 1.7.1.3.7) come in 0.10.0, with the other machines' accounts. The printed sheet that would let the host
  be recovered while OpenBao is down is **not** built now: it is part of 0.10.0's exports. Making the account is a host
  change (global Rule 12): its own consent item in setup's plan, recorded, and undone by uninstall. D2's reminder of
  local administrator accounts (1.6.12.16.7) treats it as managed. Other machines' `local-admin` stays 0.10.0.
- **Shapes:** 1.7 (1.7.1.3, 1.7.1.4), 1.2 (1.2.9.3), 1.6 (1.6.12.16.7, 1.6.13.6), 4.7
- **Made:** 2026-10-22, by the owner, answering 2.3.7.6 question 1: "b" (rotation after each use by default, or kept
  until checked out; the schedule, the exports and the envelope's two-step in 0.10.0), without the printed sheet the
  agent had recommended with it.
- **Why:** a password once used is never valid again, which needs nothing but OpenBao and the host; the envelope
  machinery is worth building once, for every machine, in 0.10.0.
- **Status:** In force; built 2026-10-22 in 0.8.0 (D6: 1.7.1.4, note [2.3.7.7](2.3.7-openbao-notes.md)). Revises 2.1.7.6 (the
  host's schedule and sealed export wait for 0.10.0) and 1.7.1.3.6 for 0.8.0. The build's choices confirmed by the
  owner on 2026-10-22 ("yes", note [2.3.7.7.4](2.3.7-openbao-notes.md)): both policies rotate after a use or a check-out in 0.8.0 (no schedule yet), and
  the account's consent item is recommended, not required.

## 2.1.7.17 A use of the host's local-admin is seen by the hourly timer

- **Decision:** the hourly timer reads the journal (the sessions PAM opens) and `wtmp` for sign-ins of `local-admin`
  and marks its password used; nothing changes in the host's PAM.
- **Shapes:** 1.7 (1.7.1.4)
- **Made:** 2026-10-22, by the owner, answering 2.3.7.6 question 2: "timer".
- **Why:** the DC's host keeps its PAM stack as it is (a broken hook there could lock the top tier out); an hour is
  short beside the grace before a rotation.
- **Status:** In force; built 2026-10-22 in 0.8.0 (D6: 1.7.1.4). The build's grace confirmed by the owner on
  2026-10-22 ("yes", note [2.3.7.7.4](2.3.7-openbao-notes.md)): 8 hours from the first use or check-out, fixed in 0.8.0 (not a setting).

## 2.1.7.18 Checking out the host's local-admin: root on the host, or the console as fabric-admin

- **Decision:** the host's `local-admin` password is checked out with `sudo fabricctl local-admin checkout` on the host
  (root is the Enterprise Admin's tier, 2.3.6.20.3) and through the console's route while signed in as `fabric-admin`.
  There is no separate `local-admin:checkout` role yet (2.1.6.78 limits a DC host's password to the Enterprise
  Admin). Each check-out is audited, and marks the password for rotation after use.
- **Shapes:** 1.7 (1.7.1.3.5, 1.7.1.4), 1.8 (the route), 4.7
- **Made:** 2026-10-22, by the owner, answering 2.3.7.6 question 3: "both".
- **Why:** the Enterprise Admin reaches the host either way; a role of its own matters only once other machines'
  passwords exist (0.10.0).
- **Status:** In force; built 2026-10-22 in 0.8.0 (D6: 1.7.1.4). The build's choice confirmed by the owner on
  2026-10-22 ("yes", note [2.3.7.7.4](2.3.7-openbao-notes.md)): a check-out is refused while OpenBao is locked, since it holds the only copy until 0.10.0's
  sealed exports.

## 2.1.7.19 local-admin over SSH: a switch kept in the domain, off by default

- **Decision:** whether the host's `local-admin` may sign in over SSH is a switch kept in the domain, as a policy is:
  **off by default** (sshd refuses it); on for a host, sshd lets `local-admin` in with its password, for that user only.
  The switch is stored in fabric's domain store (`CN=local-admin,CN=fabric,CN=System`, beside the grants), set only by
  the Enterprise Admin, for the hosts that run a DC (`sudo fabricctl local-admin ssh on|off`, and the console's route
  as `fabric-admin`), and applied on the host by fabric, at once when it changes and by the hourly timer. It is a
  relaxation (global Rule 10): `fabricctl doctor`, `fabricctl domain status` and the console's Overview show it while
  it is on. Its store is laid out so 0.10.0 can name other machine groups with the same switch; 0.8.0 builds only the
  fabric hosts.
- **Shapes:** 1.7 (1.7.1.3.1, 1.7.1.4), 1.6 (1.6.13.6), 1.2.8, 4.7
- **Made:** 2026-10-22, by the owner, answering 2.3.7.6 question 4: "ssh local-admin might still be necessary over
  ssh, i.e troubleshooting remote and trying to recover, but I hear the security risk, so maybe toggleable via gpo?".
  The owner's "maybe" was taken as this design (a switch in the domain store that reads as a domain policy, not a
  Windows GPO), **for the owner to confirm**.
- **Why:** recovering a host from afar sometimes needs its break glass over SSH; off unless the top tier turns it on
  for one host, and shown while it is on, keeps that rare.
- **Status:** In force; built 2026-10-22 in 0.8.0 (D6: 1.7.1.4). Confirmed by the owner on 2026-10-22: "yes, but I
  think that should be a suppressible alert too" (note [2.3.7.7.4](2.3.7-openbao-notes.md)); revised by 2.1.7.21 on 2026-10-22 (the alert can be
  acknowledged; the relaxation is still shown). The build's choice for a read-only DC's host also confirmed ("yes"):
  its switch is refused there and set from the writable DC's fabric host with `--dc`.

## 2.1.7.20 With OpenBao locked, a rotation due waits; the used password stays valid

- **Decision:** a rotation due while OpenBao is unreachable or sealed waits: the used password stays valid until
  OpenBao can take the new one; `fabricctl doctor` reminds of it; the rotation runs at the next timer run after
  OpenBao is back. 1.7.1.3.6's `rotate-host` path (a password rotated while OpenBao is locked) is not built.
- **Shapes:** 1.7 (1.7.1.3.6, 1.7.1.4)
- **Made:** 2026-10-22, by the owner, answering 2.3.7.6 question 5: "yes it stays valid until it can update to
  openbao".
- **Why:** a password OpenBao does not hold is a password nobody can check out; waiting keeps OpenBao the one source.
- **Status:** In force; built 2026-10-22 in 0.8.0 (D6: 1.7.1.4).

## 2.1.7.21 local-admin over SSH: its alert can be acknowledged by the Enterprise Admin

- **Decision:** while the SSH switch (2.1.7.19) is on, `fabricctl doctor` and the console's reminders raise an alert.
  The Enterprise Admin, and only that tier, can acknowledge (suppress) it: `sudo fabricctl local-admin ssh ack` or the
  console's route as `fabric-admin`. Who and when are recorded with the switch in the domain and audited. The alert
  comes back whenever the switch changes, so turning it off and on again raises it again. The switch's state is still
  shown everywhere while it is acknowledged: `fabricctl status`, the Overview and `fabricctl domain status` keep the
  relaxation (global Rule 10), saying who acknowledged its alert.
- **Shapes:** 1.7 (1.7.1.4.6, 1.7.1.4.7, 1.7.1.4.10), 1.2.8, 1.3.3, 4.7 (4.7.1.3.4)
- **Made:** 2026-10-22, by the owner, confirming 2.1.7.19: "yes, but I think that should be a suppressible alert too".
- **Why:** a switch kept on on purpose for a long recovery should not nag every doctor run, but a relaxation must never
  disappear from view; tying the acknowledgement to the switch as it is keeps a new "on" from inheriting an old one.
- **Status:** In force; built 2026-10-22 in 0.8.0 (1.7.1.4.10, note [2.3.7.7.4](2.3.7-openbao-notes.md)). Confirmed by the owner on
  2026-10-23, "all as recommended": acknowledging silences only the alert; `fabricctl status`, the Overview and
  `fabricctl domain status` keep showing the switch on.

## 2.3.4.2 Zones in seconds: what the tests found (0.7.0)

Built 2026-10-11 for 1.4.1.3 (decision 2.1.4.5); `tests/zones/run.py` runs fabric's BIND image from the configuration
fabric renders and the resolver from deploy_resolver's.

- **A new zone is served 0.2 s after the agent's call** (BIND's `rndc reconfig`, then the resolver's reload), against
  minutes for an apply on the test Pi (2.3.1.18).
- **Rendering only `named.conf.zones` is not enough:** the zone list grants update rights to TSIG keys by name, so a
  key created in the console since the last apply (its secret saved, `named.conf.keys` not yet rendered) would make
  BIND refuse the list. The quick path renders all of BIND's configuration as apply does; a key without a secret yet
  (written into the vars by hand) refuses it, since only apply makes and saves secrets.
- **A name with an underscore** (`bad_name.lan`), which the menu's `HOST_RE` accepted, is refused by BIND
  ("zone not loaded"): the first run caught it through the rollback (the vars put back, the page saying why). Zone
  names are now checked by their own `ZONE_RE`, without the underscore.
- **The resolver's forward list** (`filter_zones`) held only the site's domain, the organisation's, the linked sites',
  the reverse and AD zones: a zone added by the menu before 0.7.0 was answered by the resolver from the internet, not
  from BIND. It now holds every key of `dns:`.
- **Records in an added zone still need an apply**, as in the site's zone: only the zone list and a new zone's file
  are published in seconds.

## 2.3.4.3 A zone change dropped DHCP's reverse zones (0.7.1)

Found 2026-10-12 on 0.8.0 (2.3.10.4.10) and checked on 0.7.1: the same defect. `publish_zone_list` rendered BIND's
zone list from `render_vars` alone, without `check_settings`, so `dhcp_reverse_zones` was never set. A zone added or
removed between applies therefore dropped every reverse zone that holds only DHCP's PTRs, and Kea's key lost its
update grant in the others; DHCP's PTR registrations were refused until the next apply. Fixed by decision 2.1.4.7:
the apply and the quick path call one function, `deploy/check_rendered`.

- **Tests** (`tests/zones/run.py`): after an apply with DHCP on two subnets, a zone added keeps both reverse zones and
  Kea's grant on them (an nsupdate with Kea's key is accepted); a zone change whose settings the apply's check
  refuses (DHCP on a network interface that does not exist) is refused before any file is written, and the vars and
  BIND's files are left as they were.

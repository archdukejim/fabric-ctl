## 2.1.3.1 Python-in-.deb vs Go binary

- **Decision:** Python ([1.3.1.1](../volume_1_description_and_architecture/1.3.1-host-package.md#1311-package-design)).
- **Shapes:** 1.3, 1.1
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** the package needs no build step and hosts can read what runs (2.3.1.8.2).
- **Status:** In force; built this way.

## 2.1.3.2 Product split and privilege model

- **Decision:** fabricctl (CLI + root `fabric-agent` — deliberately not `fabricd`, FRRouting's OpenFabric daemon — `fabric-admins` group, no docker group) and the Open Fabric web UI container; one repo, two artifacts ([1.1.1.3](../volume_1_description_and_architecture/1.1.1-what-fabric-is.md#1113-two-products-fabricctl-and-the-fabric-ctl-web-control)).
- **Shapes:** 1.3, 1.8
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** the owner framed fabric as two products from the start (2.3.1.8.1).
- **Status:** In force, built differently: the CLI runs as root via sudo, `fabric-agent` serves only the web UI, no `fabric-admins` group (1.1.1.3).

## 2.1.3.3 Setup UX

- **Decision:** Default change list → Proceed / Advanced; everything settable in `vars.yaml`; `--non-interactive` ([1.3.2.1](../volume_1_description_and_architecture/1.3.2-setup-design.md#1321-setup-secure-by-default-fully-scriptable)).
- **Shapes:** 1.3, 3.3
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** a person can accept sensible defaults in one step, and an unattended install can set everything in a file.
- **Status:** In force.

## 2.1.3.4 Setup with no terminal is refused before it asks anything

- **Decision:** `fabricctl setup` that would ask a question (not `--non-interactive`, `--doctor` or `--undo`, nor
  only steps that need no input) and finds no terminal on stdin (a pipe, `ssh -T`, a script) is refused before
  anything is asked or changed, exit 1, saying to run `sudo fabricctl setup --non-interactive --file FILE` (or
  `--non-interactive` alone for the defaults). `--file` alone still asks (Guided or Advanced, and what the file
  leaves out), so it is refused the same way ([1.3.2.4](../volume_1_description_and_architecture/1.3.2-setup-design.md#1324-setup-with-no-terminal-080)).
- **Shapes:** 1.3 (1.3.2.4), 3.3 (3.3.1.1.2)
- **Made:** 2026-10-24, by the owner ("yes"), from the DHCP lab campaign (`dev/0.9.0` note 2.3.10.11.16: setup
  with no terminal crashed with Python's `EOFError` at its Guided/Advanced question).
- **Why:** a refusal that says what to run instead is what an unattended caller can act on; a traceback is not.
- **Status:** In force; built 2026-10-24 (`setup/require_terminal`).

## 2.1.3.5 The apt signing key takes fabric-ctl's name; the same key, the same fingerprint

- **Decision:** the apt repository's signing key (1.3.1.1; fingerprint `9946C72491FC85485ACD879BD0DF2E75E6E73230`,
  today's only user ID "open-fabric apt repository <apt@open-fabric.invalid>") gets a second user ID, "fabric-ctl apt
  repository <apt@fabric-ctl.invalid>", made the primary one, and `public.key` is published again with it. It is the
  same key: its fingerprint does not change, so a host that already trusts it needs nothing, and apt checks
  signatures by the key, not by its name. Done by the owner, from the key's offline copy, with
  `scripts/release/rename-apt-key.sh` (agents never handle the private key: 2.1.1.2, Rule 10); the procedure is
  [3.14.1.6](../volume_3_installation/3.14.1-building-images.md#31416-renaming-the-apt-signing-key-the-same-key).
- **The old user ID — the owner's choice, recommended (A):**
  - **(A) Kept, below the new one (recommended).** Nothing to undo later; a tool that shows every ID still shows the
    old name, under the new one. It can still be revoked at any time (B, later), but a revoked ID cannot be taken
    back.
  - (B) Revoked (`rename-apt-key.sh --revoke-old`). Only the new name is valid; irreversible.
- **Why a script on the owner's PC, not a workflow:** `public.key` is exported from the secret key at every publish
  (`packaging/apt/build-repo.sh`), so the new ID must be in the secret `GPG_PRIVATE_KEY` itself; a workflow can read
  that secret but cannot write it back (its token has no right to the repository's secrets), and an ID added in the
  workflow at each publish would differ from the offline copy. The offline copy (make-apt-key.sh's folder) holds the
  key and its passphrase, so the owner's run updates the secret and the copy together, the secret passing through
  `gh secret set` on standard input only.
- **Test:** `tests/release/apt_key_test.sh` checks the published `public.key`: one key, this fingerprint, its primary
  ID the new one, the old one not primary. Tried on a throwaway key renamed the same way (fails before, passes
  after; 2026-10-31); on the published key it fails until the rename is published.
- **Shapes:** 1.3 (1.3.1.1), 3.14 (3.14.1.6)
- **Made:** 2026-10-31, by the owner (relayed by the coordinator): give the key "a fabric-ctl name, keeping the same
  key". The old ID's fate: open, (A) recommended.
- **Status:** Decided; the script and the test written 2026-10-31 on `dev/0.9.0`. **Waiting for the owner** to run
  3.14.1.6 step 1 (and to choose A or B); then the next apt publish carries the name.

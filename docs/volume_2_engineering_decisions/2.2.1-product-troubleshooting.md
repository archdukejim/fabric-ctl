## 2.2.1.1 Likely: WSL's Ubuntu stops between test steps, taking a kept sandbox and /tmp with it

*Added 2026-11-03, while 0.9.1 was measured (2.3.8.5.1). Marked **likely**: the cause fits every case seen but has not
been proved.* Applies to the developer's machine (gaming-23: Windows, Docker in WSL's `Ubuntu-24.04`), where the
sandbox (3.1.2, `tests/sandbox/run.sh`) and the container suites run.

- **Symptom:** a sandbox left running with `KEEP=1` shows `Exited (255)` a little while later; files the suites wrote
  under `/tmp` (for example `/tmp/fabric-tests/sandbox/doctor-undo.log`) are gone; containers with a restart policy
  (other projects' too) show a fresh start. Three times on 2026-11-02 and 11-03, each soon after the last command run
  through `wsl.exe` ended: at 09:06 on 11-03 the distribution was found stopped two minutes after a sandbox run
  (294 passed) had finished.
- **Likely cause:** WSL stops a distribution shortly after its last `wsl.exe` client exits. `vmIdleTimeout=-1` in
  `.wslconfig` keeps WSL's virtual machine running, not the distribution inside it, so Docker and its containers go
  down with the distribution and `/tmp` (a tmpfs) is emptied.
- **Workaround:** keep one `wsl.exe` attached for as long as WSL's state matters. Run a kept sandbox and what uses it
  in **one** `wsl.exe` session (as 2.3.8.5.1's measurements were: the sandbox, the fills, the loads and the removal
  in one script). Write the logs a later step needs to the Windows side (`FABRIC_TEST_OUT=/mnt/c/...`), never only to
  `/tmp`. The sandbox now also prints doctor's failed lines into its own log (`doctor_why`), so a failure's reason
  outlives `/tmp`.
- **To prove it:** with nothing else attached, end a `wsl.exe` session and read `wsl.exe --list --running` a few
  times over the next minutes; then repeat with a second session left open (for example `wsl.exe -d Ubuntu-24.04
  sleep infinity`) and see that the distribution stays.
- **What it explained:** the sandbox's one failure of 2026-11-02 21:21 ("doctor passes with trust declined"; 293
  passed, 1 failed) could not be explained, because its doctor log was in `/tmp` and lost. The same check passed in
  the runs before and after it (294 passed, 0 failed, 2026-11-03), so it was not reproduced; the next failure will
  show doctor's own words.

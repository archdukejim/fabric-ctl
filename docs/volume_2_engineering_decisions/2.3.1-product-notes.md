### 2.3.1.2.5 Impact assessment

- **Architecture:** none. Documents only; no behaviour changes.
- **Breaking changes:** every manual number changes, once, and the volume folders are renamed. Things that cite them change in
  the same change: links inside the manual; `manual X.Y` references in code docstrings, comments, templates and
  messages printed to users; the tests that check the manual (the docs suite, the function reference generator and
  its number file, the review ledger); `AGENTS.md`. Old numbers stay in git history; 2.3.1's tables resolve them.
- **Scope creep risk:** large but mechanical. The risk is losing or misplacing content. Guarded by Rule 9's baseline:
  before and after, every old item is accounted for (a new place, or a removal note), every link resolves, the docs
  and lint suites pass, and no code behaviour changes (the code changes are comment and message text only; the unit
  and render suites run before and after).
- **Effort:** the largest documentation change so far — a full day of work or more, done on its own branch
  (`manual-rebaseline`) and merged after 0.6.2 so production does not wait on it.

## 2.3.1.3 Aligning fabric to the global working rules: the plan

*Written before the re-baseline of 2026-10-08: the manual numbers, volume numbers and decision IDs in this topic are the old ones, kept as written; 2.3.1.1 maps them.*

### 2.3.1.3.1 Why

The owner's global working rules (Rules 1–13, from `github.com/archdukejim/engineering-rules`) make a 5-volume
manual under `docs/` the only source of truth, settle per-project choices in a decision register (Rule 13,
chapter 1.2), and fix the repository layout (Rule 7). fabric predates them: its documentation is 51 flat files
(guides, `design/`, a generated function reference, `maintenance/`), its rules live in `AGENTS.md`, and its code
sits in `fabricctl/`, `webui/` and `installers/deb/`. Owner decision 2026-10-03: align everything in one branch,
`feature/manual-alignment`, before any new feature work (the Samba work waits).

### 2.3.1.3.2 Scope

Approved by the owner on 2026-10-03 (Rule 5.5, after the impact assessment in 5.1.1.6):

1. The manual: master index, five volumes, every existing document moved into its volume by aspect (5.8),
   numbered (5.7); the decision register (1.2) with the checklist answers (Rule 13).
2. Every reference to the old documents in code, tests, templates and tools rewritten to manual numbers; the docs
   checks in `tests/docs/` and the generated function reference (`gen_lib_doc.py`) writing into the manual; the
   in-browser manual (nginx `/manual/`) reading `docs/README.md` instead of fixed tabs.
3. `AGENTS.md` and `CLAUDE.md` cut down to pointers into the manual (Rule 7.1); facts held in the agent's memory
   moved into the manual (5.2) and the memory trimmed.
4. The repository layout of Rule 7: `src/` (with `src/ux/cli` and `src/ux/web`, decision A2), `templates/`,
   `static/` (vendored libraries recorded in `THIRD_PARTY_NOTICES`), `config/`, `packaging/`, `scripts/`,
   `examples/`; the root README under 1000 words.
5. Container image publishing (decision C5): fabric's own images built in CI from `packaging/` with one build
   matrix, multi-arch, published and pinned by digest; hosts pull instead of building. This changes existing
   designs (D9, D10, D21), so it gets its own design chapter and impact assessment before it is built.
6. Lint (decision B3): ruff and shellcheck in CI and in the definition of done.

### 2.3.1.3.3 Order of work

Each step is its own commit (or a few), checked before the next:

1. Baseline (Rule 9): the installed tree with hashes, the rendered templates, the generated reference, every test
   suite's results — captured at commit `b64302c` before any change (5.1.1.6).
2. This skeleton: master index, volume indexes, this plan, the decision register (1.2).
3. The documents, in one generated move: most old documents span several volumes, so moving a volume at a time
   would leave broken links between commits. A one-off tool moves them by a line-exact mapping, renumbers headings,
   rewrites links and `§` references, and the coverage check of 5.1.1.6 proves the result; the map of old
   sections to manual numbers is 5.1.2.
4. References in code and tests, the docs tools, the in-browser manual.
5. Agent files and memory.
6. Rule 7 layout (moves only, behaviour unchanged), then lint.
7. C5 image publishing (after its design chapter is approved).
8. Baseline comparison, every suite, the sandbox. (`HANDOFF.md`, the session handoff, was removed early on
   2026-10-03 at the owner's request: it named a test machine's address in this public repository.)

  to the baseline; the test results must match.

  removed when the last document has moved. (Removed 2026-10-03: the function reference became 1.11 and the review ledger moved to Volume 5's

### 2.3.1.8.1 Product shape (2.1.1.8, 2.1.1.9, 2.1.1.10, 2.1.1.11, 2.1.1.12, 2.1.2.3)

### 2.3.1.9.2 Docker in WSL

What running the suites there has taught (2026-10-02 to 10-03):

- Call WSL with `MSYS_NO_PATHCONV=1` from Git Bash, and put any multi-line command in a script file: inline
  `bash -c` strings lose their escapes, and a `$(…)` in them is expanded on the Windows side.
- The distribution shuts down a few seconds after its last session ends, stopping detached containers (the
  sandbox exits 255) and restarting the owner's: keep a session open for the whole run.
- Never start a second `tests/run-all.sh` with the same `FABRIC_TEST_OUT` while one runs: run-all clears that
  folder. The dirsrv, keycloak and hardening suites need `render` in the same run.
- Never edit a test script while it runs: bash reads scripts as it goes.
- The WSL kernel can hang: processes stuck in `sync()` (state D on `super_lock`) never exit, 389-DS reports
  "already running as process N" and Docker cannot stop containers. Only `wsl --shutdown` clears it, which stops
  every distribution: ask the owner first.
- A Windows `git worktree` cannot be used from WSL (its `.git` file holds a Windows path): clone inside WSL.
- From Git Bash, Python defaults to the cp1252 code page: set `PYTHONUTF8=1` before it edits UTF-8 files.

### 2.3.1.11.4 Certificate revocation, for everything (2.1.5.10)

- Step-CA publishes a **CRL** (its built-in CRL, signed by the intermediate, regenerated on every revocation and at
  least daily), served on `certs.<domain>` (HTTP, like the CA files) and named in every certificate fabric issues
  (CRL distribution point) from 0.6.3 on.
- **Revoke** any certificate fabric issued — device, person, LAN machine (ACME), service, a federation site's
  intermediate — from the web console's PKI page or `fabricctl certs revoke <serial|name> [--reason R]`, permission
  `pki:revoke` (new; in the PKI operator's bundle). Every revocation is audited.
- **Checked by** FreeRADIUS (EAP-TLS: `check_crl = yes` with the CRL fetched into its config) and nginx (client
  certificates: `ssl_crl`), both refreshed by the certificate timer (2.1.5.4). A revoked device is refused at its next
  authentication even if it is still linked. Answers open decision 2.1.5.2 (federation site CAs).
- Unlinking a device stays the quick way to cut one off; revocation is the lasting one.

  end. **Remove** asks for the uid typed back, removes the account and its Keycloak user; their issued certificates
  are revoked (2.3.1.11.4). Only the site's own people; fabric's built-in accounts are refused with the reason.
- The web console's People page gains disable, enable, remove and groups; permissions `people:disable`,
  `people:remove` and `people:groups` (new; disable in the Helpdesk bundle, the others admin).

### 2.3.1.11.8 Offline install bundles (2.1.14.14)

- `fabricctl images export --arch amd64|arm64 -o <file>` makes **one bundle per release and architecture**: fabric's
  `.deb`, the Ubuntu packages it installs (Docker and the rest, for the host's Ubuntu release), every image in the
  lock by digest (`docker save`), and their cosign signature bundles, with a manifest (versions, digests, hashes).
- `sudo fabricctl setup --offline <bundle>` (and `fabricctl images import <bundle>` on an installed host) checks the
  manifest's hashes and **every image's signature offline** (the bundled cosign bundles against fabric's identity,
  2.1.14.6), then installs the packages and loads the images; nothing is fetched. No local registry.
- An image or package whose signature or hash does not check is refused, with which one and why.

### 2.3.1.11.9 OpenBao's leftovers (2.1.7.4, 2.1.7.5)

- **Keycloak's database password rotates monthly** (2.1.7.4): Postgres gets its own admin user, separate from
  Keycloak's (which stops being a superuser); OpenBao's database engine owns Keycloak's password as a static role and
  rotates it on a monthly schedule, at night; fabric then renders Keycloak's settings and restarts it (about a minute).
  **Postgres never depends on OpenBao to start**: the password lives in Postgres; only a rotation needs OpenBao. A
  rotation that fails leaves the old password working and is a warning. `fabricctl vault rotate-db` rotates now.
- **An SSH certificate authority for the domain's Linux machines** (2.1.7.5), OpenBao's SSH engine:
  - **user certificates**, 8 hours, with the person's AD groups as principals (sudo still from AD's rules), from the
    web console (paste a public key, download the certificate) or `bao ssh` after signing in with Keycloak;
    permission `ssh:sign` (new, everyone signed in);
  - **host certificates** for joined machines (the join script asks for one; renewed by the machine's timer), so
    people's clients trust the domain's hosts without the first-connection prompt;
  - the join script trusts the user CA (`TrustedUserCAKeys`, an option, on by default) and installs a known-hosts
    line for the host CA. OpenBao off means no SSH CA, said so on the page.

### 2.3.1.11.10 The Linux join's leftovers (2.1.6.31)

- **Host groups:** AD groups in the site's `OU=groups` (`<site>-hosts-<name>`), machines as members; log-on rules per
  host group (which people's groups may log on), enforced through SSSD's GPO-based access as today. CLI `fabricctl
  machines groups | group add|remove <group> <machine>` and the web console's domain section; permission
  `machines:admin`.
- **Sudo rules:** an editor for custom sudo rules beyond the site's default: who (people or groups), which commands,
  as whom, on which host group; stored as AD sudo rules (SSSD's `sudo_provider=ad`), under the site's OU so nested
  sites inherit as today. CLI `fabricctl sudo list | add | remove`, web console; permission `sudo:admin` (new, admin
  bundle). A rule granting ALL to everyone is refused.
- **systemd-resolved:** the join script points resolved at fabric's DNS with the domain as search domain (1.6.7.5),
  keeping the machine's other links' DNS as they are; an option, on by default.
- The manual's drift is fixed with it (4.6.6 names `<site>-admins` where the code uses `<site>-linux-sudo`).

## 2.3.1.18 Proposal: 0.7.0, DNS made right, and AdGuard Home reconsidered

Written 2026-10-11 (decision 2.1.1.49) from the owner's test of `v0.8.0-rc.3` on the test Pi. Nothing here is built.

**What the owner found**

- **Adding a list took minutes.** Measured on the Pi: the lists job itself is quick (5.9 s for "Fetch every list now":
  the AdGuard DNS filter, 362,758 records, downloads in 0.1 s, converts in 2.6 s and checks in 2.6 s). The time goes
  elsewhere: every DNS filter change from the console (`agent/post_dns_filter.py`) runs `apply_changes`, a full
  `fabricctl --apply` of every service, and the console waits for it. Adding one list was still applying 3 minutes
  later. A list, rule, group or safe-search change needs only the resolver's configuration written and
  `rndc reconfig` (or one zone reloaded): seconds.
- **Lists should be checkboxes, enabling them quick:** as AdGuard Home's page (the owner's screenshot): every list
  of the catalogue with a checkbox, its rules and when it was updated. With every catalogue list fetched and
  converted daily (disk and a little CPU; no memory until enabled), enabling one is a reload, and its memory is
  known before it is ticked.
- **Memory:** a list in BIND is a response policy zone held in memory, two records per blocked name (the name and
  `*.` below it), measured at 0.53 KB a record: the AdGuard DNS filter's 181,422 rules cost about 188 MiB of the
  resolver's 384 MiB. The owner's own AdGuard Home runs 15 lists (about 2.6 million rules, HaGeZi's Threat
  Intelligence Feeds 2.0 million of them): its filter is a matcher made for the job, rules kept as compact strings,
  one rule covering a name and every name below it. Merging the enabled lists into one zone, deduplicated, would
  save what the lists share (perhaps 20-40%), not the order of magnitude.
- **Zones:** the console adds and removes records in existing zones but cannot add a zone (only `sudo fabricctl`'s
  menu can).
- **The CA's address:** one place, `info.<domain>/certs`, and `http://<host_ip>/certs/` for a computer that does not
  yet use fabric's DNS; `certs.<domain>` goes, with no redirect (the owner).

**The engine, reconsidered: AdGuard Home behind fabric's console**

The owner: "consider returning adguardhome using api instead of it's default web ui". The shape, to be confirmed:

- AdGuard Home answers clients (53, and DoT/DoH), as in 0.6, with fabric's zones forwarded to the authoritative BIND
  and never filtered, internet names to Cloudflare over DoT. `bind9-resolver` goes; the authoritative BIND stays.
- **fabric's console is its only UI:** fabric-agent drives AdGuard Home's HTTP API (`/control/...`: filtering lists
  and their enabled flag, rules, clients and their settings, safe search, the query log, statistics). AdGuard
  Home's own web UI is not published: its HTTP port is on `fabric_net` only (no nginx site), its account a
  generated password in fabric's secrets. (AdGuard serves its UI and its API from the same port, so the UI cannot be
  turned off, only left unreachable.)
- **What maps directly:** lists (catalogue checkboxes are AdGuard's own model: it fetches and refreshes them), the
  owner's allow and block rules, upstreams, safe search per client, the query log and statistics, DoT and DoH.
- **What does not map:** a client group's own lists. AdGuard Home's lists are global; per client it has settings
  (filtering on or off, safe search, blocked services, upstreams) and rules may name clients (`$client=`). A group's
  own rules map; its own lists would not, unless shown as rules. The query log is AdGuard's, not BIND's
  (`querylog.py` and the 90-day statistics are rebuilt on its API).
- **The cost:** a reversal of 2.1.12.3 a release after it was built. The work of 0.7's steps 2 to 6 for the resolver
  is replaced, not extended; the move-from-AdGuard code (2.3.12.1.9) becomes a move back, for installs that ran a
  0.8.0 candidate (only test hosts). Its container must meet fabric's hardening (non-root, capabilities dropped,
  read-only root, memory limit: 1.2.8) and its image pinned and published like the others (2.1.14).

**Impact assessment (5.5)**

- **Architecture:** the client-facing resolver changes engine; the console's DNS filter page keeps its pages and
  routes, its data from AdGuard's API instead of BIND's files and logs. The authoritative BIND, zones, TSIG, ACLs
  and the CA are untouched.
- **Breaking:** for released installs, none: 0.6.x ran AdGuard Home, and 0.7 was never released. For the owner's
  test hosts on a 0.8.0 candidate: their resolver settings move to AdGuard Home at the upgrade, groups' own lists
  reported if any.
- **Scope creep risk:** high if both engines are kept; the proposal replaces one with the other. The spike below
  comes first so the choice is made on measurements.

**A spike before the choice (Rule 4's exception), awaiting the owner's go**

On WSL, then the test Pi (arm64, 4 GB), with the owner's 15 lists: AdGuard Home with them, against BIND's resolver
with the same lists merged and deduplicated. Measured: memory after loading, time to load and to enable one more
list, answer time for blocked and allowed names (p50, p99), a restart. In `spikes/dns-engine/`; nothing merged.

**Questions for the owner (after the spike)**

1. The engine: AdGuard Home through its API, or BIND with merged lists.
2. With AdGuard Home: a group's own lists become rules naming the group's clients, or go.
3. The memory limit for the filter on a 4 GB host.

**The spike's findings** (2026-10-11, WSL, `spikes/dns-engine/`; AdGuard Home v0.107.79, BIND 9.20.29; the owner's
15 lists, one download served to both). 0 checks failed.

| | A: BIND in front, AdGuard Home behind | B: BIND alone, the lists merged |
|---|---|---|
| The 15 lists | 2 771 618 rules, added through the API in 2.3 s | 5 016 955 records, 4 587 784 merged (deduplication: 8.6%) |
| Memory, 15 lists | 350 MiB (empty: 14 MiB); BIND in front 45 MiB | 2.33 GiB |
| A 16th list (HaGeZi's Ultimate, 3.0 million rules) | 0.2 s; 921 MiB while it rebuilds, 345-434 MiB after | 29 s (merge and reload); 3.15 GiB |
| A list off / on | 0.08 s / 0.93 s | a merge and reload |
| Answer, blocked name (mean) | 0.62 ms | 0.16 ms |
| Answer, ordinary name (mean, cached) | 0.60 ms | 0.54 ms |
| Restart until blocking again | 3.5 s (345 MiB, 16 lists) | 15.1 s (2.35 GiB) |

- **Checks passed (A):** fabric's zone answered by BIND though AdGuard has a rule blocking it; a listed name
  NXDOMAIN through BIND; an ordinary name resolves; the owner's rule blocks in BIND and BIND's log names it; a group
  (the kids' view forwarding from its own address) gets its own AdGuard rule, others do not; dnstap records the client,
  name and NXDOMAIN; AdGuard's query log and statistics off; `check_host` names the rule and its list in 0.05 s.
- **AdGuard Home's defaults to change:** `blocking_mode` answers `0.0.0.0` unless set to `nxdomain`.
- **No marker on a blocked answer:** through BIND, neither a blocked NXDOMAIN nor a genuine one carried an authority
  section, so an answer alone does not tell a block from a missing name: the log job asks `check_host`, cached per name.
- **Running it non-root, as fabric's hardening needs (1.2.8):** its first launch (no `AdGuardHome.yaml`) refuses any
  user but root, `--no-permcheck` or not; root with every capability dropped cannot write folders it does not own; as
  a non-root user `no-new-privileges` voids the binary's file capability (`cap_net_bind_service`), so port 53 comes
  from the namespace's `ip_unprivileged_port_start=53`, and NET_BIND_SERVICE stays in the bounding set only so the
  kernel will run the binary at all. fabric renders `AdGuardHome.yaml` itself (schema 34), so there is no first launch.

### 2.3.1.19.5 Fabric's `info` name cannot simply be turned off

Found 2026-10-12 while building 2.1.2.22 item 6 for 0.7.1. The decision asks that deleting the landing page's
`info.<domain>` in the DNS tab turn its name off through its setting (`landing_page_cname`). It cannot be done by
the setting alone, so 0.7.1 refuses it like fabric's other names (1.4.1.4), naming the setting, and the owner
decides how it should work:

- **The setting cannot say "off".** `vars.yaml.j2` reads `landing_page_cname | default('info', true)`: an empty value
  means `info`, on purpose since 0.6.3 (installs that had none got `info`, 2.1.4.3).
- **The landing page's address does not follow it.** `hostname_landing` is rendered into the installed settings
  (`info.<domain>`) and kept from then on, so changing `landing_page_cname` later moves the DNS name but not the page.
- **The page is load-bearing.** `info.<domain>` serves the CA certificates over plain HTTP to new devices
  (`/certs/`), the join scripts point at it, and every certificate step-ca issues names its CRL there
  (`http://info.<domain>/certs/crl/…`, 2.1.5.11). Moving the page to `<domain>` (where it was before 0.6.3; nginx
  already handles `hostname_landing` equal to the domain) needs nginx's certificate for the new name before nginx
  restarts — nginx will not start without it — and leaves the certificates already issued pointing their CRL at a
  name that no longer answers until they are renewed.

Options for the owner: (a) keep `info` as fabric's, never deleted (as built); (b) a real "landing page at
`<domain>`" setting: an explicit off value for `landing_page_cname`, `hostname_landing` re-rendered from it, the
landing certificate re-issued first, and the CRL kept answering at the old name until the last certificate naming it
expires; (c) keep serving the page at `info.<domain>` but drop only the DNS name (not useful: nothing could reach it).

**Settled by 2.1.4.6 (the owner, 2026-10-12):** none of the three. The page moves to a path fabric keeps
(`http://<host_ip>/info/`, and fabric's own names), `info.<domain>` becomes an ordinary record the admin may rename,

## 2.3.1.22 The 0.7.2 release candidate: BIND's restart fix

Decision 2.1.1.57. Built 2026-10-15 on `rc/0.7.2` from `main` at `929e462a` (0.7.1).

**The bug** (found by 0.8.0's sandbox, 2026-10-15): before BIND restarts (an apply that changes its image or its
configuration, or setup's deploy), each changed zone was frozen and its new file installed as soon as `rndc freeze`
answered. BIND writes the zone's journal into the file after it answers, so when the journal held changes (names
registered by DHCP or RFC2136), BIND's copy of the old zone replaced the new file a moment later; the restart served
the old zone, and a changed record was missing until a later live swap of that zone. Reproduced by hand in the
sandbox: frozen, the file copied in at once, BIND overwrote it within 2 seconds when its journal was newer than the
file.

**The fix:** `dns/freeze_and_install` waits up to 3 seconds for BIND's write when the zone's journal is newer than its
file (the only case in which BIND has something to write), then installs the new file. Used by
`deploy/finish_without_start` and `deploy/restart_changed`. Test: `tests/dns/freeze_and_install_test.py` (the `zone`
suite).

## 2.3.1.29 A same-size change within one mtime tick was never copied: filecmp's cache (2026-10-24)

Found on `dev/0.9.0` (its 2.3.10.11.19, 24a236c9: a "flaky" `copy_tree_with_perms` test was this bug), and on `main`
and `dev/0.8.0` too. `filecmp.cmp(a, b, shallow=False)` keeps a cache keyed by each file's (type, size, mtime) and
answers from it when both signatures match, so a rewrite of the same size whose mtime did not move (two writes inside
one tick of the file system's clock, or a copy that kept the old mtime) read as unchanged and the deploy kept the old
file, saying nothing. Seen here too: two equal files, then one rewritten with the same size and its mtime set back,
and `filecmp.cmp` still answered True.

- **Fixed:** `common/same_content` compares the sizes, then every byte, on every call (`dev/0.9.0`'s
  `_same_content`, the same code). It has four callers, so it is its own file (Rule 1): `common/copy_tree_with_perms`
  (trees: fabric's code, web assets, service config), `common/copy_if_changed` (compose files, units, nginx.conf),
  `federation/deploy_federation_endpoint` (its unit), and `pki/publish_ca_certs` (fabric's CA in the host's trust
  store), the fourth found while fixing the three named. No `filecmp` is left in `src/`.
- **Tests both ways,** in the `consent` suite: `tests/common/same_content_test.py`,
  `copy_tree_with_perms_test.py`, `copy_if_changed_test.py` and `tests/federation/deploy_federation_endpoint_test.py`
  (as root, its unit path a temporary file): a same-size change in the same mtime tick is copied and reported; an
  mtime-only change is not. `publish_ca_certs` runs `update-ca-certificates` on the host when its trust files change,
  so no test calls it; its comparison is `same_content`, tested above.
- **Merging `dev/0.9.0`:** its `copy_tree_with_perms` keeps `_same_content` private; this branch's imports
  `common/same_content` instead, so that file meets a small conflict: keep the import. Its test file also checks
  bytecode caches (`dev/0.9.0`'s efa63059, not on this branch); keep its checks and these.
- **Results (2026-10-25), each suite alone:** `lint`, `consent` (the four new tests: 9, 6, 5 and 4 passed, 0
  failed), `deploy`, `render`, `pki` and `federation` passed; the sandbox 291 passed, 0 failed.

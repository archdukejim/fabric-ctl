## 2.1.1.1 Target OSes

- **Decision:** Ubuntu LTS only: 24.04 and 26.04 (reference: Raspberry Pi 4 GB, arm64); amd64 + arm64. fabric's container images stay Debian-based (2.1.1.5): that is the image base, not a host target.
- **Shapes:** 1.1, 1.2, 3.2
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner; revised 2026-10-04 (owner).
- **Why:** one large, widely supported distribution with a long support cycle rather than a test matrix spread over three (2.3.1.8.1).
- **Status:** In force, revised 2026-10-04: Debian 13 and Raspberry Pi OS are no longer host targets (with 2.1.1.10). Revised by 2.1.1.43 on 2026-10-10: Ubuntu 22.04 too.

## 2.1.1.2 Apt repo hosting

- **Decision:** GitHub Releases for the `.deb` + reprepro-built signed repo on GitHub Pages (`gh-pages`), dedicated signing key in Actions secrets ([1.3.1.1](../volume_1_description_and_architecture/1.3.1-host-package.md#1311-package-design) Distribution).
- **Shapes:** 1.1, 1.3, 3.1
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** hosts install and update with apt like any other package, from one signed source.
- **Status:** In force. The Release `.deb` was built first; the APT repository was built later (`packaging/apt/`, suites `stable` and `testing`).

## 2.1.1.3 Keep Ansible for remote install?

- **Decision:** No: removed. The local bootstrap is `installers/deb/install-from-checkout.sh` (was `setup.sh`, 2.1.1.7); remote = ssh + apt (phase 2).
- **Shapes:** 1.1, 1.3
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** one installer, the `.deb`, for a checkout and a release alike (1.1.2).
- **Status:** In force.

## 2.1.1.4 Channel signing key custody and soak period before `candidate` → `stable`

- **Decision:** Proposed: an Ed25519 key in a protected GitHub environment; a 7-day soak.
- **Shapes:** 1.14
- **Made:** proposed 2026-09-27 to 2026-10-01, while fabric was designed; never marked decided.
- **Why:** it was to protect the signed image channel of 2.1.14.2.
- **Status:** Replaced by 2.1.14.6 (2026-10-03): the channel it was for gave way to published images (2.1.1.21), signed keylessly in CI, so there is no channel key to keep.

## 2.1.1.5 Which upstream line

- **Decision:** LTS or extended-support wherever the project has one (BIND 9.20 ESV, Kea 3.0 LTS, Postgres majors, nginx stable, Debian stable, Ubuntu LTS). Projects without one (OpenBao, Keycloak, Step-CA, Fluent Bit) support only their latest release: follow it, patch releases automatically, never a major by itself (2.1.14.3). A distro package that lags the upstream LTS (Kea: Debian 2.6 vs 3.0) comes from the upstream's signed repository instead.
- **Shapes:** 1.1, 1.14
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** long-supported releases keep upgrades simple (global Rule 11).
- **Status:** In force.

## 2.1.1.6 Names

- **Decision:** The repository is `open-fabric` and the web UI is shown as "Open Fabric" (subtitle *web control*). Everything else keeps its name: the package and command `fabricctl`, `/opt/fabric`, `/etc/fabric`, `fabric.target` and the `fabric-*` units, `fabriclib`, the Keycloak `fabric:*` roles, OpenBao's `fabric/` path, the image names. The root daemon is `fabric-agent`, never `fabricd` (FRRouting's OpenFabric daemon). The repository is renamed before the image channel and APT repository are published on GitHub Pages (Pages URLs do not redirect).
- **Shapes:** 1.1, 1.3, 1.8
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** renaming the installed names would need migration code on every install for no user benefit.
- **Status:** In force.

## 2.1.1.7 Repository layout

- **Decision:** Three product folders: `fabricctl/` (the Linux host side), `webui/` (the control-plane container) and `installers/deb/` (the Debian package wrapper; more formats as siblings). The installed tree (`/usr/lib/fabricctl/fabric`, `/opt/fabric`) is unchanged: `installers/deb/assemble-tree.sh` maps the folders onto it, so installs upgrade in place. The web UI stays in this repository (it changes together with the agent API it calls). `setup.sh` became `installers/deb/install-from-checkout.sh`: a checkout installs through the same .deb as a release.
- **Shapes:** 1.2
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** the product design (2.3.1.4 maps where it went).
- **Status:** Replaced on 2026-10-03 by global Rule 7's layout, with 2.1.1.14 and 2.1.1.30 (2.3.2.1); the installed tree still never depends on the repository layout (2.1.2.5).

## 2.1.1.32 When fabric has installs that must be kept

- **Decision:** **0.6.1 is the first production release.** 0.6.0 may still be rebuilt. From 0.6.1 every release upgrades in place from the previous one (2.1.1.20 in force), with the migrations it needs, and is tested that way: the previous release from apt `stable`, upgraded to the candidate from `testing`, then the host suite and a check that people, the CA, certificates, the domain, AdGuard's settings and secrets survived. Releases from 0.6.1 are full GitHub releases on apt `stable` (no longer pre-releases); candidates stay on `testing`. 1.0 remains the federation milestone.
- **Shapes:** 1.1, 3.1, 3.3
- **Made:** 2026-10-07, by the owner. Revises 2.1.1.31, 2.1.1.20 and 2.1.1.18.
- **Why:** 0.6.0's sign-in was too strict to be usable on the owner's network; 0.6.1 (1.1.4.6, the 0.6.x sign-in work) is that feedback fixed, and the first release the owner's home fabric runs for keeps.
- **Status:** In force.

## 2.1.1.33 Deviation: tests are integration suites by domain

- **Decision:** A deviation from global Rule 7.1, "each source file gets one test file at the mirrored path". Tests are organised by domain under `tests/<domain>/` (dns, pki, samba, kea, federation, …), each suite proving its domain against real containers, plus the end-to-end sandbox (`tests/sandbox/`) and the real-host suite (`tests/host/`).
- **Shapes:** 1.1, 3.1
- **Made:** 2026-10-03, by the owner.
- **Why:** fabric's behaviour lives in how its functions drive real services (Samba, BIND, Kea, Keycloak, OpenBao). One test file per source file would test each function alone, mostly against mocks, which Rule 9 restricts to pure logic.
- **Status:** In force.

## 2.1.1.34 Deviation: sign-in starts at a password

- **Decision:** A deviation from global Rule 10, "secure by default". A new install signs everyone in, admins included, with a username and password. Every stronger layer — TOTP, a passkey, a per-user certificate, the web UI's client certificate — is raised from the web console; lowering one is done only at the command line (2.1.6.24), with a typed confirmation, an audit entry and a warning that stays visible.
- **Shapes:** 1.6, 1.8, 4.6
- **Made:** 2026-10-07, by the owner; built in 0.6.1.
- **Why:** the owner: a first standup should be simple, and everything can be raised to a more secure method from the web console. The rule's other half still holds: every relaxation below what an install has is explicit, and status output and the web UI show it.
- **Status:** In force.

## 2.1.1.35 The one-time re-baseline of the manual

- **Decision:** The manual has four volumes — 1 description and architecture, 2 engineering decisions (2.1 decisions, 2.2 troubleshooting, 2.3 notes), 3 installation, 4 operations — and Volumes 2–4 follow Volume 1's seventeen chapters, one per part (global Rules 5.9 and 5.10). Every number was mapped once (2.3.1.1); the decisions, numbered D1–D121 (and F, J, S) before, became topics of 2.1, identified by their topic numbers; the old register was deleted. A note about one part sits with that part (2.3.C); a note about the whole product sits in 2.3.1 or 2.3.2.
- **Shapes:** every chapter
- **Made:** 2026-10-07 (the re-baseline, the spine, the decisions as topics) and 2026-10-08 (four volumes; notes by part), by the owner.
- **Why:** one number leads to every aspect of one part; a decision is found by the part it shapes (2.3.1.2).
- **Status:** In force. Rule 5.10 allows it once: numbers follow 5.7 again from here.

## 2.1.1.36 Every release is tested upgrading in place from the previous one

The first run caught up on 0.6.1 → 0.6.2.
- **Shapes:** 1.1, 3.1
- **Made:** 2026-10-08, by the owner, for 0.6.3.
- **Why:** carries out 2.1.1.32, which 0.6.2 shipped without (2.3.5.3.7).
- **Status:** In force; **built 2026-10-08** for 0.6.3.

## 2.1.1.40 A release goes rc → tag -rc → promote, run as /rc, /tag and /promote

- **Decision:** Three steps, each a skill the owner runs ([3.14.1.4](../volume_3_installation/3.14.1-building-images.md#31414-publishing)).
  **`/rc`**: the candidate on `rc/<version>` (version, images published and pinned, every suite, the sandbox, the
  image-update test, the upgrade test on the test Pi, fixes) ending with the pull request to main, which the owner
  merges. **`/tag`**: after the merge, `v<version>-rc.<n>` on main (numbered per version from 1): a GitHub pre-release
  with the `.deb` and the pinned images tagged `<version>-rc.<n>`; apt is left alone. **`/promote`**: `v<version>` on
  the same commit as the last rc tag: the images tagged `<version>`, the Release, apt stable. Running `/tag` or
  `/promote` is the owner asking for that tag (global Rule 8: tags only when the owner asks).
- **Shapes:** 1.1, 3.14
- **Made:** 2026-10-09, by the owner ("/rc for release candidate … /tag … tag it -rc and then /promote promotes the RC
  to a full release number"; the tag's form, what it publishes, /rc's reach and where the skills live answered the same
  day). The skills live in the owner's engineering-rules repository (generic) and in this repository's
  `.claude/skills/` (fabric's steps, pointing here).
- **Why:** a release candidate tagged on main gives test installs exactly the build that will be released, before it
  becomes one; each step is one command for the owner.
- **Status:** In force. The rc tag's image tags (`<version>-rc.<n>`, small n) and the rc branch's publish tags
  (`<version>-rc.<run number>`, the workflow's run number, already past 60) share a form: they cannot meet while run
  numbers stay above the rc counts.

## 2.3.7.2 Proposal: local admin passwords in OpenBao

The owner's request (2026-10-10, decision 2.1.7.6): OpenBao sets every managed machine's break-glass local admin
password and keeps it, with exports for a physical safe. Design: [1.7.1.3](../volume_1_description_and_architecture/1.7.1-openbao.md#1713-local-admin-passwords-set-and-escrowed-by-openbao).

2.3.7.2.1 **The tension it settles.** Two good practices pull apart: never reuse a password after it was used, and
keep break-glass credentials sealed and checked (most secure facilities audit the envelope, not a vault). A password
rotated after every use outdates its envelope; one kept for the envelope is reused. fabric does not pick for the site:
rotation is a policy, every export knows which password version it holds, and a stale envelope is shown, never
silent. Microsoft's LAPS settles it the same way (post-authentication reset, backup to AD).

2.3.7.2.2 **Why the machine sets its own password.** Pushing from fabric would mean fabric holding a way into every
machine (WinRM or SSH as an admin); pulling means each machine holds only the right to write its own entry. Network
gear cannot run fabric's task, so it is the one case fabric pushes, per device integration.

2.3.7.2.3 **Impact assessment** (additive: a new topic and new decisions; nothing built changes).

- *Architecture:* a new KV mount and policies in OpenBao; machine certificate auth (2.1.7.7); a task installed by the
  Windows and Linux joins; a host account and a two-step rotation on the fabric host; a Keycloak role
  (`local-admin:checkout`); a web console page and a `fabricctl local-admin` command; export code that prints and
  writes to USB. Every one is a new user-accessible entry point, so each gets positive and negative tests (Rule 9).
- *Breaking changes:* none for existing installs; machines joined before 0.9 get the task when their join runs again.
  The Linux join gains an account (`local-admin`, 2.1.7.11) and the host one (`local-admin`): host changes, so they
  go through setup's consent (`accounts`).
- *Scope creep risk:* moderate. Network gear depends on vendor integrations, of which only the lab's authenticator is
  testable on gaming-23's VMs (2.1.1.45); real vendors wait for hardware and are a blocker until then. Windows is
  testable on the 0.9 supplicant VMs.
- *Testing:* the Windows and Linux member sides on gaming-23's VMs; the host side in the sandbox and on the test Pi;
  exports by reading back what was written (the PDF's text, the archive decrypted with k shares, refused with k-1).

   or `wtmp`.
3. **Who checks it out, and how:** root's `sudo fabricctl local-admin checkout` (root is the Enterprise Admin's tier,

4. **The host change:** making a local account and refusing it SSH (1.7.1.3.1: console log-on only) are changes

5. **With OpenBao locked:** a rotation due after a use waits, the used password staying valid until OpenBao is back,

## 2.3.7.7 The D6 build: the fabric host's local-admin (2026-10-22)

The owner answered 2.3.7.6's five questions on 2026-10-22 (decisions 2.1.7.16 to 2.1.7.20); D6 (1.6.12.15) was built
from them on `dev/0.8.0`. What it built is [1.7.1.4](../volume_1_description_and_architecture/1.7.1-openbao.md#1714-the-fabric-hosts-local-admin-080).

### 2.3.7.7.1 What the build settled where the design was silent (asked in the build's report)

1. **The consent item** is `local_admin`, recommended (declining leaves the host without it, shown as declined), its
   step `localadmin` right after `dbrotation` (it needs OpenBao unsealed) and before `admin`. The SSH drop-in is part
   of the same item: it is the host change that refuses the account over SSH.
2. **The grace** before a rotation is 1.7.1.3.4's default, 8 hours from the first use or check-out, and not a setting
   in 0.8.0.
3. **The two policies behave alike in 0.8.0.** 2.1.7.15 item 2 keeps rotation after use for `keep-until-checkout`,
   and 0.8.0 has no scheduled rotation, so both rotate after a use or a check-out; the switch is recorded (on the host
   and with the password in OpenBao) and shown, ready for 0.10.0's schedule. Asked.
4. **A check-out needs a reason** (1.7.1.3.5), one line of up to 200 characters; with OpenBao locked it is refused,
   since in 0.8.0 OpenBao holds the only copy (the printed sheet is 0.10.0's, 2.1.7.16).
5. **The SSH switch's store** is keyed by the DC's name (`CN=dc-host-<dc>`): every fabric host runs a DC, and the DC's
   name is permanent, unlike the host's computer account, which exists only while the host is a member. It is written
   only at a writable DC; a read-only DC's host is refused, naming the writable DC, where `--dc` sets it for another
   host. Asked: whether an RODC host should be able to set its own (by writing through the writable DC).
6. **On, sshd's drop-in** lets `local-admin` in with a password (and keyboard-interactive, which is PAM's password on
   Ubuntu), never with a key (`PubkeyAuthentication no`, `AuthorizedKeysFile none`), closed by `Match all` so nothing
   after it in sshd's configuration falls under the block; off, `DenyUsers local-admin`. Its name, `05-`, puts it
   before fabric's `10-fabric.conf` and Ubuntu's `50-cloud-init.conf`.
7. **A use** is a PAM session opened for `local-admin`, or one it opened (`sudo`, `su`), in the journal's auth and
   authpriv facilities, or a `USER_PROCESS` record of it in `/var/log/wtmp`; only those after the current password was
   set count.
8. **OpenBao's history:** a removed account's versions stay; its metadata's `current` becomes `none` with `removed`
   set. The undo refuses while the account is signed in (`userdel`), keeping the record so a second undo finishes.
9. **D2's listing** shows `local-admin` as managed only while fabric's record says fabric made it; approving it is
   refused. Another account of that name (fabric refuses to take it over) is listed and reminded of as before.

1. The SSH design of 2.1.7.19 (a switch in the domain store, off by default, set only by the Enterprise Admin):
   "yes, but I think that should be a suppressible alert too". Confirmed, and the alert's acknowledgement built as
   2.1.7.21 (1.7.1.4.10).
2. A read-only DC's host refused, its switch set from the writable DC's host with `--dc` (2.3.7.7.1 item 5): "yes".
3. The two policies alike in 0.8.0 (item 3): "yes".
4. The consent item recommended (item 1): "yes".
5. The grace fixed at 8 hours (item 2): "yes".
6. A check-out refused while OpenBao is locked (item 4): "yes".

The confirmations are recorded on 2.1.7.16 (3, 4), 2.1.7.17 (5), 2.1.7.18 (6) and 2.1.7.19 (1, 2).

How the alert was fitted to global Rule 10: the relaxation itself is never suppressed (status output and the UI show
every relaxation while it is active), so acknowledging silences only the alert, which is doctor's warning and the
console's reminders; `fabricctl status`, the Overview's relaxed settings and `fabricctl domain status` keep showing the
switch on, with who acknowledged its alert. The acknowledgement is kept with the switch in the domain (not on one
host), so the Enterprise Admin can acknowledge another host's with `--dc`, and any change of the switch drops it.

(`fabric's secrets readable (OpenBao unlocked)`) and the warnings still follow (1.7.1.4.7). Its test is in
`tests/openbao/local_admin.py` (doctor run against the sealed OpenBao's record: one failed check, then the warning).

## 2.3.7.2 Proposal: local admin passwords in OpenBao

The owner's request (2026-10-10, decision 2.1.7.6): OpenBao sets every managed machine's break-glass local admin
password and keeps it, with exports for a physical safe. Design: [1.7.1.3](../volume_1_description_and_architecture/1.7.1-openbao.md#1713-local-admin-passwords-set-and-escrowed-by-openbao).

2.3.7.2.1 **The tension it settles.** Two good practices pull apart: never reuse a password after it was used, and
keep break-glass credentials sealed and checked (most secure facilities audit the envelope, not a vault). A password
rotated after every use outdates its envelope; one kept for the envelope is reused. fabric does not pick for the site:
rotation is a policy, every export knows which password version it holds, and a stale envelope is shown, never
silent. Microsoft's LAPS settles it the same way (post-authentication reset, backup to AD).

2.3.7.2.2 **Why the machine sets its own password.** Pushing from fabric would mean fabric holding a way into every
machine (WinRM or SSH as an admin); pulling means each machine holds only the right to write its own entry. Network
gear cannot run fabric's task, so it is the one case fabric pushes, per device integration.

2.3.7.2.3 **Impact assessment** (additive: a new topic and new decisions; nothing built changes).

- *Architecture:* a new KV mount and policies in OpenBao; machine certificate auth (2.1.7.7); a task installed by the
  Windows and Linux joins; a host account and a two-step rotation on the fabric host; a Keycloak role
  (`local-admin:checkout`); a web console page and a `fabricctl local-admin` command; export code that prints and
  writes to USB. Every one is a new user-accessible entry point, so each gets positive and negative tests (Rule 9).
- *Breaking changes:* none for existing installs; machines joined before 0.9 get the task when their join runs again.
  The Linux join gains an account (`local-admin`, 2.1.7.11) and the host one (`local-admin`): host changes, so they
  go through setup's consent (`accounts`).
- *Scope creep risk:* moderate. Network gear depends on vendor integrations, of which only the lab's authenticator is
  testable on gaming-23's VMs (2.1.1.45); real vendors wait for hardware and are a blocker until then. Windows is
  testable on the 0.9 supplicant VMs.
- *Testing:* the Windows and Linux member sides on gaming-23's VMs; the host side in the sandbox and on the test Pi;
  exports by reading back what was written (the PDF's text, the archive decrypted with k shares, refused with k-1).

### 2.3.7.4.2 Vendor facts

- OpenBao's SSH secrets engine, checked against its API page (the repository's `website/content/docs/api/secret/ssh.mdx`,
  [openbao.org: SSH API](https://openbao.org/api-docs/secret/ssh/)): roles take `allow_host_certificates`,
  `allowed_domains` ("If this option is explicitly set to `*`, then credentials can be created for any domain"),
  `allow_subdomains`, `allow_bare_domains`; `sign/<role>` takes `cert_type` (`user` or `host`) and
  `valid_principals` (comma-separated). One mount holds one CA key (`config/ca`), so the host CA is a second mount.
- OpenSSH: `HostCertificate` (sshd_config(5)) may be given several times, each naming a certificate whose public key
  matches one of the host keys; `@cert-authority` lines in `ssh_known_hosts` with host patterns, negation with `!`
  (a name matching a negated pattern is not accepted by that line), ssh(1) and sshd(8)'s known-hosts format;
  `ssh-keygen -L` shows a certificate's type, signing CA, principals and validity. The certificate format is
  OpenSSH's PROTOCOL.certkeys (read by `vault/ssh/parse_ssh_cert`, checked against `ssh-keygen`'s own certificates in
  `ssh_host_test.py`).
- OpenSSH revocation, checked against [sshd(8)](https://man.openbsd.org/sshd.8) (SSH_KNOWN_HOSTS FILE FORMAT: the
  marker `@revoked` "indicate[s] that the key contained on the line is revoked and must not ever be accepted"; its
  example `@revoked * ssh-rsa …`) and [ssh_config(5)](https://man.openbsd.org/ssh_config.5) (`RevokedHostKeys`: a
  text file of keys or a KRL, the only way to revoke by certificate serial; a missing file refuses every host, one
  more reason not to use it). fabric uses `@revoked` with the certified host key.
- AD: an inherited object access entry `(OA;CIIO;WP;<attribute>;<class>;PS)` grants SELF write on one attribute of
  objects of one class; auxiliary classes are added to an object's `objectClass` (as `fabricSiteInfo` already is).
  Whether Samba honours the inherited SELF entry for a machine's own Kerberos bind is what the `samba` suite proves.

### 2.3.7.4.3 Choices made while building

- **How the machine's write meets `dev/0.9.0-rodccache`:** that branch makes `directory/run_op` the one routing
  point: every operation not in its `READS` goes to `samba/writable_server`'s DC. Here the signing run passes that
  same server itself for its writes (`prepare_ssh_hosts`, `set_ssh_host`) and reads `list_ssh_hosts` locally, so the
  two agree; once merged, `list_ssh_hosts` belongs in `READS` (else it is read at the writable DC: correct, only not
  local), and the explicit server here becomes redundant but harmless (run_op routes only when it is given none). The
  machine cannot use run_op (it is not on the fabric host), so the join script writes the same DC's name into
  `managed.env`; a DC's address alone would not do, since the machine's write is signed with Kerberos.
- **Revocation by key, not serial:** `@revoked` takes a key; a KRL (`RevokedHostKeys`) could revoke one certificate
  by serial and keep the plain key, but it is a binary file each client must be configured for. A machine taken out
  of management keeps its key, so managed clients refuse it until the old certificate's end (at most 30 days), then
  ask on first use as for any unknown host.

Recorded as decision 2.1.7.13. Also:
- **Robustness over speed:** a new machine's certificate takes up to two timer runs (publish, then sign); nothing is
  pushed to machines, so a machine that is down simply catches up.
- **Renewal margin:** 30-day certificates renewed with 10 days left, so the fabric host may be down for 20 days before
  any certificate lapses; a lapse falls back to the plain host key, never locks anyone out.
- **The fabric host's own certificate needs no round trip:** it is signed from its account's keys (which the timer
  writes as the site's agent), applied only while the host is a managed member: the `member` step's plan names it, so
  it is consented with the rest of the host's management.
- **Each machine checks what it takes from AD** (`ssh-keygen -L`: host certificate, the CA it fetched over HTTPS,
  its own key and name, valid), so a value an admin writes by mistake never reaches sshd.

### 2.3.7.5.2 Vendor facts

- OpenSSH `sshd_config(5)` (man.openbsd.org/sshd_config, read 2026-10-13): `AuthorizedPrincipalsCommand` takes the
  tokens `%u` (the user name) and `%F` (the CA key's fingerprint), among others, and "must be owned by root, not
  writable by group or others and specified by an absolute path"; `AuthorizedPrincipalsFile` takes tokens in its
  path only and lists literal principals, one per line (so a machine cannot hold one for every domain account);
  without either, the user name must appear among the certificate's principals; `TrustedUserCAKeys` holds several
  keys, one per line.
- Microsoft, *UserAccountControl property flags* (learn.microsoft.com/en-us/troubleshoot/windows-server/active-
  directory/useraccountcontrol-manipulate-account-properties, read 2026-10-13): `SERVER_TRUST_ACCOUNT` 0x2000 (a
  domain controller), `PARTIAL_SECRETS_ACCOUNT` 0x04000000 (a read-only domain controller). That Samba sets these on
  its DCs' accounts as Windows does is from its join code as remembered, not re-read: the `samba` suite's
  `read_site_dcs` case shows it.

### 2.3.7.5.3 Choices made while building

1. **The gate on the machine is the log-on GPO, not `AllowGroups`:** 2.1.6.53 made the OU's log-on policy the one
   gate; a second gate would refuse people the policy shows as allowed and would catch local (break-glass) accounts.
2. **The principal is `<user>@<site>`**, never the bare user name, so a certificate never works at a site whose
   group its holder is not in, and a machine that only trusts the CA (no principals check) cannot be entered as any
   account by it.
3. **The command form** of the principals check (`AuthorizedPrincipalsCommand`), since the file form cannot list
   principals per domain account (2.3.7.5.2).

### 2.3.7.5.5 Remote access by machine class, as built (0.9)

Built 2026-10-13 on `dev/0.9.0-promote` from the owner's answer to 2.3.7.5.4 point 1 ("layered. Also Linux vs Windows
is less important than desktop OS vs server") and the coordinator's brief; design 1.6.11.15, decisions 2.1.7.14
(second revision) and 2.1.6.36 (revision).

1. **Class OUs, not a class attribute.** A class attribute would need a schema attribute (or an existing one reused)
   and a WMI or security filter on each GPO to aim at it; Linux members' sssd applies GPOs by OU link and does not
   evaluate WMI filters. Class OUs need one GPO link per class, cover both operating systems, and show an admin the
   class where the machine sits. The class is the outer OU so that one link covers `OU=linux` and `OU=windows`
   below it.
2. **User rights do not merge.** The GPO nearest the machine that sets a right wins (Microsoft Learn, "Allow log on
   through Remote Desktop Services": local, site, domain, then OU, each overwriting), so a class GPO that set only
   its class group would take the right away from everyone the policy above names. The class GPO repeats the
   nearest policy above (the setting's `machines`, else the site's OU's, else the legacy groups) and adds its class
   group; at the keyboard it repeats that policy, or leaves the right unset when no policy above names it
   (`logon_rights_policy(None, …)`). The legacy groups are kept in the class GPOs while `logon_policies` is null, so
   an upgrade locks nobody out.
3. **RDP needs more than the right.** Microsoft's page: an RDP user must also be in the machine's Remote Desktop
   Users or Administrators. The class GPO puts its class group in each machine's own Remote Desktop Users (Restricted
   Groups "member of", as it already does for windows-admins and Administrators). The other OUs' remote groups are
   not put there (unchanged from before; a later decision if wanted).
4. **SSH through sssd.** sssd-ad(5): `ad_gpo_map_remote_interactive` lists the PAM services judged by
   "RemoteInteractiveLogonRight and DenyRemoteInteractiveLogonRight"; its default is `sshd` and `cockpit`. The join
   sets `ad_gpo_access_control = enforcing`.
5. **The class at a Linux join.** A desktop session file (`/usr/share/xsessions`, `/usr/share/wayland-sessions`)
   means a desktop. systemd's default target was rejected: `graphical.target` is systemd's own default, so servers
   report it too.
6. **The machine's class on the machine.** `fabric-managed` reads the account's DN as the machine each run into
   `/etc/fabric/machine-class`, so `fabricctl domain machine class` reaches SSH within the hour with nothing re-run
   on the machine; the principals command reads it at each sign-in and answers nothing for an unknown class.
7. **Granted from above.** Both groups are listed in `site_roles.REMOTE_ROLES`; `dev/0.9.0-roles` (09180f07) denies
   a branch's own agent any write on its grantable role groups and lets a site above grant, revoke and remake them.
   At integration: `grantable()` adds `+ list(REMOTE_ROLES)`; `role_groups.make_group` takes their description from
   `REMOTE_ROLES` and nests `remote_defaults(samdb, target, cls)`; `narrow_site_admins` leaves them alone (it touches
   only the AD roles and the host admins, so the desktop group's default `<site>-admins` stays).
8. **Tests.** Pure, run 2026-10-13: `tests/samba/class_logon_test.py` (94 checks), `tests/openbao/ssh_sites_test.py`,
   `tests/render.py`. Written, not run (the owner's direction of 2026-10-12): `tests/samba/logon.py`, `devices.py`,
   `dc.py`, `linux_join.py`, and `tests/openbao/ssh_ca.py`.

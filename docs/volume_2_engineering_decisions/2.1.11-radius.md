## 2.1.11.2 How FreeRADIUS decides

- **Decision:** fabric's own policy (python3 module) asks 389-DS on every request, as the read-only `cn=radius_reader`, over verified LDAPS: nothing is cached or exported, so a disabled device or an unlinked certificate is refused at its next authentication. EAP-TLS devices are found by the SHA-256 fingerprint of the presented certificate (recorded during verification, keyed by serial, since FreeRADIUS exposes no fingerprint); MAB by MAC. People (EAP-TTLS/PAP) are checked by binding as the person, then by membership of a mapped group (`radius_people`). The directory unreachable means Reject (fail closed).
- **Shapes:** 1.11, 1.6
- **Made:** 2026-09-27 to 2026-10-01, while fabric was designed, by the owner.
- **Why:** a change in the directory takes effect at the next authentication, with nothing to sync.
- **Status:** In force, revised by the move to Samba AD (2.1.6.6): the same policy asks AD (2.3.6.1.16).

## 2.1.11.3 Which domain machines PEAP admits, and on what VLAN

- **Decision:** The `radius_people` group mappings, as for people: an enabled computer in the site's `OU=machines` is admitted when one of its groups (e.g. Domain Computers, or one the admin makes) is mapped, on that mapping's VLAN; no mapping, no machine access.
- **Shapes:** 1.11, 1.6
- **Made:** 2026-10-05, by the owner (S3.3).
- **Why:** [2.3.6.1.16](2.3.6-identity-notes.md#236116-s3-freeradius-on-ad).
- **Status:** In force.

## 2.1.11.4 The Windows setup scripts: checked on PowerShell 5.1 now, tested on real hardware later

- **Decision:** for 0.9.2 the two scripts `windows_setup_script` generates (`tls`, `ttls`; the console's setup guides, the only
  part that reaches a PC) are checked on Windows PowerShell 5.1 on a lab Windows VM, for syntax and import only: the version
  really is 5.1, both parse, every command resolves and its modules load (3.1.5.12). They are not run. The full 802.1X test
  is deferred to real hardware, a recorded blocker (2.3.11.5). The script header's "untested on Windows ... until the hardware
  test" stays, because it stays true: a script parsed is not a script run.
- **Shapes:** 1.11, 3.1 (3.1.2.7, 3.1.5.12)
- **Made:** 2026-11-06, by the owner (relayed by the coordinator): real hardware "will be available later".
- **Why:** Windows' own PowerShell is what a PC runs these with, and no test has ever had it read them. The check catches what
  it can without touching a store, a service or the network; it does not show that 802.1X works.
- **Status:** In force from 2026-11-06.

## 2.1.11.5 The Windows setup scripts stop when `netsh lan` fails

- **Decision:** the generated scripts check `$LASTEXITCODE` after `netsh lan add profile` and after `netsh lan reconnect`. A failure
  stops the script with an error naming the step and the exit code, and "Done." is never printed. The temporary profile file is
  removed whether the add worked or not.
- **Shapes:** 1.11, 1.17.20; 3.1.5.12's check also runs these two failure paths
- **Made:** 2026-11-07, by the owner (relayed by the coordinator), for 0.9.2, before the Pi tests.
- **Why:** `$ErrorActionPreference = "Stop"` does not cover a native command, so a refused profile printed "Done." on a PC whose
  port would never open (read in the script, 2.3.11.5). That is the wrong answer at the moment a person is deciding whether it worked.
- **Status:** In force from 2026-11-07. Adds to 2.1.11.4; the header's "untested on Windows" stays: a script still not run whole. Failure paths run on 5.1: 2.3.11.5.

## 2.1.11.6 A device role names the address plan's VLAN, information first; unknown devices go to guest

- **Decision:** a groundwork before 0.11.0's 802.1X (1.11.1.2): a device role's VLAN is shown against the site's address
  plan (its name and subnets, or not in the plan), and a site's plan can mark one guest VLAN. Information only: nothing
  is refused and FreeRADIUS's answers do not change. Unknown devices will go to the guest VLAN with no access to any
  network resource. 1.11.1.2's six needed features are each a design review when 802.1X work continues.
- **Shapes:** 1.11 (1.11.1.2); 1.10 (1.10.4: the guest VLAN mark).
- **Made:** 2026-11-23, by the owner, asked whether roles should name the plan's VLANs: "All we need now is to build a
  very basic shell so that way it's a easier migration to the later versions of 802.1x handling, but for now it can
  just be information. Be sure to capture this as needed features and potential design reviews"; for unknown devices,
  "it will be put on guest, with no access to any network resources".
- **Why:** the plan tracks VLANs so that 802.1X can place and authorize by them ("if something is authorized in
  servers... it should not connect elsewhere"); a role's VLAN today is only a number, 1 to 4094, tied to nothing.
- **Status:** In force from 2026-11-23; to build after the 0.10.x patches (2.1.1.108). The needed features wait for
  0.11.0.

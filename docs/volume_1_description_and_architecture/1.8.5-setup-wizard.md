## 1.8.5.2 What the wizard changes, and what stays on the host's console

Setup's choices fall in two sets (2.1.8.7). The wizard's set is one list in the code, `settings/constants.py`
`WIZARD_KEYS`; everything else is console-only.

**The wizard** (the web console, and the settings file):

| Setting | Keys | Notes |
|---|---|---|
| Optional parts | `dns_filter` (`bind`/`none`), `install_fluentbit` and `log_forwarding` | DHCP (`install_kea`, with the first subnet's questions: `dhcp`) joins with the address manager in 0.9.0, 802.1X's switch (`install_freeradius`) with 0.10.0 (2.1.1.58); until then they stay setup's |
| Memory fabric may use | `host_ram_capacity` | Checked against the memory plan before anything changes (1.2.4.2) |
| Passwords and sign-in | `ad_password_policy`, `signin_kerberos`, `logon_policies` | The same checks as their own pages |
| The DNS filter's upstreams | `dns_filter_upstreams` | |

**Console-only** (`sudo fabricctl setup`, the vars editor, or `fabricctl security`), never from the web and never
from a settings file:

| What | Why |
|---|---|
| The permanent identity: `domain`, `ad_domain`, `dc_name`, `friendly_name`, the CA (`cert_*`, `stepca_*`, its lifetime) and every `IMMUTABLE_KEYS` entry | Cannot change once made |
| The network and the host's name: `host_ip`, `lan_cidr`, `lan_gateway`, `hostname`, `fabric_subnet` | A mistake cuts the console off from the host (owner 2026-10-14) |
| The first admin (`webui_admin_user`) | Chosen once by setup |
| Every host change (1.2.9: the ports, securing the host, its own rules, Docker's hardening, trust, time, the resolver, domain membership) | Changes the host's operating system; asked on its console (1.2.9.4) |
| OpenBao's unlock and recovery | The keys to everything |
| Lowering sign-in security (`fabricctl security lower`) | Kept where 2.1.6.24 put it |
| Client certificates (`fabricctl client-cert`) | Kept where it is |
| Every secret: passwords, keys, TSIG secrets | A settings file holds none |

## 1.8.5.3 The wizard in the web console

- **Where:** *Settings* in the console's navigation; after a fresh install the first admin's first sign-in opens it,
  with *Finish setting up* on the Overview until it has been applied once or dismissed.
- **Steps:** Optional parts; Memory; Passwords and sign-in; the DNS filter's upstreams; Review. Each step shows the
  current value, what it means and what changes; Back and Next keep what was typed; nothing changes before Review.
- **Reconfigure:** the same wizard later, every step filled in with today's values.
- **Read only:** the console-only settings are shown on the first step with their value and the command that changes
  them, never as a field.

## 1.8.5.4 The settings file: export and import, in the console and with fabricctl

One file format, two ways to use it (owner 2026-10-14): the wizard's *Export* and *Import*, and
`sudo fabricctl settings export [FILE]` / `sudo fabricctl settings import FILE [--yes]` for a host without a browser.

```yaml
fabric_settings: 1                  # the format's version
exported: "2026-10-14T18:02:11+00:00"
from: {site: pi-core, version: 0.8.0}
settings:
  dns_filter: bind
  host_ram_capacity: 4
  ad_password_policy: {minimum_length: 14, complexity: true, history: 24}
  signin_kerberos: false
  # …every key of WIZARD_KEYS, and nothing else
```

- **Export** writes every wizard key's current value, and nothing else: no console-only setting, no secret.
- **Import** takes the wizard's keys and ignores the rest, listing what it ignored and why: *console only*, *a secret*
  or *not a setting* (owner 2026-10-14: "certain fields will be ignored, such as passwords"). A wizard key whose value
  is invalid refuses the whole file, naming the key and the reason, and changes nothing. A file without
  `fabric_settings: 1` is refused.
- An imported file goes to the same plan as the wizard (1.8.5.5); with `--yes` the command applies it without asking.

## 1.8.5.5 One plan, one apply

The wizard, an import in the console and `fabricctl settings import` all end the same way:

1. **The plan:** each changed key with its old and new value, the memory plan when parts or memory change, the parts
   started or stopped, and anything ignored. Nothing has changed yet.
2. **Apply:** one apply job (as the Overview's Apply, 1.8.4.2), its progress on its job page; audited as
   `SETTINGS_CHANGE` with who, from where (web, file or cli) and the keys changed.
3. A plan whose settings no longer match what is installed (someone else applied first) is refused at Apply and
   shown again.

## 1.8.5.6 Who may use it

- A new permission, `settings:admin`, in the console admin's bundle (`fabric-console-admin`); the agent enforces it
  (default deny, 1.6.8).
- Like raising sign-in security (1.8.2), Apply needs a sign-in from the last 5 minutes; an older one is sent to sign
  in again first.
- Export needs `settings:admin` too: the file says how the site is built.

## 1.8.5.7 Setup on the host

- **Guided** keeps asking only what setup cannot do without (the console-only set above); the wizard's settings take
  their defaults, and setup's last words add a step: *finish setting up in the console's Settings*.
- **Advanced** keeps every item it has, so a host set up from its console alone needs no browser.
- `sudo fabricctl setup --file` still takes any setting, the wizard's included: an unattended install sets everything
  at once.

## 1.8.5.8 Build

- `src/fabriclib/settings/`: `constants.py` (`WIZARD_KEYS`, `FORMAT`), `read_settings.py`, `export_settings.py`,
  `parse_settings_file.py` (the ignored list, the refusals), `plan_settings.py` (the plan, using setup's own checks:
  `valid_setting`, the memory plan, the password policy's and log-on policies' validators), `apply_settings.py`
  (writes the vars and runs the apply job).
- The agent: `GET /v1/settings`, `GET /v1/settings/export`, `POST /v1/settings/plan` (the wizard's values or a file),
  `POST /v1/settings/apply` (a plan's id), each `settings:admin`.
- `fabricctl settings export|import`: the CLI's route to the same module.
- The web console: the wizard's pages, *Finish setting up* on the Overview, Export and Import.

## 1.8.5.9 Tests

- Pure (`tests/settings/`): the file round trip (export, import, the same settings); ignored keys listed by reason;
  every wizard key refused with its reason when invalid, the file unchanged; the plan's changes and memory plan.
- The agent and the web: each route allowed with `settings:admin` and refused without it, Apply refused with a stale
  sign-in and a stale plan; the wizard's pages, its import and export (the `webui` suite).
- The CLI: `fabricctl settings` export and import, positive and negative (the entry-point inventory).
- The sandbox: a wizard change applied end to end (a part turned on, the memory changed), and an imported file.

## 1.8.5.10 As built

Built 2026-10-14 for 0.8.0. What the design above left open, chosen the way the code around it already works:

- **The settings.** On 0.8.0 DHCP is not the wizard's (2.1.1.58): `install_kea` and `dhcp` in a settings file are
  ignored as console only, and the wizard has no DHCP field; they join it with the address manager in 0.9.0 (built
  on `dev/0.9.0-dhcp`, where `dhcp` is DHCP's first subnet as `fabricctl dhcp on` asks it). `log_forwarding` is the wizard's except the parts that name
  something on the host — a destination's `ca_file` (a file the apply copies) and `hosts` (names the host resolves):
  a file holding them is refused, an export leaves them out, and an apply keeps them as they are. `ad_password_policy`
  may be partial: it is laid over today's policy, then checked whole. The wizard's one line for the logs takes a
  syslog server or an Elasticsearch URL as setup asks it; where the logs go to both, that line is not offered (a
  file changes them).
- **One check, setup's.** Each value goes through the check its own page or setup uses: `check_password_policy`,
  `check_logon_policies`, `check_filter_settings` (the upstreams), `plan_memory` (the parts that run must fit the
  memory), `parse_log_target` (split out of setup's question) and `parse_upstreams` (split out of the
  DNS filter tab's). Log forwarding turned on needs a destination.
- **The plan and its Apply.** `POST /v1/settings/plan` keeps the plan in fabric-agent's memory (`agent/plan_store`)
  for 15 minutes, for the person who made it; `POST /v1/settings/apply` takes it once. A plan whose settings no longer
  match (someone applied first) is refused at Apply and answered with the plan made again from the same values,
  which the console shows; the apply checks again under the settings' lock. The apply job writes the changed keys,
  audits `SETTINGS_CHANGE` (`from web`, `from file` or `from cli`, and the keys), then runs one apply — with fabric's
  Keycloak configuration when Kerberos sign-in changed (as the Security page does).
- **Finished.** Applied once or dismissed is recorded beside the settings (`config/settings-wizard.json`, the first
  record kept); a dismissal is audited `SETTINGS_DISMISS` through a fifth route, `POST /v1/settings/dismiss`
  (`settings:admin`). Until then the first Overview of each sign-in of someone with `settings:admin` opens the
  wizard (once per sign-in), and the Overview shows *Finish setting up* with Dismiss.
- **The steps without script.** Each step is a form; the other steps' fields travel hidden, so Back and Next keep
  what was typed (the strict CSP holds). Review lists what differs from today; *Make the plan* asks the agent.
- **Apply's recent sign-in** is the web console's check, as for the Security page and OpenBao's changes; the wizard
  says up front when the sign-in is older than 5 minutes.
- **Setup's last words** add the step after Guided setup only, and only while the wizard is not finished.
- **Tests** (1.8.5.9): the model, the CLI, the agent's routes and the console's pages run with no container in the
  `settings` suite, and the dev preview's pages in the `webui` suite.

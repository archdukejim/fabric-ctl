## 1.8.7.1 Status

**Designed 2026-10-30, to build after the feature freeze (2.1.1.70)**; decision 2.1.8.32, its name 2.1.8.33
(**Open**). Nothing of it is built. Placed in the roadmap's *Not yet placed* (1.1.4.4) until the owner gives it a
release.

## 1.8.7.2 What it is for

The owner, 2026-10-30: "the ability to add cockpit play nice, if they want or are using cockpit for their device, that
we ensure that it's behind the webserver so it can get a certificate and easy url". A device that runs Cockpit (the
fabric server itself, or any other machine of the domain) is reached through fabric's nginx at a name of fabric's DNS,
with a certificate from fabric's CA, instead of `https://<address>:9090` and Cockpit's self-signed certificate.

fabric does not install, package, update or manage Cockpit (2.1.1.23, 1.2.9.2 still hold): it adds one nginx server
and one DNS name per device that asks, and says which of Cockpit's own settings the device needs (1.8.7.6). A device
without Cockpit is not touched.

## 1.8.7.3 Shape: one nginx server per device that asks

```
browser ──TLS──> nginx (fabric) ──TLS, verified──> Cockpit on the device (:9090)
        <name>.<domain>          proxy_ssl_verify on,      cockpit-ws, its certificate from fabric's CA
        fabric's certificate     proxy_ssl_name <device's own name>
```

- **Opt-in, per device.** A setting lists the devices whose Cockpit fabric proxies (`cockpit_proxies`, each
  `{host, port}`; `port` default 9090; empty by default). How a device is put on the list (a `fabricctl` command, the
  console's device page, the join script) is settled before building (1.8.7.11).
- **One nginx `server` per entry**, rendered by `templates/nginx/nginx.conf.j2` beside the console's, at the entry's
  name (1.8.7.4), listening on 443 only (port 80 sends to HTTPS, as for fabric's other names).
- **WebSocket proxying.** Cockpit's whole session runs over one WebSocket (`/cockpit/socket`): the server sets
  `proxy_http_version 1.1`, `Upgrade $http_upgrade`, `Connection "upgrade"`, `Host $host`, `X-Forwarded-Proto https`,
  and a read timeout long enough for an idle session (Cockpit's own idle logout ends it, not nginx).
- **DNS.** For a name that is not the device's own (1.8.7.4), fabric adds a CNAME to the fabric host in the site's
  zone; the name is one of fabric's claims, checked for collisions with the admin's own records (1.2.13).
- **Where nginx reaches the device.** For another device: its own name in the domain (`<hostname>.<domain>`, its A
  record) on the entry's port. For the fabric server itself: the host's address from the nginx container
  (`host_ip`), which needs a firewall allowance from `fabric_net` to the host's port 9090 (1.8.7.9); Cockpit's port
  then need not be open to the LAN at all.

## 1.8.7.4 The name

The name a device's Cockpit is reached at is **Open** (2.1.8.33). The constraints any choice must meet:

- `<hostname>.<domain>` of a device other than the fabric server is that device's own A record: ssh, its own
  services and Kerberos reach the device there. Pointing it at fabric's nginx would break the device's name, so
  another device's Cockpit always needs a name of its own: `<hostname>-cockpit.<domain>`.
- On the fabric server, `<hostname>.<domain>` already points at fabric's nginx. Today it serves the landing page
  (1.4.2.6, decision 2.1.4.8: the host's own name is the first of `landing_names`), and it is the console's name when
  `webui_hostname` (or `cname_mgr`) makes `hostname_mgr` equal to it (1.2.12: the CNAME is only skipped then). The
  host's Cockpit can take that name only when the console does not use it, and only by moving the landing page off
  it (the landing page stays at `<domain>` and the admin's aliases).
- The options, with their costs, are in 2.1.8.33.

## 1.8.7.5 Certificates on both sides

- **Browser side:** fabric's nginx presents a certificate from fabric's CA for the entry's name, issued and renewed
  as fabric's other service certificates are (1.5), so a domain device trusts it with no warning.
- **Device side:** nginx verifies Cockpit's certificate (`proxy_ssl_verify on`, fabric's root as the trust,
  `proxy_ssl_name` the device's own name); verification is never turned off (global Rule 10). The device's Cockpit
  therefore serves a certificate from fabric's CA for its own name, placed in `/etc/cockpit/ws-certs.d/` (Cockpit
  uses the last file there by name). A domain device gets it by ACME with `pki:acme` (4.8.2.1), or by the join
  script (1.6.7); the fabric server's own Cockpit gets one minted by setup. A device whose Cockpit still serves its
  self-signed certificate is shown as not reachable, saying why, never proxied unverified.

## 1.8.7.6 Cockpit's own settings: Origins and the forwarded protocol

Cockpit refuses a WebSocket whose `Origin` it does not know, so behind a proxy at another name every session fails
until `/etc/cockpit/cockpit.conf` on the device allows it:

```ini
[WebService]
Origins = https://<the proxied name> wss://<the proxied name>
ProtocolHeader = X-Forwarded-Proto
```

`Origins` lists the proxied name (and may keep the device's own `https://<hostname>.<domain>:9090` for direct use);
`ProtocolHeader` makes Cockpit trust nginx's `X-Forwarded-Proto` for its secure-cookie choice. On a domain member the
join script writes these lines when the device is opted in (1.6.7); on any other machine they are a documented step
([3.8.1](../volume_3_installation/3.8.1-cockpit-proxy.md)). On the fabric server they are a host change fabric asks
for (1.8.7.9). Cockpit reads them when `cockpit.socket` next starts a session (`systemctl try-restart cockpit`).

## 1.8.7.7 Sign-in: Cockpit's own first, single sign-on later

- **First (the first build):** Cockpit's own login page through the proxy: the device's PAM decides (a local
  account, or a domain account on a member through SSSD). nginx adds no sign-in of its own, so nothing about
  Cockpit's sessions, sudo or its idle logout changes.
- **Later:** single sign-on from Keycloak. Cockpit takes no OIDC; its single sign-on is Kerberos (GSSAPI, an
  `HTTP/<name>` key in the device's keytab, the browser's Negotiate). How Keycloak's sign-in reaches it (Kerberos
  through the domain, or a sign-in gate at nginx in front of Cockpit's own login) is designed then, as its own
  decision; it is not part of the first build.

## 1.8.7.8 Security

- The proxy adds reach, not privilege: who may use a device's Cockpit is still the device's own PAM and sudo.
- Only the names on `cockpit_proxies` are served; a request for any other name gets nginx's default server.
- Off by default, per device; status (`fabricctl status`, the console's Overview) lists each proxied device.
- The fabric server's firewall allowance (1.8.7.9) is from `fabric_net` only, never the LAN.
- Optional, to settle (1.8.7.11): a client-certificate requirement at nginx for these servers, as the console's
  `webui_client_cert` (1.8.2).

## 1.8.7.9 What it changes outside fabric

On the fabric server, opting its own Cockpit in changes another application's configuration and the firewall, so it
is asked for first, as one grouped question, and recorded for uninstall to undo (1.2.9, global Rule 12): the lines of
1.8.7.6 in `/etc/cockpit/cockpit.conf`, the certificate file in `/etc/cockpit/ws-certs.d/`, and the allowance from
`fabric_net` to port 9090. On another device, fabric changes nothing by itself: the join script asks on that device,
or the person follows 3.8.1.

## 1.8.7.10 Tests

To write with the build (3.1.2): the rendered nginx server per entry (name, certificate, WebSocket headers,
`proxy_ssl_verify on`); a refused entry (a name that collides, a device not in the domain, a port out of range);
the CNAME added and removed with the entry; and, in the sandbox, a Cockpit container behind the proxy: a session
opens through the WebSocket with `Origins` set, and is refused without it; a self-signed backend is refused.

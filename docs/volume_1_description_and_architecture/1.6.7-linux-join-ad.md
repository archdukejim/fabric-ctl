## 1.6.7.2 What it replaces

| 1.6.6 | Here |
|---|---|
| Step 3: host groups and rules written into 389-DS for SSSD's LDAP provider | logon rights from each site's GPO (SSSD `ad_gpo_access_control`), host groups as AD groups for sudo rules |
| Step 3: sudo rules in 389-DS | `sudoRole` entries in AD (sudo's schema, 1.6.3.5) |
| Step 4: machine enrolment with a token | the AD join itself: a computer account in the site's `OU=machines` |
| Step 5: an MIT KDC on 389-DS | AD's Kerberos (every DC is a KDC) |
| G4: the CA over plain HTTP | the installer pins fabric's CA by fingerprint |

## 1.6.7.3 The installer

`https://certs.<domain>/join-linux.sh`, run as root on Ubuntu 24.04 or 26.04, or Debian 12 or 13 (so Proxmox VE 8
and 9; owner 2026-10-06, for 0.6.0), with the root-CA fingerprint shown on
`certs.<domain>` as an argument: it fetches the root CA, refuses it unless the fingerprint matches, trusts it, then
installs `adcli`, `sssd-ad`, `sssd-tools`, `libpam-sss`, `libnss-sss`, `libsss-sudo`, `krb5-user`, `ldap-utils`
and `libsasl2-modules-gssapi-mit`. The join:

- **Where the site sits** is read from the DC first (sites nest, 2.1.6.20): signed in with Kerberos as the account
  that joins (`kinit`, the password on stdin), an LDAP search finds the site's OU by its mark and name, and the
  organisation's OU. A site that is not there, or a wrong password, stops the installer before anything joins.
- `adcli join --domain=<ad-domain> --domain-ou=OU=machines,<the site's OU>` with the password on stdin: a
  site admin's, or a **one-time join password** for a computer account pre-created in the web UI
  (`machines:admin`), so no admin password is typed on the machine.
- The machine's site is the installer's own site, or any other with `--site <site>` (found the same way).

## 1.6.7.4 Identities, logons and sudo

> **Correction 2026-10-10:** SSH with GSSAPI is not configured by the join yet (1.6.11.6, 0.9); the site's sudo role
> moves to `<site>-fabric-admins` (1.6.11.3).

- SSSD's AD provider, `ldap_id_mapping = false`: fabric's own uid and gid numbers (Q9).
- `access_provider = ad`, `ad_gpo_access_control = enforcing`: who may log on is the site's logon GPO (1.6.3.10:
  the site's people, admins, break-glass and grants), proven in Q16.
- `sudo_provider = ad`: rules from `OU=sudoers` of the machine's site, of each site above it (a parent's roles
  reach the sites below, 2.1.9.13) and of the organisation, each searched one level deep (so a nested site's rules
  never reach its parent's machines); a rule names AD groups of people and of machines (host groups: AD groups
  of computer accounts, e.g. `lab-web-servers`). The search bases are written at the join: a site that is
  re-parented has its machines' installer run again (1.9.8.14).
- `kinit` and SSH with GSSAPI work after the join; `passwd` changes the password in AD.

## 1.6.7.5 Client basics

> **Correction 2026-10-10:** the join does not yet point resolved at fabric's DNS, nor configure SSH; both come
> with managed machines in 0.9 (1.6.11.6).

`enumerate = false`; credentials cached so logons keep working while the DC is away (`cache_credentials = true`,
bounded by the policy's offline days); time from `ntp.<domain>`; `systemd-resolved` pointed at the site's DNS;
home directories created at first logon (`pam_mkhomedir`). With Keycloak and Kerberos sign-in on (0.6.1, 2.1.6.28), the
browsers may use the logon's ticket for `sso.<domain>`: Firefox (`/etc/firefox/policies/policies.json`, merged into any
policies already there: `Authentication.SPNEGO`), Chromium and Chrome (`fabric-sso.json` in their managed policy
folders: `AuthServerAllowlist`); `krb5.conf` maps fabric's domain to the AD realm (`[domain_realm]`).

## 1.6.7.6 Machines in fabric

Joined machines are computer accounts in their site's OU: listed in the web UI's domain section with their host
groups, moved between host groups, disabled (logons and PEAP machine sign-in refused) and removed centrally.

## 1.6.7.7 Tests

Real Ubuntu (24.04, 26.04) and Debian (12, 13) containers join a test domain: `id` with fabric's ids, an SSH password login and
a GSSAPI login, sudo allowed for an admin and refused for others, a person of another site refused until granted,
the installer refusing a wrong fingerprint, logons with the DC stopped from the cache. On the test Pi too.

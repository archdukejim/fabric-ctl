## 1.8.8.1 Status and scope

**Scoped 2026-10-31 for 0.9.1** (decision 2.1.1.72), a release after 0.9.0, planned once 0.9.0 is released; not
built. Nothing here is built during 0.9.0 (the owner: "I want to push 0.9.0 more than working on these fixes"). The
owner's words: "there are two things that I see as first priority … (1) web page speed (it's slow), and these computed
groups... aren't really necessary … The way I'd prefer to view everything is kind of like how Active Directory Tools
(RSAT) works where every AD Object is just browsable in a tree format with OUs organizing it. Furthermore, our tool
does not flexibly place everything."

It builds on the console of 1.8.6 (the frame, the page pattern, Apply per page: all kept) and on the Directory's pages
of 1.6.12 (People, Groups, Computers and OUs become views of one tree; their detail pages are kept as the tree's
"open"). Before it is built, the questions of 1.8.8.7 are answered and recorded in 2.1.8 or 2.1.6 (global Rule 4):
Q1 to Q7 were answered on 2026-10-31 (2.1.8.35, 2.1.6.98 to 2.1.6.102, 2.1.8.37); Q8 to Q10, raised by the sizing
advice the owner added the same day (1.8.8.8, 2.1.8.36), are open.

## 1.8.8.2 Page speed: measure first, then move work off the request path

The owner: "web page speed (it's slow)". The DNS filter's tab showed the way (2.1.12.10, 2026-10-30): measured first,
the cause was work done on every request (reading BIND's query log), and moving it to a timer took the overview from
4.33 s to 0.09 s and a query-log view from 4.61 s to 0.18 s.

- **Where it is measured** (decision 2.1.8.35): on the test Pi with **5 people** and a handful of computers, the
  install the owner runs; scale is not the goal ("the resources should be proportionally increased"), and a host
  small for its install is told so by the sizing advice (1.8.8.8).
- **The goal:** "as fast as it can be" (the owner). Every navigation page and detail page is profiled, server time and
  full load, each run three times, and every avoidable cost found is removed. Each slow part gets its cause named (a
  fabric-agent call, an LDAP search, a whole-tree read, a `docker exec` or other subprocess, the template) before
  anything is changed. The table of results goes in the notes (2.3.8).
- **The method:** no work on the request path that a timer or a cache can do (a cache fabric-agent keeps and
  refreshes when a change it applies touches it); no `docker exec` per request where a held connection or a cached
  read works (LDAP, `rndc`, Kea's control socket, OpenBao's API); one LDAP search per page, not one per row; paging at
  the source (the directory's paged results); then the template.
- **The regression budget:** once the work is done, the suite enforces a budget so speed cannot slide back: each
  page's server time on the test Pi's 5-person install at most the slowest page's measured best plus a margin (a
  quarter, at least 50 ms). **The number is set after measurement** and recorded in 2.1.8.35 then; until it is, the
  suite records the times without failing.
- **Kept:** every page still works without script.

## 1.8.8.3 Computed groups hidden by default

The groups fabric-agent computes for grants (`grant-<name>-who`, `grant-<name>-where` and the machine sets'
`access-<n>`, 1.6.13.4) are fabric's internals: no one adds to them, and the owner finds them noise ("these computed
groups... aren't really necessary. Furthermore, I can search them").

- The Directory's lists, its tree and its search leave them out by default.
- One switch, **Show fabric's internal groups**, on the Groups view and the tree, shows them, marked "computed by
  fabric", each linking to the grant it serves. The switch is a query key (no script), kept while browsing.
- A grant's page keeps showing its two computed groups and who is in them (1.8.6.11.10); nothing about how grants are
  compiled changes.

## 1.8.8.4 The tree: every object browsable by OU

As Active Directory Users and Computers (RSAT) shows a domain:

- **The tree** down the left of the Directory's page: the domain, then its OUs and containers nested as they are,
  each expandable. fabric's fixed OUs are marked as fabric's (1.6.12.2); the computed groups' OU follows 1.8.8.3.
- **An OU's contents** on the right: every object in it (people, groups, computers, OUs, contacts and service
  accounts), each with its kind, state light and description, sorted by kind then name, paged, searchable within the
  OU or the whole domain.
- **Open** an object (click its name): its page as today (a person's, a group's, a computer's, 1.6.12), with the tree
  still showing where it is.
- **Without script:** expanding a node is a link that opens the tree to it (`?ou=<path>`), so the page works as the
  rest of the console does (1.8.6.2); script, where it runs, expands in place and keeps the scroll.
- **Speed:** one level is read at a time (the OU's children only, one-level LDAP searches), so a large domain opens as
  fast as a small one (1.8.8.2).
- **Kept:** the People, Groups, Computers and OUs entries stay in the navigation, as filtered views of the same
  objects; old addresses keep working (1.8.6.4).

## 1.8.8.5 Placement: any object in any OU, and what must follow it

The owner chose both (2026-10-31, option (c)):

- **(a) Move any person, machine or group into any OU**, by "Move to…" on its page or in the tree, or by dragging it
  in the tree (as in RSAT). A move is a pending change on the Directory's Apply (1.8.6.5), as every other change is.
- **(b) Admins create their own OUs anywhere** and put things in them; fabric's grants and policies **follow an
  object wherever it lands**.

Today fabric assumes its own layout (1.6.13.2): machines under `OU=machines` (by type), people under `OU=people`,
groups under `OU=groups`; the access GPOs and the default deny are linked at `OU=machines` (1.6.13.4, 2.1.6.84,
2.1.6.87); the Create OU form offers only places under fabric's OUs (1.6.12.7). What must change so everything follows
the object, each decided by the owner on 2026-10-31 (1.8.8.7):

| What | Today | Follows the object by |
|---|---|---|
| Grants (people, machines, sudo, sign-in rights) | by group membership (2.1.6.72: OUs grant nothing) | already follows; checked by test after a move |
| Sign-in and local administrator (fabric's access GPOs) | linked at `OU=machines`; a machine moved out of it loses them | linked at the domain's root, security-filtered as today (2.1.6.98) |
| The default deny (`fabric: access none`) | linked at `OU=machines`, first, unfiltered | linked at the domain's root, first, filtered off the Domain Controllers and the fabric host (2.1.6.98) |
| Site membership | the `site-<name>` group (1.6.12.8) | already follows |
| Sudo rules | `sudoRole`s naming `%grant-<name>-who` and the hosts of `-where` (1.6.13.4) | already follows |
| The machine's type (workstation, server, ...) | read from its OU | an attribute or a `type-<name>` group fabric writes; the type's OU is only where a new one goes (2.1.6.99) |
| "Managed by fabric" (what may not be moved or changed) | fabric's fixed OUs and objects (1.6.12.2) | fabric's own objects and fixed OUs stay put; everything else moves (2.1.6.100) |
| Where a new object is created | fabric's OU for its kind | fabric's OU for its kind by default, with "Create in…" any OU (2.1.6.101) |
| The Directory Administrators' and the grants' rights in AD's own ACLs (so RSAT works, 2.1.6.76) | set on fabric's OUs | fabric writes them on each OU, wherever it is made (2.1.6.102) |
| Moving by dragging | not offered | "Move to…" without script, dragging on top (2.1.8.37) |

## 1.8.8.6 The console's clean-up and its colours

The audit of 2026-10-31 (2.3.8.4) found the faults on the setup wizard's page and their one cause (every form is one
`.grid`), and the same kinds across the console (lone buttons in free grid cells, four button heights, faint field
edges, colours not themed in dark mode, manual numbers in what people read). 0.9.1 fixes them as 2.3.8.4.6 lists:

- **Forms** as sections and one actions row; **one button height**; **one notice shape**; headings inside their
  card; six type sizes; a focus ring; dates as people write them.
- **The colours:** the **Sandstone** palette, light and dark both, following the browser's setting (decision
  2.1.8.34): warm stone neutrals with a cobalt accent, every pair measured at WCAG 2.2 AA (2.3.8.4.5). Its tokens
  are `spikes/webui-palette/palettes.css`' `sandstone` blocks; the spike's `mockup.css` is the draft of the
  stylesheet. The other two candidates stay in the spike for reference.
- **Tests:** the wide-screen checks the audit ran join `tests/webui/test_narrow.py`'s narrow ones.

## 1.8.8.8 Sizing advice: alerts for administrators when the host is small for the install

Decision 2.1.8.36. The owner: "The scalability is less of a concern, as the resources should be proportionally
increased.... as such I want suggestions for how to improve performance added as web ui alerts to administrators....
e.g. you are at 1000 users, and currently on 8 GB of ram, which is 5.3 GB less than recommend for your user base".

- **What is compared:** the install's size (people, computers, groups, DNS zones and records, DHCP leases, the DNS
  filter's queries a day, sites) against the host's resources (RAM, CPU cores, free disk on fabric's data volume, and
  the containers' memory limits, 2.1.14's memory budget), through a **recommended-resources table**.
- **The sizing model:** each service's memory and CPU measured on the sandbox and the lab at a few sizes (for example
  5, 100, 1,000 and 5,000 people with proportionate computers, records and leases), fitted per service as a fixed part
  plus a part per object of the kind that drives it (a straight line), summed into a recommended and a minimum total
  per resource. The table, its fit and the sizes it was measured at are published in the manual (1.8.8's notes,
  2.3.8.5) and shipped as data with fabric-agent. **The numbers are to be measured**: 2.3.8.5 records it as a blocker.
- **The levels:** **warn** when a resource is below the recommended value for the install's size; **critical** when
  below the minimum. Each alert names the numbers and the gap, as the owner's example: "1,000 people on 8 GB RAM:
  5.3 GB below the recommended 13.3 GB for that size", and says what would close it (more RAM, a larger memory
  budget, fewer lists in the DNS filter).
- **Where it shows:** on the Overview's Health, a card of the alerts with the numbers behind them; and a banner at the
  top of every page for administrators while one is critical (who exactly: Q8). Each alert can be dismissed (for how
  long: Q9); a dismissal is the person's own and is audited.
- **Nothing leaves the host:** fabric-agent computes the sizes and the alerts on the host from its own reads (a timer,
  never on a page's request, 1.8.8.2); nothing is sent anywhere, and no telemetry is added.
- **Tests:** the model's arithmetic (unit tests against the published table); an alert at, just below and just above
  each threshold, for each resource; a person without the permission of Q8 never sees it (a negative case, global
  Rule 9); a dismissal kept and its return when the gap changes; the agent's route refused without the permission.

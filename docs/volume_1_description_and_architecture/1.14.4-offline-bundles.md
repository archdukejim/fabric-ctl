## 1.14.4.1 What a bundle holds

One file per fabric release and architecture (`amd64` or `arm64`, 2.1.1.11), an uncompressed tar:

| Member | What |
|---|---|
| `images/<name>.tar` | Each image of the lock (`config/images.lock.yaml`): the upstream ones under their own names, fabric's published ones as `fabric-<name>`. Each is an OCI image layout for the one architecture: the image's own index (whose digest is the one the lock pins), the platform manifest it lists, its config and layers |
| `signatures/fabric-<name>.json` | Each published image's Sigstore bundle (2.1.14.6): the signing certificate, the transparency log's entry and inclusion proof, and the signed statement naming the image's digest |
| `manifest.json` | Format 1: fabric's version, the architecture, when it was made, every image (ref, digest, its platform manifest, its file, its signature) and every other member's sha256 and size |

The index's other platform is named in it but not carried, so the bundle is about half what both would be. No
local registry (2.1.14.14): Docker loads the images directly.

## 1.14.4.2 Making one: `fabricctl images export`

`sudo fabricctl images export --arch amd64|arm64 -o <file>` on a machine with internet and Docker, with the package
of the release to bundle installed (set up or not: the launcher runs export and import from the package's code with
the package's lock, `src/ux/cli/fabricctl`). It writes `<file>.part` and renames it when whole; a failure removes it.

- Each image is fetched **from its registry by digest** (`images/bundle/fetch_image`), anonymously, every blob
  checked against its digest as it arrives, rather than by `docker save` as 2.1.14.14 first said: Docker's classic
  store recomputes manifests and loses the registry's digests, and `cosign save` carries both architectures and no
  new-format signatures (decision 2.1.14.20, 2.3.14.3).
- Each published image's signature comes from beside it in the registry (`cosign download signature`, the pinned
  cosign, 2.1.14.11) and must be a Sigstore bundle signing that digest.
- Refused before anything is written, saying why: an unknown architecture; a file that exists; an image of the lock
  not published (`pending`, with its reason), unless `--allow-unpublished` (1.14.4.9); an image with no
  linux/`<arch>`;
  less free space beside the file than the images plus the largest one again (it is added from beside the file).
  A registry that refuses, a blob that does not match, or no network stops it with the reason and the partial file
  removed.

## 1.14.4.3 What is checked before anything is loaded

`images/bundle/check_bundle`, without Docker, against the **package's** lock and VERSION (what setup deploys, not
the running install's):

1. The file is a whole tar with a `manifest.json` of format 1 (cut short, damaged headers or junk: refused as
   damaged).
2. It is for this fabric's version and this host's architecture (each refused naming both).
3. It carries every image the lock pins, each with the lock's digest; each published one with its signature.
   An image the lock has not published (pending) is not expected: the host builds it, which needs the internet.
4. Every member matches the manifest's sha256 and size (one changed byte is refused, naming the file).
5. Each image proves itself from its own bytes: the layout names the lock's digest, the index hashes to it, and the
   linux/`<arch>` manifest it lists, the config (of that architecture) and every layer hash to the digests that name
   them.

The manifest itself is not signed: its hashes catch damage, and the lock's digests (in the installed package) and
the signatures catch anything altered.

## 1.14.4.4 Importing a bundle

`sudo fabricctl images import <bundle>`, or setup's `bundle` step with `sudo fabricctl setup --offline <bundle>`
(3.3.3), does, in order, and stops at the first refusal with its reason:

1. Docker must use the containerd image store (1.14.4.5).
2. The package must ship the trusted root (1.14.4.6), unless `image_signature_check: false`.
3. Everything of 1.14.4.3.
4. Room in the store (`/var/lib/containerd`): three times the images not yet loaded (their compressed content is
   kept and their layers unpacked); needed and free are named.
5. Signatures, offline: cosign is loaded first (its bytes are already proven to be the lock's), then each published
   image's carried signature is checked with `cosign verify-blob-attestation` run with **no network**: the bundle
   must sign that image's index, by a certificate naming fabric's images workflow (the lock's `signer` and `issuer`,
   2.1.14.6) and logged in Sigstore's transparency log, all proven from the shipped trusted root. With
   `image_signature_check: false` this is skipped and said so (the relaxation of 2.1.14.10).
6. The other images are streamed into `docker load`; one already in Docker by its digest is not loaded again (a
   second import loads nothing).
7. Each image must then be known to Docker by its pinned ref; the verified digests are remembered in
   `/etc/fabric/images/verified.json` (0600, 1.14.3.4), so setup's online signature check is satisfied for them.

Nothing is fetched. After it, nothing pulls a pinned image that is present: the deploy pulls with
`--policy missing` and `images update` pulls only an image Docker does not have (a digest never changes). A service
the host must build itself (an image not published, or other ids, 2.1.14.5) still needs the internet; the bundle
cannot help it.

## 1.14.4.5 Docker's image store

Only Docker's **containerd image store** keeps an image's index when it is loaded, so `repo:tag@digest`, as every
compose file names a pinned image, resolves offline. The classic store (`overlay2` graph driver) loads the same
image but forgets the digest, and compose would then try to pull it. Docker 29, which Ubuntu 24.04's `docker.io`
is (29.1.3 in 2026-10), uses the containerd store on a new install; a host whose Docker was installed before keeps
the classic store. The import **refuses a classic-store host** with the reason (decision 2.1.14.19); moving a host
to the containerd store is 3.14.2.3.

## 1.14.4.6 The trusted root the package ships

The offline check needs Sigstore's trusted root (its certificate authority's and transparency log's keys). It
ships **in the package**, `config/sigstore-trusted-root.json` (on a host `/usr/lib/fabricctl/fabric/`, beside the
lock), not in the bundle, so a bundle cannot bring its own (decision 2.1.14.18). `scripts/images/trusted_root.py`
writes it from Sigstore's TUF repository through the pinned cosign (which verifies it from the TUF root it ships
with); it changes only by a reviewed commit, like the cosign pin, and the images suite fails when it is no longer
Sigstore's current one (`--check`). A trusted root records its keys' validity, so a newer one still checks the
signatures of older releases.

## 1.14.4.7 Decided, not built yet

The owner, 2026-10-22, for 0.13.0:

- **The Ubuntu packages fabric installs** (2.1.14.16): the bundle carries them for one Ubuntu release, chosen with
  `--ubuntu <release>` (default: the exporting machine's), recorded in the manifest and refused on another; the
  offline host installs them from a **local, file-based apt source** made from the bundle, not by `dpkg` on loose
  files, so apt resolves what that host lacks.
- **fabric's `.deb`** (2.1.14.17): the GitHub Release asset of the lock's version, checked against the hash the
  signed apt repository publishes for it.
- **An unpublished image** (2.1.14.21): built, see 1.14.4.9.
- **The DNS filter's lists** (2.1.14.22): carried later; today a deploy fetches a missing list from the internet.

Until then, `setup --offline` needs the host's packages (and `fabricctl` with its dependencies) already installed,
as before.

## 1.14.4.8 Tests

- `tests/images/bundle.py` (the `images` suite, online): export of a small lock (cosign, nginx, fabric's bind9)
  and its manifest; the bundle checking as a whole; the carried signature verifying offline, and refused for another
  signer or another image; export refused for an unknown architecture, an existing file, a pending image (the
  repository's own lock) and too little space; check refused for another version or architecture, a missing image,
  another digest, a file cut short, a changed byte, junk; import refused without a shipped trusted root and without
  room; the shipped trusted root current; the command's usage errors.
- `tests/images/offline.sh` (run alone, about 25 minutes): a systemd + Docker box on a network with no route out,
  the package installed with `dpkg`, the import refused on the classic store, for a missing file and without room,
  then imported (signatures verified offline, every image known by its digest, a second import loading nothing),
  `setup --offline` refused for a missing bundle and then installing fabric with nothing pulled, doctor passing.

## 1.14.4.9 Leaving unpublished images out: `--allow-unpublished`

Decision 2.1.14.21 (the owner, 2026-10-22: "overrideable, if they want to attempt the setup that's on them, but they
may also have a security concern"). A lock with an image not published (`pending`) is refused by default (1.14.4.2).
`sudo fabricctl images export --arch <arch> -o <file> --allow-unpublished` exports anyway:

- the images not published are **left out** and named in the manifest's `left_out`, each with its `pending` reason;
- the import checks the rest as always (1.14.4.3; the host's lock does not expect a pending image either) and says,
  on a line beginning `relaxed:`, which images were left out and that the host must build them, which needs the
  internet (a host building them offline fails at that build, saying so);
- it is a relaxation (global Rule 10): the import records it in `/etc/fabric/images/bundle.json` (root, 0600), and
  `fabricctl status` and doctor list "offline bundle exported with --allow-unpublished" among the relaxed settings
  (`system/relaxed_settings`, 1.2.8.2) until a whole bundle is imported, which removes the record. The web UI's
  Overview reads the same list through fabric-agent, which cannot read root's record, so it does not show it.

Tested in `tests/images/bundle.py` (refused by default, left out and recorded with the flag, the `relaxed:` line,
the relaxed-settings row) and `tests/images/offline.sh` (the repository's own lock exported with the flag).

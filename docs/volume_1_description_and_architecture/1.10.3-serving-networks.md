## 1.10.3.2 Interfaces and subnets

- `dhcp.interfaces` names the interfaces Kea listens on; each may be the host's LAN or another one (a second NIC, a
  VLAN interface); one the host does not have is refused. A subnet on none of them is reached through a DHCP relay:
  Kea picks it by the relay's address, which normally lies inside it; `relay` is set only when that address lies
  outside. (A first build refused such a subnet without `relay`: the sandbox's second subnet showed it wrong.)
- fabric's **address on an interface** is read from the host when the configuration is rendered; it is what that
  interface's subnets are told to use (1.10.3.3) unless `dhcp.dns`, `dhcp.ntp` or the subnet's options say otherwise
  (2.1.10.5). A relayed subnet gets `host_ip` (it is routed to the host).
- A subnet with no router (`routers` unset) is allowed: an isolated network such as the lab.

## 1.10.3.3 What a served subnet's clients may reach

- Every subnet fabric serves joins the lists that today hold the host's LAN (2.1.10.4): BIND's `dns-resolvers` ACL, the
  filtering resolver's clients, the firewall's allowance for fabric's published ports (`DOCKER-USER`) and UFW's rules
  for them, and chrony. SSH is not among them: it stays with `lan_cidr` and `security.firewall_allow`.
- A subnet with **`access: guest`** joins only DNS (through the filtering resolver) and NTP: none of fabric's pages.
- fabric **listens on its address on each served interface**, not only on `host_ip`: the filtering resolver (53, and
  853 for DoT) for every subnet, nginx (443: the pages, the console, DoH) for full ones. BIND's own port (5053, the
  resolver's and RFC2136 clients') and RADIUS (the switches') stay on `host_ip`.
- fabric's **names stay on `host_ip`**, and each served subnet is given a route to it: a classless static route
  (DHCP option 121) `host_ip/32` via fabric's address on that network, so clients reach `host_ip` over their own
  link (Linux takes traffic for any of its addresses on any interface). A client given option 121 ignores the router
  option (RFC 3442), so a subnet with a router gets its default route in option 121 too. Found on the lab: without
  it, `info.<domain>` sent lab clients to `host_ip`, on a network they have no route to. (Answering each network with
  its own address was tried first: it needs BIND's `sortlist`, deprecated, or a view per network.)
- The lists are rebuilt from `dhcp:` on every apply, so removing a subnet removes its clients' access.

## 1.10.3.4 Reverse DNS for DHCP clients

- `kea-dhcp-ddns` also registers PTR records, in the reverse zones fabric generates (2.1.10.7): each zone covering a
  pool or reservation is dynamic, Kea's key limited to PTR and DHCID there; a DHCP subnet whose zone has no static
  record still gets one.
- On every apply fabric freezes such a zone, keeps Kea's PTR and DHCID records for the addresses it has no static
  record of, and swaps in its regenerated file with them. A static record never lies in a pool (refused), so the two
  never claim one address; a reservation's address with a static record keeps the static PTR.
- *As built (found by the `zones` suite, 2026-10-23):* each of Kea's registrations raises such a zone's serial by
  one, so BIND's can pass the render's (the epoch plus 10⁹) and BIND would keep its own copy at the thaw ("zone serial
  unchanged"): the swap (`reload_zone`) first gives the regenerated file a serial above the one BIND serves. And the
  records kept from Kea are not a change of fabric's (`zone_content_changed` compares fabric's part of the deployed
  file only), so the next apply or Sync now does not swap the zone again for them.
- *As built (found on the lab, 2026-10-24, 2.3.10.11.16):* a record BIND wrote over several lines in `( … )`, as it
  writes a long DHCID, is kept on one line without its parentheses; keeping its first line only left a file BIND
  would not load, and the zone frozen.

## 1.10.3.5 Turning DHCP on and off from the console

- The Kea tab, with DHCP off, offers to turn it on: the interface (from the host's interfaces), the first subnet and
  its pool (suggested from that interface's network), behind `dhcp:write` and the same checks as the vars file.
- Turning it off stops Kea and removes what it added: the DDNS key, its zones (forward and reverse) and their
  delegations, and the subnets' access (1.10.3.3). Leases and the settings are kept, so turning it on again resumes.
  An apply now stops, disables and removes the unit of any optional part turned off (its data kept), not only Kea's.
- A DHCP change from the console or `fabricctl dhcp` is the admin's yes to the firewall rules it implies (the `ports`
  group: 67/udp on a served interface, NTP and the domain controller's ports for its subnets): after the apply, setup's
  firewall step runs with that group approved (through systemd-run, out of fabric-agent's sandbox). Until now a subnet
  added from the console waited for the next setup for its rules. Also `fabricctl dhcp on|off`.

## 1.10.3.6 DHCP's names in the DNS tab

The DNS tab gains a **DHCP names** section (`dhcp:read`): read-only, each lease's name in `dhcp.<domain>`, its address
and its reverse name, from Kea's leases (what Kea registered; BIND allows no transfer to read its zones); editing stays
with DHCP (a reservation's hostname, the client's own name).

## 1.10.3.7 The DNS filter's groups from DHCP

0.7's client groups are addresses and subnets (2.3.12.1.5). 0.8 adds clients that follow Kea's data, kept as
references and turned into addresses on every apply: **`dhcp:<subnet name or network>`** (the subnet), **`device:<a
reservation's hostname or MAC>`** (its reserved address) and **`vlan:<n>`** (every DHCP subnet recorded with that VLAN:
where an 802.1X role puts its devices; by VLAN, so an apply never waits on the domain controller for the role). A
reference naming nothing DHCP serves is refused, and one while DHCP is off.

## 1.10.3.8 The lab suite

`tests/lab/dhcp.sh` drives an isolated network: a fabric host serving its second interface (`10.20.0.0/24`, no router)
and Ubuntu desktops as real clients (2.3.1.9.6). It checks a lease from the pool, the client's name in `dhcp.<domain>`
and its PTR, a reservation, a renewal, the client resolving through fabric and reaching the certificate page, a guest
subnet refused the pages, DHCP turned off and on from the console, and a DNS-filter group by subnet. It runs before
0.8 is released.

## 1.10.3.9 A preview in 0.7.0

0.7.0 ships DHCP as 0.8.0's candidates built it, **off by default** (`install_kea: false`), and says it is a
**preview until 0.8.0** finishes it (2.1.1.49): setup's plan names it so, on or off ("Optional, off: DHCP with Kea, a
preview until 0.8.0"), and the console's Kea tab opens with the same notice. Nothing else changes: turning it on works
as 1.10.3.5 describes. **Built 2026-10-11** for 0.7.0; tests: the consent suite reads setup's plan (DHCP named a
preview, on and off; no other part called one), the dev preview's Kea tab shows the notice and no other tab does.

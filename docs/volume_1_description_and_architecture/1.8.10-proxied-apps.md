## 1.8.10.1 Status

**Designed 2026-11-25, to build in 0.10.3** (decision 2.1.1.109, its review 2.1.1.109.1; the owner's answers are
recorded there). Nothing of it is built.

## 1.8.10.2 What it is for

The owner, 2026-11-25: "do other container hosting on the same host and allow configuration of the proxy in the
fabric-ctl ui". A person runs their own web apps on the fabric host, in containers they start themselves, and reaches
each at a name of fabric's DNS, with a certificate from fabric's CA and, if they want, Keycloak's sign-in in front,
all set in the console. They never edit nginx's files or touch fabric's own services.

fabric does not run, pull, update or harden these apps (2.1.1.109, points 2 and 4): it gives them a network to join
and proxies to them. Their hardening is the owner's, and they are not in fabric's privileges inventory (1.2.7).

## 1.8.10.3 Shape: one nginx, two networks

```
browser ──TLS──> nginx (fabric) ──> fabric's own services   on fabric_net (unchanged)
        <app>.<domain>    │
        fabric's cert     └──> the owner's apps            on other_apps (or an address on the LAN)
                               │
        (sign-in required) ──> apps-auth (oauth2-proxy) ──> Keycloak
```

- **The same nginx** (1.2.4, 1.2.7) receives and directs everything (owner, 2026-11-25). Nothing of fabric's own
  services changes: they stay on `fabric_net` (`10.255.0.0/24`, 1.2.11.1.4), and nginx stays on it.
- nginx also joins **`other_apps`** (1.8.10.4), the network the owner's apps join. An app may instead be reached at an
  address and port on the LAN.
- **One `server` per app**, at the app's name, listening on 443 on the addresses fabric's pages use (the host's, and
  each network DHCP serves in full, as the console's); port 80 sends to HTTPS. Each is in a file of its own
  (1.8.10.6).
- **The site's web access rules apply** to every app as to fabric's own names: a network not allowed web is closed
  with no reply (`$fabric_web_denied`, 1.10.4.48.3).

## 1.8.10.4 The `other_apps` network

- **fabric creates it** (owner, 2026-11-25: "fabric will create it") on the first apply that has a proxied app, or at
  setup when an app is already in the settings file: a Docker bridge network named `other_apps`, its subnet the
  setting `other_apps_subnet` (default `10.255.1.0/24`), nginx at a fixed address in it (`ip_nginx_apps`, default
  `10.255.1.10`).
- **It is a claim** (1.2.13): its subnet must not collide with `fabric_subnet`, the LAN, a DHCP subnet, the host's
  routes or the site's other networks in the address plan; its name must not be a Docker network fabric did not make.
  A collision is refused at setup and in the console, saying what it collides with.
- **The owner attaches their apps** (`networks: [other_apps]`, external, in their compose file; or
  `docker network connect other_apps <container>`). How is a documented step (3.8.10, when built). Apps on it reach
  each other and the internet as on any bridge network; that is the owner's to limit.
- **It is never `fabric_net`**, and nothing of fabric's but nginx is on it, so an app cannot reach Keycloak's
  database, OpenBao, Step-CA or the DC directly.
- **Uninstall** disconnects nginx and removes the network; if the owner's containers are still on it, it is left in
  place and uninstall says which containers hold it (nothing of the owner's is stopped).

## 1.8.10.5 An app's settings

Each app is one entry of the setting `proxied_apps` (empty by default), set in the console (1.8.10.12) and kept in
the settings file. Every setting is per app (owner, 2026-11-25: "configured by application"):

| Setting | What | Default |
|---|---|---|
| `name` | The app's host name in the site's zone; a CNAME to the fabric host, provided by fabric (1.4.1.4) | — (required) |
| `upstream.host` | A container's name on `other_apps`, or an address or name on the LAN | — (required) |
| `upstream.port` | Its port | — (required) |
| `upstream.scheme` | `http` or `https`; `https` is verified against fabric's root and the upstream's own name (`proxy_ssl_verify on`), never unverified (global Rule 10) | `http` |
| `sign_in` | Whether Keycloak's sign-in is required in front of the app (1.8.10.9) | required |
| `sign_in_groups` | Directory groups allowed in, when sign-in is required; empty means any person who signs in | empty |
| `websockets` | WebSocket upgrade headers and a long read timeout | on |
| `max_body` | Largest request body (`client_max_body_size`) | `16m` |
| `rate` | Requests per second per client address (`limit_req`), and its burst | 10 r/s, burst 50 |
| `custom` | An optional custom nginx section (1.8.10.7) | empty |
| `enabled` | Off keeps the entry but serves nothing at the name | on |

- nginx reaches the upstream **through a variable and Docker's resolver** (`set $app_upstream …; proxy_pass
  $app_upstream;`, `resolver 127.0.0.11`), so an app container that is stopped or not yet started never stops nginx
  from starting: its name answers `502` and the console shows the app as down.
- An upstream on **fabric_net**, or one of fabric's container names, or the host's own addresses, is refused (an app
  on the host joins `other_apps` instead).
- nginx passes `Host`, `X-Forwarded-For`, `X-Forwarded-Proto https` and, with sign-in, the person's user name and
  e-mail (`X-Auth-Request-User`, `X-Auth-Request-Email`); headers of those names sent by the browser are dropped.

## 1.8.10.6 One file per app

- Each app is rendered from one template (`templates/nginx/app.conf.j2`) to its own file,
  `/opt/nginx/config/apps.d/<name>.conf`, mounted read-only into nginx at `/etc/nginx/apps.d/`. The file holds the
  app's rate-limit zone and its two `server` blocks (80 and 443).
- fabric's `nginx.conf` gains one line, once: `include /etc/nginx/apps.d/*.conf;` inside `http {}`. Changing an app
  never rewrites `nginx.conf` or another app's file (owner, 2026-11-25: "it should only adjust the .conf for that
  other section").
- Removing an app removes its file, its CNAME and its certificate (1.8.10.8).

## 1.8.10.7 An app's custom section

An app may need nginx settings the table above does not have (owner, 2026-11-25: "a custom nginx section may be
necessary"). Its `custom` text is placed inside that app's own `server { }` for 443, after fabric's directives.

- **An allow-list, not a deny-list:** fabric's checks accept only directives that shape the app's own traffic —
  `location` blocks, `proxy_set_header`, `proxy_hide_header`, `proxy_*_timeout`, `proxy_buffering` and
  `proxy_buffer_size`, `proxy_redirect`, `proxy_cookie_path`, `proxy_http_version`, `add_header`,
  `client_max_body_size`, `rewrite`, `return`, `limit_except`, `sub_filter` and `gzip*`. Anything else is refused
  with its name and line. Widening the list is a design change (5.5).
- **Never accepted**, whatever a later allow-list says: `include`, `load_module`, `listen`, `server_name`, `ssl_*`,
  `root`, `alias` (nginx's folders hold every certificate's private key), `resolver`, and any `*_pass` directive (the
  upstream is fabric's setting: a custom section must not reach `fabric_net`, where OpenBao, Keycloak's admin and the
  database are).
- A custom section is shown in the console beside the file it renders to, so the person sees what nginx gets.

## 1.8.10.8 Certificates

fabric issues each app's certificate itself, on the host (owner, 2026-11-25: "our system should issue certificates on
the local host to prevent a user from needing to configure or touch are backend"):

- A Step-CA leaf for the app's name, minted at the apply that adds the app, as fabric's service certificates are
  (1.5.1.2), into `/opt/nginx/certs/apps/<name>/`; renewed by `fabric-certs.timer` with the others, nginx picking it
  up with its reload.
- Renamed or removed: the old name's certificate is revoked and its files removed.
- Nothing is asked of the owner, and the app itself needs no certificate (it may serve plain HTTP on `other_apps`).

## 1.8.10.9 The sign-in gate

- **One gate for every app:** an oauth2-proxy container, `apps-auth` (unit `fabric-apps-auth`), installed with the
  first app that requires sign-in and removed with the last one. It is fabric's own container, so fabric's rules hold:
  non-root (a `fabric-*` account with the next free id in `ids`, 2.1.2.4), `cap_drop: ALL`, `no-new-privileges`,
  read-only root, a memory limit in the budget (1.2.4.3; 64 MiB at 4 GB), on `fabric_net` only, nothing published.
  Its image is pinned by digest in `config/images.lock.yaml` (oauth2-proxy's official multi-arch image, MIT).
- **Keycloak:** a confidential client `fabric-apps` in fabric's realm; its secret and the gate's cookie secret are
  generated per install and kept in OpenBao, as fabric's other secrets (global Rule 10).
- **nginx:** each app that requires sign-in has `auth_request` to the gate, and its `/oauth2/` paths sent to the gate;
  allowed groups are passed per app (`allowed_groups`), so one gate serves every app. A gate that does not answer
  refuses the request (`500`), never lets it through.
- Sign-in is the same Keycloak session as the console's, with its second factor where the realm requires one.

## 1.8.10.10 Checks before an apply

Changes are held and applied as DNS' are (2.1.8.18, 4.8.4). An apply of the proxied apps:

1. **fabric's own checks** of every changed entry: the name (1.2.13; not one of fabric's names, a Cockpit name, the
   host's own or another app's), the upstream (1.8.10.5), the custom section (1.8.10.7). A failure changes nothing
   and says which entry and why.
2. **Render** the changed apps' files into a candidate folder (`apps.next/`), beside the live `apps.d/`.
3. **`nginx -t`** of the whole candidate configuration (fabric's `nginx.conf`, the live files of the apps not changed,
   the candidates) in a throwaway container of the same pinned nginx image (1.2.4.6), no network, as nginx's user. A
   failure changes nothing and shows nginx's own message.
4. **Swap and reload:** the candidates replace their live files, the CNAMEs and certificates are made, nginx is
   reloaded (HUP).
5. **Probe:** fabric's own health name over port 80 and each changed app's name over 443, through nginx on the host.
   Both answer: the live `apps.d/` is copied to `apps.good/` (1.8.10.11). Either fails: the fallback runs.

Every apply is audited: who, which apps, the result.

## 1.8.10.11 Fallback: the last configuration that worked

The owner asked that an error the checks miss "shouldn't stop fabric-ctl from functioning", and for "a fall back
setup" when nginx restarts. So:

- **The last configuration that worked** is kept: `apps.good/`, written only after a probe passes (1.8.10.10).
- **A reload that fails** (the probe of step 5): nginx refusing a reload keeps its running configuration (its old
  workers stay); fabric then puts `apps.good/` back as `apps.d/`, reloads again and marks the apply failed, saying
  which app. The candidates are kept in `apps.failed/` for the console to show.
- **A start that fails** (a reboot, a restart, an image update): the nginx unit tests before it starts
  (`ExecStartPre`, the throwaway `nginx -t` of step 3) with `apps.d/`; if that fails, with `apps.good/`; if that fails
  too, with **no** apps' files. nginx always starts with fabric's own names and the console; the apps that were left
  out show as failed, saying why, in the console, `fabricctl status` and `fabricctl doctor`.
- **`fabricctl` never depends on nginx:** it runs on the host. `fabricctl apps list` shows each app and its state;
  `fabricctl apps disable <name>` turns one off and applies, for when the console cannot be reached.

## 1.8.10.12 Who may change what

| Action | Permission | Bundle |
|---|---|---|
| See the proxied apps, their state and their rendered files | `proxy:read` (new) | `fabric-console-admin`, `fabric-auditor` |
| Add, change, enable, disable and remove an app (every setting but `custom`), and Apply | `proxy:write` (new) | `fabric-console-admin` only |
| Write or change an app's custom section | `proxy:write` **and** Domain Admins (checked in the DC, as backups are, 1.3.7.12) | — |

A custom section goes past fabric's own settings, so it takes the domain's highest tier, as backups do (2.1.1.105).
Lowering an app's sign-in (from required to not) asks for a sign-in from the last 5 minutes, as setup's Apply does
(1.8.2).

## 1.8.10.13 Security

- The proxy adds reach, not privilege: nginx's container, user and capabilities are unchanged (1.2.7); it gains one
  network.
- Off by default: with no app, no `other_apps` network, no gate, no `apps.d/` files.
- An app's name is served only while it is in `proxied_apps` and enabled; any other name gets nginx's default server.
- **No WAF** in this build (2.1.1.109.1): the owner's apps are not fabric's small, validated routes, so 2.1.18.21's
  reason ("no public API") does not cover them. The rate limit per app is on by default, every app is under the
  site's web access rules, and a WAF (ModSecurity with the OWASP CRS) is a later opt-in per app, decided on its own.
- Status (`fabricctl status`, the console's Overview) lists each app: up, down (its upstream does not answer), or
  failed (left out by the fallback).

## 1.8.10.14 What it changes outside fabric

fabric creates the `other_apps` Docker network (1.8.10.4), recorded as setup's other host changes are (1.2.9) and
undone by uninstall. It changes nothing of the owner's containers: attaching them is the owner's step.

## 1.8.10.15 Tests

To write with the build (3.1.2, global Rule 9), positive and negative for each entry point:

- **The console's proxy page and its routes, and `fabricctl apps`:** an app added, changed, disabled and removed
  renders, serves and leaves no trace (file, CNAME, certificate); refused without `proxy:write`; a custom section
  refused to a `proxy:write` holder who is not a Domain Admin.
- **Collisions:** an app's name against the host's, fabric's names, a Cockpit name, an admin's own record and another
  app; `other_apps_subnet` against `fabric_subnet`, the LAN, a DHCP subnet and a Docker network fabric did not make.
- **Custom section:** each never-accepted directive refused with its name and line; an allowed one rendered.
- **Fallback, in the sandbox against real nginx:** a candidate that fails `nginx -t` changes nothing; a reload whose
  probe fails restores `apps.good/`; a start with a broken `apps.d/` and a broken `apps.good/` starts with fabric's
  names and the console, the apps marked failed.
- **Upstreams:** a stopped app container does not stop nginx starting (`502` at its name); an HTTPS upstream with a
  self-signed certificate is refused; an upstream on `fabric_net` is refused.
- **Sign-in:** an app requiring sign-in sends an unsigned browser to Keycloak and lets a signed-in member of an allowed
  group through; a person outside the groups gets `403`; a stopped gate refuses, never admits.
- **Uninstall:** removes the network when nothing else is on it; leaves it, naming the containers, when something is.

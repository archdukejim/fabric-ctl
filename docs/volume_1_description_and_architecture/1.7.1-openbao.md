## 1.7.1.1 Secrets: OpenBao

> **Status (iteration 1, built):** container, Raft, TLS, `vault.<domain>`,
> static-seal auto-unseal via key slots (fabric-unlock, key in RAM only at start; key-file slot, rotation), one-time
> init (recovery keys to `~/fabric-admin`), root token revoked, AppRoles
> `fabric-setup` / `fabric-agent` bound to fabric_net, KV v2 `fabric/` and
> `apps/`, declarative audit log, `fabricctl vault status`, web UI status tab,
> doctor checks, backup/reinstall; `fabric-secrets.yml` imported into
> `fabric/secrets` (verified, shredded, marker file; OpenBao locked → setup
> stops, never regenerates). Since then built: unlock methods (key file,
> USB sticks — tested on a Pi —, PKCS#11 security keys and KMIP HSMs, the
> latter two against SoftHSM2 / PyKMIP only), Keycloak sign-in to OpenBao's
> own UI per role bundle, break glass. **Not yet:** rotated credentials,
> SSH CA, a Secrets section in the web UI that edits `apps/` (the OpenBao
> tab points to OpenBao's own UI instead).
>
> As built, the details below differ in small ways: the key-file slot
> replaces the bare `unseal.key`;
> fabric-unlock is the `openbao` unit's start condition
> (`fabricctl vault unlock`), not a separate unit; a USB stick is mounted
> next to the RAM key folder (`usb-<slot id>`) only while it is read; when
> the last present unlock device is pulled, fabric **stops** OpenBao (a udev
> rule runs `fabricctl vault device-event`) rather than calling
> `bao operator seal`; the CLI is `fabricctl vault slots | test | remove |
> rotate | add-usb | add-kmip | tokens | add-key | break-glass`.

**OpenBao** (MPL-2.0, Linux Foundation fork of Vault; Vault-compatible API,
CLI and clients) rather than HashiCorp Vault, whose BSL licence is not open
source. Multi-arch images; ~150 MB at 4 GB (fits the [1.2.6.1](1.2.6-targets-and-hardening.md#1261-targets-and-hardening) budget).

- **Deployment:** container `openbao` on `fabric_net`, integrated **Raft**
  storage in `/opt/openbao/data`, TLS listener with a Step-CA certificate;
  published as `https://vault.<domain>` through nginx (CNAME `vault`). Same
  hardening as every container ([1.2.6.1](1.2.6-targets-and-hardening.md#1261-targets-and-hardening)); image pinned via the channel ([1.14.1.1](1.14.1-image-channels.md#11411-image-channels-tested-versions-decoupled-from-releases)).
- **Unseal (decided: auto-unseal from a local key file):** the unseal key
  lives in `/etc/fabric/openbao/unseal.key` (root, 0400) — optionally on a
  removable USB stick mounted at boot. OpenBao unseals itself on start, so a
  power cut does not need a human. **Trade-off, stated in the installer:**
  whoever holds the SD card (or USB stick) holds the vault. Recovery shares
  and the initial root token are shown once at `init`; the root token is
  revoked after bootstrap.
- **Unlock methods = key slots (decided, 2.1.7.2).** OpenBao keeps one seal:
  the built-in `static` seal with one 32-byte key **K**. fabric decides how
  K reaches it, the way LUKS does for disks: K is stored *wrapped* in one or
  more **slots**, and **any one enabled slot unlocks** (a later option can
  require several together: k-of-n across slots).

  | Slot | K is… | Present when | Tested against |
  |---|---|---|---|
  | Local file | in `/etc/fabric/openbao/` (openbao user, 0400) | always (no kill switch while this slot exists) | real image |
  | USB stick (one slot per stick) | on the stick; the stick is recognised by filesystem UUID + USB serial and unknown sticks are refused | the stick is plugged into the host | loop device; real stick on a Pi 5 |
  | Security key (PKCS#11: YubiKey, Nitrokey, SmartCard-HSM, …) | encrypted by a non-exportable RSA-2048 key inside the token (RSA-OAEP; SHA-1, the digest every token supports); PIN root-only on the host; touch via the key's own policy (set with the vendor tool) | the token is plugged in | SoftHSM2 (hardware tokens untested) |
  | HSM / key manager (KMIP: CipherTrust, Fortanix, Entrust, IBM, Cosmian, OVH, …) | encrypted by an active AES key on the device, over mutual TLS | the device is reachable and authorises this client | PyKMIP |

  Keypad-encrypted USB drives (Apricorn, IronKey, iStorage, …) are USB
  stick slots: unlocked by PIN on the drive, then read like any stick.
  Examples of devices are not a support list: fabric supports interfaces
  (plain storage, PKCS#11, KMIP). Vendor specifics (licensing, login rules,
  enabled algorithms) are the device's; the UI says which simulator a slot
  type was tested against.

  - **fabric-unlock** (host unit, before `openbao`; re-run by udev on
    insert): tries every slot, writes K to `/run/fabric/openbao/<key id>.key`
    (tmpfs, openbao user, 0400). OpenBao's static seal reads it and
    unseals; the file is then wiped. No slot present → OpenBao stays sealed
    (unhealthy) while every core service keeps running. Last slot device
    removed → `bao operator seal` immediately (kill switch), unless a
    local-file slot exists, which the UI states.
  - **HSM work happens on the host**, not in the OpenBao container: no
    vendor libraries, plugins or device passthrough in the container, which
    stays capability-free and read-only (and the Alpine/musl vs glibc
    vendor-library problem disappears).
  - **Trade-off, stated in the docs:** unlike OpenBao's native HSM seals,
    K exists briefly in host RAM while unsealing. Root on the running host
    could take it, and could equally read the unsealed vault from memory.
  - **Web UI** (OpenBao tab → Unlock methods) and `fabricctl vault slot …`:
    list slots (type, label, device id, added, Test); **add** a slot (only
    while unlocked); **remove** (never the last one); **rotate K** (new key,
    re-wrapped into every remaining slot, OpenBao moved over with the static
    seal's `previous_key` → `current_key` rotation). Rotation is the answer
    to a lost stick or token: its slot stops working without being needed.
    Every change is audited and needs the host name typed as confirmation.
  - With auto-unseal, OpenBao's recovery keys cannot decrypt the vault:
    losing every slot loses the data. The UI warns while only one
    removable slot exists and recommends a second (a backup stick in the
    safe, or a second token with the same imported key).
  - Security keys: K is imported into (or wrapped by) the token's key.
    Tokens that allow import (YubiKey PIV/OpenPGP, SmartCard-HSM) can hold
    the same key in two tokens; otherwise the backup is another slot type.
  - Cloud KMS (AWS/Azure/GCP) would be another slot type, but it needs the
    internet to unseal (against the offline requirement): not offered
    unless asked for.
  - Build order: slot store + fabric-unlock + local-file slot (replacing
    today's direct key file), USB stick slots, security keys, KMIP.

- **USB stick slots — details:**
  - The stick is plugged into the fabric host. The UI lists removable USB
    block devices; the admin picks one and types the host name to confirm
    (it is wiped). fabric writes K (key id + checksum), verifies it, records
    the stick's UUID and serial, and tests the slot.
  - Mounted read-only at `/run/fabric/key-usb/<uuid>` only while
    fabric-unlock reads it (tmpfs mount point, never under `/opt`).
  - Limits, stated in the UI: a plain stick can be copied by anyone who
    holds it for a moment (rotate if one goes missing); someone holding
    the host and a slot device together can unseal; a stick left in the
    host is the same as the local file.

- **Boot independence:** no core service (DNS, DHCP, LDAP, SSO, nginx) reads
  OpenBao to *start*. fabricctl renders secrets into each service's config at
  deploy time; if OpenBao is down or sealed, the last rendered config keeps
  running and deploys that need a changed secret wait and report.

**Uses (all four selected):**

| Use | How |
|---|---|
| fabric's own secrets | KV v2 at `fabric/`. `fabric-secrets.yml` is imported once, then OpenBao is the source of truth; fabricctl and fabric-agent authenticate with AppRole (credentials root-only on the host). The plaintext file is removed after import (kept only inside encrypted backups). |
| Secrets for your apps | KV v2 at `apps/`. Humans log in with **Keycloak OIDC** (client `fabric-openbao`); LDAP group → OpenBao policy (e.g. `admins` → admin, `<app>-owners` → `apps/<app>/*`). |
| Dynamic / rotated credentials | Database engine on the fabric Postgres; **static roles** with scheduled rotation for Keycloak's DB user (Keycloak needs a stable password in its config, so fabricctl re-renders and restarts it on rotation). LDAP engine rotates the domain's service accounts (`fabric-keycloak-<site>`, …; [1.6.3](1.6.3-samba-directory.md)). Apps can use true dynamic, per-lease DB users. |
| SSH certificate CA | SSH engine signs short-lived user certificates (`bao ssh`/`fabricctl ssh`), principals from LDAP groups; hosts trust the CA key via `TrustedUserCAKeys` (the Linux join installer `join-linux.sh` gains an option for it). |

The web UI gains a Secrets section (browse/edit `apps/`, rotate, issue SSH
certs) through fabric-agent, which talks to OpenBao with its own AppRole —
the webui container still holds no secrets itself.

## 1.7.1.2 Keycloak's database password, rotated by OpenBao

Built 2026-10-08 for 0.6.3 (decision 2.1.7.4; design 2.3.1.11.9). Setup step `dbrotation`
(`setup/ensure_db_rotation`), after `vault`.

- **Roles in Postgres.** `fabric_admin` is Postgres's own admin (a superuser; password `postgres_admin_password`),
  which OpenBao's database engine connects as. Keycloak runs as its own role, `keycloak_db` (no superuser), which owns
  Keycloak's database and everything in it. The role Postgres was created with (`keycloak`, from `POSTGRES_USER`) is
  its *bootstrap superuser*, which Postgres 16+ never lets lose that attribute (found by the test): Keycloak moves off
  it to `keycloak_db`, and it is then locked (no login, no password). SQL goes to `psql` on stdin, over the
  container's local socket: no password on a command line.
- **OpenBao's database engine** (`database/`): connection `postgres` (`postgresql-database-plugin`) to Postgres's alias
  on `fabric_net`, `sslmode=verify-full` against fabric's root (2.1.2.15: nothing leaves the host); a static role
  `keycloak` for `keycloak_db`. Making the role rotates the password at once: setup saves it (with `keycloak_db_user`)
  in fabric's secrets, re-renders and restarts Keycloak in the same run, and waits until it is healthy. OpenBao's own
  rotation period is set far beyond a month, a backstop only.
- **Monthly**, `fabric-db-rotate.timer` (the 1st, 03:45, spread over half an hour) runs `fabricctl vault rotate-db
  --scheduled` (`vault/rotate_db_password`): OpenBao sets a new password in Postgres, fabric saves it, applies
  Keycloak's settings (`fabricctl --apply`) and waits until Keycloak is healthy (about a minute; connections Keycloak
  holds keep working meanwhile). The run is recorded (`/opt/fabric/archive/db-rotation.json`) and audited
  (`DB_ROTATE`); doctor fails when the last run failed or is older than 40 days.
- **Postgres never needs OpenBao to start:** the password lives in Postgres. Postgres's own settings never change with a
  rotation: `POSTGRES_PASSWORD` is `postgres_init_password`, used once on an empty data folder (it starts equal to
  Keycloak's first password; an existing install keeps its current one, so nothing restarts).
- **A failure:** OpenBao refusing the rotation leaves the old password working; a new password Keycloak could not take
  up is recorded and raised: run `fabricctl vault rotate-db` again (4.7.1.2).
- **Tests:** `tests/openbao/db_rotation.py` (the real Postgres and OpenBao images on a private network: the take-over,
  the roles and ownership, a rotation, converging without a change, and the refusals, including OpenBao reaching
  Postgres by a name its certificate does not carry); the sandbox runs it in a full install (setup's take-over,
  `rotate-db` with Keycloak restarted, doctor, the timer).

## 1.7.1.3 Local admin passwords, set and escrowed by OpenBao

> **Status: designed 2026-10-10 for 0.9, not built** (decisions 2.1.7.6 to 2.1.7.10; proposal and impact
> [2.3.7.2](../volume_2_engineering_decisions/2.3.7-openbao-notes.md#2372-proposal-local-admin-passwords-in-openbao)).
> All its decisions were settled by the owner the same day.
> **0.8.0 builds the fabric host's own account** (D6, 2.1.7.15 to 2.1.7.20): what it does is 1.7.1.4, which decides
> where 0.8.0 differs from this design (no schedule, no exports, no two-step, nothing rotated while OpenBao is locked).

Every machine fabric manages keeps one local admin account that works when the domain does not: the break-glass
way in. OpenBao generates each one's password, the machine (or fabric, for what cannot do it itself) sets it, and
OpenBao keeps it, so no two machines share a password and none is ever reused after it was used. The same passwords
can be printed or written out for a physical safe, because most secure sites keep break-glass credentials sealed in
an envelope.

1.7.1.3.1 **Which accounts**

| Kind | Account | Set by |
|---|---|---|
| Windows domain members | `local-admin`, a local account in Administrators, made by fabric's task at join (2.1.7.11; the built-in Administrator is left as it is) | the machine itself (1.7.1.3.3) |
| Linux domain members | `local-admin`, a local account in `sudo`, made by the join script (1.6.7) | the machine itself |
| The fabric host | `local-admin`, a local account in `sudo`, console log-on only (SSH refused) | fabric, on the host |
| Network gear (switches, access points, the 802.1X authenticator) | the device's local admin | fabric, through the device's integration (`src/integrations/<name>/`) |

1.7.1.3.2 **Where they are kept.** A KV v2 mount of its own, `local-admin/`, path
`<site>/<kind>/<machine>/<account>`, separate from `fabric/` and `apps/` so its policies stand alone. Each version
records the password, when and why it was set (`initial`, `scheduled`, `after use`, `checked in`, `manual`), and
which sealed exports hold it. The last 10 versions are kept for the audit; only the newest is valid. Passwords come
from an OpenBao password policy: 24 characters, no characters that are easily misread on paper (`0 O 1 l I`).

1.7.1.3.3 **How a machine sets its own.** A member machine never gives fabric a way in: it asks OpenBao for a new
password, sets it locally, then writes it to its own path. Its OpenBao policy allows writing its own path only, never
reading any (its own included), so a compromised machine learns nothing it did not already hold. The machine side is
a scheduled task on Windows (SYSTEM) and a systemd timer on Linux, installed by the join (1.6.5, 1.6.6), checking every
hour; it signs in to OpenBao with its machine certificate from fabric's CA, the one 0.9's 802.1X gives it at join
(OpenBao's cert auth, 2.1.7.7). On Windows it is fabric's own task, not Windows LAPS (2.1.7.8). A password is written to OpenBao before the old one is replaced on the
machine, and only marked current once the machine confirms it set it, so a failure in between leaves the old password
working and still recorded.

1.7.1.3.4 **Rotation, per policy.** Each kind and each machine has a rotation policy (2.1.7.6); the site's default is
**after use**:

| Policy | A new password when |
|---|---|
| `after-use` (the default) | the account was used (a log-on seen on the machine: Windows event 4624 for its SID, PAM on Linux) or checked out, after a grace period (8 h by default) |
| `schedule` | every N days (365 by default), and after use as well unless turned off |
| `checkout` | it is checked in, or its check-out lapses (8 h by default) |
| `manual` | only when an admin asks (a relaxation: shown by status and the web console, Rule 10) |

1.7.1.3.5 **Check-out.** Reading a password is a check-out: the person needs `local-admin:checkout` (a role in
Keycloak, 1.6), gives a reason, and the check-out is audited in fabric's audit log and OpenBao's. In the web console
(OpenBao tab, *Local admins*) and as `fabricctl local-admin checkout <machine> [--account A]`; `checkin` ends it.
Under `after-use` and `checkout` a check-out starts the rotation clock.

1.7.1.3.6 **The fabric host's own break-glass.** It must work when OpenBao does not, so it lives in an envelope first:
its policy is `schedule` (365 days by default) with a sealed export required. A scheduled rotation is two-step: fabric
generates the new password and its export, and applies it only once an admin confirms the new envelope is sealed (its
serial typed back); until then the old one stays, and doctor warns when the confirmation is overdue. With OpenBao
locked the host's password can still be rotated from the console (`fabricctl local-admin rotate-host`), printed, and
written to OpenBao once it is back. Its export can add OpenBao's recovery key shares, one per split sheet, when asked; off by default, so one
opened envelope set cannot reach both (2.1.7.10).

1.7.1.3.7 **Exports for the safe.** Any of these, for one machine, a kind, or all; each is audited and recorded on the
versions it holds, and status, doctor and the web console show every export that is stale (a password rotated since):

- **Printed sheet**: a PDF per account (machine, account, password in a clear type, set on, the export's serial to
  write on the envelope), for printing and sealing.
- **Encrypted file**: one archive of the selected passwords, written to a USB stick on the fabric host (the stick
  handling of 1.7.1.1's USB unlock slot), encrypted with `age` for a passphrase or an `age` key held apart (2.1.7.9).
- **Split sheets**: the encrypted file's key split k-of-n (Shamir; 3 of 5 by default), one share per sheet, each sheet
  in its own envelope, so no single envelope opens anything.

1.7.1.3.8 **What it is not.** Not a password manager for people and not domain accounts (Keycloak and Samba keep
those). Network gear is managed only where an integration exists; the first is the 0.9 lab's authenticator.

## 1.7.1.4 The fabric host's local-admin (0.8.0)

Step D6 of 1.6.12.15 (decisions 2.1.7.15 to 2.1.7.20; build note
[2.3.7.7](../volume_2_engineering_decisions/2.3.7-openbao-notes.md)): the fabric host's own break-glass account, the
first `local-admin` OpenBao sets and keeps. Every other machine's comes with 0.10.0 (1.7.1.3).

- **1.7.1.4.1 The account, a host change** (2.1.7.16, global Rule 12): setup's step `localadmin`, after `dbrotation`,
  makes `local-admin` on the host: a local account (`useradd`, a home folder, `/bin/bash`), in the `sudo` group (or
  `wheel` where there is no `sudo`), its comment "fabric local-admin (OpenBao, break glass)". It is its own consent
  item, `local_admin` (recommended: declining leaves the host without it, shown by `fabricctl status`). fabric makes
  the account only when no account of that name exists, or when its own record (`<config>/local-admin.json`, 0600)
  says fabric made it (a reinstall makes it again); an account of that name fabric did not make is refused, nothing
  changed. Undone by `sudo fabricctl setup --undo local_admin` and by uninstall: the account and its home removed (an
  account still signed in is refused by `userdel`, and said), the SSH drop-in removed and sshd reloaded, the record
  removed; OpenBao's versions stay as its history, marked removed.
- **1.7.1.4.2 Where it is kept** (1.7.1.3.2): a KV v2 mount `local-admin/` (10 versions kept), at
  `<site_name>/fabric-host/<hostname>/local-admin`. Each version holds the password, when it was set (`set_on`, UTC),
  why (`initial` or `after use`; a check-out counts as a use) and the host. The path's metadata names the version that
  is current (`current`) and the rotation policy. Passwords come from OpenBao's password policy `local-admin`: 24
  characters of upper and lower case letters and digits without `0 O 1 l I`, each class at least once. fabric-setup's
  OpenBao policy may write and read there; nobody else's. A new password is written to OpenBao first, then set on the
  host with `chpasswd` (on stdin), and only then marked current: a failure between leaves the old password working and
  current.
- **1.7.1.4.3 Its rotation policy** (2.1.7.16): `after-use` (the default) or `keep-until-checkout` (2.1.7.15 item 2).
  In 0.8.0 both rotate after a use or a check-out, once the grace has passed (8 hours, 1.7.1.3.4's default, not a
  setting yet); neither has a scheduled rotation, which is what tells them apart from 0.10.0 on (asked, 2.3.7.7). Set
  with `sudo fabricctl local-admin policy after-use|keep-until-checkout`, root acting for the Enterprise Admin,
  audited `LOCAL_ADMIN_POLICY`.
- **1.7.1.4.4 A use, and the rotation after it** (2.1.7.17, 2.1.7.20): `fabric-local-admin.timer` runs `fabricctl
  local-admin check --scheduled` hourly. It reads the journal's sign-in messages (facilities auth and authpriv: PAM's
  "session opened for user local-admin", or a session opened by it) and `/var/log/wtmp` (its sign-ins as
  `USER_PROCESS`) since the current password was set; the first one found marks the password used (audited
  `LOCAL_ADMIN_USED`, how and when). Once a use or a check-out is 8 hours old the rotation is due: fabric signs in to
  OpenBao with fabric-setup's AppRole, takes a new password from the policy, keeps it as a new version, sets it, marks
  it current (audited `LOCAL_ADMIN_ROTATE`, never a password). With OpenBao unreachable or sealed the rotation waits:
  the used password stays valid, the record says since when and why, `fabricctl doctor` and the console's reminders
  say so, and the next timer run after OpenBao is back rotates it. Nothing rotates while OpenBao is locked (1.7.1.3.6's
  `rotate-host` is not built).
- **1.7.1.4.5 Check-out** (2.1.7.18): `sudo fabricctl local-admin checkout --reason "<why>"` on the host (root acts for
  the Enterprise Admin) or `POST /v1/local-admin/checkout` (body `reason`) through the console signed in as
  `fabric-admin`: fabric-agent asks the DC the caller's tier (1.6.12.17.2) and refuses anyone below the Enterprise
  Admin's, Directory Administrators included (the route itself needs only a sign-in). The reason is required, one line
  of up to 200 characters. The current version is read from OpenBao (audited there as well), shown once, and the
  check-out audited `LOCAL_ADMIN_CHECKOUT` (who, from where, the reason; never the password); it marks the password for
  rotation after use (1.7.1.4.4). With OpenBao locked a check-out is refused: in 0.8.0 OpenBao holds the only copy.
- **1.7.1.4.6 local-admin over SSH** (2.1.7.19): a switch kept in the domain. The store is
  `CN=local-admin,CN=fabric,CN=System`, one `msDS-App-Configuration` per target, its JSON in `msDS-Settings` as the
  grants' (1.6.13.11.1): `CN=dc-host-<dc>` for the host that runs the DC `<dc>`, `{"kind": "dc-host", "dc", "ssh",
  "by", "when"}`; no object is off. 0.10.0 adds targets of other kinds (a machine group by its `objectGUID`) to the same
  store. It is written inside a writable DC as the system (the container's `local_admin_tool.py`), read at any DC.
  - Set with `sudo fabricctl local-admin ssh on|off [--dc dc-NNNN]` (default this host's DC) or `POST
    /v1/local-admin/ssh` (body `ssh`: `on` or `off`, `dc` optional), only by the Enterprise Admin's tier, as a
    check-out is; audited `LOCAL_ADMIN_SSH`. From a host whose DC is read-only it is refused, naming the writable DC
    to run it at (`--dc` names this host's DC there); a `--dc` that is no DC of the domain is refused.
  - Applied on the host at once when it names this host's DC, and by every timer run (another host's at its next run;
    a DC that does not answer leaves the last applied state, said). Where an SSH server is installed fabric writes
    `/etc/ssh/sshd_config.d/05-fabric-local-admin.conf`: off, `DenyUsers local-admin` (sshd refuses it before any
    password); on, a `Match User local-admin` block allowing password authentication for that user only
    (`PasswordAuthentication yes`, `KbdInteractiveAuthentication yes`, `PubkeyAuthentication no`, `AuthorizedKeysFile
    none`), closed by `Match all`. sshd checks it (`sshd -t`) before and after; one it refuses is put back and never
    loaded; sshd is reloaded (open sessions stay).
  - While it is on for this host it is a relaxation (global Rule 10): `fabricctl status` and the console's Overview
    list it (relaxed settings), `fabricctl doctor` warns, `fabricctl domain status` says it.
- **1.7.1.4.7 Status and doctor:** `sudo fabricctl local-admin status`: the account, its policy, the current version
  and when it was set, a use or check-out seen and when the rotation is due, a rotation waiting and why, the SSH switch
  as applied, the last timer run. Doctor checks (a failed check) that the account exists and its current version in
  OpenBao is the one the host set, while the consent is given; and warns while a rotation waits, the last timer run
  failed, or SSH is on. Uses, check-outs and rotations are in fabric's audit log (and the journal).
- **1.7.1.4.8 D2's listing** (1.6.12.16.7): `fabricctl host accounts list` shows `local-admin` as managed by OpenBao,
  with no reminder, while fabric's record says it made it; any other account of that name is listed and reminded of
  as before.
- **1.7.1.4.9 Tests:** `tests/openbao/local_admin.py` against the real OpenBao image (the mount and policy, initial and
  rotated versions, current marked only after the host took it, check-out, policy, OpenBao sealed: the rotation waits
  and runs once it is back; the host's side stood in for: `chpasswd`, the journal and `wtmp` as files);
  `tests/samba/domain.py` against a real DC (the switch's store, its reads and writes, a read-only DC's refusal,
  `fabricctl local-admin ssh`, the Enterprise Admin's tier
  through fabric-agent's route code: fabric-admin and root allowed, a Directory Administrator and a delegated person
  refused); `tests/consent/run.py` (the consent item, its plan and undo); the sandbox on the real host (the account
  made, its password in OpenBao, SSH refused by default and allowed when on, a use seen and the rotation after it, a
  check-out, keep-until-checkout, OpenBao stopped: waiting then rotated, the CLI refused as anyone but root, the undo
  and uninstall removing it).

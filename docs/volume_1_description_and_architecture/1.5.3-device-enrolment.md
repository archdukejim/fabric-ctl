## 1.5.3.2 What a person gets

A person who may enrol devices (`pki:enrol`) opens the web console's Step-CA page, **Enrol a device**, and downloads
one file for one device:

- **iPhone, iPad, Mac:** a configuration profile (`<name>.mobileconfig`). Installed on the device, it trusts fabric's
  root CA, makes a key on the device (never exported), asks fabric's Step-CA for a certificate over SCEP with a
  one-time challenge (1.5.3.4), and, when a Wi-Fi name is given, joins that network with 802.1X EAP-TLS using the
  certificate, trusting only fabric's RADIUS server certificate (`hostname_radius`) issued by fabric's root. A Mac can
  have the wired 802.1X payload too.
- **Android and other devices:** a password-protected PKCS#12 (`<name>.p12`) holding a key made by fabric, its
  certificate and the CA chain; the password is shown once on the result page and kept nowhere (the key is not kept
  either, as for every key fabric generates, 1.5.1.1).

Either certificate may be linked to a directory device at once (optional): FreeRADIUS admits a certificate only through
its device, enabled and with `network:eap-tls` (1.11.1), so a Wi-Fi profile is only useful with a device chosen. The
person's own enrolments and every one made on the site are listed with their state and revoked there (1.5.3.7).

## 1.5.3.3 SCEP on fabric's Step-CA

Step-CA's own SCEP provisioner (Step-CA 0.30, the pinned image; smallstep's documentation and source, 2.3.5.4.2):

- **The provisioner `fabric-scep`** in `ca.json`, converged by setup's `pki` step on every run
  (`pki/scep/configure_scep_provisioner.py`, from `setup/init_pki._configure_ca_json`): `forceCN`, a minimum key of
  2048 bits, the request encrypted with AES-256-CBC (`encryptionAlgorithmIdentifier` 2), the root in `GetCACert`
  (`includeRoot`, for macOS), **no static challenge**: two webhooks decide instead (1.5.3.4) — `SCEPCHALLENGE` (is
  this challenge good?) and `NOTIFYING` (the certificate it issued, so fabric records it). Its certificates use
  fabric's `leaf.tpl` (so they name the CRL, 1.5.1.6) and live `scep_cert_days` (1.5.3.9).
- **The RSA decrypter (the "RA").** SCEP clients encrypt their request to an RSA key, and Step-CA's intermediate is EC
  (P-256, 1.5.2.1.13 is not applied). Step-CA 0.30 takes a provisioner's own RSA key instead
  (`decrypterCertificate`, `decrypterKeyPEM`, `decrypterKeyPassword`), which also signs its SCEP answers. Setup makes
  it **per install** (`pki/scep/ensure_scep_ra.py`): an RSA-3072 key and a certificate `scep-ra.<domain>` from the
  intermediate (digital signature and key encipherment), 730 days, issued again when it has under 90 days left or is
  missing; the key is kept encrypted (AES-256) in Step-CA's `secrets/scep_ra_key` (0600, the `step` user) with a
  password made per install (`scep_ra_password`, one of fabric's secrets: in OpenBao once the vault holds them,
  `deploy/generate_missing_secrets`). Step-CA reads its copy from `ca.json` (owned by `step`, 0600) and never needs
  OpenBao to start (1.2.8.5).
- **Served over plain HTTP**, as SCEP is (its messages are signed and encrypted; most clients, Apple's among them,
  speak HTTP): Step-CA's `insecureAddress` (port 9080 inside `fabric_net`, never published) and nginx's default HTTP
  server passing `/scep/` to it. The profile names `http://<hostname_stepca>/scep/fabric-scep` (`ca.<domain>`, a
  name fabric keeps, 1.5.1.6).
- **The webhooks** are HTTPS (Step-CA refuses any other), at `https://<hostname_mgr>/hooks/scep/challenge` and
  `/hooks/scep/issued`: the web console's nginx server, which asks for a client certificate. Step-CA presents its own
  TLS certificate when asked (its webhook client), and fabric's hook accepts a call only when nginx verified a client
  certificate from this CA naming `hostname_stepca`, `localhost` and `127.0.0.1` — the names Step-CA's own certificate
  carries and no service certificate does. Step-CA's webhook signature is no help here: a webhook in `ca.json` has no
  secret (Step-CA keeps webhook secrets only in its admin database, which fabric does not run; 2.3.5.4.2), so the
  client certificate is the hook's authentication.
- **The hook itself** is `fabric-scep-hook`, a small root service like `fabric-federation` (1.9.4): a unix socket
  mounted into nginx (`/srv/scephook/scep-hook.sock`), nginx's uid and root only, serving the two routes
  (`src/scephook/server.py` → `pki/scep/answer_hook.py`). Root because a notification links the certificate to its
  device in the directory (the domain's agent account) and records it in the ledger; hardened as the federation unit
  is. It exists only with the web console (`install_webui`): without the console there is no enrolment, the
  provisioner is not configured and `/scep/` answers nothing useful.

## 1.5.3.4 The one-time challenge

- **Made** when a person asks for an Apple profile (`pki/scep/create_challenge.py`): 32 random characters (192 bits),
  given to the person once, inside the profile; fabric keeps only its SHA-256, in
  `/opt/fabric/archive/scep-challenges.json` (root, 0600), with an id, the person who made it, when, its expiry
  (`scep_challenge_minutes`, 60 by default), the certificate name it is for (the profile's CN), the device to link, and
  its state.
- **Single use.** The first time Step-CA asks about a challenge it is spent, whatever the answer, and every later
  request with it is refused (`pki/scep/check_challenge.py`). One exception keeps a lost reply from stranding a
  device: the same SCEP transaction asked again after it was allowed (Step-CA retries a webhook once; a device
  resends its pending request) gets the same answer, and only that transaction. Refused too: an expired one, a withdrawn one, and a
  request whose CN is not the name its profile asked for — a challenge copied out of a profile cannot enrol another
  name.
- **Bound to the person** who made it: the challenge, the certificate it gives and the ledger entry carry their name;
  only they, or a person with `pki:revoke`, may withdraw it.
- **Audited:** `SCEP_CHALLENGE` (made: by whom, for which name and device, until when), `SCEP_CHALLENGE_USED`,
  `SCEP_CHALLENGE_REFUSED` (with why), `SCEP_CHALLENGE_WITHDRAWN`, `SCEP_ISSUED` (serial, name, device), each with the
  challenge's id and never the challenge.
- **Issued:** the notification hook records the certificate in the issued-certificate ledger (kind `scep`, the
  person as its issuer; `pki/scep/record_scep_issue.py`) and links it to the device chosen. A link that fails is kept
  in the challenge's record and shown in the list (the certificate is still listed and revocable), never silent.

## 1.5.3.5 The Apple profile

`pki/scep/make_mobileconfig.py`, a property list (`plistlib`) with these payloads, all removed with the profile:

| Payload | What |
|---|---|
| `com.apple.security.root` | fabric's root CA (DER) |
| `com.apple.security.scep` | `URL` (1.5.3.3), `Name` `fabric-scep`, `Subject` CN = the name given, `Challenge`, `Keysize` 2048, `Key Type` RSA, `Key Usage` 5 (signing and encryption), `Retries` 3, `RetryDelay` 10 |
| `com.apple.wifi.managed` (with a Wi-Fi name) | `SSID_STR`, `AutoJoin`, `EncryptionType` `Any`, `EAPClientConfiguration`: `AcceptEAPTypes` [13] (EAP-TLS), `TLSTrustedServerNames` [`hostname_radius`], `PayloadCertificateAnchorUUID` the root payload; `PayloadCertificateUUID` the SCEP payload |
| `com.apple.firstactiveethernet.managed` (a Mac, ticked) | the same 802.1X settings for the first active Ethernet port |

The profile is not signed (iOS shows it as "Not Verified"); it is downloaded straight from the console's answer
(`Content-Type: application/x-apple-aspen-config`), so opening the console on the iPhone itself installs it, and it
can be AirDropped or mailed. Not pinned: the SCEP payload's `CAFingerprint` — which certificate of `GetCACert` Apple
compares it with (the RA, the intermediate or the root) could not be confirmed from Apple's documentation, and a wrong
pin breaks every enrolment; left as an open point for a lab run (2.3.5.4.4).

## 1.5.3.6 The PKCS#12 for Android and other devices

`pki/scep/enrol_p12.py`: an RSA-2048 key (what every Android version and most supplicants take) and a certificate
named as asked, `scep_cert_days` long, from the intermediate (`leaf.tpl`, so it names the CRL), in a PKCS#12 with the
chain and a random password (20 characters) shown once on the result page and kept nowhere. The cipher:

- **Default: AES-256-CBC with PBKDF2, SHA-256 MAC** (OpenSSL 3's own default). Android 12 and later import it (PBES2
  arrived in Android's Conscrypt/BouncyCastle through a Mainline update; 2.3.5.4.2); Windows 10 1709+, macOS and iOS
  too.
- **"For Android 11 and older"** (a box on the form): 3DES with a SHA-1 MAC, the only form those versions read. It is
  the weaker cipher, chosen per file, said on the form and recorded in the audit and the ledger entry; the password
  is long and random, which is what protects the file.

Recorded in the ledger as kind `enrol-p12` and audited `PKI_ENROL_P12` (name, device, cipher; never the password).

## 1.5.3.7 The list, withdrawing and revoking

The **Enrol a device** view lists: open challenges (not yet used, not expired: who made it, for which name and device,
until when) with **Withdraw**; and every certificate issued by enrolment (kind `scep` or `enrol-p12`: name, device,
who, state as in 1.5.1.3, a link failure if any) with **Revoke** (`pki:revoke`, the revocation of 1.5.1.3: the CRL at
once, FreeRADIUS refuses it). Agent route GET `/v1/pki/enrolments` (`pki/scep/list_enrolments.py`).

## 1.5.3.8 Permissions, routes and the audit

- **`pki:enrol`** (new): make an Apple profile or a PKCS#12 for a device, and withdraw one's own open challenge. In
  the admin bundle, `fabric-pki-operator` and `fabric-equipment-operator`. Linking at enrolment needs no
  `pki:link-device`: the link is part of the enrolment and audited with it.
- **Agent routes:** POST `/v1/pki/enrol/apple` (body `name`, `device`, `ssid`, `wired`) → `{filename, profile_b64,
  expires, id, cn}`; POST `/v1/pki/enrol/p12` (body `name`, `device`, `legacy`) → the PKCS#12 and its password;
  POST `/v1/pki/enrolments/<id>/withdraw`; GET `/v1/pki/enrolments` (`pki:read`). Revoking is POST `/v1/pki/revoke`.
- **Web console:** Step-CA → *Enrol a device* (`/stepca?view=enrol`); forms POST `/stepca/enrol/apple` (answers the
  profile itself), `/stepca/enrol/p12` (the result page with the download and the password), `/stepca/enrol/<id>/
  withdraw`.
- **The hook's routes** (not agent routes, not for people): POST `/hooks/scep/challenge`, `/hooks/scep/issued` on
  `hostname_mgr`, for Step-CA only (1.5.3.3).

## 1.5.3.9 Settings

| Setting | Default | What |
|---|---|---|
| `scep_challenge_minutes` | `60` | How long an Apple profile's one-time challenge may be used: a whole number of minutes, 5 to 1440 |
| `scep_cert_days` | `365` | How long a certificate from enrolment lives (SCEP and the PKCS#12): 1 to `pki_manual_max_days` days |

Both checked at every apply (`pki/scep/check_scep_settings.py`, from `deploy/check_settings`). `scep_cert_days` is
written into the provisioner's lifetime by setup's `pki` step.

## 1.5.3.10 Device management (MDM): after 1.0

Decided with 2.1.5.12: device management is evaluated after 1.0 — Fleet first (it manages Apple devices with its own
MDM and runs osquery), then NanoMDM (an Apple MDM core), and Headwind MDM for Android. Nothing of it is built. A
device enrolled by hand today would be re-enrolled through an MDM then; the SCEP provisioner and its challenge
webhook are what an MDM would use too.

## 1.5.3.11 Tests

Written 2026-10-12, **not run** (the owner's direction): `tests/pki/enrol.py` (no Docker: a CA laid out as an
install's, as `revocation.py` does), `tests/pki/scep.py` (the real Step-CA image: the RA certificate, the provisioner
converged into `ca.json`, the CA starting with it and answering GetCACaps and GetCACert), the agent's routes in
`tests/pki/run.py`, the web forms in `tests/webui/test_container.py` and `test_devserver.py`, nginx and the hook's
unit in `tests/render.py`. A device really enrolling is a lab test (2.3.5.4.1).

- the challenge: made, used once, **refused on reuse**, refused **after its expiry**, refused for another CN,
  withdrawn and refused, only its maker or `pki:revoke` withdraws; only its hash on disk;
- the hook: a call without Step-CA's client certificate refused, a call with another fabric certificate refused, the
  notification recording the certificate in the ledger with its device;
- the profile's contents: the payload types, the SCEP URL, the CN, the challenge, the root's DER, the Wi-Fi
  settings (EAP-TLS, the RADIUS name, the anchor), the wired payload only when asked;
- the PKCS#12: **opens with its password** and **is refused with a wrong one**, both ciphers (the legacy one's
  algorithms are 3DES and SHA-1), the certificate's lifetime and CRL point, nothing stored;
- **revoke**: an enrolled certificate revoked lands in the CRL and is listed revoked;
- the settings: accepted and refused values.

A run needs: the `pki` suite (`sudo tests/run-all.sh pki`, Docker for its Step-CA part), the `render` and `nginx`
suites (the `/scep/` and `/hooks/scep/` locations, the hook's unit), the `webui` suite (the view and forms), and, for
the devices themselves, the lab: a real iPhone or Mac and an Android phone against the sandbox or the test Pi with a
switch or access point doing 802.1X (2.1.1.45's VMs cannot stand in for a phone).

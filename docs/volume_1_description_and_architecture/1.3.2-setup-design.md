## 1.3.2.1 Setup: secure by default, fully scriptable

`sudo fabricctl setup` (first run, or `--reconfigure` later):

1. Preflight (architecture, RAM, cgroup memory controller, Docker, ports).
2. Shows **the full list of changes it will make by default** — every one a
   hardened choice — then offers **Proceed** or **Advanced**.
3. **Advanced** holds only permanent choices (the CA root's lifetime, before
   the CA exists); every other item is changed after the install, the plan
   stating what relaxing it costs (2.1.2.16, since 0.6.4).

Default plan (each item is a setting under `security:` / `updates:` /
`vault:` in `fabric.yaml`):

| Item | Default | Can relax to |
|---|---|---|
| Host firewall (nftables) | On: only fabric's service ports inbound; management (443/`mgr`, SSH) from `lan_cidr` only | Off, or custom allow-lists |
| Container hardening | On: non-root, `cap_drop: ALL`, `no-new-privileges`, read-only root where possible | Per-service exceptions |
| Docker daemon | Hardened `daemon.json` (`no-new-privileges`, `icc: false`, `userland-proxy: false`, `live-restore`) | Stock daemon config |
| userns-remap | **On** (container root → unprivileged host uid; fabricctl shifts bind-mount ownership) | Off |
| Rootless Docker | Off | On, with stated limits: Kea DHCP unavailable, DNS/RADIUS source-IP ACLs need the slower slirp4netns/pasta port driver |
| OpenBao unseal | Local key file | USB kill switch, any KMIP key manager, any PKCS#11 HSM, or manual Shamir |
| Image updates | On: signed stable channel, weekly, health-checked with rollback | Off, candidate channel, or offline-only |
| Web UI access | mTLS + Keycloak OIDC + TOTP | TOTP optional |

Non-interactive: `sudo fabricctl setup --file ./vars.yaml` takes every
answer (including all of the above) from the file; the walkthrough only
prompts for missing or invalid values. `--non-interactive` never prompts
and fails on anything missing — for automation and re-provisioning.

Every setting can be changed later (`fabricctl security …`,
`fabricctl vault seal-…`, `fabricctl updates …`, or editing `fabric.yaml` +
`fabricctl --apply`). `fabricctl status` and the fabric-ctl web UI show a
**security posture** summary that lists every relaxed default as a warning.

> **Built:** the Proceed / Advanced / Quit plan (`fabriclib/setup/choose_plan.py`)
> with `--file`, `--non-interactive`, `--yes`, `--offline` and `--step`; re-running
> `fabricctl setup` is the reconfigure (there is no `--reconfigure`). Settings are
> saved to `/opt/fabric/config/fabric.yaml` and rendered to `vars.yaml`. What the
> plan covers today:
>
> - Firewall: **UFW** (SSH from the LAN only) plus `DOCKER-USER` iptables rules
>   so Docker-published ports are LAN-only, re-applied at boot by
>   `fabric-firewall.service` (`security.firewall`, `security.firewall_allow`) —
>   not nftables.
> - Docker daemon hardening as in the table (`security.docker_daemon_hardening`).
> - Container hardening: always on (no per-service setting).
> - Optional services: Keycloak and the web UI on, and Kea, FreeRADIUS and Fluent
>   Bit off, turned on after the install (2.1.2.16).
>
> **Not built:** userns-remap and rootless Docker (2.1.2.2), the image-update item
> (image updates follow 2.1.14.3 instead: applied only by `fabricctl images update`),
> the "TOTP optional" relaxation, `fabricctl security …` / `fabricctl updates …`,
> and the security posture summary in `fabricctl status` and the web UI.
> OpenBao's unlock is chosen after setup with `fabricctl vault …` ([1.7.1.1](1.7.1-openbao.md#1711-secrets-openbao)).

## 1.3.2.2 Permanent answers are marked (0.7.0)

**Designed 2026-10-11 for 0.7.0 (decision 2.1.2.20); built 2026-10-11** (as built: the end of this topic). Setup
asks what cannot be changed later
(2.1.2.16), but the questions did not say which they were: the owner, answering the host's name, could not tell.

- Every question whose answer cannot be changed after the install carries a yellow **⚠ Permanent** after its label,
  in setup's questions and in Advanced: fabric's DNS domain, the AD domain, the DC's name (1.6.5.23), the
  organisation's name (it names the CA), and the CA settings Advanced offers (the root's lifetime).
- The list is one place in the code, the vars editor's `IMMUTABLE_KEYS`, so the label and the editor's refusal
  cannot disagree; the organisation's name counts as permanent because the CA's name is made from it.
- Without a terminal's colours (`NO_COLOR`, not a TTY) the label is the same words, uncoloured.
- **Tests:** the consent suite reads each permanent question's prompt and finds the label, and none on a question
  that can change (the IP, the subnet, the gateway, the host's name).
- **As built:** `setup/permanent_mark.py` gives the label for a key in `IMMUTABLE_KEYS`; `collect_vars` (the DNS
  domain, the organisation's name), `ask_ad_domain`, `ask_dc_name` and Advanced's CA lifetime put it after their
  label. `friendly_name` joined `IMMUTABLE_KEYS` (the vars editor now refuses it too) and `hostname` left it
  (1.6.5.23). The console's colours (`common/console.py`) now also stay off with `NO_COLOR`. The consent suite also
  checks the label is yellow on a terminal and the same words without colour under `NO_COLOR`.

## 1.3.2.3 Setup's work survives a dropped session (0.8.0)

**Designed and decided 2026-10-15 for 0.8.0 (decision 2.1.2.26).** The owner's SSH session dropped during
`sudo fabricctl setup`, in the certificates step, and setup died with it, half-way. Setup now hands its work to
systemd once the last question is answered, so the session only watches.

### 1.3.2.3.1 Two halves: the questions in the session, the work in a unit

- **The questions stay in the person's session**, as before: the start ([G]uided / [A]dvanced), the settings, the
  first admin's password, the join invitation, the plan and its one yes (1.2.9.11), the consent answers. Any refusal
  before the first step (a missing answer unattended, the ports declined while ufw is on) is said there, and nothing
  is started.
- **The work after the last answer** — every step in [3.3.3](../volume_3_installation/3.3.3-setup-steps.md),
  from `preflight` to `ready`, then *fabric is ready* and the first steps — runs as a transient systemd unit,
  `fabric-setup.service`, started with `systemd-run --unit fabric-setup --collect` running
  `fabricctl setup --worker <run>`. `--worker` is internal (hidden from `--help`) and refuses a run that is not the
  one recorded (1.3.2.3.3).
- The unit has no terminal: a question a step would ask takes its unattended answer. Two steps had one: the site's
  number at `start` takes the suggestion, said in the log with how to change it (`fabricctl ipam block`, 2.1.10.16;
  open point 2.3.2.4.5), and the first admin's password, when the `admin` step finds no such person though setup did
  not ask for one, is refused as unattended (the message names `--admin-password-file`);
  `sudo fabricctl setup --step admin` stays in the session and asks.
- Every full run takes this path, unattended ones too (`--file`, `--non-interactive`, the `restore` and `reinstall`
  that end in setup). `--step` (a repair, also run by fabric's own programs), `--undo`, `--list` and `doctor` stay in
  the session as before.
- On a host not booted with systemd (no `/run/systemd/system`) setup says so and runs the steps in the session, as
  before, still keeping the run record.

### 1.3.2.3.2 Following, detaching, re-attaching

- The unit writes everything it prints (stdout and stderr) to `<config>/setup-run.log` (0600); the console prints
  that log as it grows, so a person sees what they saw before (without colours: the unit has no terminal). The
  previous run's log is kept as `setup-run.log.1`.
- **The console's exit status is the run's result**: 0 when it finished (*fabric is ready*), 1 when a step stopped
  it (its message is in the log, ended by how to go on), 130 when a step was interrupted.
- **Ctrl-C while following detaches**: the console says the work goes on as `fabric-setup.service` and how to follow
  it again (`sudo fabricctl setup`, or `journalctl -u fabric-setup` for systemd's own lines), and exits 130. It never
  stops the work. A dropped connection is the same, without the message.
- **`sudo fabricctl setup` while the unit runs re-attaches**: no questions, a line saying a setup is already running,
  then the log from the start of that run and on to its end, and its result as the exit status. Options given then
  are not used (the running setup has its answers).

### 1.3.2.3.3 The run record and resuming

- `<config>/setup-run.yaml` (0600) records each full run: its id, the steps done so far, the step running, the
  services whose configuration changed (the `start` step restarts them; held in memory before), the options the
  steps read (offline, the plan's mode, whether a join or a first admin's password was part of it, the
  `--admin-password-file` path) and, at the end, its state (`done` or `failed`) and result. It holds no secret.
- Before `deploy` has run, each step's settings are saved to `fabric.yaml` as it ends, so a resumed run starts from
  what the steps before it found (the `join` step adds the organisation's settings).
- When `sudo fabricctl setup` finds no unit running and the record says the last run did not finish (`failed`, or
  still `running` because its process died: the host restarted, the unit was killed), it **resumes from the first
  step that did not finish**: no questions, except, when a step still ahead needs one, the first admin's password
  (the `admin` step, when that run had one) and the join invitation (the `join` step). Steps are idempotent
  (3.3.1.1); where one is not across a stop, 2.3.2.4.3 says so.
- `--restart`, `--file` and `--join` start over: the questions again, every step (they bring new answers).
  A finished run's record changes nothing: setup behaves as before.
- `restore` and `reinstall` put the config folder back from a copy; they remove a copied run record, so the setup
  they end in starts over.

### 1.3.2.3.4 Secrets handed to the unit

- The secrets setup holds in memory between its questions and its steps are two: the first admin's password
  (2.1.6.33: memory only, never saved) and the join invitation (it carries the join's secret). Every other secret is
  in fabric's secrets file or OpenBao already.
- The console writes them to `/run/fabric/setup-<run>.handoff`: created new (`O_EXCL`, no symlink followed), 0600,
  owned by root, on tmpfs (gone at a restart). The unit's command line names only the run; its environment holds no
  secret (`systemctl show` shows both to any user). The worker reads the file once and removes it before its first
  step, refusing one that is not a root-owned 0600 regular file. A failed start removes it; a later run removes one
  an earlier run left; uninstall removes any left.
- The unit's environment carries only names: `SUDO_USER` (whose home receives `~/fabric-admin`), `SSH_CONNECTION`
  (the firewall step's lockout guard), `HOME=/root` and Python's output settings.

### 1.3.2.3.5 What it leaves on the host

- `--collect` unloads the transient unit when it ends, failed or not: nothing is written under `/etc/systemd`, and
  nothing of it is left to undo (global Rule 12). The run record and the log are in fabric's config folder, removed
  with it; the hand-off file is gone once read.
- **Uninstall stops a running `fabric-setup.service` first**, before it removes anything, and removes any hand-off
  file left in `/run/fabric`.

### 1.3.2.3.6 As built

Built 2026-10-15 for 0.8.0: `fabriclib/setup/detach/` (one unit per file; its README lists them), called from
`setup/run_setup.py` for full runs; `setup/run_steps.py` is the step loop shared by the unit, a run in the session and
`--step`; uninstall and restore changed as above. Tests and the idempotency review: 2.3.2.4.

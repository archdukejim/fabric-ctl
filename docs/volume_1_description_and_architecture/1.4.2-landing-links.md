## 1.4.2.1 Landing Page Links (`link-vars.yaml`)
The `link-vars.yaml` file (`<deploy_base_dir>/fabric/config/link-vars.yaml`; until it exists, the shipped `config/link-vars-template.yaml`) defines the dynamic list of quick links shown on the landing portal. It is managed interactively via `fabricctl` under the **Landing Page Links** menu.

### 1.4.2.1.1 `links`
**Description:** A list of dictionaries containing `name` and `link` keys for each quick link to display on the landing page. The `link` values can use Jinja variables like `{{ domain }}` or `{{ hostname_keycloak }}` which will be evaluated natively during deployment.

**Default Value:**
```yaml
links:
  - name: Keycloak (Admin)
    link: "sso.{{ domain }}/admin"
```

**Effected Jinja Templates:**
- `nginx/www/landing/index.html.j2`

## 1.4.2.2 Links from DNS records (0.6.1, 2.1.4.2)

The owner (2026-10-07): a name added to the site's zone, such as `host1.<domain>` for a Proxmox host, can appear on
the landing page as a link, beside the links of 1.4.2.1.

- **Only records marked for it** (2.1.4.2): an A, AAAA or CNAME record of the site's zone (`dns.dynamic_zone_var`) may
  carry `link: {label, port, path}`. Records without it (printers, switches, anything that is not a web page) are
  not listed.
- **The address:** `https://<name>.<domain>` with the record's `port` (e.g. 8006 for Proxmox VE) and `path` when
  set; `label` is the text shown (default: the name). Only https links are made.
- **Who sees them:** everyone on the LAN, like the rest of the landing page (no sign-in). Only marked records are
  listed, so the page never shows the zone as a whole.
- **Where it is set:** the web console's DNS tab, in the landing page's own section since 0.7.1 (1.4.2.4; until
  then *Add record*: *Show on the landing page*, and a link changed only by deleting the record and adding it again)
  or the settings file (`link:` on the record).
  Validated with the record (`validate_record`): a label of up to 60 printable characters without `<`, `>`, `"` or a
  backslash, a port 1–65535, a path starting with `/` without spaces, quotes, backslashes or `<>`. Wildcard names
  are never listed. The mark is not part of the zone: BIND's zone file is the same with or without it.
- **When it shows:** the landing page is rendered by every apply, so a link appears or goes with the apply that
  changes its record. The links are listed as "This network", sorted by label, after fabric's own and before the
  `link-vars.yaml` links.

## 1.4.2.3 The info page at info.<domain>

Built in 0.6.3 (decision 2.1.4.3). The landing page — the instructions, the CA download, the manual and the "This
network" links — lives at **`info.<domain>`** (`landing_page_cname`, default `info`; a value an admin set is kept).

- **Over plain HTTP too, with no redirect:** a new device opens `http://info.<domain>/`, downloads the root certificate
  from `/certs/` (every system's format; since 0.7.0 the only place by name, `certs.<domain>` dropped: 1.5.1.5) and checks it against the root's SHA-256
  fingerprint shown on the page (read from `/certs/ca-certs.json`) before trusting it. Over HTTPS it is the same page.
  The manual (`/manual/`) and the "This network" links stay on HTTPS: the page links to them there.
- **`<domain>` and the host's own name redirect** (301) to `info.<domain>`: HTTP to its HTTP page, HTTPS to its HTTPS
  page, so old bookmarks keep working. `<domain>` keeps its A record for this (unless the admin's own records name it),
  and BIND gets `info` like the other names; the page's service certificate names all three.
- **Revised in 0.7.1 (2.1.4.6, 1.4.2.5):** `<domain>` and the host's own name serve the page themselves instead of
  redirecting, and `info` is an ordinary record the admin may rename, repoint or delete.

## 1.4.2.4 The landing page's own section of the DNS tab (0.7.1)

Built for 0.7.1 (decision 2.1.2.22 item 4; the owner at the 0.7.0 test install: "What's the 'landing' page?
wouldn't that be set on some other device or tab?"). How to use it: 4.4.4.2.

- **Its own section:** BIND9 tab → *Landing page* (`/bind9?view=landing`), beside *Forward zones*. It says what the
  landing page is (fabric's start page at `info.<domain>`: the instructions, the CA certificates, the manual and a
  link to each of your services) and lists its links: the label, the address it opens
  (`https://<name>.<domain>[:port][/path]`), the record, and *Remove*. *Add a link* picks a record of the site's zone
  (A, AAAA or CNAME, never a wildcard) and takes a label, a port and a path; linking a record that is linked already
  replaces its link. The record form no longer asks about the landing page (1.4.1.4).
- **The same storage, so nothing migrates:** the link stays on the record (`link: {label, port, path}`, 1.4.2.2,
  2.1.4.2), checked by the same rules (`dns/common/landing_link.py`, shared by `validate_record` and the new unit).
  `dns/set_record_link.py` sets or clears it on one record, only if it is still the record the page showed (the
  name at its position), locked and audited (`DNS_LINK`, `DNS_UNLINK`); refused: another zone, another type, a
  wildcard, a stale record, a bad label, port or path.
- **Route and permission:** `POST /v1/zones/<key>/records/link` (`dns:write`, like a record), body `type`, `index`,
  `name`, `link` (`on` links, anything else unlinks), `link_label`, `link_port`, `link_path`; the console's forms
  post to `/bind9/landing/add` and `/bind9/landing/remove` (`webui/routes/landing_post.py`). Apply publishes the
  page, as for a record.
- **Tests:** the `webui` suites: the section and its forms per bundle; a link saved on the record through the real
  agent and listed, removed again; refusals (a port out of range, a path without `/`, a stale record, no record
  picked, a TXT record, the auditor's 403).

## 1.4.2.5 The landing page at a path; `info.<domain>` an ordinary alias (0.7.1)

Built for 0.7.1 (decision 2.1.4.6; the owner, 2026-10-12: "we can just make it [fabric-host ip]/info and then
whatever DNS record they want is just an alias to that"). Before it, `info.<domain>` was load-bearing (2.3.1.19.5).

- **Where the page is.** fabric's nginx (`templates/nginx/nginx.conf.j2`) serves the landing page at **`/info/`** on
  every name and address that reaches it on plain HTTP (the default server: `http://<host_ip>/info/`), and at `/`
  and `/info/` on its landing names over HTTP and HTTPS: `hostname_landing` (rendered once at install, `info.<domain>`
  by default), `<domain>` and the host's own name, which the page's certificate names. `<domain>` and the host's name
  serve the page themselves; they no longer redirect to `info.<domain>` (2.1.4.3, revised). `/certs/` stays where it
  is on every name (1.5.1.5); the page's own links are relative (`/certs/`, `/manual/`, `/style.css`), so it works at
  whatever name or address it is opened.
- **Any other name pointing at the host** shows the page: the default server sends a request for `/` on a name that
  is not one of fabric's HTTPS services to `/info/` (302), and `/manual/` to the host's own name over HTTPS. fabric's
  service names (`dns`, `ca`, `vault`, `sso`, the console's, `federation`) still go to HTTPS (an nginx `map` lists them).
  Over HTTPS such a name has no certificate (2.3.1.20.7). **Revised by 1.4.2.6 (2.1.4.8):** every alias of the host
  the zone holds at an apply is a landing name, served at `/` over HTTP and HTTPS with the page's certificate; only a
  name the zone did not hold at the last apply (or one a hosts file alone knows) falls to the default server.
- **`info.<domain>` is the admin's.** The render that installs a site (the one that also fixes `hostname_landing`)
  adds `info` (`landing_page_cname`, default `info`) to the site's zone as an ordinary CNAME to the host; later renders
  never add it back. An install upgraded from 0.7.0 keeps the record it has, which goes on working. The DNS tab no
  longer marks or refuses it (`dns/common/fabric_record.py` no longer lists it): the admin deletes it, adds it under
  another name, or points it at another machine. `landing_page_cname` now only names that first record and
  `hostname_landing`.
- **Nothing of fabric's names `info`.** The CRL point in certificates (1.5.1.6), the install and join scripts, the
  certificate page's commands, the console's PKI and RADIUS guides, setup's last words, the ACME help and the admin's
  README name the CA's files at `http://<hostname_stepca>/certs/` (`ca.<domain>`) and `http://<host_ip>/certs/`;
  `ca.<domain>` opened in a browser goes to the host's own name's `/certs/`; a site fetches another site's CRL at
  `ca.<their domain>` (then `info.<their domain>`, for a site whose `ca` name is another); `fabricctl doctor` checks
  the host's own name and `http://<host_ip>/info/` instead of `info.<domain>`.
- **Tests:** `tests/render.py` (the page at `/info/` on the default server and the landing names, the map, no
  redirect to `info`; the first render adds `info`, a later one does not add it back once deleted; `info` is not
  fabric's, `ca` is); the `nginx` suite (the rendered configuration in a real nginx: `/info/` by address, `/` on an
  unknown name to `/info/`, a fabric name to HTTPS); the `webui` suites (deleting `info` through the real agent and
  adding it pointing elsewhere; `ca` and the host's A still refused).

## 1.4.2.6 The landing names follow the zone; HTTPS at a renamed alias (0.7.1)

Built for 0.7.1 (decision 2.1.4.8; the owner, 2026-10-12, answering 2.3.1.20.7: "B mint a new certificate, probably
should revoke the old one, and it should have up and only the new url for the landing page"). Revises 1.4.2.5's
landing names.

- **The landing names** (`dns/common/landing_names.py`, one function for nginx, the certificate and doctor): the
  host's own name, `<domain>`, then every record of the site's zone (`dns.dynamic_zone_var`) that points at the host,
  sorted: an A record to `host_ip`, or a CNAME whose target is one of the host's names (a relative target is under
  `<domain>`, one ending in `.` is absolute; CNAMEs to CNAMEs are followed). Left out: wildcards and names that are
  not host names (`_acme-challenge`), fabric's own records (`dns/common/fabric_record.py`: `ca`, `dns`, `sso`,
  `vault`, `ntp`, the console's, `federation`), and the names fabric's other services answer at (`hostname_bind9`,
  `ns`, `hostname_stepca`, `hostname_openbao`, `hostname_keycloak`, `hostname_mgr`, `hostname_federation`,
  `hostname_radius`, `hostname_dc`, `filter`): each has its own certificate and nginx server. A record pointing at
  another machine is never one. On a new install the names are the host's, `<domain>` and `info.<domain>`, as before.
- **nginx** (`templates/nginx/nginx.conf.j2`) renders the landing servers' `server_name` from them through the Jinja
  global `landing_names()` (`common/jinja_env.py`), so a renamed alias answers at `/` over HTTP (no redirect) and HTTPS,
  and its `/manual/` over plain HTTP goes to HTTPS at the same name. The page's own links stay relative (1.4.2.5): they
  work at any name. A name the zone did not hold at the last apply still gets the default server (1.4.2.5).
- **The certificate** holds exactly the landing names: CN the host's own name (a name fabric keeps), the others as
  subject alternative names. Its folder keeps its name, `<base>/nginx/certs/<hostname_landing>/`, which nginx reads;
  `hostname_landing` is a landing name only while a record points it at the host. How it is issued again and what
  happens to the one it replaces: 1.5.1.7.
- **When it changes:** records are published by an apply (1.4.1), so the names change at the apply: it renders
  nginx with the new names, then, with the services up, issues the certificate again when its names differ
  (`deploy/renew_landing_cert.py`, the last step of `deploy/apply_deployment.py`). Setup's `certs` step and the
  nightly `fabric-certs.timer` make the same comparison (`setup/mint_service_certs.py`), so a missed one converges.
  Before the first certificate exists (a new install's deploy step) the apply issues nothing: setup's `certs` step
  does.
- **Doctor** (`setup/verify_install.py`) checks that the certificate holds the landing names (saying which are not yet
  on it, or no longer, until an apply) and checks HTTPS at each name it holds, the host's own name and `<domain>`.
  The host-trust check uses the host's own name.
- **Upgrade:** a certificate issued before (CN `info.<domain>`, names info, the host's and `<domain>`) holds the
  same names while `info` points at the host, so it is left to its renewal; a renamed or repointed `info` is issued
  again by the upgrade's `certs` step.
- **Tests:** `tests/render.py` (the names: a renamed alias, a CNAME chain, an absolute target; never the old name,
  another machine, a wildcard, `_acme-challenge`, fabric's records or another service's name; nginx's server names
  from them, the certificate's folder kept); the `nginx` suite (the rendered configuration in a real nginx); the `pki`
  suite (`tests/pki/landing.py`, the real Step-CA image: setup issues the names, an apply after a rename issues it
  again without the old name and revokes the one it replaced; nothing issued while current or before the first;
  a failed revocation reported, the new certificate kept).

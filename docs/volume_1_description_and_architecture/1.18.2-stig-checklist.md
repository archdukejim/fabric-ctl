## 1.18.2.1 The data file

The checklist is one tab-separated file, [`assets/stig-checklist.tsv`](assets/stig-checklist.tsv): one row per part
and requirement (or requirement group, 1.18.2.4), with the part's answer. It is data, so a test can read it
(1.18.2.5), the console can show it (1.18.2.7) and a change to an answer shows in a diff beside the code that changed
it. It covers fabric's own parts (1.18.1.4) against the four application-level guides; the members' OS STIGs are not
rows here: they are what the baselines of 1.18.3 apply, and a member's compliance is the scan of 2.1.18.16.

## 1.18.2.2 Its columns

| Column | What |
|---|---|
| `parts` | one or more part names of 1.18.1.4, comma-separated, when they share the answer |
| `guide` | `ASD`, `API`, `AS`, `DNS-SRG`, `BIND` (later `ADD`, `DB`, `WEB`, `AAA`, ... with 2.1.18.4) |
| `version` | the guide's version the row was answered against, `V6R5` and so on |
| `req` | a rule's DISA id (`V-222536`), or a group's id (`ASD-12`) in the first pass |
| `rules` | for a group: the rules it holds (`V-222536..V-222548`); for a rule: its SRG id |
| `title` | short, in fabric's words |
| `cat` | the highest severity in it: `I`, `II`, `III` |
| `answer` | one of the four of 1.18.2.3 |
| `evidence` | for `met`: the manual section and the test (`tests/<suite>/...`); for `to-build`: what is missing; for `exempt-dod`: which kind of 1.18.1.5.1; for `n/a`: why |
| `decision` | the 2.1 decision that shapes it, if any |

Lines starting with `#` are comments; the first non-comment line is the header.

## 1.18.2.3 The four answers

- **`met`**: fabric does it today, in the part's shipped configuration, and a test proves it (1.18.2.5).
- **`to-build`**: it applies and fabric does not do it yet, or does it only in part (the evidence says which), or a
  decision must settle it first (the decision column names it).
- **`n/a`**: it does not apply to the part (no SOAP in fabric, no API served by the part, and so on), with why.
- **`exempt-dod`**: it applies only to the DoD as an organisation (1.18.1.5.1, by its kind number); the technical
  requirement under it, if any, has its own row.

## 1.18.2.4 The first pass: by requirement group

**The first pass (2026-10-22) is by requirement group, not by rule.** DISA's rules come in runs that ask the same
thing of the same mechanism (ASD V-222413 to V-222421 audit each kind of account change; BIND V-272375 to V-272378 the
TSIG keys' files), so each group is one row per set of parts that answer it alike, with the group's rules listed. It
was written from the guides' rule lists as published on the mirrors on 2026-10-22 (2.3.18.2), against the manual and
the templates as they are on `dev/0.8.0`; an answer is `met` only where the manual or the template shows it and a
named suite checks it, otherwise `to-build`. A group whose rules would not all get one answer is split when a feature
reaches it (1.1.6.5). The per-rule pass, every V-id of each guide on its own row, is open (2.1.18.17).

## 1.18.2.5 How a "met" is proven

- Every `met` row names a test in `evidence`: a suite file under `tests/` that checks the property against the real
  container (the global Rule 9: real components, the refusal too). A docs check is to be built in `tests/docs/`
  (`check_stig.py`): the file parses; every `parts` name is one of 1.18.1.4's; every `answer` is one of the four; every
  `met` names an existing test file; every `exempt-dod` names a kind 1..7; every `decision` exists in 2.1.
- Configuration rules (BIND's `version none`, nginx's TLS versions, a container's user) are checked by reading the
  running service: the suites already do this for hardening (the `hardening` suite, 1.2.7.1); STIG rows extend them.
- Behaviour rules (lockout after N failures, idle sign-out, token expiry) are checked by doing it: N failed sign-ins
  against Keycloak and the DC, then the refusal.
- Scans: the members' baselines, and the host's if chosen, are proven by a SCAP scan in the lab (2.1.18.16).

## 1.18.2.6 Keeping it current

DISA publishes quarterly. A new version of a guide is read when its quarter's release appears: rows whose rules changed
(DISA's "digest of updates") are answered again, new rules added, removed rules marked removed (their row kept, the
answer `n/a` and why, as 5.7 keeps numbers). The `version` column shows which rows are behind.

## 1.18.2.7 How it is shown (to build)

To build in 0.11.0, after 2.1.18.6 settles the profile: `fabricctl stig report [--part <part>] [--answer <answer>]`
and the console's **Security → STIG** page show the checklist as it shipped with the release, the counts per part and
answer, and, for this install, the rows whose answer depends on a setting (a log-forwarding target, a banner, the
profile) with the setting's value; `fabricctl doctor` warns on each such row the install leaves unmet.

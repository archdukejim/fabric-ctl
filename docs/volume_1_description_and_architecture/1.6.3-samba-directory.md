## 1.6.3.2 What the directory is

One Samba AD domain is fabric's only directory (2.1.6.6). It holds everything 389-DS holds today — people, groups,
POSIX ids, devices and their roles, the address plan — plus what only AD gives: Windows machine accounts, Group
Policy, Kerberos for Linux, the NT hashes PEAP-MSCHAPv2 needs, one password per person. Every site runs a domain
controller (DC) of the type it chose — writable, read-only or none (S2 revised, 2.1.6.7) — and the full stack beside
it (2.1.9.9).

## 1.6.3.3 The domain and its name

- The **AD domain** is chosen at setup on the first node (the root site), with no default, and is permanent (2.1.6.11).
  The installer suggests a **protected sibling** at the top of the organisation's name, apart from the sites'
  names: `ad.` plus the domain without its first label (`lan.j-j.family` → `ad.j-j.family`). A two-label domain has
  no parent to sit beside, so it gets a sub-domain: `ad.` plus the domain (`home.arpa` → `ad.home.arpa`; owner
  2026-10-08, so Enter always takes a suggestion; until 0.6.1 it got none). Any domain will do except fabric's own or a parent of it — **same-domain mode was dropped** (2.1.6.11
  revised, 2026-10-04), so fabric's zones and the AD zone never share a name; a sub-domain (`ad.lan.j-j.family`)
  stays allowed. Sites get the domain from their invitation.
- Realm = the domain upper-cased; the NetBIOS name is its first label (at most 15 characters, settable once).
- The base DN follows from the domain (`DC=ad,DC=example,DC=org`); `ldap_base_dn` (M1b, F10) is no longer a
  setting.
- One domain, one forest: Samba has no child domains (Q5). Sites are OUs.

## 1.6.3.4 Layout: everything under OU=sites

Everything fabric manages lives under `OU=sites`, one OU per site (2.1.6.12). AD's own containers (`CN=Users`,
`CN=Computers`, `CN=Builtin`, `OU=Domain Controllers`) are left as AD makes them; AD's defaults for new users
and new computers (`redirusr`, `redircmp`) point at the root site's `OU=people` and `OU=machines`, so nothing
created by Windows' own tools lands outside `OU=sites`.

```
DC=ad,DC=example,DC=org
└── OU=sites
    ├── OU=lan                      root site
    │   ├── OU=organisation         organisation-wide (only in the root site's OU)
    │   │   ├── OU=groups           fabric-admins, the RBAC bundle groups, fabric-break-glass, shared groups
    │   │   ├── OU=device-roles     roles any site may use
    │   │   └── OU=sudoers          sudo rules for every site
    │   ├── OU=people               this site's people
    │   ├── OU=groups               <site>-users, <site>-admins, the five role groups (2.1.9.13), <site>-<role> (2.1.9.11)
    │   ├── OU=machines             domain-joined computers (Windows and Linux)
    │   ├── OU=devices              802.1X devices (fabric's classes)
    │   ├── OU=device-roles         this site's own roles
    │   ├── OU=networks             this site's part of the address plan (1.10.2.8)
    │   ├── OU=sudoers              this site's sudo rules
    │   ├── OU=service-accounts     this site's fabric-agent, Keycloak and FreeRADIUS accounts
    │   └── OU=lab                  a site whose parent is lan: the same, without OU=organisation (2.1.6.20)
    │       └── OU=lab2             a site nested under lab
```

- **A site's OU is in its parent's OU** (revised 2026-10-05, 2.1.6.20; was: every site's OU one level under
  `OU=sites`). The root's OU is the only one directly under `OU=sites`; the parent is also recorded on the OU
  (`fabricParentSite`), and re-parenting moves the OU
  ([1.9.8.14](1.9.8-federation-on-ad.md#19814-nesting-and-inheritance)).
- A search that means one site's objects starts at that site's own sub-OU (`OU=people`, `OU=devices`, ...), never
  at the site's OU with a subtree scope, which would take in the sites below it.
- Site names are unique and never `organisation`.
- The site's AD Group Policy objects are linked to its OU (logon rights, 1.6.3.10); the trust GPO is linked to
  the domain.

## 1.6.3.5 fabric's schema in AD

fabric's own attributes and classes (devices, device roles, networks, sites: today's 11 attributes and 4 classes,
plus `fabricParentSite` and the per-site id block of 1.6.3.9) are added to AD's schema (Q3):

- OIDs under Microsoft's arc for unregistered extensions, derived from fabric's UUID:
  `1.2.840.113556.1.8000.2554.39383.57305.1842.18547.37174.2331831.2413377` (AD refuses the `2.25.<UUID>` arc).
- Loaded in two sessions (attributes, then the classes using them); every structural class carries a
  `defaultSecurityDescriptor` granting authenticated users read (Q9).
- sudo's schema with sudo's own registered OIDs (`1.3.6.1.4.1.15953.9`); Ubuntu no longer ships it.
- A schema extension is permanent: fabric adds, never changes or removes; a new attribute is a new OID.
- Devices are `device` + `ieee802Device` + fabric's classes, the MAC in `macAddress`; device roles are AD groups
  with the `fabricRole` class (members are device objects; `fabricRoleName` on devices stays, M1).

## 1.6.3.6 Who may write what: delegation per site

AD limits **who** writes, not which DC takes the write (Q12). The per-site limits of S2 are therefore limits on
accounts:

| Account or group | May write | Default |
|---|---|---|
| Domain Admins, the Administrator | everything | Used only at the root site, by setup and joins; the Administrator's password is in the root's OpenBao. No person is in Domain Admins by default |
| `fabric-agent-<site>` (each site's agent) | full control below `OU=<site>`, except `OU=service-accounts`; create and link GPOs for its own OU | read everywhere else |
| `fabric-agent-<root>` | as above, plus `OU=organisation`, the domain-linked trust GPO and the password policy | |
| `<site>-admins` (people) | member of the four role groups below by default | |
| `<site>-ou-admins` | the site's OU: people, groups, sub-OUs (not `OU=service-accounts`) | 2.1.9.13 |
| `<site>-machine-admins` | the site's `OU=machines` and `OU=devices` | 2.1.9.13 |
| `<site>-gpo-admins` | the site's two admin GPOs (admin settings, controls) and their SYSVOL folders; the site's OU's `gPLink` and `gPOptions` (its links and blocked inheritance; a parent's enforced link still wins) | 2.1.9.13 |
| `<site>-linux-sudo` | **[DELETED]** replaced in 0.9 by `<site>-fabric-admins` (1.6.11.3, 2.1.6.37): its members are moved there on upgrade | 2.1.9.13 |
| `<site>-fabric-admins`, `fabric-admins` (people) | nothing in AD: the site's `sudoRole` (`CN=<site>-fabric-admins`) lets them run any command as root on the site's Linux machines and those of the sites below (1.6.11) | 2.1.6.37 |
| `<site>-windows-admins` | nothing in AD: the site's log-on GPO makes the group a member of each Windows machine's local Administrators (Restricted Groups "member of": added, never replacing) | 2.1.9.13 |
| Keycloak's account | people and groups of its site (writable sign-in, password changes) | |
| FreeRADIUS's account | read only | |

- **Overrides** (S2's "listed limits, overrides in the Federation tab"): an override adds an ACL granting a site's
  agent and admins rights on another site's OU (all of it, or one kind: people, devices, machines) or on
  `OU=organisation`. Each override is listed with who set it and when; removing it removes the ACL. Only the
  root's admins (`federation:admin`) set overrides.
- ACLs are written with `samba-tool dsacl`, container-inherited (Q4), and are checked by every DC, offline too (Q12).
  Because a site's OU is in its parent's (2.1.6.20), a parent's agent and roles reach every site below it, except its
  service accounts (the parent's principals are denied there too). No site's admins or agent may change
  permissions or owners (`WD`, `WO` are left out of their rights; fabric's convergence sets ACLs as the system),
  so a child can neither remove an inherited ACE nor protect its OU from inheritance.
- The web UI never writes as the person: it asks fabric-agent, which checks the person's permissions (RBAC,
  1.6.8) and writes with its site's account, so a site's web UI cannot exceed its site's limits.
- **A writable DC holds every secret of the domain**; a read-only DC only those it may cache (1.9.8.3). The
  limits above stop a site's people and services, not someone who controls a writable DC's host.

## 1.6.3.7 Service accounts and secrets

- AD users in each site's `OU=service-accounts`: `fabric-agent-<site>`, `fabric-keycloak-<site>`,
  `fabric-radius-<site>`. Random passwords, generated per install, kept in that site's OpenBao and delivered to
  containers as files (2.1.7.3); never on a command line. 389-DS's seven role accounts are not carried over (Q11).
- `fabric-sso-<site>` (0.6.1, 2.3.6.2.6.2): Keycloak's Kerberos sign-in account, made by the DC's converge (`ensure_sso_account.py`) with the SPNs `HTTP/<hostname_keycloak>` and `HTTP/<hostname>.<domain>`, AES keys only (`msDS-SupportedEncryptionTypes` 24: Java refuses RC4 tickets) and a random password that never leaves the DC. Its keytab is exported to the DC's `/data/sso.keytab` and copied to Keycloak. None at a read-only DC.
- The Administrator's password: random at provisioning, set from a file (Q1), kept in the root site's OpenBao.
  Provisioning's own output is discarded (it prints a temporary password).
- The DC does not need OpenBao to start (the core-services rule, 1.2.8): its own secrets are in its database.

## 1.6.3.8 Passwords

- **The policy is the admin's** (2.1.6.13): minimum length, complexity, history, minimum and maximum age, and the
  lockout threshold, duration and window. A new domain starts from fabric's default (2.1.6.35: 12 characters,
  complexity, 5 remembered, never expires, locked for 15 minutes after 10 failures in 15), not asked at setup
  (2.1.2.16); a vars file may set any of it; changed later with `fabricctl domain password-policy` (`domain:admin`). fabric writes them as the domain's policy
  (`samba-tool domain passwordsettings`).
- **One-time passwords** fabric generates (a new person, a reset) satisfy the policy and must be
  changed at the next sign-in.
- **The old-password window:** AD accepts a previous password for network sign-ins for 60 minutes after a change
  (Q7). Proposed: 0 (2.1.6.15).
- Where a password is set — Keycloak, Windows (Ctrl-Alt-Del), `passwd` on a joined Linux machine, a reset in the
  web UI — it is set in AD; there is no second store and nothing to synchronise.

## 1.6.3.9 POSIX identities

- People and groups carry RFC 2307 attributes (`--use-rfc2307`): `uidNumber`, `gidNumber`, `homeDirectory`,
  `loginShell`, assigned by fabric as today (1.6.6 step 1), never reused.
- **Each site has its own id block** (2.1.6.17), handed out by its parent at join (`fabricIdRange` on the site's OU;
  block size `posix_id_block`, default 100 000), and a high-water mark in its OU. The parent takes the block after
  every one its DC holds (each site OU's, replicated), so a nested parent never repeats another branch's; two
  parents handing out blocks while cut off from each other could (not detected yet: 2.3.6.3). Writable
  site DCs cut off from the root then never assign an id another site uses.
- fabric's everyone-group `users` becomes AD's **Domain Users** with fabric's gid (5000) (Q11).

## 1.6.3.10 Access is authorized per site

People and machines are known across the domain; **access is granted per site** (2.1.6.14):

- Every person created in a site's `OU=people` is a member of `<site>-users`. Default: a site's people may log on
  only to that site's machines, join that site's network with 802.1X, and sign in to that site's web services.
- **Log-on rights:** a GPO per site (`<site> logon rights`, linked to its OU) grants interactive and remote log-on
  to `<site>-users`, `<site>-admins`, the `windows-admins` role and the fabric-admins of the site and of every site
  above it (the `linux-sudo` role before 0.9, 1.6.11.3), the admins of the sites above it (their roles reach this one, 2.1.9.13), the organisation's admin group (`webui_admin_group`, default `admins`), **`fabric-break-glass`** and each machine's own local
  Administrators (the policy replaces Windows' local lists; added in S1.7) (so a mistake cannot lock
  everyone out; Q16), plus the grants below. Windows applies it itself; Linux machines through SSSD
  (`ad_gpo_access_control = enforcing`, 1.6.7).
- **802.1X:** FreeRADIUS at a site admits people in the groups that site allows (its `radius_people` mappings name
  site groups) and devices in its own OU, plus the grants below. Domain machines signing in with PEAP (as
  `host/<name>`) follow the same mappings: an enabled computer in the site's `OU=machines` whose groups include a
  mapped one, on that mapping's VLAN (2.1.11.3). Only groups under `OU=sites` match a mapping (plus `users`, AD's
  Domain Users).
- **Web sign-in:** each site's Keycloak admits its site's groups and the organisation's admin groups.
- **Grants** (Federation tab, `federation:admin`): explicit — a person, group or site allowed at another site — or
  **blanket** — everyone in the organisation (Domain Users) at a site. One grant changes all three (log-on GPO,
  FreeRADIUS, Keycloak) together. This replaces decision F3's replication by consent (2.1.9.12).

## 1.6.3.11 How the other services use it

| Service | Today (389-DS) | With Samba AD |
|---|---|---|
| Keycloak | LDAP provider, vendor `rhds`, writable | LDAP provider in AD mode, writable, LDAPS to the site's DC verified against fabric's CA (Q7); UUID `objectGUID`, username `sAMAccountName`; password changes land in AD |
| FreeRADIUS | device lookups and EAP-TTLS binds on 389-DS | device lookups in AD (read account); **PEAP-MSCHAPv2** for people and machines through the DC's winbind (`ntlm_auth`, Q8); EAP-TTLS binds to AD; EAP-TLS and MAB unchanged |
| BIND | its own zones | its own zones, and the AD zone through Samba's DLZ module (Q2) |
| fabric-agent, web UI | `fabriclib/ldap` | a directory layer speaking AD (`fabriclib/directory`, S2); routes keep their shape (1.6.3.15) |
| Linux machines | SSSD on 389-DS (M10) | joined to AD (adcli, SSSD's AD provider, Q9; 1.6.7) |
| Windows machines | — | joined to AD into their site's OU; Group Policy (1.6.5) |

## 1.6.3.13 What this design changes, and its impact

The impact of the replacement as a whole was assessed and approved (2.3.6.1.4). What this design adds to it:

- **Trust between sites changes** (1.9.1.3): with 389-DS a compromised site held only read-only copies; with AD a
  writable site DC holds every password hash of the domain. The admin chooses the DC type knowing it; setup and
  the Federation tab say so. Read-only DCs keep the old property for everything but cached site passwords.
- **People are no longer created only at the root:** a site with a writable DC creates its own people offline;
  ids cannot collide (1.6.3.9).
- **Decisions changed by this design**, each for the owner (2.1.6): 2.1.9.3 becomes an access grant (2.1.9.12), F4
  (2.1.9.4) groups move into the site's OU (2.1.9.11), 2.1.9.8 is replaced by 2.1.6.11. New: 2.1.6.15 (old-password window), 2.1.6.16
  (SYSVOL), 2.1.6.17 (id blocks), 2.1.6.18 (the DC on the host network), 2.1.13.1 (Windows time), 2.1.1.31 (no migration before 1.0).

## 1.6.3.14 No migration before the 1.0 milestone

There are no users to keep updated until the 1.0 milestone release (2.1.1.31). Installs made before AD are rebuilt, not
migrated: build step S7 removes 389-DS and everything that served it, with no migration command and no upgrade path.

## 1.6.3.15 Agent routes added with Samba AD (planned)

Moved here from 1.3.3.2. Each route joins the fixed API ([1.3.3.1](1.3.3-agent-api.md#1331-fixed-api)) in the build step that builds it.

The routes of 1.3.3.1 keep their shape; from
build step S2 the people, devices, roles and DHCP-network routes are served from AD. `/v1/people/<uid>/reset`
returns a one-time password that satisfies the domain's policy (2.1.6.13). New routes and permissions:

| Method | Route | Needs |
|---|---|---|
| GET | `/v1/domain` (DC type, roles, replication, password policy) | `domain:read` |
| POST | `/v1/domain/password-policy` | `domain:admin` |
| GET | `/v1/machines` | `machines:read` |
| POST | `/v1/machines` (pre-create, one-time join password), `/v1/machines/<name>/{groups,disable,enable,delete}` | `machines:admin` |
| GET | `/v1/gpos`, `/v1/gpos/<guid>`, `/v1/admx`, `/v1/admx/<template>` | `gpo:read` |
| POST | `/v1/gpos`, `/v1/gpos/<guid>/{settings,link,unlink,delete}`, `/v1/admx` (upload a template) | `gpo:admin` |
| GET | `/v1/federation/limits`, `/v1/federation/grants` | `federation:read` |
| POST | `/v1/federation/overrides`, `/v1/federation/overrides/<id>/delete`, `/v1/federation/grants`, `/v1/federation/grants/<id>/delete` | `federation:admin` |

The new permissions join the admin bundle; `domain:read`, `machines:read` and `gpo:read` the auditor bundle;
`machines:admin` the equipment operator bundle ([1.6.8](1.6.8-rbac.md)). Each write is limited further by the site's own account
(1.6.3.6): a site's agent cannot change another site's objects whatever the caller holds.

## 1.6.3.16 Disabling, removing and regrouping people

Built 2026-10-08 for 0.6.3 (decision 2.1.6.30; design 2.3.1.11.7). The same functions serve `fabricctl people`
([4.6.1.3](../volume_4_operations/4.6.1-people.md#4613-fabricctl-people)) and the web console's People page; the
directory operations run in the DC as the site's agent (1.6.3.6), so AD's per-site access control applies too.

- **Only this site's people.** The DC's `set_person` and `remove_person` find the person in the site's own
  `OU=people` only: a person of another site, nested or parent, or a service account is "no such entry".
- **Disable** sets the account's `ACCOUNTDISABLE` flag (every sign-in through the domain is refused: Keycloak, 802.1X,
  Windows and Linux logons) and ends the person's Keycloak sessions at once (`keycloak/sign_out_person`). Their
  account, groups and certificates stay; **enable** clears the flag, and enables Keycloak's copy of the user
  (`keycloak/enable_person`): a sign-in tried while disabled makes Keycloak's AD mapper disable its own copy.
- **Remove** needs the user name typed back (the agent checks it, not only the page). Their sessions end, the account
  is deleted with its group memberships, Keycloak's copy of the user goes, and every certificate fabric issued to
  their name that is still in force is revoked (`cessationOfOperation`, the CRLs published once, 2.1.5.10). Their uid
  number is never reused (1.6.3.9).
- **Groups:** `add_group_member` / `remove_group_member` for the site's groups, and the organisation's at the root
  site. Keycloak reads a change at the person's next sign-in.
- **Guards** (`directory/common/person_guard`), the same for the CLI, the agent and the page: a member of a fabric
  group (one carrying a bundle) is disabled, removed or reset only by an admin (`system:admin`, or root on the host),
  and only an admin changes a fabric group's members; nobody disables or removes themselves; and the admin group's
  last member who can still sign in is never disabled, removed or taken out of it.
- **Audit:** `PERSON_DISABLE`, `PERSON_ENABLE`, `PERSON_REMOVE` (with the number of certificates revoked, each also
  `PKI_REVOKE`), `PERSON_GROUP_ADD`, `PERSON_GROUP_REMOVE`.
- **Permissions:** `people:disable` (in the helpdesk bundle), `people:remove` and `people:groups` (admins only):
  [1.8.2](1.8.2-webui-security.md), routes [1.3.3](1.3.3-agent-api.md).
- **Tests:** the `samba` suite (a real DC: disable refuses the sign-in, enable restores it, groups in and out once,
  removal, and refusals for a service account and another site's person); the `keycloak` suite (a live session ended
  by disable, sign-in refused and restored, removal drops Keycloak's user, the guards); the `webui` suites (the page's
  forms per bundle, the agent's 403s).

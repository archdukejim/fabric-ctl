## 1.3.6.1 Status and scope

Designed 2026-11-07 for 0.9.4 (2.1.1.92), after 0.9.3, and built in 0.9.4 (`src/fabriclib/setup/site/`). The owner: "I kind of want to do all setup
in a webui ... when fabric ctl guided is chosen it produces a temporary self signed cert to do an https setup. when it's
done it presents the new certificate on that site, provides pictures and the codeblocks for commands to update dns".

- **In scope:** Guided on a new install (2.1.8.46).
- **Stays in the terminal:** Advanced, unattended runs and upgrades. Guided keeps `sudo fabricctl setup --terminal` for a
  host reached with no browser. The plan's **Menu** opens Advanced's settings, so the page offers only Proceed and Cancel.
- **After setup nothing changes:** 1.8.5.2's console-only settings stay console-only.

One command in a terminal is still needed, to install the package and start the site.

## 1.3.6.2 The flow

1. `sudo fabricctl setup`, then **Guided**. The terminal asks one question, whether to open the site's port when the
   host's firewall would block it (1.3.6.7), then prints the URL, the one-time code and the certificate's fingerprint.
2. The browser warns about the certificate. The person compares the fingerprint, continues and enters the code.
3. Guided's questions, the plan and its one confirmation for host changes, in the browser.
4. **Proceed** hands the work to `fabric-setup.service`, as today (1.3.2.3), and the page follows it live.
5. The finish (1.3.6.6). Then the site stops, and any port it opened is closed.

## 1.3.6.3 The temporary site and its trust

A recorded deviation from global Rule 10 (2.1.1.93): a browser cannot verify this first certificate, so a person verifies
it by eye.

- **Certificate:** self-signed, made for this run, valid one day, naming the host's address and name. Its key lives in
  memory or tmpfs only and is gone when the site stops.
- **Fingerprint:** printed on the terminal and shown on the page, with a plain line saying what it protects against.
- **One-time code:** random, printed on the host's terminals only, never in the URL, never logged. Five wrong tries
  replace it, and every terminal attached to setup prints the new one. A terminal attaches with `sudo fabricctl setup`
  (2.1.8.60), so a lost terminal does not lose the code.
- **One session at a time** (2.1.8.62): the code opens a session. Entered in a second browser while one is open, it asks
  first, then ends the other at once and tells that browser so. Root gives a single-use ticket for that confirmation, so
  the code is never in a page. A session ends after 15 minutes without requests or an open live stream. Closing the
  browser drops its cookie, so the code is needed again; moving away from the page and back keeps it.
- **Session:** a `__Host-` `Secure`, `HttpOnly`, `SameSite=Strict` cookie, a CSRF token and an `Origin` check on every
  change. Never `Strict-Transport-Security`: the person must be able to pass the first certificate's warning, and the second.
  `Referrer-Policy` is `same-origin`, because `no-referrer` makes a browser send `Origin: null` with its forms.
- **Privilege:** the listener runs as uid and gid 649, which no account holds (2.1.8.61), in a session of its own, and
  holds no power. Setup, as root, keeps the
  questions and the checks, and the two talk over a socket only they can use. Root takes no answer until the code, which
  only its terminal shows, has been given; from then on the listener passes on what the person types, the password included.
- **Runtime:** Python's standard library on the host, because Docker's containers do not exist yet and the package already
  depends on `python3` and `openssl`.
- **Limits:** 30 minutes idle before Proceed closes the site with nothing changed. The terminal says so and how to start
  again. Ctrl-C, a closed terminal and SIGTERM do the same, and the install folder is put back as it was, because Guided's
  questions write the settings as they go.
- **The relaxation is visible:** terminal and page both say a temporary certificate is in use for as long as it is.

A person who skips the fingerprint check can be intercepted by someone on their LAN. The code does not prevent that, and
the page says so.

## 1.3.6.4 Questions, consent and secrets

- **One list of questions:** the terminal and the site are two front ends on Guided's existing questions and checks
  (`setup/collect_vars`, `common/ask`), so a refusal reads the same in both and neither can drift.
- **Permanent choices** are marked as today (2.1.2.20).
- **Host changes** are shown as one grouped list with one confirmation (global Rule 12, 1.2.9.11). Declining changes
  nothing.
- **The first admin's password** is typed twice, checked against the policy and handed to setup in memory. It is written to
  no lasting file: as from the terminal, it reaches the unit through a `0600` hand-off under `/run`, removed once read
  (2.1.6.69). It travels only over this site's TLS.

## 1.3.6.5 Progress, and losing the connection

- The page follows the same run as the terminal (`setup-run.log`) as a server-sent stream, and reloads by itself without
  script. Its answer for "did setup end?" is `follow_run`'s, with its re-check (2.3.1.46).
- **A dropped connection stops nothing:** after Proceed the work goes on (2.1.2.26). The same browser comes back into its
  session; another browser takes it over with the code (1.3.6.3). A stream on a network gone silent ends within 30 seconds
  (`TCP_USER_TIMEOUT`), and a later session ends an earlier one's stream.
- **A lost terminal:** `sudo fabricctl setup` in a new one attaches to the running setup (2.1.8.60). It shows the URL,
  the code and the fingerprint, then what setup prints. Ctrl-C there only detaches.
- **After Proceed, the terminal is free to go:** a closed terminal stops nothing. Ctrl-C ends the following and stops the
  site; the work goes on, and `sudo fabricctl setup` follows it again.
- **If a network change cuts the page off:** the terminal keeps showing progress and prints how to recover, including the
  finish's steps. `sudo fabricctl setup` follows the run again.

## 1.3.6.6 The finish: certificate, pictures and commands

1. **The new certificate:** the site restarts on a certificate from fabric's new CA, naming the host's address. The page
   offers the root CA and shows its fingerprint, which the terminal also prints.
2. **Trust:** illustrated steps for each OS, with the installers already on `http://<host_ip>/certs/`. Reloading without a
   warning proves the root is trusted.
3. **DNS:** illustrated steps and copyable commands per OS, with the real address and domain filled in (Windows PowerShell,
   macOS, Ubuntu). They are copies of the manual's topic in Volume 4 (global 5.3).
4. **The check:** the page confirms `fabric-ctl.<domain>` resolves and answers with a trusted certificate, and says which
   of the two failed if not. The console's answer is a redirect to sign in on Keycloak's name, so the page's policy lets
   the check follow it there (`connect-src`), and nowhere else.
5. **Onward:** a link to the console, and where the login kit is (4.6.3.1). The site stops on **Finish**, or one hour after
   setup ends.

Pictures are fabric's own drawings, not OS screenshots (2.1.8.47): they do not go out of date when an OS changes its screens
and carry no vendor's artwork.

## 1.3.6.7 Claims and collisions

The site claims TCP **8443** on the host, for the length of setup only (Keycloak's 8443 is inside the containers' network,
not on the host). This goes into 1.2.13's inventory.

- **Taken:** it tries the next ports up to 8453 and prints what it found. All taken: it says what holds 8443 and offers
  `--terminal`.
- **A firewall in the way:** opening it is a host change, so it is asked first in the terminal, recorded and undone when
  the site stops (global Rule 12). The rule carries the comment `fabric-setup-site`, which is the evidence that removes it,
  also after a killed run.
- **Setup's own firewall:** the firewall step turns ufw on with incoming denied, which would cut the page off in the middle
  of the run. A record in `/run/fabric-setup/site-port` tells that step to keep the site's port open from this LAN. The plan
  lists this as one line under the firewall's changes, and the rule is not counted as one of the host's own.
- **The address:** the one Guided detected. A host with several prints each with its URL. A rule the site opened admits the
  detected LAN only, and the terminal says so.
- **A second setup:** while one site runs, `sudo fabricctl setup` attaches to it (2.1.8.60) and never starts a second.
  The attach socket, `/run/fabric-setup/site-attach.sock`, is root's only (`0600`, and the peer's uid checked).
- **The listener's user number:** 649 (2.1.8.61). An account, a group or a process already at 649 is named and refused,
  offering `--terminal`.

## 1.3.6.8 How it is tested

Against real components, from the published package on a clean machine (global Rule 9):

- An end-to-end acceptance test of Guided through the site, with a real browser, accepting every default.
- **Refusals, each leaving nothing half-changed:** wrong code and the lockout, a second browser, a bad answer to each
  question, declined consent, a stale CSRF token, a wrong `Origin`.
- **Collisions:** 8443 taken, all ten ports taken, and the firewall blocking with consent declined.
- **Failure paths:** the connection dropped before and after Proceed, the idle timeout, Ctrl-C, and a failed step shown on
  the page.
- **Clean-up:** after Finish the port is closed, the key is gone and nothing is listening.
- `--terminal` keeps its existing suite. Every new entry point joins the inventory.

**Results, 2026-11-07** (`dev/0.9.4`, b872c50d):

- **The sandbox** (`tests/sandbox/web_guided.sh`, the package in Ubuntu 24.04, real ufw, real step-ca, headless Chromium):
  47 of 47. It covered every default accepted through a working install, the reconnect after the browser's network was
  cut, the collisions, ufw declined and agreed, a killed setup, and the clean-up after Finish.
- **What the runs found:** the finish's check called DNS with its arguments in the wrong order. The page's `connect-src`
  also refused the console's redirect to its sign-in, so a real person would have been told the console did not answer.
  Both are fixed and tested.
- **An independent review of the boundary** found no way past the code or the session, and no privilege gain. It found
  the defects fixed in b4bbeb00.
- **The clean machine** (3.1.5.13, approved by the owner 2026-11-07): 21 of 21 on a fresh `g23-vm-ub24-1` (Ubuntu
  Server 24.04, from its `clean` checkpoint). The branch's package (0a02f10) was installed with `apt install`, then
  `sudo fabricctl setup` ran in a real terminal over SSH, with Guided in a real browser on another machine. Every default
  was accepted (the domain `home.arpa`), through to Finish, the finish's check passing with the domain resolving to the
  VM, `fabricctl doctor` passing, and nothing of the site left. The first run's one failure was the test's own: it read
  the root from nginx's folder, which `labadmin` cannot read. The check now uses the root published at `/certs/`, as a
  person does, and the second run, from `clean` again, passed whole.

**Results, 2026-11-07, after 2.1.8.60–62** (`dev/0.9.4`, feece60f to 44253147):

- **The sandbox:** 49 of 49. Two checks are new: a second `fabricctl setup` attaches with the current code, and Ctrl-C
  there only detaches; after the browser's network is cut, a new browser is asked, then takes the session over. It
  also checks that the listener runs as uid and gid 649.
- **The suites:** `attach_server_test`, `attach_site_test` and `site_account_test` joined `consent`. On CI, the first
  run failed because the non-root probe could not read the checkout. The probe now gets its own readable copy of the
  modules it imports.
- **The clean machine was not repeated:** the 21 of 21 above was run before attach, uid 649 and the session rules.
  The owner chose (2026-11-07) to rely on the sandbox until 0.9.5's release candidate, whose tests repeat it.
- **Not run:** the package from the apt repository (a release publishes it), the trust and DNS commands on real Windows,
  macOS and Ubuntu clients, and the trust failure in a real browser (Chromium checks it only with certificate errors
  ignored; `flow_test.py` proves it with real TLS).

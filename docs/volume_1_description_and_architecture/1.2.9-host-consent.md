## 1.2.9.1 Status


Status: **built** (owner decision 2026-10-02; `fabriclib/consent/`, `fabriclib/undo/`, suite `tests/consent`): the
questions, the checks, `fabricctl status` and the web UI's Overview, uninstall listing what it does per group, `setup

## 1.2.9.2 The rule

fabricctl changes only what it needs to run fabric. **Anything outside fabric's own tree — system files, other
applications' configuration, accounts, the firewall — needs an explicit yes from the person installing.**
Changes are grouped so one answer covers one kind of change (all service accounts are one question). Nothing
is approved by default, by `--yes`, or by a web UI click that did not say what it changes.

Two rules meet here: *secure by default* and *no change without consent*. Both hold: the secure
choice is the recommended answer, and declining it is recorded and shown in `fabricctl status` and the web UI
as a relaxation ([1.2.8](1.2.8-security-defaults.md#128-security-defaults)).

Integrations with software fabric does not own (Cockpit, an existing Docker, a reverse proxy) never go into
fabricctl: if one is ever built it is a separate package with its own lifecycle and its own consent, and
fabricctl offers only generic extension points. (A Podman move and a fabric Cockpit bridge were considered
and dropped by the owner on 2026-10-02: Docker stays, and a community Cockpit plugin already shows fabric's
compose stacks.)

## 1.2.9.3 What fabric changes on the host today

Inventory of 2026-10-02 (setup, apply and the timers):

| `runtime` | `/etc/docker/daemon.json` hardening and **a Docker restart (every container on the host, not only fabric's)** | setup `docker` | recommended |
| `services` | fabric's own units in `/etc/systemd/system/` (`fabric-*`, `fabric.target`, timers), `/usr/local/bin/fabricctl`, `/usr/local/bin/step`, the vault unlock udev rule | deploy/apply, vault | required |
| `accounts` | the service users and groups (`service_users`), names and ids listed | setup `accounts` | required |
| `trust` | fabric's root and site CAs in the host trust store (`/usr/local/share/ca-certificates`, `update-ca-certificates`) | setup `pki`, apply | recommended |
| `resolver` | systemd-resolved stub off and the host resolver pointed at `dns_server` (only with `use_host_dns: false`, to free port 53) | setup `network` | required by that choice |
| `ports` | (0.6.2, 2.1.2.13) the ufw rules opening what fabric itself needs on the host: the domain controller's ports from the LAN, fabric's containers and the federation's peers; NTP; DHCP. | `own_rules` | (asked only after `firewall` is allowed, and only when the host has ufw rules fabric did not add) removing them, listed one by one: yes removes them (recorded, put back by uninstall), no keeps them | setup `firewall` | recommended |
| `time` | `/etc/chrony/chrony.conf`, `/etc/default/chrony`, a `chrony-wait` drop-in (the host's time source) | apt, apply (M9) | recommended |
| `member` | (0.7.1, [1.6.11.8](1.6.11-host-access.md#16118-the-fabric-host-as-a-member-of-its-domain)) this host as a member of its own domain: the packages `sssd-ad`, `sssd-tools`, `libnss-sss`, `libpam-sss`, `libsss-sudo`, `krb5-user`, `libsasl2-modules-gssapi-mit` when missing; `adcli` when `host_machine_password_renew_days` is on (1.6.11.12); the host's own computer account `<HOSTNAME>$`, placed once in the site's `OU=fabric-hosts` and in `<site>-fabric-machines` (2.1.6.48, 2.1.6.49; at a read-only DC's site made at the writable DC and in `<site>-rodc-cache`, 2.1.6.52); who signs in by domain account is that OU's log-on policy alone (2.1.6.53); `/etc/krb5.keytab` (that account's keys only), `/etc/krb5.conf`, `/etc/sssd/sssd.conf`; `sss` in `/etc/nsswitch.conf` and PAM (`pam-auth-update`); the DC's name in `/etc/hosts` when the host cannot resolve it; the classic sudo where sudo-rs is the default; while the host is in `<site>-fabric-machines`, fabric's management (1.6.11.11): `/etc/ssh/sshd_config.d/10-fabric.conf` (Kerberos for SSH) and `pam_localuser` in `/etc/pam.d/sshd` (a domain account's password not taken over SSH; local accounts unchanged) where an SSH server is installed, `/etc/systemd/resolved.conf.d/fabric.conf` (the domain's names from fabric's DNS) with `use_host_dns` (kept in step hourly by `fabric-host-managed.timer`, one of fabric's timers). Not planned with `host_join_domain: false` | setup `member` | recommended |

Levels: **required** — declining stops setup with the reason; **recommended** — declining leaves that part
unmanaged and shows a relaxation; **required by that choice** — declining asks for the other choice
(`resolver`: keep the host resolver, so the DNS port must be free another way).

Not a host change, never asked: files under the install (`/opt/fabric`, `/etc/fabric`), fabric's containers,
its networks and images.

Each group is asked as one short question, its changes listed below it (2.1.2.21, since 0.7.1;
`consent/groups.py`): `packages` "(Packages) Install the packages fabric needs?", `runtime` "(Docker) Harden the
Docker daemon?", `services` "(Services) Install fabric's own services?", `accounts` "(Accounts) Create fabric's
service accounts?", `resolver` "(DNS) Turn off the host's own resolver so fabric answers on port 53?", `ports`
"(Firewall) Open the ports fabric needs?", `firewall` "(Firewall) Let fabric manage this host's firewall?",
`own_rules` "(Firewall) Drop this host's own firewall rules, keeping fabric's?", `trust` "(Trust) Trust fabric's CA on
this host?", `time` "(NTP) Use fabric as the domain's network time provider?", `member` "(Domain) Make this host a
member of its domain?".

## 1.2.9.4 How it works

1. **Plan first, ask once, then run unattended.** After the settings are collected and before the first step,
   setup computes every group's planned changes (each group has a pure `plan` function reading the vars) and
   shows them. A full setup takes ~20 minutes: all questions come at the start, none half-way.
2. **One question per group**, listing exactly what changes: `Firewall: enable ufw (deny incoming), allow
   22/tcp from 192.168.4.0/22, 53 tcp+udp from …  Apply? [Y/n] (recommended)`. Required groups say what
   declining means (`setup stops`).
3. **Approvals are recorded** in `config/consent.yaml`: per group the answer, a digest of the planned changes,
   when and who (`SUDO_USER`). A re-run asks again **only for groups whose planned changes differ** from what
   was approved, and shows the difference. An earlier **no that stops setup** (a required or choice group, and
   `ports` while ufw is on) is asked again in the next interactive run, so a person is never stuck with it (0.6.2,
   found by the installer test). A question that needs another (`firewall` needs `ports`, `own_rules` needs
   `firewall`, 2.1.2.13) is not asked once that one is declined.
4. **Steps check before acting.** Each step that touches the host asks `consented(ctx, group, changes)`:
   approved with the same digest → act; anything else → do not act (a required group raises `SetupError`).
5. **Unattended installs** approve explicitly: `--approve ports,firewall,accounts,…` or `--approve all`, and
   `--decline GROUP`. `--yes` keeps its meaning (accept the plan) and approves nothing. A group without an
   answer stops a non-interactive run naming the groups and the flag.
6. **apply, the web UI, the agent and the timers never ask.** When a change would need a new approval (a new
   firewall rule after a settings change), they leave the host as it is, log it, and status shows
   *waiting for approval: `sudo fabricctl setup --step firewall`*. They never widen an approval.
7. **Status** (`fabricctl status`, the web UI) lists every group: approved, declined (with the relaxation it
   means) or waiting.
8. **Uninstall** lists, per group, what it removes (services, accounts), undoes (firewall, resolver, time, trust) or
   keeps (packages; Docker's daemon settings, since putting them back restarts Docker — `setup --undo runtime` first),
   before its questions and its confirmation.
9. **Explicit commands are their own consent.** A command that exists to change the host — `fabricctl vault
   add-usb` writing its udev rule, `fabricctl uninstall` — is the admin's request; it is not asked again.

Decisions made while building (2026-10-02):

- **Kinds, not lines, for `services` and `time`.** Their changes follow fabric's own settings (which services
  are on, which time sources), so the question approves the kind; a new fabric unit or a new NTP source does
  not ask again. `firewall`, `accounts`, `packages`, `runtime` and `resolver` are asked line by line.
- **The subset rule.** A step may make a change only when it is among the changes its group's yes covered; a
  yes keeps what was approved before, so a re-run that changes less still matches.
- **No default answer.** The interactive question needs `y` or `n` typed; Enter asks again.
- **Installs set up before consent existed** keep converging through apply, the agent and the timers (nothing
  new is changed by those for them except fabric's own units and chrony, which they already ran); the next
  `fabricctl setup` asks for everything once.

## 1.2.9.5 Upgrades

An existing install has no `consent.yaml`. The next setup shows the plan for everything already in place and
asks once (non-interactive: `--approve`). Declining a recommended group stops managing it from then on; what
was changed earlier is left as it is and reported, not reverted silently: `fabricctl setup --undo GROUP` reverts it on
request.

**Undo** (built 2026-10-03, `fabriclib/undo/`):

- Before fabric first changes a host file it keeps it in `config/host-originals/<path>` (`common/keep_original`): a
  copy, a symlink's target, or a note that it did not exist; ufw's on/off state likewise. Only the first copy is kept,
  and a file already carrying fabric's marker is never taken for the original. Installs from before this have no
  copies: undo then removes only fabric's values (`daemon.json`) or says the file stays as fabric wrote it (chrony).
- `setup --undo GROUP` works for the recommended groups (`runtime`, `firewall`, `trust`, `time`, `member`) and `resolver` once
  `use_host_dns` is true. It says what it will do and what that leaves unmanaged, asks (`--yes` unattended, never
  without it), undoes, and records the group as declined with the changes setup would make now — so setup, apply
  and the timers leave it alone and status shows the relaxation. `--approve GROUP` makes the change again.
- `packages`, `services` and `accounts` are fabric itself: only uninstall undoes them. An install never asked (no
  `consent.yaml`) is refused: setup asks first.
- `doctor` checks the host's trust in fabric's CA only while `trust` is approved.

## 1.2.9.6 Related

- fabric adds no apt sources (owner decision 2026-10-02): Docker is Ubuntu's `docker.io` + `docker-compose-v2` +
  `docker-buildx`. A release upgrade (`do-release-upgrade`) disables third-party sources, which left Docker's
  own `docker-ce` without updates on the test Pi; an install that still runs `docker-ce` keeps it until its
  owner switches.
- The apt dependencies (chrony, ufw) are installed by apt, which shows and asks for them itself (e.g. chrony
  replacing systemd-timesyncd); fabricctl's prompts are in `fabricctl setup`, never in package scripts.

## 1.2.9.7 Build

`fabriclib/undo/`: one `undo_<group>.py` per group fabric can revert, `undo_group.py` (`setup --undo`), `uninstall_plan.py`
(uninstall's list); `common/keep_original.py` / `common/restore_original.py`. The web UI's Overview reads
`GET /v1/host-changes` (`status:read`).

`fabriclib/consent/`: `plan_host_changes.py` (the groups' plans, one `plan_<group>.py` each), `ask_consent.py`
(the grouped questions), `allowed_to_change.py` / `check_consent.py` (the checks steps and apply make),
`load_consent.py` / `save_consent.py`, `consent_status.py` / `show_consent_status.py`. Setup gains `--approve` /
`--decline`; restore passes them on. The steps that change the host check first: `host` (packages), `docker`
(runtime), `deploy` and every apply (services; time through `deploy_optional_parts`), `accounts`, `network`
(resolver), `firewall`, `pki` (trust). Tests: `tests/consent` (no containers) and the sandbox (an unattended
setup without `--approve` changes nothing; with it, everything installs).

## 1.2.9.8 Service accounts (built with consent)

fabric's accounts were named like Ubuntu's own (`bind`, `postgres`, `nginx`, …) on ids Ubuntu reserves; the
26.04 release upgrade on the test Pi asked to remove `bind` (uid 53, in `base-passwd`'s 0–99). Now: `fabric-*`
names (`fabric-dns`, `fabric-proxy`, `fabric-ca`, `fabric-sso`, `fabric-db`, `fabric-webui`,
`fabric-vault`, `fabric-logs`, `fabric-dhcp`, `fabric-radius`, `fabric-dnsfilter`, `fabric-auth`) on ids
600–612 (band 600–649: the quiet middle of Debian's system range; 601, `fabric-ldap`, went with 389-DS in S7). An id held by another account stops setup.
An older install's settings drop the previous defaults (`upgrade_vars`), the accounts step moves each previous
account's files to its new one and removes the previous account (once no container runs as it: else on the
next setup), and the images fabric builds are rebuilt for the new ids (`org.fabric.ids` label).

## 1.2.9.9 A question split in a later release

When a release splits one group into several (0.6.2 split `firewall` into `ports`, `firewall` and `own_rules`,
2.1.2.13), an install's earlier answer **carries over** to every group the old one covered (2.1.2.14): 0.6.1's
`firewall` answers `ports` and `firewall`, with the changes now planned, its time and who gave it, and a note
naming where it came from; a group that is genuinely new (`own_rules`, removing the host's own rules, was never
asked) is asked as usual. So an unattended `fabricctl setup` after an upgrade asks only what is new. Each split is
recorded beside the groups (`consent/groups.py`, `SPLITS`), with the release it came in and the group whose
presence shows an install already answered after it. Built in 0.6.3 (`consent/carry_over_splits.py`); tested in
`tests/consent` and by the upgrade test.

## 1.2.9.11 Setup's start: guided, or a menu of every setting; one confirmation

**Designed 2026-10-11 (decisions 2.1.2.17, 2.1.2.18, 2.1.2.19); built 2026-10-12 for 0.7.1 (2.1.2.21):**
`setup/choose_mode.py`, `setup/advanced/` (the menu and its items), `setup/choose_plan.py` (the plan and its one
yes); yes/no items through `common/ask.py`'s `ask_yes_no` (1.1.5.6). Suite: `tests/consent`; the installer test
(`tests/host/installer.py`) on a test host.

1.2.9.11.1 **The start.** An interactive setup on a new install begins with:

```
fabric setup

  [G]uided   - the questions fabric needs, one at a time (recommended)
  [A]dvanced - a menu of every setting
  [Q]uit
```

(ID `setup.mode`). An upgrade or a re-run, where the settings exist, goes straight to the plan (1.2.9.11.4).

1.2.9.11.2 **Guided** asks only what setup needs and cannot default (2.1.2.16), one question at a time as today: the DNS
domain, this host's name, the organisation's name, the AD domain, the network (found, confirmed), the first admin and
their password; the domain controller's name is fabric's, never asked and never shown (2.1.6.65). Then the plan
(1.2.9.11.4).

1.2.9.11.3 **Advanced** is one numbered menu of every setting, each with its value, in three parts:

```
  Required (setup cannot proceed until each has a value):
    1) DNS domain ...................... lan.example
    2) This host's name ................ pi-core
    3) Organisation's name ............. (needs an answer)
    4) Windows (AD) domain ............. ad.lan.example
    5) Network ......................... 192.168.4.0/22, gw 192.168.4.1 (found)
    6) First admin ..................... fabric-admin, password (needs an answer)
  Before the install:
    7) CA root lifetime ................ 10 years (fixed once the CA is made)
    8) DHCP with Kea ................... off
    9) 802.1X with FreeRADIUS .......... off
   10) Log forwarding .................. off
   11) DNS filter ...................... on
   12) Memory fabric may use ........... 4 GB (the split is in the plan, 1.2.4.3)
  Changes to this host (recommended; each can be declined):
   13) Harden the Docker daemon ........ yes
   14) Ports fabric needs (firewall) ... yes
   15) Secure this host (firewall) ..... yes
   16) The host's own firewall rules ... out (fabric's rules only)
   17) Trust fabric's CA on this host .. yes
   18) Time service (chrony) ........... yes
   19) This host as a member of its domain yes

  [P]roceed (waits for 3, 6)   a number to change it   [Q]uit
```

A number asks that one item with the same question and checks guided mode uses (same IDs: `setup.ad_domain`,
`setup.admin_password`, …; a yes/no item [Y/n] or [y/N] with the current value the default; a part turned on asks
what it needs, as `fabricctl dhcp on` does; a host change turned off first shows what declining it means and records
it declined, a relaxation shown by status as today, taking along one another needs: the firewall needs ports, the
host's own rules need the firewall); then the menu again. Something that is not on the list is refused, saying which
numbers are. Values found or defaulted show as such; a required item without one shows "(needs an answer)", and
`[P]roceed` names those it waits for. The resolver item appears when fabric would take port 53. IDs: `setup.menu` for
the menu's choice, then each item's own.

1.2.9.11.4 **The plan** shows what setup will do (as today), the memory split (1.2.4.3) and **every host change**, by
group, each with its changes: the required groups (packages, fabric's own services, service accounts) and every
recommended or choice group that is on. `[P]roceed` is the one yes that approves all groups listed, recorded in the
consent file as today (1.2.9.4); `[M]enu` opens the menu of 1.2.9.11.3 to change anything; `[Q]uit` changes nothing.
No separate consent question is asked in an interactive run. Neither the plan nor its host changes name the domain
controller (2.1.6.65, revised 2026-10-18): a new domain's plan says how many DCs it uses and how many can be added
(`Create the Windows (AD) domain ... with this host's domain controller: 1 DC used, 1998 can be added`), and the
`member` group's changes say "this host's domain controller".

1.2.9.11.5 **Unattended runs and upgrades.** `--non-interactive` with a vars file, `--approve`/`--decline`, and
`--yes` are unchanged. An upgrade that adds or changes a group's changes shows the plan's host-change list with those
groups marked, and Proceed approves them (an unattended upgrade still names them: `--approve <group>`).

## 1.2.9.12 The host's own firewall rules, said apart (0.7.1)

Topics: 1.2.9.12.1 The plan; 1.2.9.12.2 The step; 1.2.9.12.3 Keeping them.

- **1.2.9.12.1 The plan:** when `own_rules` is on and the host has ufw rules fabric did not add, the plan shows them in
  a block of their own after the host changes, in warning colour: *Firewall rules of this host's own that fabric will
  REMOVE (n)*, one line each, then how to keep them. Turned off, the block is gone and the group shows under *Not
  made* with what that means (the rules stay beside fabric's).
- **1.2.9.12.2 The step:** removing them says so first (how many, that uninstall puts them back, and
  `sudo fabricctl setup --undo firewall` to do it now), then each rule as it goes, as warnings, not information.
- **1.2.9.12.3 Keeping them:** interactively, [M]enu and turn off *The host's own firewall rules*; unattended,
  `--decline own_rules` (`--approve all` includes removing them; `fabricctl setup --help` names every group,
  `ports` and `own_rules` included). Decision 2.1.2.24.

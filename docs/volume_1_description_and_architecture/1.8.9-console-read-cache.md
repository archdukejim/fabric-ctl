## 1.8.9.1 Status and scope

Designed 2026-11-07 for 0.9.3 (2.1.1.90), on `dev/0.9.3`. Decided by the owner the same day (2.1.8.43, 2.1.8.44,
2.1.8.45); being built.

The owner asked for pages under 100 ms on a 5-person install. 19 of the 32 pages measured already are (2.3.8.5.3). The
rest wait on other services, not on the web server or TLS, so streaming a page would change when its bytes arrive and
not how long the server takes to gather them. This chapter continues 1.8.8.2's method: no work on the request path that
a timer or a cache can do.

## 1.8.9.2 What is kept, and what never is

- **Kept:** the reads named as causes in 2.3.8.5.3, the grants' list (`/directory/sites`, `/directory/access`, a person's
  page) and the Overview's container state and certificates. Each other page over 100 ms has its cause named first
  (1.8.8.2), then joins this list or is fixed on its own.
- **Where:** in fabric-agent's memory only, never on disk, and lost when it restarts. A read with nothing kept yet is made
  live, as today. **The host itself** (a root peer) and anything but a running fabric-agent always read live.
- **As built:** `fabriclib/readcache/kept_reads.py`, started by `agent/kept_store.py`; which reads, `KEPT_FIXED` in
  `agent/get_route.py`, with a zone's detail, a person's explained grants and the groups they manage kept per name. Each
  fixed page's read is made once at the agent's start. A read answering with an error is shown as it is and not kept.
  The Overview's reminders are kept with its services while there are none. While one shows it is read afresh, so a reminder
  goes as soon as its cause does (2.1.6.69), which costs the Overview its target until the file named is deleted.
- **Served after the agent's own checks:** the route's permission and any filtering by viewer run on every request, as
  they do now.
- **Never kept:** secrets, or anything read from OpenBao's secret values. `/secrets` may cache names only, which is why
  it is outside the target (2.1.8.43).
- **Never used to decide access:** what a person may do is checked live. A kept list only draws a page, so it can show a
  revoked grant for a moment but cannot give one.
- **Replaced at once** when a change the agent applies touches it. Changes made elsewhere (RSAT, `samba-tool`, another
  DC's replication) arrive at the next refresh.

## 1.8.9.3 Freshness sized to the host

Decision 2.1.8.44. The owner: on a large host fabric "should be leveraging as much of the system it can"; on a 4 GB Pi
"we should not try to tax and focus on reliability first and foremost".

The class comes from the host's cores and
`host_ram_capacity`, the same memory figure the budget uses (1.2.4.3.1):

| Class | Host | Share of one core | Refresh between | Held processes |
|---|---|---:|---:|---:|
| Small | under 8 GB, or 4 cores or fewer | 2% | 30 s and 5 min | 2 |
| Medium | 8 GB or more, and 5 or more cores, not Large | 5% | 10 s and 5 min | 4 |
| Large | 32 GB or more, and 8 or more cores | 10% | 2 s and 5 min | 8 |

- **The interval follows the work:** the time the last refresh took, divided by the class's share, held between the
  class's two limits. A larger directory therefore refreshes less often by itself, and the sizing advice (1.8.8.8) says
  when the host is small for it.
- **Who asked:** a read asked for in the last 10 minutes takes part in each refresh; any other only at the upper limit, so an
  idle console costs one small refresh every 5 minutes. On a Pi one or two pages asked for lately refresh about every 30 s;
  all of them would take about 150 s (2.3.8.9.2).
- **Reliability first, on every class:** one refresh runs at a time; while available memory is under 15% or the load
  average is over the core count, the interval doubles up to its upper limit and pages keep serving what is kept.
- **Held processes** (1.8.8.2) count in the DC's memory limit: at 110 MiB each (2.3.8.9.3) they may take half of it, on any
  class. Since a refresh runs at the upper limit even when idle, one held process now usually stays alive.
- **Memory limits do not change here:** containers already share `host_ram_capacity` (1.2.4.3).
- **Worked out again** when the agent starts, so a host given more memory or cores moves class by itself.

## 1.8.9.4 What a page shows, and when a refresh fails

Decision 2.1.8.45.

- A page drawn from kept data says how old it is ("Updated 20 s ago"), and works without script (1.8.8.2).
- It has a **Refresh** action that reads again now, at most once per the class's lower limit; past that it refuses and
  says when it can run. It is a new entry point, with positive and negative tests (global Rule 9).
- A failed refresh is shown on the page with the data's age and logged. It never silently passes old data off as new.

## 1.8.9.5 The speed target

Decision 2.1.8.43: every page except `/secrets` at 100 ms or less of server time on the test Pi's 5-person install. The
suite enforces it on the **median**, so a lucky run cannot pass. `/secrets` gets a best effort. Network and the browser's
drawing come on top and are not in this number. **As built:** `BUDGET_MS` and `--budget` in `tests/host/page_speed.py`, which
loads each page once uncounted, since a first load may be read live. The Overview meets it only once no reminder shows
(1.8.9.2). Results: 2.3.8.9.4.

## 1.8.9.6 How it is tested

Against real components (global Rule 9); `tests/sandbox/read_cache.py` holds all but the first, by hand on a default sign-in
(3.1.2.8), and the back-off with `--load`:

- `tests/host/page_speed.py --budget` on the test Pi, for the target and for the Small class.
- A change through the console shows on the next load; one made with `samba-tool` shows within the interval.
- A grant revoked outside the console is refused at once, while the page may still list it for up to one interval.
- With load pushed past 1.8.9.3's line, the interval backs off, pages still answer and nothing is killed. Memory is pushed past
  its line only in the unit tests: filling a shared kernel's memory would disturb what else runs there.
- Class and interval as unit tests of pure logic, with the table's edges. The Large class's behaviour runs in the sandbox
  on gaming-23: no Large host is available as real hardware, recorded as a blocker in 2.3 when building starts.

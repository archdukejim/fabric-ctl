## 1.5.1.1 PKI Chain

```
Root CA  (Step-CA's own, created by `step ca init` at setup; or bring your own with `byoc: true`)
    └── Step-CA Intermediate CA
            ├── Service certs  (issued by the running CA during setup's `certs` step)
            │       ├── dns.<domain>      → nginx DoH, BIND9
            │       ├── <host>.<ad_domain> → the domain controller (LDAPS, StartTLS; also names ad_domain and host_ip)
            │       ├── ca.<domain>, vault.<domain> (nginx and OpenBao), the landing page (info.<domain>)
            │       ├── sso.<domain> (nginx, Keycloak) and postgres (Keycloak's database), with Keycloak
            │       ├── radius.<domain>   → FreeRADIUS EAP server cert (optional)
            │       └── fabric.<domain>   → nginx → web UI (only when install_webui)
            ├── Web UI client certs  (setup's first admin; fabricctl client-cert <user>; CN = Keycloak username)
            ├── Hand-issued certs    (web UI Step-CA tab: signed CSRs, generated key pairs; capped by pki_manual_max_days)
            └── extra_certs          (signed offline with the intermediate key, per-entry config)
```

By default setup lets Step-CA create its own root and intermediate (keys in `/opt/stepca/data/secrets`, readable by the `step` user only). With `byoc: true` the root certificate, intermediate certificate and intermediate key come from `ca_crt_path`, `ica_crt_path` and `ica_key_path`; the root key never reaches the host. Step-CA also serves ACME and signs leaf certs via its intermediate CA. DNS-01 challenges can be fulfilled via a zone's TSIG key (RFC2136).

With BYOC the intermediate key path defaults to `ica_crt_path` with `.crt` replaced by `.key`; set `ica_key_path` in the vars file to override it.

Internal CA files are distributed to services as `root_ca.crt` volume mounts. The PKI info page is available at two URLs:

- `https://ca.<domain>/pki/` — hosted on the Step-CA vhost
- `http(s)://info.<domain>/` (`landing_page_cname`, 1.4.2) — dedicated vhost with theme selector and clean download URLs (`/root_ca.crt`, `/intermediate_ca.crt`)

## 1.5.1.2 Certificate Relay

Core service certificates (`dns.<domain>`, the DC's `hostname_dc`, `ca.<domain>`, `vault.<domain>`, the landing page (`info.<domain>`; `certs.<domain>` until 0.7.0, 1.5.1.5), `sso.<domain>` and `postgres` with Keycloak, `fabric.<domain>` with the web UI, `radius.<domain>` with FreeRADIUS) are Step-CA leaf certs (`cert_service_days`, default 47 days, decision 2.1.5.4) issued by the running CA (`step ca certificate`) during setup's `certs` step. They are renewed at `cert_renew_after_days` (30) days old — or when missing, missing a name, not from this CA, or longer-lived than `cert_service_days` (2.1.5.7) — by the daily `fabric-certs.timer` (`fabricctl certs --scheduled`, 03:30 spread over half an hour, a missed night run at boot), by setup and by `fabricctl certs`. Each service takes its renewed certificate with the least interruption it allows (`pki/pick_up_cert.py`): nginx, Postgres and OpenBao reload on a HUP (OpenBao stays unsealed), Keycloak re-reads its files by itself, BIND, the DC and FreeRADIUS restart (seconds). Every run is recorded (`/opt/fabric/archive/cert-renewal.json`); a failed run or a service certificate under 7 days is a failure in `fabricctl doctor`, shown in `fabricctl status` and on the web console's Overview, and the CA within 180 days and issued certificates within 30 are warnings (2.1.5.5). `extra_certs` and admin client certificates are signed offline with the intermediate; client certificates are recorded in the issued-certificate ledger. The root's lifetime is `cert_root_ca_days` (default 10 years), the intermediate's a year less (2.1.5.6). There is no certbot container or cert-relay service. nginx reads the issued certs directly from the volume paths set during install. The DC's cert is copied to `/opt/samba/tls/` (mounted read-only into the DC; [1.6.5](1.6.5-samba-dc.md)). For webui client-certificate verification nginx trusts `/opt/nginx/certs/client-ca/ca-bundle.pem` (intermediate + root).

## 1.5.1.3 Revocation (CRLs)

Built in 0.6.3 (decision 2.1.5.10). Any certificate fabric issued can be revoked — a device's or a person's, a client
certificate, one a LAN machine got over ACME, a service certificate, a site CA this install signed — from the web
console's PKI page (Issued, permission `pki:revoke`) or `fabricctl certs revoke <serial|name> [--reason R]`. A
revocation is recorded (`/opt/fabric/archive/revoked-certs.jsonl`) and audited, and the CRLs are published at once.

- **Two CRLs**, signed with the CA keys on this host by `fabriclib/pki/publish_crl.py` (openssl, so certificates signed
  offline are covered as well as Step-CA's own): the **intermediate's** (every leaf) and the **root's** (the site CAs
  it signed; only where the root key is on this host — not with a brought-in root). Each is valid 7 days and published
  again on every setup run and every night by `fabric-certs.timer`.
- **Served** with the CA files, also over plain HTTP: `http://info.<domain>/certs/crl/intermediate.crl` (DER) and
  `.pem`, `root.crl` and `.pem`, and the same under `http://<host_ip>/certs/crl/` (on `certs.<domain>` until 0.7.0,
  1.5.1.5). Every leaf fabric issues from 0.6.3 names the intermediate's CRL as its distribution point
  (Step-CA's `leaf.tpl`).
- **Checked** by FreeRADIUS (EAP-TLS, `check_crl = yes`; the CRLs follow the CA certificates in its `ca.pem`, with the
  other sites' intermediate CRLs fetched from `http://info.<their domain>/certs/crl/`, so a roaming device from another site is checked too)
  and by nginx for the web console's client certificates (`ssl_crl`, through `conf.d/client-crl.inc`; nginx checks
  every level of the chain, so this needs the root's CRL and is off where the root key is not on this host).
- **In force at once:** after a revocation nginx reloads and FreeRADIUS restarts (seconds); a revoked device is refused
  at its next authentication even while it is still linked. Unlinking stays the quick way to cut a device off;
  revocation is the lasting one.
- The issued list (PKI page, `fabricctl certs issued`) shows each certificate as valid, expires soon, expired or
  revoked.

## 1.5.1.4 ACME for machines on the LAN

Built in 0.6.3 (decision 2.1.5.8). Machines fabric does not run — a Proxmox host, a NAS, a printer, a server — get
certificates from fabric's CA automatically with any standard ACME client, at
`https://ca.<domain>/acme/acme/directory` (nginx passes it to Step-CA).

- **Names under fabric's domain only, never an address.** Step-CA's ACME provisioner issues with its own template,
  `acme.tpl` (`templates/stepca/acme.tpl.j2`), which refuses any other name or an IP address: a self-hosted Step-CA
  enforces issuance policies only for the whole authority, which would bind fabric's own service certificates too.
  Each certificate lives `cert_acme_lifetime_hours` (47 days) and names the intermediate's CRL (1.5.1.3), so it can be
  revoked like any other.
- **http-01** for a machine answering on port 80 under its name: Step-CA resolves the name through fabric's BIND and
  checks the challenge; nothing to enroll.
- **dns-01** for a machine without a web server: `fabricctl acme enroll <name> --dns` gives it a TSIG key (`acme-<name>`)
  that may change only `_acme-challenge.<name>.<domain>`'s TXT record — fabric's own per-name RFC2136 grants in the
  main zone (2.1.4.1 keeps dynamic records out of the rendered ones; these are challenge records only). Its settings,
  with the secret, are in `/opt/acme-<name>/rfc2136.ini` (certbot's RFC2136 format); the client sends updates to the
  host's BIND port (5053 behind the DNS filter). `fabricctl acme list` and `fabricctl acme remove <name>`. In the web
  console, Step-CA → ACME shows the directory and how to use it (`pki:read`) and the machines enrolled; enrolling
  and withdrawing need `tsig:manage`, since each is a TSIG key (also listed on the BIND page), shown once like any
  other and published by Apply.
- **Configured on every setup run:** `init_pki._configure_ca_json` converges `ca.json` (the provisioner, its lifetime and
  template, the authority's maximum), restarting Step-CA when it changed; before 0.6.3 it was written only once.
- Tested against the real Step-CA image (`tests/pki/acme.py`): a machine gets a 47-day certificate over http-01; a
  name outside the domain is refused even when its challenge passes; an address and a name the machine does not answer
  for get nothing.

## 1.5.1.5 The CA served at info.<domain>/certs; certs.<domain> dropped (0.7.0)

**Designed 2026-10-11 for 0.7.0 (decision 2.1.5.11); built 2026-10-11.** One place for the CA by name and one by
address:

- **`http://info.<domain>/certs/`** (and over HTTPS) and **`http://<host_ip>/certs/`** for a device with no DNS from
  fabric yet: the certificate page, every format, the install and join scripts, the fingerprints and the CRLs
  (`/certs/crl/`). Both were served since 0.6.3 (1.4.2.3); 0.7.0 makes them the only ones.
- **`certs.<domain>` goes, with no redirect** (the owner, 2026-10-11): its nginx server, its service certificate (no
  longer issued; the old files deleted at upgrade), its DNS name (`cname_certs`) and the var `hostname_certs`. The
  page, the scripts (`install-*.sh`, `join-linux.sh`), the landing page's links, the console's PKI and RADIUS guides,
  the first-steps text and the admin's README name `info.<domain>/certs/` instead. `ca.<domain>` opened in a browser
  goes to `https://info.<domain>/certs/`, and so does an old `/certificates` link on the info page.
- **Built:** nginx (`templates/nginx/nginx.conf.j2`) has no `certs.<domain>` server; setup issues no certificate for
  it and deletes `/opt/nginx/certs/certs.<domain>/` left by an older install (`setup/mint_service_certs.py`); the
  upgrade drops
  `cname_certs`, `hostname_certs` and the main zone's `certs` CNAME to this host if an older settings file holds it
  (`setup/upgrade_vars.py`); `fabricctl doctor` checks `https://info.<domain>/certs/` and the `ca.<domain>` redirect
  (`setup/verify_install.py`).
- **The CRL's distribution point** in every leaf fabric issues becomes `http://info.<domain>/certs/crl/intermediate.crl`
  (Step-CA's `leaf.tpl` and `acme.tpl`). Leaves from 0.6.2 carry none, so the owner's install loses nothing. Leaves
  from the 0.8.0 candidates (test hosts only) name `certs.<domain>`: a device's certificate keeps the old point until
  it is issued again, and a checker that demands its CRL (Windows' EAP-TLS) refuses it meanwhile. Accepted for test
  hosts. **Found while building (2026-10-11):** fabric's own service certificates carry no distribution point at
  all — setup issues them through Step-CA's `admin` JWK provisioner, which has no template; `leaf.tpl` is used by
  hand-signed CSRs and generated pairs (`pki/sign_csr.py`) and offline-signed leaves (`pki/mint_offline_cert.py`),
  `acme.tpl` by ACME. So no service certificate has to be issued again for this change; whether service certificates
  should name the CRL too is a question for the owner (1.5.1.3 says every leaf does).
- **Federation:** each site fetches the other sites' CRLs from `http://info.<their domain>/certs/crl/` (1.5.1.3).
- **Tests:** the sandbox's certs page test (`tests/sandbox/certs_page_test.sh`) runs against `info.<domain>/certs/`
  and `<host_ip>/certs/`, with the CRLs; `certs.<domain>` no longer resolves, has no certificate and nginx has no
  server for it; Step-CA's `leaf.tpl` on the host names the new CRL point. `tests/render.py` checks the same in the rendered
  configuration, templates and texts; `tests/pki/acme.py` that an ACME leaf names the new point; `tests/consent`
  the upgrade of an older settings file.

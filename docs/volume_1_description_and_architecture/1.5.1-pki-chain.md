## 1.5.1.1 PKI Chain

```
Root CA  (Step-CA's own, created by `step ca init` at setup; or bring your own with `byoc: true`)
    └── Step-CA Intermediate CA
            ├── Service certs  (issued by the running CA during setup's `certs` step)
            │       ├── dns.<domain>      → nginx DoH, BIND9
            │       ├── <host>.<ad_domain> → the domain controller (LDAPS, StartTLS; also names ad_domain and host_ip)
            │       ├── ca.<domain>, vault.<domain> (nginx and OpenBao), the landing page (its names, 1.4.2.6)
            │       ├── sso.<domain> (nginx, Keycloak) and postgres (Keycloak's database), with Keycloak
            │       ├── radius.<domain>   → FreeRADIUS EAP server cert (optional)
            │       └── fabric-ctl.<domain> → nginx → web UI (only when install_webui)
            ├── Web UI client certs  (setup's first admin; fabricctl client-cert <user>; CN = Keycloak username)
            ├── Hand-issued certs    (web UI Step-CA tab: signed CSRs, generated key pairs; capped by pki_manual_max_days)
            └── extra_certs          (signed offline with the intermediate key, per-entry config)
```

By default setup lets Step-CA create its own root and intermediate (keys in `/opt/stepca/data/secrets`, readable by the `step` user only). With `byoc: true` the root certificate, intermediate certificate and intermediate key come from `ca_crt_path`, `ica_crt_path` and `ica_key_path`; the root key never reaches the host. Step-CA also serves ACME and signs leaf certs via its intermediate CA. DNS-01 challenges can be fulfilled via a zone's TSIG key (RFC2136).

With BYOC the intermediate key path defaults to `ica_crt_path` with `.crt` replaced by `.key`; set `ica_key_path` in the vars file to override it.

Internal CA files are distributed to services as `root_ca.crt` volume mounts. The certificate page, with the CA's
files (`root-ca.crt`, `intermediate-ca.crt`, their `.pem` and Windows `.cer` forms, `ca-chain.pem`; `pki/publish_ca_certs.py`)
and the CRLs (1.5.1.3), is served at two URLs (1.5.1.5):

- `http(s)://info.<domain>/certs/` (`landing_page_cname`, 1.4.2), also over plain HTTP so a new device can fetch the CA
  before it trusts anything
- `http://<host_ip>/certs/`, for a device without fabric's DNS yet

`ca.<domain>` is Step-CA's API and ACME only: opening it in a browser (`/`, or an old `/certificates` link) redirects to
`https://info.<domain>/certs/`. Corrected 2026-10-11: this section named `https://ca.<domain>/pki/`, which nginx passes
to Step-CA, and download URLs at the info page's root that it does not serve.
Revised in 0.7.1 (2.1.4.6, 1.5.1.6): the page is also at `http://ca.<domain>/certs/` (nginx's default server), which
fabric's texts and scripts now name, and `ca.<domain>` in a browser goes to the host's own name's `/certs/`;
`info.<domain>` is an ordinary record the admin may change.

## 1.5.1.2 Certificate Relay

Core service certificates (`dns.<domain>`, the DC's `hostname_dc`, `ca.<domain>`, `vault.<domain>`, the landing page (`info.<domain>`; `certs.<domain>` until 0.7.0, 1.5.1.5), `sso.<domain>` and `postgres` with Keycloak, `fabric.<domain>` with the web UI, `radius.<domain>` with FreeRADIUS) are Step-CA leaf certs (`cert_service_days`, default 47 days, decision 2.1.5.4) issued by the running CA (`step ca certificate`) during setup's `certs` step. They are renewed at `cert_renew_after_days` (30) days old — or when missing, missing a name, not from this CA, or longer-lived than `cert_service_days` (2.1.5.7), or naming another CRL point than the current one (from 0.7.1, 1.5.1.6), or, for the landing page's, holding other names than its landing names (from 0.7.1, 1.5.1.7) — by the daily `fabric-certs.timer` (`fabricctl certs --scheduled`, 03:30 spread over half an hour, a missed night run at boot), by setup and by `fabricctl certs`. Each service takes its renewed certificate with the least interruption it allows (`pki/pick_up_cert.py`): nginx, Postgres and OpenBao reload on a HUP (OpenBao stays unsealed), Keycloak re-reads its files by itself, BIND, the DC and FreeRADIUS restart (seconds). Every run is recorded (`/opt/fabric/archive/cert-renewal.json`); a failed run or a service certificate under 7 days is a failure in `fabricctl doctor`, shown in `fabricctl status` and on the web console's Overview, and the CA within 180 days and issued certificates within 30 are warnings (2.1.5.5). `extra_certs` and admin client certificates are signed offline with the intermediate; client certificates are recorded in the issued-certificate ledger. The root's lifetime is `cert_root_ca_days` (default 10 years), the intermediate's a year less (2.1.5.6). There is no certbot container or cert-relay service. nginx reads the issued certs directly from the volume paths set during install. The DC's cert is copied to `/opt/samba/tls/` (mounted read-only into the DC; [1.6.5](1.6.5-samba-dc.md)). For webui client-certificate verification nginx trusts `/opt/nginx/certs/client-ca/ca-bundle.pem` (intermediate + root).

## 1.5.1.3 Revocation (CRLs)

Built in 0.6.3 (decision 2.1.5.10). Any certificate fabric issued can be revoked — a device's or a person's, a client
certificate, one a LAN machine got over ACME, a service certificate, a site CA this install signed — from the web
console's PKI page (Issued, permission `pki:revoke`) or `fabricctl certs revoke <serial|name> [--reason R]`. A
revocation is recorded (`/opt/fabric/archive/revoked-certs.jsonl`) and audited, and the CRLs are published at once.

- **Two CRLs**, signed with the CA keys on this host by `fabriclib/pki/publish_crl.py` (openssl, so certificates signed
  offline are covered as well as Step-CA's own): the **intermediate's** (every leaf) and the **root's** (the site CAs
  it signed; only where the root key is on this host — not with a brought-in root). Each is valid 7 days and published
  again on every setup run and every night by `fabric-certs.timer`.
- **Served** with the CA files, also over plain HTTP: `http://info.<domain>/certs/crl/intermediate.crl` (DER) and
  `.pem`, `root.crl` and `.pem`, and the same under `http://<host_ip>/certs/crl/` (on `certs.<domain>` until 0.7.0,
  1.5.1.5). Every leaf fabric issues from 0.6.3 names the intermediate's CRL as its distribution point
  (Step-CA's `leaf.tpl`); setup's service certificates from 0.7.0 (1.5.1.5).
  From 0.7.1 the point is `http://ca.<domain>/certs/crl/intermediate.crl` (1.5.1.6).
- **Checked** by FreeRADIUS (EAP-TLS, `check_crl = yes`; the CRLs follow the CA certificates in its `ca.pem`, with the
  other sites' intermediate CRLs fetched from `http://info.<their domain>/certs/crl/`, so a roaming device from another site is checked too)
  and by nginx for the web console's client certificates (`ssl_crl`, through `conf.d/client-crl.inc`; nginx checks
  every level of the chain, so this needs the root's CRL and is off where the root key is not on this host).
- **In force at once:** after a revocation nginx reloads and FreeRADIUS restarts (seconds); a revoked device is refused
  at its next authentication even while it is still linked. Unlinking stays the quick way to cut a device off;
  revocation is the lasting one.
- The issued list (PKI page, `fabricctl certs issued`) shows each certificate as valid, expires soon, expired or
  revoked.

## 1.5.1.4 ACME for machines on the LAN

Built in 0.6.3 (decision 2.1.5.8). Machines fabric does not run — a Proxmox host, a NAS, a printer, a server — get
certificates from fabric's CA automatically with any standard ACME client, at
`https://ca.<domain>/acme/acme/directory` (nginx passes it to Step-CA).

- **Names under fabric's domain only, never an address.** Step-CA's ACME provisioner issues with its own template,
  `acme.tpl` (`templates/stepca/acme.tpl.j2`), which refuses any other name or an IP address: a self-hosted Step-CA
  enforces issuance policies only for the whole authority, which would bind fabric's own service certificates too.
  Each certificate lives `cert_acme_lifetime_hours` (47 days) and names the intermediate's CRL (1.5.1.3), so it can be
  revoked like any other.
- **http-01** for a machine answering on port 80 under its name: Step-CA resolves the name through fabric's BIND and
  checks the challenge; nothing to enroll.
- **dns-01** for a machine without a web server: `fabricctl acme enroll <name> --dns` gives it a TSIG key (`acme-<name>`)
  that may change only `_acme-challenge.<name>.<domain>`'s TXT record — fabric's own per-name RFC2136 grants in the
  main zone (2.1.4.1 keeps dynamic records out of the rendered ones; these are challenge records only). Its settings,
  with the secret, are in `/opt/acme-<name>/rfc2136.ini` (certbot's RFC2136 format); the client sends updates to the
  host's BIND port (5053 behind the DNS filter). `fabricctl acme list` and `fabricctl acme remove <name>`. In the web
  console, Step-CA → ACME shows the directory and how to use it (`pki:read`) and the machines enrolled; enrolling
  and withdrawing need `tsig:manage`, since each is a TSIG key (also listed on the BIND page), shown once like any
  other and published by Apply.
- **Configured on every setup run:** `init_pki._configure_ca_json` converges `ca.json` (the provisioner, its lifetime and
  template, the authority's maximum), restarting Step-CA when it changed; before 0.6.3 it was written only once.
- Tested against the real Step-CA image (`tests/pki/acme.py`): a machine gets a 47-day certificate over http-01; a
  name outside the domain is refused even when its challenge passes; an address and a name the machine does not answer
  for get nothing.

## 1.5.1.5 The CA served at info.<domain>/certs; certs.<domain> dropped (0.7.0)

**Designed 2026-10-11 for 0.7.0 (decision 2.1.5.11); built 2026-10-11.** One place for the CA by name and one by
address:

- **`http://info.<domain>/certs/`** (and over HTTPS) and **`http://<host_ip>/certs/`** for a device with no DNS from
  fabric yet: the certificate page, every format, the install and join scripts, the fingerprints and the CRLs
  (`/certs/crl/`). Both were served since 0.6.3 (1.4.2.3); 0.7.0 makes them the only ones.
- **`certs.<domain>` goes, with no redirect** (the owner, 2026-10-11): its nginx server, its service certificate (no
  longer issued; the old files deleted at upgrade), its DNS name (`cname_certs`) and the var `hostname_certs`. The
  page, the scripts (`install-*.sh`, `join-linux.sh`), the landing page's links, the console's PKI and RADIUS guides,
  the first-steps text and the admin's README name `info.<domain>/certs/` instead. `ca.<domain>` opened in a browser
  goes to `https://info.<domain>/certs/`, and so does an old `/certificates` link on the info page.
- **Built:** nginx (`templates/nginx/nginx.conf.j2`) has no `certs.<domain>` server; setup issues no certificate for
  it (`setup/mint_service_certs.py`; what removed an older install's, and its settings, is retired with the
  upgrades from before 0.8.0, 2.1.1.61); `fabricctl doctor` checks `https://info.<domain>/certs/` and the `ca.<domain>` redirect
  (`setup/verify_install.py`).
- **The CRL's distribution point** in every leaf fabric issues becomes `http://info.<domain>/certs/crl/intermediate.crl`
  (Step-CA's `leaf.tpl` and `acme.tpl`). Leaves from 0.6.2 carry none, so the owner's install loses nothing. Leaves
  from the 0.8.0 candidates (test hosts only) name `certs.<domain>`: a device's certificate keeps the old point until
  it is issued again, and a checker that demands its CRL (Windows' EAP-TLS) refuses it meanwhile. Accepted for test
  hosts. **Found while building (2026-10-11):** fabric's own service certificates carry no distribution point at
  all — setup issues them through Step-CA's `admin` JWK provisioner, which has no template; `leaf.tpl` is used by
  hand-signed CSRs and generated pairs (`pki/sign_csr.py`) and offline-signed leaves (`pki/mint_offline_cert.py`),
  `acme.tpl` by ACME. **The owner, 2026-10-11: "add the CRL point to service certs".** The `admin` JWK provisioner
  now issues with `leaf.tpl` too (`setup/init_pki.py` converges ca.json on every apply), so every leaf names the CRL,
  as 1.5.1.3 says. A service certificate gains it when it is next issued: at its renewal (within `cert_service_days`,
  47 days) or when its names change; none is issued again early, which would only restart the services.
  `tests/pki/acme.py` issues one as setup does and checks it names the CRL.
- **Federation:** each site fetches the other sites' CRLs from `http://info.<their domain>/certs/crl/` (1.5.1.3).
- **Tests:** the sandbox's certs page test (`tests/sandbox/certs_page_test.sh`) runs against `info.<domain>/certs/`
  and `<host_ip>/certs/`, with the CRLs; `certs.<domain>` no longer resolves, has no certificate and nginx has no
  server for it; Step-CA's `leaf.tpl` on the host names the new CRL point. `tests/render.py` checks the same in the rendered
  configuration, templates and texts; `tests/pki/acme.py` that an ACME leaf names the new point; `tests/consent`
  the upgrade of an older settings file. Run 2026-10-11 in local Docker: render, nginx, consent, webui, pki (with
  renewal and acme), samba's `linux_join.py` and the sandbox (the certs page test 25 of 25, `certs.<domain>` not
  resolving, doctor) all pass; the host suite (a real machine) was not run.

## 1.5.1.6 The CRL point at the CA's own name (0.7.1)

Built for 0.7.1 (decision 2.1.4.6), when `info.<domain>` became a record the admin may rename, repoint or delete
(1.4.2.5). A certificate's CRL distribution point must answer for as long as the certificate lives, so it names a
name fabric keeps.

- **The point:** every leaf fabric issues names `http://<hostname_stepca>/certs/crl/intermediate.crl`
  (`ca.<domain>`): Step-CA's `leaf.tpl` (service certificates, signed CSRs and generated pairs, offline leaves) and
  `acme.tpl` (ACME). `ca.<domain>` is fabric's (refused in the DNS tab, 1.4.1.4), is not tied to the host's address,
  and on plain HTTP reaches nginx's default server, which serves `/certs/` (and so `/certs/crl/`) on every name; it
  did so on every install since 0.6.3, so nothing new is needed on the serving side. The address
  (`http://<host_ip>/…`) was rejected: a new address would leave every certificate pointing at the old one.
- **Certificates issued before:** they name `http://info.<domain>/certs/crl/intermediate.crl` (0.7.0). It keeps
  answering while `info` points at the host; once the admin renames, repoints or deletes it, a checker that demands
  the CRL is refused until the certificate is issued again. So fabric's own service certificates naming another
  point are **issued again at once**: `setup/mint_service_certs.py` treats a different point like a missing name
  (1.5.1.2), so the upgrade's `certs` step moves them all, and so does the nightly timer should one be missed. One
  naming no point at all (issued before 0.7.0) is left to its renewal, as 1.5.1.5 decided: it depends on no name, and
  a CA whose templates add none would otherwise issue it again on every run. Devices' ACME certificates move at their next renewal (30 days, 2.1.5.4); client
  certificates at their next issue. fabric itself never reads a CRL point: nginx and FreeRADIUS are given the CRL
  files (1.5.1.3).
- **Other sites' CRLs** are fetched at `http://ca.<their domain>/certs/crl/intermediate.pem`, then at
  `info.<their domain>` (`pki/publish_crl.py`).
- **Tests:** `tests/render.py` (both templates name the point at `hostname_stepca`, never `info`); the `pki` suite
  (`tests/pki/acme.py`: a certificate issued as setup does names the new point; `tests/pki/renewal.py`: a service
  certificate naming the old point is issued again, one naming the current point is left alone).

## 1.5.1.7 A landing certificate replaced for its names expires (0.7.1)

Built for 0.7.1 (decision 2.1.4.8). The landing page's certificate holds exactly its landing names (1.4.2.6); when they
change, the certificate is replaced at once. **Revised 2026-10-12 by the owner:** the one it replaces is not revoked;
it expires on its own (built first with a revocation, removed the same day).

- **Issued again at once:** `setup/mint_service_certs.py` marks the landing target exact: a certificate on disk whose
  names (`pki/common/cert_names.py`) differ from the landing names in any way, one more or one fewer, is issued again
  whatever its age, like a missing name (1.5.1.2). An apply runs it as soon as it finds them changed
  (`deploy/renew_landing_cert.py` → `setup/renew_service_certs.py`, so nginx picks it up with a reload); setup's
  `certs` step and the nightly timer do too.
- **The old one expires:** like every renewed service certificate (1.5.1.2) it is overwritten in nginx's folder and
  runs out within `cert_service_days` (47 days by default, 2.1.5.4); it is not in the revocation record or the CRL.
  The old name no longer reaches it: nginx serves only the landing names (1.4.2.6). An admin who wants it revoked
  anyway uses `fabricctl certs revoke <serial>` (1.5.1.3).
- **When the new one cannot be issued** (Step-CA down or refusing), the certificate on disk is left as it is, the
  renewal record (`cert-renewal.json`) holds the failure, which `fabricctl status`, doctor and the console's Overview
  show (1.5.1.2), and the apply ends with it as its error: integrations fail loudly (1.1.5).
- **Tests:** the `pki` suite (`tests/pki/landing.py`, against the real Step-CA image: after a rename the replaced
  certificate is in neither the revocation record nor the published CRL, and both it and the new one pass
  `openssl verify -crl_check`; an alias repointed elsewhere leaves the certificate at the next apply; with Step-CA
  stopped the apply fails, the certificate unchanged; `tests/pki/renewal.py`: the old `certs.<domain>` folder still
  found by folder, not by name).

## 1.5.1.8 The install scripts: certificate first, then HTTPS (0.9.2)

*Decision 2.1.1.87; the same as the join's first steps, 2.1.1.85 and 4.6.6.2.* A script fetched by plain HTTP and run as root can be swapped by
anyone on the path, and a fingerprint it checks itself vouches for nothing. So:

- **1.5.1.8.1 The page's steps:** the admin holds the root's SHA-256 from the page. The steps fetch the root by HTTP, compare it with that, then fetch
  `install-all-<domain_file>.sh` by HTTPS from the host's own name, trusting that root alone, not the system's store (2.3.1.49's trap), and run it with
  the fingerprint. The join's and install-all's steps are one macro of `index.html.j2`, `fetch_steps`.
- **1.5.1.8.2 `install-all`** takes the fingerprint, as a required argument, checks the root again itself and fetches each script it runs (`install-certs`, `-python`,
  `-firefox`, `-chrome`) the same way. A script that cannot be trusted is not run, and says why.
- **1.5.1.8.3 `install-certs`** takes the fingerprint too. Certificates may come by plain HTTP, as a machine does not trust HTTPS yet, because they are checked before
  any is installed: the root against the fingerprint; the intermediate proved by that root (`openssl verify`, the system's store left out); each file one
  certificate, as a second behind it would be trusted unchecked. Any failure installs nothing, the good root included.
- **1.5.1.8.4 Not changed:** the certificates page's by-hand commands (a certificate fetched to a file, Windows' too), which run nothing, and rely on the admin comparing
  the fingerprint as the page says. `-python`, `-firefox` and `-chrome` read the certificate `install-certs` put in the store and fetch nothing.
- **1.5.1.8.5 Tests:** `tests/samba/join_steps.py` runs the page's block and the real rendered scripts in real Ubuntu and Debian containers, with curl and with wget alone
  (right fingerprint however typed; wrong; none; another root served; a root that is not the server's; the server's root in the system store; an intermediate not
  under the root; a second certificate behind it). `tests/docs/check_join_fetch.py` fails if any page, template, code or manual fetches one by HTTP. In the lab: the
  joined campaign's `certs` step (3.1.5).

## 1.5.1.9 Any certificate revoked from the console (planned: 0.10.0)

Designed 2026-11-08 (decision 2.1.5.13; the owner: "the pki section... I don't see a way to revoke certificates").
Placed in 0.10.0 by the owner on 2026-11-08 (1.1.4).

**What is there today, and why this is a fix.** 1.5.1.3 promises that any certificate fabric issued can be revoked
from the console. The unit does take any serial (`pki/revoke_cert.py`: one not in the ledger is "issued over ACME or by
setup"), and so does `fabricctl certs revoke`. But the console reaches it only through **Revoke** on a certificate's own
page (`/pki/issued/<serial>`), and its Issued list is the hand-issued ledger alone (`pki/list_issued.py`,
`archive/issued-certs.jsonl`). A LAN machine's ACME certificate and fabric's own service certificates have no page, so
the console cannot revoke them. The list has no Revoke of its own either, so a person who does not open a row sees
none. Until 2.1.8.52 is built, a person without `pki:revoke` sees no button at all.

- **1.5.1.9.1 Every certificate in Issued.** Issued lists, each marked by where it came from:
  - **Issued here:** the ledger, as today.
  - **fabric's own:** the service certificates fabric keeps (1.5.1.2), read from the certificates on disk that the
    renewal record names: each one's names, serial, expiry and the service that uses it.
  - **Over ACME:** the certificates Step-CA issued to LAN machines (1.5.1.4). How fabric learns them is settled by a
    spike before the build (2.1.5.13): from Step-CA's own records if they can be read safely, otherwise from a record
    fabric keeps when each one is issued. Until then they are revoked by 1.5.1.9.2.
- **1.5.1.9.2 Revoke by serial or file.** Issued also has **Revoke a certificate not listed**: a serial, or the
  certificate's PEM pasted or uploaded (fabric reads the serial and checks that this install's CA signed it). It runs
  the same unit as the command line.
- **1.5.1.9.3 Revoke from the list.** Each row that may be revoked has **Revoke** beside it, opening the same
  confirmation as the certificate's page: the subject, the serial, the reason, and the subject's name typed again.
- **1.5.1.9.4 fabric's own certificates are replaced first.** Revoking a service certificate as it is would cut off
  every client that checks the CRL. So the confirmation says it will be issued again, and fabric issues and installs the
  new one (`setup/renew_service_certs.py`, the service reloaded or restarted as on renewal, 2.1.5.4) before the old
  serial is revoked. If the new one cannot be issued, nothing is revoked, and the console says why.
- **1.5.1.9.5 At once, as today.** A revocation is done at once (2.1.8.23), recorded, audited and published in the CRLs
  (1.5.1.3). `pki:revoke` as before.
- **1.5.1.9.6 Refused, saying why, nothing changed:** a serial this install's CA did not sign; a file that is not a
  certificate; one already revoked; a reason that is not in the list; the CA's own certificates (a site CA stays as
  1.5.1.3 says).
- **1.5.1.9.7 Tests** (3.1.2), against the real Step-CA: a LAN machine's ACME certificate revoked from the console is in
  the CRL and refused by nginx's client check; a service certificate revoked is replaced first and the service keeps
  answering with the new one; Step-CA down, nothing revoked; each refusal of 1.5.1.9.6; the new routes in the
  entry-point inventory with positive and negative cases.

## 1.5.1.10 Lifetimes and renewal set in the console (planned: 0.10.0)

Designed 2026-11-08 (decision 2.1.5.14; the owner: "or to adjust certificate lifetimes, we should be able to adjust
the auto renewal times"). Placed in 0.10.0 by the owner on 2026-11-08 (1.1.4).

**What is there today.** The lifetimes and renewal age are settings in the settings file, with no page in the console
(1.5.2.1): `cert_service_days` (47) and `cert_renew_after_days` (30) for fabric's own certificates, renewed by the
daily `fabric-certs.timer` (2.1.5.4); `cert_acme_lifetime_hours` (`1128h`) for LAN machines over ACME;
`stepca_cert_max_lifetime_hours` for the authority's maximum; and a **days** field on each hand-issued certificate.
The root and intermediate lifetimes are fixed once the CA exists (2.1.5.6), and stay so.

- **1.5.1.10.1 PKI → Lifetimes.** One page, with permission `pki:settings` (new; given to `fabric-pki-operator` and the
  administrators), shows and changes:
  - **fabric's own certificates:** lifetime (days) and **renew at** (age in days), with the date each one will next
    be renewed under the values shown.
  - **LAN machines over ACME:** lifetime (days). Each machine's own client chooses when to renew (certbot, for one,
    renews 30 days before expiry by default). The page says so, and shows the client setting that matches the
    lifetime.
  - **Hand-issued certificates:** the default the issue and sign forms fill in, and the longest they accept.
  - The authority's maximum is no longer a separate setting: it is worked out as the longest of the values above.
- **1.5.1.10.2 Checked, saying why, nothing changed:** a lifetime under 2 days or over 398 (the longest a browser
  accepts for a server certificate); **renew at** not at least 7 days before the lifetime's end (under 7 days left is
  already a warning, 2.1.5.4) or under 1 day; a hand-issued default over its own maximum.
- **1.5.1.10.3 Held for PKI's Apply.** A change carries no secret, so it is held like other settings (1.8.6.5); PKI gains
  an Apply for it. The Apply saves the settings, converges Step-CA's `ca.json` (the provisioners' lifetimes and the
  authority's maximum, `init_pki._configure_ca_json`) and restarts Step-CA when it changed. Then fabric's certificates
  older than the new **renew at**, or longer-lived than the new lifetime, are renewed at once, as the timer would.
  Certificates already issued keep their expiry until they are renewed.
- **1.5.1.10.4 The command line:** `fabricctl certs lifetimes` shows the values; `--service-days`, `--renew-after-days`,
  `--acme-days`, `--issue-default-days` and `--issue-max-days` change them, with the same checks and the same steps.
  The settings file keeps its keys; `stepca_cert_max_lifetime_hours` given there is refused when it is shorter than
  a lifetime it must allow.
- **1.5.1.10.5 Found while designing, to settle at the build:** 1.5.2.1 says `cert_acme_lifetime_hours` is written only
  at Step-CA's first start and cannot change, but `init_pki` converges it on every setup run (1.5.1.4). It also gives
  `stepca_cert_max_lifetime_hours` a default of `1128h`, while the code uses `131400h`. The build corrects 1.5.2.1 to
  match what the code does.
- **1.5.1.10.6 Tests** (3.1.2), against the real Step-CA: a shorter ACME lifetime set in the console is the lifetime of
  the next ACME certificate; a later **renew at** moves fabric's certificates' next renewal date, and one lowered below a
  certificate's age renews it at the Apply; each refusal of 1.5.1.10.2 leaves the settings unchanged; the change waits
  for PKI's Apply; `pki:settings` refused to a person without it; the command line and the console reach the same unit.

## 1.12.2.2 Shape

```
clients ── host_ip:53 ──> bind9-resolver (recursive, response policy zones)
                              ├─ fabric's zones ──> bind9 (authoritative, bind_dns_port 5053)   never filtered
                              └─ internet names ──> Cloudflare over DoT (1.1.1.1, 1.0.0.1)
```

A second BIND, `bind9-resolver`, answers clients; the authoritative BIND (1.4.1) stays authoritative-only, so a bad
list or a resolver restart never touches the zones ACME, Kea, federation and the AD zone depend on. DHCP hands out
only an address, so whatever answers clients is on 53 (1.12.1.2): the resolver takes `host_ip:53` and BIND moves to
`bind_dns_port` (5053), as it does behind AdGuard.

## 1.12.2.3 Settings

The settings are listed in [1.1.9.9](1.1.9-optional-parts.md#1199-dns-filter-the-bind-resolver); they live in the
vars file, so a reinstall keeps them. `dns_filter: bind` turns the resolver on (`install_resolver`).

## 1.12.2.4 The container

- **`bind9-resolver`**, from fabric's `bind9` image (the same BIND 9.20, 2.1.1.5) with a configuration of its own.
  It is a unit of its own with no `requires`: an apply that restarts the authoritative BIND never takes the clients'
  DNS down.
- **Its own service account**, `resolver` (`fabric-resolver`, 613): it reads the lists and writes its logs, and
  nothing of the authoritative BIND's (keys, zones, the AD zone's database).
- On `fabric_net` at `ip_resolver` (10.255.0.33). No capabilities, read-only root, `no-new-privileges`; Docker
  publishes `host_ip:53` (TCP and UDP) to its port 53.
- `named -f` (not the image's `-g`, which ignores the logging statement, 2.3.12.1.16).
- Memory limit: **128 MiB**, planned with the others (1.2.4.3; `resolver_mem_limit` fixes it): since 0.7.0 it
  holds no lists (AdGuard Home does, 1.12.3.9).
- Health check: `rndc status` with the resolver's own control key (`resolver_rndc_secret`, generated per install).
- Certificates for the upstream's DoT: the host's CA bundle (`/etc/ssl/certs/ca-certificates.crt`), mounted
  read-only, kept current by the host's updates.
- Folders under `<base>/resolver/`: `config` (named.conf and the rules zones, rendered at apply), `lists` (the
  converted lists, written by the list job), `log` (the query and RPZ logs), `cache` (named's working folder), `tls`
  (the DNS name's certificate for DoT and DoH, 1.12.2.16).
- Ports: `host_ip:53` (TCP, UDP) and `host_ip:853` (TCP, DoT) published; 8053 (DoH from nginx) on fabric_net only.

## 1.12.2.5 The main view

One view in step 2, `everyone` (groups are chained views on it from step 6, 2.3.12.1.16):

- `recursion yes` for the networks AdGuard allowed (`lan_cidr`, `fabric_subnet`, `security.firewall_allow`);
  everyone else is REFUSED.
- **fabric's zones** — this site's domain, the organisation's, the linked sites', the reverse zones, the AD zone —
  are forward zones to the authoritative BIND (`ip_bind9`, port 53 on `fabric_net`), and `validate-except` (a
  private zone has no DNSSEC chain from the root).
- `dnssec-validation auto` for everything else.
- `response-policy`, first match wins: **`fabric.rpz`** (passthru for fabric's zones: never filtered, even when a list
  names them) → **`owner.rpz`** (the owner's allows and blocks) → **one zone per list**, in the settings' order.
  `break-dnssec yes` and `qname-wait-recurse no`.
- A blocked name answers **NXDOMAIN** (2.1.12.3).

## 1.12.2.6 Lists: fetched, converted, loaded

- A list is `{name, url}` in `dns_filter_lists`; the default is the **AdGuard DNS filter** (2.1.12.3).
- **Converting** (`dns_filter/convert_list`): hosts files, plain domains, RPZ as published, and AdGuard's DNS syntax
  (`||name^`, `@@||name^`, `||*.name^`, `$denyallow`, `$dnsrewrite` to a name, `$badfilter`, `$important`,
  `||1.2.3.4^` as an `rpz-ip` trigger). Rules RPZ cannot express are **skipped and counted**, never guessed:
  wildcards inside a name, regular expressions, other modifiers, unanchored patterns. What the spike measured:
  2.3.12.1.16.
- **Each list is a zone of its own**, `<id>.list.rpz`, where `<id>` is the first 12 hex digits of the SHA-256 of
  its URL, so reordering or renaming a list does not reload it. The RPZ log names that zone, so a block is traced
  back to its list.
- **Checks before a list is used:** at least one rule converted, at most 2,000,000 RPZ records, `named-checkzone`
  passes. A list that fails keeps its last good copy; a list never fetched yet is left out of the configuration,
  so the resolver never starts on a missing file.
- Each list's state is kept in `<base>/resolver/lists/state.json`: last fetch, last success, rules converted and
  skipped, RPZ records, its estimated memory (records × 0.53 KB, 2.3.12.1.17) and the last error.

## 1.12.2.7 The owner's rules

`dns_filter_allow` and `dns_filter_block`: names, each meaning **the name and every name below it** (AdGuard's
`@@||name^` and `||name^`). They make `owner.rpz`, before every list: an allow beats every list, a block applies
whatever the lists say. A name in both, or one inside fabric's own zones, is refused by the settings check.

## 1.12.2.8 Upstreams

`dns_filter_upstreams`: `[{address, name}]`, forwarded to over **DoT** (port 853) with the certificate's name
verified. Default: Cloudflare, `1.1.1.1` and `1.0.0.1`, name `cloudflare-dns.com` (2.1.12.3). `[]`: no forwarders —
BIND resolves from the root servers itself (plain DNS to the internet's servers).

## 1.12.2.9 Logs

- **Query log** and **RPZ log**, each a file in `<base>/resolver/log` (rotated: 2 × 20 MB). The query line names the
  client and its view (the group, from step 6); the RPZ line names the rule's zone (the list or `owner.rpz`).
  Read into Postgres by the query-log job (1.12.2.13).
- Everything else (start, loads, errors) to the journal, like every container.

## 1.12.2.10 Deploy, apply and the list timer

- **Apply** renders the configuration and the rules zones; a change is reloaded by the running resolver (`rndc
  reload`: the configuration and every zone whose file changed), or the resolver restarts when its compose file
  changed. A list in the settings that has no converted copy yet is fetched
  during the apply (the resolver then starts with it); an apply offline leaves it out until a fetch succeeds.
- *Since 0.8.0 (2.1.4.9):* an apply, DNS' own Apply and a zone's add or removal make the resolver forget the names
  of fabric's zones whose records they changed (`rndc flushname`, every view; a new or removed zone whole), so a name
  published after a client asked for it resolves at once: 1.4.1.6.
- **`fabricctl dns-filter lists`** fetches every list now, converts it, and reloads only the zones that changed
  (`rndc reload <zone>`): the others keep answering. `--scheduled` is the timer's run.
- **`fabric-dns-lists.timer`**: daily at 04:15 (spread by up to 30 minutes, a missed night runs at boot), only while
  `dns_filter` is `bind`.
- **`fabricctl dns-filter status`**: each list's state (1.12.2.6) and the resolver's.
- *Since 2026-10-24 (2.1.10.46):* an apply, DNS' own Apply and Sync now make the resolver forget the names of
  fabric's zones whose records they changed (`rndc flushname`, every view), so a name published after a client
  asked for it resolves at once: 1.10.4.44.

## 1.12.2.13 The query log and statistics

Decisions 2.1.12.4 (7 days, admins only; statistics without client addresses, 90 days), 2.1.12.5 (collected
every 5 minutes and on demand) and 2.1.12.10 (since 2026-10-30 only the timer and `fabricctl dns-filter ingest`
collect: a read never does).

- **Where:** fabric's Postgres, a database `dnslog` owned by a role of its own, `fabric_dnslog`; no other role may
  connect to it (`CONNECT` revoked from `PUBLIC`), so Keycloak's role never sees it. It exists only where Postgres
  does (`install_keycloak`, on by default): without it the resolver still logs to its files, and the status says
  the query log is off.
- **How fabric talks to it:** SQL on stdin to `psql` in the Postgres container over its local socket, as fabric's
  other Postgres work does (`setup/ensure_db_rotation`): no client library on the host, no password, nothing on a
  command line but checked values. Searches are bound as `psql` variables (`:'name'`), never pasted into SQL.
- **Tables:**

  | Table | Holds | Kept |
  |---|---|---|
  | `queries` | time, client address and port, view (the group), name, type; when a response policy rewrote it: the action (`NXDOMAIN`, `PASSTHRU`, `Local-Data`) and the zone (a list's `<id>.list.rpz`, `owner.rpz`, `fabric.rpz`), `blocked` when the answer was NXDOMAIN | 7 days |
  | `stats_hourly` | per hour and per zone (`''` for all): queries, blocked | 90 days |
  | `stats_blocked` | per day: blocked names, their zone and count (no client) | 90 days |

- **Collecting** (`dns_filter/ingest_dns_log`): the new lines of `query.log`, then of `rpz.log`, from where the last
  run stopped; a rotated file (BIND renames it `.0` at 20 MB) is finished first, found by its inode. Each RPZ line
  marks its query (same client, port and name, within 2 seconds). The hours and days the run touched are recomputed
  from `queries`, so the statistics never drift. Then rows past 7 days (queries) and 90 days (statistics) go. Its
  place in the files is kept in `<base>/resolver/ingest.json` (root's: the resolver cannot move it) and moves only after Postgres took the lines.
- **When:** `fabric-dns-log.timer` every 5 minutes (`fabricctl dns-filter ingest --scheduled`, installed while the
  resolver and Postgres are both on), or `fabricctl dns-filter ingest` by hand. *Revised 2026-10-30 (2.1.12.10):* the
  reads below no longer collect first (each view of the console's tab waited on the timer's lock, read the log and
  asked AdGuard Home before it showed anything); each read is one query, as fresh as the timer's last run, and says
  when that was (the time of `ingest.json`, touched by every run). Before the timer's first run they say the log is
  not read yet.
- **Reading:**
  - `fabricctl dns-filter log [--client ADDRESS] [--name NAME] [--blocked] [--limit N]`: newest first, at most 500;
    a name matches it and every name below it.
  - `fabricctl dns-filter stats`: the last 24 hours by hour, the last 7 days' totals, blocked per list, the top
    blocked names.
  - Agent: `GET /v1/dns-filter` (statistics and each list's state, `dns:filter`) and `POST /v1/dns-filter/querylog`
    (a search in the body, `dns:querylog`: the admin bundle only). The web console's tab uses them (step 5): a view is
    one Postgres query (the statistics), the query log's two (with its search).

## 1.12.2.14 The web console's DNS filter tab

The tab **DNS filter** (`/dns-filter`), shown with `dns:filter` or `dns:querylog` (2.3.12.1.8):

- **Overview:** queries and blocked per hour (24 hours), the 7 days' totals, blocked per list and rules zone, the
  most blocked names; each list's last fetch and good copy, its rules and memory. It and the query log say when fabric
  last read the resolver's log (2.1.12.10).
- **Lists:** the lists in use (remove; fetch now). Add one from **AdGuard's catalogue**, by group (general, security,
  regional, other) with its description and home page, or by URL.
- **Rules:** the names allowed past every list and the names blocked whatever the lists say (add, remove).
- **Query log** (`dns:querylog`): search by client, name, blocked only; each blocked line names its list or rule and
  offers *Allow*, each other line *Block* (a rule, `dns:filter`).
- **Settings:** the DoT upstreams (`<address> <certificate name>` pairs, or none: the root servers).

Each change is a settings change (the vars file, under its lock, audited) applied at once like the DHCP tab's: the
resolver reloads, nothing restarts. The agent (fabric-agent) has no internet by design (its unit allows only
localhost and fabric's subnet): **fetching** a list or the catalogue is the `fabric-dns-lists` job's, which the
agent starts (`systemctl start fabric-dns-lists.service`) when a list is added or *Fetch now* is pressed. The job
fetches the lists and AdGuard's catalogue (kept in `<base>/resolver/lists/catalogue.json`, so the catalogue is read
from AdGuard's registry daily and on demand, never shipped with a release, 2.3.12.1.11 Q13), and when a list it
fetched is not in the running configuration yet, applies (`dns_filter/refresh_lists`).

Agent routes, `dns:filter` unless said: `GET /v1/dns-filter` (the overview and the catalogue);
`POST /v1/dns-filter/lists`, `/v1/dns-filter/lists/delete`, `/v1/dns-filter/rules`, `/v1/dns-filter/rules/delete`,
`/v1/dns-filter/upstreams`, `/v1/dns-filter/fetch`; `POST /v1/dns-filter/querylog` (`dns:querylog`). The groups'
routes: 1.12.2.15.

## 1.12.2.15 Client groups and safe search

Design: 2.3.12.1.5, 2.3.12.1.14, the spike's chained views (2.3.12.1.16) and Q14 (groups only add). Step 6.

**Settings** (vars, so a reinstall keeps them; each change audited and applied at once, like the rest of 1.12.2.14):

- *everyone* (the main view): `dns_filter_safe_search` (`false` by default) and `dns_filter_youtube` (`strict` or
  `moderate`, read only while safe search is on).
- `dns_filter_groups`: a list of groups, each `{name, clients, safe_search, youtube, lists, allow, block}`.
  - `name`: lowercase letters, digits and `-`, at most 32 characters; not `everyone`. It is the view's name in the
    query log.
  - `clients`: IPv4 addresses and subnets (`192.168.4.50`, `192.168.10.0/24`), at least one. Each must lie inside the
    networks the resolver answers (`lan_cidr`, `security.firewall_allow`) and outside fabric's own (`fabric_subnet`,
    `127.0.0.0/8`: the chain's own hop, below). A subnet with host bits set, or the same address or subnet in two
    groups, is refused.
  - `safe_search`, `youtube`: as for *everyone*.
  - `lists`: lists **added** for this group (`{name, url}`), never one already on *everyone*.
  - `allow`, `block`: names, each with every name below it, like the owner's rules (1.12.2.7).

**The most specific address wins.** A client in a group's subnet and another group's address belongs to the address's
group (AdGuard Home did the same). Each group's `match-clients` lists, before each of its subnets, the more specific
entries of the other groups inside it as exclusions (`!192.168.10.7; 192.168.10.0/24;`), so the groups' matches never
overlap and their order does not matter.

**Chained views** (the spike's `MODE=chain`). A client in no group is answered by the main view, `everyone`, as
before. Each group is a view placed before it:

- `forward only; forwarders { 127.0.0.1; }`: what the group's own policy does not answer goes to the main view, which
  applies fabric's zones, the owner's rules, everyone's safe search and every list on *everyone*. The lists are loaded
  once, in the main view, so a group costs only its own zones (2.3.12.1.16).
- Its response policy, first match wins: **`group-<name>.rpz`** (the group's allows as passthru, then its blocks) →
  **`safesearch-strict.rpz`** or **`safesearch-ytmoderate.rpz`** when its safe search is on → **its own lists** (each
  list's zone, a copy in this view: its memory counts again).
- Each **allowed name** is also a forward zone straight to the upstreams (over DoT, the same `tls` blocks), or, with
  no upstreams, `forwarders { }` (resolved from the root servers): the name never reaches the main view's lists or
  the owner's blocks. Groups only add (Q14): a group cannot switch a list on *everyone* off, only allow names past it.
- `dnssec-validation no` (the main view validates what it answers; the upstream what an allow sends it: the spike's
  finding) and `max-ncache-ttl 0`: a blocked answer from the main view is never cached in the group's view, so every
  blocked query passes through the main view and is logged as blocked.
- Everyone's safe search reaches a group through the chain. A group's own setting is applied first, so a group may
  choose YouTube moderate where *everyone* is strict; it cannot turn everyone's safe search off.

**Safe search** is two rules zones fabric renders from one table (`dns_filter/common/safe_search`), which the console
reads too, so the switch's label always names what the zone does (2.3.12.1.14):

| Engine | Names rewritten | Answer |
|---|---|---|
| Google | `www.google.<domain>` for each domain Google publishes as its search sites (`google.com/supported_domains`: 187 on 2026-10-10) | `CNAME forcesafesearch.google.com` |
| YouTube | `www.youtube.com`, `m.youtube.com`, `youtubei.googleapis.com`, `youtube.googleapis.com`, `www.youtube-nocookie.com` | `CNAME restrict.youtube.com`, or `restrictmoderate.youtube.com` (moderate) |
| Bing | `www.bing.com`, `edgeservices.bing.com` | `CNAME strict.bing.com` |
| DuckDuckGo | `duckduckgo.com`, `www.duckduckgo.com`, `start.duckduckgo.com` | `CNAME safe.duckduckgo.com` |
| Yandex | `yandex.<domain>` and `www.yandex.<domain>` for its 24 country domains, `ya.ru`, `яндекс.рф` (52 names) | `A 213.180.193.56` (family search) |
| Pixabay | `pixabay.com` | `CNAME safesearch.pixabay.com` |
| Ecosia | `www.ecosia.org` | `CNAME strict-safe-search.ecosia.org` |

Not covered (no DNS mechanism): Brave Search and Startpage. The console says so beside the switch.

**Memory.** The resolver's estimate is the sum, over every view, of the lists loaded in it (each list's records ×
0.53 KB, 1.12.2.6) plus 16 MiB for the resolver itself. A list whose copy would take the estimate past 80% of
`resolver_mem_limit` is **left out** of the configuration, and its state says so ("left out: it would pass the
resolver's memory limit"): the resolver never starts into its memory limit. Lists are counted in order, *everyone's*
first, then each group's.

**The query log through the chain.** A group's query is logged twice: by the group's view (the client, `view kids`)
and, when it is passed on, by the main view (client `127.0.0.1`). The collector (1.12.2.13) drops the main view's
copies. A rewrite the main view logged for `127.0.0.1` (a shared list or the owner's block) is put on the group query
of the same name it answered (each group query of that name within 2 seconds with no rewrite of its own), so the log
and the statistics name the real client and the list that blocked it.

**Client addresses** must reach the resolver unchanged. Docker's userland proxy would replace them with its gateway
address; fabric's hardened `daemon.json` turns it off (1.2.6; checked on the test Pi, 2.3.12.1.22). While groups exist
and the proxy is not off, `fabricctl status` and the console's Overview list it as a relaxed setting: "client
addresses hidden: every client is answered as *everyone*".

**From AdGuard Home:** the import 0.7 used to carry 0.6's AdGuard Home settings over (persistent clients as groups among
them) was deleted in 0.8.0, its one caller retired (stale-code register S12, the owner 2026-10-20).

**The console:** the DNS filter tab gains **Groups** (`?view=groups`): each group's clients, safe search, lists and
rules, added and removed like *everyone's*. The switch reads **Strict safe search** and lists every engine and name
count from the table above, with YouTube's strict/moderate choice beside it; the same switch is in **Settings** for
*everyone*. Agent routes (`dns:filter`): `POST /v1/dns-filter/groups` `{name, clients}` (add, or change the
clients), `/v1/dns-filter/groups/delete` `{name}`, `/v1/dns-filter/safe-search` `{group ('' = everyone), on,
youtube}`; the lists and rules routes take an optional `group`.

## 1.12.2.16 DNS-over-TLS and DNS-over-HTTPS for clients

Decision 2.1.12.2 (moved to the resolver by 2.1.12.3). Encrypted DNS from clients reaches the resolver, so it is
filtered like plain DNS and answers internet names too (before 0.7, DoH reached the authoritative BIND: fabric's names
only).

- **The certificate:** the DNS name's (`hostname_bind9`, `dns.<domain>`, with `ns.<domain>`), the one nginx serves for
  DoH, issued by Step-CA and renewed with the other service certificates (`setup/mint_service_certs`): a third copy goes
  to `<base>/resolver/tls`, readable by the resolver's account, and a renewal restarts the resolver (a few seconds
  without DNS, once a month). Clients must trust fabric's root CA, as for every service; the public wildcard
  (2.1.5.9) will serve here too when it is built.
- **DoT:** the resolver listens on 853 (TCP) with that certificate; Docker publishes `host_ip:853`, LAN-only like every
  published port (DOCKER-USER, 2.1.2.13), and only while the resolver is on. Clients connect directly, so the
  resolver sees their own address: groups, the query log and statistics work as for plain DNS.
- **DoH:** `https://<dns name>/dns-query`, as before: nginx terminates TLS and passes the query over cleartext HTTP/2
  to the resolver's plain DoH listener (port 8053 on fabric_net, never published). The resolver sees **nginx's
  address**, not the client's: a DoH client is answered as *everyone* and logged as nginx. BIND cannot read the
  client's address from nginx (it takes the PROXY protocol, which nginx's HTTP proxy does not send); a client that
  needs its group uses plain DNS or DoT.
- **Until the certificate exists** (a first deploy before the certificates step), the resolver starts without the DoT
  and DoH listeners and takes them at the next apply.
- **Doctor** checks DoT beside DoH: a query to `host_ip:853` with the certificate verified against fabric's root must
  answer the host's address (`common/dot_query`).
- With the resolver off (`dns_filter: none`), DoH goes to the authoritative BIND as before, and nothing listens on 853.

## 1.12.2.17 The tab refreshes itself while a fresh install's first fetch runs (0.7.1)

Built for 0.7.1 (decision 2.1.2.22 item 1; the owner at the 0.7.0 test install: the "page did not automatically
refresh and load the adguard dns filters"). On a fresh install the lists job (1.12.2.14) fetches AdGuard's catalogue
and the ticked lists a minute or so after setup; until then the Lists section says "not yet" and "The catalogue has
not been read yet", and it stayed so until the page was reloaded by hand.

- **While the first fetch runs** — the filter on, and AdGuard's catalogue not read yet or a ticked list never
  fetched (no copy and no failed attempt) — the Overview and Lists sections say so and refresh themselves every
  10 seconds (`webui/views/dns_filter.py`). It is a `<meta http-equiv="refresh">` in the page's head, only while
  pending: no script, so the strict Content-Security-Policy stands (1.8.2), as the job pages do (1.8.4.2).
- **Then it stops:** once every ticked list has a copy (or a failed attempt, shown as *failed*) and the catalogue is
  read, the page carries no refresh. It also stops after 30 refreshes (five minutes; the count rides in the
  address, `wait=`), and then says what to do: *Fetch every list now*, or `sudo fabricctl dns-filter status` on the
  host.

## 1.12.2.18 Cached answers last at most 5 minutes (0.9.0)

*Added 2026-10-31 (2.1.12.11); built 2026-10-31 on `dev/0.9.0` (2.1.1.71).* No cache on the DNS path keeps an answer
more than 300 s, so an answer is asked again (a signed one validated again, 2.1.12.7) or dropped after 5 minutes:

- **The filtering resolver** (BIND): `max-cache-ttl 300` and `max-ncache-ttl 300` in its options
  (`templates/resolver/config/named.conf.j2`), so in every view; a client group's view keeps no miss at all (below). Before
  0.9.0 it set neither, so BIND's defaults applied: a week for an answer, 3 hours for a miss. An upgrade's apply
  renders the file and the running resolver reloads it (no restart).
- **AdGuard Home** (behind it, 1.12.3): `cache_ttl_max: 300` in `templates/dnsfilter/AdGuardHome.yaml.j2` (`0`, no
  cap, before 0.9.0). Its API cannot set it, so it is one of the file's fixed parts (1.12.3.4): the upgrade's apply
  writes the file again and restarts AdGuard once.
- **A client group's view keeps no miss:** `max-ncache-ttl 0` in each group's view (1.12.3.6), so a name published
  after a group's client asked answers it at once; its answers keep the 300 s cap (the owner, 2026-10-31, 2.1.12.11:
  the chained views of 1.12.2.15 had set it, and 1.12.3.6 had dropped it in 0.7.0). Everyone's view takes the
  options' 300 s.
- **Unchanged:** fabric's own zones keep their 30 s miss and are flushed by an apply (2.1.4.9, 1.4.1).
- **Tests:** the render test (both caps in the resolver's options, `max-ncache-ttl 0` in each group's view and not in
  everyone's, AdGuard's `cache_ttl_max` 300 in
  its fixed part); the `resolver` suite with real containers (both caps in the deployed configuration, AdGuard's file;
  a record its zone gives 86400 s answered through the resolver, asked and from its cache, with a TTL never over
  300 s; with the internet, `a.root-servers.net` (3600000 s at the root) and a `.com` miss (900 s) likewise); its
  `groups.py` (each group's view keeps no miss in the deployed configuration; a name published after a kid and an
  adult asked answers the kid at once, while the adult's view still holds its NXDOMAIN).

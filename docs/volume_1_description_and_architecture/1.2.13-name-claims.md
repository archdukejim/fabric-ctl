## 1.2.13.1 Status and why

**Designed 2026-10-17 for 0.8.0, not built** (decisions 2.1.2.27, 2.1.8.12; global Rule 9's collision test). The
owner's production install of 0.7.2 named its host `fabric`, the label of the web console's default address
(`fabric.<domain>`): nginx gave the name to the landing page and the console was unreachable at its address, with
every other check green (2.3.1.22). Each value was valid alone, so no test caught the pair. 0.8.0 lists everything
fabric claims and checks every pair, and against the machine and network, before using it.

## 1.2.13.2 The inventory

Every claim, the setting that decides it, and what it must not collide with. The list is kept in code
(`fabriclib/common/claims`) and this table is generated from it, so a new claim cannot be added without its checks.

| Kind | Claims (default) | Setting | Must not collide with |
|---|---|---|---|
| Host's name | `<hostname>.<domain>` | `hostname` | every DNS name below; the AD domain's DC names; 15 characters (NetBIOS) |
| DNS names in the site's zone | `ca`, `dns`, `sso`, `vault`, `ntp`, `radius`, `federation`, `ns`, `filter`, the landing alias `info`, the console's label (1.2.13.4) | `cname_*`, `landing_page_cname`, `webui_hostname` | each other; the host's name; the domain itself; a record the admin made that points elsewhere |
| AD names | the AD domain, its NetBIOS name, the DC's name (`dc-0001` to `dc-1999`, 2.1.6.63; chosen by fabric, 2.1.6.65) | `ad_domain`, `dc_name` | fabric's DNS domain (a sibling, never the same); the host's name; another DC or computer in the domain |
| Networks | the containers' network `10.255.0.0/24` and its addresses | `fabric_subnet`, `ip_*` | the LAN, every DHCP subnet, the host's routes, and the site's other networks in the address plan |
| Ports on the host | DNS 53, HTTP 80, HTTPS 443, DNS-over-TLS 853, NTP 123, the DC's (88, 135, 389, 445, 464, 636, 3268, 3269, RPC `49152-49251`), RADIUS 1812/1813, DHCP 67 | the parts installed; `ad_rpc_ports` | a service on the host already listening there (other than fabric's own) |
| People's user names | `fabric-admin` (the Enterprise Admin, 2.1.6.69); the groups fabric makes (`directory-admins`, `dc-hosts`, `server-admins`, `desktop-admins`, `network-admins`, `site-*`, `machines-*`, `hosts-*`, `rodc-cache-*`, the grants' computed `grant-*` and `access-*`); the `fabric-*` accounts; the DCs' `dc-NNNN`; the system's and AD's built-in accounts (`root`, `admin`, `administrator`, `guest`, `krbtgt`, `nobody`, `daemon`, `users`) | `webui_admin_user` | the first Directory Administrator's user name, refused with why at setup's questions (`person_name_refused`, 1.6.12.16.2) |
| Accounts and ids | the `fabric-*` service accounts, uids and gids 600 to 610, the groups they use | `ids` (2.1.2.4) | an existing user, group, uid or gid on the host |
| Paths and units | `/opt/fabric`, `/etc/fabric`, `/run/fabric-setup`, `fabric.target` and the `fabric-*` units | none | anything there that fabric did not put there |
| Certificates | each name a certificate is issued for | follows the names | two certificates naming one name |

## 1.2.13.3 When each is checked

- **At setup's plan**, before anything changes: every pair in the inventory, then each against the machine (ports
  listening, accounts and ids, paths) and the network (the LAN and its routes). A collision is refused with what it
  collides with and the setting that changes it ("the host's name `fabric` is the web console's address: name the host
  differently, or set `webui_hostname`"). Unattended, the run stops with the same message.
- **At every change of a setting** that is in the inventory (the wizard, `fabricctl settings import`, the console's
  pages, a record added in the zone): the same checks for what changes.
- **At `fabricctl doctor`**: the checks again, so a collision that came from outside (a service installed later on a
  port fabric uses) is reported with what to do.
- **The landing page** never takes a name that another of fabric's services answers at (`landing_names` leaves them out
  today, but not the host's own name: that gap is closed here).

## 1.2.13.4 The web console's default name

The console's default label becomes **`fabric-ctl`** (`fabric-ctl.<domain>`, the product's name, 2.1.1.53) for a new
install. An install that already has a console address keeps it on upgrade (`cname_mgr` or `webui_hostname` as
installed): an address people use never moves by itself. The setting stays: any name, checked as 1.2.13.3 says.

**Built 2026-10-23** (the default only; the checks of 1.2.13.2 and 1.2.13.3 are not built): `cname_mgr` defaults to `fabric-ctl` in `templates/vars.yaml.j2`. An install's `vars.yaml` holds its own `cname_mgr` (0.7.x wrote `fabric` there), so an upgrade renders the address it had; `tests/setup/import_old_vars_test.py` checks both (note [2.3.8.3.4](../volume_2_engineering_decisions/2.3.8-webui-notes.md#23834-the-consoles-default-address-2026-10-23)).

## 1.2.13.5 Tests

- **A collision case for every row** of the inventory, refused at setup's plan with its message and nothing changed:
  the host named after each of fabric's DNS labels (`fabric`, `fabric-ctl`, `ca`, `dns`, ...); two `cname_*` the
  same; the AD domain equal to the DNS domain; the containers' network inside the LAN; a port in use; a uid taken;
  `/opt/fabric` holding something not fabric's.
- **The sandbox** installs once with a colliding host name and expects the refusal, then with the default and expects
  the console at `fabric-ctl.<domain>` (2.3.1.22's case, kept).
- **The upgrade test** from 0.7.1 keeps the console's old address.
- **doctor** reports a port taken after the install.

## 1.6.13.1 Status and scope

**Designed 2026-10-18 for 0.8.0** (decisions 2.1.6.72 to 2.1.6.76; proposal 2.3.6.15). **D1 built 2026-10-19:**
the folders, the groups, the tiers' AD rights, ids per DC, service accounts per DC, Keycloak, the GPOs at OU=machines,
the machine types and the fabric host (1.6.13.10); grants (1.6.13.4 to 1.6.13.7) are not built (D3, D4). It is the home of
who may do what, where, below the tiers of [1.6.12.2](1.6.12-domain-management.md) (2.1.6.68). It replaces the site
layout of 1.6.3 (`OU=sites`), the access per site of 1.6.3.10, and 1.6.11's site groups, OU log-on policies and site
sudo rule (1.6.11.2 to 1.6.11.4). What 1.6.11 builds on a machine (the join, sssd, SSH by Kerberos, resolved, the
`fabric-managed` timer) stays; only who gets in, and how that is written, changes.

## 1.6.13.2 The directory's folders

One set of folders for the whole domain, made by setup, fabric's own and marked so (1.6.12.2):

| OU | Holds |
|---|---|
| `OU=people` | every person, flat (2.1.6.64) |
| `OU=service-accounts` | accounts that are not people: fabric's own (`fabric-agent`, the Keycloak bind, ...) and an admin's |
| `OU=groups` | every group; `OU=fabric` inside it for the grants' computed groups (1.6.13.4) |
| `OU=service-accounts` (per DC) | `fabric-agent-dc-NNNN`, `fabric-keycloak-dc-NNNN`, `fabric-radius-dc-NNNN` (2.1.6.82) |
| `OU=machines` | `OU=servers`, `OU=desktops`, `OU=network`: one per machine type |
| `OU=fabric-hosts` | the fabric hosts' member accounts (2.1.6.49) |
| `OU=devices`, `OU=device-roles` | 802.1X's devices and their roles (2.1.6.80) |
| `OU=networks` | the address plan's networks |
| `OU=sudoers` | the `sudoRole`s fabric writes and an admin's own |
| `CN=fabric,CN=System` | fabric's state (2.1.6.79): `CN=dcs` (each DC's id ranges and marks, its site), `CN=grants` |

AD's own containers (Domain Controllers, Users, Computers, Builtin) stay as AD has them; the domain's default
containers for new users and computers point to `OU=people` and `OU=machines`. An admin adds folder OUs under
`OU=people`, `OU=service-accounts`, `OU=groups` and each type's OU, as they like. **OUs grant nothing** (2.1.6.72):
fabric links no GPO by folder, and nothing fabric decides reads an object's OU.

## 1.6.13.3 The groups: sites, machine types, administrators

- **Sites:** `site-<name>` for each site (the root's at setup, a branch's at its join, 1.9.8), holding the site's people
  and machines; a person who works at two sites is in both (roaming, 2.1.9.12). The join puts a machine in its DC's
  site group (or `--site`); People → Add puts a person in the site of the admin's choosing.
- **Machine types:** `machines-servers`, `machines-desktops`, `machines-network`, filled by fabric: the Linux join takes
  `--type server|desktop` (server by default), a Windows machine is sorted by its `operatingSystem` (a Server edition is
  a server), `add-machine --type` pre-creates any of the three. The OU of its type is where fabric files it; changing a
  computer's type in the console changes its group and offers to move it to that type's folder.
- **Machines fabric manages:** `fabric-managed` (`<site>-fabric-machines` until now, 1.6.11.6), one for the domain.
- **Machine groups:** any group of computers an admin makes (today's host groups, 1.6.11.7, without the site prefix).
- **Administrators:** the tiers' groups (1.6.12.2: `directory-admins`, and `dc-hosts` for the DCs' hosts, 2.1.6.81), `server-admins`, `desktop-admins` and `network-admins` (2.1.6.74),
  and any group an admin makes for a grant.

Every name is checked against the collision inventory ([1.2.13](1.2.13-name-claims.md)) when fabric or an admin makes it.

## 1.6.13.4 Grants, and how fabric makes AD, sssd and Windows enforce them

A grant (2.1.6.73) is kept in the domain, so every DC holds it: one `container` object per grant under
`CN=grants,CN=fabric,CN=System` (2.1.6.79), its definition in the object's `info` attribute as JSON that only fabric-agent writes
(no schema extension). It holds its name, who (people groups, all required), its rights, and where (machine groups,
all required; or people groups for rights on people).

| Category | Rights | Where it applies | Enforced by |
|---|---|---|---|
| People | edit, reset a password, unlock, disable and enable, add and remove | people in all the where groups | fabric-agent, on every call |
| Machines | add, move between folders, disable and enable, remove, change machine groups | machines in all the where groups | fabric-agent |
| Sign-in | at the keyboard; remotely (RDP, SSH) | machines in all the where groups | Windows and sssd, from fabric's GPOs |
| Sudo | every command, or a list | as above | sssd and sudo, from fabric's `sudoRole`s |
| Local administrator | Windows' Administrators group | as above | Windows, from fabric's GPOs |

**AD, sssd and Windows only know "any of these groups"**, so fabric-agent compiles each grant:

1. **Computed groups:** `grant-<name>-who` (the people in all its who groups, nesting followed) and
   `grant-<name>-where` (the machines, or people, in all its where groups), in `OU=fabric,OU=groups`, written only by
   fabric-agent (an ACL denies member writes to everyone else, the Directory Administrators too).
2. **Sign-in and local administrator, without GPO precedence fights:** Windows (and sssd after it) takes a user right
   from the one GPO of highest precedence that sets it, so two grants' GPOs on one machine would overwrite each other.
   fabric therefore groups machines by the set of grants that reach them: each set gets **one** GPO, `fabric: access
   <n>`, linked at `OU=machines` (2.1.6.84), filtered by security to a computed group of exactly those
   machines (`access-<n>`), granting each right to the union of those grants' who groups, followed by
   `BUILTIN\Administrators` and the machine's `local-admin` (so the break-glass ways in are never locked out, as
   1.6.11.4 keeps today). A machine is in one such set only. sssd's `ad_gpo_access_control = enforcing` applies it to
   Linux as it does today.
3. **Sudo:** one `sudoRole` per grant with sudo, `sudoUser: %grant-<name>-who`, its `sudoHost`s written from
   `grant-<name>-where`'s members as 1.6.11.7 writes a host group's today.
4. **When:** at once for a change fabric-agent makes (the queue stream shows it, 1.8.6.5), and every 5 minutes for a
   change made elsewhere (RSAT, 2.1.6.76). A machine sees it at its next policy refresh (Windows: 90 minutes, or
   `gpupdate`; sssd: its GPO and sudo refresh, 15 minutes).

**Restricting grants** (2.1.6.77): a grant may instead restrict: where (machine groups, all required), a right,
and who keeps it there. For each set of machines, a right goes to the allowing grants' people who are also in every
restricting grant's who on those machines; fabric writes that as the set's computed group (`access-<n>-<right>`), so
the GPO still names one group per right. `BUILTIN\Administrators` and `local-admin` are never restricted.

**Refused,** with why: a grant on the tiers' groups or their members (2.1.6.66); a grant reaching the domain controller
hosts group but by `fabric-admin` (1.6.13.6); sudo of every command for every person; a who or where with no group; a
grant whose computed group would be empty is allowed but marked "reaches nobody".

## 1.6.13.5 What a fresh install ships

| Grant | Who | Rights | Where |
|---|---|---|---|
| Server administrators | `server-admins` | sign-in (both), sudo (every command), local administrator | `machines-servers` |
| Desktop administrators | `desktop-admins` | the same | `machines-desktops` |
| Network administrators | `network-admins` | the same | `machines-network` |
| Desktops | every person (the domain's people) | sign-in at the keyboard | `machines-desktops` |
| Helpdesk (template, nobody) | none until given | people: edit, reset, unlock | none until given |
| Limited Directory Administrator (template, nobody) | none until given | every category | none until given |

The groups start empty but for the first Directory Administrator, who is in none of them: they administer the
directory; a grant gives them a machine.

## 1.6.13.6 The hosts that run a DC

Root on a DC's host reads the domain's secrets (2.1.6.75). So it is the top tier's (2.1.6.78): no grant reaches the
domain controller hosts group, and nobody from the domain signs in. The ways in are `fabric-admin` and the host's
`local-admin`, whose password OpenBao releases only to the Enterprise Admin. The account that ran setup is the root
break glass until `local-admin` takes over, then ideally deleted: fabric never touches it, but it and any other
local root or administrator account OpenBao does not manage bring a daily reminder (the console's top bar and
Overview, `fabricctl doctor`) until it is removed or approved as break glass by the Enterprise Admin (`fabricctl
host accounts approve|unapprove <name>`, audited `LOCAL_ACCOUNT_APPROVE`). There, root resets a lost break-glass password:
`sudo fabricctl admin reset-break-glass` (a new generated password in `~/fabric-admin/`, 0600, as setup writes it; the
account unlocked; audited `BREAK_GLASS_RESET`), refused on a host without a writable DC.

## 1.6.13.7 Pages, routes and the CLI

- **Directory → Access** (1.6.12): the grants, a grant's page (its who, rights and where, the people and machines it
  reaches, as counts with the lists), **Add grant** from a template or empty, each category's rights as switches.
  `groups:admin` (the Directory Administrators).
- **A person's and a computer's page** show the grants that reach them and what each gives.
- **CLI:** `fabricctl domain grant list|show|add|set|remove`, `fabricctl domain grant explain <person> [<machine>]`
  (which grants reach them, and why); routes `/v1/domain/grants` (GET `domain:read`; POST `groups:admin`).
- **Audit:** `GRANT_ADD`, `GRANT_SET`, `GRANT_REMOVE`; each compile's changes to the computed groups and GPOs.

## 1.6.13.8 Tests

Against a real Samba AD DC and real joined machines (the samba suite, the sandbox's Linux member, and a Windows member
in 0.10's Incus cluster), positive and negative for every entry point:

- each shipped grant: a server admin signs in and gets sudo on a server, and is refused on a desktop; a site's
  person signs in at a desktop of their site and is refused at another site's;
- the owner's case: a grant on `site-a` and `machines-servers` reaches only site A's servers; a restricting grant
  on `site-a` and `machines-desktops` keeps site A's desktops to site A's people, and every other desktop open;
- the DC host: a grant reaching it refused; the setup account reminded daily until approved, then not;
- two grants on one machine both hold (the one-GPO-per-set rule); a person removed from a who group loses the right at
  the next refresh; a change made with `samba-tool` is compiled within 5 minutes;
- sssd honours the GPO's security filtering (checked first: it is what the design rests on);
- every refusal of 1.6.13.4 and 1.6.13.6, with its message; the computed groups refused to anyone writing them but
  fabric-agent; `reset-break-glass` refused on a host with no writable DC.

## 1.6.13.9 Open points

None. Settled 2026-10-18 (2.3.6.15): nobody from the domain signs in to a DC's host (2.1.6.78); every person signs
in at desktops unless a restricting grant narrows it (2.1.6.77); the names as written; the sign-in factors stay
Keycloak's pages until 1.0 or later (2.1.1.62).

## 1.6.13.10 What D1 built (0.8.0)

Built 2026-10-19 as step D1 of [1.6.12.15](1.6.12-domain-management.md#161215-build-order) (note
[2.3.6.17](../volume_2_engineering_decisions/2.3.6-identity-notes.md#23617-the-d1-build-the-directorys-layout-2026-10-19)).
Grants (1.6.13.4, 1.6.13.5) are D3's: until then nothing restricts who signs in to a joined machine (2.3.6.17.2).

- **1.6.13.10.1 The folders:** 1.6.13.2's, made by every DC's convergence (`ensure_layout`), each marked as fabric's
  in its description; OU=fabric inside OU=groups; OU=servers, OU=desktops and OU=network inside OU=machines;
  `CN=fabric,CN=System` with `CN=dcs`. AD's default containers for new users and computers point at OU=people and
  OU=machines (`wellKnownObjects`). No site OU, no `OU=organisation`, no OS-family OU; nothing is moved from an older
  layout (0.8.0 installs fresh, 2.1.1.60).
- **1.6.13.10.2 Ids per DC:** each DC's record `CN=dc-NNNN,CN=dcs,CN=fabric,CN=System` (classes `fabricDcInfo`,
  `fabricIdLayout`, `fabricSiteInfo`) holds its range (`fabricIdRange`: dc-N owns N x 1000000 to N x 1000000 +
  999999, 2.1.6.63), one mark per fixed range (`fabricIdMark`, 1.6.3.17) and its site (`fabricSite`). A number comes
  from the DC's own range first, then from the same range of its site's other DCs in name order; every DC of the site
  full is refused, naming the range. A read-only DC's record is written by the writable DC that prepares its join, and
  its ids are taken there (2.1.6.85). A DC not named `dc-NNNN` is refused before anything is written. The settings
  `posix_id_start`, `posix_id_block`, `posix_id_range` and their checks are gone (2.1.6.86); a join answers with the
  joining DC's range, derived from the name it gives it (`dc_id_range`). The reserve 2000-2146 and reclaiming are
  0.11.0's.
- **1.6.13.10.3 The groups,** all in OU=groups, with gids from the converging DC's built-in range (fabric's fixed
  `ldap_groups` first at the root): `directory-admins` (the console's admin group; `webui_admin_group` and `admins`
  are gone), `dc-hosts`, `fabric-managed`, `fabric-break-glass`, `server-admins`, `desktop-admins`,
  `network-admins` (empty until D3's grants), `machines-servers`, `machines-desktops`, `machines-network`,
  `site-<name>` per site, and `rodc-cache-<dc>` for a read-only DC (not POSIX). No group is nested in another; the site
  role groups, `<site>-users`, `<site>-admins`, `fabric-admins`, `<site>-fabric-admins` and the site sudo rule are not
  made. Host groups are `hosts-<name>`, the domain's (1.6.11.7).
- **1.6.13.10.4 The tiers' AD rights** (2.1.6.68, 2.1.6.76; `ensure_directory_acl`, every convergence):
  `directory-admins` have full control of OU=people, OU=service-accounts, OU=machines and OU=groups and what is below,
  and may write their GPO links (`gPLink`, `gPOptions`); never `WD` or `WO`, so no holder lifts a deny. Denied: fabric's
  own accounts in OU=service-accounts (`fabric-agent-*`, `fabric-keycloak-*`, `fabric-radius-*`, `fabric-sso-*`,
  `fabric-join-*`: any change, and the password reset), the tiers' groups (`directory-admins`, `dc-hosts`) and OU=fabric.
  They have no rights on AD's own containers, the Domain Controllers OU, OU=fabric-hosts or `CN=fabric,CN=System`.
  The top tier: every account in OU=people or OU=service-accounts that is a member (nesting followed) of Enterprise,
  Schema or Domain Admins or Administrators, or carries `adminCount`, gets the same deny (`protect_top_tier`; Samba
  runs no AdminSDHolder propagation). Setup puts the first person in Enterprise, Schema and Domain Admins at the root's
  DC as root (`ensure_top_tier.py`) and in `directory-admins`. Each DC's agent has full control of the folders but
  OU=service-accounts, and of `CN=fabric,CN=System`, which every authenticated account reads; each DC's Keycloak
  account has full control of OU=people and writes the members of OU=groups.
- **1.6.13.10.5 Service accounts per DC** (2.1.6.82): `fabric-agent-dc-NNNN`, `fabric-keycloak-dc-NNNN` and
  `fabric-radius-dc-NNNN` in OU=service-accounts, made by the DC's convergence, or by the parent preparing a joining
  DC; uids from the DC's service range. The Kerberos sign-in account keeps its site's name, `fabric-sso-<site>`.
- **1.6.13.10.6 Keycloak** (2.1.6.83): `usersDn` OU=people, admitting every enabled person (the filter leaves out a
  disabled account); bound as the DC's `fabric-keycloak-dc-NNNN`; its group mapper reads OU=groups; the console's
  admin role comes from `directory-admins`.
- **1.6.13.10.7 Group Policy** (2.1.6.84): each site's Windows baseline and admin GPOs are linked at OU=machines; the
  trust GPO stays linked at the domain. With several sites, every site's baseline applies to every machine until D3's
  per-set GPOs.
- **1.6.13.10.8 Machine types:** the Linux join takes `--type server|desktop` (server by default; with `--one-time`
  the type add-machine gave it) and files the machine in that type's OU, its group and its site's group (as the admin
  who joins it); `add-machine --type server|desktop|network` pre-creates one (without a type: in OU=machines itself);
  the hourly sort files a Windows machine that joined itself by its `operatingSystem` (a Server edition into
  OU=servers, any other into OU=desktops) and adopts a Linux machine of the site into `fabric-managed`. FreeRADIUS
  finds people in OU=people, machines in OU=machines, devices and roles in OU=devices and OU=device-roles, and binds as
  its DC's `fabric-radius-dc-NNNN`.
- **1.6.13.10.9 The fabric host** (2.1.6.70, 2.1.6.75, 2.1.6.78): its account is made in no site's group, then placed
  in OU=fabric-hosts, `fabric-managed` and `dc-hosts`; sssd on it denies every domain account (`access_provider =
  deny`) and reads no domain sudo rule (`sudo_provider = none`): nobody from the domain signs in or gets sudo there.
- **1.6.13.10.10 Sudo rules and networks** are the domain's: rules in OU=sudoers (a rule of ALL commands to everyone,
  or to a whole site's group, is refused); the address plan's networks in OU=networks, each `<site>/<name>` with its
  site recorded on it.

## 1.4.1.1 DNS Architecture

BIND9 runs as an **authoritative-only** server (recursion disabled). It serves:
- Internal forward zones defined in the `dns:` block of the vars file (`dynamic_zone_var` key resolved to `domain` at render time)
- Each zone with `zone_authority: true` gets an NS A record pointing to `host_ip`
- Reverse zones (PTR) generated at apply from A and AAAA records by `fabriclib/dns/reverse_zones.py`. There is one `/24` `in-addr.arpa` zone per IPv4 subnet and one `/64` `ip6.arpa` zone per ULA prefix, with one PTR per address. Only private addresses (RFC 1918, 100.64/10, ULA) get one; zones written by hand in `dns:` are left alone. See [operations.md](../volume_4_operations/4.4.5-reverse-dns.md#4451-reverse-dns)
- RFC2136 updates, deny-by-default: per key `records` → only `_acme-challenge.<record>.<zone>`; `primary` → `subdomain _acme-challenge`; explicit `any_name` → `zonesub`; plus the grants of any ACL policy (`bind_acl_policies`) the key is a member of. Keys live in vars, their secrets with fabric's secrets in OpenBao (managed with `fabricctl tsig`)

BIND9 answers plain DNS itself; nginx fronts only DNS-over-HTTPS:

```
host_ip:<bind_dns_port> TCP/UDP → bind9:53     plain DNS (published by Docker)
:443 dns.<domain>/dns-query     → bind9:8053   DNS-over-HTTPS (nginx terminates TLS; HTTP/2 to BIND) — with the
                                               DNS filter on, to the resolver instead (resolver:8053, 1.12.2.16)
```

`bind_dns_port` (default `53`) is the Docker host port mapped to BIND9's internal port 53, published on `host_ip` only (so it does not clash with `systemd-resolved` on loopback). DNS-over-TLS (853) is the DNS filter's: the resolver
answers it with the DNS name's certificate ([1.12.2.16](1.12.2-bind-resolver.md#112216-dns-over-tls-and-dns-over-https-for-clients)).

BIND's DNS-over-HTTPS speaks HTTP/2 only, so nginx reaches it with `grpc_pass` (cleartext HTTP/2), not
`proxy_pass` (HTTP/1.1). Until 0.6.3 it used `proxy_pass`: BIND's HTTP/2 answer came back as an HTTP/0.9 blob and
DoH through nginx never worked; doctor's DoH check (2.1.12.2) found it on the 0.6.3 upgrade test, and the render test
now guards it.

## 1.4.1.2 DNS with Samba AD (planned)

Design approved by the owner 2026-10-04 ([1.6.5.6](1.6.5-samba-dc.md#1656-dns)); proven
by the spike (Q2, Q14).

- BIND stays the only DNS server. It serves the AD zone from the DC's database through Samba's DLZ module; the DC's
  own DNS server is off. Windows and Linux members register their names with Kerberos-signed (GSS-TSIG) updates;
  unsigned updates are refused in every zone.
- **The AD zone is always its own zone** (2.1.6.11: never fabric's domain; suggested: a sibling, `lan.j-j.family` →
  `ad.j-j.family`): fabric's zones are
  unchanged, and the AD zone is one more zone in BIND. (Same-domain mode, where DLZ would own fabric's zone and TSIG
  clients would need an ACME zone beside it — spike Q14 — was dropped on 2026-10-04.)
- A site with a DC serves the AD zone from its own DC; a site with none forwards `ad.<domain>` to its parent's
  BIND (1.9.8).

## 1.4.1.3 Zones added and removed in the console (0.7.0)

**Designed 2026-10-11 for 0.7.0 (decision 2.1.4.5); built in 0.7.0 on 2026-10-11** (how to use it: 4.4.1.2; how it
is built: below the list). Until 0.7.0 only the command-line menu (`sudo fabricctl`, DNS Configuration, `a`) added a
zone, and nothing removed one.

- **The console's Zones page** has *New zone* (a name) and, on each zone but the site's own, *Remove zone*; the menu
  gets *remove* beside *add*. Both call one unit each, `fabriclib/dns/add_zone.py` and `remove_zone.py`, through the
  agent (`POST /v1/zones`, `POST /v1/zones/<key>/delete`), with permission `dns:write`; audited like a record.
- **A new zone** is a key of `dns:` in the vars, with `zone_authority: true` (its `ns` record), served by BIND like the
  site's own, and forwarded by the resolver to BIND, never filtered (1.12.3.2). Its records are added on its page as
  for any zone; A and AAAA records with a private address get their PTR as before.
- **A name is refused**, with the reason, when it is not a valid lowercase DNS name of at least two labels (the
  menu's `HOST_RE`, which keeps it safe as a file name and in `named.conf`), or when BIND already answers for it:
  the site's domain, the DHCP zone (`<ddns_subdomain>.<domain>`), the AD zone, another site's zone (federation), a
  reverse zone (`*.arpa`, generated: 1.4.1.1), or an existing zone. A name under a public top-level domain (any but
  the private-use ones: `home.arpa`, `internal`, `lan`, `local`, `test`, `localhost`, `invalid`, `example`) is
  accepted only with *Hide the public name* ticked, since every client of the site then gets this zone's answers
  instead of the real ones.
- **Removing a zone** drops it with its records, its zone file and journal. The form names how many records go and
  asks for the zone's name typed again; the records removed are kept in the audit entry. It is refused while a TSIG
  key or an ACL policy names the zone (they are removed first, on the Keys page).
- **In seconds, not an apply:** the change is saved to the vars (locked, audited), then BIND's zone list and the new
  zone file are rendered and BIND reloads its configuration (`rndc reconfig`), then the resolver's configuration is
  rendered and reloaded the same way (its forward zones, `validate-except`). Nothing restarts. If a reload fails, the
  vars change is rolled back, both configurations are rendered again, and the console says why.
- **Tests** (3.1.2): add a zone, a record in it resolves through the resolver; add refused for each case above;
  remove refused while a key names it; remove drops its answers; the menu and the console reach the same unit.

How it is built: `fabriclib/dns/publish_zone_list.py` is the quick path both units call under the vars lock. It reads
the vars and fabric's secrets (read only), renders and checks the settings as apply does (one shared function,
`deploy/check_rendered`: the settings check, which sets DHCP's reverse zones and Kea's grants, the reverse zones and
the federation links; decision 2.1.4.7), and writes **all of BIND's
configuration** (`named.conf*`, `rndc.key`; the keys file and `rndc.key` 0600) plus the new zone's file, because the
zone list names TSIG keys and ACLs that must exist beside it; then `rndc reconfig` and `rndc zonestatus <zone>` for a
new zone. A removed zone's file, `.jnl` and `.jbk` go only after BIND has dropped it. The resolver is rendered and
reloaded through `deploy_resolver`, and its forward list (`dns_filter/common/filter_zones.py`) now holds every key of
`dns:` beside the site's domain. A TSIG key in the vars whose secret apply has not yet made refuses the quick path
("run an apply first"): it never makes or saves a secret. Settings the apply's check refuses refuse the quick
path the same way, before any file is written (`NotPublished`): only the vars are put back. A zone's name is checked by `ZONE_RE` (`add_zone.py`):
the menu's `HOST_RE` without the underscore a record name may carry, since BIND will not load a zone named with one
(2.3.4.2). The console's forms are on the BIND9 tab's zone view
(`/bind9/zones/new`, `/bind9/zones/<key>/remove`, `webui/routes/zones_post.py`); the menu's `r` asks for the zone,
shows its record count and asks for the name again. Tests: `tests/zones/run.py` (BIND and the resolver in
containers), the web UI suites for the forms.

## 1.4.1.4 Records in the console: the form asks only what a type needs; fabric's own names (0.7.1)

Built for 0.7.1 (decision 2.1.2.22, items 3 and 6; the owner at the 0.7.0 test install: the record form was
"unnecessarily complicated", and deleting `info.<domain>` "didn't work"). How to use it: 4.4.1.3.

- **The record form** (BIND9 tab, a zone, *Add record*) asks the type, the name and one **value**: the address for A
  and AAAA, the host it points to for CNAME, MX and SRV, the text for TXT. *Priority* shows for MX and SRV, *weight*
  and *port* for SRV only. The page has no script (the strict CSP, 1.8.2): the stylesheet hides the fields with
  `:has()` on the type's selected option, so a browser without `:has()` shows every field and the form still works.
  The landing-page fields left the form (1.4.2.4).
- **Checked per type on the server**, as before: `dns/validate_record.py` takes `value` into the type's own field
  (`ip`, `target` or `text`; `VALUE_FIELD`) when that field is empty, then checks exactly that type's fields (an
  MX without a priority, an SRV without a port, a TXT with a quote are refused with the reason). The menu and the
  settings file keep their own fields.
- **Fabric's own names.** `templates/vars.yaml.j2` adds names to the site's zone on every render (`default_cnames`,
  `default_a`): `ca`, `dns`, `sso`, `vault`, the landing page's `info` (`landing_page_cname`), the console's name
  (`webui_hostname`, inside the domain), `federation` (with the federation endpoint), `ntp` (while the host serves
  time), the host's own A record and `<domain>`'s (`@`). The installed settings file is the rendered one, so they
  are records there like the admin's; a delete removed one until the next apply put it back, silently.
  `dns/common/fabric_record.py` recognises them by name **and** target (an admin's own record of the same name
  pointing elsewhere is theirs), for the site's zone only.
- **Marked and refused.** The zone's table marks them *provided by fabric* (the service and the setting in its
  title) and shows "kept by fabric: <setting>" where the Delete button would be. A delete that reaches fabric-agent
  or the menu anyway (`sudo fabricctl`, DNS Configuration, `d`) is refused by `dns/remove_record.py`, the one unit
  both call: "`info.<domain>` is provided by fabric (the landing page, from the setting `landing_page_cname`): every
  apply adds it back, so it cannot be deleted here". Nothing is changed.
- **No name is turned off from here in 0.7.1**, the landing page's `info` included; 2.1.2.22 item 6 asked for that
  one to be turned off through its setting, which needs more than a setting: 2.3.1.19.5.
- **`info` is no longer fabric's (0.7.1, 2.1.4.6).** The landing page moved to a path fabric keeps (1.4.2.5), so its
  `info` record is added once, by the render that installs the site, as an ordinary record: it is not marked, and the
  admin renames (deletes and adds), repoints or deletes it like their own. The other names above stay fabric's and
  refused. Superseding the two bullets above for `info` only.
- **Tests:** `tests/render.py` (the value per type and its refusals; fabric's names in a rendered zone, an admin's
  record of the same name not), the `webui` suites (the form's fields, an MX from value and priority, an SRV without
  a port refused; the pill; `info` and the host's A refused through the real agent, the settings unchanged), the
  `zones` suite (the menu's delete of the host's A refused, naming `hostname`; an admin's record still deleted).

## 1.4.1.5 A changed zone at an apply: swapped live, or put in place before BIND restarts (0.7.2)

An apply (and setup's deploy) renders every zone file and puts in place only those whose records changed
(`find_changed_zones`, the serial ignored). How depends on BIND:

- **BIND running and staying up:** each changed zone is swapped live (`reload_zone`): frozen, so BIND writes its
  journal (what DHCP and RFC2136 registered) into the file, the new file installed (a reverse zone keeps Kea's PTR and
  DHCID records, 2.1.10.7), thawed, and the served serial checked; BIND's own write can land after the new file, so
  the swap is repeated until BIND serves the new serial (up to five times).
- **BIND running and about to restart** (its image or configuration changed, as on an upgrade): each changed zone is
  frozen and the new file installed only once BIND's own write has landed (`freeze_and_install`: it waits up to 3 s
  when the zone's journal is newer than its file, the only case in which BIND has something to write); the restart
  then loads the new file. Until 0.7.2 the file went in as soon as `rndc freeze` answered, which is before BIND has
  written: its copy of the old zone replaced the new file a moment later and the restart served the old zone (a
  setting's new record missing until a later live swap of that zone; found by 0.8.0's sandbox, 2.3.1.22).
- **BIND down:** the files are installed; its start loads them.
- **Tests:** the `zone` suite (`tests/zone_test.py`: the live swap repeated after BIND's late write;
  `tests/dns/freeze_and_install_test.py`: BIND's write waited for, no wait without a newer journal or for a static
  zone), the sandbox (a setting's record served by the restarted BIND after `fabricctl setup --file`).

## 1.4.1.6 A name asked before it exists: 30 s of "no such name", and the resolver flushed after a publish (0.8.0)

Decision 2.1.4.9. A resolver that was told a name does not exist keeps that answer for the zone's negative-caching
TTL (RFC 2308: the SOA's minimum, or the SOA record's own TTL if lower); clients' caches (systemd-resolved, Windows)
do the same.

- **30 s in every zone fabric serves.** The SOA minimum is 30 in the site's and every added forward zone
  (`zone.j2`) and every reverse zone (`reverse-zone.j2`, DHCP's included: 300 s before). The DHCP subzone
  (`dhcp.<domain>`) is made once with 30 (`dhcp/ensure_ddns_zone`); one an older release made with 300 is given 30
  by the next apply under the running BIND (`dns/set_negative_ttl`): `rndc freeze` (BIND writes its journal into the
  file), the SOA's minimum set and serial raised, `rndc thaw`; what DHCP registered stays. With BIND down and a journal
  newer than the file it is left, with a warning, for the next apply. The AD zone is Samba's through DLZ and keeps
  Samba's SOA.
- **The resolver forgets what a publish changed.** An apply and DNS' own Apply compare each changed zone's new file
  with the deployed one before swapping it in (`dns/changed_names`: added, changed and removed owner names, the
  serial ignored); once BIND serves the new zones the filtering resolver flushes each name (`rndc flushname`, every
  view: the client groups' too), or the whole zone (`rndc flushtree`) when it is new or more than 50 names changed
  (`dns_filter/flush_published_names`). A zone added or removed in the console (1.4.1.3) is flushed whole. With the
  resolver off nothing is asked.
- **A failed flush is a warning**, never a failure: the apply prints it, DNS' Apply and a zone's add or removal say
  it on their row of the Review, the menu prints it. The records are served either way; the cached miss ends within
  30 s.
- **Not changed:** the resolver's `max-ncache-ttl` (BIND's 3 h cap) for answers from the internet; from 0.9.0,
  300 s (1.12.2.18, 2.1.12.11).
- **Tests:** `tests/render.py` (every rendered zone's minimum is 30, none a day or 300 s); the `zone` suite
  (`tests/dns/set_negative_ttl_test.py`: BIND's and fabric's SOA forms, BIND down with and without a journal, a
  refused thaw; `changed_names_test.py`, `flush_published_names_test.py` from dev/0.9.0); the `deploy` suite (the
  apply's flush and its warning; a change's warning on the Review); the `kea` suite with a real BIND (a new DHCP
  subzone has 30 s; an older one's 300 s made 30 s under the running BIND, laptop1's registration kept, DHCP's
  updates taken after); the `resolver` suite with real BIND (a cached NXDOMAIN ends within 30 s; after the apply's
  flush a new name answers at once, the resolver having held its NXDOMAIN until then); the `zones` suite (a zone's
  add flushed without a warning).

## 1.4.1.7 Cockpit names on the DNS page (planned)

Planned, after the feature freeze (decision 2.1.8.33; design [1.8.7.12](1.8.7-cockpit-proxy.md#18712-changing-a-cockpit-name-on-the-dns-page)).
Each device whose Cockpit fabric proxies has a CNAME in the site's zone, `<hostname>-cockpit` by default, the fabric
server's included. It is a record provided by fabric (1.4.1.4), so it cannot be deleted or edited as an ordinary
record; its row has **Change name** instead. A new name already used by another record or by one of fabric's own
names is refused, saying which; an accepted one is held for DNS' Apply, which moves the record, nginx's server and
the certificate to the new name and removes the old name's.

## 1.4.1.8 A move or a rename: fabric's names, the DC's records and `/etc/hosts` follow the host (0.9.2)

Decision 2.1.1.74 (the fix of known issue 2.3.1.34). Before 0.9.2 a move (4.2.4.2) or a rename (4.2.4.3) left the old
address or name in three places, which the operator cleaned by hand. From 0.9.2 the apply and the member step do it:

- **1.4.1.8.1 fabric's own names in the site's zone.** Each render writes the records it added as fabric's own
  (the host's `A`, `@`'s `A`, the aliases `ca`, `dns`, `sso`, `vault`, `ntp`, the console's and the federation
  endpoint's) into `vars.yaml` as `dns_fabric_own`, and the next render drops exactly those before adding its own
  again from today's settings (`dns/common/drop_previous_own`, called by `deploy/render_vars`). So after a move the
  host and `@` name the new address only, and after a rename fabric's aliases name the new host once each. An
  admin's alias of the host's old name (the landing page's `info`, 2.1.4.6, among them) follows it to the new name;
  every other admin record is left as it is. An install from before 0.9.2 kept no list: only the records that match
  fabric's names under today's settings exactly are taken for fabric's (positive evidence), so its first apply
  changes nothing. `dns_fabric_own` is fabric's own record, never an admin's setting: a value that is not a mapping of
  `A` and `CNAME` lists of records is refused.
- **1.4.1.8.2 The DC's records in the AD domain's DNS.** The DC's own update (`samba_dnsupdate`) asks its old address
  after a move and fails. The domain's convergence (converge.py's `ensure_dc_address`, after every start and apply)
  reads the addresses the DC's own name holds; any other than its address (`HOST_IP`) is its old one, and is removed
  from the DC's name, the domain itself (`@`), `DomainDnsZones`, `ForestDnsZones` and `gc._msdcs` unless another DC's
  name holds it; the DC's address is added where it is missing. A record of any other name at the old address is the
  admin's and stays. The apply then makes the filtering resolver forget the AD domain's answers (`rndc flushtree`).
- **1.4.1.8.3 `/etc/hosts`.** The member step's line for the DC (only when DNS does not give it) replaces a line
  naming the DC at another address, instead of being appended after it (`setup/join_host_domain`).
- **1.4.1.8.4 Doctor checks it** (`setup/address_checks`): the host's name, the site's domain (when `@` is fabric's) and
  `ca.<domain>` answer the host's address alone; the DC's name answers it alone and the AD domain names it;
  `/etc/hosts` names the DC at most once, at that address. The same checks as 4.2.4.7, run by `fabricctl doctor` and
  the console's Overview.
- **1.4.1.8.5 Not covered:** members fabric does not manage, and members joined before 0.9.2 and not refreshed (1.6.11.15),
  whose script does not follow an announcement, stay the operator's steps (4.2.4.2 step 5); moves outside 4.2.4 (another network,
  linked sites) are not built (2.1.1.77). The members fabric manages follow 1.4.1.8.7.
- **1.4.1.8.6 Tests.** The `zone` suite (`tests/dns/drop_previous_own_test.py`: vars.yaml.j2 rendered for real, moved
  and renamed, an install that has been ready, an install from before 0.9.2, `dns_fabric_own` refused when it is not
  fabric's list); `tests/render.py` (a render of a render changes nothing); the `samba` suite (`tests/samba/dc.py`: the
  DC's records at an old address removed by the next converge, another name's kept); the `consent` suite
  (`/etc/hosts` after a move, in `tests/consent/run.py`; doctor's checks in `tests/setup/address_checks_test.py`); the
  lab's joined campaign (3.1.5.11 steps 7 and 8: a real move and rename with no clean-up by hand).
- **1.4.1.8.7 The members follow: `fabricctl move prepare <new address>` (decision 2.1.1.79).** The host has no channel
  to a member, and after the move a member cannot ask it (2.3.1.39.1), so the news goes first, while it can:
  - **The record.** `CN=<dc>,CN=moves,CN=fabric,CN=System,<domain>`, a container whose description is `<old> <new>`, in
    fabric's state: every authenticated account reads it, only the system and fabric's agents write it (2.1.6.79). It
    is written inside the DC (`move_tool`, `member_dns`). A convergence that finds the host no longer at the record's
    old address takes the record out.
  - **Refused** (`check_new_address`), saying why, nothing changed: not an IPv4 address; off `lan_cidr`; the LAN's
    network, broadcast or gateway address; the address the host has now; an install with linked sites. An address
    announced again changes nothing; another replaces it. `fabricctl move status` says what is announced;
    `fabricctl move cancel` withdraws it. Both change audited `MOVE_PREPARE`, `MOVE_CANCEL`.
  - **A Linux member** (`fabric-managed check`, hourly, in `templates/nginx/www/certs/join-linux.sh.j2`), while it is in
    `fabric-managed`, asks the DC as the machine, with the address it uses now in the filter. An address found is
    checked for its form and kept in `/etc/fabric/managed.next`; apply lists `DNS=<old> <new>`. No record: the file goes,
    and the member has the old alone again. The DC not answering changes nothing. Each check first looks at a kept
    address: the old silent on TCP 53 and the new answering means the host moved, so `FABRIC_DNS` becomes the new,
    the file goes, the caches are flushed and SSSD restarts (its `kdcinfo` file names the DC's old address). Both silent
    means the member's own network, and changes nothing. Taken out of `fabric-managed`, the file goes with the rest.
  - **A Windows member:** the GPO `fabric: <site> DNS servers`, linked at the domain's root, denied to the DCs and the
    fabric hosts, holds a Group Policy Preferences Scheduled Task run as SYSTEM. On a fixed-address adapter naming one of
    fabric's addresses, it sets the servers (both, old first, while a move is announced; the host's alone after); then, if
    `nltest /sc_verify` fails, it clears the DNS cache and runs `nltest /sc_reset:<domain>`. It runs when it is registered
    (a Group Policy refresh), on Netlogon's 5719, and every 5 minutes while a move is announced: 5719 is logged once and
    may come before the DC's new address is in place. An adapter on DHCP is left to DHCP. Fabric keeps the address the
    task must take out (`CN=<dc>-previous,CN=moves`): the one a move left, or the one a cancelled move announced. DNS
    Client's own policy is not used: real Windows Server 2025 ignored it (2.3.1.44). An install that never announced a
    move has no GPO.
  - **The wait:** up to an hour for a Linux member's check, up to 90 minutes for Group Policy (or `gpupdate`). The
    operator waits before step 2 of 4.2.4.2. After the move, a Linux member settles at its next check, so up to an hour
    again; until then its resolver falls back to the new address, and `kinit` may fail until SSSD restarts.
  - **Tests.** `tests/samba/linux_join.py`: the command's positive and negative cases against the real DC, a real joined
    container following, withdrawing and settling; the GPO's files, its link and its filter; the convergence after the
    move. The lab's joined campaign (`move`, 3.1.5.11) on real members: 2.3.8.8.

## 1.4.1.9 A TSIG key's names changed in the console; an A record picked with its aliases (planned: 0.10.0)

Designed 2026-11-08 (decisions 2.1.4.13 and 2.1.4.14; the owner: "editing the scope of an existing tsig key... e.g. I
want to add a url, or remove one", and "a quick select this a record, and all associated cname records can get quick
added"). Placed in 0.10.0 by the owner on 2026-11-08 (1.1.4). Builds on the key's modes, ACME (DNS-01) and Custom
(2.1.4.12, not placed yet). Until those are built, the pick (1.4.1.9.4) is offered in Edit names and in New key's
*acme-hosts* scope, which is where a key's names are chosen today.

**What is there today.** A key's grants (1.4.1.1) come from its `tsig_keys` entry. `fabricctl tsig update` already
changes them with the secret untouched (`dns/update_tsig_key.py`, 4.4.2.1). The console has only **New key**, **New
secret** and **Remove** (`webui/routes/tsig_post.py`; the agent's `POST /v1/tsig`, `/v1/tsig/<name>/rotate` and
`/delete`). So nothing is broken: the console is missing an edit that the command line has. To add or drop one name, a
person removes the key and makes it again, which gives it a new secret, and every client must then be updated.

- **1.4.1.9.1 Edit on the key's page.** The key's page (`/dns/zones?view=key&key=<name>`) gets **Edit names**. It shows
  the names the key may update now, each with **Remove**, and **Add** for more:
  - An ACME (DNS-01) key, or a Custom key that lists `records`, edits its `records`. Add offers the zone's existing
    records, as making the key does (2.1.4.12). A Custom key may also be given a name typed in, as `--record` takes one.
  - A Custom key also edits its record types and its scope (`records`, `primary` or `any_name`), with the same choices
    and refusals as when it was made.
  - The key's **zone, algorithm, secret and credentials file do not change here**. A key for another zone is a new
    key; a new secret is **New secret**. The command line keeps `--domain`, `--algorithm` and `--out` for a script.
- **1.4.1.9.2 Held for DNS' Apply.** An edit carries no secret, so it is held on DNS → Zones like any other DNS change
  (2.1.8.18), shown as "Change TSIG key npm: add web, remove nas", and DNS' Apply runs it and reloads BIND. The key's
  clients keep working, since the secret and the key's name stay the same. The change goes through one new agent route,
  `POST /v1/tsig/<name>/update`, which calls `update_tsig_key` (the same unit as `fabricctl tsig update`) under
  `dns:write`. It is audited as `TSIG_UPDATE` with the names added and removed.
- **1.4.1.9.3 Refused, saying why, nothing changed:** removing a key's last name (a key that may update nothing is
  removed instead: "remove the key instead"); a name already granted; a name not valid as a record name; any change
  to an ACME (DNS-01) key that ACME mode would not make; a key no longer there. A change of a key's ACLs stays on the
  ACLs page and the command line.
- **1.4.1.9.4 An A record and its aliases in one pick.** Where a key's names are chosen from the zone's records (making
  an ACME (DNS-01) key, and **Add** above), each A record offers **with its aliases**: the A record's name and the name
  of every CNAME in the same zone that points at it are added in one step. That includes a chain (a CNAME to a CNAME
  to the A record) and fabric's own aliases of the host (1.4.1.4). The list shows which names the pick adds before it
  is taken, and each one can still be removed by itself. AAAA records offer the same.
  - **What is granted is the names**, written into `records` when the pick is taken. A CNAME added to the zone later is
    not granted until someone adds it. A name in the key that is later renamed or removed in the zone follows 2.1.4.12.
  - A CNAME whose target is outside the key's zone, or a CNAME in another zone, is not offered: a key updates one zone.
- **1.4.1.9.5 The command line.** `tsig update --record` keeps its meaning: the names given replace the key's list.
  New, for one name at a time: `--add-record <name>`, `--drop-record <name>` and `--add-record-with-aliases <name>`,
  which does what the pick does and prints the names it added. `tsig update` refuses the same cases as 1.4.1.9.3.
- **1.4.1.9.6 Tests** (3.1.2), against a real BIND: a name added in the console is updated by the key's client with
  the same secret and a removed one is refused by BIND; each refusal of 1.4.1.9.3 leaves `vars.yaml` unchanged; the
  edit waits on DNS → Zones until DNS' Apply; an A record with two CNAMEs and a chain adds all of them; a CNAME
  pointing outside the zone is not offered; the command line and the console reach the same unit; the entry-point
  inventory lists the new route and the new flags, each with positive and negative cases.

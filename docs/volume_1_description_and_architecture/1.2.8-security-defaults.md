## 1.2.8.1 Where security is described

This is the home chapter for security (5.8). The global rules (Rule 10) apply to fabric as they are; this chapter
holds what fabric adds. Each aspect lives in its own volume: the agent's privilege model in 1.8.2 and 1.3.3,
people's access in 1.6.8, secrets in 1.7.1, container hardening in 1.2.4 and 1.2.6, the host changes fabric asks
about in 1.2.9, and the relaxations an install may choose in 2.1 (2.1.2.9). Moved from `AGENTS.md` §4 on
2026-10-03.

## 1.2.8.2 Never weaken silently

Secure by default; every relaxation is an explicit setting, shown in `fabricctl status` and the fabric-ctl web
UI (2.1.2.9).

Where: host changes the admin declined are under "host changes" (1.2.9); relaxed settings under "relaxed security
settings" in `fabricctl status` and at the top of the web UI's Overview (`fabriclib/system/relaxed_settings`, agent
route `/v1/relaxed-settings`). Today that is `image_signature_check: false` (1.14.3.4, 2.1.14.10).

## 1.2.8.3 Containers and privileges

- Containers: non-root, `cap_drop: ALL` (+ only what is needed, 2.1.2.8), `no-new-privileges`, read-only root where
  possible. Nothing mounts the Docker socket. Nobody is added to the `docker` group.
- Privileged work happens only in `fabric-agent`, through a fixed, validated API — never "run this command"
  (1.3.3).

## 1.2.8.4 Secrets, TLS and images

- Secrets never on a command line (`argv` is world-readable); pass them via files (0400/0600) or environment
  (2.1.7.3). No hard-coded or shared default passwords.
- Never in a systemd unit's command line or environment either: `systemctl show` prints both to any user. Setup's
  work runs as `fabric-setup.service` (2.1.2.26); the secrets typed in its questions (the first admin's password, the
  join invitation) reach it through a root-owned 0600 file in `/run/fabric-setup` (root, 0700), created new and removed once read
  ([1.3.2.3.4](1.3.2-setup-design.md#13234-secrets-handed-to-the-unit)).
- TLS everywhere, verified against the fabric root CA — never `verify off` for new code (2.1.2.10).
- Images are pinned by digest; local builds start `FROM` a pinned digest. An upstream push must never change what
  runs (2.1.14.4).

## 1.2.8.5 Core services start without OpenBao

Core services (DNS, DHCP, LDAP, SSO, nginx) must never depend on OpenBao to *start*: a sealed or broken vault
must not take the network down with it (1.7.1).

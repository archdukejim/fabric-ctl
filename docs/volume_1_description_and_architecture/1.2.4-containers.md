## 1.2.4.1 Container Hardening

> The privileges of every container and host service, with their real uids: [1.2.7](1.2.7-container-inventory.md) (2.1.2.8).

Every container runs non-root, with `cap_drop: ALL` and **no** capabilities added back, `no-new-privileges` and a read-only root filesystem (writable paths are volumes or small tmpfs mounts). The one documented exception is the optional `kea-dhcp4`: DHCP needs the LAN interface itself, so it runs in the host network as root inside the container with exactly `NET_RAW` and `NET_BIND_SERVICE` (still read-only, `no-new-privileges`). The other is `samba`, the domain controller: root in its container, in the host network, with six capabilities ([1.2.7.4](1.2.7-container-inventory.md#1274-what-changes-with-samba-ad)). Memory limits: every container has one, planned as a budget from `host_ram_capacity` (1.2.4.3). Proven by the `hardening` test suite (`sudo tests/run-all.sh hardening`), which starts the real rendered compose files and checks each process from the host, including zero effective capabilities.

Where an upstream image fights these settings, a thin **local build layer** (`packaging/images/<svc>/Dockerfile`, deployed to `/opt/<svc>/build`, image `fabric/<svc>:local`) fixes it once at build time instead of as root at every start. It always builds `FROM` the image given in `image_<svc>` (to be a pinned digest from the image channel).

| Container | User | Local layer | Writable paths |
|---|---|---|---|
| `nginx` | `nginx` 443 | — | tmpfs: `/tmp`, `/var/cache/nginx`, `/var/run`, `/var/log/nginx` |
| `bind9` | `bind` 53 | Yes: bind uid/gid baked in, runs `named` directly as `bind` (no root entrypoint, no SETUID/SETGID/CHOWN) | volumes: data, cache, log; tmpfs: `/run/named`, `/tmp` |
| `step-ca` | `step` 135 | Yes: strips the upstream binary's `cap_net_bind_service` file capability (a no-new-privileges container refuses to exec it; step-ca listens on 9000 and never needed it) | volume: `/home/step`; tmpfs: `/tmp` |
| `samba` | root in the container | Yes: Debian + Samba's DC packages | volumes: data, winbind sockets; secrets, TLS and converge code read-only; tmpfs: `/tmp`, `/run`, `/var/log/samba` |
| `postgres` | `postgres` 901 | — | volume: data; tmpfs: `/var/run/postgresql`, `/tmp` |
| `keycloak` | 900:0 | Yes: pre-built (`kc.sh build`) so it starts with `start --optimized` — no re-augmentation at boot (read-only root, faster on a Pi) | volume: `/opt/keycloak/data`; tmpfs: `/tmp` |
| `webui` | `webui` 912 | Yes: Debian + python3-jinja2 + app | tmpfs: `/tmp`; its socket dir |
| `openbao` | `openbao` 913 | — (pinned upstream image; `bao server` runs directly instead of the root-oriented entrypoint, `init: true` reaps) | volumes: data (Raft), logs (audit); seal key read-only; tmpfs: `/tmp` |
| `fluentbit` (optional) | `fluentbit` 914 | — | volume: buffer; journal and OpenBao audit log read-only |
| `kea-dhcp4` / `kea-ddns` (optional) | root in the container / `kea` 915 | Yes: Debian + Kea 3.0 LTS from ISC's signed repository (version and key pinned in `images.lock.yaml`) | volumes: leases, run (control socket); tmpfs: `/tmp` |
| `freeradius` (optional) | `freeradius` 916 | Yes: Debian `freeradius` + fabric's python3 policy | tmpfs: `/tmp`, `/run/freeradius` |

Low ports need no capability: Docker sets `net.ipv4.ip_unprivileged_port_start=0` inside each container's network namespace.

`apply` rebuilds a local layer only when its build context changed or it was built from another base than its pinned one; every base is pinned by digest (`config/images.lock.yaml`), and `fabricctl images update` moves bases and pulled images to the validated list (health-gated, with rollback).

## 1.2.4.2 Dynamic Resource Constraints & Boot Staggering

> The memory ceilings of 1.2.4.2.2 are replaced by the budget of 1.2.4.3 (built 2026-10-11, 0.9); 1.2.4.2.1 (the smallest host, setup measuring it) and 1.2.4.2.3 (the staggered boot) stand.

To guarantee stability on resource-constrained hardware (e.g. Raspberry Pi), `fabric` natively enforces dynamic memory ceilings (`mem_limit`) and staggered boot sequences across its Docker containers via the `host_ram_capacity` variable.

### 1.2.4.2.1 Validation Enforcement
**4 GB is the smallest host** (2.1.2.3; owner 2026-10-06: the 3 GB tier is gone). **Setup inspects the host and asks**
(owner 2026-10-06): it measures the memory (`/proc/meminfo`, rounded: a 4 GB Raspberry Pi reports 3.88 GiB), shows
what fabric's largest containers would then get, and asks how many GB fabric may use — all of it by default; less
restricts fabric, leaving the rest to other work on the host. The answer is kept as `host_ram_capacity` (asked once;
an unattended setup takes the measured amount). Below 4 GB setup refuses; an answer above what the host has is
refused too. There is no "unlimited" any more.

### 1.2.4.2.2 Docker Compose Memory Ceilings
Every container has a memory limit at every size (2.1.2.3, global Rule 7.2):

- The services that grow with the directory and its sign-ins use the host's memory as it grows, each in
  proportion to its 4 GB size: Keycloak `1200M * (host_ram_capacity / 4)` (its JVM heap 80% of it), the domain
  controller `512M * …` (`samba_mem_limit`), Postgres `200M * …`, BIND9 `128M * …` (Samba's DLZ libraries). At 8 GB:
  2400M, 1024M, 400M, 256M.
- nginx `256M`, Step-CA `128M` (it peaks near 80 MB starting: 50M had it killed, 2.3.6.1.27), webui `96M`: the same
  at every size (they do not grow with the host).
- OpenBao, Kea, FreeRADIUS, the BIND resolver (`resolver_mem_limit`, 384M: its lists are zone data,
  about 0.53 KB a record, 2.3.12.1.17) and Fluent Bit: their own `*_mem_limit` settings.
- The ceilings together stay at about two thirds of `host_ram_capacity`; the rest is the system's, Docker's and the
  page cache's.

> [!WARNING]
> **JVM Memory Scaling (Keycloak)**
> Because Keycloak runs on a Java Virtual Machine (JVM), applying a rigid Docker `mem_limit` without instructing the JVM about it can cause blind memory allocation leading to an abrupt OOM-kill. To prevent this, the templates compute and inject `JAVA_OPTS_APPEND=-Xmx{HeapSize}` into the Keycloak container, sizing the heap to exactly 80% of the calculated Docker ceiling.

### 1.2.4.2.3 Staggered Boots
If the server cold-boots with the smallest capacity (`host_ram_capacity` 4), parallel spin-up of all containers can trigger a "thundering herd" resource exhaustion, overloading the CPU and crashing the system before initialization completes.

To mitigate this, artificial boot delays (`ExecStartPre=/bin/sleep N`) are automatically injected into the `systemd` wrapper templates, forcing the following strict sequence:
1. **Postgres**: Boots immediately (`0s`).
2. **Keycloak**: Waits `15s` for Postgres to stabilize.
3. **Rest of Stack**: every other unit (nginx, BIND9, Samba, Step-CA, OpenBao, the web UI and the optional services) waits `30s` (15s after Keycloak).

## 1.2.4.3 Memory as a budget

**Built 2026-10-11 for 0.9 (decision 2.1.1.47):** `fabriclib/system/plan_memory.py` plans it, `vars.yaml.j2` renders it as `memory_plan` on every render (and so refuses it, in setup and every apply), each compose file takes its service's limit through `memory_mb('<service>')` (`system/memory_limit_mb.py`); `system/show_memory_plan.py` prints it for `fabricctl status` and setup's plan. Tests: `tests/render.py`, the `hardening` suite.

1.2.4.3.1 **The budget.** `host_ram_capacity` (GB, at least 4: what the owner lets fabric use, 1.2.4.2) less a
reserve for the host itself (the OS, Docker, fabric's own Python: 512 MB) is the budget. Only installed services take
part: a part that is off (1.1.9) has no container and takes nothing.

1.2.4.3.2 **Floors and shares.** Every service has a floor, the limit it needs to run (today's fixed numbers, e.g.
step-ca 128 MB, nginx 256 MB, Kea 128 MB per container, FreeRADIUS 128 MB, Fluent Bit 64 MB, OpenBao 256 MB, the web
console 96 MB). The services that use memory when they have it get the rest by weight: Keycloak 6, Samba 3, the
resolver 2, Postgres 1, BIND 1 (Keycloak's JVM and Samba's database grow most; the resolver holds the lists). Each
one's limit is its floor plus its share; the plan prints every limit and the reserve, so the numbers add up to the
budget. A floor or weight can be overridden in the settings (`memory_floors`, `memory_weights`), checked like any
setting.

1.2.4.3.3 **The check.** If the floors of the installed services do not fit the budget, setup and every apply refuse,
naming the parts that could be turned off and how much memory the plan needs. The JVM's heap follows Keycloak's limit
as today. `fabricctl status` and the web console's overview show the split. The hardening suite checks that each
container's limit is the planned one; a render test checks that the limits always sum to the budget and that turning a
part off raises the others'.

1.2.4.3.4 **As built (2026-10-11).** The floors and weights:

| Service | Floor (MB) | Weight |
|---|---|---|
| Keycloak | 1024 | 6 |
| Samba (the DC) | 512 | 3 |
| the DNS filter's resolver | 128 | 0 |
| Postgres | 128 | 1 |
| BIND | 128 | 1 |
| nginx | 256 | 0 |
| OpenBao | 256 | 0 |

1.2.4.3.5 **AdGuard Home joins the budget (0.7.1, decision 2.1.12.8).** Its memory is steady while it serves, and
briefly about 2.5 times that while it compiles its lists (after a list changes, at the daily fetch, at a start:
1.12.3.9). The budget counts the steady part: AdGuard Home has a floor of 384 MB (the owner's 16 lists take about 380
MiB) and a weight of 1, and goes with the DNS filter (`dns_filter: none` turns it off). Its container's limit is 2.5
times its share, so compiling fits; what the limits reach past the budget during that minute is reported, never
refused: setup's plan and `fabricctl status` show each service's line, AdGuard Home's with "up to N MB while it
compiles its lists", and a warning with how far past the budget fabric may go. A steady need that does not fit is
refused: the floors' check (1.2.4.3.3), and a list ticked past AdGuard Home's share (1.12.3.9). An admin's
`adguard_mem_limit` fixes the container's limit, and the budget counts it / 2.5; the 0.7.0 default it held (1 GiB at
4 GB) counts as not set. The limits with Keycloak and the web console on:

Decisions made while building:

- **An explicit `*_mem_limit` wins.** The six services that had a limit setting before 0.7.1 (`openbao_mem_limit`, `kea_mem_limit`, `samba_mem_limit`, `freeradius_mem_limit`, `fluentbit_mem_limit`, `resolver_mem_limit`) keep it: an admin's value fixes that service's limit (it takes no share and counts against the budget like a floor, even below the floor). A value not set is `null` in the settings file (every install from 0.7.1 on); any value set is the admin's (the values held by default before 0.7.1 are no longer read as unset: 2.1.1.61). Otherwise `memory_floors` and `memory_weights` override the built-in values service by service.
- **The check is in the render.** `vars.yaml.j2` plans the memory, so every render — setup's plan, setup's deploy, every apply — refuses a plan whose floors do not fit, naming each part that could be turned off with what it frees, and the GB the plan needs. `memory_floors` takes MB or a size (`512m`), at least 1 MB; `memory_weights` a number, 0 or more (0: the floor only); an unknown service is refused naming the known ones.
- **Status and the plan** print the split (`show_memory_plan`); the web console's overview does not yet.

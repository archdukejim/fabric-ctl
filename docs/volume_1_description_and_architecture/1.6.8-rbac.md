# 1.6.8 Access control for people across the stack

Topics:

## 1.6.8.1 Access control for people: RBAC across the stack (decided, 2.1.6.1; built)

Today the web UI has one role (`fabric-console-admin`, `fabric-admin` before 0.6.4) that can do everything. The
389-DS roles of [1.10.1.1](1.10.1-kea-design.md#11011-kea-dhcp)/[1.11.1.1](1.11.1-freeradius-design.md#11111-8021x-freeradius) are what *devices* may do on the network; this is
what *people* may do in fabric.

- **Permissions** per area and action, each a Keycloak realm role:
  `dns:read|write`, `tsig:manage`, `pki:read|issue|sign|link-device`,
  `devices:read|enroll|admin`, `roles:admin` (device roles),
  `radius:read|admin|coa` (802.1X; `coa`: disconnect or re-authenticate a session, 1.11.1.4), `people:read|create|reset`,
  `vault:status|unlock-methods`, `audit:read`, `system:admin`
  (services, updates, settings).
- **Bundles** are Keycloak composite roles granted to LDAP groups; fabric
  ships these, admins add their own in Keycloak:

  | Bundle | Can |
  |---|---|
  | Admin | everything (today's `fabric-console-admin`), and alone the site's sudo rules (`sudo:admin`) |
  | Network operator | DNS records and zones, TSIG keys, reverse zones, DHCP (Kea) — **no** device management |
  | Equipment operator | all 802.1X (FreeRADIUS) and 389-DS hardware management: devices, device roles, enable/disable, link certificates to devices |
  | PKI operator | sign CSRs, issue key pairs, convert certificates, link issued certificates to devices (TSIG keys belong to Network operator) |
  | Helpdesk | create realm users, reset their sign-in (password, TOTP), enrol devices; read-only elsewhere |
  | Auditor | read every tab and the audit log; changes nothing |

- **Enforced twice.** The web UI shows only what the user may do; the
  fabric-agent re-checks every call against the user's **signed Keycloak
  token**, which the web UI forwards and the agent verifies itself
  (signature via the realm's keys, issuer, audience, expiry, roles). A
  compromised web UI container cannot act beyond the signed-in user.
- **OpenBao** uses the same roles: each bundle maps to OpenBao policies
  through the OIDC role's claims (built: Admin → `fabric-console-admin`, Auditor →
  `fabric-auditor` via external identity groups; others not admitted).
- **Built:** permission roles, bundles and their groups in Keycloak and
  389-DS, the agent's token check and route table, pages that follow the
  permissions, token renewal (a removed role ends the session), the
  Helpdesk people pages (add a person, reset a sign-in; fabric-group
  members only by an admin). The permission list as built
  (`src/fabriclib/rbac/permissions.py`, roles named
  `fabric:<permission>`) differs slightly from the list above: it adds
  `status:read` and `dhcp:read|write`, names the unlock-method permission
  `vault:unlock`, and uses `system:admin` only for the admin bundle (and a
  privileged sign-in reset); no route needs it yet. Host access (1.6.11) added
  `machines:admin` (the site's machines and its host groups: the equipment
  operator bundle too) and `sudo:admin` (the site's sudo rules, 1.6.11.7:
  the admin bundle only, since a rule gives root on machines). The whole
  list, with what each permission allows and where, is
  [1.8.2](1.8.2-webui-security.md). The bundles are the
  Keycloak roles `fabric-console-admin` (the configurable `webui_admin_role`; 2.1.6.33),
  `fabric-network-operator`, `fabric-equipment-operator`,
  `fabric-pki-operator`, `fabric-helpdesk` and `fabric-auditor`.
- **The host CLI** stays root (`sudo fabricctl` = everything); RBAC covers
  the web UI and its agent API. Step-up sign-in (5 min) and the typed host
  name stay on dangerous changes whatever the role. *As built, both apply
  to OpenBao unlock-method changes only.*

## 1.6.8.2 The site helpdesk and roles granted from above

Decision 2.1.9.21 (owner, 2026-10-13); built 2026-10-13 for 0.9, not yet run against containers (2.3.9.2). The
directory side (who may write what in AD) is [1.6.3.18](1.6.3-samba-directory.md#16318-layered-roles-in-the-directory-09);
granting and the Federation tab are [1.9.8.20](1.9.8-federation-on-ad.md#19820-layered-roles-and-sibling-isolation).

1.6.8.2.1 **Two layers.** *Central IT* is the organisation's groups in `OU=organisation` (`admins`, `network-operators`,
`helpdesk`, ...): every site's Keycloak maps them to their bundles, as before, so they act at every site. A *branch's
local admins* are its `<site>-admins`: by default they are the **site helpdesk** and nothing more.

1.6.8.2.2 **The site helpdesk bundle**, `fabric-site-helpdesk`: `status:read` and the site forms of the people
permissions — `site:people:read`, `site:people:create`, `site:people:reset`, `site:people:unlock`,
`site:people:disable`. A site's Keycloak grants it to its own `<site>-admins` group only.

- The agent accepts a site form wherever the route needs the plain permission (`rbac/holds_permission`,
  `rbac/permissions.SITE_SCOPED`), then narrows the operation: the People list shows this site's own people; a
  reset, unlock, disable or enable is refused, with why, for a person who is not in this site's own `OU=people`
  (a sub-site's, a parent's or a sibling's) or who holds a role — a fabric group, the host admins, or any site's admin
  or role group (`directory/common/site_helpdesk_refusal`). Adding a person always adds them to this site.
- The pages treat a site form as the permission it narrows (the buttons show), and say on the People page that only
  this site's people are listed.
- `people:unlock` is new for everyone who resets (the `fabric-helpdesk` bundle, the admin): it clears the lockout in
  AD and in Keycloak's brute-force protection and keeps the password (`fabricctl people unlock`, Directory → People →
  Unlock).

1.6.8.2.3 **Roles granted from above.** Each site has, empty, the console role groups `<site>-network-operators`,
`<site>-equipment-operators`, `<site>-pki-operators`, `<site>-helpdesk` and `<site>-auditors`, besides the AD role
groups of 2.1.9.13. A site's Keycloak maps **only its own** site's groups (1.9.3.1's decision F4): a second LDAP group
mapper, `fabric site groups`, reads them read-only from the site's `OU=groups` with nested membership
(`LOAD_GROUPS_BY_MEMBER_ATTRIBUTE_RECURSIVELY`, AD's `LDAP_MATCHING_RULE_IN_CHAIN`), and each is granted its bundle
(`keycloak/site_bundle_grants`). So a role granted at `branch1` gives its bundle in `branch1`'s console and nowhere
else, and a group of another site gives nothing here. The organisation's own mapper ignores that mapper by name.

1.6.8.2.4 **What it does not change.** The host CLI is still root. The fabric-agent's own rights in AD are unchanged
(owner, 2026-10-13): the narrowing is of the people, not of the agent.

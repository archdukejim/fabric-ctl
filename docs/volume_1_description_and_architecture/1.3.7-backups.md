## 1.3.7.1 Status and scope

*Designed 2026-11-19 for 0.10.1 (decisions 2.1.1.105, 2.1.1.106, 2.1.3.6). Built on `dev/0.10.1-backup`: the bundle, backups by hand and on a schedule, whole and section restores, uninstall and reinstall through bundles; the console's Backups page (1.3.7.9: the list, download, upload, back up now, the schedule, one section or the
whole bundle restored); the setup site's restore, from a bundle on the host or uploaded (1.3.7.10); not yet built: a host rename in a
restore (1.3.7.7).* The owner: "Uninstall and
reinstall in place with changes ... directories can be kept, certificate authorities, and dns can all remain inplace,
with an ip change ... This also should be used as a backup ... an encrypted tar or zip bundle ... Backup scheduleling
should also be included." And, 2026-11-19, the main reason for it: "so I can migrate my system to a different vlan
and subnet, and change my host ip". **Moving an install to another VLAN and subnet, with a new host address, is the case
this chapter is built and tested for first** (1.3.7.7, 1.3.7.14).

One encrypted bundle is fabric's backup, its export at uninstall and its way to move to another network:

- **A backup**, made by hand (CLI, console) or on a schedule (1.3.7.5).
- **A whole restore**, onto the same host or a new one, with the address, subnet, gateway or host name changed if
  wanted (1.3.7.6, 1.3.7.7). The domain, its members, the CA, DNS, OpenBao and second factors stay as they were.
- **A section restore** on a running install: one of seven sections put back, the rest left as they are (1.3.7.8).

Who: Domain Admins only, in the console; root on the host, in the CLI (1.3.7.12). Not in scope: linked sites
(decision 2.1.1.77 stands for them), copies to a share or another host (after 0.11.0), the domain or DC renamed
(2.1.6.45).

## 1.3.7.2 The bundle

One file, `fabric-<host>-<UTC yyyymmddThhmmssZ>-<kind>.fabric.tar`, `kind` being `manual`, `scheduled`, `uninstall` or
`reinstall`. It is a plain `tar` (not compressed, not encrypted) holding:

| Member | What | Encrypted |
|---|---|---|
| `manifest.json` | format version (1), fabric version and commit, host name, domain, `host_ip`, `lan_cidr`, `lan_gateway`, `dns_server`, whether it has linked sites (`linked`), when, kind, how it was made (`cold` or `online`), how it is opened (`passphrase` or the public key's `age1…` recipient), and per section: name, file, size, SHA-256 of the encrypted file, what it holds | no |
| `<section>.tar.zst.age` | one per section (1.3.7.3): the section's files as a `tar`, compressed with zstd, encrypted with `age` | yes |
| `README.txt` | what this file is, how to open it (`age -d`), and that whoever opens it has the CA and the vault | no |

- **The manifest holds no secret.** It names the host, the domain and the addresses, so a bundle can be listed and
  checked (each section's SHA-256) before anyone gives the key. A changed manifest or section fails the check, and the
  restore stops before it touches anything.
- **Encryption** is `age` (2.1.3.6): a bundle made by hand, at uninstall or at reinstall takes a passphrase typed twice
  (scrypt, `age -p`); a scheduled bundle is encrypted to the public key set with the schedule (`age -r`), so the host
  holds nothing that opens it. Every section of one bundle is encrypted the same way.
- **Nothing is written unencrypted.** Each section is streamed `tar | zstd | age` to its file; no plain copy is made
  on disk, and a section that fails leaves no partial file (written as `.part`, renamed when whole).
- **The folder:** `/var/backups/fabric/` (root, 0700; each bundle 0600), for every kind.

## 1.3.7.3 Sections

Each section names its folders under the install root, its folders outside it, and the `vars.yaml` keys it owns. A
`vars.yaml` key belongs to one section only; the keys of no section belong to **settings**.

| Section | Holds | `vars.yaml` keys | Depends on |
|---|---|---|---|
| `directory` | the domain: Samba's database and SYSVOL (people, groups, machines, devices, policies, the address plan, 2.3.1.38.1), the Administrator's password file | `ad_*`, `dc_name` | `dns` (the domain's own zones live in the directory, its records in BIND) |
| `dns` | BIND's zones and keys, the resolver, the DNS filter and AdGuard Home's settings | the zone's records, `tsig_keys`, `dns_*`, `dnsfilter_*` | — |
| `pki` | Step-CA whole (root and intermediate keys, its database), every issued certificate and key (nginx, bind9, keycloak, postgres, openbao, webui) | `ca_*`, `byoc*` | — |
| `secrets` | OpenBao's data (a raft snapshot online, the data folder cold), its vault key and unlock-method files | `openbao_*` | every section: it holds their passwords |
| `signin` | Keycloak and its Postgres database (second factors, sessions) | `keycloak_*` | `secrets` |
| `dhcp` | Kea's files and leases | `kea_*`, `dhcp_*` | `directory` (the address plan) |
| `settings` | `vars.yaml` (all of it), fabric's config folder, the audit log, federation's registry, the host's run records | every key not above | — |

- **A whole bundle** always holds all seven. Whatever is not installed (DHCP off, no Keycloak) is an empty section,
  listed as such.
- **`settings` holds all of `vars.yaml`**, so a whole restore has every key; a section restore takes only its own keys
  from it (1.3.7.8).

## 1.3.7.4 Making a bundle

- **Cold** (uninstall, reinstall): as 0.10.0's export did (`setup/stop_for_copy.py`): fabric's secrets read
  out of OpenBao while it runs, then every fabric timer and unit stopped and proven stopped (2.3.1.53), then each
  section streamed. The stack stays stopped for the uninstall that follows.
- **Online** (by hand, scheduled): fabric keeps running. Each service is copied by its own consistent method:

| Service | Online method | Pause |
|---|---|---|
| Samba (the DC) | `samba-tool domain backup online` against the local DC, into the section's stream | none |
| Postgres (Keycloak's) | `pg_dump` of each database | none |
| OpenBao | `bao operator raft snapshot save` (raft storage, `templates/openbao/openbao.hcl.j2`) | none |
| Step-CA | its database (badger) cannot be read while it writes: the unit is stopped, the folder copied, the unit started (`systemctl_up`) | seconds; ACME and renewals retry |
| BIND | `rndc freeze` of each dynamic zone, its files copied, `rndc thaw` | dynamic updates wait, seconds |
| Kea, AdGuard Home, the resolver, config | files copied as they are (each rewritten whole, never in place) | none |

- **A run takes a lock** (`/run/fabric/backup.lock`): one bundle at a time, and no setup, `--apply`, image update or
  restore starts while one is made (each is refused, naming the backup running).
- **Every run is audited** (`BACKUP_MADE`, `BACKUP_FAILED`): who, kind, file, size, the sections and how long.
- **Disk:** before it starts, the run checks the folder has twice the install's size free; short of that it refuses,
  naming the space needed.

## 1.3.7.5 The schedule

- **One schedule per install**, off until set: the time of day (default 03:00, the host's time), how many scheduled
  bundles to keep (default 7), and the public key (`age1…`). Kept in `vars.yaml` (`backup_schedule_time`,
  `backup_keep`, `backup_public_key`; a public key is not a secret).
- **A systemd timer**, `fabric-backup.timer` (`Persistent=true`, so a run missed while the host was off happens at
  boot), runs `fabric-backup.service`, which makes an online bundle (1.3.7.4).
- **Keeping:** after a scheduled bundle is whole, the oldest scheduled bundles beyond `backup_keep` are removed. Bundles
  made by hand, at uninstall or at reinstall are never removed by it.
- **A failed run** is audited, shown on the console's Overview and by `fabricctl doctor` until a later run succeeds.
- **The private key** is the operator's, made on another machine (`age-keygen`); the console and the CLI print how. It
  is asked for only to restore (1.3.7.6, 1.3.7.8).

## 1.3.7.6 Restoring a whole bundle

Onto a host where fabric is not installed (after `fabricctl uninstall`, or a new host with the package installed):

1. The bundle is checked: manifest format, each section's SHA-256, and the fabric version (a bundle from a newer fabric
   than the package is refused; an older one within the upgrade window, 2.1.1.20, is restored and setup migrates it).
2. The key is asked for (the passphrase, or the private key for a scheduled bundle) and held in memory only.
3. Each section is decrypted and unpacked straight into place, owners and modes kept, as `restore_install` does today.
   A cold bundle is then whole: its folders are the install as it was. An online bundle's three dumps (1.3.7.4) stay
   in RAM (`/run/fabric/backup/dumps`) and are loaded by setup, each at the moment its service allows
   (`config/restore-pending.json` names them; each is crossed off once loaded, so a setup run again goes on):
   - **The domain**, before the DC first starts: the offline copy's `private/`, `state/` and `etc/` files go over the
     folders packed live (SYSVOL among them, with its ACLs), and the copy's backup marks (`backupDate`,
     `sidForRestore`, `backupType`), with which Samba refuses to start, are removed from `sam.ldb` by
     `finish_restore.py`, run in the DC's own image (`docker compose run`) while the DC is stopped. Samba's own
     `backup restore` is not used: it gives the DC a new name, which fabric never changes (2.1.6.45).
   - **OpenBao**, once setup has started and initialised it: the snapshot is loaded with `sys/storage/raft/snapshot-force`
     and the new cluster's one-time root token; OpenBao reopens on the bundle's data with the bundle's vault key, the
     one-time token (now unknown to it) is deleted, and setup goes on with the bundle's own AppRoles.
   - **Keycloak's database**, once Postgres runs and before Keycloak starts: `pg_restore --clean --if-exists` into the
     `keycloak` database over the container's own socket.
4. Setup runs on it unattended (`--yes --non-interactive`), as `fabricctl restore` does today: the same CA, directory,
   Keycloak, DNS with its TSIG keys, OpenBao with its vault key.
   Setup makes no first admin and asks no password for one: the directory comes back with its admins, also from an
   online bundle, whose dump is still pending when setup decides (`first_admin_needed` reads `restore-pending.json`;
   found 2026-11-23 by the sandbox's whole restore from the console).

With no changes asked, the install comes back at the same address and name. With changes, 1.3.7.7.

## 1.3.7.7 Reinstalling with changes

A whole restore may change, before setup runs: `host_ip`, `lan_cidr`, `lan_gateway`, the upstream `dns_server` (the old
network's router may have been it; added 2026-11-19), and the host's name (`hostname`; not built yet: refused, pointing
to 4.2.4.3). Never the domain, the realm or the DC's name (2.1.6.45).

**The host is re-addressed first** (2026-11-19, found by tracing setup): setup refuses a `host_ip` the machine does not
have (`network_problem`), so the restore checks it before anything is unpacked, and refuses with the steps to take.
For another VLAN and subnet that means the operator's procedure 4.2.4.8: uninstall with a bundle, move the host to the
new VLAN and give it its new address, then restore the bundle with the changes. `fabricctl reinstall --set …` does all
of it in one run, so it refuses an address the host does not have yet and points to 4.2.4.8.

**Host changes asked again** (2026-11-19, found by the sandbox's move): the firewall's and the ports' networks and the
domain member's address are host changes the operator allowed for the old network (global Rule 12), and setup asks
for them again when they change. A restore with a new address asks one question up front, before unpacking: allow
again the groups `consent.yaml` records as allowed (setup gets `--approve` with those; a declined group stays
declined). Unattended, it never assumes yes: `--approve GROUPS` is given by name.

What moves with each, and nothing else:

- **The address** (`host_ip`, and with another network `lan_cidr` and `lan_gateway`): the zone's own records render at
  the new address only (1.4.1.8, 2.1.1.74), the DC re-registers its records at the new address with the old ones
  removed (1.4.1.8.6), `/etc/hosts` is rewritten, the firewall's rules are made for the new network (1.2.11), the
  resolver's and DHCP's own-address settings follow; certificates naming the old address are re-issued from the same
  CA (the CA stays; only leaf certificates change). Settings the admin made that name the old address or subnet are listed
  for the admin to change, never changed silently (2.1.4.6): `old_address_uses` walks the restored `vars.yaml` (the
  zone's records, DHCP's subnets, pools, routers and options, RADIUS clients, firewall allowances, extra certificates'
  names, the upstream DNS server), leaving out fabric's own, which setup renders again; the restore prints them.
- **The address plan's LAN subnet moves with it** (the owner's choice, 2026-11-19): the plan's subnet that was the old
  `lan_cidr` becomes the new one in the same VLAN, under the same name, its gateway, ranges (DHCP pools) and addresses
  keeping their host numbers (`.200 - .220` stays `.200 - .220`; one that does not fit a smaller subnet is left out and
  named). The restore records the move in `restore-pending.json` (`plan_move`); until the DC runs, every render uses
  the plan moved in memory (`ipam/moved_plan`), and once the domain has converged setup writes it with the plan's own
  functions (`ipam/move_lan_subnet`: the old subnet removed, the new one added, then each range and address), then
  crosses it off. A run that stops part way goes on at the next setup. The subnet's DHCP options are not carried and
  are named for the admin. The plan's other VLANs and subnets stay as they are.
- **The host's name**: as 4.2.4.3 does it (break glass's rename, applied), with the host's join moved to the new name.
- **The machines fabric manages** keep their accounts (the directory comes back) but still ask the old address for
  the domain's names until pointed at the new one. Announced before the uninstall, `fabricctl move prepare <address>
  --network <subnet>` (1.4.1.8.7, 2.1.1.79 revised 2026-11-22), they follow: the record is in the directory, so the
  bundle carries it, and each member switches once the old address is silent and the new answers (it needs a route to
  the new subnet). Not announced, they are pointed at it by hand (4.2.4.2 step 5).
- **Refused:** a site with linked sites (the bundle's manifest records `linked`; for a reinstall, `federation.yaml`),
  until they are unlinked (2.1.1.77); a new address this host does not have yet (above). Not built yet: a new address
  that collides with anything fabric claims or the network holds (1.2.13; global Rule 9).

The CLI form is one command (1.3.7.11): `fabricctl reinstall --set host_ip=… --set lan_cidr=… --set lan_gateway=…`
makes a cold bundle, uninstalls, and restores it with the changes. The browser form is 1.3.7.10.

## 1.3.7.8 Restoring one section

On a running install, one section of a bundle replaces that section's state; the other six are left as they are.

1. **The warning** (the console's and the CLI's own words): what the section holds, that its current state is replaced
   and lost, that it cannot be undone, and the sections that depend on it (1.3.7.3's last column), with what each will
   then see. The CLI asks for the site's name typed; the console asks as 1.3.7.9 says.
2. **A safety bundle first:** an online bundle of the same section, with `settings` (which holds the `vars.yaml` a
   section is restored with), the other sections empty; kind `manual`, encrypted the same way as the one being
   restored, so the replaced state can be put back. If it cannot be made, nothing is restored.
3. **The section's services stop** (only theirs), its files are replaced, or its dump loaded into the running
   database (whose folder an online bundle leaves out and the restore leaves in place), its `vars.yaml` keys
   (1.3.7.3) are replaced with the bundle's, the rest of `vars.yaml` untouched.
4. **`--apply` runs** for the section's services, and doctor's checks for them (`fabricctl doctor`).
5. **Audited** (`RESTORE_SECTION`): who, the bundle, the section, the safety bundle's file.

Per section:

- `dns`, `pki`, `signin`, `dhcp`, `settings`: restored alone, with the warning naming what depends on them. `pki`:
  certificates issued after the bundle was made are no longer known to the CA (their holders renew).
- `directory`: restored alone with the DC stopped; machines that changed their password since the bundle was made fall
  off the domain and rejoin (4.6.6, 4.6.7); the warning lists how many changed (`pwdLastSet` after the bundle's time).
- `secrets`: **not restored alone.** OpenBao holds every service's password; put back alone it would no longer match the
  running databases. It comes back only in a whole restore (1.3.7.6; 2.1.1.106 point 2).

A section restore needs the bundle's fabric version to equal the installed one: it does not migrate (a whole restore
does).

## 1.3.7.9 In the console

A **Backups** page under Settings, shown only to Domain Admins (1.3.7.12):

- **The list:** every bundle in `/var/backups/fabric/` with its kind, time, size, fabric version, sections and whether its
  check passes; **Download** for each (streamed, the file unchanged).
- **Back up now:** asks a passphrase, twice (or "use the schedule's public key" when one is set), then makes an online
  bundle as a job (1.8.6.5), followed live.
- **The schedule:** on or off, the time, how many to keep, the public key (checked as an `age1…` recipient), with the
  next and last runs and the last run's result.
- **Restore:** pick a bundle from the list (or upload one, 1.3.7.10's limits), then **whole** (offered only as the
  reinstall it is: the console says the page will go down and setup will run on the host; 1.3.7.6) or **one section**
  (1.3.7.8). The key is asked for. Then the destructive-act warning, in full: what is replaced, that the current state is
  lost, that it cannot be undone, the sections that depend on it. Then the confirmation (1.3.7.12).
- **Every action is a job** with its outcome kept (1.8.6.5); fabric-agent does the work as root (1.3.3), never the
  console.

How it is built (fabric-agent's routes: 1.3.3.1):

- **The page** is `/settings/backups`. Its entry under Settings is shown when the sign-in found the person a Domain
  Admin (`GET /v1/backup/allowed`, asked once per sign-in). That only hides the entry: fabric-agent checks again at
  every backup route, and the page answers 403 to anyone else.
- **Domain Admins** are checked in the DC by the grants tool's `domain_admin` op. It takes the members of the group
  whose SID ends in -512, nested groups followed, and answers whether the caller is one of them. Root on the host
  passes without asking.
- **The list's check** is each bundle's SHA-256 check (`check_bundle`), done by fabric-agent. The result is kept by
  file, size and modified time, so each bundle is hashed once, not at every visit. The list also shows how each bundle
  is opened (a passphrase, or the schedule's private key).
- **Download** streams the file through fabric-agent and the console, never read whole into memory. The download
  is audited (`BACKUP_DOWNLOAD`). It is a separate fabric-agent route because it answers the file, not JSON.
- **The schedule's runs** come from systemd: the timer's next and last trigger, and the service's last result
  (`systemctl show`).
- **Back up now and Restore one section** are fabric-agent jobs (`backup`, `restore`), followed on the job's page.
  Each is audited when it starts (`BACKUP_START`, `RESTORE_SECTION_START`) and again when it ends, by the function
  doing the work. A job is kept in fabric-agent's memory (1.3.3), and the audit log keeps the outcome after a restart.
  The passphrase or private key goes to fabric-agent in the request body and stays in the job's memory. It is never
  written to the job's kept result.
- **The step-up** is the console's: a sign-in older than 5 minutes is sent to sign in again before Back up now, the
  schedule or a restore. A restore also asks for the site's name typed.
- **A whole restore** is `fabricctl reinstall --from <bundle>` run by fabric-agent as a systemd unit of its own,
  `fabric-console-restore`. The uninstall stops fabric-agent and the console, and the unit keeps going without them.
  Before anything is touched, fabric-agent checks what the CLI would check: the bundle whole, made by this fabric or
  an older one within the upgrade window, for this install root, its addresses on this host, the key opening it, and
  no backup, restore or earlier console restore running. Then the run:
  1. A safety bundle of the install as it is, cold, sealed the same way the chosen bundle is: the same passphrase, or
     the public key that bundle was made to.
  2. Fabric uninstalled (the host's domain account kept), the chosen bundle restored whole, unchanged.
  3. Setup run on it, as after any restore.

  The key reaches the unit in a root-only file in `/run/fabric/` (RAM), which `--key-file-once` reads and removes;
  never on a command line. The unit's output is appended to `/var/backups/fabric/console-restore.log` (root, 0600).
  The page shows the end of that log and whether the unit runs, once the console is back. The start is audited
  (`RESTORE_WHOLE_START`) before the audit log is replaced. The restore itself is audited in the restored log
  (`RESTORE`, by the person). Changing addresses on the way is not offered here: that is the move procedure (4.2.4.8).
- **An upload** adds a bundle to the list: a file of up to 8 GiB, from **Upload a bundle** on the page.
  - **nginx** lets that one path take 8 GiB and passes the body on as it arrives, never spooling it to disk. Every
    other console path keeps its 64 KiB limit.
  - **The console** checks the Origin and the form's CSRF field, which comes first in the form, before reading the
    file. It then passes the file's bytes to fabric-agent as they arrive (chunked), never holding the file.
  - **fabric-agent** checks Domain Admins first. It writes the bytes to a hidden `.part` file (0600) in
    `/var/backups/fabric/` and stops past 8 GiB or when less than 1 GiB would be left free.
  - **Once the file is whole**, it must carry a bundle's name not already in the folder and pass `check_bundle`.
    Only then is it renamed to that name, so the list never shows a partial or damaged upload.
  - **Audit:** the upload is audited (`BACKUP_UPLOAD`). A refusal removes the `.part` file.

## 1.3.7.10 In the setup site

The setup site (1.3.6) gains a first choice: **New install** (Guided, as today) or **Restore from a backup**.

1. **The bundle:** one already on the host (the site lists `/var/backups/fabric/` and accepts a path the person types),
   or an upload. An upload is streamed to `/var/lib/fabric-setup/upload/` (owned by the site's uid 649, 0700), checked
   against its manifest as it lands, and handed to setup as a file; never held in memory.
2. **The manifest** is shown: host, domain, addresses, when, fabric version, the sections and the check.
3. **The key**, typed and handed to setup in memory, as the first admin's password is (1.3.6.4).
4. **The changes** (1.3.7.7): the address, subnet, gateway and name, prefilled with the bundle's; each collision checked
   as Guided checks its answers (1.3.6.7).
5. **The plan**, with the host changes as one list and one confirmation (1.3.6.4), then **Proceed**: the restore runs in
   `fabric-setup.service`, followed live (1.3.6.5), and the finish shows what moved (1.3.6.6).

The listener never decrypts: it holds the uploaded file and passes the key to the root setup worker, which does
(1.3.6.3's privilege split).

**As built** (2026-11-22, `src/fabriclib/setup/site/ask_start.py`, `ask_restore.py`, `setup/detach/run_restore.py`):

- The first choice is setup's question `setup.start`, asked once the site is open, two buttons on the page (New install
  first). Restore's questions are setup's own (`restore.bundle`, `restore.key`, `restore.<setting>`, `restore.plan`),
  asked through the same front end as Guided's, so a terminal attached to the site (2.1.8.60) answers them too.
- The bundle is picked by its number in the folder's list or by a path; a bundle that `check_bundle` refuses is said
  and asked again. The manifest is printed above the key's question. The key is a passphrase or, for a scheduled
  bundle, the `AGE-SECRET-KEY-1…` line.
- `check_whole_restore` with the changes runs before the plan: the version, the install root, `check_changes`, the
  addresses (changed or not) on this host, and the key opening the bundle. A refusal is said, nothing is unpacked, and
  the key and the addresses are asked again.
- The plan lists the changes; with a new address, its one Proceed also allows again the host changes allowed when the
  bundle was made (as `fabricctl restore` asks in `restore.approve_move`, 1.3.7.7). Quit changes nothing.
- Proceed hands the key over as the first admin's password is (`/run/fabric-setup`, 0600, removed when the run ends)
  and records the bundle, the changes and the allow-again in the run's options. In `fabric-setup.service` the worker
  restores the bundle (`restore_bundle`, audited as the setup site, source `web`), keeps what moved in the run record,
  then runs `fabricctl setup --yes --non-interactive` with every step in the same unit, with `--approve` for the groups
  allowed before; the site follows the one log. A unit restarted after the unpack does not unpack again.
- The finish adds **Restored from the bundle**: each change, old and new, and the settings still naming the old
  address (`old_address_uses`).
- Refused before any question: fabric already installed here (restore from the console, 1.3.7.9, or
  `fabricctl reinstall --from`).
- **The upload** (`listener/save_upload.py`, `listener/multipart_reader.py`, `site/ask_restore._take_upload`): the
  bundle's page has an upload form, its token and the question's number sent before the file. The listener reads the
  body as it arrives (the standard library's own copy of the console's reader, 1.3.6.3), checks the token first,
  writes a hidden `.part` (`0600`) in the upload folder and renames it to its bundle name once whole, then answers the
  question with that path; up to 8 GiB, leaving 1 GiB free, telling setup every 30 s that the person is still there.
  Root never uses the listener's file in place: it opens it without following links, refuses anything but a plain
  file, copies it into `/var/backups/fabric/` through `receive_upload` (checked whole, renamed only then), and removes
  the listener's copy and folder. A refused upload leaves nothing in either folder. Refused at the route: no session,
  another site's Origin, a stale token, no file, a name not a bundle's, too large, the disk too full, a cut body, or
  the bundle not being asked.

## 1.3.7.11 Commands

| Command | What |
|---|---|
| `sudo fabricctl backup [--public-key age1… \| --scheduled-key \| --key-stdin]` | an online bundle of all seven sections now; asks a passphrase twice unless given a public key (the schedule's with `--scheduled-key`) |
| `sudo fabricctl backup list` | the bundles, as the console lists them |
| `sudo fabricctl backup check <file>` | the manifest and each section's SHA-256; no key needed |
| `sudo fabricctl backup schedule --time HH:MM --keep N --public-key age1…` / `--off` | the schedule (1.3.7.5) |
| `sudo fabricctl restore <file> [--set key=value …]` | a whole restore, with changes (1.3.7.6, 1.3.7.7) |
| `sudo fabricctl restore <file> --section <name>` | one section on a running install (1.3.7.8) |
| `sudo fabricctl reinstall [--set key=value …]` | cold bundle, uninstall, whole restore with the changes |
| `sudo fabricctl reinstall --from <file> [--key-file PATH \| --key-stdin]` | a safety cold bundle, uninstall, then `<file>` restored whole, unchanged (the console's whole restore, 1.3.7.9) |
| `sudo fabricctl uninstall [--backup \| --no-backup]` | uninstall, with a cold bundle first (default yes) |

The key is never an argument (global Rule 10): it is asked on the terminal, or read from a file (`--key-file PATH`,
root 0600: a private key line, or else its first line is the passphrase; `--key-file-once PATH` also removes the file
once read), or from standard input (`--key-stdin`) for unattended runs.

## 1.3.7.12 Security

- **Domain Admins only, in the console:** fabric-agent refuses every backup route unless the person is a member of
  the domain's Domain Admins (RID 512, checked in the directory at each request, nested membership counted). Fabric's
  own admin roles (`fabric-admins`, grants, 1.6.13) do not give it. The page and its navigation entry are not shown to
  anyone else (403 by address).
- **Confirming a restore** (decision 2.1.1.105 point 7): a step-up sign-in (password and second factor again, 1.8.6),
  then the site's name typed. Making a bundle and changing the schedule need the step-up too; downloading one does not
  (it is encrypted) but is audited.
- **Keys:** a passphrase is typed twice and checked against the admin password policy's length; it and a private key
  are held in memory for the one run, passed to `age` on a file descriptor, never on its command line, never logged,
  never in a job's kept output.
- **At rest:** the folder root 0700, each bundle 0600, every section encrypted; the manifest carries no secret.
- **The schedule's public key** cannot open a bundle; the private key never reaches the host except typed or read for a
  restore.
- **Integrity:** each section's SHA-256 in the manifest is checked before any key is asked; `age` authenticates each
  section's contents.

## 1.3.7.13 What it replaces

- **`fabricctl uninstall --export DIR`**, its plain-text folder: replaced by `--backup`, a cold bundle in
  `/var/backups/fabric/`. `--export` is kept one release as a name for `--backup`, printing so.
- **`fabricctl reinstall`'s `/root/fabric-reinstall-<time>/`** plain copy (`setup/backup_install.py`): replaced by a
  cold bundle encrypted with a passphrase asked first; it also brings Keycloak back, which today's copy does not.
- **`fabricctl restore <folder>`** on an export folder: kept for exports made before 0.10.1; a bundle is the new form.
- **`apt purge`'s export** to `/var/backups/fabric/fabric-export-<time>/` (apt cannot ask; 2.1.1.106 point 3): with a
  schedule's public key set, a cold bundle to it; without one, purge removes the package only and leaves fabric's data
  and services in place, saying to run `sudo fabricctl uninstall`.
- **3.3.4.1**'s steps by hand for a fabric install: replaced by 1.3.7.7. 3.3.4.1 stays for pre-fabric (core-template)
  hosts.
- **Decision 2.1.1.77** for another network: revised by 2.1.1.106 once built; linked sites stay out.

## 1.3.7.14 How it is tested

- **Unit:** the manifest and its check (a changed byte in a section or the manifest refused), section membership of every
  `vars.yaml` key (a key in two sections, or a fabric folder in none, fails the test), the keeping of scheduled bundles,
  refusals (not a Domain Admin, no step-up, a wrong key, a newer bundle, `secrets` alone, a lock held, too little disk).
- **Host suite, on the test VM from clean** (3.1.5): a bundle made by hand and on the timer while the stack serves
  (DNS answered, a certificate issued, a person signed in during the copy); each section restored alone with what
  depends on it checked; a whole restore onto a fresh VM with no change; a whole restore with another `host_ip`,
  `lan_cidr` and `lan_gateway`, a joined Ubuntu member and a Windows member checked to follow (4.2.4.4); the
  same through the setup site (`tests/setup/site/ask_restore_test.py` for its questions and checks,
  `tests/setup/detach/run_restore_test.py` for its run, `save_upload_test.py` and `upload_test.py` for the upload
  through a real listener).
- **Upgrade:** an export folder from 0.10.0 restored by 0.10.1; a fresh install, where the upgrade does nothing (global
  Rule 9).
- **Entry points:** every command and route above in the inventory with positive and negative cases (2.1.1.38).

## 1.3.7.15 Settings

In `vars.yaml`; the console's schedule form and `fabricctl backup schedule` write them (1.3.7.5). All three belong to
the `settings` section (1.3.7.3), so a restored install keeps its schedule.

| Setting | Default | What |
|---|---|---|
| `backup_public_key` | none | the schedule's age public key (`age1…`); the schedule runs while it is set |
| `backup_schedule_time` | `03:00` | the time of day of the scheduled backup (24 hours, the host's time) |
| `backup_keep` | `7` | how many scheduled bundles are kept (1 to 365); bundles made otherwise are never removed by it |

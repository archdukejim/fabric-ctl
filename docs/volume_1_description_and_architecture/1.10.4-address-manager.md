## 1.10.4.2 What it is

fabric's DHCP becomes an address manager (IPAM) for VLAN-segmented sites: every site's VLANs and their subnets, the
ranges inside each, and **every address** — static ones, reservations and live leases — shown together, in one
plan for the organisation, edited by each house and by the owner above them all (2.1.9.19). The site's gateway
(at the owner's houses a UniFi gateway) routes between VLANs, enforces the policy between them and relays each
VLAN's DHCP to fabric (2.1.10.8); fabric serves the addresses, names them in DNS and tracks them.

## 1.10.4.3 The model

### 1.10.4.3.1 The objects

*Revised 2026-10-23 (1.10.4.34, 2.1.10.36):* "the owner's roles at the top" are the Directory Administrators, and
anyone a grant gives the networks rights at the object's site.

Each object belongs to its site; the owner's roles at the top may edit any site's (2.1.9.5, 2.1.9.13).

| Object | Holds |
|---|---|
| **Block** | the site's number: its second octet in the suggested plan, `10.<site>.0.0/16` (2.1.10.12); unique in the organisation, chosen at install or join |
| **VLAN** | ID (1-4094, unique in the site), name (unique in the site), purpose and notes, `access` (`full` or `guest`, 1.10.3.3) |
| **Subnet** | one per VLAN by default, more allowed (2.1.10.18; a VLAN without one is a record only); CIDR, gateway (the router's address in it), served by DHCP or not, options (1.10.4.6) |
| **Range** | inside a subnet, never overlapping another of its ranges: `gateway`, `static` (set by hand), `dhcp` (Kea's pool), `reserved` (kept free) |
| **Address** | one IP: kind (`static`, `reservation`, `infrastructure`), name, MAC, owner, notes, options (a reservation's), DNS (an A and a PTR in fabric's zone, or none) |
| **Lease** | live from Kea, never stored: shown with the address it holds; its name in `dhcp.<domain>` as today (1.10.3.4) |

### 1.10.4.3.2 The rules

- One address, one claim: a static address, a reservation or the gateway; a second claim is refused, naming the
  first.
- An address inside a `dhcp` range may only be a reservation; a `static` address lies in a `static` range, or is
  warned about (never refused: the admin may know better).
- A subnet that overlaps another anywhere in the organisation is refused, as today (1.10.2.6); `--allow-overlap`
  allows it where networks are never routed together (NAT, separate paths).
- Every refusal says why and changes nothing (Rule 9).

### 1.10.4.3.3 What fabric suggests

Suggestions only, never enforced (2.1.10.9, 2.1.10.12): a site's admins and the owner may enter any subnet, split
and routing, NAT or another path included.

- A new VLAN `n` at site `s` is offered `10.<s>.<n>.0/24` (VLAN 10 management: `10.<s>.10.0/24`; VLAN 255 storage:
  `10.<s>.255.0/24`).
- Inside a /24: gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254`, editable per VLAN.

## 1.10.4.4 Where the plan is kept

*Revised 2026-10-23 (1.10.4.33, 2.1.10.35):* the plan lives in the domain's one `OU=networks`, each entry named with
its site, not in a site's own OU.

In AD (2.1.10.11): each site's VLANs, subnets, ranges, static addresses and options are objects in its own
`OU=networks` (1.10.2.8 already keeps the subnets there), in new classes of fabric's OID arc added through the
schema path 0.7.0 fixed (1.6.5.24). Every DC holds the whole plan. Each site's `vars.yaml` keeps only what is the
host's own: the interfaces Kea listens on (`dhcp.interfaces`) and the global defaults. An apply reads the plan from
AD; a site whose DC does not answer keeps its last rendering.

## 1.10.4.5 How a VLAN is served

- **Relay:** each VLAN's gateway relays DHCP to fabric's `host_ip` (2.1.10.8); Kea picks the subnet by the relay's
  address, the gateway inside it (1.10.3.2). fabric opens 67/udp to the gateways' addresses (the `ports` consent
  group, 1.10.3.5). The gateway's steps (UniFi: each network's DHCP mode "relay", server `host_ip`) are in 4.10.
- **What a VLAN's clients get:** the gateway as router, fabric as DNS and NTP (2.1.10.5), the domain and its search
  list; `access: guest` VLANs only DNS and NTP (1.10.3.3). fabric's own names stay on `host_ip`, reached through
  the gateway.
- **DNS:** a static address with DNS on gets an A in the site's zone and a PTR in its reverse zone (one per /24, so
  one per VLAN); leases register in `dhcp.<domain>` with their PTRs as today (2.1.10.7). A reservation with DNS on
  gets its A and PTR in the site's zone and nothing from DHCP: a name set by hand outranks DHCP's (2.1.10.17,
  2.1.10.20, 1.10.4.19).
- **802.1X:** a role's VLAN (1.11) names a VLAN of the plan, so the console shows "VLAN 20 (iot, 10.1.20.0/24)".
- **The DNS filter's groups** by VLAN keep working (1.10.3.7).

## 1.10.4.6 DHCP options and netboot

### 1.10.4.6.1 Options at every level

Options can be set on the organisation (every site), a site, a VLAN's subnet, a client class and an address (a
reservation); the most specific wins, as in Kea (2.1.10.14). Any option by name or code, with a custom definition
for a code Kea has no name for. Every option appears under its standard name with its code — option 67 "boot file
name", 66 "TFTP server name", 6 "DNS servers", 42 "NTP servers" — never only a number. Almost all are unset. For a
subnet or an address, the console shows the options it ends up with and where each came from.
As built (1.10.4.24.3): Kea ranks a client class's options below the subnet's, so the order is organisation, site,
class, subnet, address.

### 1.10.4.6.2 Options fabric provides

The options fabric sets because it runs the service — DNS (6), NTP (42), the domain name (15) and the search list
(119) — carry a **"provided by fabric"** marker: fabric keeps their values with the stack. An admin may override
one; the marker then says it is overridden.

### 1.10.4.6.3 Netboot presets

A VLAN or an address can switch on a preset, each a set of client classes and options the admin can edit, pointing
at a boot server the owner runs (an address, or a name in fabric's DNS); fabric serves no boot files (2.1.10.15,
1.10.2.7):

- **PXE, BIOS and UEFI:** classes on the client's architecture (option 93: 0 BIOS, 7 and 9 x64 UEFI, 11 arm64 UEFI),
  each with its own boot file name (67), next server and TFTP server name (66);
- **iPXE chain-load:** a client already running iPXE (user class `iPXE`, option 77) gets the iPXE script's URL
  instead of the iPXE binary, so it does not loop;
- **UEFI HTTP boot:** vendor class `HTTPClient` gets an `http://` boot URL, with option 60 echoed back.

## 1.10.4.7 Addresses in use that nobody recorded

Kea pings an address before handing it out and skips one that answers (Kea 3.0's ping-check hook); an admin may also
**scan a subnet on request** (ping and ARP from fabric's host; a routed VLAN answers what its gateway lets through)
(2.1.10.13). Neither ever blocks: an address found in use but unrecorded is shown as "in use, unrecorded" (with the
MAC when ARP saw it), and the console offers to make it a reservation for that device, or a static record; the admin
may also ignore it or register something else there.

## 1.10.4.8 Editing a house from the top

*Revised 2026-10-23 (1.10.4.35, 2.1.10.37):* "the top" is any site's console used by someone with the right at the
site edited; there is no site above another.

An edit from the top's console is written on the top's DC to the house's `OU=networks`; replication carries it to the
house (1.9.8.5). Each site's fabric polls its own DC's highest USN every 30 s; when its OU changed it renders Kea and
reloads it through its control socket (2.1.10.6), with its DNS records and the access lists. A house cut off from the
top keeps serving from its own copy, and its own edits merge when the link is back (AD keeps the last writer per
attribute; the console names a conflict object if one appears, 1.9.8). A site with a read-only DC (1.9.8.3) is
edited from a writable DC above it.
Revised by 2.1.10.24 (as built, 1.10.4.26): the poll is a timer that re-renders and restarts Kea alone (and the
firewall when the served subnets change); DNS records wait for the next apply.

## 1.10.4.9 The console and the command line

*Revised 2026-10-23 (1.10.4.35, 1.10.4.40):* every site is shown; a change needs the grant at its site; the tab is
ported after the console's redo.

- **A Networks tab** replaces the Kea tab's subnet parts: the sites (the top sees every house), a site's VLANs, a
  subnet's map (its ranges as a bar, used and free) and its address table (static, reservation, lease, unrecorded,
  free; search by IP, name or MAC; export as CSV); the options with their sources and markers. Reading needs
  `dhcp:read`, changing `dhcp:write`; a house's admin sees only their house.
- **`fabricctl ipam`:** `block [<n>]` (2.1.10.16), `vlan add|set|remove`, `subnet add|set|remove` (2.1.10.18),
  `range add|remove`, `address add|set|remove`, `option set|remove`,
  `netboot on|off`, `scan <subnet>`, `show [<site>]`, `find <ip|name|mac>`, `export`; `--site` for the top. Every
  entry point gets positive and negative tests and joins the inventory (3.1.2.5).
- Today's `fabricctl dhcp add-subnet` and the other subnet commands become aliases of the new ones for one release,
  then go.

## 1.10.4.10 The upgrade from 0.7

*Revised 2026-10-23 (1.10.4.37, 2.1.10.40):* the upgrade is from 0.8.0, not 0.7.

At the upgrade, each site's `dhcp.subnets` (with their pools, reservations and options) moves into its plan once,
recorded, and `vars.yaml` stops carrying them; each subnet's VLAN becomes a VLAN object (one without a VLAN gets the
next free ID, named after the subnet, and is listed for the admin to check). The site's number is asked once (the
suggestion: its order in the organisation), by setup just before the move (2.1.10.16, 1.10.4.18.1). Nothing a
running site serves changes. A site with a read-only DC keeps its subnets in `vars.yaml` until its parent can write
its plan (S8, 2.1.10.19).

overlap reason), given the `fabricSubnet` class for what only the plan's subnets hold. Every DC holds every site's
entries, so the overlap rule (1.10.2.6) and `read_networks` see the plan's subnets with no second copy.

### 1.10.4.13.2 Where each entry lives

*Revised 2026-10-23 (1.10.4.33, 2.1.10.35):* the entries live in the domain's `OU=networks`, named `<site>/...`; the
site's number is on its record (1.10.4.32).

In the site's `OU=networks` (`CN` values escaped, whatever they hold):

- a VLAN: `CN=<VLAN ID>`, class `fabricVlanRecord` (its name is an attribute, so renaming it moves nothing);
- a subnet: `CN=<subnet name>`, classes `fabricNetwork` and `fabricSubnet`; its `fabricNetworkKind` is `dhcp` when
  Kea serves it, else `subnet`;
- a range: `CN=<kind>-<first address>` below its subnet's entry;
- an address: `CN=<address>` below its subnet's entry.

Removing a subnet removes its ranges and addresses with it (a tree delete). The site's number is on the site's OU.

### 1.10.4.13.3 Who reads and writes it

*Revised 2026-10-23 (1.10.4.33, 1.10.4.34):* AD's per-site access no longer decides: fabric-agent checks the
grant, then writes as the DC's agent account.

- Two directory operations run inside the DC as the site's agent account (1.6.3, 1.6.5.16), so AD's access rules
  decide who writes which site: `read_plan` (one site's plan, or every site's, with every site's number and the
  order the sites' OUs were made) and `write_plan` (a list of changes: add, set or remove a VLAN, subnet, range or
  address, or set a site's number). A site's agent has full control below its own OU, so the site above writes a
  house's plan (`--site`) and a house never writes its parent's (2.1.9.13).
- `write_plan` writes; it checks nothing of the model. Every rule of 1.10.4.3.2 is checked by fabric first, on the
  plan just read (`fabriclib/ipam`: `check_vlan`, `check_subnet`, `check_range`, `check_address`), so a refusal writes
  nothing. Changes go in order; one AD refuses leaves those before it made (each command writes one to six).
- Convergence (1.6.5.15) still writes the site's other networks (its LAN, and 0.7's DHCP subnets until the upgrade
  moves them) and never changes or removes an entry with the `fabricSubnet` class, nor writes a network of the same
  name or CIDR. The AD site's subnets (1.9.8.5) are the site's networks and its plan's subnets.

### 1.10.4.13.4 The site's number

*Revised 2026-10-23 (1.10.4.32, 2.1.10.34):* `fabricBlock` is on the site's record in `CN=fabric,CN=System`; the
suggestion is the site's order by its record's creation.

`fabricBlock` on the site's OU (class `fabricAddressBlock`), 1-255, unique in the organisation. When a site first
needs one (the upgrade, or `vlan add` with no `--subnet`), fabric gives it the suggestion: its order in the
organisation (the sites by when their OUs were made, the first 1), or the next number no site has. Setup asks it
once and `fabricctl ipam block` changes it (2.1.10.16, 1.10.4.18.1); a site that reaches a command needing a number
before it was asked (setup could not reach the DC) is still given the suggestion, as above.

## 1.10.4.14 The plan at an apply

- Every apply reads the site's plan from its DC before the settings are checked (`load_address_plan`), unless the
  settings still carry `dhcp.subnets` (an install not yet upgraded, 1.10.4.15). Each subnet Kea serves becomes the
  `dhcp.subnets` entry the Kea template has always rendered (`plan_to_dhcp`): its id, name, VLAN, notes, the VLAN's
  access, the gateway as its router, its relay and options, its `dhcp` ranges as pools and its reservations (with
  their names and options). So Kea's configuration, the DNS registration, the reverse zones (2.1.10.7) and the access
  lists (1.10.3.3) come out of the plan exactly as they came out of the settings.
- Each `static` or `infrastructure` address with DNS on becomes an A record of the site's zone, and its PTR follows
  (the generated reverse zones). A name the settings' `dns:` already holds in that zone keeps the settings' record;
  the apply says so.
- The plan read is kept in `<config>/address-plan.json` (root's, 0600, no secret in it). A DC that does not answer
  leaves the apply on that copy, so the site keeps its last rendering, and the apply says when it was read. With no
  copy and DHCP on, the apply stops before it changes anything ("start the samba service").
- Between applies the firewall (DOCKER-USER and UFW's rules for the subnets' clients), the consent plans and the Kea
  tab read the subnets from that copy (`planned_subnets`), so they never lose them because `vars.yaml` no longer
  carries them.
- **What the plan lays over the settings is the render's only** (fixed 2026-10-15, 2.3.10.10.4). The `vars.yaml` an
  apply installs is the settings without it (`deploy/vars_to_save`): no `dhcp.subnets` (unless the settings still
  carry their own), the settings' own `dhcp.options`, `option_defs` and `client_classes`, and only the settings' own

  commands (1.10.4.21.6) edited `vars.yaml` instead of the plan, the next apply's upgrade found those subnets "already
  in the plan" and dropped the edit (a reservation lost), and each plan name became a settings record that would
  outlive its address. The DNS filter's `dhcp:`, `device:` and `vlan:` references read the subnets through

## 1.10.4.15 The upgrade, as built

*Revised 2026-10-23 (1.10.4.37):* read "0.7" as 0.8.0.

- After convergence, at every setup and every apply (`move_subnets_to_plan`), a site whose `vars.yaml` still carries
  `dhcp.subnets` moves them into its plan: each subnet a VLAN with its own VLAN ID (one without gets the lowest free
  ID and is named after the subnet) and that VLAN's subnet, served by DHCP, keeping its Kea id, name, router (now its
  gateway, with a one-address `gateway` range unless a pool holds it), relay, notes, overlap reason, access and
  options; each pool a `dhcp` range; each reservation a `reservation` address with its hostname and options. A
  subnet without a name is named after its network (`net-10-1-20-0-24`). An entry convergence wrote under the same
  name is converted in place. The site is given its number if it has none (1.10.4.13.4).
- Then the record `<config>/ipam-upgrade-<time>.json` (0600): what moved, the VLAN IDs fabric chose, what was already
  in the plan, any key of a subnet the plan does not hold ("not carried"), and the subnets as they were; and
  `vars.yaml` loses `dhcp.subnets`, keeping `dhcp.interfaces` and the global defaults (options, option definitions,
  client classes, lease time, DNS and NTP servers). The apply lists the VLANs fabric chose, to check
  (`fabricctl ipam show`).
- Idempotent (global Rule 12): a subnet the plan already has is left alone, settings without subnets change nothing.
  A move that cannot happen yet (the DC not answering, a read-only DC, settings Kea's checks refuse) is reported and
  left for the next apply, the settings untouched. The apply that moves renders Kea from the settings, the next from
  the plan: the same subnets, ids, pools and reservations, so nothing a running site serves changes.
- The upgrade writes `vars.yaml` without the vars lock: the apply that runs it already holds it when the console or a
  command started it.
- From then on the 0.7 commands that edited subnets in the settings (`fabricctl dhcp add-subnet`, `set-subnet`,
  `remove-subnet`, `reserve`, `unreserve`, an option on a subnet or a reservation, and the Kea tab's same actions)
  refuse with "change them with fabricctl ipam" (since 1.10.4.21.6, add-subnet, set-subnet, remove-subnet, reserve
  and unreserve are its aliases instead); global options and client classes stay in the settings and are
  edited as before, checked with the plan's subnets. `fabricctl dhcp on` turns DHCP on over the plan's subnets.
  Their aliases to the new commands (1.10.4.9) are left for a later phase (1.10.4.17).
- A reservation may now lie inside a pool (a `dhcp` range may hold reservations, 1.10.4.3.2): `normalize_dhcp` no
  longer refuses one, whether the subnets come from the plan or the settings (Kea gives that address only to its
  MAC). A static A record inside a pool is still refused.
- **During setup** (fixed 2026-10-15, 2.3.10.10.4) setup works from `fabric.yaml`, and its deploy has already
  installed a `vars.yaml` carrying the subnets: the move takes them out of both, so neither reads as the settings'
  own afterwards.

- **A VLAN and its subnet are added together.** `vlan add` makes the VLAN, its subnet (the one given, or

- **The rules** (1.10.4.3.2), each refusal naming why and changing nothing: a VLAN ID 1-4094 and a name (one DNS

  naming the first); inside a `dhcp` range only a reservation; a reservation has a MAC, unique among the site's

- **Applying:** a change to this site's plan runs the apply (Kea, DNS and the firewall, as `fabricctl dhcp` does)

## 1.10.4.19 A name set by hand outranks DHCP's

The owner's rule (2.1.10.20): a DNS record set by hand (in fabric's zones, or an address of the plan with DNS on) is
authoritative, and DHCP's dynamic updates never overwrite or replace it, forward or reverse. Two layers keep Kea off
it ([2.3.10.4.8](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#231048-a-name-set-by-hand-outranks-dhcps-how-kea-is-kept-off-it-and-results)):

- **Kea sends nothing for such a reservation.** A reservation is `"ddns": false` in Kea's subnets when the plan
  publishes it (`plan_to_dhcp`) or when any A record set by hand names its address (`normalize_dhcp`; a 0.7
  reservation may also say `ddns: false`). The Kea template puts it in the `SKIP_DDNS` client class and then loads the
  ddns-tuning hook (`libdhcp_ddns_tuning.so`), which makes Kea skip every DNS update for clients in that class: no
  name in `dhcp.<domain>` and no PTR. Kea 3.0 has no way to skip only the reverse update (DDNS settings in a client
  class are refused), so the reservation's names are the site zone's A and PTR alone. Its address is left out of
  the reverse zones Kea registers in (`dhcp_reverse_zones`).
- **BIND refuses Kea's key every name set by hand.** In each reverse zone Kea may write, a `deny "kea-ddns" name
  <name> ANY` rule comes before the zone's grant for every reverse name whose PTR fabric generates from a record set
  by hand (`dns/reverse_by_hand`, rendered by apply and by `dns add-zone` from the same checked settings,
  `deploy/check_rendered`, 2.1.10.21). Kea's key never had any forward zone but
  `dhcp.<domain>`, and the apply's regenerated reverse zones keep Kea's records only where fabric has no PTR
  (2.1.10.7).

Leases and reservations that nobody named by hand register in `dhcp.<domain>` with their PTRs as before.

## 1.10.4.20 A DHCP name left behind is deleted, at every apply and hourly

Decision 2.1.10.22. A device that DHCP registered before (`cam3.dhcp.<domain>`) and whose names are then set by hand
keeps that old name: Kea skips the client from then on (1.10.4.19) and never removes it, and fabric never rewrites
`dhcp.<domain>` (2.1.4.1). Fabric deletes it:

- **What is deleted.** In `dhcp.<domain>`, every A or AAAA record whose address a record set by hand covers (an A or
  AAAA record of fabric's zones: the settings' `dns:` or an address of the plan with DNS on, as the apply's checked
  settings hold them), and the name's DHCID once no address record is left at it. Nothing else: a DHCP name whose
  address no record set by hand names is left alone, and a record set by hand is never touched (the update goes to
  `dhcp.<domain>` only, and Kea's key reaches nothing else, 1.10.4.19).
- **The PTR.** Kea's PTR for that address (and its DHCID there) is already gone at the apply that publishes the name
  set by hand: fabric regenerates the reverse zone with its own PTR and keeps Kea's records only at names it has no
  PTR for (`merge_dynamic_records`, 2.1.10.7); BIND then denies Kea's key that name. The update touches the forward
  zone only.
- **How the names are found.** BIND transfers none of its zones (1.10.3), so fabric reads the zone as BIND serves it:
  its file with the journal applied, by `named-compilezone -j` in BIND's container (read only; `rndc sync` would
  write the file only later, so it is not used).
- **How they are deleted.** One RFC 2136 update per run, signed with Kea's key (`kea-ddns`), sent by `nsupdate` to
  BIND (`host_ip`, `bind_dns_port`); the key is in a 0600 temporary file, never on the command line. The update is one
  message: BIND applies all of it or none. Each removal is audited (`DHCP_NAME_CLEAR`: the name, its type and
  address, `apply`, `timer` or `cli`). A second run finds nothing and sends nothing.
- **When.** (a) At every apply on a running install, once BIND serves the new configuration and zones, from the
  apply's checked settings. (b) Hourly, by `fabric-dhcp-names.timer` (`fabricctl dhcp clean-names --scheduled`, 10
  minutes after boot, then every hour): the cleanup alone, not an apply, which would restart every service whose
  configuration changed. The plan's published names are read from the DC at the apply, so the timer reads the
  addresses set by hand that the last apply kept (`<deploy base>/kea/hand-set.json`, root, 0600). The timer is
  installed while Kea is (`install_kea`); with DHCP's DNS registration off (`dhcp.ddns: false`) the run does
  nothing. By hand: `sudo fabricctl dhcp clean-names`.
- **When BIND refuses.** A refused update (a key BIND no longer knows, BIND not answering) changes nothing and is
  reported: the apply finishes its other steps and then fails with an `Error:` naming the refusal; the timer's run
  fails (`systemctl status fabric-dhcp-names`, the journal); the command exits 1. The hourly run tries again.

## 1.10.4.22 Ping-check and the scan of a subnet, as built

The operator's procedure is 4.10.2.13 (on `dev/0.9.0-dhcp`; Volume 4 follows each ported area, 1.10.4.41).

### 1.10.4.22.1 Ping-check before an offer

- Kea loads its **ping_check hook** (`libdhcp_ping_check.so`, open source since Kea 2.5.4, shipped in ISC's
  `isc-kea-hooks` package that fabric's Kea image already installs; [2.3.10.6](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#23106-ping-check-and-the-scan-built-untested)).
  Before it offers an address Kea parks the offer and pings the address once (100 ms to answer); an answer means
  the address is in use: Kea drops the offer, keeps a **declined** lease for that address (so it is not offered
  again for Kea's probation period, a day by default) and offers the next free one. No answer, or an error (an ICMP
  "unreachable", a full socket buffer), and the offer goes out: ping-check never stops DHCP. An address the same
  client renewed in the last 60 s is not pinged again (`ping-cltt-secs`).
- **On by default**; `dhcp.ping_check: false` in the settings leaves the hook out (not a security relaxation: a
  busy network may prefer offers without the 100 ms wait). Checked by `normalize_dhcp` (true or false only).
- The parameters are the hook's global ones only; none is set per subnet (ISC's own documentation of the
  per-subnet form was reported wrong upstream, [2.3.10.6](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#23106-ping-check-and-the-scan-built-untested)).
- Kea pings from the host (its container is on the host network): a relayed VLAN's device answers only when its
  gateway lets ICMP from fabric through.
- A declined lease shows in the lease list (`state declined`), and a scan shows its address as in use but unrecorded
  (1.10.4.22.3).

### 1.10.4.22.2 The scan: where it runs and what it may do

Decision 2.1.10.26.

- **Where.** Inside Kea's own container (`kea-dhcp4`: host network, and the NET_RAW capability it already has to
  answer DHCP clients), by `docker exec` with two **fixed argument lists**, never a shell string: `fping -a -r 1 -t
  500 -i 10 -g <network>`, then `cat /proc/net/arp` (the host's neighbour table after the pings). fabric-agent keeps
  its sandbox (it may not reach the LAN itself: `IPAddressDeny`), the web container keeps none, and no container
  gains a capability. Kea's image adds Debian's `fping` from 0.8.0; an older image is refused, loudly ("update Kea's
  image").
- **Which subnets.** Only one this site's Kea serves (`scannable_subnets`: the plan's DHCP subnets, or 0.7's
  `dhcp.subnets` before the upgrade), named by its name or its exact network; at most a /22 (1022 addresses).
  Anything else is refused, naming the subnets that may be scanned: another network, a typo, a part of a served
  subnet, another site's (a scan runs at the site that serves the subnet), DHCP off.
  *Revised 2026-10-13 by 2.1.10.28 (1.10.4.27.1):* every subnet of this site's plan may be scanned, DHCP on or off,
  under the same limits, and only where the scan policy allows it.
- **Rate.** One probe every 10 ms, one retry, 500 ms to answer (a /24 in about 3 s, a /22 in about 12 s); one scan at
  a time on the host (a lock in `/run/fabric-ipam-scan/`, root 0700, shared by the command and the console); the
  same subnet at most once a minute (refused, saying how long to wait).
- **Who.** From the console, `dhcp:write` (it sends traffic onto the site's networks and offers to change the plan:
  whoever may change DHCP); listing what may be scanned, `dhcp:read`. From the command line, root (`sudo`).
  *Revised 2026-10-13 by 2.1.10.30 (1.10.4.29):* at a site below the top, its own admins scan only where a site above
  allows local scans (off by default); a site above triggers a scan there through AD.
- **Audited.** `IPAM_SCAN` (who, from where, the subnet, how many answered, how many unrecorded); a refused scan
  probes nothing and audits nothing. The result itself is shown, not kept.

### 1.10.4.22.3 What a scan shows, and recording a find

- Every address that answered: its MAC when ARP saw it (only on a network the host is on), how it answered (`ping`,
  `arp` — a device that drops pings still answers ARP — or both), and what fabric knows of it: **recorded** (the
  gateway, a static, reservation or infrastructure address of the plan, or 0.7's reservations and router; a
  reservation answering from another MAC is noted), a **lease** (an active one), or **in use, unrecorded** (nothing
  recorded and no active lease; an address Kea's ping-check declined is one, noted so).
- For each find in use but unrecorded the admin is **offered** to record it (2.1.10.13: informs and asks, never
  blocks): "make it a reservation?" for the MAC ARP saw, through the reservation unit (`add_address`, kind
  `reservation`), or "record it as a static address?" when no MAC was seen (a routed VLAN). Either takes an optional
  name; the notes say `found by a scan on <date>`; every rule of the plan holds (a refusal is shown and nothing is
  recorded); the change is applied like every plan change (audited `IPAM_ADDRESS_ADD`). Ignoring it changes nothing.

### 1.10.4.22.4 The command and the console

- **`sudo fabricctl ipam scan <subnet> [--no-ask] [--no-apply]`**: prints the result and the command that would
  record each find; on a terminal it then asks, for each, whether to record it (question IDs `ipam.scan_record`,
  `ipam.scan_name`; no is the default); `--no-ask`, or no terminal, only prints. What it recorded is applied unless
  `--no-apply`. `--site` is refused. *Revised 2026-10-13 by 2.1.10.30:* `--site <s>` requests the scan at a site below
  (1.10.4.29.3).
- **The console**: its own page, `/networks/scan` (route `networks_scan_page` / `networks_scan_post`, view
  `ipam_scan`, template `ipam_scan.html`), so the Networks tab (1.10.4.9) links to it or includes it as it is: the
  subnets that may be scanned with a **Scan now** button, then the result table with a "Make it a reservation?" (or
  "Record it as a static address?") form on each find. Agent routes: `GET /v1/ipam/scan` (dhcp:read), `POST
  /v1/ipam/scan` and `POST /v1/ipam/scan/record` (dhcp:write).
- **Wired into the Networks tab** (merged 2026-10-12): the page is under the Networks entry of the console's
  navigation (the tab `networks`, `dhcp:read` shows it); a subnet's view in the Networks tab (1.10.4.21) links
  **Scan this subnet** for this site's subnets that DHCP serves, opening the page with that subnet chosen
  (`/networks/scan?subnet=<network>`); the page links back to the tab. The dev preview shows the page with sample
  subnets.

### 1.10.4.24.2 Who may edit which scope

*Revised 2026-10-23 (1.10.4.34, 2.1.10.36):* who edits a site's set is a grant's `options` there, the domain's at
`all`; `fabric-dhcp-org-editors` and `dhcp:org-options` are not made.

  the site's own agent and any site above it (`--site`); in the console `dhcp:write`.
- **The organisation's set:** AD lets the top site's agent write it (its OU holds it) and the members of
  `fabric-dhcp-org-editors` (`OU=groups,OU=organisation`), whose access entry on the set's entry grants reading and
  writing its three attributes only. The top adds a site's agent to the group (`fabricctl ipam option-editors add
  <site>`, audited `IPAM_OPTION_EDITOR_ADD`; `remove` takes it out). In the console the change needs `dhcp:org-options`
  as well (fabric-agent's route); the admin bundle has it at every site, no operator bundle does. A site the top has not
  added is refused by AD: "the directory refused the change (not permitted for this site)", and the console shows the
  organisation's options read-only there.
- **Where it is written:** this site's DC; at a site whose DC is read-only (`ad_dc_type: rodc`), the writable DC it

  the choice is one unit, `samba/writable_server`, shared with the host's own account (1.6.11.13); it was

  or the poll (`kea-dhcp4 -t`), and a configuration it refuses is never written.

### 1.10.4.24.3 What Kea gets, and where each option comes from

Kea has no organisation or site level: one Kea serves one site. At an apply (`load_address_plan`, through
`plan_to_dhcp`) and at the poll, the site's Kea is rendered with:

- **global options:** fabric's own (DNS 6, NTP 42, domain name 15, search list 119, "provided by fabric"), then the
  organisation's, then the site's, then any the settings still carry (an install whose options have not moved yet,
  1.10.4.24.4), each replacing the one before by option (name and code are the same option);
- **definitions and classes:** the organisation's, then the site's (a site's definition or class of the same name
  replaces the organisation's), then the netboot classes (1.10.4.25);
- **each subnet:** fabric's router (the gateway) and its own options; **each reservation:** its options.

Kea then picks, for a client, the most specific (Kea 3.0's order, [2.3.10.5](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#23105-dhcp-options-in-the-plan-netboot-and-the-plan-poll-built-untested)):
the reservation's, then the subnet's, then a client class's, then the global ones. So a class's option is overridden
by the same option set on the subnet: 1.10.4.6.1's order (organisation, site, subnet, class, address) is read with the
class below the subnet, as Kea applies it.

**The provenance** (`ipam/options/effective_options`, one function the Networks tab and the options page both use;
agent route `GET /v1/ipam/options/<site>/<target>`): for a subnet or an address, every option it ends up with: its
code and standard name, its value, its source (`fabric`, `organisation`, `site`, `settings`, `subnet <name>`,
`address <ip>`), the sources it overrides, and the "provided by fabric" marker (with "overridden" when an admin's
option replaced fabric's); then each class's options as conditional rows ("clients in class X"), each marked when the
subnet or address overrides it.

### 1.10.4.24.4 The upgrade: the settings' options into the site's set

`ipam/options/move_options_to_plan`, after `move_subnets_to_plan` at every apply: once a site's subnets live in the
plan (`plan_holds_subnets`) and `vars.yaml` still carries `dhcp.options`, `dhcp.option_defs` or `dhcp.client_classes`,
they are written into the site's set (an option, definition or class the set already holds keeps the set's: "not
carried"), recorded in `<config>/ipam-options-upgrade-<time>.json` (0600) and removed from `vars.yaml`. A DC not
answering leaves them for the next apply. Until moved they are served above the site's set; once moved, nothing in
`vars.yaml` overrides the plan (2.1.10.23), and `fabricctl dhcp option` (without a subnet or reservation),
`fabricctl dhcp class` and the Kea tab's same forms refuse: "the site's DHCP options and client classes are in the
address plan since 0.8.0: change them with fabricctl ipam option and ipam class".
That refusal comes first (fixed 2026-10-15, 2.3.10.10.4): before, an option for a class the settings did not hold
(`dhcp option set … --class C`, the class being the plan's) was refused with "no client class 'C'", which named no
way forward.

## 1.10.4.25 Netboot presets, as built

Decision 2.1.10.25, built 2026-10-12 on `dev/0.8.0-options` (tests written, not run). Points at a boot server the
owner runs; fabric serves no boot files (2.1.10.15).

```
fabricctl ipam netboot show <vlan|subnet|ip>
fabricctl ipam netboot on <vlan|subnet|ip> --server ADDRESS|NAME [--bios FILE] [--uefi FILE] [--arm64 FILE]
                         [--ipxe URL] [--http URL]
fabricctl ipam netboot off <vlan|subnet|ip>
```

- **The preset** (`ipam/options/check_netboot`): a boot server (an IPv4 address, or a name: one DNS name, which Kea
  sends as option 66 and the `sname` field only, as Kea's `next-server` takes an address; some firmware reads only
  the address, which `show` says), and at least one of: PXE boot files by architecture (`--bios`, `--uefi`, `--arm64`:
  a file name or path, at most 127 characters), an iPXE script's URL (`--ipxe`, `http://` or `https://`), a UEFI HTTP
  boot URL (`--http`, `http://` or `https://`). `on` again replaces it; `off` removes it.
- **Where:** a VLAN (each of its subnets), a subnet, or an address that is a reservation (a static address gets no
  DHCP answer: refused, saying so).
- **What Kea gets** (`ipam/options/netboot_classes`), for a subnet with id `n`, classes named `fabric-nb-s<n>-<kind>`,
  each `only-in-additional-list` and named in the subnet's `evaluate-additional-classes`; for a reservation, the marker
  class `fabric-nb-a-<address>` (no test; the reservation lists it in its `client-classes`) and classes
  `fabric-nb-a-<address>-<kind>` testing `member('KNOWN') and member('fabric-nb-a-<address>')`, so they are evaluated after
  the host lookup. The kinds, each excluding the ones after it in this list so one client matches one:

  | Kind | Test (besides the scope) | Gets |
  |---|---|---|
  | `ipxe` | `substring(option[77].hex,0,4) == 'iPXE'` | `boot-file-name` (the field and option 67) = the script URL |
  | `http` | `substring(option[60].hex,0,10) == 'HTTPClient'` | the URL as the field and option 67; option 60 `HTTPClient` |
  | `bios` | `option[93].hex == 0x0000` | the BIOS file, `next-server`, option 66 |
  | `uefi` | `option[93].hex == 0x0007 or option[93].hex == 0x0009` | the UEFI x64 file, `next-server`, option 66 |
  | `arm64` | `option[93].hex == 0x000b` | the arm64 file, `next-server`, option 66 |

  A kind without its file or URL is left out. A preset on an address replaces its subnet's for that client (its
  classes are evaluated in the normal pass, which outranks the subnet's additional classes in Kea).
- **Provenance:** the preset's options show as conditional rows "netboot (<kind>)" in the effective options.
- **Console:** the options page's netboot form on each subnet and reservation (1.10.4.24.6).

## 1.10.4.26 The 30-second plan poll

Decision 2.1.10.24, built 2026-10-12 on `dev/0.8.0-options` (tests written, not run). It is how an edit made at
another site (the top editing a house, or a house editing the organisation's options) reaches this site's Kea
(1.10.4.8), with no apply.

- **The units:** `fabric-plan-watch.timer` (`OnBootSec=30s`, `OnUnitActiveSec=30s`, `AccuracySec=1s`) starts
  `fabric-plan-watch.service` (oneshot): `fabricctl ipam watch --scheduled` (`ipam/poll_plan`). Installed by the
  apply while Kea is (`install_timers`), removed when Kea is turned off, and by uninstall.
- **Each run:** (1) Kea not installed, or the subnets still in `vars.yaml`: nothing. (2) The DC's
  `highestCommittedUSN` (`samba/read_usn`: `src/containers/samba/read_usn.py` in the DC's container, an anonymous read
  of the root DSE on loopback: no secret). Unchanged since the last run (`<config>/plan-watch.json`, 0600): done.
  (3) Changed: fabric's secrets are loaded and the site's plan and option sets read; a digest of what Kea is rendered
  from (`plan_to_dhcp`'s subnets, global options, definitions and classes) is compared with the last rendering's.
  Equal (another change in the domain): the USN is kept, done. (4) Different: under the settings' lock (taken without
  waiting: an apply in progress reads the plan itself, so the run skips and the next one tries again), the settings are
  rendered and checked as an apply checks them (`render_vars`, `load_address_plan`, `check_settings`) and Kea's
  configuration written by `deploy_kea` (Kea's own check first; refused: nothing written, the run fails); when it
  changed, Kea is restarted (`start_unit`, health-checked). When the set of served subnets changed, the host firewall
  is brought in line (`refresh_firewall`). (5) When the published names or the subnets changed, DNS waits for the next
  apply: the run says so and `fabricctl ipam watch` shows "an apply is needed" until an apply runs. What DNS was last
  rendered from (`<config>/plan-dns.json`) is written only once BIND took it: at the end of an apply that went
  through (after the restarts, or after a first install's deploy), and by a zone change once BIND serves the new zone
  list (`publish_zone_list`); an apply that fails part-way leaves it as it was, so the poll keeps saying an apply is
  needed (2.3.10.5.6). *Revised 2026-10-13 by 2.1.10.29:* the poll keeps reporting, and **Sync now** (1.10.4.28)
  publishes BIND's records on demand. (6) The USN and the
  digest are kept; the run is audited (`IPAM_WATCH_RENDER`, what changed). A failure (the DC, OpenBao locked, Kea's
  check) fails the unit (`systemctl status fabric-plan-watch`) and keeps the last USN, so the next run tries again.
- *Revised 2026-10-15 by 2.1.10.31:* in (3), a plan with **no subnet with a DHCP range** renders nothing: the run
  reports `no subnet` and why (define the subnet first, then its DHCP range: best practice), leaves Kea as it is and
  keeps the USN; it is not a failure.
- **`fabricctl ipam watch`** (by hand, as root) runs the same once and prints what it did; with `--scheduled` it is
  quiet when nothing changed.
- After an apply the next run renders the same file Kea already has (`deploy_kea` finds no change), so Kea is not
  restarted twice.

### 1.10.4.28.1 What it does

1. **Refused**, changing nothing, while an apply holds the settings' lock ("an apply is running: it reads the plan

2. Under that lock (taken without waiting), **the plan poll at once**, whatever the DC's USN says (`poll_plan` with

3. When the poll reports DNS pending (the plan's published names or its subnets differ from what BIND last took),

   DNS filter's resolver re-rendered when the zone list changed. `plan-dns.json` is written once BIND serves the new
   records, so the poll no longer says an apply is needed.
4. **Never a full apply**, and no service restarted but Kea (BIND is reconfigured and its zones reloaded, as `dns
   add-zone` does). Audited `IPAM_SYNC` (the person, the source, what the poll found, whether Kea restarted, the
   firewall, the zones published). A failure part-way says what was done (Kea in line, BIND's records not) and leaves

## 1.10.4.29 Scans from the top down

*Replaced 2026-10-23 (1.10.4.36, 2.1.10.38):* the top-down rule and the local-scan setting are not ported; the
request through AD, its limits and its answer are, checked again at the serving site.

Decision 2.1.10.30, from the owner's answer of 2026-10-13 ("they should only be able to scan their own subnets though
others may trigger that sites scans (specifically top down)"), in a layered IT model: central IT at the top manages
every site, a site's local admins do little by default. It revises 2.1.10.28: the organisation-wide scan policy and its
enforced switch (1.10.4.27.2 to 1.10.4.27.5) are gone. Built 2026-10-13 on `dev/0.8.0-scantrigger`, tests written, not
run ([2.3.10.9](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#23109-scans-from-the-top-down-built-tests-written-not-run)).
The operator's procedure is 4.10.2.20 (on `dev/0.9.0-dhcp`; Volume 4 follows each ported area, 1.10.4.41).

### 1.10.4.29.1 The rule

- **A scan always runs at the site that owns the subnet**, on that site's own Kea, only on a subnet of that site's
  plan, under 1.10.4.22.2's and 1.10.4.27.1's limits unchanged (at most a /22, one probe every 10 ms, one scan at a
  time on the host, the same subnet once a minute, in Kea's container, audited). No site ever probes another site's
  network.
- **A site above a branch may trigger a scan there.** "Above" is the Networks tab's own rule (`ipam/visible_sites`,
  `common/site_scope`, 1.10.4.21.2): the sites that joined below this install, at any depth its registry holds; so the
  top may trigger at every site, a middle site at the sites below it. The request is written into AD under the
  branch's plan; the branch's 30-second plan poll runs it and writes the result back on the request (1.10.4.29.3).
- **A sibling, or a site below, can never trigger.** The agent refuses before AD is asked ("not this site or one below
  it"), and AD refuses anyway: a site's agent has write access only below its own OU (1.6.3.6, `ensure_site_acl`:
  full control, inherited, of its own OU), so it has none in a sibling's or its parent's OU. The branch's own agent
  is denied creating a request in its own plan (1.10.4.29.2), and the branch's poll runs only a request whose creator
  in AD is the agent of a site above it.
- **Whether a branch's own admins may scan its subnets locally** (the console's Scan now, `fabricctl ipam scan` at the
  branch) is set by the sites above it, stored on the branch's OU where the branch's own agent and OU admins are
  denied writing it (1.10.4.29.4). **Default: off**, so central IT scans and the local admins do not. A scan triggered
  from above runs whatever it says.
- **The top site's own admins may always scan the top's subnets**: no site is above it to decide.

### 1.10.4.29.2 Kept in AD: the schema and who may write it

Schema (1.10.4.13.1's, 1.10.4.24.1's and 1.10.4.27.2's tables, continued; additive). The numbers follow the highest
taken: 35 and 36 and class 13 by 2.1.10.28 (dropped by this decision before any release, never reused), 37, 38 and
class 14 by the 0.9 branch. The retired numbers are listed in `ensure_schema.RETIRED`, and
`tests/samba/ensure_schema_test.py` fails when any live attribute or class takes one:

| Attribute (arc `.1.n`) | n | Syntax | Holds |
|---|---|---|---|
| `fabricLocalScan` | 39 | boolean, single | on a site's OU: its own admins may start scans (none: no) |
| `fabricLocalScanBy` | 40 | string, single | who set it: `<site> <person> <date and time>` |
| `fabricScanRequestedBy` | 41 | string, single | on a request: the site that asked |
| `fabricScanActor` | 42 | string, single | the person who asked |
| `fabricScanState` | 43 | string, single | `pending`, `done`, `refused` or `expired` |
| `fabricScanResult` | 44 | string, single | the result as JSON, at most 48 000 characters; or why it was refused |
| `fabricScanDoneAt` | 45 | IA5, single | when the branch answered |

| Class (arc `.2.n`) | n | Kind | Must / may |
|---|---|---|---|
| `fabricLocalScanSet` | 15 | auxiliary, on a site's OU | — / `fabricLocalScan`, `fabricLocalScanBy` |
| `fabricScanRequest` | 16 | structural, below a subnet's `fabricNetwork` entry | `fabricCidr`, `fabricScanRequestedBy` / `fabricScanActor`, `fabricScanState`, `fabricScanResult`, `fabricScanDoneAt`, `description` |

Access (`ensure_site_acl`, at every site's convergence; nothing at the root, which has no site above it):

- On the site's own OU, **explicit deny entries, not inherited**: writing `fabricLocalScan` and `fabricLocalScanBy`,
  for the site's `fabric-agent-<site>` and `<site>-ou-admins`. An explicit deny is evaluated before the full control
  they inherit on the OU, and neither holds the right to change permissions or the owner (`FULL` leaves out WD and WO,
  2.1.6.20), so they cannot lift it. The sites above write it through the full control they inherit from their own OU.
  Not inherited, so the branch still sets it on the sites below it.
- On the site's `OU=networks`, a **deny of creating a `fabricScanRequest`**, inherited by its subnets' entries, for
  the same two. The branch may still write a request's state and result and delete it (its full control), which is
  how its poll answers and clears them.
- A request's creator is its owner in AD (the creating account; an agent is no administrator), which nobody below can
  change. The branch's poll reads it (`read_scan_requests`: the security descriptor's owner, with the `sd_flags`
  control) and runs a request only when the owner is `fabric-agent-<s>` and `<s>` is the request's
  `fabricScanRequestedBy` and a site above the branch in AD (`paths.ancestors`).

AD could express "writable by the parent, not by the branch" cleanly, so the setting is kept at the branch's OU, the
first choice of the owner's brief, not on the parent's side.

`read_plan` returns `local_scan`: `{<site>: {"allowed" (bool), "set_by" (text), "top" (bool), "above" (the sites
above it, nearest first)}}` for every site;
`write_plan` takes a `local_scan` change (the site, `allowed`, `by`); the plan copy every read keeps carries it
(1.10.4.14). Two directory operations of their own: `read_scan_requests` (a site's requests, each with its subnet,
network, who asked and when, `whenCreated`, its state, result and owner check) and `write_scan_request` (`add` by the
asking site, `finish` and `remove` by the branch).

### 1.10.4.29.3 A scan requested from above

1. **Asked** (`ipam/scancontrol/request_scan`): at a site above, naming the branch and one subnet of the branch's plan
   (its name or exact network, at most a /22). Refused, writing nothing: the branch not below this site (or this site
   itself: "a scan of this site's subnet runs here: Scan now"), a subnet not in the branch's plan, a request for that
   subnet still pending, four requests pending at the branch. Written as `CN=scan-<time>-<random>` below the subnet's
   entry at a writable DC (`samba/writable_server`), state `pending`; audited at the asking site
   (`IPAM_SCAN_REQUEST`: the person, `from=`, the branch, the subnet, the request).
2. **Picked up** by the branch's plan poll (1.10.4.26, `ipam/scancontrol/run_scan_requests`): a new request changes the
   DC's USN, so the next run (within 30 s) reads the branch's requests. Then, for each:
   - a request older than **24 hours** (by its `whenCreated`, which nobody writes) is **removed**, whatever its state;
   - one whose creator is not the agent of a site above the branch is answered `refused` ("not requested by a site above
     <branch>") and audited `IPAM_SCAN_REQUEST_REFUSED`; it is never run;
   - one still `pending` an hour after it was made is answered `expired`, not run (a branch that was down does not fire
     old requests);
   - otherwise it is **run**: `scan_subnet` at the branch, as `<person>@<site>`, source `request`, with the local-scan
     setting not asked (a scan from above always runs), under every limit; audited at the branch (`IPAM_SCAN` with
     `requested_by=` and `request=`). Another scan running, or the same subnet within the minute, leaves it `pending`
     for the next run; any other refusal (no Kea at the branch, the subnet gone from the plan, an old Kea image) is
     answered `refused` with why.
   - At most one request is run per poll run (a /22 takes about 12 s); the poll keeps a "requests pending" mark, so the
     next run reads them again even when the USN did not move.
3. **Answered** (`write_scan_request` `finish`): state `done`, the result as JSON (`ipam/scancontrol/bound_result`:
   the subnet, when, how many probed, answering and unrecorded, and the answering rows, the unrecorded first; rows that
   do not fit in **48 000 characters** are left out and counted as `truncated`), and when. The result lives in AD with
   the plan, replicated like it, readable by the domain's authenticated accounts as the plan's addresses are.
4. **Shown** at the asking site: the Networks tab, on the branch, lists the branch's requests with their state, and a
   done one's result (`ipam/scancontrol/list_scan_requests`); `fabricctl ipam scan <subnet> --site <branch>` waits for
   the answer (up to 120 s, `--no-wait` to return at once) and `fabricctl ipam scan-requests --site <branch>` lists
   them.

### 1.10.4.29.4 Local scans, set from above

- `ipam/scancontrol/local_scan_state`: at the top site, **allowed** ("the top site"); elsewhere allowed only when a site
  above set `fabricLocalScan` TRUE on the branch's OU; unset or FALSE: **off** (the default). When off, a local scan is
  refused before anything is probed, saying "local scans at <site> are off: the sites above it decide (set by …, or
  not set: off by default); a site above may scan here: Scan at <site> on its Networks tab, or fabricctl ipam scan
  <subnet> --site <site>". Nothing is probed and nothing audited.
- Read as for every scan (`read_local_scan`): from this site's DC as its agent; when the DC does not answer, from the
  plan copy last kept, saying so; with neither, refused ("cannot be read": secure by default).
- **Set** (`set_local_scan`) only from a site above, for a site below (the Networks tab's scope, and never this site:
  "whether <site>'s admins may scan is set by the sites above it"); written at a writable DC with the setter
  (`fabricLocalScanBy`: this site, the person, when) and audited `IPAM_LOCAL_SCAN_SET`. Nothing is applied: the next
  scan reads it. AD refuses the branch's own agent (1.10.4.29.2) even if a request got past fabric-agent.
- **Who:** `dhcp:write` at the console (the permission a scan needs, held at the site above); root at the command line.
- **The highest site above wins** (*revised 2026-10-13*, 2.1.10.30's revision): the setting in force is the one the
  highest ancestor that set it wrote (the top over a region over the branch's parent). A lower site above sets it only
  where no higher one has, or changes its own value; changing a value set from higher up is refused: "local scans at
  <branch> were set by <site>, above <this site>: only <site> or a site above it may change them". The ranking is the
  branch's ancestors in AD, nearest first (`local_scan.above`, read with the plan); the setter is the first word of
  `fabricLocalScanBy`. fabric-agent enforces it (`set_local_scan`); AD cannot (an access entry cannot depend on who
  wrote a value) and only stops the branch itself.
- **Clearing it** (*revised 2026-10-13*, 2.1.10.30's second revision): the site that set the value, or any site above
  that one, may remove it (`local-scan clear`, the card's **Clear** button). Both attributes are removed and the branch
  is back to the default, **off**: only one value is kept, so no lower site's earlier value returns. A lower site above
  may then set it again. Refused for anyone lower than the setter (naming it) and where nothing is set ("nothing to
  clear"). Audited `IPAM_LOCAL_SCAN_CLEAR`, with the value removed.

### 1.10.4.29.5 The command, the console and the agent's routes

```
fabricctl ipam scan <subnet>                         a local scan (this site's subnet, where local scans are allowed)
fabricctl ipam scan <subnet> --site S [--no-wait]    a scan at S, a site below: requested, then its answer awaited
fabricctl ipam scan-requests [--site S]              S's requests and their answers (this site's without --site)
fabricctl ipam local-scan [show] [--site S]          whether S's (this site's) own admins may scan, and who set it
fabricctl ipam local-scan allow|deny --site S        set it for S, a site below
fabricctl ipam local-scan clear --site S             remove it (back to off): the site that set it or one above that
```

Routing only (`ipam/scancontrol/run_scan_command`, called by `run_ipam_command`). `fabricctl ipam scan-policy` is gone.

- **The Networks tab, on a site below:** a **Scans at <site>** card: whether its admins may scan locally and who set it,
  the form to allow or deny it (`dhcp:write`, `POST /networks/scan/local`), a **Clear** button when a value is set
  (`allowed=clear`, naming who may clear it), and its requests with their state and, for
  a done one, what answered (unrecorded first); on a subnet's view, **Scan at <site>** (`POST /networks/scan/request`),

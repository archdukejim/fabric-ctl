## 1.10.4.1 Status

Designed 2026-10-12 from the owner's answers of 2026-10-11 (decisions 2.1.10.8 to 2.1.10.15; the proposal and its
impact assessment: [2.3.10.3](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#23103-proposal-080-an-address-manager-for-vlan-segmented-sites)).
To build in 0.8.0, which carries DHCP alone (2.1.1.51), all of it in one release (2.1.10.10). It revises how 1.10.2
keeps subnets: from 0.8.0 the plan lives in AD and `vars.yaml` keeps only what is the host's own (1.10.4.10).

## 1.10.4.2 What it is

fabric's DHCP becomes an address manager (IPAM) for VLAN-segmented sites: every site's VLANs and their subnets, the
ranges inside each, and **every address** — static ones, reservations and live leases — shown together, in one
plan for the organisation, edited by each house and by the owner above them all (2.1.9.19). The site's gateway
(at the owner's houses a UniFi gateway) routes between VLANs, enforces the policy between them and relays each
VLAN's DHCP to fabric (2.1.10.8); fabric serves the addresses, names them in DNS and tracks them.

## 1.10.4.3 The model

### 1.10.4.3.1 The objects

Each object belongs to its site; the owner's roles at the top may edit any site's (2.1.9.5, 2.1.9.13).

| Object | Holds |
|---|---|
| **Block** | the site's number: its second octet in the suggested plan, `10.<site>.0.0/16` (2.1.10.12); unique in the organisation, chosen at install or join |
| **VLAN** | ID (1-4094, unique in the site), name (unique in the site), purpose and notes, `access` (`full` or `guest`, 1.10.3.3) |
| **Subnet** | one per VLAN by default (a VLAN without one is a record only); CIDR, gateway (the router's address in it), served by DHCP or not, options (1.10.4.6) |
| **Range** | inside a subnet, never overlapping another of its ranges: `gateway`, `static` (set by hand), `dhcp` (Kea's pool), `reserved` (kept free) |
| **Address** | one IP: kind (`static`, `reservation`, `infrastructure`), name, MAC, owner, notes, options (a reservation's), DNS (an A and a PTR in fabric's zone, or none) |
| **Lease** | live from Kea, never stored: shown with the address it holds; its name in `dhcp.<domain>` as today (1.10.3.4) |

### 1.10.4.3.2 The rules

- One address, one claim: a static address, a reservation or the gateway; a second claim is refused, naming the
  first.
- An address inside a `dhcp` range may only be a reservation; a `static` address lies in a `static` range, or is
  warned about (never refused: the admin may know better).
- A subnet that overlaps another anywhere in the organisation is refused, as today (1.10.2.6); `--allow-overlap`
  allows it where networks are never routed together (NAT, separate paths).
- Every refusal says why and changes nothing (Rule 9).

### 1.10.4.3.3 What fabric suggests

Suggestions only, never enforced (2.1.10.9, 2.1.10.12): a site's admins and the owner may enter any subnet, split
and routing, NAT or another path included.

- A new VLAN `n` at site `s` is offered `10.<s>.<n>.0/24` (VLAN 10 management: `10.<s>.10.0/24`; VLAN 255 storage:
  `10.<s>.255.0/24`).
- Inside a /24: gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254`, editable per VLAN.

## 1.10.4.4 Where the plan is kept

In AD (2.1.10.11): each site's VLANs, subnets, ranges, static addresses and options are objects in its own
`OU=networks` (1.10.2.8 already keeps the subnets there), in new classes of fabric's OID arc added through the
schema path 0.7.0 fixed (1.6.5.24). Every DC holds the whole plan. Each site's `vars.yaml` keeps only what is the
host's own: the interfaces Kea listens on (`dhcp.interfaces`) and the global defaults. An apply reads the plan from
AD; a site whose DC does not answer keeps its last rendering.

## 1.10.4.5 How a VLAN is served

- **Relay:** each VLAN's gateway relays DHCP to fabric's `host_ip` (2.1.10.8); Kea picks the subnet by the relay's
  address, the gateway inside it (1.10.3.2). fabric opens 67/udp to the gateways' addresses (the `ports` consent
  group, 1.10.3.5). The gateway's steps (UniFi: each network's DHCP mode "relay", server `host_ip`) are in 4.10.
- **What a VLAN's clients get:** the gateway as router, fabric as DNS and NTP (2.1.10.5), the domain and its search
  list; `access: guest` VLANs only DNS and NTP (1.10.3.3). fabric's own names stay on `host_ip`, reached through
  the gateway.
- **DNS:** a static address with DNS on gets an A in the site's zone and a PTR in its reverse zone (one per /24, so
  one per VLAN); leases register in `dhcp.<domain>` with their PTRs as today (2.1.10.7).
- **802.1X:** a role's VLAN (1.11) names a VLAN of the plan, so the console shows "VLAN 20 (iot, 10.1.20.0/24)".
- **The DNS filter's groups** by VLAN keep working (1.10.3.7).

## 1.10.4.6 DHCP options and netboot

### 1.10.4.6.1 Options at every level

Options can be set on the organisation (every site), a site, a VLAN's subnet, a client class and an address (a
reservation); the most specific wins, as in Kea (2.1.10.14). Any option by name or code, with a custom definition
for a code Kea has no name for. Every option appears under its standard name with its code — option 67 "boot file
name", 66 "TFTP server name", 6 "DNS servers", 42 "NTP servers" — never only a number. Almost all are unset. For a
subnet or an address, the console shows the options it ends up with and where each came from.

### 1.10.4.6.2 Options fabric provides

The options fabric sets because it runs the service — DNS (6), NTP (42), the domain name (15) and the search list
(119) — carry a **"provided by fabric"** marker: fabric keeps their values with the stack. An admin may override
one; the marker then says it is overridden.

### 1.10.4.6.3 Netboot presets

A VLAN or an address can switch on a preset, each a set of client classes and options the admin can edit, pointing
at a boot server the owner runs (an address, or a name in fabric's DNS); fabric serves no boot files (2.1.10.15,
1.10.2.7):

- **PXE, BIOS and UEFI:** classes on the client's architecture (option 93: 0 BIOS, 7 and 9 x64 UEFI, 11 arm64 UEFI),
  each with its own boot file name (67), next server and TFTP server name (66);
- **iPXE chain-load:** a client already running iPXE (user class `iPXE`, option 77) gets the iPXE script's URL
  instead of the iPXE binary, so it does not loop;
- **UEFI HTTP boot:** vendor class `HTTPClient` gets an `http://` boot URL, with option 60 echoed back.

## 1.10.4.7 Addresses in use that nobody recorded

Kea pings an address before handing it out and skips one that answers (Kea 3.0's ping-check hook); an admin may also
**scan a subnet on request** (ping and ARP from fabric's host; a routed VLAN answers what its gateway lets through)
(2.1.10.13). Neither ever blocks: an address found in use but unrecorded is shown as "in use, unrecorded" (with the
MAC when ARP saw it), and the console offers to make it a reservation for that device, or a static record; the admin
may also ignore it or register something else there.

## 1.10.4.8 Editing a house from the top

An edit from the top's console is written on the top's DC to the house's `OU=networks`; replication carries it to the
house (1.9.8.5). Each site's fabric polls its own DC's highest USN every 30 s; when its OU changed it renders Kea and
reloads it through its control socket (2.1.10.6), with its DNS records and the access lists. A house cut off from the
top keeps serving from its own copy, and its own edits merge when the link is back (AD keeps the last writer per
attribute; the console names a conflict object if one appears, 1.9.8). A site with a read-only DC (1.9.8.3) is
edited from a writable DC above it.

## 1.10.4.9 The console and the command line

- **A Networks tab** replaces the Kea tab's subnet parts: the sites (the top sees every house), a site's VLANs, a
  subnet's map (its ranges as a bar, used and free) and its address table (static, reservation, lease, unrecorded,
  free; search by IP, name or MAC; export as CSV); the options with their sources and markers. Reading needs
  `dhcp:read`, changing `dhcp:write`; a house's admin sees only their house.
- **`fabricctl ipam`:** `vlan add|set|remove`, `range add|remove`, `address add|set|remove`, `option set|remove`,
  `netboot on|off`, `scan <subnet>`, `show [<site>]`, `find <ip|name|mac>`, `export`; `--site` for the top. Every
  entry point gets positive and negative tests and joins the inventory (3.1.2.5).
- Today's `fabricctl dhcp add-subnet` and the other subnet commands become aliases of the new ones for one release,
  then go.

## 1.10.4.10 The upgrade from 0.7

At the upgrade, each site's `dhcp.subnets` (with their pools, reservations and options) moves into its plan once,
recorded, and `vars.yaml` stops carrying them; each subnet's VLAN becomes a VLAN object (one without a VLAN gets the
next free ID, named after the subnet, and is listed for the admin to check). The site's number is asked once (the
suggestion: its order in the organisation). Nothing a running site serves changes.

## 1.10.4.11 Tests

- Unit: the model's rules (overlaps, one claim per address, ranges inside their subnet, the suggestions).
- Real containers: Kea rendered from the plan answering a relayed request on each VLAN (a relay container on each of
  three Docker networks); DNS and PTR for a static address; a lease shown beside the plan; a second claim refused;
  options set at a subnet overridden at an address; a BIOS, a UEFI and an iPXE client each given its own boot file;
  an option with a code Kea does not know, defined and sent; ping-check skipping an address that answers.
- Two sites (the `site_join` suite's setup): an edit at the top reaches the site's Kea.
- The Incus test bed (2.1.1.50): a routed lab with a relaying gateway and real clients on two VLANs, the release's
  gate.

## 1.10.4.12 Not in scope

fabric does not route, firewall between VLANs or configure switches and gateways (2.1.10.8); scans run only on
request and never block (2.1.10.13); fabric serves no boot files (2.1.10.15).

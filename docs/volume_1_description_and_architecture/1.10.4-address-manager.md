## 1.10.4.2 What it is

fabric's DHCP becomes an address manager (IPAM) for VLAN-segmented sites: every site's VLANs and their subnets, the
ranges inside each, and **every address** — static ones, reservations and live leases — shown together, in one
plan for the organisation, edited by each house and by the owner above them all (2.1.9.19). The site's gateway
(at the owner's houses a UniFi gateway) routes between VLANs, enforces the policy between them and relays each
VLAN's DHCP to fabric (2.1.10.8); fabric serves the addresses, names them in DNS and tracks them.

## 1.10.4.3 The model

### 1.10.4.3.1 The objects

Each object belongs to its site; the owner's roles at the top may edit any site's (2.1.9.5, 2.1.9.13).

| Object | Holds |
|---|---|
| **Block** | the site's number: its second octet in the suggested plan, `10.<site>.0.0/16` (2.1.10.12); unique in the organisation, chosen at install or join |
| **VLAN** | ID (1-4094, unique in the site), name (unique in the site), purpose and notes, `access` (`full` or `guest`, 1.10.3.3) |
| **Subnet** | one per VLAN by default, more allowed (2.1.10.18; a VLAN without one is a record only); CIDR, gateway (the router's address in it), served by DHCP or not, options (1.10.4.6) |
| **Range** | inside a subnet, never overlapping another of its ranges: `gateway`, `static` (set by hand), `dhcp` (Kea's pool), `reserved` (kept free) |
| **Address** | one IP: kind (`static`, `reservation`, `infrastructure`), name, MAC, owner, notes, options (a reservation's), DNS (an A and a PTR in fabric's zone, or none) |
| **Lease** | live from Kea, never stored: shown with the address it holds; its name in `dhcp.<domain>` as today (1.10.3.4) |

### 1.10.4.3.2 The rules

- One address, one claim: a static address, a reservation or the gateway; a second claim is refused, naming the
  first.
- An address inside a `dhcp` range may only be a reservation; a `static` address lies in a `static` range, or is
  warned about (never refused: the admin may know better).
- A subnet that overlaps another anywhere in the organisation is refused, as today (1.10.2.6); `--allow-overlap`
  allows it where networks are never routed together (NAT, separate paths).
- Every refusal says why and changes nothing (Rule 9).

### 1.10.4.3.3 What fabric suggests

Suggestions only, never enforced (2.1.10.9, 2.1.10.12): a site's admins and the owner may enter any subnet, split
and routing, NAT or another path included.

- A new VLAN `n` at site `s` is offered `10.<s>.<n>.0/24` (VLAN 10 management: `10.<s>.10.0/24`; VLAN 255 storage:
  `10.<s>.255.0/24`).
- Inside a /24: gateway `.1`, static `.2-.99`, DHCP `.100-.249`, reserved `.250-.254`, editable per VLAN.

## 1.10.4.4 Where the plan is kept

In AD (2.1.10.11): each site's VLANs, subnets, ranges, static addresses and options are objects in its own
`OU=networks` (1.10.2.8 already keeps the subnets there), in new classes of fabric's OID arc added through the
schema path 0.7.0 fixed (1.6.5.24). Every DC holds the whole plan. Each site's `vars.yaml` keeps only what is the
host's own: the interfaces Kea listens on (`dhcp.interfaces`) and the global defaults. An apply reads the plan from
AD; a site whose DC does not answer keeps its last rendering.

## 1.10.4.5 How a VLAN is served

- **Relay:** each VLAN's gateway relays DHCP to fabric's `host_ip` (2.1.10.8); Kea picks the subnet by the relay's
  address, the gateway inside it (1.10.3.2). fabric opens 67/udp to the gateways' addresses (the `ports` consent
  group, 1.10.3.5). The gateway's steps (UniFi: each network's DHCP mode "relay", server `host_ip`) are in 4.10.
- **What a VLAN's clients get:** the gateway as router, fabric as DNS and NTP (2.1.10.5), the domain and its search
  list; `access: guest` VLANs only DNS and NTP (1.10.3.3). fabric's own names stay on `host_ip`, reached through
  the gateway.
- **DNS:** a static address with DNS on gets an A in the site's zone and a PTR in its reverse zone (one per /24, so
  one per VLAN); leases register in `dhcp.<domain>` with their PTRs as today (2.1.10.7). A reservation with DNS on
  gets its A and PTR in the site's zone and nothing from DHCP: a name set by hand outranks DHCP's (2.1.10.17,
  2.1.10.20, 1.10.4.19).
- **802.1X:** a role's VLAN (1.11) names a VLAN of the plan, so the console shows "VLAN 20 (iot, 10.1.20.0/24)"
  (built in 0.9: 1.11.1.8); a reservation may name a device role and is then admitted by MAB on its VLAN (1.11.1.7).
- **The DNS filter's groups** by VLAN keep working (1.10.3.7).

## 1.10.4.6 DHCP options and netboot

### 1.10.4.6.1 Options at every level

Options can be set on the organisation (every site), a site, a VLAN's subnet, a client class and an address (a
reservation); the most specific wins, as in Kea (2.1.10.14). Any option by name or code, with a custom definition
for a code Kea has no name for. Every option appears under its standard name with its code — option 67 "boot file
name", 66 "TFTP server name", 6 "DNS servers", 42 "NTP servers" — never only a number. Almost all are unset. For a
subnet or an address, the console shows the options it ends up with and where each came from.

### 1.10.4.6.2 Options fabric provides

The options fabric sets because it runs the service — DNS (6), NTP (42), the domain name (15) and the search list
(119) — carry a **"provided by fabric"** marker: fabric keeps their values with the stack. An admin may override
one; the marker then says it is overridden.

### 1.10.4.6.3 Netboot presets

A VLAN or an address can switch on a preset, each a set of client classes and options the admin can edit, pointing
at a boot server the owner runs (an address, or a name in fabric's DNS); fabric serves no boot files (2.1.10.15,
1.10.2.7):

- **PXE, BIOS and UEFI:** classes on the client's architecture (option 93: 0 BIOS, 7 and 9 x64 UEFI, 11 arm64 UEFI),
  each with its own boot file name (67), next server and TFTP server name (66);
- **iPXE chain-load:** a client already running iPXE (user class `iPXE`, option 77) gets the iPXE script's URL
  instead of the iPXE binary, so it does not loop;
- **UEFI HTTP boot:** vendor class `HTTPClient` gets an `http://` boot URL, with option 60 echoed back.

## 1.10.4.7 Addresses in use that nobody recorded

Kea pings an address before handing it out and skips one that answers (Kea 3.0's ping-check hook); an admin may also
**scan a subnet on request** (ping and ARP from fabric's host; a routed VLAN answers what its gateway lets through)
(2.1.10.13). Neither ever blocks: an address found in use but unrecorded is shown as "in use, unrecorded" (with the
MAC when ARP saw it), and the console offers to make it a reservation for that device, or a static record; the admin
may also ignore it or register something else there.

## 1.10.4.8 Editing a house from the top

An edit from the top's console is written on the top's DC to the house's `OU=networks`; replication carries it to the
house (1.9.8.5). Each site's fabric polls its own DC's highest USN every 30 s; when its OU changed it renders Kea and
reloads it through its control socket (2.1.10.6), with its DNS records and the access lists. A house cut off from the
top keeps serving from its own copy, and its own edits merge when the link is back (AD keeps the last writer per
attribute; the console names a conflict object if one appears, 1.9.8). A site with a read-only DC (1.9.8.3) is
edited from a writable DC above it.

## 1.10.4.9 The console and the command line

- **A Networks tab** replaces the Kea tab's subnet parts: the sites (the top sees every house), a site's VLANs, a
  subnet's map (its ranges as a bar, used and free) and its address table (static, reservation, lease, unrecorded,
  free; search by IP, name or MAC; export as CSV); the options with their sources and markers. Reading needs
  `dhcp:read`, changing `dhcp:write`; a house's admin sees only their house.
- **`fabricctl ipam`:** `block [<n>]` (2.1.10.16), `vlan add|set|remove`, `subnet add|set|remove` (2.1.10.18),
  `range add|remove`, `address add|set|remove`, `option set|remove`,
  `netboot on|off`, `scan <subnet>`, `show [<site>]`, `find <ip|name|mac>`, `export`; `--site` for the top. Every
  entry point gets positive and negative tests and joins the inventory (3.1.2.5).
- Today's `fabricctl dhcp add-subnet` and the other subnet commands become aliases of the new ones for one release,
  then go.

## 1.10.4.10 The upgrade from 0.7

At the upgrade, each site's `dhcp.subnets` (with their pools, reservations and options) moves into its plan once,
recorded, and `vars.yaml` stops carrying them; each subnet's VLAN becomes a VLAN object (one without a VLAN gets the
next free ID, named after the subnet, and is listed for the admin to check). The site's number is asked once (the
suggestion: its order in the organisation), by setup just before the move (2.1.10.16, 1.10.4.18.1). Nothing a
running site serves changes. A site with a read-only DC keeps its subnets in `vars.yaml` until its parent can write
its plan (S8, 2.1.10.19).

## 1.10.4.11 Tests

- Unit: the model's rules (overlaps, one claim per address, ranges inside their subnet, the suggestions).
- Real containers: Kea rendered from the plan answering a relayed request on each VLAN (a relay container on each of
  three Docker networks); DNS and PTR for a static address; a lease shown beside the plan; a second claim refused;
  options set at a subnet overridden at an address; a BIOS, a UEFI and an iPXE client each given its own boot file;
  an option with a code Kea does not know, defined and sent; ping-check skipping an address that answers.
- Two sites (the `site_join` suite's setup): an edit at the top reaches the site's Kea.
- The Incus test bed (2.1.1.50): a routed lab with a relaying gateway and real clients on two VLANs, the release's
  gate.

## 1.10.4.12 Not in scope

fabric does not route, firewall between VLANs or configure switches and gateways (2.1.10.8); scans run only on
request and never block (2.1.10.13); fabric serves no boot files (2.1.10.15).

## 1.10.4.13 The plan's entries in AD

### 1.10.4.13.1 The schema

Added through `ensure_schema` (the schema path 0.7.0 fixed, 1.6.5.24) in fabric's OID arc, after the attributes and
classes already there (a schema addition is permanent: a new need is a new number):

| Attribute (arc `.1.n`) | n | Syntax | Holds |
|---|---|---|---|
| `fabricPurpose` | 15 | string | a VLAN's purpose |
| `fabricAccess` | 16 | string | a VLAN's access: `full` or `guest` |
| `fabricGateway` | 17 | IA5 | a subnet's gateway (the router's address in it) |
| `fabricDhcpServed` | 18 | boolean | whether Kea serves the subnet |
| `fabricSubnetId` | 19 | integer | the subnet's Kea id (leases are tied to it, 1.10.2.3) |
| `fabricRelay` | 20 | IA5 | the relay's address when it lies outside the subnet (1.10.3.2) |
| `fabricDhcpOption` | 21 | string, multi | one DHCP option per value, `<position>:<JSON>` (LDAP keeps no order) |
| `fabricRangeKind` | 22 | string | `gateway`, `static`, `dhcp` or `reserved` |
| `fabricFirst`, `fabricLast` | 23, 24 | IA5 | a range's first and last address |
| `fabricIp` | 25 | IA5 | an address |
| `fabricAddressKind` | 26 | string | `static`, `reservation` or `infrastructure` |
| `fabricMac` | 27 | IA5 | an address's MAC (lower case, colons) |
| `fabricHostName` | 28 | IA5 | an address's name (one DNS label) |
| `fabricOwner` | 29 | string | who an address belongs to (free text) |
| `fabricDns` | 30 | boolean | whether the address is published in DNS (1.10.4.5) |
| `fabricBlock` | 31 | integer | the site's number (1.10.4.13.4) |
| `fabricVlanName` | 32 | string | a VLAN's name |

| Class (arc `.2.n`) | n | Kind | Must / may |
|---|---|---|---|
| `fabricVlanRecord` | 7 | structural, in an OU | `fabricVlan`, `fabricVlanName` / `fabricSite`, `fabricPurpose`, `fabricAccess`, `description` |
| `fabricSubnet` | 8 | auxiliary, on a `fabricNetwork` entry | — / `fabricGateway`, `fabricDhcpServed`, `fabricSubnetId`, `fabricRelay`, `fabricDhcpOption` |
| `fabricRange` | 9 | structural, below a `fabricNetwork` | `fabricRangeKind`, `fabricFirst`, `fabricLast` / `description` |
| `fabricAddress` | 10 | structural, below a `fabricNetwork` | `fabricIp`, `fabricAddressKind` / `fabricMac`, `fabricHostName`, `fabricOwner`, `fabricDns`, `fabricDhcpOption`, `description` |
| `fabricAddressBlock` | 11 | auxiliary, on a site's OU | — / `fabricBlock` |

A subnet is not a new class: it is the `fabricNetwork` entry 1.10.2.8 already keeps (CIDR, VLAN, kind, notes,
overlap reason), given the `fabricSubnet` class for what only the plan's subnets hold. Every DC holds every site's
entries, so the overlap rule (1.10.2.6) and `read_networks` see the plan's subnets with no second copy.

A reservation that names a device role (0.9, 1.11.1.7) is also given the existing auxiliary class `fabricDeviceRoles`
(1.6.3.4) and holds the role in `fabricRoleName`, as a device does: no new attribute or class.

### 1.10.4.13.2 Where each entry lives

In the site's `OU=networks` (`CN` values escaped, whatever they hold):

- a VLAN: `CN=<VLAN ID>`, class `fabricVlanRecord` (its name is an attribute, so renaming it moves nothing);
- a subnet: `CN=<subnet name>`, classes `fabricNetwork` and `fabricSubnet`; its `fabricNetworkKind` is `dhcp` when
  Kea serves it, else `subnet`;
- a range: `CN=<kind>-<first address>` below its subnet's entry;
- an address: `CN=<address>` below its subnet's entry.

Removing a subnet removes its ranges and addresses with it (a tree delete). The site's number is on the site's OU.

### 1.10.4.13.3 Who reads and writes it

- Two directory operations run inside the DC as the site's agent account (1.6.3, 1.6.5.16), so AD's access rules
  decide who writes which site: `read_plan` (one site's plan, or every site's, with every site's number and the
  order the sites' OUs were made) and `write_plan` (a list of changes: add, set or remove a VLAN, subnet, range or
  address, or set a site's number). A site's agent has full control below its own OU, so the site above writes a
  house's plan (`--site`) and a house never writes its parent's (2.1.9.13).
- `write_plan` writes; it checks nothing of the model. Every rule of 1.10.4.3.2 is checked by fabric first, on the
  plan just read (`fabriclib/ipam`: `check_vlan`, `check_subnet`, `check_range`, `check_address`), so a refusal writes
  nothing. Changes go in order; one AD refuses leaves those before it made (each command writes one to six).
- Convergence (1.6.5.15) still writes the site's other networks (its LAN, and 0.7's DHCP subnets until the upgrade
  moves them) and never changes or removes an entry with the `fabricSubnet` class, nor writes a network of the same
  name or CIDR. The AD site's subnets (1.9.8.5) are the site's networks and its plan's subnets.

### 1.10.4.13.4 The site's number

`fabricBlock` on the site's OU (class `fabricAddressBlock`), 1-255, unique in the organisation. When a site first
needs one (the upgrade, or `vlan add` with no `--subnet`), fabric gives it the suggestion: its order in the
organisation (the sites by when their OUs were made, the first 1), or the next number no site has. Setup asks it
once and `fabricctl ipam block` changes it (2.1.10.16, 1.10.4.18.1); a site that reaches a command needing a number
before it was asked (setup could not reach the DC) is still given the suggestion, as above.

## 1.10.4.14 The plan at an apply

- Every apply reads the site's plan from its DC before the settings are checked (`load_address_plan`), unless the
  settings still carry `dhcp.subnets` (an install not yet upgraded, 1.10.4.15). Each subnet Kea serves becomes the
  `dhcp.subnets` entry the Kea template has always rendered (`plan_to_dhcp`): its id, name, VLAN, notes, the VLAN's
  access, the gateway as its router, its relay and options, its `dhcp` ranges as pools and its reservations (with
  their names and options). So Kea's configuration, the DNS registration, the reverse zones (2.1.10.7) and the access
  lists (1.10.3.3) come out of the plan exactly as they came out of the settings.
- Each `static` or `infrastructure` address with DNS on becomes an A record of the site's zone, and its PTR follows
  (the generated reverse zones). A name the settings' `dns:` already holds in that zone keeps the settings' record;
  the apply says so.
- The plan read is kept in `<config>/address-plan.json` (root's, 0600, no secret in it). A DC that does not answer
  leaves the apply on that copy, so the site keeps its last rendering, and the apply says when it was read. With no
  copy and DHCP on, the apply stops before it changes anything ("start the samba service").
- Between applies the firewall (DOCKER-USER and UFW's rules for the subnets' clients), the consent plans and the Kea
  tab read the subnets from that copy (`planned_subnets`), so they never lose them because `vars.yaml` no longer
  carries them.

## 1.10.4.15 The upgrade, as built

- After convergence, at every setup and every apply (`move_subnets_to_plan`), a site whose `vars.yaml` still carries
  `dhcp.subnets` moves them into its plan: each subnet a VLAN with its own VLAN ID (one without gets the lowest free
  ID and is named after the subnet) and that VLAN's subnet, served by DHCP, keeping its Kea id, name, router (now its
  gateway, with a one-address `gateway` range unless a pool holds it), relay, notes, overlap reason, access and
  options; each pool a `dhcp` range; each reservation a `reservation` address with its hostname and options. A
  subnet without a name is named after its network (`net-10-1-20-0-24`). An entry convergence wrote under the same
  name is converted in place. The site is given its number if it has none (1.10.4.13.4).
- Then the record `<config>/ipam-upgrade-<time>.json` (0600): what moved, the VLAN IDs fabric chose, what was already
  in the plan, any key of a subnet the plan does not hold ("not carried"), and the subnets as they were; and
  `vars.yaml` loses `dhcp.subnets`, keeping `dhcp.interfaces` and the global defaults (options, option definitions,
  client classes, lease time, DNS and NTP servers). The apply lists the VLANs fabric chose, to check
  (`fabricctl ipam show`).
- Idempotent (global Rule 12): a subnet the plan already has is left alone, settings without subnets change nothing.
  A move that cannot happen yet (the DC not answering, a read-only DC, settings Kea's checks refuse) is reported and
  left for the next apply, the settings untouched. The apply that moves renders Kea from the settings, the next from
  the plan: the same subnets, ids, pools and reservations, so nothing a running site serves changes.
- The upgrade writes `vars.yaml` without the vars lock: the apply that runs it already holds it when the console or a
  command started it.
- From then on the 0.7 commands that edited subnets in the settings (`fabricctl dhcp add-subnet`, `set-subnet`,
  `remove-subnet`, `reserve`, `unreserve`, an option on a subnet or a reservation, and the Kea tab's same actions)
  refuse with "change them with fabricctl ipam"; global options and client classes stay in the settings and are
  edited as before, checked with the plan's subnets. `fabricctl dhcp on` turns DHCP on over the plan's subnets.
  Their aliases to the new commands (1.10.4.9) are left for a later phase (1.10.4.17).
- A reservation may now lie inside a pool (a `dhcp` range may hold reservations, 1.10.4.3.2): `normalize_dhcp` no
  longer refuses one, whether the subnets come from the plan or the settings (Kea gives that address only to its
  MAC). A static A record inside a pool is still refused.

## 1.10.4.16 `fabricctl ipam` in phase 1

Routing only (`run_ipam_command`); each command calls one function, which reads the plan, checks the rules and
writes. The operator's procedure is [4.10.2](../volume_4_operations/4.10.2-address-manager.md).

```
fabricctl ipam show [<site>]                 a site's number, VLANs, subnets, ranges and address table (leases too)
fabricctl ipam find <ip|name|mac>            across every site: the row, or for an address nobody recorded its
                                             subnet and range
fabricctl ipam export [<site>]               the address table as CSV (every site without one)
fabricctl ipam block [<n>]                   the site's number, shown or set (1.10.4.18.1)
fabricctl ipam subnet add|set|remove …       a VLAN's further subnets (1.10.4.18.3)
fabricctl ipam vlan add <id> --name N [--subnet CIDR | --no-subnet] [--gateway IP] [--purpose T] [--notes T]
                        [--access full|guest] [--dhcp on|off] [--relay IP] [--no-split] [--allow-overlap "<why>"]
fabricctl ipam vlan set <id> [--name N] [--purpose T] [--notes T] [--access full|guest] [--gateway IP|none]
                        [--dhcp on|off] [--relay IP|none] [--allow-overlap "<why>"|none]
fabricctl ipam vlan remove <id> [--force]
fabricctl ipam range add <vlan> gateway|static|dhcp|reserved <first> <last> [--notes T]
fabricctl ipam range remove <vlan> <first>
fabricctl ipam address add <ip> --kind static|reservation|infrastructure [--name N] [--mac M] [--owner T]
                        [--notes T] [--dns on|off] [--vlan V] [--role R]
fabricctl ipam address set <ip> [--kind K] [--name N|none] [--mac M|none] [--owner T] [--notes T] [--dns on|off]
                        [--role R|none]                   (--role: a reservation's device role, 1.11.1.7)
fabricctl ipam address remove <ip>
--site S on every change: another site's plan; a change to this site's plan applies at once unless --no-apply
```

- **A VLAN and its subnet are added together.** `vlan add` makes the VLAN, its subnet (the one given, or
  `10.<site>.<VLAN>.0/24`; a VLAN above 255 has no suggestion and needs `--subnet`) named after the VLAN with the next
  Kea id, its gateway (given, else the first host) and in a /24 the suggested split (gateway `.1`, static `.2-.99`,
  DHCP `.100-.249`, reserved `.250-.254`) unless `--no-split`; `--no-subnet` makes a record only. A name that is the
  site's LAN entry (convergence's `lan`) with the same network becomes that VLAN's subnet. Further subnets on a VLAN
  are `subnet add` (2.1.10.18, 1.10.4.18.3).
  `vlan set` changes the record and, on a VLAN with one subnet, the subnet's gateway, DHCP, relay and overlap reason
  (on a VLAN with several it refuses them, naming its subnets: `subnet set`); the VLAN's ID and its subnets'
  networks stay (remove and add again). Renaming a VLAN keeps its subnets' names, which Kea and the DNS filter's
  groups use. `vlan remove` removes every subnet of the VLAN and refuses while they record addresses, unless
  `--force`.
- **The rules** (1.10.4.3.2), each refusal naming why and changing nothing: a VLAN ID 1-4094 and a name (one DNS
  label), each unique in the site; a subnet of at least four addresses, overlapping no other network in the
  organisation unless either side gives a reason (`--allow-overlap`), never fabric's own container network; ranges
  inside their subnet, never overlapping, a `dhcp` range over no address but reservations and not over the gateway;
  one claim per address (a static, a reservation, an infrastructure address or the gateway; a second is refused
  naming the first); inside a `dhcp` range only a reservation; a reservation has a MAC, unique among the site's
  reservations; a static address outside every `static` range is warned about, never refused, and so is a
  reservation in a subnet DHCP does not serve. DNS on needs a name, unique among the site's published names and not
  already in the settings' zone; a reservation may have DNS on too (2.1.10.17, 1.10.4.18.2).
- **Applying:** a change to this site's plan runs the apply (Kea, DNS and the firewall, as `fabricctl dhcp` does)
  unless `--no-apply`; a change to another site's plan says it takes effect at that site's next apply (the USN poll
  that applies it there at once is 1.10.4.8, a later phase). Every change is audited (`IPAM_VLAN_ADD`, …).
- Options per subnet and address are kept (the upgrade carries them) and rendered, but set with `option set|remove`
  only in a later phase (1.10.4.6).

### 1.10.4.18.2 A reservation in the site's zone

A reservation may have DNS on (2.1.10.17), under the rules of every published name (a name, unique among the site's
published names, not already in the settings' zone). At an apply it is both: Kea's reservation with its hostname,
which DHCP registers in `dhcp.<domain>` as before, and an A record of the site's zone (`plan_to_dhcp`), whose PTR

### 1.10.4.18.3 More than one subnet per VLAN: `ipam subnet`

```
fabricctl ipam subnet add <vlan> <cidr> [--name N] [--gateway IP] [--dhcp on|off] [--relay IP] [--notes T]
                         [--no-split] [--allow-overlap "<why>"]
fabricctl ipam subnet set <name|cidr> [--gateway IP|none] [--dhcp on|off] [--relay IP|none] [--notes T]
                         [--allow-overlap "<why>"|none]
fabricctl ipam subnet remove <name|cidr> [--force]
```

- `subnet add` gives a VLAN another subnet (or a first one to a VLAN kept as a record): named after the VLAN while
  no subnet has its name, else `<VLAN name>-2`, `-3`, …, or `--name`; made exactly as `vlan add` makes one
  (`common/new_subnet`: checked, its gateway, the next Kea id, a /24's suggested split unless `--no-split`).
- `subnet set` changes one subnet's gateway, DHCP, relay, notes and overlap reason (`common/change_subnet`, which
  `vlan set` shares); `subnet remove` removes one with its ranges and addresses, refusing while it records
  addresses unless `--force`; the VLAN stays, a record only once its last subnet goes.
- A VLAN's other commands find the right subnet: `range add <vlan>` and `address add --vlan` take the VLAN's subnet
  holding the address (refused, naming the subnets, when none does), `range remove <vlan> <first>` looks in all of
  them, `show` lists each subnet under its VLAN (a second one by its name), `find <vlan name>` names all of them.
- Kea renders each served subnet as before; several may carry the same VLAN (`normalize_dhcp` no longer requires a
  VLAN to be unique among the subnets, so 0.7's `fabricctl dhcp add-subnet --vlan` at a site not yet upgraded
  accepts one too), and the DNS filter's `vlan:<n>` groups already take every subnet of the VLAN
  (1.10.3.7). Audited `IPAM_SUBNET_ADD`, `IPAM_SUBNET_SET`, `IPAM_SUBNET_REMOVE`.

## 1.10.4.19 A name set by hand outranks DHCP's

The owner's rule (2.1.10.20): a DNS record set by hand (in fabric's zones, or an address of the plan with DNS on) is
authoritative, and DHCP's dynamic updates never overwrite or replace it, forward or reverse. Two layers keep Kea off
it ([2.3.10.4.8](../volume_2_engineering_decisions/2.3.10-dhcp-notes.md#231048-a-name-set-by-hand-outranks-dhcps-how-kea-is-kept-off-it-and-results)):

- **Kea sends nothing for such a reservation.** A reservation is `"ddns": false` in Kea's subnets when the plan
  publishes it (`plan_to_dhcp`) or when any A record set by hand names its address (`normalize_dhcp`; a 0.7
  reservation may also say `ddns: false`). The Kea template puts it in the `SKIP_DDNS` client class and then loads the
  ddns-tuning hook (`libdhcp_ddns_tuning.so`), which makes Kea skip every DNS update for clients in that class: no
  name in `dhcp.<domain>` and no PTR. Kea 3.0 has no way to skip only the reverse update (DDNS settings in a client
  class are refused), so the reservation's names are the site zone's A and PTR alone. Its address is left out of
  the reverse zones Kea registers in (`dhcp_reverse_zones`).
- **BIND refuses Kea's key every name set by hand.** In each reverse zone Kea may write, a `deny "kea-ddns" name
  <name> ANY` rule comes before the zone's grant for every reverse name whose PTR fabric generates from a record set
  by hand (`dns/reverse_by_hand`, rendered by apply and by `dns add-zone` from the same checked settings,
  `deploy/check_rendered`, 2.1.10.21). Kea's key never had any forward zone but
  `dhcp.<domain>`, and the apply's regenerated reverse zones keep Kea's records only where fabric has no PTR
  (2.1.10.7).

Leases and reservations that nobody named by hand register in `dhcp.<domain>` with their PTRs as before.

## 1.10.4.20 A DHCP name left behind is deleted, at every apply and hourly

Decision 2.1.10.22. A device that DHCP registered before (`cam3.dhcp.<domain>`) and whose names are then set by hand
keeps that old name: Kea skips the client from then on (1.10.4.19) and never removes it, and fabric never rewrites
`dhcp.<domain>` (2.1.4.1). Fabric deletes it:

- **What is deleted.** In `dhcp.<domain>`, every A or AAAA record whose address a record set by hand covers (an A or
  AAAA record of fabric's zones: the settings' `dns:` or an address of the plan with DNS on, as the apply's checked
  settings hold them), and the name's DHCID once no address record is left at it. Nothing else: a DHCP name whose
  address no record set by hand names is left alone, and a record set by hand is never touched (the update goes to
  `dhcp.<domain>` only, and Kea's key reaches nothing else, 1.10.4.19).
- **The PTR.** Kea's PTR for that address (and its DHCID there) is already gone at the apply that publishes the name
  set by hand: fabric regenerates the reverse zone with its own PTR and keeps Kea's records only at names it has no
  PTR for (`merge_dynamic_records`, 2.1.10.7); BIND then denies Kea's key that name. The update touches the forward
  zone only.
- **How the names are found.** BIND transfers none of its zones (1.10.3), so fabric reads the zone as BIND serves it:
  its file with the journal applied, by `named-compilezone -j` in BIND's container (read only; `rndc sync` would
  write the file only later, so it is not used).
- **How they are deleted.** One RFC 2136 update per run, signed with Kea's key (`kea-ddns`), sent by `nsupdate` to
  BIND (`host_ip`, `bind_dns_port`); the key is in a 0600 temporary file, never on the command line. The update is one
  message: BIND applies all of it or none. Each removal is audited (`DHCP_NAME_CLEAR`: the name, its type and
  address, `apply`, `timer` or `cli`). A second run finds nothing and sends nothing.
- **When.** (a) At every apply on a running install, once BIND serves the new configuration and zones, from the
  apply's checked settings. (b) Hourly, by `fabric-dhcp-names.timer` (`fabricctl dhcp clean-names --scheduled`, 10
  minutes after boot, then every hour): the cleanup alone, not an apply, which would restart every service whose
  configuration changed. The plan's published names are read from the DC at the apply, so the timer reads the
  addresses set by hand that the last apply kept (`<deploy base>/kea/hand-set.json`, root, 0600). The timer is
  installed while Kea is (`install_kea`); with DHCP's DNS registration off (`dhcp.ddns: false`) the run does
  nothing. By hand: `sudo fabricctl dhcp clean-names`.
- **When BIND refuses.** A refused update (a key BIND no longer knows, BIND not answering) changes nothing and is
  reported: the apply finishes its other steps and then fails with an `Error:` naming the refusal; the timer's run
  fails (`systemctl status fabric-dhcp-names`, the journal); the command exits 1. The hourly run tries again.

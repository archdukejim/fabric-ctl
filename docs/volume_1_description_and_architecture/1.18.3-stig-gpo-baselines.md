## 1.18.3.1 Status and the idea

**Designed 2026-10-22 for 0.11.0, its decisions settled 2026-10-23 (2.1.18.11 to 2.1.18.14, 2.1.18.18), nothing built.** The owner:
"we should make it easy to apply them as a part of a gpo for Windows or Linux systems using their stigs via Group
Policy" (2.1.18.3). So an admin picks a STIG for a set of machines and fabric turns it into a Group Policy object that
the domain applies: on Windows, the GPO DISA publishes, with the DoD-only settings taken out; on Linux, a GPO that
carries the OS STIG's profile for a client-side extension to apply. It is **opt-in**: a fresh install links no
baseline, and nothing reaches a machine until an admin adds one.

## 1.18.3.2 A baseline, and how it fits the grants

### 1.18.3.2.1 What a baseline is

A **STIG baseline** is kept in the domain as a grant is (1.6.13.4, 2.1.6.79): one object under
`CN=stig,CN=fabric,CN=System`, of class `msDS-App-Configuration`, its definition JSON in `msDS-Settings`, written only
by fabric-agent. It holds:

- its **name** (2-40 characters, a-z 0-9 -) and a description;
- its **product**: one GPO of a loaded package (`DoD Windows 11 STIG Computer`, its version) or one Linux profile
  (`Ubuntu 24.04 STIG`, the content's version), and the package's hash;
- its **where**: machine groups, all required, as a grant's where (1.6.13.4): `machines-desktops`, `site-a`, an admin's
  `hosts-<name>`;
- its **overrides**: each setting the admin keeps, removes or changes from what fabric imported, with a reason, shown
  beside the setting.

### 1.18.3.2.2 How it is compiled

By the grants' compiler, in the same run and at the same DC (the root site's writable DC, 1.6.13.11.1), every 5 minutes
and at once on a change:

1. **The computed group** `stig-<name>-where` in `OU=fabric,OU=groups`: the computers in all the where groups **whose
   OS is the product's** (by `operatingSystem`, as the hourly sort reads it, 1.6.13.10.8); a computer of another OS is
   left out and the compile says so. Computers only, as `access-<n>` (a person in it would carry the GPO, 1.6.13.4).
2. **The GPO** `fabric: stig <name>`, linked at `OU=machines` and security-filtered to that group and to each of its
   computers by SID (the 2.1.6.94 rule, for sssd before 2.9.4).
3. **Its place in `gPLink`:** after `fabric: access none` and before every `fabric: access <n>`. A set's access GPO
   stays the last, so on any right both set, the grants win (1.6.13.4's precedence); the rights fabric owns are taken
   out of a baseline in any case (1.18.3.3.2).
4. **Refused,** with why: a computer reached by two baselines of the same product (two Windows 11 baselines); a
   baseline whose where holds a DC host or names `dc-hosts` (1.6.13.6); a where with no group. Baselines of different
   products stack (Windows 11 and Edge on one desktop). A baseline that reaches no computer is allowed and marked so.

### 1.18.3.2.3 What does not change in 0.8.0's model

Nothing of 1.6.13 changes: no right is added to a grant, `fabric: access none` stays first and every access set's GPO
stays after the baselines, the computed groups keep their names and rules, OUs still grant nothing, and no baseline
reaches the fabric host (it is in `OU=fabric-hosts`) or a DC's host. A baseline is a new kind of object beside the
grants, compiled by the same run, with the same where and the same filtering.

## 1.18.3.3 Windows: DISA's GPO package

### 1.18.3.3.1 Loading the package

DISA's quarterly package (1.18.1.3.4) holds each product's GPOs as GPMC backups (a folder per GPO with `Backup.xml`,
`bkupInfo.xml`, `gpreport.xml` and, under `DomainSysvol\GPO\`, the machine side's `Registry.pol`,
`Machine\microsoft\windows nt\SecEdit\GptTmpl.inf` and `Machine\microsoft\windows nt\Audit\audit.csv`), the ADMX
templates they need, and reports. The admin downloads it from DISA and loads it (`fabricctl stig package load <zip>`,
or the console's upload); fabric does not download it (2.1.18.11), and does not ship it (as
Microsoft's templates, 1.6.5.9). fabric shows the zip's SHA-256 beside the line to compare it with DISA's, keeps the
package in the DC's own store (not SYSVOL), lists its GPOs by product and version, and loads its ADMX templates into the
central store through the ADMX editor (1.6.5.9) so every setting can be read in the editor and in RSAT. A file that is
not a GPO backup, a backup whose files do not parse, or a package with no GPO is refused, with why.

### 1.18.3.3.2 What fabric takes out or changes

Each is applied when a baseline is made from the package's GPO, listed on the baseline's page, and overridable there
with a reason (except a.):

- a. **The rights fabric's access GPOs own** are taken out: `SeInteractiveLogonRight`, `SeRemoteInteractiveLogonRight`
  in `[Privilege Rights]`, and the local Administrators group's members (`[Group Membership]`). The grants decide them
  (1.6.13.4), more tightly than the STIG (which lets every user sign in at the keyboard); the checklist's row says
  "met by the grants". Not overridable: two GPOs setting one right would undo the grants.
- b. **The DoD banner** (`LegalNoticeCaption`, `LegalNoticeText` under
  `MACHINE\Software\Microsoft\Windows\CurrentVersion\Policies\System`): replaced by the organisation's own notice if
  the install has one (2.1.18.8), otherwise taken out. Exempt kind 1.
- c. **DoD certificates**: any `Software\Policies\Microsoft\SystemCertificates` entry (DoD roots in Root, the
  Interoperability and CCEB cross-certificates in Disallowed) is taken out; fabric's trust GPO (1.6.5.9) stays the
  root. Exempt kind 2.
- d. **Settings that name DoD services** (a DoD time or update server, a DoD-licensed tool): taken out. Exempt kind 6.
- e. **Deny rights on local accounts** (`SeDenyNetworkLogonRight`, `SeDenyRemoteInteractiveLogonRight` naming
  "Local account", `*S-1-5-113` / `*S-1-5-114`): they also keep the machine's `local-admin` from signing in remotely,
  which 1.6.13.4 keeps as a way in. Kept by default; the admin may override them per baseline, with a reason (2.1.18.12). The deny rights on the domain's top tier
  (Enterprise and Domain Admins on members) are kept: they match fabric's tiers (2.1.6.68).
- f. **Account policies** in `[System Access]` apply only to the member's local accounts (domain accounts keep the
  domain's policy, 1.6.12.10): kept. The compile warns when a baseline's maximum password age is shorter than the
  interval at which OpenBao rotates the machine's `local-admin` (2.1.7.15), so it cannot expire unseen.
- g. **Settings that would break what fabric sets up** are listed for the lab to check before they ship (2.1.18.16):
  the Windows Defender Firewall STIG's inbound block against the join guide's Domain profile (1.6.5.10), the 802.1X
  profile (PEAP), Kerberos sign-in to the console, the trust GPO.

### 1.18.3.3.3 Writing the GPO

fabric writes `fabric: stig <name>` with the GPO writer the ADMX editor uses (inside the DC as the system, 1.6.13.11.1):
the edited `Registry.pol`, `GptTmpl.inf` and `audit.csv`, the machine extension names for the registry, security and
advanced audit client-side extensions, the version bumped in AD and `GPT.INI`, SYSVOL's ACLs reset. The GPO is fabric's,
as a set's access GPO is: RSAT shows it; a change made there is overwritten at the next compile, and the compile says
so. The user side of a package's GPO (its user `Registry.pol`) applies to people signing in on those machines through
loopback processing in merge mode, only if the admin turns it on for the baseline (off by default).

### 1.18.3.3.4 What the package has that fabric does not offer

- The **domain controller** GPOs (Windows Server 2025 DC): fabric's DCs are Samba, not Windows; the DC's own STIG items
  are the Active Directory STIGs' (2.1.18.4).
- **Domain-level** settings (the domain's password and Kerberos policy): the domain's own, set by fabric's tiers
  (1.6.12.10), never from a package.
- Products with no member here (Office, Exchange) are listed but offered like any other, opt-in.

## 1.18.3.4 Linux: the OS STIG by Group Policy

### 1.18.3.4.1 What samba-gpupdate can apply

Samba's `samba-gpupdate` applies a GPO's Linux settings on a member (research 2.3.18.4.2). Its client-side extensions
cover the login notice (`/etc/issue`, `/etc/motd`), sudo rules, files and symbolic links, scripts run from cron and at
start-up, OpenSSH server options, PAM access rules, firewalld (RHEL family, not Ubuntu's ufw), GNOME settings (the
screen lock), Firefox and Chromium policies, smb.conf and certificate auto-enrolment (with AD CS, which fabric does not
run). It applies at a random interval of 90 to 120 seconds, and takes its settings off again when a GPO stops applying.
It does **not** apply a security template (`GptTmpl.inf`) to a member: password and Kerberos policy apply only on
Samba DCs. On an sssd member it needs the machine password in Samba's `secrets.tdb` (`adcli join --add-samba-data`, or
sssd's `ad_update_samba_machine_account_password`) and `oddjob-gpupdate`, which Debian and Ubuntu do not package.
Most of an OS STIG (auditd rules, PAM password quality and faillock, kernel parameters, packages, AIDE, AppArmor, file
modes) is outside these extensions, reachable only as a script.

### 1.18.3.4.2 fabric's own client-side extension

Decided by 2.1.18.13 (Ubuntu Pro's USG may be used instead where Pro is attached): the step that applies a baseline is fabric's, in `fabric-managed` (1.6.11.6), which already
runs hourly on every managed Linux member signed in as the machine:

- **Finding its baselines:** the machine reads which `stig-<name>-where` groups hold it (the same check `fabric-managed`
  makes for its own group), and each baseline's GPO.
- **The settings:** the GPO carries, in its SYSVOL folder, `Machine/fabric/stig.json`: the profile (the OS STIG as
  ComplianceAsCode's SCAP Security Guide content expresses it, `xccdf_org.ssgproject.content_profile_stig` for
  `ubuntu2404`, at the content version fabric pinned), the rules fabric always turns off (1.18.3.4.3) and the admin's
  overrides, as an XCCDF tailoring. The machine fetches it over SMB with its own Kerberos ticket.
- **Applying:** OpenSCAP from the member's packages (`oscap xccdf eval --remediate --tailoring-file`) with the pinned
  content fabric publishes in its apt repository (2.1.1.2; ComplianceAsCode is BSD-3-Clause, to be listed in 1.1.7),
  then a scan whose result stays on the machine (`/var/lib/fabric/stig/`) for the lab and the report (2.1.18.16).
- **What it changed** is recorded (global Rule 12): the files it wrote and their earlier contents. A machine leaving a
  baseline gets back the recorded files; what cannot be put back (a removed package, a changed boot setting) is listed
  in the baseline's preview before it is linked, and again when it is removed.
- **Why fabric's and not samba-gpupdate:** it needs nothing new on the member, applies the whole profile rather than
  the few settings Samba's extensions know, and reports what passed. The GPO is still a real GPO: linked, filtered and
  versioned, seen in RSAT.

### 1.18.3.4.3 What fabric always turns off

On a member, these rules are taken out of the tailoring, each with its reason in the baseline's page:

- Smart card, PIV and CAC sign-in (`pam_pkcs11`, `sssd` certificate maps): exempt kind 3.
- DoD banner text in `/etc/issue`, `/etc/issue.net` and the graphical greeter: the organisation's notice instead, or
  none (2.1.18.8). Exempt kind 1.
- DoD CAs in the trust store: fabric's root is installed by the join (1.6.7). Exempt kind 2.
- AIDE's mail to the ISSO: AIDE stays; who is told is 2.1.18.5's. Exempt kind 4.
- A DoD time source: chrony uses `ntp.<domain>` (1.13). Exempt kind 6.
- Rules that would cut fabric's own ways in: the SSH options fabric sets (Kerberos only, `UsePAM yes`, 1.6.11.6) and
  sssd's configuration are left as the join wrote them where the STIG's rule would differ; the firewall rule is kept
  with SSH allowed.
- The audit offload target (`audisp-remote`) is set from the install's log-forwarding choice (2.1.18.19), or the rule
  stays failed and is said.

### 1.18.3.4.4 What Group Policy cannot do on Linux

- **Install-time rules:** separate file systems for `/var`, `/var/log/audit`, `/tmp` and `/home`, and disk encryption,
  are set when a machine is installed. They are listed as failed with why.
- **Reboot-time rules:** a boot-loader password, kernel arguments (`audit=1`) and FIPS mode take effect only at the next
  boot; fabric never reboots a member and reports "reboot pending". FIPS mode on Ubuntu needs Ubuntu Pro's FIPS packages
  (2.1.18.9).
- **Systems with no STIG:** Ubuntu 26.04 (none yet), Debian 12 and 13 and Proxmox VE (none at all), and RHEL-family
  members (no join yet). Decided by 2.1.18.14: Ubuntu 26.04 gets the 24.04 profile marked "preview" until DISA
  publishes; Debian and Proxmox VE get none; RHEL 9 and 10 when the join supports them.

## 1.18.3.5 The fabric host

No GPO reaches the fabric host (it is in `OU=fabric-hosts`, 1.6.13.10.9), and it is not a member to harden from the
DC it runs. `fabricctl setup` applies the Ubuntu STIG to the host itself in an opt-in step `stig` (on under the `stig`
profile), with the same engine and a tailoring
that keeps fabric working (its firewall, Docker, the DC's host network, the audit rules' cost on a 4 GB Pi),
consented to as host changes (1.2.9) and undone by uninstall (2.1.18.15).

## 1.18.3.6 Pages, the CLI and routes

- **Directory → STIG baselines** (1.6.12): the loaded packages and their GPOs; the baselines, a baseline's page (its
  product, where, the computers it reaches, the settings fabric took out and why, the overrides), **Add baseline**,
  and a preview of what it would change before it is linked.
- **CLI:** `fabricctl stig package load|list|show|remove`, `fabricctl stig baseline list|show|add|set|remove|preview`;
  a computer's page and `fabricctl domain grant explain` show the baselines that reach it.
- **Routes:** GET `/v1/stig/packages`, `/v1/stig/baselines`, `/v1/stig/baselines/<name>` (`domain:read`); POST
  `/v1/stig/packages`, `/v1/stig/baselines`, `/<name>`, `/<name>/delete`, `/<name>/preview` (`stig:admin`, a new permission in the
  Directory Administrators' bundle, 2.1.18.18).
- **Audit:** `STIG_PACKAGE_LOAD`, `STIG_PACKAGE_REMOVE`, `STIG_BASELINE_ADD`, `STIG_BASELINE_SET`,
  `STIG_BASELINE_REMOVE`, and each compile's changes in `GRANT_COMPILE`.

## 1.18.3.7 Tests

Against a real Samba DC and the lab's real members (2.1.18.16), positive and negative for every entry point:

- a Windows 11 desktop in a baseline gets its GPO (`gpresult /r`), its settings hold, and the grants still decide who
  signs in: a grant's person signs in, anyone else is refused; `local-admin` as 2.1.18.12 decides;
- a desktop outside the where does not get it; a Linux computer in a Windows baseline's where is left out and the
  compile says so; a second Windows 11 baseline over the same computer is refused;
- no DoD banner and no DoD certificate on any member; the organisation's notice when set;
- an Ubuntu 24.04 member: the scan before and after, the rules fabric turns off untouched, sssd sign-in, sudo and SSH by
  Kerberos still working after the profile; the machine leaving the baseline gets its recorded files back;
- refusals: a zip that is not a GPO package; a baseline on `dc-hosts`; a baseline by someone without the permission;
  the compile's refusals of 1.18.3.2.2, each with its message.

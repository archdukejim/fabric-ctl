## 1.6.4.2 What it is for, and what stays

The owner wants Windows machines (up to about seven, across two houses) joined to a domain and managed with
Group Policy, 802.1X with PEAP and machine authentication, and one sign-in everywhere. Only Active Directory
gives Windows that, and Samba is the open-source AD domain controller in Ubuntu's own archive.

| Stays as it is | Comes from Samba AD (only when it is on) |
|---|---|
| **389-DS is the source of truth for identity**: people, groups, ids (POSIX), devices, roles, the address plan; created at the root site, replicated by M5 | A Windows domain (Kerberos realm, LDAP, SMB) mirroring fabric's people and groups |
| Keycloak for every web sign-in (TOTP), with its users in 389-DS | Windows logons, Group Policy, machine accounts |
| BIND for every name the network asks for | AD's own DNS zone (`ad.<domain>`), answered by Samba **behind** BIND |
| Step-CA for every certificate (EAP-TLS, services) | Nothing: Samba's own CA features stay off |
| chrony on the host for time | Windows time pointed at fabric's NTP by policy |
| FreeRADIUS: EAP-TLS, MAB, EAP-TTLS | **PEAP-MSCHAPv2** for people and for machines (computer accounts) |

Samba AD is **optional** (`install_samba: false` by default) and changes nothing for an install that does not
turn it on. Its first controller is at the **root site**; each other site may have its own ([1.6.4.9](#1649-more-than-one-site)).

## 1.6.4.3 Shape

- **One forest, one domain.** Realm `AD.<DOMAIN>` (DNS `ad.<domain>`, a sub-domain fabric owns: never the
  same name as fabric's own zone, so the two DNS servers never fight over a name). NetBIOS name from the
  first label of the domain, at most 15 characters, settable (`samba_netbios`).
- **A container like every other part**: `fabric/samba:local`, built `FROM` a pinned Ubuntu digest with
  Ubuntu's `samba`, `winbind` and `krb5-user` packages (no apt source added); non-root is not possible for a DC
  (it binds 88, 389, 445 and switches users for file access), so it gets only the capabilities it needs
  (`NET_BIND_SERVICE`, `SETUID`, `SETGID`, `CHOWN`, `DAC_OVERRIDE`, `FOWNER`), no-new-privileges, a memory
  limit (512 MB; measured in S0 against the [1.2.6](1.2.6-targets-and-hardening.md#1261-targets-and-hardening) budget at 4 GB) and its data in `/opt/samba`.
- **Provisioned once**, idempotent: `samba-tool domain provision --use-rfc2307` with a random administrator
  password kept in fabric's secrets (OpenBao), never on a command line. A re-run finds the domain and
  converges its settings.

## 1.6.4.4 Network and DNS

Windows clients talk to a DC on many ports (DNS 53, Kerberos 88/464, LDAP 389/636, GC 3268/3269, SMB 445, RPC
135 and a dynamic range), and they register their own names by **dynamic DNS updates sent straight to the
server named in the zone's SOA**. Publishing all of that through the host clashes with BIND on port 53.

**Proposal: the DC gets its own LAN address** (`samba_ip`), on a Docker macvlan network on the LAN interface,
and is also on `fabric_net`:

- Clients keep using BIND as their resolver. BIND gets a **forward zone** `ad.<domain>` → the DC's
  `fabric_net` address (BIND reaches it inside the host; the host cannot reach its own macvlan child). An SOA
  query for `ad.<domain>` returns the DC's name and LAN address, so Windows' own updates go straight to
  Samba, signed with Kerberos (GSS-TSIG). Samba's internal DNS serves only the AD zone (no recursion).
- `fabricctl` writes the DC's records in fabric's zone (`dc1.<domain>` CNAME, `_kerberos` pointers if
  wanted) through the usual `apply`.
- **Firewall:** traffic to a macvlan address never passes the host's firewall. The DC's ports are meant for
  the LAN, so this is shown in `fabricctl status` as a relaxation, and the DC's `hosts allow` limits SMB and
  LDAP to `lan_cidr` and the site's subnets (address plan). A VLAN that should not reach the DC is the
  router's job, as today.
- Alternative (decision S3): an extra address on the host's interface (a host change, asked under a new
  consent group) with Samba's ports published on it. More moving parts on the host, so macvlan is proposed.

## 1.6.4.5 Identity and passwords

**People and groups** flow one way, 389-DS → AD, by a fabric sync (`fabricctl samba sync`, a 5-minute timer,
and at once after a fabric change): each person becomes an AD user with the same name, uidNumber/gidNumber
(rfc2307), display name and mail; groups and memberships follow; a person disabled or removed in fabric is
disabled or removed in AD. Objects fabric did not create in AD (Windows admins' own) are never touched.

**Passwords** are the one hard part: Windows needs NT hashes, 389-DS keeps only one-way hashes, so a password
must reach Samba **in clear at the moment it is set**. Every place a password is set:

| Where a password is set | How it reaches the other store |
|---|---|
| Admin creates a person or resets a sign-in (`create_person`, `reset_sign_in`: fabric functions) | The function writes it to Samba too (`samba-tool user setpassword`, from a file) |
| The person changes it in Keycloak (first sign-in, account page) | A small **Keycloak LDAP mapper** (`passwordUpdated` callback, the hook Keycloak's own AD mapper uses) hands it to fabric-agent, which writes it to Samba |
| The person changes it on Windows (Ctrl-Alt-Del) or with `kpasswd` | Samba's `samba-tool user syncpasswords --script` (built for this) hands it to fabric-agent, which writes it to 389-DS as Directory Manager |
| `passwd` on a joined Linux machine | After S6 Linux machines join the AD realm, so this is the Kerberos case above |

Loops are cut by fabric-agent remembering a just-written password's hash for a minute. `syncpasswords` keeps
a GPG-encrypted copy of new passwords in AD (its documented requirement); the GPG key lives only in the DC's
data, root-only. This is **decision S1**; the alternatives are in [2.1.6](../volume_2_engineering_decisions/2.1.6-identity.md).

**Keycloak** keeps 389-DS as its user store. Web sign-in with a Windows ticket (SPNEGO) is a later option.

## 1.6.4.6 802.1X

FreeRADIUS gains **PEAP-MSCHAPv2** when Samba is on: the FreeRADIUS container runs `winbind` as a member of
the domain and checks passwords with `ntlm_auth`, for people (the `radius_people` groups, as EAP-TTLS today)
and for **machines** (computer accounts, `host/` names) so a Windows machine is on the network before anyone
logs on. VLANs keep coming from fabric's device roles and groups. EAP-TLS with Step-CA certificates stays the
recommended method; the Windows guide in the FreeRADIUS tab gains a PEAP profile.

## 1.6.4.7 Group Policy

- GPOs are edited from a domain-joined Windows machine with Microsoft's RSAT (Samba's own tools cover only a few kinds of policy).
  fabric ships a small default set: Windows time from `ntp.<domain>` ([1.6.4.8](#1648-time)), the Wi-Fi/wired 802.1X profile
  (PEAP or EAP-TLS) and trust in fabric's root CA, each one a template it re-applies only when the admin has
  not changed it.
- **SYSVOL is not replicated by Samba.** With more than one DC, fabric copies the root DC's SYSVOL to the
  others (one way: GPOs are edited at the root) over the federation link, then resets its ACLs
  (`samba-tool ntacl sysvolreset`).

## 1.6.4.8 Time

Kerberos fails beyond 5 minutes of skew; chrony already keeps every site within a second (M9). Windows
members normally take time from their DC with signed NTP, which would need chrony inside the DC. Instead the
default GPO points Windows Time at `ntp.<domain>` (plain NTP from the host's chrony), as for every other
client; nothing runs NTP in the DC container.

## 1.6.4.9 More than one site

Built after host-1/host-2 are rebuilt, together with M6 (owner 2026-10-03):

- Each site that turns Samba on gets a DC joined to the one domain over the federation link (the WireGuard
  tunnels between houses). **Decision S2:** a read-only DC (RODC: people are only written at the root, as in
  M5; logins at the site keep working from cached passwords while the root is away) or a full DC (simpler
  replication, but a second place where people could be changed outside fabric). RODC is proposed if S0 shows
  Samba's RODC works for logins, password caching and PEAP with the root away.
- **AD sites and subnets come from the address plan** (M8): each fabric site becomes an AD site with its
  networks, so Windows finds its own site's DC.
- The forward zone at each site's BIND points at the site's own DC; the root's DC stays the PDC emulator.

## 1.6.4.10 Joining machines (domain-join.md, rescoped)

- **Windows:** "Access work or school → join a domain" with `ad.<domain>`; an admin in fabric's
  `fabric-admins` group may join machines (delegated in AD; *revised 2026-10-19, D1:* the Directory
  Administrators, `directory-admins`, 1.6.13.10.4). Joined machines appear in the Directory tab
  (read from AD).
- **Linux:** `realm join ad.<domain>` (SSSD's AD provider) replaces steps 4–5: the machine account, Kerberos
  and single sign-on come from AD. Step 3 stays fabric's: host groups and login rules become AD groups plus
  SSSD's `simple` access rules written by the installer, and **sudo rules stay in 389-DS** (SSSD's LDAP sudo
  provider), so no AD schema extension is needed (decision S4). The installer still pins fabric's CA by
  fingerprint.
- Without Samba, a Linux join stays the LDAP-only installer (step 3).

## 1.6.4.11 Consent, settings, operations

- **Host changes:** none beyond today's groups (the DC is a container; macvlan is a Docker network). setup
  lists the DC's LAN address in its plan. Alternative S3 (a host address) would add a consent group.
- **Settings:** `install_samba`, `samba_ip`, `samba_parent_interface` (default: the LAN interface),
  `samba_netbios`, `samba_realm` (default `ad.<domain>`), `samba_mem_limit`.
- **Operations:** `fabricctl samba status / sync / join-info`, doctor checks (Kerberos ticket for a test
  principal, LDAP over TLS, DNS SRV records through BIND, SYSVOL in step), the web UI's Directory tab with a
  Windows domain section. Export, restore and uninstall carry the AD database (`samba-tool domain backup
  offline` while stopped). Offline: the image is built from the bundle's base image and Ubuntu packages
  already in the bundle's apt cache.
- **Upgrades:** turning Samba on later provisions the domain and syncs everyone; people's passwords reach AD
  only when next set, so setup offers to reset sign-ins (or each person changes theirs once).

## 1.6.4.13 Related, separate designs (after this one)

- *Out of fabric's scope (2.1.9.10, 2026-10-04): the links between sites — WireGuard is run by another stack.* The text
  below is kept as it was proposed.
- **Edge role** (per house: the only box with open ports): WireGuard between houses with keys exchanged at
  federation join and routes from the address plan; the public reverse proxy; ddns. Kept outside the core
  node, as the owner runs it today.
- **Let's Encrypt via Cloudflare DNS-01** for user-facing names (separate Cloudflare tokens for ddns and for
  ACME, no IP filter: the home address is dynamic); Step-CA stays for everything internal, client
  certificates and EAP-TLS, and is the offline fallback. A Let's Encrypt certificate cannot sign others, so
  it cannot be the root of fabric's CA.

## 1.6.5.2 The image

`fabric/samba`, one of fabric's own published images (2.1.1.21), built from `packaging/images/samba/` `FROM` the pinned
Debian base with **Debian's** `samba-ad-dc`, `winbind`, `krb5-user` and `python3-samba` (Q1). Debian, not Ubuntu:
Samba's DLZ module must match BIND's version, and fabric's BIND is Debian's (2.3.6.1.7). The image has a `bind` group
with fabric's gid (600) so provisioning grants BIND access to the DNS partition (Q2).

fabric's BIND image gains Samba's `samba-libs` and `samba-dsdb-modules` (the DLZ module `dlz_bind9_18.so`, which
serves BIND 9.18 and 9.20).

## 1.6.5.3 Hardening and resources

- `cap_drop: ALL` and back only **CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, NET_BIND_SERVICE** (Q1, Q16: SETUID
  and SETGID for sign-ins and share access, the next three for Group Policy's ACLs on SYSVOL; NET_BIND_SERVICE for
  the DC's low ports, because in the host network Docker's unprivileged-port setting does not apply — found on the
  test Pi in S1.7, owner 2026-10-04; the spike ran on a bridge and did not need it). NetBIOS is off (AD needs none).
- Runs as root inside the container (a DC switches users for file access); `no-new-privileges`; read-only root;
  writable: its data volume (`/opt/samba`: database, SYSVOL, private), `/run` (sockets, `ntp signd`), tmpfs
  `/var/log/samba` and `/tmp`.
- Its full host name (`dc1.<ad-domain>`, or `<site>-dc.<ad-domain>` at a site), or Kerberos asks for the wrong
  service name (Q1).
- Memory limit `samba_mem_limit`: 512 MiB at 4 GB (peak measured 229 MiB, an RODC 254 MiB), 384 MiB at 3 GB.
  BIND's limit goes to 128 MiB at 4 GB (69 MiB measured with DLZ), 96 MiB at 3 GB. Budget at 4 GB: 389-DS's 384 MiB
  goes, the DC's 512 MiB comes, BIND +48 MiB: about +176 MiB on ≈ 2.3 GB, within 4 GB (Q10). Measured on the Pi in S1.
- The privileges inventory: [1.2.7](1.2.7-container-inventory.md).

## 1.6.5.4 Network: the host's address

The DC answers on the host's address (2.1.6.8), **IPv4 only** (2.1.6.29, 0.6.2): it provisions and joins with its
interfaces limited to `127.0.0.1`, the host's IPv4 address and, from 0.6.3, `fabric_net`'s gateway
(`ip_fabric_gateway`: containers — Keycloak, FreeRADIUS — reach it there, so their traffic stays on the bridge,
2.1.2.15; its certificate names that address too, and its own DNS updates name the LAN address only,
`samba_dnsupdate --current-ip`), and every converge removes AAAA records from the AD
zones — a host with IPv6 addresses otherwise published them, and Windows, preferring IPv6, tried an address the DC
never answered on. Proposed (2.1.6.18): **the DC runs in the host network**, like Kea,
bound to the LAN interface only (`interfaces = <lan iface>`, `bind interfaces only = yes`). Why not ports published
from `fabric_net`: AD hands its own address to clients — in DNS records, CLDAP replies and the RPC endpoint mapper —
and behind Docker's NAT that would be the container's address. The spike ran the DC on its own bridge network, so
**S1 proves the host-network DC with a real Windows join** (host-1).

- Ports on the LAN address: 88 and 464 (Kerberos, TCP/UDP), 135 (RPC endpoint mapper), 389 (LDAP, CLDAP on UDP),
  445 (SMB), 636 (LDAPS), 3268/3269 (global catalog), and a narrowed RPC range
  (`rpc server dynamic port range = 49152-49251`). Port 53 stays BIND's; the DC's own DNS server is off
  (`server services = -dns`).
- nginx no longer passes 389/636 through (389-DS's ports): the DC owns them.
- The host firewall allows these ports from `lan_cidr`, the site's subnets in the address plan, `fabric_subnet`
  (Keycloak and FreeRADIUS reach the DC at the host's address) and, between DCs, peer DCs (1.9.8.5). A host change in
  the firewall group (consent).
- The DC's resolver is the host's address (fabric's `resolv.conf`, mounted read-only): in the host network it would
  otherwise use the host's resolver, which does not know the AD zone when the host keeps its own (`use_host_dns`),
  and the DC could not find its own KDC or send its signed updates (found on the test Pi, S1.7).
- FreeRADIUS reaches the DC's winbind through its socket folder shared read-only (privileged folder in group 610),
  not the network (Q8).

## 1.6.5.5 Provisioning and re-runs

- Once at the root site: `samba-tool domain provision --use-rfc2307 --dns-backend=BIND9_DLZ` with the domain of
  2.1.6.11, then the password policy of 2.1.6.13, the Administrator's password from a file through Samba's Python bindings,
  `ntlm auth = mschapv2-and-ntlmv2-only` (PEAP), `redirusr`/`redircmp`, fabric's and sudo's schema (two sessions),
  the layout of 1.6.3.4, the ACLs of 1.6.3.6, the root site's AD site and subnets, the trust GPO, the site's logon
  GPO. Provisioning's output is discarded.
- Idempotent: a re-run finds the domain and converges each item (schema checked by OID, OUs, ACLs, GPOs by
  name and version); nothing is provisioned twice (Q1).
- At a site: a join (1.9.8.4), not a provision.

## 1.6.5.6 DNS

BIND serves the AD zone through DLZ beside fabric's zones (Q2): read-only mounts of the DC's `smb.conf` and
`bind-dns` folder, `--url` naming the database, writable `/var/tmp` for Kerberos' replay cache. Signed (GSS-TSIG)
updates from Windows and Linux members are accepted; unsigned refused. The AD zone is never fabric's own (2.1.6.11):
[1.4.1.2](1.4.1-dns-architecture.md#1412-dns-with-samba-ad-planned).

## 1.6.5.7 Certificates

The DC's LDAPS/TLS certificate comes from Step-CA like every service (2.1.5.3): names `dc1.<ad-domain>`,
`<ad-domain>` and the host's names; renewed by `fabricctl certs` with the others; Samba's own CA off (`tls enabled`
with fabric's files). Keycloak, FreeRADIUS and Linux members verify it against fabric's root CA.

## 1.6.5.8 Time

Kerberos fails beyond 5 minutes of skew; chrony keeps every site within a second (M9). Proposed (2.1.13.1): Windows
members keep their default (time from their DC, signed with the DC's key): **the host's chrony answers them**,
since the DC's address is the host's, signing through the DC's signing socket (chrony's `ntpsigndsocket`, the DC's
`/run/samba/ntp_signd` on the host). No time GPO, nothing runs NTP in the container; Linux machines use
`ntp.<domain>` as today. A change to the time consent group (1.2.9). Proven in S5.

## 1.6.5.9 Group Policy and the ADMX editor

- **Pushed by default** (2.1.6.10) only what fabric's services need: **trust in fabric's root CA** (a GPO linked to
  the domain, written as Windows' *Trusted Root Certification Authorities* policy into `Registry.pol`; Q13, the
  Windows check in S5), and each site's **logon rights** (1.6.3.10; `GptTmpl.inf`, `[Privilege Rights]`; Q16).
- **Everything else is the admin's**, through fabric's **ADMX editor** (web UI and `fabricctl gpo`): templates are
  loaded into the domain's central store (`samba-tool gpo admxload`); fabric parses ADMX/ADML (Microsoft's and
  Samba's forms), shows each policy with its names and elements, and writes chosen values into a GPO's
  `Registry.pol` through Samba's PReg encoding (Q13, `spikes/samba/admx.py`), bumping the GPO's version in AD and
  `GPT.INI` and resetting SYSVOL's ACLs. The standard tools (RSAT) keep working.
- **Templates:** fabric ships **its own ADMX** (its settings for Windows machines) and a **blank starter template**
  for an admin's own; **Microsoft's templates are linked, not shipped** (licensing): the admin downloads them and
  uploads them in the editor.
- The 802.1X wired/Wi-Fi profiles are not ADMX policies: the FreeRADIUS tab's guides cover them (PEAP or EAP-TLS).
- Between sites: 1.9.8.8.

## 1.6.5.10 Joining Windows machines

"Access work or school → join a domain" with the AD domain. A machine joins into its site's `OU=machines`: the
site's admins (or the site's agent, pre-creating the account in the web UI with a one-time join password) may join
machines there (delegated). Machines appear in the web UI's domain section (read from AD); disabling one also
refuses its PEAP machine sign-in (Q8).

## 1.6.5.11 Settings, consent and operations

- **Settings:** `ad_domain` (2.1.6.11, required, permanent), `ad_netbios`, the password policy (2.1.6.13, required),
  `ad_old_password_minutes` (2.1.6.15), `samba_mem_limit`, `posix_id_block` (2.1.6.17), `site_dc_type` (from the invitation).
- **Consent:** firewall (1.6.5.4), time (1.6.5.8), packages unchanged (everything is in images).
- **Operations:** `fabricctl domain status | password-policy | gpo … | machines …`; doctor checks a Kerberos
  ticket for a test principal, LDAPS, the SRV records through BIND, replication and SYSVOL in step, `CNF:` objects;
  export, restore and uninstall carry the AD database (`samba-tool domain backup offline`, stopped). Offline
  installs: the image comes in the bundle like the others (2.1.1.22).
- **Agent routes and permissions:** [1.6.3.15](1.6.3-samba-directory.md#16315-agent-routes-added-with-samba-ad-planned).

## 1.6.5.23 The DC's own name (0.7.5)

**Designed 2026-10-11 for 0.7.5 (decision 2.1.6.45), not built.** Until 0.8.0 the domain controller took the host's
name (`hostname`: Samba's `--host-name`, its NetBIOS name, its computer account `<hostname>$`, `hostname_dc` =
`<hostname>.<ad-domain>`), so the host's name was permanent (2.1.2.16). The DC is a container; the name it has in the
domain need not be the host's.

- **`dc_name`**, a setting of its own: the DC's name in the domain (one label, at most 15 characters: NetBIOS; not
  `localhost`). Setup asks it, as a permanent question (1.3.2.2), suggesting `dc-<hostname>`, cut to 15 characters,
  so the name says which machine it lives on; any valid name may be given. `hostname_dc` becomes
  `<dc_name>.<ad-domain>`; every use of the host's name as the DC's (Samba's provision and join, its keytab's
  principals, `check_samba_settings`) takes `dc_name` instead.
- **Unique in the domain:** a site joining an upstream checks the name against the domain's DCs before it joins and
  refuses one in use, with the names taken.
- **Permanent:** the vars editor refuses a change to `dc_name`, as to `ad_domain`; renaming an AD DC is not supported.
- **The host's name is no longer permanent:** `hostname` leaves `IMMUTABLE_KEYS` for the warned settings (the menu
  asks before applying, as for `host_ip`); a change re-renders what names the host (its certificate's names, the
  landing page) and leaves the DC alone.
- **Existing installs** keep their DC: an install without `dc_name` takes it from its `hostname` at the upgrade,
  once, and saves it, so nothing in the domain is renamed.
- **Tests:** render (the default, the 15-character cut, an install upgraded without `dc_name` keeps its name); the
  vars editor refuses `dc_name` and warns on `hostname`; the samba suite provisions with a `dc_name` unlike the host's
  and a person signs in; site_join refuses a name in use; the lab: the host renamed after install, the DC and a
  joined client unaffected (2.1.1.48, 0.8.1).

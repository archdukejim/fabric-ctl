## 1.12.3.1 Status

**Built 2026-10-11 for 0.7.0 (decision 2.1.12.6).** The spike that chose it: 2.3.1.18; what the build changed from
the design is said in place and listed in 1.12.3.15. The resolver of
1.12.2 stays and answers clients; the lists move out of it into AdGuard Home, which only matches them. Where this
chapter and 1.12.2 differ, this chapter holds from 0.7.0 (1.12.3.12 lists what of 1.12.2 it replaces).

## 1.12.3.2 Shape

```
clients ── host_ip:53, :853 (DoT), DoH via nginx ──> bind9-resolver (views, safe search, the owner's rules)
                              ├─ fabric's zones ──> bind9 (authoritative)                 never filtered
                              └─ everything else ──> adguard-filter (the lists only) ──> Cloudflare over DoT
```

- **BIND's resolver** (1.12.2) keeps: answering clients (plain DNS, DoT, DoH), fabric's zones (forward zones to the
  authoritative BIND, never filtered), the owner's allow and block rules (`owner.rpz`), safe search, the groups (views),
  the query log and statistics.
- **AdGuard Home** (`adguard-filter`) answers only the resolver, matches the site's lists and the groups' rules, and
  forwards what it lets through to the upstreams (`dns_filter_upstreams`, Cloudflare over DoT by default), at least
  one. AdGuard reaches each **by its address** (`tls://1.1.1.1`) and verifies the certificate for that address (the
  providers' certificates name their addresses): by name, `cloudflare-dns.com` resolves to addresses that serve no DoT
  and every query timed out (found by the resolver suite, 2.3.1.18). The name stays in the vars and the console. A blocked
  name answers **NXDOMAIN** (`blocking_mode: nxdomain`; its default, `0.0.0.0`, is not used: 2.3.1.18).
- Each view of the resolver forwards to AdGuard Home (`forward only`) instead of to the upstreams or to the main view:
  the chained views of 1.12.2.15 go, each view is independent.
- `dnssec-validation no` in the resolver's views (a blocked answer from AdGuard carries no signature: validating would
  turn it into SERVFAIL); AdGuard Home validates (`enable_dnssec`), as the upstream did for the chained views.

## 1.12.3.3 The container

- **`adguard-filter`**, from AdGuard Home's own image (`adguard/adguardhome`), pinned by digest in the images lock's
  third-party section like nginx and Postgres (`image_adguard`, tracked `v0.107.*`, policy `auto`: 2.1.14). A unit of
  its own. The resolver's unit does not require it (as built): each starts and restarts on its own, and while AdGuard
  is down the resolver fails closed (below).
- **Its own service account**, `adguard` (`fabric-adguard`, 614 in fabric's band, 1.2.2).
- On `fabric_net` at `ip_adguard` (10.255.0.34): port 53 (UDP, TCP) and 853 (DoT, for the groups: 1.12.3.6), and its
  HTTP API on 3000. **Nothing is published** on the host.
- **Hardening** (1.2.8), as the spike found it must be (2.3.1.18): runs as its account, every capability dropped but
  `NET_BIND_SERVICE`, kept because the binary carries it as a file capability and the kernel refuses to run it
  otherwise; `no-new-privileges`; port 53 also allowed by the network namespace's
  `net.ipv4.ip_unprivileged_port_start=53`; read-only root. Docker gives an added capability to a non-root process
  too, so `NET_BIND_SERVICE` is its one effective capability (`CapEff 0x400`, checked by the resolver suite).
- **Folders** under `<base>/dnsfilter/`: `conf` (its `AdGuardHome.yaml`, read-write: AdGuard rewrites it when the API
  changes it), `work` (its data: the compiled lists, read-write), `lists` (fabric's copies of the lists, read-only to
  it: 1.12.3.5), `tls` (the certificate for the groups' DoT, 1.12.3.6).
- **Memory limit** `adguard_mem_limit` (1.12.3.9). **Health check:** its sign-in page answers
  (`/login.html`), which needs no password, so none is in the container's definition.
- **DoT on 853** only once its certificate exists (`filter.<domain>` and `*.filter.<domain>`, minted with the other
  service certificates); until then the groups' views forward over plain DNS. A renewed certificate restarts it.
- Started with `--no-check-update` (updates are fabric's, through the images lock) and `--no-permcheck`.
- **While it restarts** (33 s on the test Pi with the owner's lists: only when an apply changes its container or file,
  or its image is updated; never for a console change, 1.12.3.8) the resolver has nowhere to send internet names and
  answers them SERVFAIL after its 10 s query timeout (a client may give up first); fabric's own names keep answering. **Fail closed**: nothing unfiltered passes. The status
  and the console show AdGuard starting.
- **Its first start** (a new install, or its data folder gone) reads a list given as a file only at its first update,
  about 5 s after it answers (measured 2026-10-11, 2.3.1.18), and lets names through until then. The gap closes on
  its own; a sync within it (1.12.3.4: a console change, the lists job) asks AdGuard to read every ticked list it has
  not read yet (`/control/filtering/refresh`). A restart reads the lists from its data folder before it answers.

## 1.12.3.4 What fabric renders, and who changes what

- **fabric renders `AdGuardHome.yaml`** at apply (`templates/dnsfilter/AdGuardHome.yaml.j2`, AdGuard's schema 34), so
  AdGuard never has a first launch (which refuses any user but root: 2.3.1.18): its account `fabric-agent` with a
  bcrypt hash of a password generated per install (`adguard_api_password`, in fabric's secrets and OpenBao); DNS on
  53 and 853; the upstreams; `blocking_mode: nxdomain`, `blocked_response_ttl: 10`; DNSSEC on; its own query log and
  statistics **off**; the filters (1.12.3.5) with `safe_fs_patterns` naming the lists folder; the groups as clients and
  their rules (1.12.3.6); its update check off.
- **The vars file stays the truth** (1.12.2.3). A change from the console (1.12.3.8) is saved to the vars under their
  lock and audited, then made in AdGuard through its API, so AdGuard never restarts for it. An apply makes what
  the API sets (lists, rules, groups, upstreams) through the API, and writes the file and restarts AdGuard (3.5 s,
  2.3.1.18) only when a part the API cannot set has changed (fabric keeps a digest of that part), the file is
  missing, or the API does not answer; it says so.
- **Only fabric-agent and the apply speak to the API**, with that account; nothing else has its password.

## 1.12.3.5 Lists: AdGuard's catalogue as checkboxes, fabric's local copies

- **The site's lists** (`dns_filter_lists`, `{name, url, enabled}`) apply to every client of the site. Groups have no
  lists of their own (the owner, 2026-10-11: "group lists will be limited to per site").
- **The catalogue** (AdGuard's HostlistsRegistry, read by the lists job daily, as 1.12.2.14) is shown as one table
  with a **checkbox per list**, its rules, its estimated memory and when its copy was fetched, like AdGuard Home's own
  page. Ticking adds or enables it; unticking disables it (kept, its copy kept); *Remove* drops it. A list by URL is
  added the same way.
- **fabric's local copies** (the owner's choice): the lists job (`fabric-dns-lists`, daily and on demand; the agent
  has no internet, 1.12.2.14) downloads **every list of the catalogue**, enabled or not, and every list added by URL,
  into `<base>/dnsfilter/lists/<id>.txt` (`<id>`: the first 12 hex digits of the URL's SHA-256, as 1.12.2.6). Checks
  before a copy replaces the last: the download within its size limit, at least one rule, and not less than half
  the last copy's rules (a truncated download never empties a list). A list that fails keeps its last good copy.
- **AdGuard reads the copies as files** (`/lists/<id>.txt`, its filter URL a path, allowed by `safe_fs_patterns`), so
  it needs no internet for the lists and enabling one is a read and a compile: 0.08-0.93 s in the spike, against
  29 s for BIND (2.3.1.18). After the job has written new copies it asks AdGuard to refresh (`/control/filtering/refresh`).
- **Each list's state** (last fetch, last success, rules, estimated memory, last error) is kept in
  `<base>/dnsfilter/state.json` (beside the folder AdGuard reads) and shown beside its checkbox; AdGuard's own rule count is shown once enabled.

## 1.12.3.6 Groups

The groups of 1.12.2.15 keep their settings, their views and their matching (the most specific address wins), with
these changes:

- **Each view forwards to AdGuard Home on its own**, the main view (*everyone*) over plain DNS, each group's view
  over **DoT with a ClientID**: its `tls` block names `<group>.filter.<domain>` (`remote-hostname`), which AdGuard
  takes as the client's ID from the TLS server name (its `server_name: filter.<domain>`, a certificate for
  `*.filter.<domain>` from fabric's CA in `<base>/dnsfilter/tls`, renewed with the other service certificates). Each
  group is an AdGuard client of that ID. One network, no address per group. (To confirm: 1.12.3.14.)
- **A group's rules:** its blocks stay in its view's `group-<name>.rpz` (they beat the lists); its allows are
  passthru there (past the owner's blocks, as before) **and** AdGuard rules for that client
  (`@@||name^$client='<group>'`), so they pass the lists too. The forward zones per allowed name (1.12.2.15) go.
- **The owner's allows** stay passthru in `owner.rpz` and are also AdGuard rules for everyone
  (`@@||name^$important`), so they pass the lists too.
- **Safe search** stays in BIND, per view, as built (one table, `dns_filter/common/safe_search`).
- **Each view keeps its own copies** of `fabric.rpz`, `owner.rpz` and its safe-search zone (small: no lists in any view
  now), instead of reaching them through the main view.
- **Groups' lists from before** (1.12.2.15's `lists`) are not carried: an upgrade lists them as not moved (1.12.3.11).

## 1.12.3.7 The query log and statistics

As 1.12.2.13 (Postgres `dnslog`, 7 days of queries, 90 of statistics, every 5 minutes), except where the answer is
read from:

- **The resolver logs each answer** (`responselog yes`, category `responses`, into the query log's file): `response:
  <name> IN <type> <code> ...` after each `query:` line, same client and port (checked on BIND 9.20, 2026-10-11).
- **The collector pairs** each query with its response. An answer `NXDOMAIN` that no response policy zone of the
  resolver gave (the RPZ log has no line for it) came from AdGuard or from the internet: the collector asks AdGuard
  (`/control/filtering/check_host?name=<name>&client=<group>`) once per name and group in each run, and marks it
  **blocked**, with the list (AdGuard's `filter_list_id`, mapped to the list's name) or the group's rule, when AdGuard
  says it is filtered. A genuine NXDOMAIN (a name that does not exist) stays unblocked.
- What the owner's rules and safe search did is read from the RPZ log as before. The view names the group, as before.
- AdGuard's own query log and statistics stay off: fabric's are the only ones, in fabric's console.

## 1.12.3.8 Changes from the console take seconds

A change from the console no longer runs a full apply (`apply_changes`), which took minutes on the test Pi
(2.3.1.18). Each change is saved to the vars (locked, audited), then made where it lives:

| Change | Where it is made |
|---|---|
| A list ticked, unticked, added by URL, removed | AdGuard's API (`/control/filtering/add_url`, `set_url`, `remove_url`); a list with no copy yet starts the lists job, and is enabled when its copy arrives |
| An upstream | AdGuard's API (`/control/dns_config`) |
| The owner's rules, safe search, a group's blocks | the resolver's zones rendered, `rndc reload <zone>` |
| A group added, changed or removed | the resolver's configuration rendered, `rndc reconfig`; AdGuard's client and rules through its API |

The console answers when the change is made; nothing restarts. A full apply stays for everything else.

## 1.12.3.9 Memory

- **The resolver** holds no lists: its limit drops to `resolver_mem_limit` **128 MiB** (45 MiB measured in front of
  AdGuard with the owner's lists, 2.3.1.18).
- **AdGuard Home** holds them compactly: on the test Pi (arm64, 4 GB) 356 MiB for the owner's 15 lists (2.58 million
  rules, about 0.14 KB a rule), 338-491 MiB with a 16th (2.81 million); on amd64 350 MiB for 2.77 million. Rebuilding
  them (a list enabled, a refresh, a start) briefly takes more: 751 MiB at most on the Pi (2.1 × the steady size), 921
  MiB on amd64 (2.6 ×). `adguard_mem_limit` is **1 GiB** on a 4 GB host and follows the host's memory (1.2.4); each
  list's estimate (rules × 0.14 KB) is shown beside its checkbox. A list whose estimate would take the sum × 2.5 past
  `adguard_mem_limit` is refused when ticked, with the reason: the owner's 16 lists fit (about 380 MiB × 2.5).

## 1.12.3.10 Security

- AdGuard's web UI and API share one port; it is on `fabric_net` only, never published and never proxied by nginx,
  so its UI is unreachable from the LAN. Its only account is fabric-agent's, with a generated password.
- Only the resolver reaches its port 53 and 853 (the DOCKER-USER rules keep fabric_net's services from the LAN;
  AdGuard's `allowed_clients` lists only the resolver's address).
- It never sees the clients' addresses (only the resolver's and the groups' IDs), so its configuration and data
  hold no client data; fabric's query log stays the only one, in Postgres, admins only (2.1.12.4).

## 1.12.3.11 Upgrades

- **From 0.6.x (AdGuard Home in front):** as 1.12.2.12: its settings move to the vars (lists, rules, upstreams,
  clients as groups), the old AdGuard (its units, container, `<base>/adguard`, its sign-in proxy, Keycloak client,
  accounts and secrets) leaves the host; then `adguard-filter` is set up behind the resolver from the vars. The old and
  new are different containers, folders and accounts, so retiring one never touches the other.
- **From a 0.8.0 candidate (test hosts only: lists in BIND):** the lists (`dns_filter_lists`) carry over unchanged;
  the converted zones in `<base>/resolver/lists` and the list views' configuration go; groups' own lists are listed as
  not moved.

## 1.12.3.12 What goes from 1.12.2

Replaced from 0.7.0: 1.12.2.6 (lists converted to response policy zones: removed, see 1.12.3.5); in 1.12.2.4 the
384 MiB limit (1.12.3.9); in 1.12.2.10 the lists' zones reloaded (the lists job now writes copies for AdGuard,
1.12.3.5); in 1.12.2.13 a block found from the RPZ log alone (1.12.3.7); in 1.12.2.14 the lists' table (1.12.3.5) and
each change's apply (1.12.3.8); in 1.12.2.15 the chained views, a group's lists, its allows' forward zones and the
memory rule (1.12.3.6, 1.12.3.9). `dns_filter/convert_list`, `add_filter_list` and `common/all_lists` were deleted
at build (no caller left; the import from AdGuard does not need them).

## 1.12.3.13 Tests

- **resolver suite:** the shape of 1.12.3.2 in containers: a listed name NXDOMAIN through the resolver, an ordinary
  name resolves, fabric's zone answered though AdGuard has a rule against it, the owner's rule in BIND, a group's
  block and a group's allow (past a list), safe search per group; the query log marks AdGuard's block with its list
  and leaves a genuine NXDOMAIN unblocked; AdGuard's UI and API unreachable from outside `fabric_net`; it runs as its
  account with only the capabilities above.
- **Console and agent:** ticking a list answers in under 2 seconds and the list blocks; each change of 1.12.3.8 is made
  without an apply; negative cases: a list past the memory rule refused, a URL not http(s) refused, AdGuard down → the
  change is saved and the console says it waits for the next apply.
- **Upgrades:** from 0.6.2 on the test Pi (its AdGuard settings in the new AdGuard), and from a 0.8.0 candidate.
- **The sandbox** and **images** suites take the new container and its pinned image.

## 1.12.3.14 To confirm before building

1. **Groups by ClientID over DoT: confirmed** 2026-10-11 (`spikes/dns-engine/clientid.sh`, 2.3.1.18): BIND 9.20 sends
   `remote-hostname` as the TLS server name; AdGuard Home takes `kids.filter.<domain>` as the client `kids` and applies
   its rule; the main view, over plain DNS, is not affected. Its TLS settings are given as file paths.
2. **Lists read as files: confirmed** the same day: a list at `/lists/<id>.txt`, allowed by `safe_fs_patterns` (in the
   rendered file: the API cannot set it), blocks for everyone. A fresh AdGuard adds its own default lists, so the
   rendered file names the filters explicitly.
3. **Memory on the test Pi: measured** 2026-10-11 (1.12.3.9, 2.3.1.18): 1 GiB holds the owner's lists, no OOM.

## 1.12.3.15 As built: what changed from the design

Found while building and testing (resolver suite, 2026-10-11), each said in place above:

1. Upstreams by address, the certificate verified for it (1.12.3.2): by name, Cloudflare's DoT timed out.
2. No unit requires another (1.12.3.3): the resolver fails closed while AdGuard is down.
3. `NET_BIND_SERVICE` is AdGuard's one effective capability (1.12.3.3), not none.
4. The health check reads the sign-in page, so no password is in the container's definition (1.12.3.3).
5. DoT to AdGuard only once its certificate exists; a renewal restarts it (1.12.3.3, 1.12.3.6).
6. An apply restarts AdGuard only for a part its API cannot set (1.12.3.4).
7. The owner's allows also go to AdGuard, past the lists (1.12.3.6).
8. A first start leaves the lists unread for about 5 s; a sync reads them at once (1.12.3.3).

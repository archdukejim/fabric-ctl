## 3.1.5.1 What the lab is for

the containers.

automated suites (3.1.2): fabric installed fresh and moved from 0.7.1 (3.3.5), a second site joining, Linux members of

## 3.1.5.2 Build the switch and the VMs

**The owner, once** (decision 2.1.1.65): on gaming-23, in **PowerShell run as administrator**, from the repository's
checkout, then sign out of Windows and back in:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\lab\prepare_host.ps1
```

It puts the owner's account (the one the agent runs as) in gaming-23's **Hyper-V Administrators** group, and makes the
internal switch `fabric-lab` and the host address `10.88.0.1`: the only parts of the lab that need administrator
rights. It makes no NAT (3.1.5.1). Run again, it keeps what exists. `-Undo` removes them (after 3.1.5.6), and a
`fabric-lab-nat` if an earlier version made one; never another NAT.

**The agent, from then on**, with Hyper-V Administrators' rights (no elevated PowerShell): `new_hyperv_lab.ps1` makes
the ten VMs and the private switches of 3.1.5.7 (generation 2; Linux with the Microsoft UEFI CA secure-boot template,
the router included; Windows with a virtual TPM), each with its installer ISO from `D:\os\AMD64-x86` as the first boot
device, its disk in `D:\Hyper-V\fabric-lab`, and every NIC with a static MAC (`02-88-00-<address octet>-00-<n>`,
`n` 1 for the lab NIC) so the unattended installs can match it. It refuses, changing nothing, while `fabric-lab` or
`10.88.0.1` is missing (prepare_host.ps1 has not run) or the account has no Hyper-V rights; it checks every ISO first
and changes nothing if one is missing. Run again, it keeps what exists and makes only what is missing.
`-Only g23-vm-ub24-1,g23-vm-ub26-2` makes only those; `-IsoDir` and `-VmDir` change the folders.

## 3.1.5.3 Install each VM, unattended

Decision 2.1.1.65: every VM installs without anyone at its console. Two steps, both the agent's.

**1. The answer media, in WSL** (Ubuntu 24.04; needs `xorriso`, `openssl`, `python3`):

```sh
sudo apt-get install -y xorriso          # once
scripts/lab/make_seeds.sh                # or --only g23-vm-rtr-1,g23-vm-ub24-1
```

It writes into `D:\Hyper-V\fabric-lab\seed\` and only reads the ISOs in `D:\os\AMD64-x86`:

| Installer | Media | What the VM gets |
|---|---|---|
| Ubuntu Server 24.04, 26.04 (and the router, the authenticator, Kubuntu) | `<iso>-autoinstall.iso`, one per installer ISO: a copy whose first GRUB entry boots with `autoinstall ds=nocloud` (subiquity asks to confirm before it writes the disk unless `autoinstall` is on the kernel line), timeout 3 s; and `<vm>.iso`, a NoCloud seed labelled `CIDATA` (`user-data` with `autoinstall:`, `meta-data`) | the address on the NIC with the lab MAC (named `lab`), gateway `10.88.0.2`, DNS `1.1.1.1`, hostname = the VM's name; LVM on the disk; OpenSSH with password sign-in off (`/etc/ssh/sshd_config.d/10-fabric-lab.conf`, root sign-in off); `labadmin` made by cloud-init on first boot with **no password** (locked) and the lab key; `/etc/sudoers.d/labadmin` (0440, `NOPASSWD:ALL`, checked with `visudo -c`) |
| Kubuntu 26.04 | as Ubuntu Server 26.04, plus the package `kubuntu-desktop` | Kubuntu 26.04's desktop over the same base. Kubuntu's own ISO installs with Calamares, which has no unattended mode, so the Kubuntu ISO is not used (2.1.1.65) |
| Proxmox VE 9.1 | `<vm>.iso`: the Proxmox ISO with `answer.toml`, `auto-installer-mode.toml` (`mode = "iso"`, as `proxmox-auto-install-assistant prepare-iso --fetch-from iso` writes) and the first-boot hook `proxmox-first-boot` added; its GRUB then boots *Install Proxmox VE (Automated)* | FQDN `g23-vm-pve9-1.lab.test`, `10.88.0.22/24`, gateway `10.88.0.2`, DNS `1.1.1.1`, ext4 on `sda`; `root` with the lab key and a generated password (hashed in the answer); on first boot the enterprise repositories off, `sudo` installed, `labadmin` as on Ubuntu, root's SSH sign-in by key only, password sign-in off |
| Windows Server 2025 eval, Windows 11 25H2 Pro | `<vm>.iso`, labelled `LABANSWER`: `autounattend.xml` (Setup reads it from the root of any CD) and `fabric-lab\setup.ps1` | the image *Windows Server 2025 Standard Evaluation (Desktop Experience)* (no key: the evaluation's own install) or *Windows 11 Pro* (Microsoft's generic install key, which activates nothing); the disk wiped (GPT: EFI, MSR, Windows); a local administrator `labadmin` with the generated password, no Microsoft account and no OOBE pages (BypassNRO on Windows 11); one automatic sign-in runs `setup.ps1`: the static address on the NIC with the lab MAC, DNS `1.1.1.1`, OpenSSH server installed (Windows 11: from Windows Update, through the router) and started, password sign-in off, the lab key in `C:\ProgramData\ssh\administrators_authorized_keys` (Administrators and SYSTEM only), the firewall rule for port 22; then the automatic sign-in is turned off and Setup's copies of the answer file are deleted |

**The generated passwords.** Windows' `labadmin` and Proxmox's `root` need one (their answer formats require it); the
agent never uses either. `make_seeds.sh` generates each once (20 random characters) into
`%USERPROFILE%\fabric-lab\windows-admin.txt` and `%USERPROFILE%\fabric-lab\pve-root.txt`, owner-only (inheritance
off; the owner, SYSTEM and Administrators), and into the answer media; it never prints, logs or passes them on a
command line, and later runs reuse them. They are lab-only: never used on any other machine.

**2. The install, from PowerShell on gaming-23** (Hyper-V Administrators' rights), **the router first**:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\lab\install_vm.ps1 -Name g23-vm-rtr-1
powershell -ExecutionPolicy Bypass -File scripts\lab\install_vm.ps1 -Name g23-vm-ub24-1
```

`install_vm.ps1` attaches the media (Ubuntu: the remastered installer on the first DVD drive, the seed on a second;
Proxmox: the prepared ISO on the first; Windows: the original ISO on the first, the answer ISO on a second), starts
the VM, types Enter for a Windows ISO's *Press any key to boot from CD or DVD* (`send_key.ps1`, through Hyper-V's
`Msvm_Keyboard`, every half second for 20 seconds) and then sets a Windows VM to boot from its disk, so Setup's own
restarts never meet that prompt again; and waits until `labadmin` answers SSH at the VM's address with the lab key
(default 90 minutes; a progress line every minute). While it waits it records no host key: Ubuntu's live installer
runs its own SSH server at the same address with other keys. The installed system's key is recorded once `labadmin`
(an account that exists only there) gets in. Then it ejects the media, boots from the disk, shuts the VM down and
takes the checkpoint `clean` (3.1.5.5); the router is started again. The first full run's times are in 2.3.1.27. It refuses any other VM while the router does not answer
and route (its `fabric_lab` table loaded and `1.1.1.1` reachable), since every other installer reaches the internet
through it. A VM that already answers SSH is left alone; one that is running without answering is refused (restore
or stop it first). Host keys go to `%USERPROFILE%\fabric-lab\known_hosts`, not the owner's own.

## 3.1.5.4 The agent's way in

Built into every install (3.1.5.3); the owner does nothing. The agent signs in as `labadmin` with the lab key
`g23_lab` (in `%USERPROFILE%\.ssh\` on gaming-23), never with a password:

```sh
ssh -i ~/.ssh/g23_lab -o UserKnownHostsFile=~/fabric-lab/known_hosts labadmin@10.88.0.10 hostname
```

On the Linux VMs (Proxmox too) `labadmin` has no password and passwordless sudo; on Windows it is an administrator
whose key is in OpenSSH's file for administrators. Passwordless sudo and the generated passwords are for the lab only;
neither is ever set on a production or house machine.

## 3.1.5.5 Checkpoints

`install_vm.ps1` takes each VM's checkpoint `clean` after its install (3.1.5.3), so a test can start again from a fresh
machine. To put a VM back: `Restore-VMCheckpoint -VMName <name> -Name clean -Confirm:$false`. Members of gaming-23's
local **Hyper-V Administrators** group (prepare_host.ps1 puts the owner's account in it, 3.1.5.2) start, stop,
checkpoint and restore VMs without being administrators, so the agent does this itself.

## 3.1.5.6 Take the lab down

```powershell
powershell -ExecutionPolicy Bypass -File scripts\lab\remove_hyperv_lab.ps1
```

It lists what it removes (the VMs with their disks, the switches and the host address, and a `fabric-lab-nat` if one
exists), asks once, and removes only those; never the `Default Switch` or another lab's switch or NAT. Then
`prepare_host.ps1 -Undo` as administrator removes the group membership.

## 3.1.5.7 The router, the authenticator and the private switches

Decisions 2.1.1.64, 2.1.1.65. `new_hyperv_lab.ps1` also makes four **private** switches (no host, no internet) and the
extra NICs on them; running it again on a lab made before adds what is missing, NICs on running VMs included:

| Switch | What is on it |
|---|---|
| `Default Switch` | Hyper-V's built-in switch: the router's NIC `wan` (DHCP from it, internet) |
| `fabric-lab-vlan` | a trunk of VLANs 10, 20, 30 (untagged native): the router's NIC `vlans` and the authenticator's uplink; `kub26-1` on VLAN 10 and `w11-1` on VLAN 20 as DHCP clients |
| `fabric-8021x-p1` to `p3` | one 802.1X port each, MAC spoofing on: the authenticator's port NICs; `ub26-2` on port 1 and `w11-1` on port 2 as supplicants |

- **`g23-vm-rtr-1` (Ubuntu Server 26.04):** installed unattended like the other Ubuntu VMs (3.1.5.3), first. Its
  NICs are named in the guest as on Hyper-V: `lab` (`10.88.0.2/24`, no gateway), `wan` (DHCP from the Default Switch:
  the default route), `vlans` (no address) with `vlans.10`, `vlans.20`, `vlans.30` at `10.88.10.1/24`,
  `10.88.20.1/24`, `10.88.30.1/24`. It forwards (`/etc/sysctl.d/90-fabric-lab-router.conf`) and its nftables table
  `inet fabric_lab` (`/etc/nftables.conf`) masquerades `10.88.0.0/24` and the three VLANs out of `wan`, forwards
  between the lab and the VLANs, and takes nothing in from `wan` but replies and DHCP. `isc-dhcp-relay` is installed
  with its settings in `/etc/default/isc-dhcp-relay` (to fabric, `10.88.0.10`, on `lab` and the VLANs) but disabled
  and masked: no DHCP server or relay runs in the lab until 0.9.0's DHCP tests unmask it.
- **`g23-vm-auth-1` (Ubuntu Server):** installed as 3.1.5.3 on its first NIC at `10.88.0.3`; the other four NICs stay
  without addresses. The agent installs hostapd, one wired authenticator per port NIC, each sending its RADIUS to
  fabric. Hyper-V passes EAPOL between a port and its supplicant only on a private switch, as gaming-23's first lab
  proved (2.3.11.4).
- **`g23-vm-ub24-2`:** as 3.1.5.3 at `10.88.0.12`.

## 3.1.5.9 A development build on a lab VM

How a branch's fabric gets onto a lab VM (written 2026-10-23 for the `dhcp` campaign; any campaign that installs
fabric uses it). The VM starts from its checkpoint `clean` (3.1.5.5), so nothing of an earlier install is left.

1. **The package, in WSL**, from the branch's worktree (as the sandbox builds it, `tests/sandbox/run.sh`):

   ```sh
   OUT=/tmp/lab-dist bash packaging/deb/build-deb.sh     # prints /tmp/lab-dist/fabricctl_<version>~git<time>.<commit>_all.deb
   ```

   Copy it where Git Bash reaches it (the scratch folder of the session, or `/mnt/c/...`).
2. **The settings file**: the campaign's own (`tests/lab/<campaign>_vars.yaml`), with no secret in it.
3. **The install, from Git Bash on gaming-23** (Windows OpenSSH, the lab key):

   ```sh
   scripts/lab/install_dev_build.sh 10.88.0.10 <the .deb> tests/lab/dhcp_vars.yaml
   ```

   It copies both to the VM; generates the first Directory Administrator's password there
   (`/root/lab-admin-pw`, 0600; it never leaves the VM, and the campaign's console checks read it there); runs
   `apt-get install` of the package (its dependencies, Docker among them, from Ubuntu's archive through the router)
   and then `fabricctl setup --file /root/lab-vars.yaml --non-interactive --yes --approve all
   --admin-password-file /root/lab-admin-pw`. Images the lock marks pending (`config/images.lock.yaml`) are built
   by setup on the VM; the others are pulled from GHCR. Setup runs as `fabric-setup.service`, so a dropped SSH
   session does not stop it (3.3.1.1.6): `sudo fabricctl setup` on the VM follows it again. It accepts only an
   address of `10.88.0.0/24`. A fourth argument, lab only, is a script run as root on the VM between the package
   and setup: `scripts/lab/keep_converge_errors.sh` makes the domain's convergence keep its whole error output in
   `/root/converge-errors.log` (0600; it can hold a secret, so it is read on the VM and never copied off).
4. **Removing files:** never with `rm` on a path built from a variable that could be empty, and never through
   `wsl.exe bash -c '…'` with a path built on the Windows side; write the path out, or build it inside WSL and
   check it with `${VAR:?}` and that it lies under `/tmp` or the scratch folder (2.3.10.11.16: an empty variable
   removed WSL's `/bin`, `/lib`, `/lib64` and `/sbin`).
5. **Afterwards**: the VM back to `clean` (3.1.5.5) once the campaign is done; nothing of the install is kept.

## 3.1.5.10 The `dhcp` campaign (0.9.0)

What it proves is 1.10.4.39's list; the results of each run are notes in 2.3.10 (from 2.3.10.11.16). Every step from
gaming-23, as the agent (Hyper-V Administrators' rights, the lab key).

1. **Start it:** `powershell -ExecutionPolicy Bypass -File scripts\lab\start_lab.ps1 -Campaign dhcp` (rtr-1,
   ub24-1, kub26-1, w11-1; the lab's other VMs stopped). Note whether the router was running before: it is left as it
   was at the end.
2. **The router's relay** (allowed for this campaign, 2.1.1.64): on `g23-vm-rtr-1`,
   `sudo systemctl unmask isc-dhcp-relay && sudo systemctl enable --now isc-dhcp-relay`. Its settings are the
   router's own (`/etc/default/isc-dhcp-relay`, 3.1.5.7): to `10.88.0.10`, on `lab` and the three VLAN interfaces.
   Restoring the router's checkpoint (step 7) masks it again.
3. **fabric on `g23-vm-ub24-1`:** 3.1.5.9 with `tests/lab/dhcp_vars.yaml` (VLAN 10's subnet in the settings, moved
   into the plan by the first apply, 1.10.4.37).
4. **The clients' VLAN NICs:** `g23-vm-kub26-1`'s second NIC (MAC `02:88:00:1f:00:02`, VLAN 10) gets a DHCP
   connection; `g23-vm-w11-1`'s NIC with MAC `02-88-00-2A-00-02` (VLAN 20) is DHCP already. The lab NICs keep their
   static addresses, so SSH never depends on a lease.
5. **The checks:** from Git Bash, `tests/lab/dhcp_campaign.sh` (its header lists them, each 1.10.4.39's): the plan
   from the CLI (VLAN 20 added, a reservation, a name set by hand, options, a scan, Sync now, the plan poll) and
   from the console as a signed-in person (`tests/lab/dhcp_console.py`, run on the fabric VM), the clients' leases
   through the relay, their names and PTRs in fabric's DNS, ping-check, and the refusals.
6. **Record** each run in 2.3.10's notes: what passed, what failed with its output, what was not run and why.
7. **Put the lab back:** `start_lab.ps1 -Campaign none`, then every VM the campaign changed back to its checkpoint
   (`Restore-VMSnapshot -VMName <vm> -Name clean -Confirm:$false`: rtr-1, ub24-1, kub26-1, w11-1); start the router
   again if it was running before step 1.

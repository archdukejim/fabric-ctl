## 3.3.1.1 Run the Installer

From fabric's apt repository (signed; 2.1.1.2):

```bash
wget -qO- https://archdukejim.github.io/open-fabric/public.key | sudo gpg --dearmor -o /usr/share/keyrings/fabric-archive-keyring.gpg
```

```bash
echo "deb [signed-by=/usr/share/keyrings/fabric-archive-keyring.gpg] https://archdukejim.github.io/open-fabric stable main" | sudo tee /etc/apt/sources.list.d/fabric.list
```

```bash
sudo apt update && sudo apt install fabricctl    # installs the tool; changes nothing else
```

```bash
sudo fabricctl setup                              # installs fabric (or: --file vars.yaml)
```

Or the release's package by hand: `sudo apt install ./fabricctl_<version>_all.deb` (each GitHub Release carries it;
`packaging/deb/build-deb.sh` builds it from a checkout). One package serves amd64 and arm64. Installing it only adds `/usr/bin/fabricctl` and the code in `/usr/lib/fabricctl` — it never starts services or touches the network; `fabricctl setup` copies the code to `/opt/fabric` and does the rest. Example settings: `/usr/share/doc/fabricctl/examples/vars.yaml`.

**Upgrade:** `sudo apt update && sudo apt upgrade` (or install the newer `.deb`), then `sudo fabricctl setup`; until you do, every other command reminds you (`note: the fabricctl package is newer than the running install`). An upgrade that makes a host change the install has not had a yes for asks for it again, interactively, and an unattended setup stops naming the group to approve (`--non-interactive` then needs `--approve <group>`). An upgrade never changes the container images a host runs: `fabricctl images update` does (see [operations.md](../volume_4_operations/4.14.1-images.md#41411-fabricctl-images)). `apt remove fabricctl` removes the tool and leaves the running install alone. An install of 0.7.x is
not upgraded to 0.8.0: it moves by its settings file ([3.3.5](3.3.5-moving-to-080.md), 2.1.1.60); from 0.8.0 on,
releases upgrade in place again (2.1.1.61).

**From a git checkout (development):** `sudo scripts/install-from-checkout.sh [setup options]` builds the `.deb` from the checkout (`build-deb.sh`, needs `dpkg-deb`, `git` and `tar`), installs it with apt, then runs `fabricctl setup` with the options given (e.g. `--file custom-vars.yaml --non-interactive --yes`). Running it again upgrades the host to the checkout's current code. Afterwards use `sudo fabricctl …` as usual.

Setup is idempotent: change a setting and run it again; finished steps are quick, and certificates are only re-issued when missing, expiring within 30 days, missing a name or not from this CA.

### 3.3.1.1.1 The default plan

Setup asks only what cannot be changed later (2.1.2.16): the domain, the host's name (changed later if need be: it is no longer the domain controller's, 2.1.6.45), the organisation's name (it names the CA), the directory's AD domain (permanent; suggested: a sibling of fabric's domain, `lan.example.org` → `ad.example.org`; 2.1.6.11, [1.1.9.8](../volume_1_description_and_architecture/1.1.9-optional-parts.md#1198-the-directory-samba-ad-required)), the network (found and confirmed) and, on a new install, the first Directory Administrator: your own user name (never `fabric-admin`, which setup makes itself as the Enterprise Admin and break-glass account, nor another of fabric's names), your first and last names and, if you want, your e-mail address (2.1.6.93), and the password you will sign in with, typed twice and checked against the domain's password policy (2.1.6.69, [1.6.12.16](../volume_1_description_and_architecture/1.6.12-domain-management.md#161216-what-d2-built-080)); `--non-interactive` refuses without them, naming what is missing and why. The domain controller is never named to you and never asked: fabric names it, and a vars file that sets `dc_name` is refused for a new install; an installed DC keeps the name it has. The plan says how many domain controllers the domain uses and how many can still be added (a new domain: `1 DC used, 1998 can be added`; a site joining one hears its count at the join, 3.9.1) (2.1.6.65, [1.6.5.26](../volume_1_description_and_architecture/1.6.5-samba-dc.md#16526-dcs-numbered-dc-nnnn-each-with-its-own-id-range)). The rest takes defaults, changed after the install: the password policy starts from fabric's default (12 characters, complexity, 5 remembered, never expires, locked for 15 minutes after 10 failures in 15; 2.1.6.35; `sudo fabricctl domain password-policy`), fabric may use all of the host's memory (at least 4 GB, 2.1.2.3; every container's limit follows, 1.2.4.2), and sign-in with the domain logon (Kerberos) is off (2.1.6.32; the Security page).

Each question whose answer cannot be changed after the install shows a yellow **⚠ Permanent** after its label (the DNS domain, the organisation's name, the AD domain, and in Advanced the CA root's lifetime; uncoloured with `NO_COLOR` or without a terminal; 2.1.2.20). The others (the host's name, the network) can be changed later.

A new install starts with **[G]uided** (the questions above, one at a time; Enter), **[A]dvanced** (one numbered menu of every setting, among them the CA root's lifetime, fixed once the CA exists, 2.1.5.6; the optional parts; the memory; each recommended host change) or **[Q]uit** ([1.2.9.11](../volume_1_description_and_architecture/1.2.9-host-consent.md#12911-setups-start-guided-or-a-menu-of-every-setting-one-confirmation)). An upgrade or a re-run goes straight to the plan.

Every default is the hardened choice. The plan shows what setup will do, the memory split, and every change it makes to this host outside fabric's folders; **[P]roceed** is the one yes for all of them, **[M]enu** opens the menu to change anything, **[Q]uit** changes nothing. `--yes` or `--non-interactive` proceeds without asking (`--approve` / `--decline` answer the host changes).

| Setting | Default | Relaxing it means |
|---|---|---|
| `security.firewall` | on | UFW default-deny; fabric's ports from the LAN only, also enforced for Docker-published ports (`DOCKER-USER`, re-applied at boot by `fabric-firewall.service`). SSH stays allowed from the LAN, and from your current SSH client so setup cannot lock you out. `security.firewall_allow` adds CIDRs. |
| `security.docker_daemon_hardening` | on | `/etc/docker/daemon.json` gains `no-new-privileges`, `icc: false`, no userland proxy, `live-restore`, bounded logs (merged into what is there, never replaced). |
| `install_keycloak` | on | Keycloak SSO + Postgres (needed by the web UI) |
| `install_webui` | on | Web UI at `https://fabric-ctl.<domain>` (`webui_hostname`): client certificate + Keycloak login + TOTP. Forced off when Keycloak is off |

Optional services, off by default (turned on after the install in the settings, `sudo fabricctl`, or set in the vars file):

| Setting | What it needs | See |
|---|---|---|
| `install_kea` + `dhcp` | A preview until 0.8.0 (1.10.3.9). DHCP on this LAN with Kea: interface, subnet, address pool (default: the top quarter of the subnet) and router, suggested from the default route. Switch off your router's DHCP first | [operations.md](../volume_4_operations/4.10.1-dhcp.md#41011-dhcp-optional-kea) |
| `install_freeradius` | 802.1X with FreeRADIUS, reading the domain (Samba AD). Switches are added afterwards with `fabricctl radius add-client` | [operations.md](../volume_4_operations/4.11.1-radius.md#41111-8021x-optional-freeradius) |
| `install_fluentbit` + `log_forwarding` | Forward all logs with Fluent Bit: a syslog server `host[:port]` over TLS (port 6514 by default) and/or an Elasticsearch/OpenSearch URL and user; its password afterwards with `fabricctl logs set-password elastic` | [operations.md](../volume_4_operations/4.15.1-log-forwarding.md#41511-log-forwarding-optional-fluent-bit) |

Regardless of the plan, every container runs non-root with all capabilities dropped (the exceptions, Kea's DHCP
server and the Windows domain controller, are listed in [1.2.7](../volume_1_description_and_architecture/1.2.7-container-inventory.md)), `no-new-privileges` and a read-only root filesystem (see [architecture.md](../volume_1_description_and_architecture/1.2.4-containers.md#1241-container-hardening)).

Any of these can be set in the vars file and changed later by re-running setup.

### 3.3.1.1.2 Non-interactive install

```bash
sudo fabricctl setup --file vars.yaml --non-interactive --yes --approve all
```

`--non-interactive` never prompts and fails if a required value is missing or invalid (a new install needs the first Directory Administrator's `webui_admin_user`, `webui_admin_first_name` and `webui_admin_last_name` (and optionally `webui_admin_email`) in the vars file and their password from `--admin-password-file FILE`, checked against the password policy, never on the command line: 2.1.6.69; `fabric-admin`'s password is generated and written to its file as in an interactive setup; Kerberos sign-in stays off, 2.1.6.32); `--yes` accepts the plan; `--approve` allows the host changes (below) without asking — `--yes` alone approves none.

### 3.3.1.1.3 Changes to the host: asked first

Before its first step, setup lists every change it would make **outside fabric's own folders**, by group, and asks a yes/no for each ([host-consent.md](../volume_1_description_and_architecture/1.2.9-host-consent.md#1291-status)):

| Group | What changes | If you say no |
|---|---|---|
| `packages` | apt packages, from the host's own sources (fabric adds none) | setup stops |
| `runtime` | `/etc/docker/daemon.json` hardening and one Docker restart (every container on the host restarts once) | Docker is not hardened (shown in status) |
| `services` | fabric's own systemd units (`fabric.target`, one per service, `fabric-agent`, `fabric-*` timers) | setup stops |
| `accounts` | the service users and groups `fabric-*` in the uid band 600–649 | setup stops |
| `resolver` | systemd-resolved's stub listener off (only with `use_host_dns: false`) | choose `use_host_dns: true` |
| `firewall` | ufw on with incoming denied, and each rule fabric adds | the firewall is not managed (shown in status) |
| `trust` | fabric's CA in the host's trust store | the host does not trust fabric's CA (shown in status) |
| `time` | chrony's configuration | chrony keeps its own configuration (shown in status) |

Answers are recorded in `config/consent.yaml`; a re-run asks again only about changes not approved before. `apply`, the web UI and the timers never ask: a change that needs a new answer waits for `sudo fabricctl setup`. `fabricctl status` and the web UI's Overview list the answers.

Before fabric first changes a host file (`daemon.json`, chrony's files, `/etc/resolv.conf`) it keeps a copy in `config/host-originals/`, and it notes whether ufw was on. `sudo fabricctl setup --undo GROUP` reverts one recommended change (`runtime`, `firewall`, `trust`, `time`; `resolver` once `use_host_dns` is true), says what it will do and asks first (`--yes` unattended), then records the answer as no; `--approve GROUP` makes the change again. The groups fabric needs (`packages`, `services`, `accounts`) are undone only by uninstall.

### 3.3.1.1.4 Options

| Option | Meaning |
|---|---|
| `--file <path>` | Settings to apply (overrides the existing install's values for the keys it sets) |
| `--non-interactive` | Never prompt |
| `--yes`, `-y` | Accept the plan without asking (approves no host change) |
| `--approve <groups>` | Allow these host changes without asking (comma-separated, repeatable, or `all`) |
| `--decline <groups>` | Refuse these host changes (recommended ones are then left unmanaged and shown in status) |
| `--undo <group>` | Revert one host change fabric made and record it as declined; nothing else runs (above) |
| `--offline` | Never download; packages and images must already be present |
| `--deploy-base <dir>` | Install root (default `/opt`) |
| `--step <name>` | Run only this step (repeatable); the plan is not shown. An unknown name is refused |
| `--list` | List the steps |
| `--restart` | Start over with the questions and every step, though the last run did not finish (without it, setup resumes that run: 3.3.1.1.6) |
| `--join [@FILE \| -]` | Join an existing fabric as a new site (a fresh install only). The invitation is pasted at a hidden prompt, read from `@FILE` or from stdin (`-`); never on the command line, which every user on the host can read: see [Joining an existing fabric](3.9.1-joining.md#3911-joining-an-existing-fabric-a-new-site) |

After setup, `sudo fabricctl doctor` re-runs the end-to-end checks at any time. When a step fails, setup stops there with the reason (exit 1; some errors show a Python traceback instead): fix it and run setup again. Interrupted, it exits 130.
Since 0.8.0 the steps run as `fabric-setup.service` and running setup again resumes from the step that stopped
(3.3.1.1.6).

### 3.3.1.1.6 A dropped connection: the work goes on (0.8.0)

Setup asks its questions in your session; once you answer the plan's **[P]roceed** (or `--yes`), the work goes to
systemd as `fabric-setup.service` and your session only shows its progress (design
[1.3.2.3](../volume_1_description_and_architecture/1.3.2-setup-design.md#1323-setups-work-survives-a-dropped-session-080),
decision 2.1.2.26):

```
  · setup's work runs as fabric-setup.service: a dropped connection does not stop it
    Ctrl-C stops following, not the work; sudo fabricctl setup follows it again
```

- **The connection drops, or you press Ctrl-C:** the work goes on. Ctrl-C says so and exits 130.
- **Follow it again** (no questions are asked while it runs; it shows the run from its start):

```bash
sudo fabricctl setup
```

  It ends as the run ends: *fabric is ready* and exit status 0, or the step's error and 1. systemd's own lines
  (the unit starting and ending): `journalctl -u fabric-setup`. The run's whole output stays in
  `/opt/fabric/config/setup-run.log` (the run before it: `setup-run.log.1`).
- **The run stopped before it finished** (a step failed, or the host restarted): fix what the error names and run
  `sudo fabricctl setup` again. It resumes from the step that stopped, without the questions, except the first
  admin's password or the join invitation when a step still ahead needs it. To answer the questions again from the
  start: `sudo fabricctl setup --restart` (a `--file` or `--join` run also starts over).
- **Unattended** (`--file … --non-interactive --yes`) takes the same path; its exit status is the run's.
- `--step`, `--undo` and `doctor` still run in your session.
- Uninstall stops a running setup first ([3.2.4](3.2.4-reinstall-uninstall.md)).

# 3.14.1 Building fabric's images

Topics:

- 3.14.1.2 Building by hand

- 3.14.1.4 Publishing

Status: **built 2026-10-03** (decision 2.1.1.21; proposal 2.3.14.1, 2.1.14.5, 2.1.14.6, 2.1.14.7, 2.1.14.8, 2.1.14.9): the build matrix, the smoke test, the CI
build on both architectures, the signed publishing and the release promotion. How hosts use the images: 1.14.3.

## 3.14.1.1 What is built

Seven images, each for `linux/amd64` and `linux/arm64` (2.1.1.11; `adguard` until 0.7): `bind9`, `freeradius`, `kea`,
`keycloak`, `samba`, `stepca` and `webui`. Their build files are in `packaging/images/<name>/`; a host installs the
same folders as `jinja/<name>/build/` (1.2.2), and `packaging/images/stage-contexts.sh` stages them from the
assembled tree so a published image is built from exactly what a host would build from (the web UI's with its app
in `app/`).

Every input is pinned: the bases by digest and Kea's package by version and signing key, all from
`config/images.lock.yaml` (`packaging/images/bake_env.py` prints them); no Dockerfile has a default base, so an
unpinned build fails at its `FROM`. The service account ids are the Dockerfiles' defaults (600–649, 2.1.2.4); a host
with other ids builds that image itself (P1, 2.1.14.5).

## 3.14.1.2 Building by hand

Any machine with Docker (global Rule 7.2). One image with a plain `docker build`:

```bash
bash packaging/images/stage-contexts.sh build/contexts
```

```bash
docker build --build-arg BASE_IMAGE="$(python3 packaging/images/bake_env.py | sed -n 's/^BASE_DEBIAN=//p')" -t fabric/bind9:local build/contexts/bind9
```

`bind9`, `freeradius`, `kea`, `samba` and `webui` build FROM `BASE_DEBIAN`; `stepca` and `keycloak` FROM
`BASE_STEPCA` and `BASE_KEYCLOAK`; `kea` also takes the `KEA_*` values
(`packaging/docker-bake.hcl`). All eight at once, for this machine's platform:

```bash
bash -c 'set -a; . <(python3 packaging/images/bake_env.py); CONTEXTS=build/contexts; set +a; docker buildx bake -f packaging/docker-bake.hcl --load'
```

Then smoke test one: `bash packaging/images/smoke-test.sh bind9 ghcr.io/archdukejim/fabric-ctl/bind9:dev`. The
`images` suite (3.1.2) does all of this and checks the build inputs against a default host's compose files.

## 3.14.1.3 In CI

The `images` workflow (`.github/workflows/images.yml`) runs on every push and pull request that touches an image's
inputs: it builds the eight images on GitHub's native runners, `ubuntu-24.04` and `ubuntu-24.04-arm` (P3, 2.1.14.7: no
emulation), and smoke tests each one. The smoke test (`packaging/images/smoke-test.sh`) runs the image's program as
its service account with every capability dropped, no-new-privileges, a read-only root and no network, and checks
the labels hosts read (`org.fabric.base`, `org.fabric.ids`). Whether each service then works is proven by the
suites before a release (Rule 9; 3.1.2): `hardening`, `kea`, `freeradius`, `samba`, `resolver` and the sandbox.

## 3.14.1.4 Publishing

By hand, from `main` or a release-candidate branch `rc/<version>` (decision 2.1.14.9; Actions → images → Run workflow,
with **publish** ticked). `<version>` is `config/VERSION`; an rc branch must be named for it.

1. Each runner pushes its architecture as `<tag>-amd64` / `<tag>-arm64` to `ghcr.io/archdukejim/fabric-ctl/<name>`
   (2.1.1.19), with the repository's own token. The tag is `<version>` from main and `<version>-rc.<run number>` from an
   rc branch.
2. One job joins them into one multi-arch image, `<name>:<tag>`, and signs its digest with cosign, keyless (P2,
   2.1.14.6): the signer is the workflow's GitHub identity on that ref, recorded in Sigstore's public transparency log;
   there is no key to keep. The run's summary names the tag and lists the digests.
3. Pin them, on the rc branch, with a reviewed commit (2.1.14.4):

```bash
python3 scripts/images/pin_published.py 0.6.0-rc.1
```

   It refuses an image without both architectures or without a valid signature by fabric's workflow (the check
   hosts make), and writes nothing then. Then run the suites and the sandbox, which now pull the pinned images.
   An image that is new or rebuilt on a branch is marked `pending: "<why>"` in the lock, with an empty digest, until
   this step pins it (and drops the mark): hosts build a pending image themselves, and the `images` suite refuses an
   empty digest without the mark. Pinning also records each image's source hash (2.1.14.13), so pin from the
   commit the publish ran on. When a change touches an image's sources, the `images` suite fails until that image
   is unpinned and marked pending; `python3 scripts/images/source_hash.py --check` names them.
4. **The apt path, before the release:** run the `package` workflow by hand on `rc/<version>` with
   **apt_testing** ticked: the candidate's `.deb` goes to the apt repository's `testing` suite (`stable` keeps the
   released ones); install it on a test host from `… testing main` and run setup there.
   **The upgrade test** (2.1.1.36, 2.1.1.61): from 0.8.1 on, the candidate upgrades in place on the test Pi from the
   floor, 0.8.0 until 1.0, and from the previous release when it differs (`tests/host/upgrade.sh FROM=0.8.0`, then
   `FROM=<previous>`; a `FROM` older than the floor is refused before the host is reached). **0.8.0 has no upgrade
   test:** nothing upgrades into it (2.1.1.60); its **move test**, `sudo tests/sandbox/move.sh`, takes the place of the
   upgrade from 0.7.1: 0.7.1 built from its tag and set up in a sandbox, its settings file imported into a fresh 0.8.0
   with `setup --file` as 3.3.5 says, and the same zones, records, TSIG keys' rights and parts checked.
   **The rehearsal** (2.1.1.54), by the agent before the owner's own test install: on the test Pi, purged, from
   `testing`, every setup route — unattended (`APT_SUITE=testing tests/host/run.sh`) and interactive, Guided then
   Advanced with every default left (`tests/host/installer.py`) — then the landing page and the console checked as a
   user would. The Pi is left purged with only `fabricctl` installed; the owner's install comes after a clean
   rehearsal.
5. **The owner merges** the pull request `rc/<version>` → main (the agent never merges). With step 1–4 and the tests,
   that is what `/rc` does: it ends by opening that pull request (2.1.1.40).
6. **Tag the candidate on main**, `v<version>-rc.<n>` (`/tag`; `<n>` counts the version's rc tags from 1): on the merge
   commit, once main's CI is green. The `package` workflow makes it a GitHub **pre-release** with the `.deb` (apt is
   left alone: stable never takes a pre-release), and the `promote` job verifies the digests the lock pins and tags
   them `<version>-rc.<n>`. Test installs use that pre-release's `.deb`. A fix goes through `rc/<version>` and a
   pull request again, then the next `-rc.<n+1>`.
7. **Promote** (`/promote`): tag `v<version>` on the same commit as the last rc tag. The tag builds no image: the
   `promote` job verifies the digests the tagged lock pins and tags those same digests `<version>`, so a release runs
   exactly what its candidate tested (1.14.3.6). The `package` workflow attaches the `.deb` to the Release and
   rebuilds the apt repository: `stable` from every full Release's `.deb` of its own version (pre-releases, everything
   before 0.6.1 (2.1.1.32), are left out: v0.5.0's asset is the 1.5.0 it was built as before the renumbering, which
   outranked 0.6.1 at the first tag), `testing` from the tag's.

**The apt repository** (2.1.1.2, 1.3.1.1) is built with reprepro (`packaging/apt/`) and published, alone, to the
`gh-pages` branch, which GitHub Pages serves (turned on once in the repository's Pages settings: branch `gh-pages`,
root). It is signed with a dedicated key the owner makes once with `scripts/release/make-apt-key.sh`, which stores
it in the Actions secrets `GPG_PRIVATE_KEY` and `GPG_PASSPHRASE` (run from Git Bash on the owner's PC, in the
repository's folder). GitHub never gives a secret back, so the script also writes the offline copy to the folder
the owner names (a USB stick): the private key encrypted with its passphrase, the passphrase, the revocation
certificate and the public key. With it the key's two-year expiry is extended (`gpg --quick-set-expire`, then
the secrets set again) or a lost secret restored; without it, a new key, which every host fetches again.

The first publish of an image creates its package as private: make it **public** once in the repository's Packages
settings (P4, 2.1.14.8), so hosts pull without credentials.

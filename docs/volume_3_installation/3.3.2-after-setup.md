## 3.3.2.1 CA certificates for your devices

Setup's last words give the order (2.1.1.41): **first** the root certificate from `http://info.<domain>/certs/` (or `http://<host_ip>/certs/`), with the SHA-256 fingerprint it must show; then the client certificate from the login kit when the web console asks for one; **then** sign in at `https://fabric.<domain>` with the password you chose in setup (2.1.6.33); after Guided setup, until it is done, **finish setting up** in the console's Settings, which opens at that first sign-in (the setup wizard, [4.8.3](../volume_4_operations/4.8.3-setup-wizard.md#4831-finish-setting-up-or-reconfigure-in-the-console)). On a new device, start at **`http://info.<domain>/`** (or **`http://<host_ip>/info/`**, which needs no DNS and stays whatever is done to the `info` record, 1.4.2.5; plain HTTP works: the device does not trust fabric's CA yet): download the root certificate from its `/certs/`, check it against the SHA-256 fingerprint the page shows, and install it (1.4.2.3). `http://info.<domain>/certs/` (and `https://`; `certs.<domain>` until 0.7.0, 1.5.1.5) lists the root and intermediate CA certificates with their fingerprints, per-system instructions and every format:

| File | Format | For |
|---|---|---|
| `root-ca.cer`, `intermediate-ca.cer` | DER | Windows |
| `root-ca.crt`, `intermediate-ca.crt` | PEM | Linux, macOS, iOS, Android |
| `root-ca.pem`, `intermediate-ca.pem` | PEM, shown as text | copy & paste into network devices |
| `root-ca.der`, `intermediate-ca.der` | DER | devices that want a binary certificate |
| `ca-chain.p7b` | PKCS#7 (root + intermediate) | Windows, Java, many appliances |
| `ca-chain.pem` | PEM bundle (intermediate, then root) | devices that import a chain |
| `ca-certs.json` | subjects, validity, SHA-256/SHA-1 fingerprints | scripts |

`https://ca.<domain>/` is Step-CA's API (ACME: `https://ca.<domain>/acme/acme/directory`); opened in a browser it redirects to the certificate page. The files are re-published on every setup run.

## 3.3.2.2 The login kit

With the web UI enabled, setup finishes by creating your first admin and leaving everything your computer needs in `~/fabric-admin/` (of the account that ran `sudo`): the client certificate `<user>.p12` and its password (while the console asks for one), the fabric root CA (`.crt`, and `.cer` for Windows) and a README with the remaining steps: copy the folder to your computer, trust the CA, import the `.p12`, open `https://fabric.<domain>`. Details: [webui.md](../volume_4_operations/4.6.3-first-sign-in.md#4631-first-time-setup).

On this host setup already trusts the fabric CA (`/usr/local/share/ca-certificates`), and every service has its certificate from it.

## 3.3.2.3 Running it: systemd

Every service is its own systemd unit, all grouped under **`fabric.target`**, which is enabled at boot:

```bash
sudo fabricctl status            # the target, every unit and its container health
sudo fabricctl stop              # = systemctl stop fabric.target (every fabric service)
sudo fabricctl start             # returns once every service is up and healthy
sudo fabricctl restart
systemctl status fabric-web      # one service
```

Units: `bind9`, `stepca`, `nginx`, `samba`, `postgres`, `keycloak`, `openbao`, `fabric-agent`, `fabric-web`; with the optional services `kea`, `freeradius`, `fluentbit`. `fabric-firewall` re-applies the firewall rules at boot. `openbao` starts only when an unlock method is present (see [operations.md](../volume_4_operations/4.7.1-openbao.md#4711-openbao-secrets)).

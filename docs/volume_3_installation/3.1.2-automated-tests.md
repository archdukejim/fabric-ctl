## 3.1.2.1 Running them

The suites live in `tests/<domain>/`, one per area, and run against real containers (the global Rule 9; the
layout is deviation 2.1.1.29): `sudo tests/run-all.sh [suite …]`, every suite when none is named. `tests/README.md`
lists what each suite proves. Moved from `AGENTS.md` §6 on 2026-10-03.

## 3.1.2.2 What a change needs

- Behaviour is proven against **real containers**, not mocks, wherever a container is involved (2.1.1.27 lists the only
  stand-ins).
- Every feature adds to or extends a suite, including the refusal and security cases (what must be refused).
- A change is not done until the relevant suites, and `ruff` and `shellcheck` (2.1.1.15), pass; results are reported
  faithfully, including what was not run (global Rule 9).

## 3.1.2.3 Lint

The `lint` suite (`tests/lint/run.sh`, also the `lint` workflow in GitHub Actions on every push and pull request)
runs ruff, shellcheck and Python 3.10 from their published images, pinned by digest, so nothing is installed on the host:

- **ruff** on `src/`, `scripts/` and `tests/` with the rules in the root `pyproject.toml`: pycodestyle and pyflakes,
  120 characters per line — except in `tests/`, whose one-line check messages may be longer.
- **shellcheck** at warning level on every shell script: the product's (`src/`, `packaging/`, `scripts/`) with no
  exception; the tests' with three exceptions their `eval`-run checks cause (SC2034, SC2097, SC2098).
- **Python 3.10** (`tests/lint/parse_py.py`, in a pinned `python:3.10-slim`) parses every file in `src/` and
  `scripts/`: the oldest supported host, Ubuntu 22.04, runs 3.10 (2.1.1.43), and ruff, which parses with the newest
  grammar whatever its target, cannot catch syntax only 3.12 accepts.
- **No bare prompts** (`tests/lint/no_bare_prompts.py`, in the same image): no `input()` or `getpass()` in `src/`
  outside `fabriclib/common/ask.py`, and every `ask()` / `ask_secret()` names its question with a literal
  `<area>.<name>` ID (1.1.5.6); read from the syntax tree, so comments and docstrings never count.

Templates (`*.sh.j2` and the like) are not linted: they are not code until rendered (global Rule 1).

## 3.1.2.4 In CI

The `suites` workflow (`.github/workflows/suites.yml`, decision 2.1.1.37) runs every suite of `tests/run-all.sh` on
GitHub's `ubuntu-24.04` (amd64) and `ubuntu-24.04-arm` (arm64) runners: one job per suite and architecture, named
`<suite> (<arch>)`, on every push and pull request. Nightly (03:17 UTC), by hand (`gh workflow run suites.yml`) and on
a pull request to main it also runs the sandbox, kept, and the image-update test on it (`sandbox and image update
(<arch>)`). Each job keeps its suite's log as an artifact for 30 days; never the rest of `/tmp/fabric-tests`, which holds the
run's keys and secrets.

The owner's merge to main waits for these checks (global Rule 8): which ones are required is set in the repository's
branch protection for `main` (*Settings → Branches*), by the owner. A suite a hosted runner cannot host is reported
skipped by the suite, with the reason, never passed silently.

## 3.1.2.5 The entry-point inventory

Every way a person or client puts something into fabric (global Rule 9) is listed, generated from the code, and each
needs a positive and a negative test (decisions 2.1.1.38, 2.1.1.46). **Status: designed 2026-10-10, being built for
0.9.**

3.1.2.5.1 **The inventory.** `python3 scripts/docs/entrypoints.py` writes `tests/entrypoints.yaml`, one entry per
entry point, with its kind and where it is declared; the docs suite fails when the committed file differs from what
the script generates. Its IDs:

| Kind | ID | Read from |
|---|---|---|
| command | `cli:<command>[.<sub>]`, e.g. `cli:dhcp.on` | `fabricctl`'s top-level commands (`fabriclib/cli.py`) and each `run_*_command.py`'s `USAGE` (every one has a `USAGE`, argparse ones included) |
| question | `ask:<area>.<name>`, e.g. `ask:setup.ad_domain` | every prompt goes through `ask()` with a stable ID (1.1.5.6) |
| agent route | `agent:<get\|post>.<segments>`, e.g. `agent:post.dhcp.on` | the permission table (`rbac/required_permission.py`), the routes' one list |
| web page or form | `web:<get\|post>.<path>`, e.g. `web:post.bind9.tsig.*.rotate` | the pages of `webui/routes/get_page.py` and the forms' `action` in `templates/webui-app/`, placeholders as `*` |
| setting | `setting:<key>`, e.g. `setting:dhcp` | the top-level keys of `templates/vars.yaml.j2` |

3.1.2.5.2 **Coverage markers.** A test claims an entry point with a comment beside the check:
`# covers: cli:dhcp.on +` for the positive case, `-` for the negative (several IDs may share one marker). A setting
whose value cannot be wrong (free text with no rule) is listed in `tests/entrypoints-reasons.yaml` with the reason,
instead of a negative case; that list is reviewed like code.

3.1.2.5.3 **The check** (in the docs suite) fails when: an entry point lacks a case and is not in
`tests/entrypoints-gaps.txt`; a listed gap is now covered (remove it) or names nothing; a marker names an entry point
that does not exist; the inventory is stale. `scripts/docs/entrypoints.py --gaps` prints the current gaps, which is how
the list is first written and how it shrinks.

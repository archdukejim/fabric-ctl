# 3.14.2 Offline install from a bundle

Topics:
- 3.14.2.1 Making a bundle
- 3.14.2.2 Installing from a bundle
- 3.14.2.3 Moving a host to Docker's containerd image store
- 3.14.2.4 Refreshing the trusted root

Status: **0.13.0** (design 1.14.4, decisions 2.1.14.14, 2.1.14.16, 2.1.14.17): a bundle carries fabric's `.deb`,
the Ubuntu packages it and setup install, and every image, so the offline host needs only Ubuntu.

## 3.14.2.1 Making a bundle

On a machine with internet and Docker, with the fabric package of the release you will install (`fabricctl`, set up
or not), for the offline host's architecture (`dpkg --print-architecture` there) and Ubuntu release
(`. /etc/os-release; echo $VERSION_ID` there):

```bash
sudo fabricctl images export --arch arm64 --ubuntu 24.04 -o /var/tmp/fabric-0.13.0-arm64.tar
```

`--ubuntu` defaults to the exporting machine's release. It takes the space of every image for that architecture
(about 2.5 GB) and the packages (about 150 MiB) plus the largest image again while it is added, and refuses before
it starts when that is not free. The `.deb` is the release's, checked against fabric's signed apt repository; for
a version not released, `--deb <file>` carries a `.deb` you built instead, a relaxation the export, the import and
the host's status then show (1.14.4.10). A release whose images are not all published is
refused, naming them (1.14.4.2); `--allow-unpublished` leaves them out instead, a relaxation the host then shows
(1.14.4.9): it must build them itself, which needs the internet. Note the bundle's sha256 (`sha256sum`) and carry
both to the host.

## 3.14.2.2 Installing from a bundle

On the offline host (Ubuntu 24.04, 26.04 or 22.04, 3.2.1):

1. Check the bundle you carried: `sha256sum fabric-0.13.0-arm64.tar` is the one you noted.
2. Install `fabricctl` from the bundle's own packages, as a local apt source used for this one install (1.14.4.10;
   the host's apt sources are not changed, and apt checks Ubuntu's signatures and every package's hash):

   ```bash
   sudo mkdir -m 755 /var/tmp/fabric-apt && cd /var/tmp/fabric-apt
   sudo tar -xf /var/tmp/fabric-0.13.0-arm64.tar ubuntu deb
   for d in ubuntu/dists/*; do
     echo "deb [signed-by=/usr/share/keyrings/ubuntu-archive-keyring.gpg] file:/var/tmp/fabric-apt/ubuntu ${d##*/} main universe"
   done | sudo tee bundle.list
   sudo mkdir -p lists/partial cache/archives/partial parts sources.d
   printf '%s "%s";\n' Dir::Etc::SourceList "$PWD/bundle.list" Dir::Etc::SourceParts "$PWD/sources.d" \
     Dir::Etc::Parts "$PWD/parts" Dir::State::Lists "$PWD/lists" Dir::Cache "$PWD/cache" \
     Acquire::By-Hash no Acquire::Languages none | sudo tee apt.conf
   sudo env APT_CONFIG="$PWD/apt.conf" apt-get update
   sudo env APT_CONFIG="$PWD/apt.conf" apt-get install --no-install-recommends ./deb/fabricctl_*_all.deb
   cd / && sudo rm -rf /var/tmp/fabric-apt
   ```

   `apt.conf` makes apt read only this source and none of the host's apt settings (`/etc/apt/apt.conf.d`, whose
   hooks, such as command-not-found's, would ask for indexes the bundle does not carry). `apt-get update` must
   report no error. A host already running `fabricctl` of this version skips this.
3. Docker must use the containerd image store: `docker info -f '{{json .DriverStatus}}'` names
   `io.containerd.snapshotter.v1`. A Docker installed for fabric on a new host does; otherwise 3.14.2.3.
4. Install:

   ```bash
   sudo fabricctl setup --offline /var/tmp/fabric-0.13.0-arm64.tar --file custom-vars.yaml
   ```

   Its `host` step installs Docker and the host's packages, and its `member` step the domain member's, from the
   bundle's packages in the same way (after the `packages` consent, 1.2.9); its `bundle` step checks the bundle and
   loads the images (1.14.4.4). A refusal says why and loads nothing (cosign alone may have been loaded when a
   signature is refused). Every setup option works as online (3.3.1).

To load the images first and set up later, `sudo fabricctl images import <bundle>` does the same check and load;
setup's `bundle` step then finds them present and loads nothing.

**Upgrading an offline host**: install the newer bundle's `.deb` as in step 2, then `sudo fabricctl setup --offline <its bundle>`; the
bundle must be for the package's version, not the running one's.

## 3.14.2.3 Moving a host to Docker's containerd image store

The import refuses a host whose Docker keeps images in the classic store (1.14.4.5). Switching stores leaves the
classic store's images behind (Docker no longer sees them, and they still take their space), so do it before
fabric runs on the host, or with fabric stopped:

```bash
sudo systemctl stop fabric.target
sudo python3 -c 'import json,os; p="/etc/docker/daemon.json"; d=json.load(open(p)) if os.path.exists(p) else {}; d.setdefault("features", {})["containerd-snapshotter"]=True; d.pop("storage-driver", None); json.dump(d, open(p,"w"), indent=2)'
sudo systemctl restart docker
docker info -f '{{json .DriverStatus}}'
```

The last line must name `io.containerd.snapshotter.v1`. Then install from the bundle (3.14.2.2, step 4), which also
starts fabric again. The classic store's old images stay in `/var/lib/docker` until removed by hand.

## 3.14.2.4 Refreshing the trusted root

The package ships Sigstore's trusted root (1.14.4.6). When the images suite says it is no longer current, or
Sigstore announces a key change, on a branch:

```bash
python3 scripts/images/trusted_root.py
```

then review the diff of `config/sigstore-trusted-root.json` and commit it, as for a change of the cosign pin.

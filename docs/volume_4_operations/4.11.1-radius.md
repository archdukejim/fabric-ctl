## 4.11.1.1 802.1X (optional: FreeRADIUS)
Off unless turned on later in the settings (`sudo fabricctl`, then applied) or with `install_freeradius: true` (2.1.2.16).
It asks the site's domain controller (AD), part of every install. FreeRADIUS 3.2 answers your
switches and access points on UDP 1812 (accounting 1813, acknowledged and
not stored) at the host IP.

**Who may join** is decided per device in the directory (Directory tab →
Devices and Roles), on every request:

- **EAP-TLS** — the device presents a certificate from the fabric CA that is
  *linked* to it (issued or signed for the device on the Step-CA tab, or
  linked on its page), and one of its roles grants `network:eap-tls`.
  Supplicants should check the server certificate `radius.<domain>`
  against the fabric root CA.
- **MAB** (printers, cameras, IoT without a supplicant) — the switch sends
  the device's MAC; one of its roles grants `network:mab`. A MAC can be
  copied, so give MAB roles a restricted VLAN.
- **People and Windows machines by password (EAP-TTLS or PEAP)** — PEAP is
  what Windows offers by default; a domain machine signs in with PEAP as
  itself before anyone logs on, if one of its groups is mapped (for example
  `fabricctl radius map-group "Domain Computers" --vlan 40`) and it is in
  this site's machines. A person's user name and password,
  inside a TLS tunnel to `radius.<domain>`, checked against the domain (AD):
  the domain's lockout counts network logins, and a person still on their
  one-time password signs in to the web UI first to set their own.
  Only members of the groups you map may join, each group with an optional
  VLAN. A mapping names a group fabric manages (a site's or the
  organisation's, or `users` for everyone); AD's own groups such as
  `Guests` never match. Mapped at first: the directory groups `network-staff` and
  `network-guests`, both empty and without a VLAN — nobody can join by
  password until someone is added to one (in Keycloak). Give
  `network-guests` its guest VLAN before using it:
  `fabricctl radius map-group network-guests --vlan 50 --priority 100`.
- **Default device roles** — a new install starts with `workstations`,
  `phones-tablets`, `servers` (EAP-TLS), `printers`, `iot` (MAB) and
  `network-gear` (SCEP), without VLANs and without devices. They are created
  once: edit or delete them like any role; setup never brings one back.
- **VLAN** — from the device's role (or the person's mapped group) with the
  lowest priority number that sets one (none: the switch port's default).
- **Refused**: a disabled device, an unlinked certificate, a certificate
  from another CA, a role without the permission, a wrong password or a
  locked account, a person in no mapped group, a password sent outside the
  tunnel, and everything while the directory cannot be asked (fail closed). Disabling a device or unlinking a
  certificate takes effect at its next authentication.

RADIUS clients (the switches and access points that ask):

```bash
sudo fabricctl radius add-client switch1 192.168.4.2 --vendor unifi   # prints its shared secret once
sudo fabricctl radius add-client aps 192.168.10.0/24 --secret-prompt   # keep a secret they already have
sudo fabricctl radius set-client switch1 --vendor cisco --transport radsec   # vendor: unifi | cisco | generic
sudo fabricctl radius rotate-secret switch1                  # new secret, shown once (--secret-prompt: give one)
sudo fabricctl radius remove-client switch1
sudo fabricctl radius map-group staff --vlan 20              # staff may join by password, on VLAN 20
sudo fabricctl radius map-group visitors --vlan 50 --priority 60   # priority default 100
sudo fabricctl radius unmap-group visitors
sudo fabricctl radius status                                 # server name, clients, groups that may join by password
sudo fabricctl radius log -n 100                             # recent decisions (default 50): accepted / refused and why
sudo fabricctl radius sessions                               # open sessions (4.11.1.4)
```

Each client names its **vendor** (`unifi`, `cisco`, or `generic`, the default): it decides how fabric reads its MAB
requests, whether RadSec and CoA are offered, and which setup page applies (1.11.1.2; 4.11.1.2, 4.11.1.3).

Every change is saved and applied at once (FreeRADIUS restarts); `--no-apply`
records it only (apply later with `sudo fabricctl --apply`). A secret is
never taken on the command line: `--secret-prompt` asks for it, hidden.
`add-client … --no-message-authenticator` is the command-line form of
`message_authenticator: false` (below).

Or in `vars.yaml` (re-run setup): `radius_clients: [{name: switch1, address:
192.168.4.2}]`. Secrets live in OpenBao (`radius_secrets`); a `secret:`
written in the vars file is moved there. Every client must send a
Message-Authenticator (BlastRADIUS, CVE-2024-3596); set
`message_authenticator: false` only for a device that cannot, and it shows
on the FreeRADIUS tab. Clients outside the LAN are let through the
firewall to the RADIUS ports only.

Step-by-step setup for switches (UniFi included) and Windows PCs, with
this install's values filled in and a generated Windows setup script per
method, is on the FreeRADIUS tab: **Connect a switch** and **Connect
Windows**.

Password logins, things to know: the directory's lockout counts them (5
wrong passwords lock the account for 15 minutes — someone at any port can
lock a person out by guessing), and there is no second factor. Map only
the groups that need it; devices are better served by certificates.
Supplicants must be set to check the server certificate (`radius.<domain>`,
fabric root CA) — otherwise a rogue access point could collect passwords.
Windows offers PEAP by default, which fabric answers through the domain;
EAP-TTLS needs a profile on Windows.

## 4.11.1.2 Connecting UniFi switches and access points

Built 2026-10-12 for 0.9, **untested with UniFi hardware** (2.3.11.5); the console's **Connect a switch → UniFi**
shows the same steps with this install's values. Menu names follow UniFi Network 8/9 and may differ in yours.

1. **In fabric:** FreeRADIUS tab → Overview → RADIUS clients → add the switch (or access point) by its management IP,
   vendor **UniFi**, transport **RADIUS/UDP**; or `sudo fabricctl radius add-client switch1 192.168.4.2 --vendor
   unifi`. Keep the shared secret it shows once. The client is then listed under relaxed settings (RADIUS/UDP
   protects its secret with MD5 only, 1.11.1.3): keep the switch's management on a trusted LAN.
2. **UniFi Network → Settings → Profiles → RADIUS → Create New:** name `fabric`; authentication server the fabric
   host's address, port 1812, the shared secret; accounting server the same address, port 1813, the same secret, with
   interim updates (fabric's Sessions view is built from accounting); turn on wired networks and RADIUS-assigned VLAN.
3. **Settings → Networks:** the VLANs that fabric's device roles and mapped groups name, with the same numbers.
4. **Devices → the switch → Settings → Services → 802.1X Control:** on, RADIUS profile `fabric`; fallback VLAN empty
   (refused devices get nothing) or a guest VLAN.
5. **The switch → Ports:** `Auto` for 802.1X devices, `MAC-based` for printers and IoT, `Force Authorized` for
   uplinks, access points, the fabric host's port and the UniFi console's.
6. **Wi-Fi:** a WPA2/WPA3-Enterprise network with the `fabric` profile; MAB on Wi-Fi is UniFi's *RADIUS MAC
   Authentication* (any MAC format: fabric reads them all).
7. **Check:** FreeRADIUS tab → Recent decisions (or `sudo fabricctl radius log`).

What differs for UniFi: a MAB request carries the MAC as both user name and password, and fabric refuses one whose
password is not that MAC. **No CoA:** Disconnect and Re-authenticate are refused for UniFi clients with the reason;
to cut a device off at once, disable it (Directory tab), then *Client Devices → the client → Reconnect* in UniFi
Network. **No RadSec** for UniFi yet (2.1.11.5).

## 4.11.1.3 Connecting Cisco Catalyst switches (IOS-XE)

Built 2026-10-12 for 0.9, **untested with Cisco hardware** (2.3.11.5). Add the switch with vendor **Cisco**:

```bash
sudo fabricctl radius add-client core-sw 192.168.4.5 --vendor cisco                    # RADIUS/UDP
sudo fabricctl radius add-client core-sw 192.168.4.5 --vendor cisco --transport radsec # RadSec (TCP 2083)
sudo fabricctl radius set-client core-sw --transport radsec                            # change it later
```

The console's **Connect a switch → Cisco** then shows the switch's IOS-XE configuration, generated for it: the RADIUS
server (UDP 1812/1813, or RadSec on TCP 2083 matching `radius.<domain>`), the `FABRIC` server group, 802.1X and
accounting (with interim updates), CoA from the fabric host on UDP 3799 (`aaa server radius dynamic-author`), the
RADIUS attributes fabric reads, and an access-port template (802.1X, then MAB). **The shared secret is never in it:**
type the secret shown once when the client was added wherever it says `<SHARED-SECRET>`; `password encryption aes`
keeps it out of the clear running configuration. Paste it in global configuration mode, and leave 802.1X off on
uplinks, access points, the fabric host's port and the switch's management port.

**RadSec** (1.11.1.3): the switch makes its own key and certificate request; the configuration's
`crypto pki` lines walk through it:

1. `crypto pki authenticate fabric-root`: paste fabric's root CA; `crypto pki authenticate fabric-radsec`: paste the
   intermediate CA (both on the Step-CA tab).
2. `crypto pki enroll fabric-radsec` prints a request with CN `radsec-<client name>`. Sign it on the Step-CA tab (Sign
   a CSR); a certificate with any other common name is refused by FreeRADIUS (`REJECT method=radsec
   reason=certificate_not_this_client` in the log).
3. `crypto pki import fabric-radsec certificate`: paste the signed certificate.
4. Inside TLS the RADIUS secret is `radsec`; the client's own secret is used only for CoA (`server-key`).

The certificate has fabric's manual lifetime (`pki_manual_max_days`): renew it the same way before it expires (the
Step-CA tab's expiry warnings list it).

## 4.11.1.4 Sessions: Disconnect, Re-authenticate, Move VLAN

Built 2026-10-12 for 0.9, **untested** (2.3.11.5). FreeRADIUS tab → **Sessions** lists the open 802.1X sessions,
from the switches' accounting (a switch that sends none shows none): who, MAC, VLAN, switch and port, since when.
For a Cisco switch, with the `radius:coa` permission (Admin, Equipment operator):

- **Disconnect** ends the session; the device starts again from the beginning (and is refused if it no longer may
  join).
- **Re-authenticate** makes the device prove itself again: a disabled device is cut off, a changed role or VLAN
  applies, at once.
- **Move VLAN** bounces the port, so the device also asks DHCP again, on its new VLAN.

```bash
sudo fabricctl radius sessions                                  # open sessions and what can be done to each
sudo fabricctl radius disconnect core-sw 0A0B0C0D000000120004F2A1
sudo fabricctl radius reauthenticate core-sw 0A0B0C0D000000120004F2A1 [--bounce]
```

The answer is shown: acknowledged, refused by the switch (with its reason), or no answer — then check the switch's
`aaa server radius dynamic-author` (the fabric host's address, the same secret, port 3799) and that nothing between
drops UDP 3799. For UniFi and other switches it is refused with why, and nothing is sent: disable the device and
reconnect it on the switch instead. Every attempt that reaches a switch is in the audit log (`RADIUS_COA`).

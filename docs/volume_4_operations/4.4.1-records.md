## 4.4.1.1 DNS Configuration

Add or remove records in BIND9 zones without a full redeploy via the interactive menu (DNS Configuration → a zone; `a` adds a zone, `r` removes one: 4.4.1.2). Supported record types include `A`, `AAAA`, `CNAME`, `MX`, `TXT`, and `SRV`.

**DNS Sync Status & Actions:**
When entering a specific zone, the menu compares the serial BIND9 is serving (`rndc zonestatus`) with the serial in the deployed `db.<zone>` file:
- `IN SYNC (serial N)`: BIND9 serves the deployed file (or newer, e.g. after dynamic updates).
- `OUT OF SYNC (serving serial N, file has M; run 'l')`: the file on disk is newer than what BIND9 serves.
- `NOT LOADED in BIND9` / `? BIND9 not reachable`: the zone failed to load or the container is down.

Records are listed with their full value (`A`/`AAAA` ip, `CNAME` target, `MX` priority + exchange, `TXT` text, `SRV` priority/weight/port/target). Records without a name (or named `None`) are shown as `(missing name)`, rejected on entry, and filtered out at render time.

You have two powerful options to apply your pending `vars.yaml` modifications directly from the menu:
- **`l` (Live update):** Runs the same apply as `fabricctl --apply`: each changed zone is frozen, its file swapped, the `.jnl` removed and the zone thawed. *Non-disruptive to DNS resolution.*
- **`f` (Force update):** Stops BIND9, deletes `db.<zone>` and its `.jnl`, then runs the apply, which rewrites the zone and starts BIND9 again. *Warning: Disruptive — DNS is down while it runs.*

Changes edit `vars.yaml` and re-render forward and reverse zone files natively using Jinja2. Rendered files are written to `/opt/bind9/data/` with bind ownership. **Reverse zones are generated** from the A and AAAA records with private addresses — see [Reverse DNS](4.4.5-reverse-dns.md#4451-reverse-dns).

Under `dns:`, the key `dynamic_zone_var` is the main zone (`domain`); it stays that way in `vars.yaml` and is resolved when the zone is rendered. Any other key is a zone name of its own:

```yaml
dns:
  dynamic_zone_var:         # = domain
    zone_authority: true    # emit the "ns" A record pointing to host_ip
    A:
    - { name: myserver, ip: 10.0.3.99 }
    CNAME:
    - { name: app, canonical: myserver }
    TXT:
    - { name: myserver, text: "v=spf1 -all" }
```

## 4.4.1.2 Adding and removing a zone (0.7.0)

Design: [1.4.1.3](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#1413-zones-added-and-removed-in-the-console-070).
Both need the permission `dns:write` (the admin bundle). Neither needs **Apply**: BIND and the DNS filter take the
change within seconds; if either refuses it, nothing is kept and the page says why.

**In the console** (BIND9 tab, Zones):
1. **Add zone** (in the bar at the top): type the name (e.g. `home.lan`) and press **Add zone**. A name under a public top-level domain
   (`.com`, `.net`, …) also needs **Hide the public name** ticked: every client of this site then gets this zone's
   answers instead of the real ones. `home.arpa` and `.internal`, `.lan`, `.local`, `.test`, `.example` need no tick.
   It waits for **Apply** in the top bar (with any records you add to it meanwhile); then BIND answers for it.
2. *Remove zone* (on any zone but the site's own): the card says how many records go with it. Type the zone's name
   again, press **Remove zone**, then **Apply**. A TSIG key or ACL policy for the zone must be removed first (TSIG keys view).

**In the menu** (`sudo fabricctl`, DNS Configuration): `a` asks for the name (and, for a public name, whether it hides
the real one); `r` asks which zone, shows its record count and asks for its name again.

Refused, with the reason: a name that is not a DNS name of at least two labels; the site's own domain; the DHCP zone
(`dhcp.<domain>`); the Windows domain's zone; another site's zone; a reverse zone (`*.arpa`, generated); a zone that
exists. The audit log records `DNS_ZONE_ADD` and `DNS_ZONE_DELETE` (with the records removed).

## 4.4.1.3 Adding a record in the console; fabric's own names (0.7.1)

Design: [1.4.1.4](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#1414-records-in-the-console-the-form-asks-only-what-a-type-needs-fabrics-own-names-071).
Needs `dns:write`; each change waits for **Apply** in the top bar, which reloads only BIND (4.8.4).

1. BIND9 tab → the zone → *Add record*: pick the **type**, type the **name** (`www`, or `@` for the zone itself) and
   the **value**: the address for A and AAAA, the host it points to for CNAME, MX and SRV, the text for TXT.
2. For **MX**, also the *priority*; for **SRV**, the *priority*, *weight* and *port*. Those fields show only for
   those types (in an old browser every field shows: fill only what the type needs).
3. **Add record**, then **Apply** in the top bar. A refusal is said on the Review (an address that is not one, an MX
   without its priority, quotes in a TXT).

Names marked **provided by fabric** (`ca`, `dns`, `sso`, `vault`, the console's name, `ntp`, `federation`,
the host's own name and `@`) are fabric's: every apply adds them back from their setting, so they cannot be deleted —
the row names the setting and *Delete a record* does not offer them; the menu's `d` refuses them the same way.
To delete one of yours: the zone → *Delete a record*, pick it, **Delete record**, then **Apply**. To link a record
from the landing page, see 4.4.4.2.

The landing page's **`info`** is yours since 0.7.1 (2.1.4.6, design 1.4.2.5): a new install gets it, pointing at this
host, and you may delete it, add it under another name (to rename it: delete `info`, add a CNAME `welcome` to the
host) or point it at another machine (delete it, add `info` with the other machine as its value), then **Apply**.
Nothing of fabric's uses it: the landing page stays at `http://<host address>/info/`, at `<domain>` and at
the host's own name, and any name you point at the host shows it over plain HTTP. From 0.7.1 every name in the
site's zone that points at the host (a renamed `info` included) also shows it over HTTPS after the whole apply on the
host (`sudo fabricctl --apply`; DNS' Apply in the console reloads only BIND and issues no certificate, and its
row on DNS' Review then says which names the certificate lacks or still holds, 2.1.8.29): the
apply issues the landing page's certificate again for the names it now has, without the old name; the one it
replaced is not revoked and simply expires (1.4.2.6, 1.5.1.7). If the apply ends with "could not be issued again",
Step-CA did not issue it: check `sudo fabricctl status`, then apply again. Certificates issued before 0.7.1
name their CRL at `info.<domain>`; the upgrade issues fabric's own again at once, devices' ACME certificates move at
their next renewal (1.5.1.6).

## 4.4.1.4 Edit, delete or add a record in the zone's table

From 0.10.0. Design [1.4.1.10](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#14110-records-changed-in-their-table-edit-delete-and-add-in-place-0100).

1. Open DNS → **Zones** and pick the zone.
2. **Edit:** the pencil on the record's row. Change its name or value, **Save** (or **Cancel**). The old record stays
   until the new one is accepted.
3. **Delete:** the bin on the record's row.
4. **Add:** fill in the table's last row and press **Add**.
5. Press **Apply** in the top bar. Fabric's own records show "kept by fabric" and cannot be changed here.

## 4.4.1.5 [DEPRECATED] Give one VLAN its own answer for a name

This item has been removed from scope of fabric as of (0.10.2 / 2026-11-24). See 4.4.1.6 for newest applicable method.

From 0.10.0 until 0.10.2. Design [1.4.1.11](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#14111-a-vlans-own-answers-split-horizon-dns-0100).

Split DNS needs the DNS filter on (decision 2.1.4.16): with it off, a record for one VLAN is refused, and so is
turning the filter off while one exists. Give those records back to everyone (or delete them) first.

1. In the zone's table, add (or edit) a record with the same name and pick the VLAN in its **VLAN** column.
2. **Apply.** Clients on that VLAN now get that record for the name; everyone else keeps the zone's own.
3. **Check it** from a client on the VLAN: `nslookup <name>.<domain>` answers the VLAN's address; from another network,
   the zone's.

The refusal reads "split DNS needs the DNS filter on ..." and names the records for one VLAN: turn the DNS filter on
in the setup wizard, or give those records back to everyone.

## 4.4.1.7 Answer a zone to some networks only

From 0.10.2. Design [1.4.1.13](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#14113-a-zones-networks-and-split-tabs-0102);
decision 2.1.4.18. Needs the DNS filter on (setup wizard).

1. Open DNS → **Zones** and pick the zone.
2. In its **Networks** row, untick **every network** and tick the networks that should see the zone: the host's LAN
   or any subnet of the site's address plan.
3. **Save networks**, then **Apply**.
4. **Check it:** from a client in a picked network, `nslookup <name>.<zone>` answers; from a client elsewhere it says
   the name does not exist.

To give the zone back to every network, tick **every network** alone and save.

Refusals, each changing nothing:
- "pick at least one network": nothing ticked.
- "every network already holds the others": **every network** beside a network. Tick it alone.
- "... is neither the host's LAN nor a subnet of the site's plan": add the subnet to the address plan first (4.10.2).
- "the site's own domain is never mapped ...", "... holds the zone ...": map another zone, or split this one (4.4.1.8).
- "... is in a split of this zone": the split holds that network; remove it from the split first.
- "split DNS needs the DNS filter on ...": turn the DNS filter on in the setup wizard.

## 4.4.1.8 Give some networks their own answers: a split

From 0.10.2. Design [1.4.1.13](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#14113-a-zones-networks-and-split-tabs-0102);
decision 2.1.4.18. Needs the DNS filter on.

1. Open DNS → **Zones**, pick the zone, then **+ Split**.
2. Tick the networks the split is for, then **Add split**. Its tab opens with a copy of the All networks tab's
   records (fabric's own names stay in All networks and answer everywhere).
3. In the split's tab, edit, delete or add records as in 4.4.1.4. Its clients get exactly this tab's records for the
   zone: a name deleted here does not exist for them.
4. **Apply.**
5. **Check it:** from a client in the split's network, `nslookup <name>.<zone>` gives the split's answer; from a
   client in another network, the All networks answer.

To change which networks a split holds, tick them in its tab and **Save networks**; **Remove split** gives its
networks back to the All networks tab. A 0.10.0 record given to a VLAN shows after the upgrade as a split for that
VLAN's subnets.

Refusals, each changing nothing:
- "pick at least one network", "... is neither the host's LAN nor a subnet of the site's plan": as 4.4.1.7.
- "... is already in another split of this zone": a network sits in one split per zone.
- "... is not one of the zone's networks": the zone is mapped elsewhere; add the network to it first (4.4.1.7).
- "a reverse zone is never split": its PTRs follow the records.
- "the split changed since it was shown; reload and try again": another change got there first.
- "split DNS needs the DNS filter on ...": turn the DNS filter on in the setup wizard.

## 4.4.1.1 DNS Configuration

Add or remove records in BIND9 zones without a full redeploy via the interactive menu (DNS Configuration → a zone; `a` adds a zone, `r` removes one: 4.4.1.2). Supported record types include `A`, `AAAA`, `CNAME`, `MX`, `TXT`, and `SRV`.

**DNS Sync Status & Actions:**
When entering a specific zone, the menu compares the serial BIND9 is serving (`rndc zonestatus`) with the serial in the deployed `db.<zone>` file:
- `IN SYNC (serial N)`: BIND9 serves the deployed file (or newer, e.g. after dynamic updates).
- `OUT OF SYNC (serving serial N, file has M; run 'l')`: the file on disk is newer than what BIND9 serves.
- `NOT LOADED in BIND9` / `? BIND9 not reachable`: the zone failed to load or the container is down.

Records are listed with their full value (`A`/`AAAA` ip, `CNAME` target, `MX` priority + exchange, `TXT` text, `SRV` priority/weight/port/target). Records without a name (or named `None`) are shown as `(missing name)`, rejected on entry, and filtered out at render time.

You have two powerful options to apply your pending `vars.yaml` modifications directly from the menu:
- **`l` (Live update):** Runs the same apply as `fabricctl --apply`: each changed zone is frozen, its file swapped, the `.jnl` removed and the zone thawed. *Non-disruptive to DNS resolution.*
- **`f` (Force update):** Stops BIND9, deletes `db.<zone>` and its `.jnl`, then runs the apply, which rewrites the zone and starts BIND9 again. *Warning: Disruptive — DNS is down while it runs.*

Changes edit `vars.yaml` and re-render forward and reverse zone files natively using Jinja2. Rendered files are written to `/opt/bind9/data/` with bind ownership. **Reverse zones are generated** from the A and AAAA records with private addresses — see [Reverse DNS](4.4.5-reverse-dns.md#4451-reverse-dns).

Under `dns:`, the key `dynamic_zone_var` is the main zone (`domain`); it stays that way in `vars.yaml` and is resolved when the zone is rendered. Any other key is a zone name of its own:

```yaml
dns:
  dynamic_zone_var:         # = domain
    zone_authority: true    # emit the "ns" A record pointing to host_ip
    A:
    - { name: myserver, ip: 10.0.3.99 }
    CNAME:
    - { name: app, canonical: myserver }
    TXT:
    - { name: myserver, text: "v=spf1 -all" }
```

## 4.4.1.2 Adding and removing a zone (0.7.0)

Design: [1.4.1.3](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#1413-zones-added-and-removed-in-the-console-070).
Both need the permission `dns:write` (the admin bundle). Neither needs **Apply**: BIND and the DNS filter take the
change within seconds; if either refuses it, nothing is kept and the page says why.

**In the console** (BIND9 tab, Zones):
1. *New zone*: type the name (e.g. `home.lan`) and press **Add zone**. A name under a public top-level domain
   (`.com`, `.net`, …) also needs **Hide the public name** ticked: every client of this site then gets this zone's
   answers instead of the real ones. `home.arpa` and `.internal`, `.lan`, `.local`, `.test`, `.example` need no tick.
   The page opens the new zone: add its records there as in any zone (records still need **Apply**).
2. *Remove zone* (on any zone but the site's own): the card says how many records go with it. Type the zone's name
   again and press **Remove zone**. A TSIG key or ACL policy for the zone must be removed first (TSIG keys view).

**In the menu** (`sudo fabricctl`, DNS Configuration): `a` asks for the name (and, for a public name, whether it hides
the real one); `r` asks which zone, shows its record count and asks for its name again.

Refused, with the reason: a name that is not a DNS name of at least two labels; the site's own domain; the DHCP zone
(`dhcp.<domain>`); the Windows domain's zone; another site's zone; a reverse zone (`*.arpa`, generated); a zone that
exists. The audit log records `DNS_ZONE_ADD` and `DNS_ZONE_DELETE` (with the records removed).

## 4.4.1.3 Adding a record in the console; fabric's own names (0.7.1)

Design: [1.4.1.4](../volume_1_description_and_architecture/1.4.1-dns-architecture.md#1414-records-in-the-console-the-form-asks-only-what-a-type-needs-fabrics-own-names-071).
Needs `dns:write`; **Apply changes** publishes the records.

1. BIND9 tab → the zone → *Add record*: pick the **type**, type the **name** (`www`, or `@` for the zone itself) and
   the **value**: the address for A and AAAA, the host it points to for CNAME, MX and SRV, the text for TXT.
2. For **MX**, also the *priority*; for **SRV**, the *priority*, *weight* and *port*. Those fields show only for
   those types (in an old browser every field shows: fill only what the type needs).
3. **Add record**, then **Apply changes**. A refusal says why (an address that is not one, an MX without its
   priority, quotes in a TXT).

Names marked **provided by fabric** (`ca`, `dns`, `sso`, `vault`, the console's name, `ntp`, `federation`,
the host's own name and `@`) are fabric's: every apply adds them back from their setting, so they cannot be deleted —
the row names the setting instead of a *Delete* button, and the menu's `d` refuses them the same way. To link a record
from the landing page, see 4.4.4.2.

The landing page's **`info`** is yours since 0.7.1 (2.1.4.6, design 1.4.2.5): a new install gets it, pointing at this
host, and you may delete it, add it under another name (to rename it: delete `info`, add a CNAME `welcome` to the
host) or point it at another machine (delete it, add `info` with the other machine as its value), then **Apply
changes**. Nothing of fabric's uses it: the landing page stays at `http://<host address>/info/`, at `<domain>` and at
the host's own name, and any name you point at the host shows it over plain HTTP. Certificates issued before 0.7.1
name their CRL at `info.<domain>`; the upgrade issues fabric's own again at once, devices' ACME certificates move at
their next renewal (1.5.1.6).

## 4.8.3.1 Finish setting up, or reconfigure, in the console

After a fresh install, the first admin's first sign-in opens **Settings**, and the Overview shows *Finish setting up*
until the wizard has been applied once or dismissed. Later, **Settings** opens the same wizard filled in with today's
values.

1. Sign in to the console. Applying needs a sign-in from the last 5 minutes: if the wizard says your sign-in is older,
   sign in again first.
2. **Optional parts:** DHCP (turning it on with no subnet yet asks the first one: the interface to serve, the subnet,
   a pool `first - last`, the router), the DNS filter, log forwarding and where the logs go (`host[:port]` for a TLS
   syslog server, `https://…` for Elasticsearch). The settings changed only on the host are listed read only, each
   with its command.
3. **Memory:** how many GB fabric may use, 4 to what the host has.
4. **Passwords and sign-in:** the domain's password policy, signing in with the domain logon (Kerberos), and who may
   sign in to the site's machines, one OU a line: `OU path | console groups | remote groups` (`site` for the site's
   OU).
5. **The DNS filter's upstreams:** one a line, `address name-on-its-certificate`.
6. **Review**, then **Make the plan**. Back and Next keep what you typed; nothing has changed yet.
7. The plan shows each change (now → after), the parts started or stopped, and the memory plan. A value that is not
   valid is refused with its reason and nothing changes: correct it and make the plan again.
8. **Apply** runs one apply; its page follows it to the end. If someone else applied first, the plan is refused and
   shown again against today's settings: review it and apply again. A plan waits 15 minutes.

To keep setup's choices instead, **Dismiss** (in the wizard or on the Overview's *Finish setting up*).

Every apply is in the audit log as `SETTINGS_CHANGE` with who, from where (`web`, `file` or `cli`) and the keys; a
dismissal as `SETTINGS_DISMISS`.

## 4.8.3.2 Export and import the settings file

- **Export** (in the wizard) downloads `<site>-settings.yaml`: every wizard setting, no secret and nothing
  console-only.
- **Import** takes such a file (upload or paste) and shows its plan, as the wizard's own (4.8.3.1, from step 7). Keys
  that are not the wizard's are listed as ignored with why: *a secret*, *console only* or *not a setting*. A file
  without `fabric_settings: 1`, or with one invalid wizard value, is refused whole and changes nothing.

## 4.8.3.3 On a host without a browser: fabricctl settings

```
sudo fabricctl settings export site.yaml          # every wizard setting into site.yaml (0600); no FILE: printed
sudo fabricctl settings import site.yaml          # the plan, what was ignored and why, then: Apply this plan now? [y/N]
sudo fabricctl settings import site.yaml --yes    # the same, applied without asking
```

Exit status: 0 applied, nothing to change, or not confirmed; 1 refused (the file, or a value: nothing changed) or the
apply did not finish; 2 usage. An apply that did not finish has saved the settings: fix what its output names and
apply again (`sudo fabricctl --apply`).

## 4.8.3.4 What the wizard does not change

The permanent identity (the domains, the DC's name, the organisation and the CA), the network and the host's name, the
first admin, every host change, OpenBao's unlock and recovery, lowering sign-in security, client certificates and
every secret: `sudo fabricctl setup`, the vars editor (`sudo fabricctl`) or `fabricctl security` on the host. In log
forwarding, a destination's `ca_file` and `hosts` stay the host's too.

## 4.9.1.1 Federation (sites)

Several fabrics can form one: an **upstream** owns identity and the root CA, **sites** join it and run
their own network (design [federation.md](../volume_1_description_and_architecture/1.9.1-sites.md#1911-status)). On the upstream:

```bash
sudo fabricctl federation status            # standalone, upstream or site; joined sites; open invitations
sudo fabricctl federation enable            # the endpoint sites join through: https://federation.<domain>
sudo fabricctl federation invite lab        # one-time invitation (one hour); lab attaches flat
sudo fabricctl federation invite lab --nest 1   # lab may hold one level of sites of its own
sudo fabricctl federation invite lab3 --via edge1  # lab3 joins (and talks) through the site edge1, which only relays
sudo fabricctl federation invite edge --dc rodc  # edge's domain controller joins read-only (default: writable)
sudo fabricctl federation invitations       # open invitations
sudo fabricctl federation revoke branch1    # withdraw one (by id or site)
sudo fabricctl federation remove lab        # forget a site that joined here (a lab torn down); its CA revoked
sudo fabricctl federation disable           # no new joins; sites that joined stay
```

**Nesting.** An invitation made on the root site attaches the new site flat (its CA signed by the root).
Made on a site that was invited with `--nest 1` or more (and has its endpoint enabled), it nests the new
site under that site: the site signs its CA, and every chain the nested site hands out carries its
parent's CA. How deep sites may nest is capped by the root's path length (`ca_nest_depth`, default 1,
chosen when the root site is installed). A nested site whose parent is gone for good moves under another
parent with that parent's invitation — on the site itself:

```bash
sudo fabricctl federation reparent         # paste the new parent's invitation at the prompt
```

It keeps its name, directory part and data; it gets a new CA, Step-CA switches to it and every service
certificate is re-issued. People's web UI certificates must then be re-issued (`fabricctl client-cert`).

**DNS between sites.** Each join creates a TSIG key for that link (kept in both sites' secrets). The
parent delegates the site's domain when it lies below its own (`lab.<domain>`: NS + glue), and each side
keeps a read-only secondary copy of the other's zone: transfers are signed with the link's key, changes
are pushed with NOTIFY. The parent applies this right after the join; `remove` takes it away again. The
two sites must reach each other on their DNS ports: each site reports its `bind_dns_port` when it joins,
so a BIND published on 5053 behind another resolver on 53 (e.g. fabric's DNS filter) works. Resolvers follow a
delegation only on port 53, so with BIND on another port the resolver in front of it forwards the
site domains instead. Sites that joined before this existed have no key: they
get one when they join again (or are re-parented).

**The directory between sites.** An invitation names the organisation's AD domain: the new site's setup asks
for no domain or password policy. Before it answers, the inviting site — the root, or any site with a writable
DC — makes the new site's part of the domain in its own DC (its OU, inside the inviting site's; groups, service
accounts, the next free id numbers in the domain, networks and AD site, linked to the inviting site's) and a
join account that expires within the hour; the site's DC then joins the domain — writable, or read-only with `--dc
rodc` — and deletes that account. From then on AD replicates between the DCs by itself. Each site writes its
own part; a read-only site's writes go to a writable DC. Design: [1.9.8](../volume_1_description_and_architecture/1.9.8-federation-on-ad.md);
a site whose DC is read-only cannot invite (its DC cannot prepare the new site), and sites with no DC are not
built (1.6.5.22, S8.8). A site inherits its parent's Group Policy unless it overrides it, except the parent's
controls (4.6.8.5).

Each site's id block is a million ids, site *S*'s from *S* × 1 000 000 (a uid names its site at a glance; an
organisation installed before 0.7.0 keeps its older blocks); a join that would need a 1000th block is refused
([1.6.3.17](../volume_1_description_and_architecture/1.6.3-samba-directory.md#16317-the-ranges-inside-a-sites-id-block-070)).

**The Federation tab** (`federation:read`) shows the sites that joined here with their DC type and id block, this site's DC's replication with each partner (every partition, the last success, failures), AD's conflict objects (`CNF:`: the same name made on two DCs while they were apart — keep one, delete the other), each site's write limits, and the address plan with any overlap.

**Relay nodes.** `--via edge1` names a site that joined this install (with its endpoint enabled) as the
new site's way in: the invitation points at edge1, edge1 forwards the join to the root, and the root
signs. edge1 signs nothing and keeps nothing of the new site, but it terminates TLS, so it sees the join
request — including the invitation's single-use secret — on the way through. If the relay goes away, the
site talks to its upstream directly:

```bash
sudo fabricctl federation relay direct     # on the site
```

The new site runs `sudo fabricctl setup --join` and pastes it at the prompt (or `--join @FILE`; see
[install.md](../volume_3_installation/3.9.1-joining.md#3911-joining-an-existing-fabric-a-new-site)). The invitation carries the endpoint's
name and address, the root CA's fingerprint and a single-use secret — send it over a channel you trust;
only a hash of the secret is kept. The joining node fetches the root over plain HTTP, accepts it only if
it matches the fingerprint, then joins over TLS verified against that root. The upstream signs the
site's intermediate CA (path length 0, never outliving the root) with its root key; the site's key never
leaves the site. Joins, refusals and invitations are audited (`FED_*`).

An upstream whose CA was brought in (`byoc`) has no root key on the host and cannot sign a site's CA
online yet.

## 4.9.1.2 Changing a site's DC type (0.9)

A site that has grown gets a writable DC; one that shrinks, a read-only one (design
[1.9.8.20](../volume_1_description_and_architecture/1.9.8-federation-on-ad.md#19820-changing-a-sites-dc-type-requested-from-above-09),
decision 2.1.9.23). Built for 0.9; its tests are written and not yet run (2.3.9.3). Central IT asks from a site above;
the site's admin carries it out. Plan for the site's DC to be away for the change (about as long as a join): the
site's services use the writable DC meanwhile, so plan it when the link to it is up.

**1. At a site above the site** (its parent or any site above it; the federation endpoint on):

```bash
sudo fabricctl federation dc-type branch1 writable   # or rodc
```

It prints a **change token** (`fabric-dctype-1.…`), good for one hour and for this one change. Send it to the site's
admin over a channel you trust; it lets the site fetch the temporary account its DC re-joins with. Asking again
replaces the request and its token.

**2. At the site**, as root on its fabric host:

```bash
sudo fabricctl federation dc-type show               # the request: type, from which site, who, when
sudo fabricctl federation dc-type accept             # the plan, then "yes" to go on, then paste the token
sudo fabricctl federation dc-type accept @/root/token --yes   # unattended: the token from a file
```

`accept` checks that a writable DC answers and that this DC's replication is healthy, then demotes the DC, keeps its
old data in `samba/data.before-dc-type-<time>`, and joins it again with the new type under the same name. If it stops
part way, fix what it names and run `accept` again: it goes on from where it stopped. When it ends,
`fabricctl federation status` and the console's Federation tab show the new type.

**Undo:** ask for the change back from above (step 1 with the other type) and accept it at the site. A demoted DC is
never put back from its old data.

| What you see | Why, and what to do |
|---|---|
| "… is not below this site" | Ask from the site's parent or a site above it; a sibling or a site below cannot. |
| "… is already writable/read-only" | Nothing to do. |
| "this site's domain controller is read-only: it cannot prepare …" | Ask from a site above with a writable DC. |
| "replication is not healthy: …" (at either end) | The partner and the failure are named: fix the link (`fabricctl federation status`, the Federation tab's Replication), then try again. |
| "none of this site's writable domain controllers answers (…)" | Each DC tried is named: bring the link up, or list another writable DC in `ad_writable_servers` (4.6.5.7). |
| "the change token is not valid (unknown, used, withdrawn or expired)" | Ask for a new one (step 1). |
| "no change of this site's DC type is requested" | The request was removed or never made: ask from above. |
| "the DC holds an FSMO role" (to read-only) | Move the role to another writable DC first. |

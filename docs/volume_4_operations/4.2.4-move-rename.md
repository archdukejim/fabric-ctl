## 4.2.4.1 Before either: what this covers

- **One install, no linked sites.** A site's linked sites keep its old address and name (federation stores them when
  they link, 1.9): with links (`sudo fabricctl federation status` lists any), this procedure is not enough, and is not
  tested; leave the host as it is, or uninstall and reinstall (the last item below).
- **The same network.** The new address is on the same LAN (`lan_cidr` and `lan_gateway` unchanged). A move to
  another network also changes those two settings and the firewall; that is not covered here: uninstall and
  reinstall (the last item below).
- **The domain controller keeps its name** (`dc_name`, permanent): a rename changes the host's name, its certificates'
  names and its pages, never the DC's (2.1.6.45).
- **A console on the host** (its screen, or a hypervisor's) is the safe place to work: an SSH session drops when the
  address changes. Over SSH, the address change is applied detached (step 2 below), and you sign in again at the new
  address.
- Both changes are *warned* settings: the interactive menu (`sudo fabricctl --interactive`, Advanced Configuration)
  asks again before it applies them. This procedure edits `vars.yaml` and runs `--apply` instead (4.3.1.2.3), which is
  the same change without the menu.
- **Anything else means uninstall and reinstall** (decision 2.1.1.77, owner 2026-11-02). To reuse the host on another
  network, or to move or rename a site that is linked to other sites, fabric is not moved: it is removed and installed
  again, with the existing procedures only:
  1. **A linked site is unlinked first**, on its parent: `sudo fabricctl federation remove <site>` (4.9.1.1; its CA
     is revoked, its DNS link goes; in 0.9.0 the site's domain controller, AD site and OU stay in the domain:
     2.3.1.38.3). A site that other sites joined is refused until they are re-parented (`sudo fabricctl federation
     reparent` on each, with another parent's invitation) or removed.
  2. **Uninstall** on the host: `sudo fabricctl uninstall` (3.2.4.1), with an export if you want one kept. Do not
     restore that export on the new network: `fabricctl restore` brings back the same settings, address and name
     (3.2.4.1), which is the move this procedure leaves out.
  3. **Install** again on the new network or under the new name: `sudo fabricctl setup` (3.3.1.1), or, to be a site
     again, `sudo fabricctl setup --join` with a new invitation from the parent (3.9.1.1).
  4. **The machines joined to it** join the new install's domain again (4.6.6 for Linux, 4.6.7 for Windows).
  What an export could carry across in future, to make that easier, is an idea under investigation (2.3.1.38), not a
  procedure.

## 4.2.4.2 Moving the host to a new address

1. **Note the old and new addresses.** `ip -4 addr` shows the old one; the new one must be free on the LAN (not in a
   DHCP pool: fabric's own, `sudo fabricctl ipam`, or the network's).
1a. **Announce it, then wait** (0.9.2, decision 2.1.1.79, design 1.4.1.8.7):

   ```bash
   sudo fabricctl move prepare <new address>
   ```

   It refuses an address off the LAN, the host's own, and an install with linked sites, saying why. `sudo fabricctl move
   status` says what is announced; `sudo fabricctl move cancel` withdraws it. Then wait for the machines, or the ones
   you care about: a Linux machine fabric manages checks hourly (`sudo fabric-managed check` does it at once, and
   `/etc/systemd/resolved.conf.d/fabric.conf` then names both addresses); a Windows machine takes Group Policy within 90
   minutes (`gpupdate /target:computer /force` does it at once, and within a minute `Get-DnsClientServerAddress` names
   both, on an adapter with a fixed address; one on DHCP gets the new address from DHCP).
2. **Change the host's own address** in its netplan file (`/etc/netplan/*.yaml`: the `addresses:` entry, keeping the
   prefix, for example `10.88.0.10/24` to `10.88.0.13/24`), then apply it. From a console, `sudo netplan apply`. Over
   SSH, let systemd apply it 10 seconds later, so the command returns and your session ends before the address
   changes, then sign in again at the new address:

   ```bash
   sudo systemd-run --quiet --on-active=10 --unit=fabric-move-netplan netplan apply
   exit
   ```

   *Corrected 2026-11-01 (the joined campaign's run 5, 2.3.1.33):* this used `nohup setsid sh -c 'sleep 2; netplan
   apply' &`, which left the SSH session open when the address changed, so the session hung until the client gave up.

3. **Tell fabric:** set `host_ip:` in `/opt/fabric/config/vars.yaml` to the new address (`sudoedit`), then apply:

   ```bash
   sudo fabricctl --apply
   ```

   The apply renders everything that names the address (the zone's `A` records for the host and the domain, the
   ports' bindings, nginx, the CA page, Kea's DNS server for its clients, the domain controller's interfaces and its
   own DNS registration, `samba_dnsupdate --current-ip`) and restarts what changed. Since 0.9.2 it also drops
   fabric's records at the old address from the site's zone, moves the domain controller's records in the AD
   domain's DNS to the new address (its line *Windows domain: DNS …: the DC's old address … removed*), and makes the
   filtering resolver forget the old answers.
4. **The host's own join** takes the new address (its resolver for the domain's names, and the DC's name in
   `/etc/hosts` when it needs one):

   ```bash
   sudo fabricctl setup --step member --non-interactive --approve member
   ```

   Since 0.9.2 it replaces the old line for the DC in `/etc/hosts` instead of adding one after it.
5. **Point the clients at the new address.** Machines fabric's DHCP serves get the new DNS server at their next
   lease renewal (or at once: `sudo networkctl renew <interface>`, `ipconfig /renew`). Elsewhere set it on the
   network's DHCP server, or on each machine with a fixed address: Linux, `sudo resolvectl dns <interface> <new
   address>` (and in its netplan or NetworkManager settings, to keep it); Windows, `Set-DnsClientServerAddress
   -InterfaceIndex <n> -ServerAddresses <new address>` (an administrator's PowerShell). A Linux member fabric's
   join script set up (it has `/etc/fabric/managed.env`) keeps the address there instead, and its own check puts it
   back at each run, so on it change that file and reapply: `sudo sed -i 's/^FABRIC_DNS=.*/FABRIC_DNS=<new
   address>/' /etc/fabric/managed.env && sudo fabric-managed apply`. On a member joined before 0.9.2, whose `fabric-managed` takes no
   lock, first let a check under way finish (`while systemctl is-active -q fabric-managed.service; do sleep 1;
   done`): one started before the change writes the old address back over your apply (2.3.1.42). Either way,
   `grep DNS= /etc/systemd/resolved.conf.d/fabric.conf` then names the new address. Then clear each client's DNS cache, which may
   still hold the old answers: Linux, `sudo resolvectl flush-caches`; Windows, `ipconfig /flushdns`. A Linux
   member joined to the domain (SSSD) also keeps the DC's old address in the file it hands Kerberos
   (`/var/lib/sss/pubconf/kdcinfo.<REALM>`), so `kinit` says "Cannot contact any KDC" until SSSD looks again:
   `sudo systemctl restart sssd` (the file then names the new address). A Windows
   member that lost its domain controller while its DNS still named the old address keeps no secure channel until
   Netlogon tries again, up to minutes later (System log: NETLOGON 5719); set it up again at once, in an
   administrator's PowerShell: `nltest /sc_reset:<ad domain>` ("NERR_Success"; `Test-ComputerSecureChannel` then
   says True). A machine that followed the announcement of step 1a does these three itself: Linux at its next hourly
   check (`sudo fabric-managed check` does it at once), Windows by its scheduled task, within 5 minutes of the new address answering. These
   steps by hand are for machines fabric does not manage, for one joined before 0.9.2 and not refreshed (its script does
   not follow; 4.6.6.12 refreshes it), and for one that was off while the announcement stood. On real members: 2.3.8.8.
6. **Check** it: 4.2.4.7 on the host (only the new address is left); `sudo fabricctl doctor` passes; on a client,
   `getent hosts info.<domain>` (Windows: `Resolve-DnsName info.<domain>`) gives the new address; then 4.2.4.4.

## 4.2.4.3 Renaming the host

*Revised 2026-11-01 (decision 2.1.6.104):* a host that runs a domain controller (every fabric host with an AD domain)
is renamed only through break glass, `fabricctl admin rename-host`; changing `hostname:` in vars.yaml and applying is
refused there, naming this procedure (1.6.11.14). A host without a DC is still renamed by vars.yaml (the last item).

1. **The new name:** one label of letters, digits or dashes, not only digits, whose first 15 characters (its
   account in the domain) are not the DC's `dc_name` nor a computer the domain already has (the member step refuses
   that one, 1.6.11.8).
2. **Rename the host through break glass**, as root on the host, with the reason the audit log keeps (one line, up to
   200 characters):

   ```bash
   sudo fabricctl admin rename-host <new-name> --reason "<why>"
   ```

   It renames the host (`hostnamectl`), sets `hostname:` in `/opt/fabric/config/vars.yaml`, moves the name an apply
   holds the host to, gives the host's `local-admin` a new password under its new name in OpenBao (check it out again
   when you need it, 4.7.1) and audits `HOST_RENAME`. It refuses, changing nothing, while OpenBao is sealed or does
   not answer: unseal it first (4.7.1). If it stops part-way, run the same command again: it does what is left.
3. **Apply** it:

   ```bash
   sudo fabricctl --apply
   ```

   The host's certificate and pages take the new name; the DC keeps its own (`hostname_dc` does not change).
4. **The host's own join** moves to an account under the new name: the account made, its keys in
   `/etc/krb5.keytab`, and the account fabric made under the old name removed (1.6.11.8):

   ```bash
   sudo fabricctl setup --step member --non-interactive --approve member
   ```

   If it says the old account was *not removed*, remove it in the web console (Directory → Machines).
5. **Nothing to clean up** (since 0.9.2, 1.4.1.8): the apply of step 3 put fabric's names under the new name only,
   and an alias you made of the old name (the landing page's `info`) follows it. (In 0.9.0 this was 4.2.4.6.)
6. **Check** it: 4.2.4.7 (only the new name is left); `sudo klist -k /etc/krb5.keytab` lists `<NEW-NAME>$` (upper
   case, cut to 15 characters); `sudo adcli testjoin -D <ad domain>` passes where adcli is installed;
   `sudo fabricctl doctor` passes; then 4.2.4.4.

A host **without a domain controller** (no AD domain: `ad_domain` empty in vars.yaml) is renamed without break glass:
`sudo hostnamectl set-hostname <new-name>`, then `hostname:` set in vars.yaml (`sudoedit`) and `sudo fabricctl --apply`.

## 4.2.4.4 Checking the joined machines afterwards

Nothing on a joined machine is changed by either move: its computer account and password are the DC's, and the DC
kept its name. After each, on a Linux member: `sudo adcli testjoin -D <ad domain>`, `id <a person>@<ad domain>`, and
`getent hosts <the DC's name>`; on a Windows member: `Test-ComputerSecureChannel` (True) and `nltest
/dsgetdc:<ad domain>`. A member that cannot find the DC still asks the old address: step 5 of 4.2.4.2.

## 4.2.4.7 Checking that only the new address and name are left

*Added 2026-11-01 (decision 2.1.1.74); since 0.9.2 `sudo fabricctl doctor` runs the same checks (1.4.1.8.4).* On the
host, after step 4 of 4.2.4.2 or 4.2.4.3. `<DOMAIN>` is the site's domain (`domain`), `<HOST>` the host's name now,
`<OLD>` and `<NEW>` the old and new addresses (`<NEW>` the host's address after a rename), `<DC>` the domain
controller's full name (`hostname_dc` in vars.yaml, for example `dc-0001.ad.example.com`), `<AD>` the AD domain
(`ad_domain`) and `<OLD-NAME>` the host's old name. Ask fabric's DNS at its own address:

```bash
for n in <HOST>.<DOMAIN> <DOMAIN> ca.<DOMAIN> <DC> <AD>; do echo "$n: $(dig +short @<NEW> "$n" | tr '\n' ' ')"; done
grep -n '<DC>' /etc/hosts
```

Each name gives `<NEW>` alone (`ca.<DOMAIN>` first gives `<HOST>.<DOMAIN>.`, then `<NEW>`), never `<OLD>`; and
`/etc/hosts` names `<DC>` at most once, at `<NEW>`. After a rename also `dig +short @<NEW> <OLD-NAME>.<DOMAIN>` gives
nothing. An old address or name still shown: run `sudo fabricctl --apply` and the member step again (4.2.4.2 steps
3 and 4), then this check; if it is still there, it is a fault in fabric: report it with doctor's output.

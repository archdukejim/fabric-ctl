## 4.4.2.1 TSIG Keys (RFC2136 dynamic updates)

TSIG keys let other systems update DNS over RFC2136 — typically a reverse proxy obtaining Let's Encrypt certificates with DNS-01, like nginx-proxy-manager's certbot `rfc2136` plugin. A key is a `tsig_keys` entry in the vars; its secret lives only with fabric's secrets (in OpenBao; `fabricctl secrets show tsig/<name>`). From them fabric renders the BIND key, its `update-policy` grants and an `rfc2136.ini` for the client; nothing edits the rendered BIND files by hand, so keys survive every apply and setup re-run.

```yaml
tsig_keys:
- name: npm                   # nginx-proxy-manager
  records: [npm, shelfmark]   # may only set _acme-challenge.npm.<domain> and _acme-challenge.shelfmark.<domain>
  secret: "base64..."         # OPTIONAL: keep an existing key (its clients keep working unchanged)
  acls: [npm-updaters]        # OPTIONAL: BIND ACLs the key belongs to (created if missing)
- name: acme_nas-proxy
  any_name: true              # may update any name in the zone (zonesub) — must be explicit
  record_types: [TXT, A]
```

**Update rights are deny-by-default.** A key may change only what is granted: its own `records`, `primary`, an explicit `any_name`, or the policy of an ACL it is in (below). A key with none of these can authenticate but change nothing.

| Field | Default | Meaning |
|---|---|---|
| `name` | — | Key name the client uses (`dns_rfc2136_name`) |
| `secret` | generated once | Base64 secret. Given in the vars, it is moved into fabric's secrets (OpenBao) and removed from the vars files; it always wins over a stored one |
| `algorithm` | `hmac-sha256` | `hmac-sha256/384/512/224`, `hmac-sha1`, `hmac-md5` |
| `domain` | the fabric domain | Zone the key may update |
| `records` | — | Hosts allowed a DNS-01 challenge: `grant <key> name _acme-challenge.<record>.<zone>. <types>` |
| `records_with_aliases` | — | A or AAAA records granted the same, each with every CNAME of the zone pointing at it as the zone is at each apply (4.4.2.4) |
| `any_name` | — | `grant <key> zonesub <types>`: any name in the zone (never implied) |
| `record_types` | `[TXT]` | Record types it may change |
| `primary` | — | The zone's own ACME key: `grant <key> subdomain _acme-challenge <types>` |
| `out` | `/opt/<name>/rfc2136.ini` | Credentials file for the client (`0600`): server = `host_ip`, port = `bind_dns_port`, key, secret, algorithm |
| `acls` | — | BIND ACLs holding `key "<name>"` (see [ACLs](4.4.3-acls.md#4431-acls)) |

`tsig list` shows each key's effective rights, including those inherited from ACL policies, or `no update rights`.

```bash
sudo fabricctl tsig list                                     # keys, what each may update, ACLs, credentials file
# add: a new secret, or keep an existing one (pasted, hidden), optionally into ACLs
sudo fabricctl tsig add npm --record npm --acl npm-updaters --secret-prompt
sudo fabricctl tsig add nas --record nas                     # new secret -> /opt/nas/rfc2136.ini
sudo fabricctl tsig set-secret npm --secret-prompt           # replace the secret with one you give
sudo fabricctl tsig rotate npm                               # generate a new secret (update its clients)
sudo fabricctl tsig update npm --record npm --record web     # change what it may update (secret untouched)
sudo fabricctl tsig update npm --any-name --types TXT,A      # any name in the zone, TXT and A (explicit)
sudo fabricctl tsig update npm --acl lab --drop-acl npm-updaters
sudo fabricctl tsig remove npm                               # also leaves every ACL; its rfc2136.ini is deleted
```

`add` and `update` take the fields of the table above as options: `--domain`, `--record` (repeatable),
`--record-with-aliases` (repeatable), `--any-name` (not together with `--record`), `--types TXT,A`, `--algorithm`,
`--out`, `--acl` (repeatable); `add` also `--mode acme|custom` (4.4.2.2), and with neither a mode nor a scope it asks;
`update` also `--drop-acl`, `--add-record`, `--drop-record`, `--add-record-with-aliases` and
`--drop-record-with-aliases` (4.4.2.3), and refuses when given nothing to change. `update --record` replaces the key's
list of names. `set-secret` needs `--secret-file` or `--secret-prompt`.

Every change updates the vars and secrets and applies at once: BIND reloads its configuration, and apply fails loudly if BIND rejects it. `--no-apply` records a change without applying (batch several, then `fabricctl --apply`). A secret is never taken on the command line: `--secret-file` or `--secret-prompt`.

## 4.4.2.2 Make a key by its mode: ACME (DNS-01) or Custom (0.10.0)

A new key starts with its mode (decision 2.1.4.12). **ACME (DNS-01)** is for a certificate client proving names with
DNS-01, as most keys are: the key may update only TXT at `_acme-challenge.<record>.<zone>` for the records you pick,
nothing else. **Custom** is everything else, as before: listed hosts, any `_acme-challenge` name in the zone (a
wildcard certificate, `*.<zone>`, needs this one), or any name with chosen record types.

In the console:

1. DNS → Zones → **TSIG keys** → **New TSIG key**, then **ACME (DNS-01)** or **Custom**.
2. ACME (DNS-01): pick the zone and **Next: its records**. The zone's A, AAAA and CNAME names are listed; tick each
   record the key may prove. An A or AAAA record also offers **with its aliases** (4.4.2.4).
3. Custom: today's form: the zone, what it may update, the hosts or the record types.
4. Give the key a name (and an existing secret, if a client already has one) and **Create key**. The secret and the
   client's `rfc2136.ini` are shown once; BIND takes the key at once.

On the host:

```bash
sudo fabricctl tsig add npm                                             # asks: the mode, the zone, the records
sudo fabricctl tsig add npm --mode acme --record nas --record-with-aliases proxy   # the same for a script
sudo fabricctl tsig add wild --mode custom --domain lan.example --types TXT --any-name
```

The questions take numbers: the mode (Enter: ACME), the zone (Enter: the site's), then the records, comma-separated,
a record's number with `+` for it with its aliases (`2,5+`). A key made with flags and no `--mode` is Custom.
`--mode acme` refuses a name that is not a record of the zone and `--any-name` or `--types`, saying why.

A record an ACME key names that is later **removed** is dropped from the key, with a note on its page, in
`tsig list` and in the audit; a rename of the host follows to its new name. A Custom key keeps the names it was
given. A key made by hand, or before 0.10.0, shows as Custom when it holds more than ACME mode gives.

## 4.4.2.3 Change a key's names, keeping its secret (0.10.0)

Add or remove a name a key may update without making the key again (decision 2.1.4.13): the key keeps its secret,
so its clients keep working.

1. DNS → Zones → **TSIG keys** → the key. **Edit names** lists each name it may update, each with **Remove**.
2. **Add**: pick a record of the key's zone (or a record with its aliases, 4.4.2.4). A Custom key may also take a name
   typed in, and change its scope and record types under **Change scope**.
3. The change waits on DNS → Zones as "Change TSIG key npm: add web, remove nas"; **Apply** in the top bar runs it
   and reloads BIND.

The zone, algorithm, secret and credentials file do not change here: a key for another zone is a new key, and a new
secret is **New secret**. Refused, saying why and changing nothing: removing the key's last name ("remove the key
instead"), a name already granted, one not valid as a record name, anything an ACME (DNS-01) key's mode does not give
(a name that is not a record of its zone, a scope, record types), a key no longer there. Its ACLs stay on
`fabricctl tsig update --acl` (4.4.3).

On the host, one name at a time, applied at once unless `--no-apply`:

```bash
sudo fabricctl tsig update npm --add-record web --drop-record nas
sudo fabricctl tsig update npm --add-record-with-aliases proxy
sudo fabricctl tsig update npm --drop-record-with-aliases proxy
```

The command line refuses the same cases. Changing a key's names needs the permission `tsig:manage`, like making one.

## 4.4.2.4 Grant a record with its aliases (0.10.0)

A host behind a reverse proxy usually has one A record and several aliases (CNAMEs), and a certificate naming them
needs each one's challenge. Pick the A or AAAA record **with its aliases** (making an ACME key, 4.4.2.2, or **Add** in
Edit names, 4.4.2.3; `--record-with-aliases` on the host): the key may then update the challenge of the record and of
every CNAME in the same zone that points at it, chains included (decision 2.1.4.14).

- **The aliases follow the zone.** A CNAME made later that points at the record is granted at the next DNS' Apply; one
  removed or repointed loses its grant there. The key's page and `tsig list` show the names it covers today.
- **Said when it happens.** When a key holds a record with its aliases, the zone's **Add record** card says so, the
  Review's row of a new CNAME says "TSIG key npm may update this name's _acme-challenge", and the record's audit
  entry names the key.
- **Removed whole.** Removing the entry removes the record and all its aliases from the key. To grant only some
  aliases, add their names one by one instead. A name in both stays granted until it is in neither.
- **Not covered:** a CNAME in another zone, or one whose chain leaves the key's zone (a key updates one zone); a chain
  that loops; a wildcard name.

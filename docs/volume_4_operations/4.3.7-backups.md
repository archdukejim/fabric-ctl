How backups are designed: [1.3.7](../volume_1_description_and_architecture/1.3.7-backups.md). Moving the host to another
network with a bundle: [4.2.4.8](4.2.4-move-rename.md). In the console, the page is **Settings ·
Backups**, shown only to the domain's Domain Admins. Each change asks for a sign-in from the last 5 minutes first.

## 4.3.7.1 Back up now

In the console:

1. Open **Settings · Backups**.
2. Under **Back up now**, type a passphrase of 12 characters or more, twice. Or, when a schedule is set, tick **Use the
   schedule's public key** to encrypt it to that key instead.
3. Choose **Back up now**. The job's page follows it; when it is done it names the bundle.
4. Keep the passphrase somewhere safe, away from the host. Fabric does not keep it, and without it the bundle cannot be
   opened.

On the host:

```
sudo fabricctl backup
```

It asks the passphrase twice. `--scheduled-key` uses the schedule's public key instead.

## 4.3.7.2 Set the backup schedule

1. On another machine, make the key pair the scheduled bundles are encrypted to: `age-keygen -o fabric-backup.key`. It
   prints the public key (`age1…`). Keep `fabric-backup.key` off the host: it is the only thing that opens these bundles.
2. In the console, under **Settings · Backups · Schedule**, set the time of day (the host's time), how many scheduled
   bundles to keep (1 to 365) and the public key, then choose **Save the schedule**. Or, on the host:

   ```
   sudo fabricctl backup schedule --time 03:00 --keep 7 --public-key age1…
   ```

3. The page shows the next run. After it, it shows the last run and whether it was done or failed.
4. To stop it, choose **Turn it off** (or `sudo fabricctl backup schedule --off`). Scheduled bundles already made are
   kept.

## 4.3.7.3 Download a bundle

1. In **Settings · Backups**, find the bundle in the list. Its light is green when its check passed.
2. Choose **Download**. The file is the encrypted bundle as it is on the host, and the download is audited.
3. Keep the copy on another machine or medium: a bundle on the host is lost with the host.

## 4.3.7.4 Restore one section

This replaces one part of the running install with the bundle's copy. What it holds now is lost, and this cannot be
undone; a safety bundle of it is made first. The bundle must be from the same fabric version as the install. To put
everything back: 4.3.7.6.

1. In **Settings · Backups**, choose **Restore…** on the bundle.
2. Pick the section and choose **Next**. `secrets` is offered only with the whole bundle.
3. Read the warning: what is replaced, and what depends on it.
4. Type the bundle's passphrase (or, for a scheduled bundle, paste the private key line `AGE-SECRET-KEY-1…`) and the
   site's name, then choose **Restore**. The job's page follows it and names the safety bundle when it is done.

On the host:

```
sudo fabricctl restore /var/backups/fabric/<file> --section <name>
```

It asks the site's name, then the key.

## 4.3.7.5 Troubleshoot backups

| Symptom | Cause | Fix |
|---|---|---|
| **Backups** is not under Settings | The sign-in did not find you in Domain Admins, or the DC did not answer then | Ask a Domain Admin to add you (nested groups count), then sign out and in again |
| A bundle's light is amber, "checking" | Its SHA-256 check runs in the background the first time it is listed | Reload the page after a few seconds |
| A bundle's light is red, "differs from the manifest's" | The file was changed or cut short (a copy that did not finish, a disk fault) | Use another bundle; a copy made elsewhere of the same bundle can be put back in `/var/backups/fabric/` |
| "A backup or restore is running" | Another backup, a scheduled one or a restore, holds the lock | Wait for it to end, then try again |
| A section is refused: "restored only into the same version" | The bundle is from another fabric version | Restore the whole bundle instead (setup migrates it) |
| The schedule's last run failed | Read why in the audit log (`BACKUP_FAILED`) or `journalctl -u fabric-backup.service` | Fix the cause (often the disk: the folder needs twice the install's size free), then **Back up now** to check |
| The console did not come back after a whole restore | The restore or setup stopped part way | On the host, read `/var/backups/fabric/console-restore.log`; it names the bundle and the safety bundle. `sudo fabricctl restore <file>` tries again, or restores the safety bundle to go back (1.3.7.6) |
| An upload is refused: "not a bundle's" name | The file was renamed after it was downloaded | Give it back its name, `fabric-<host>-<when>-<kind>.fabric.tar`, and upload it again |
| An upload is refused: it differs from its manifest, or was cut short | The copy is damaged or did not finish | Upload a good copy; nothing of the refused one is kept |
| The setup site refuses: "fabric is installed here" | Restore from a backup is for a host without fabric | Restore from the console (4.3.7.6), or `sudo fabricctl uninstall` first, keeping a bundle |
| The setup site refuses the addresses: "Give this host its new address first" | The host does not have the address yet | Give it the address (4.2.4.8 step 3), then start the site again |
| The setup site refuses an upload: "not a bundle's" name, "not whole", or "cut short" | The file was renamed, damaged or not sent whole | Give it back its name and upload it again, or copy it to the host (step 1); nothing of the refused one is kept |
| The setup site refuses an upload: "setup is not asking for a bundle now" | The page was old: the bundle was already given | Reload the page |
| A restore from the setup site stopped: "Setup stopped" | The restore or setup failed in `fabric-setup.service` | Read `/opt/fabric/config/setup-run.log`. If the bundle was unpacked, `sudo fabricctl setup` carries on; if not, nothing changed: start again |
| An upload stops with a page from the web server (413) | It is larger than 8 GiB | Copy it to the host instead: put it in `/var/backups/fabric/` (root, 0600) and it is listed |

## 4.3.7.6 Restore the whole bundle

This puts everything back as it was in the bundle, in place of the install: the domain, the CA, DNS, the vault,
sign-in, DHCP and the settings. Everything made since is lost. A safety bundle of the install as it is now is made
first, sealed the same way as the chosen bundle. The bundle's addresses must be this host's; to move to other
addresses, follow [4.2.4.8](4.2.4-move-rename.md) instead.

1. In **Settings · Backups**, choose **Restore…** on the bundle, then **Restore the whole bundle…**.
2. Read the warning.
3. Type the bundle's passphrase (or, for a scheduled bundle, paste the private key line `AGE-SECRET-KEY-1…`) and the
   site's name, then choose **Restore the whole bundle**. A refusal (a wrong key, a bundle from a newer fabric or of
   another address) is said at once, and nothing changes.
4. The console goes down in a moment: fabric is removed and set up again on the host. Wait some minutes, then open the
   console and sign in again. Sign-ins are the bundle's, so use a password from then.
5. **Settings · Backups** shows the end of the restore's log under **The last whole restore from the console**.

On the host:

```
sudo fabricctl reinstall --from /var/backups/fabric/<file>
```

It asks the key and a yes. Or, with fabric already removed, `sudo fabricctl restore /var/backups/fabric/<file>`
([1.3.7.6](../volume_1_description_and_architecture/1.3.7-backups.md)).

## 4.3.7.7 Upload a bundle

1. In **Settings · Backups**, under **Upload a bundle**, choose the file. Keep the name it was downloaded with.
2. Choose **Upload**. A bundle of several GiB takes as long as your network needs to send it; keep the page open.
3. Once it is whole and its check passes, it is in the list, ready to restore (4.3.7.4, 4.3.7.6). A refused upload
   leaves nothing behind.

## 4.3.7.8 Restore from the setup site

For a host where fabric is not installed: a new host, or this one after `sudo fabricctl uninstall` kept a bundle. To
move to another VLAN and subnet, follow [4.2.4.8](4.2.4-move-rename.md), giving the host its new address first.

1. Put the bundle in `/var/backups/fabric/` (root, 0600), or note its path on the host. An uninstall leaves its bundle
   there.
2. Run `sudo fabricctl setup`, choose **Guided**, and open the site as the terminal says (4.3.6.1).
3. Choose **Restore from a backup**.
4. Pick the bundle by its number, or type its path. Or, under **Or upload one from this computer**, choose the file
   (keep the name it was downloaded with) and choose **Upload**; keep the page open while it is sent. It is kept in
   `/var/backups/fabric/`. Check what the page shows: its host, domain, addresses, when and by which fabric it was
   made.
5. Type its passphrase, or for a scheduled bundle paste the private key line `AGE-SECRET-KEY-1…`.
6. Keep each address as it is, or type the new network's: the host's address, the subnet, the gateway and the
   upstream DNS server. A wrong key or an address this host does not have is said at once; nothing changes.
7. Read the plan, then choose **Proceed**. The restore and setup run as `fabric-setup.service`; the page follows them.
   A closed browser does not stop it: `sudo fabricctl setup` follows it again.
8. The finish shows what moved, and any of your settings still at the old address: change those in the console. Then
   trust fabric's CA and point DNS at it as for a new install (4.3.6.2, 4.3.6.3). Sign-ins are the bundle's.

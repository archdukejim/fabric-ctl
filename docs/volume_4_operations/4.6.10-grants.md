# 4.6.10 Who may do what, where: grants

Every right below the tiers is a grant ([1.6.13.4](../volume_1_description_and_architecture/1.6.13-access-by-grants.md#16134-grants-and-how-fabric-makes-ad-sssd-and-windows-enforce-them)):
who (groups of people, a person must be in all of them), what (rights by category) and where (groups of machines,
a machine must be in all of them). fabric compiles the grants into groups, one GPO per set of machines and sudo rules,
which Windows and sssd enforce. You change them as root on the root site's fabric host (the Directory Administrators
will do it from the console's Directory → Access page with the console's next pages).

## 4.6.10.1 Reading the grants

```bash
sudo fabricctl domain grant list                 # every grant: who, rights, where, whom it reaches
sudo fabricctl domain grant show server-administrators   # its people and machines by name, its groups and sets
```

A fresh install ships four grants (1.6.13.5): `server-administrators`, `desktop-administrators` and
`network-administrators` (sign-in, sudo of every command and local administrator for `server-admins`,
`desktop-admins`, `network-admins` on their type's machines) and `desktops` (every person signs in at a desktop's
keyboard). The administrators' groups start empty: put people in them to give them their machines. Two templates,
`helpdesk` and `limited-directory-administrator`, give rights to a grant you make from them.

## 4.6.10.2 Giving a group sign-in, sudo or local administrator on some machines

1. Make (or pick) the groups: who (`ops`), and where, by overlapping groups (`site-a` and `machines-servers` for site
   A's servers).
2. Add the grant:

   ```bash
   sudo fabricctl domain grant add site-a-servers --who ops --where site-a,machines-servers \
       --signin remote --sudo /usr/bin/systemctl,/usr/bin/journalctl --description "ops on site A's servers"
   ```

   Rights: `--signin keyboard,remote`, `--sudo ALL` or absolute paths, `--local-admin yes`, `--people
   edit,reset,unlock,disable,add`, `--machines add,move,disable,remove,groups` (the people and machines rights are
   checked by fabric-agent on every call). From a template: `--template helpdesk --who helpdesk-a --where site-a`.
3. fabric compiles it at once and prints what changed. Refused, with why: the tiers' groups (`directory-admins`,
   Domain, Enterprise or Schema Admins, Administrators), the hosts that run a DC (`dc-hosts`), sudo of every command
   for every person or a whole site, a grant with no who, no where or no right, a name taken.

A grant's sudo always runs the commands as root, so sudo's log reads the same everywhere: `--run-as` with any
other account is refused (2.1.6.90).

## 4.6.10.3 Narrowing a right with a restricting grant

To keep site A's desktops to site A's people (every person signs in at every desktop otherwise):

```bash
sudo fabricctl domain grant add site-a-desktops --restrict --who site-a --where site-a,machines-desktops \
    --signin keyboard
```

A restricting grant names where, the right it narrows (sign-in or local administrator) and who alone keeps it there;
`BUILTIN\Administrators` and the machine's `local-admin` always keep it.

## 4.6.10.4 Changing and removing a grant

```bash
sudo fabricctl domain grant set site-a-servers --signin keyboard,remote     # the fields given replace the stored
sudo fabricctl domain grant set site-a-servers --sudo none                  # a list's `none` clears it
sudo fabricctl domain grant remove site-a-servers
```

A grant's kind (allowing or restricting) stays: remove it and add it again to change it. Every change is audited
(`GRANT_ADD`, `GRANT_SET`, `GRANT_REMOVE`, and `GRANT_COMPILE` with what the compile changed).

## 4.6.10.5 Why can, or can't, someone sign in here?

```bash
sudo fabricctl domain grant explain alice web1
```

It lists each grant with the groups alice (or web1) is missing, and what she may do on web1: sign-in at the keyboard
and remotely, local administrator, sudo.

## 4.6.10.6 When a change takes effect

- A change made with fabric (a grant, a person's groups in fabric, a machine fabric adds or sorts) is compiled at once;
  one made elsewhere (RSAT, `samba-tool`, a machine's join) within 5 minutes by the `fabric-grants` timer, or at once
  with `sudo fabricctl domain grant sync`.
- On Linux, someone moved in or out of a grant's groups is seen at their next sign-in; a grant whose rights change at
  sssd's next check (its GPO's version is bumped); sudo rules at sssd's sudo refresh (15 minutes; `sss_cache -E` on
  the machine for at once).
- On Windows, at its policy refresh (90 minutes, or `gpupdate /force`), a person's groups at their next sign-in.

## 4.6.10.7 A machine nobody can sign in to

A machine that no grant reaches admits nobody from the domain (2.1.6.87): only `BUILTIN\Administrators` and its
`local-admin` sign in. A freshly joined machine is reached once its type's group is compiled (at once for one fabric
pre-created, within 5 minutes for one joined with an administrator's password). If it should be reachable:

1. `sudo fabricctl domain grant explain <person> <machine>`: which where groups the machine is missing.
2. Put it in them (its type's group, its site's, a machine group) and run `sudo fabricctl domain grant sync`.

To leave every machine that no grant reaches open to the whole domain instead (sssd's and Windows' default), set
`grants_fallback_open: true` (`sudo fabricctl` → vars, or a settings file), then `sudo fabricctl --apply`. It is a
relaxation: `fabricctl status`, the console's Overview, `fabricctl doctor` and `fabricctl domain status` show it
while it is on. Set it back to `false` and apply to close them again (2.1.6.88).

On Debian 12 and Proxmox VE 8 (sssd 2.8) no grant reaches the machine yet, whatever its groups: everyone from the
domain is refused there, and its local accounts still sign in (2.3.6.19.6).

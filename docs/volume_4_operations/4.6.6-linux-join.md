## 4.6.6.1 What a joined machine gets

An Ubuntu 24.04 or 26.04, or Debian 12 or 13 machine (Proxmox VE 8 and 9 are Debian: the same script) joins the
domain into `OU=machines`, filed by its type (`--type server|desktop`; design:
[1.6.7](../volume_1_description_and_architecture/1.6.7-linux-join-ad.md), [1.6.13.10](../volume_1_description_and_architecture/1.6.13-access-by-grants.md#161310-what-d1-built-080)). Afterwards the domain's people log
on with their domain password (at the console or over SSH), with the same user and group numbers on every machine;
until 0.8.0's grants are built (D3) nothing restricts which of the domain's people may log on; `kinit` gives them a
Kerberos ticket; their home folder
is made at first logon; and they keep logging on with the password they last used while the domain controller is
away. The machine trusts fabric's CA and takes its time from `ntp.<domain>`.

Local users keep working beside the domain's. The join moves the subordinate ids that rootless Podman and Docker give
local users made **after** it above the domain's ids (`SUB_UID_MIN` and `SUB_GID_MIN` 2147483648 in
`/etc/login.defs`); a local user who already has a range overlapping a DC's id range is named in a
`WARNING` line and left as it is (moving it would break that user's container storage). Give such a user a new
range by hand if they use rootless containers ([1.6.3.17](../volume_1_description_and_architecture/1.6.3-samba-directory.md#16317-the-ranges-inside-a-dcs-id-range-070)).

The installer is on the certificates page, `http://info.<domain>/certs/`, which also shows the root CA's SHA-256
fingerprint. The installer refuses to go on unless the CA it downloads has exactly that fingerprint, and then
nothing on the machine has changed.

## 4.6.6.2 Joining with a Directory Administrator's account

On the machine, as root, with the fingerprint from the certificates page:

```bash
wget -nv http://info.<domain>/certs/join-linux.sh
```

```bash
sudo bash join-linux.sh <root CA SHA-256> --user <directory admin> --type server
```

It asks for the admin's password (it is never taken from the command line); the admin is a member of
`directory-admins`. `--type server` (the default) files the machine in `OU=servers`, `--type desktop` in
`OU=desktops`; a network device is not joined this way (pre-create it: `add-machine --type network`). The join puts the
machine in its type's group (`machines-servers`, `machines-desktops`) and its site's (`site-<site>`). The machine's
name is its host name; `--name <name>` gives another (1–15 letters, digits or dashes). `--site <site>` joins it to
another site than the one whose certificates page served the installer; a site the domain does not have is refused
before anything changes.

## 4.6.6.3 Joining with a one-time join password

So that no admin password is typed on the machine, pre-create it on the fabric host:

```bash
sudo fabricctl domain add-machine <name> --type server
```

`--type server|desktop|network` puts it in that type's OU and group (`OU=servers` and `machines-servers`, and so
on) and in this site's group; without it, it stays in `OU=machines` itself. `--os` is gone (0.8.0). The join records
the machine's OS (name and version) on its account.

This prints a one-time join password once. On the machine:

```bash
sudo bash join-linux.sh <root CA SHA-256> --one-time
```

and give that password when asked. The machine's account is in the site's machines from the start.

**Managed by fabric** (the default; 1.6.11.6): after the join, SSH to this machine takes Kerberos (from a domain
machine: `kinit`, then `ssh <machine>`) and **no passwords, for any account, local ones too**; keys keep working.
Make sure you have a key, or the console, before joining a machine you only reach over SSH with a password. The
domain's names come from fabric's DNS. `--unmanaged` joins without this (and `add-machine --unmanaged` for a
pre-created machine); taking a machine out of `fabric-managed` later undoes it within the hour.

## 4.6.6.4 Sudo

From 0.8.0 nobody has sudo from the domain until a rule gives it ([1.6.13.10](../volume_1_description_and_architecture/1.6.13-access-by-grants.md#161310-what-d1-built-080)): there is no default rule and no
fabric-admins group. Rules (some commands, on some machines, for some people or groups) are made with fabric's sudo
editor (4.6.6.8); rules made with Windows' RSAT tools in the domain's `OU=sudoers` keep working and fabric leaves them
as they are. Every joined machine reads the domain's rules. On Ubuntu 26.04 the installer makes
the classic `sudo` the default, because the default `sudo-rs` cannot read the domain's rules.

## 4.6.6.5 When it does not work

- *the root CA served is …, not the fingerprint given*: copy the fingerprint again from the certificates page; if it
  still differs, the machine is not talking to your fabric host — do not continue.
- *the join was refused*: a Directory Administrator (`directory-admins`) with the right password, or (`--one-time`) a machine
  pre-created with `fabricctl domain add-machine` under the same name and the password it printed. A one-time
  password works once.
- *no site … in …*: the `--site` given is not one of the domain's sites; *--type is server or desktop*: a network
  device is pre-created with `add-machine --type network`.
- A person cannot log on: they must be an enabled person in `OU=people`, and have set their own
  password at the web sign-in first; `sudo sssctl user-checks <name>` on the machine shows why.

## 4.6.6.6 Other machines: Windows, TrueNAS SCALE, Proxmox VE

The certificate page (`http://info.<domain>/certs/#join`, linked from the landing page) carries the join steps for each
kind of machine, filled in with this network's names: the Linux script above (Debian installs `sudo` with it, and
a machine using chrony, as Proxmox VE does, gets the site's time source beside its own); Windows (*Settings*, or
`Add-Computer` in PowerShell; the domain's policies do the rest after the restart); TrueNAS SCALE (its nameserver
and NTP set to this network, the root CA imported, then *Directory Services → Active Directory* with a site admin's
account; a certificate for its web interface minted with `fabricctl certs --mint-certs` and imported); Proxmox VE's
web interface (an *Active Directory* realm on the domain's DC over LDAPS, and certificates by ACME from Step-CA's
directory `https://ca.<domain>/acme/acme/directory`). Every machine first uses this network's DNS (it finds the
domain's controller) and its time (sign-ins refuse more than five minutes of skew).

## 4.6.6.7 The fabric host itself

Setup makes the fabric host a member of its own domain (design:
[1.6.11.8](../volume_1_description_and_architecture/1.6.11-host-access.md#16118-the-fabric-host-as-a-member-of-its-domain)),
with nothing to run on it. From 0.8.0 **nobody from the domain but `fabric-admin` signs in to it or gets sudo there** ([1.6.13.10](../volume_1_description_and_architecture/1.6.13-access-by-grants.md#161310-what-d1-built-080)): a host
that runs a domain controller is the top tier; it is run from the console with its local accounts (the one you
installed with, and `local-admin`), and `fabric-admin` breaks glass there (SSH with a Kerberos ticket, and sudo:
[4.6.9](4.6.9-administrators.md)). The host is in the domain as its own computer account, named after it
(`<HOSTNAME>$`, in `OU=fabric-hosts`, in `fabric-managed` and `dc-hosts`, listed under Directory → Machines), so a GPO
linked to `OU=fabric-hosts` reaches it.

- **Who may sign in with a domain account:** the per-OU log-on policies are retired (0.8.0, design
  [1.6.11.4](../volume_1_description_and_architecture/1.6.11-host-access.md#16114-deleted-who-may-sign-in-per-ou));
  sssd on the host refuses every domain account but `fabric-admin` (`access_provider = simple`, `sudo_provider = none`;
  fabric-admin's sudo a local rule in `/etc/sudoers.d/fabric-admin`); the host's
  local accounts and root never go through the domain.

- **The account:** setup makes it and keeps its keys in `/etc/krb5.keytab`; `sudo klist -k /etc/krb5.keytab` shows
  `<HOSTNAME>$` and its `host/` names. Do not remove it in the console while the host is a member (domain sign-in on
  the host stops; `sudo fabricctl setup --step member` makes it again). If setup refuses because *the domain already
  has a computer named* the host's name, that computer is not this host's: remove it in the web console (Directory →
  Machines), or rename the host, then run `sudo fabricctl setup --step member`. At a site whose domain controller
  is read-only the account is made at the writable domain controller it replicates from and cached by the read-only
  one (1.6.11.13); when that domain controller does not answer, setup refuses and changes nothing: bring the link
  back (`fabricctl federation status`) and run `sudo fabricctl setup --step member` again. If it says the read-only
  domain controller *could not cache* the account, its `rodc-cache-dc-NNNN` group is not on its allow list (a
  site joined before 0.7.1): add it there (RSAT: the read-only DC's account, *Password Replication Policy*, Allow),
  then run the step again. Setup refuses a domain controller named as
  the host (`dc_name` equal to the host's name; fabric never names a new DC so, 2.1.6.65, so only an installed DC
  can): rename the host (`hostname`), or set `host_join_domain: false`.

- **Local accounts stay as they were:** root, the account you installed with and its `sudo` work as before, also
  while the domain controller is stopped.
- **Check it:** `getent passwd <name>` shows a person's domain account (names still resolve); `sudo sssctl
  user-checks <name>` shows the sign-in refused.
- **Leave it out:** at install, choose *Advanced* in setup's plan and answer `n` to *Make this host a member of its
  domain* (or set `host_join_domain: false` in the settings file for an unattended install, or decline the
  question *This host as a member of its domain*). On an installed host, `sudo fabricctl setup --undo member` removes
  the host's account from the domain, puts every file back as it was and turns domain sign-in off; `sudo fabricctl status` then shows it declined.
  `sudo fabricctl setup --approve member --step member` makes the host a member again. An unattended upgrade from
  a release before 0.9 needs `--approve member` (or `--decline member`).

## 4.6.6.8 Host groups and sudo rules

A **host group** is a group of the domain's machines, `hosts-<name>` (design:
[1.6.11.7](../volume_1_description_and_architecture/1.6.11-host-access.md#16117-host-groups-and-sudo-rules)). A
**sudo rule** says who may run which commands, as whom, on which host group (or on every joined machine); every
joined Linux machine reads it from the domain's `OU=sudoers`.

On the fabric host:

```bash
sudo fabricctl machines group create web                 # the group hosts-web
sudo fabricctl machines group add web web01              # one of the domain's machines in it (remove: take it out)
sudo fabricctl machines groups                           # every host group, its machines and the rules on it
sudo fabricctl sudo add web-restart --who alice,%web-ops         --commands "/usr/bin/systemctl restart nginx,/usr/bin/journalctl -u nginx" --hosts web
sudo fabricctl sudo list                                 # fabric's rules and admins' own
sudo fabricctl sudo remove web-restart
sudo fabricctl machines group delete web                 # refused while a rule names it
```

- **Who:** user names and `%groups`, separated by commas. **Commands:** absolute paths, with their arguments, or
  `ALL`. **As** (`--as`): the account the commands run as, `root` when left out. **Where** (`--hosts`): a host
  group, or `ALL` (the default) for every joined machine.
- **Refused:** a rule giving `ALL` commands to everyone (`ALL`, `%Domain Users`, `%users`) or to a whole site
  (`%site-<site>`): name the people or groups who need it, or the commands. Also refused, each
  saying why: someone or a group not in the domain, a command that is not an absolute path, a host group or machine
  the domain does not have, a name already taken.
- **Only fabric's rules are removed here:** `sudo list` marks each rule `fabric` or *not fabric's* (made with
  other tools: read-only here).
- **A rule follows its host group:** a machine put in the group gets the rule, one taken out loses it, at once
  (the machines' sssd reads the change at its next refresh, within about 15 minutes; `sudo systemctl restart sssd`
  on a machine reads it now). A machine added to the group with RSAT is picked up at the next apply.

In the web console: **Directory → Machines**. *Host groups* lists each group with its machines and rules; *New host
group* makes one, the membership form puts a machine in or takes it out, *Remove* deletes a group no rule names
(permission `machines:admin`). *Sudo rules* lists every rule of the domain; *Add* takes the name, who and the commands
(each separated by commas), as whom and where; *Remove* is offered on fabric's rules only (permission `sudo:admin`,
the admin bundle's). Each change waits on the Machines page until its **Apply** ([4.8.4](4.8.4-apply.md#4841-changes-wait-for-apply)).

## 4.6.6.9 The fabric host as a managed machine (0.7.1)

The fabric host is a machine fabric manages, in `OU=fabric-hosts` (design:
[1.6.11.11](../volume_1_description_and_architecture/1.6.11-host-access.md#161111-the-fabric-host-as-a-machine-fabric-manages-071)).
Link a GPO to `OU=fabric-hosts` to aim it at fabric's hosts only; GPOs on `OU=machines` do not reach them.

- **Signing in over SSH with a domain account:** refused from 0.8.0 (4.6.6.7); until then a fabric admin signed in
  with a Kerberos ticket (`ssh -K <name>@<host>.<ad_domain>`).
- **Local accounts stay as they were**, over SSH too: the account you installed with signs in with its password (or
  its key) also while the domain controller is stopped. This is the way in when the domain controller is broken; keep
  that account's password. To turn passwords off for local accounts as well, set `PasswordAuthentication no` in your
  own sshd configuration (fabric leaves it alone) only once a key works for that account.
- **Check it:** `sudo fabricctl domain host-managed` says whether the host's account is in `fabric-managed`
  and applies or removes fabric's SSH and DNS settings at once (the timer `fabric-host-managed.timer` does the same
  hourly). `sudo sshd -T | grep -i gssapi` shows Kerberos on.
- **Take the host out of fabric's management:** remove it from `fabric-managed` (web console, Directory →
  Machines, or RSAT); within the hour, or at once with `sudo fabricctl domain host-managed`, the SSH and DNS settings
  are removed. It stays a member of its domain; setup never puts it back.
- **Renewing its machine password:** off by default. Set `host_machine_password_renew_days` (1 to 999) in the
  settings file (`/opt/fabric/config/vars.yaml`), then run `sudo fabricctl setup --step member`: adcli is installed and sssd
  renews the password once it is that old. 0 turns it off again.

## 4.10.2.1 What it is, and after the upgrade

From 0.8.0 every site's VLANs, subnets, ranges and addresses are one plan, kept in the domain (design:
[1.10.4](../volume_1_description_and_architecture/1.10.4-address-manager.md)); Kea and the site's static names are
rendered from it at every apply. `vars.yaml` keeps only `dhcp.interfaces` and the global defaults (4.10.1).

At the first apply (or setup) of 0.8.0 each site's `dhcp.subnets` move into its plan once (1.10.4.15); the apply
prints what moved and where its record is (`/opt/fabric/config/ipam-upgrade-<time>.json`). Then:

1. Check the VLANs fabric chose for subnets that had none (the apply lists them):
   `sudo fabricctl ipam show`.
2. Correct a VLAN ID that is wrong by removing the VLAN and adding it again with the right one (4.10.2.3): its
   subnet, ranges and addresses go with `vlan remove --force`, so note them first (`fabricctl ipam export`).
3. From then on `fabricctl dhcp add-subnet`, `set-subnet`, `remove-subnet`, `reserve` and `unreserve` (and the Kea
   tab's same actions) refuse: use the commands below. Global options and client classes stay with `fabricctl dhcp
   option` and `class` (4.10.1).

Every change below is checked first, and a refusal says why and changes nothing. A change to this site's plan is
applied at once (Kea, DNS, the firewall) unless `--no-apply`.

## 4.10.2.2 Seeing the plan

```bash
sudo fabricctl ipam show                 # this site: its number, each VLAN, its subnet and ranges, every address
sudo fabricctl ipam show house2          # another site's plan
sudo fabricctl ipam find 10.1.20.37      # the address's row in any site, or its subnet and range if unrecorded
sudo fabricctl ipam find cam1            # an address or a VLAN by name
sudo fabricctl ipam find aa:bb:cc:dd:ee:ff
sudo fabricctl ipam export > plan.csv    # every site's address table (export <site> for one)
```

`show` lists this site's live leases beside the addresses (kind `lease` for one nobody recorded). The CSV's columns:
site, VLAN, VLAN name, subnet, address, kind, range, name, MAC, owner, DNS, lease, notes.

## 4.10.2.3 VLANs and their subnets

```bash
sudo fabricctl ipam vlan add 20 --name iot --purpose "cameras and sensors"     # 10.<site>.20.0/24, split suggested
sudo fabricctl ipam vlan add 30 --name guest --subnet 192.168.30.0/24 --access guest
sudo fabricctl ipam vlan add 300 --name lab --subnet 10.1.64.0/22 --gateway 10.1.64.1 --no-split
sudo fabricctl ipam vlan add 40 --name printers --no-subnet                   # a record only
sudo fabricctl ipam vlan set 20 --notes "trunked on switch1 port 24" --dhcp off
sudo fabricctl ipam vlan remove 40
```

- Without `--subnet` a VLAN from 1 to 255 is given `10.<site number>.<VLAN>.0/24` with gateway `.1`, static
  `.2-.99`, DHCP `.100-.249` and reserved `.250-.254`; `--no-split` leaves out the ranges. A site without a number is
  given its suggested one, and the command says which.
- `--allow-overlap "<why>"` lets a subnet overlap another site's network where the two are never routed together
  (NAT, separate paths).
- `--relay IP` is needed only when the relay's address lies outside the subnet (1.10.3.2).
- `vlan remove` refuses while the subnet records addresses; `--force` removes them with it.

## 4.10.2.4 Ranges

```bash
sudo fabricctl ipam range add 20 dhcp 10.1.20.100 10.1.20.199
sudo fabricctl ipam range add 20 reserved 10.1.20.250 10.1.20.254 --notes "spare for the new switch"
sudo fabricctl ipam range remove 20 10.1.20.100          # by its first address
```

Ranges never overlap. A `dhcp` range is Kea's pool and may hold only reservations, so one over a static address or
the gateway is refused.

## 4.10.2.5 Addresses

```bash
sudo fabricctl ipam address add 10.1.20.10 --kind static --name nas --owner office --dns on   # nas.<domain> + PTR
sudo fabricctl ipam address add 10.1.20.150 --kind reservation --mac aa:bb:cc:dd:ee:ff --name cam1
sudo fabricctl ipam address add 10.1.20.2 --kind infrastructure --name switch1 --dns on
sudo fabricctl ipam address set 10.1.20.10 --notes "backups at 02:00"
sudo fabricctl ipam address remove 10.1.20.150
```

- One claim per address: a second (or the gateway's address) is refused, naming the first.
- A reservation needs the device's MAC and may lie inside a DHCP range; the device gets it at its next renewal.
- A static address outside the static ranges is warned about, never refused.
- `--dns on` publishes `<name>.<domain>` and its PTR at the apply, a reservation's too:
  `sudo fabricctl ipam address add 10.1.20.151 --kind reservation --mac aa:bb:cc:dd:ee:01 --name cam3 --dns on`.
- A name set by hand always wins over DHCP's (2.1.10.20): a reservation published with `--dns on`, or whose address
  a record of the settings' `dns:` names, gets no DHCP registration at all (no `<name>.dhcp.<domain>`, no PTR from
  DHCP); its names are `<name>.<domain>` and its PTR. A name DHCP registered for the device before is deleted from
  `dhcp.<domain>` at the apply, and hourly after it (`fabric-dhcp-names.timer`, 2.1.10.22); each deletion is in the
  audit log (`DHCP_NAME_CLEAR`). To run it at once: `sudo fabricctl dhcp clean-names`. If BIND refuses it, the apply
  ends with an `Error:` and the timer's run fails (`systemctl status fabric-dhcp-names`); fix what it names, then run
  it again. BIND refuses DHCP any change to a PTR set by hand.

## 4.10.2.6 Another site's plan

The site above a house may change the house's plan with `--site <house>` on any change; a house cannot change its
parent's. The change is written to the house's plan on this site's DC and replicates to the house, where it takes
effect at the house within 30 s (its plan poll, 4.10.2.14; a change DNS needs waits for its next apply).

```bash
sudo fabricctl ipam vlan add 10 --name mgmt --site house2
sudo fabricctl ipam address add 10.2.10.5 --kind static --name nas --site house2
```

## 4.10.2.7 The gateway's DHCP relay

Each VLAN's gateway relays its DHCP to fabric (1.10.4.5). On a UniFi gateway: *Settings → Networks →* the VLAN's
network *→ DHCP mode: DHCP Relay*, server: fabric's address (`host_ip`). Other gateways call it a DHCP helper or
relay; point it at the same address. fabric opens 67/udp for it at the apply.

## 4.10.2.8 The site's number

The site's number is the second octet of every subnet fabric suggests, `10.<number>.<VLAN>.0/24` (2.1.10.12). Setup
asks it once ([3.3.1.1.5](../volume_3_installation/3.3.1-running-setup.md#33115-the-sites-number-080)); to see or
change it later:

```bash
sudo fabricctl ipam block                  # this site's number, or "none (suggested n)"
sudo fabricctl ipam block 4                # set it: 1-255, no other site's
sudo fabricctl ipam block 3 --site house2  # a site below this one
```

Changing it changes only what fabric suggests from then on; subnets already in the plan keep their networks, and
nothing is applied. A number another site has is refused, naming that site.

## 4.10.2.9 More than one subnet on a VLAN

A VLAN may have more than one subnet, for example a second network while renumbering (2.1.10.18):

```bash
sudo fabricctl ipam subnet add 20 10.1.21.0/24 --notes "renumbering"   # named iot-2 (after VLAN 20, iot)
sudo fabricctl ipam subnet add 40 10.1.40.0/24                         # a first subnet for a VLAN kept as a record
sudo fabricctl ipam subnet set iot-2 --dhcp off                        # by name, or by network
sudo fabricctl ipam subnet remove 10.1.21.0/24 --force                 # with its ranges and addresses
```

- `subnet add` takes the same options as `vlan add` (`--name`, `--gateway`, `--dhcp`, `--relay`, `--no-split`,
  `--allow-overlap`); every rule still holds (no overlap without a reason, one claim per address).
- On a VLAN with several subnets, `vlan set`'s subnet options (`--gateway`, `--dhcp`, `--relay`,
  `--allow-overlap`) are refused: change each subnet with `subnet set`. `range add 20 …` and
  `address add … --vlan 20` go to the VLAN's subnet holding the address.
- `subnet remove` refuses while the subnet records addresses, unless `--force`; the VLAN stays.

## 4.10.2.10 A site with a read-only DC

Its DHCP subnets stay in its `vars.yaml` after the upgrade and are served from there; each apply says so. They move
into the plan once the site above can write it (S8, 2.1.10.19); nothing is to be done by hand until then. Its number
is set from the site above: `sudo fabricctl ipam block <n> --site <site>` there.

## 4.10.2.11 DHCP options

DHCP options are kept in the plan at five places (design:
[1.10.4.24](../volume_1_description_and_architecture/1.10.4-address-manager.md)): the organisation (every site), the
site (every subnet here), a subnet, a client class, and a reservation's address. A client gets the most specific:
its reservation's, then its subnet's, then a class's, then the site's, then the organisation's.

```bash
sudo fabricctl ipam option show                         # the organisation's and this site's, each subnet's
sudo fabricctl ipam option show subnet iot              # what a client on iot gets, and where each comes from
sudo fabricctl ipam option set site ntp-servers 10.1.10.1
sudo fabricctl ipam option set subnet iot domain-name-servers 10.1.20.1
sudo fabricctl ipam option set address 10.1.20.20 66 boot.lan        # by code: kept by its name (tftp-server-name)
sudo fabricctl ipam option remove subnet iot domain-name-servers
sudo fabricctl ipam option set org ntp-servers 10.0.0.1             # the organisation's (see 4.10.2.13)
```

- A custom option needs its definition first, at the organisation or the site:
  `sudo fabricctl ipam option define site ztp-url 239 string`, then `option set … ztp-url http://ztp.lan/cfg`;
  `option undefine site ztp-url` once no option uses it.
- A client class: `sudo fabricctl ipam class add site uefi --test "option[93].hex == 0x0007" --boot-file ipxe.efi`,
  then `option set class uefi tftp-server-name boot.lan`; `class remove site uefi`. A subnet's own option beats a
  class's (Kea's order): `option show subnet <name>` marks such a class row "overridden".
- `--site <house>` changes a house's options from the site above it.
- Each change is checked (a name Kea does not know is refused, saying how to define it), written, audited, and applied
  here at once (`--no-apply` to wait); other sites take it within 30 s (4.10.2.14).
- In the console: *Kea → DHCP options* (`/kea/options`): the same, with a subnet's or reservation's effective options
  and their sources under *What a client gets*.

After the upgrade to 0.8.0 the options and classes in `vars.yaml` move into the site's options at the first apply
(it prints what moved, and the record `/opt/fabric/config/ipam-options-upgrade-<time>.json`). From then on
`fabricctl dhcp option` without `--subnet`, and `fabricctl dhcp class`, refuse and point here.

## 4.10.2.12 Network boot (netboot presets)

A preset points PXE, iPXE and UEFI HTTP boot clients at a boot server you run (fabric serves no boot files) (design:
[1.10.4.25](../volume_1_description_and_architecture/1.10.4-address-manager.md)).

```bash
sudo fabricctl ipam netboot on 20 --server 10.1.10.5 --bios undionly.kpxe --uefi ipxe.efi \
     --ipxe http://boot.lan/boot.ipxe               # every subnet of VLAN 20
sudo fabricctl ipam netboot on 10.1.20.20 --server 10.1.10.6 --bios kiosk.0        # one reservation
sudo fabricctl ipam netboot on lab --server 10.1.10.5 --http http://boot.lan/grubx64.efi   # UEFI HTTP boot
sudo fabricctl ipam netboot show 20                 # the preset and the classes Kea gets
sudo fabricctl ipam netboot off 20
```

- `--server` is the boot server's address (a name works too; some firmware reads only an address, and `show` warns).
- Give at least one of `--bios`, `--uefi`, `--arm64` (files on the boot server's TFTP), `--ipxe` (an iPXE script's
  URL) or `--http` (a UEFI HTTP boot URL). With iPXE binaries as the PXE files, give `--ipxe` too, or a client that
  has loaded iPXE is handed iPXE again (`on` warns).
- A reservation's preset replaces its subnet's for that client. A static address gets no DHCP answer, so it takes none.
- In the console: the *Netboot* form under each subnet and reservation on *Kea → DHCP options*.

To check: boot a client of each kind and watch Kea's log (`sudo docker logs kea-dhcp4`) or the boot server's.

## 4.10.2.13 Letting another site edit the organisation's options

By default only the top site's admins (and fabric-admins) change the organisation's options. At the top site:

```bash
sudo fabricctl ipam option-editors                  # the sites that may
sudo fabricctl ipam option-editors add house2
sudo fabricctl ipam option-editors remove house2
```

Then at house2, its admins change them as at the top (`fabricctl ipam option set org …`, or the organisation's forms
on *Kea → DHCP options*). In the console the change also needs the permission `dhcp:org-options`, which every site's
admin role has and no operator role does. A site not added is refused by the directory: "not permitted for this site".
Every change is audited with the person and the site it came from; each site's Kea takes it within 30 s.

## 4.10.2.14 The plan poll

`fabric-plan-watch.timer` checks the domain every 30 s while Kea is on (design:
[1.10.4.26](../volume_1_description_and_architecture/1.10.4-address-manager.md)); a change made at another site to
this site's plan or options re-renders Kea alone and restarts it. Nothing is to be done. To see it work or check it:

```bash
systemctl list-timers fabric-plan-watch.timer       # when it last ran and runs next
systemctl status fabric-plan-watch.service          # the last run: failed when the DC, OpenBao or Kea's check refused
sudo fabricctl ipam watch                           # run it now and say what it did
```

- "an apply is needed": the change also touches DNS (a published name, a new subnet's reverse zone); run
  `sudo fabricctl --apply` to bring DNS in line.
- "busy": an apply was running; the next run tries again.
- A failed run keeps the last state, so the next run tries the same change again; fix the cause shown in the status
  (OpenBao sealed: unseal it, [4.7.1](4.7.1-openbao.md); Kea's check refusing: the option named in the message).

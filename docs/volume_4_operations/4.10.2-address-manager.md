## 4.10.2.1 What it is, and where 0.9.0's port stands

From 0.9.0 every site's VLANs, subnets, ranges and addresses are one plan, kept in the domain (design:
[1.10.4](../volume_1_description_and_architecture/1.10.4-address-manager.md)). Kea and the site's static names
are rendered from it at every apply.

0.9.0 is ported onto 0.8.0's directory area by area (1.10.4.41), and this chapter grows with it:

- **Ported:** the commands below, which write the plan, its DHCP options and its netboot presets; the old
  `fabricctl dhcp` subnet commands as their aliases (4.10.2.12); Kea and the site's names rendered from the plan at
  every apply, the plan poll (4.10.2.13) and Sync now (4.10.2.14); the upgrade's move of a site's `dhcp.subnets`
  and options into the plan; ping-check and the scans, here and at another site (4.10.2.15, 4.10.2.16); setup's
  question for the site's number (4.10.2.8) and the setup wizard's DHCP step (4.8.3.1); the console's DHCP →
  Networks (with Sync now and the scan page) and DHCP options (4.10.2.17, 4.10.2.18).
- **Still to come:** the lab's run of the whole port against real DCs (1.10.4.41, area 10).

At the first apply (or setup) of 0.9.0 each site's `dhcp.subnets` move into its plan once (1.10.4.15), and at the
apply after it the settings' global options. At a site whose DC is read-only the move is written through its
writable partner DC (2.1.10.43). The apply prints what moved and where its record is
(`/opt/fabric/config/ipam-upgrade-<time>.json`). Kea keeps serving what it served: the next apply renders the same
subnets from the plan. Then:

1. Check the VLANs fabric chose for subnets that had none (the apply lists them): `sudo fabricctl ipam show`.
2. Correct a VLAN ID that is wrong by removing the VLAN and adding it again with the right one (4.10.2.3): its
   subnet, ranges and addresses go with `vlan remove --force`, so note them first (`fabricctl ipam export`).
3. From then on use the commands below; the old `fabricctl dhcp` subnet commands are their aliases for one release
   (4.10.2.12), and the global options are `fabricctl ipam option` (4.10.2.10).

You run every command as root on a fabric host. Root acts for the Enterprise Admin, so it may change any site's
plan. Who else may change a plan is set by the grants' networks rights (4.6.10.8). A change to a plan never needs an
apply of another site.

## 4.10.2.2 Seeing the plan

```bash
sudo fabricctl ipam show                 # this site: its number, each VLAN, its subnet and ranges, every address
sudo fabricctl ipam show house2          # another site's plan
sudo fabricctl ipam find 10.1.20.37      # the address's row in any site, or its subnet and range if unrecorded
sudo fabricctl ipam find cam1            # an address or a VLAN by name
sudo fabricctl ipam find aa:bb:cc:dd:ee:ff
sudo fabricctl ipam export > plan.csv    # every site's address table (export <site> for one)
```

`show` lists this site's live leases beside the addresses: a lease on an address nobody recorded has the kind
`lease`.

The CSV's columns are: site, VLAN, VLAN name, subnet, address, kind, range, name, MAC, owner, DNS, lease and notes.
A cell a spreadsheet would read as a formula is written with a leading apostrophe.

## 4.10.2.3 VLANs and their subnets

```bash
sudo fabricctl ipam vlan add 20 --name iot --purpose "cameras and sensors"     # 10.<site>.20.0/24, split suggested
sudo fabricctl ipam vlan add 30 --name guest --subnet 192.168.30.0/24 --access guest
sudo fabricctl ipam vlan add 300 --name lab --subnet 10.1.64.0/22 --gateway 10.1.64.1 --no-split
sudo fabricctl ipam vlan add 40 --name printers --no-subnet                   # a record only
sudo fabricctl ipam vlan set 20 --notes "trunked on switch1 port 24" --dhcp off
sudo fabricctl ipam vlan remove 40
```

- **The suggested subnet:** without `--subnet`, a VLAN from 1 to 255 is given `10.<site number>.<VLAN>.0/24`, split
  as:
  - gateway `.1`;
  - static `.2-.99`;
  - DHCP `.100-.249`;
  - reserved `.250-.254`.

  `--no-split` leaves out the ranges. A site without a number is given its suggested one, and the command says which.
- **Overlaps:** `--allow-overlap "<why>"` lets a subnet overlap another site's network, for two networks that are
  never routed together (NAT, separate paths).
- **The relay:** `--relay IP` is needed only when the relay's address lies outside the subnet (1.10.3.2).
- **Removing:** `vlan remove` refuses while the subnet records addresses. `--force` removes them with it.

## 4.10.2.4 Ranges

```bash
sudo fabricctl ipam range add 20 dhcp 10.1.20.100 10.1.20.199
sudo fabricctl ipam range add 20 reserved 10.1.20.250 10.1.20.254 --notes "spare for the new switch"
sudo fabricctl ipam range remove 20 10.1.20.100          # by its first address
```

Ranges never overlap. A `dhcp` range is Kea's pool and may hold only reservations, so a `dhcp` range over a static
address or over the gateway is refused.

## 4.10.2.5 Addresses

```bash
sudo fabricctl ipam address add 10.1.20.10 --kind static --name nas --owner office --dns on   # nas.<domain> + PTR
sudo fabricctl ipam address add 10.1.20.150 --kind reservation --mac aa:bb:cc:dd:ee:ff --name cam1
sudo fabricctl ipam address add 10.1.20.2 --kind infrastructure --name switch1 --dns on
sudo fabricctl ipam address set 10.1.20.10 --notes "backups at 02:00"
sudo fabricctl ipam address remove 10.1.20.150
```

- **One claim per address:** a second claim, or a claim on the gateway's address, is refused, naming the first.
- **Reservations:** a reservation needs the device's MAC and may lie inside a DHCP range.
- **Static addresses:** one outside the static ranges is warned about, never refused.
- **DNS:** `--dns on` publishes `<name>.<domain>` and its PTR at the apply, a reservation's too:
  `sudo fabricctl ipam address add 10.1.20.151 --kind reservation --mac aa:bb:cc:dd:ee:01 --name cam3 --dns on`.
- **A name set by hand always wins over DHCP's** (2.1.10.20): a reservation published with `--dns on`, or whose
  address a record of the settings' `dns:` names, gets no DHCP registration at all (no `<name>.dhcp.<domain>`, no PTR
  from DHCP); its names are `<name>.<domain>` and its PTR. BIND refuses DHCP any change to a PTR set by hand.
- **A DHCP name left behind** for such a device is deleted from `dhcp.<domain>` at the apply, and hourly after it
  (`fabric-dhcp-names.timer`, 2.1.10.22); each deletion is in the audit log (`DHCP_NAME_CLEAR`). To run it at once:
  `sudo fabricctl dhcp clean-names`. If BIND refuses it, the apply ends with an `Error:` and the timer's run fails
  (`systemctl status fabric-dhcp-names`); fix what it names, then run it again.

## 4.10.2.6 Another site's plan

`--site <site>` on any change writes to that site's plan.

```bash
sudo fabricctl ipam vlan add 10 --name mgmt --site house2
sudo fabricctl ipam address add 10.2.10.5 --kind static --name nas --site house2
```

- **Who may do it:** root may change any site's plan. Anyone else needs a grant with the networks right `plan` at
  that site, or at `all` (4.6.10.8). The Directory Administrators may do it everywhere.
- **Where it is written:** this site's DC, or at a site with a read-only DC, the writable DC it replicates from. It
  reaches the other site by replication.
- **When it takes effect:** at that site's next rendering of its plan.

## 4.10.2.7 The gateway's DHCP relay

Each VLAN's gateway relays its DHCP to fabric (1.10.4.5).

- **On a UniFi gateway:** *Settings → Networks →* the VLAN's network *→ DHCP mode: DHCP Relay*, server: fabric's
  address (`host_ip`).
- **On other gateways:** the setting may be called a DHCP helper or a relay. Point it at the same address.

fabric opens 67/udp for the relay at the apply.

## 4.10.2.8 The site's number

The site's number is the second octet of every subnet fabric suggests, `10.<number>.<VLAN>.0/24` (2.1.10.12). Its
suggestion is the site's order in the domain. To see it or set it:

```bash
sudo fabricctl ipam block                  # this site's number, or "none (suggested n)"
sudo fabricctl ipam block 4                # set it: 1-255, no other site's
sudo fabricctl ipam block 3 --site house2  # another site's
```

Changing the number changes only what fabric suggests from then on: subnets already in the plan keep their
networks, and nothing is applied. A number another site has is refused, naming that site.

Setup asks it once, at its start step, while the site has none: `Site number [<suggestion>]:`, Enter takes the
suggestion (1.10.4.18.1). An unattended setup takes the suggestion. A site with a read-only DC is not asked: setup
names the `fabricctl ipam block` command to run (it writes at the writable partner DC). If the domain did not
answer, setup says so: set the number later with the commands above.

## 4.10.2.9 More than one subnet on a VLAN

A VLAN may have more than one subnet, for example a second network while renumbering (2.1.10.18):

```bash
sudo fabricctl ipam subnet add 20 10.1.21.0/24 --notes "renumbering"   # named iot-2 (after VLAN 20, iot)
sudo fabricctl ipam subnet add 40 10.1.40.0/24                         # a first subnet for a VLAN kept as a record
sudo fabricctl ipam subnet set iot-2 --dhcp off                        # by name, or by network
sudo fabricctl ipam subnet remove 10.1.21.0/24 --force                 # with its ranges and addresses
```

- **Options:** `subnet add` takes the same options as `vlan add` (`--name`, `--gateway`, `--dhcp`, `--relay`,
  `--no-split`, `--allow-overlap`). Every rule still holds: no overlap without a reason, and one claim per address.
- **On a VLAN with several subnets:**
  - `vlan set`'s subnet options (`--gateway`, `--dhcp`, `--relay`, `--allow-overlap`) are refused: change each
    subnet with `subnet set`.
  - `range add 20 …` and `address add … --vlan 20` go to the VLAN's subnet that holds the address.
- **Removing:** `subnet remove` refuses while the subnet records addresses, unless you give `--force`. The VLAN
  stays.

## 4.10.2.10 DHCP options

DHCP options are kept in the plan at five places (design:
[1.10.4.24](../volume_1_description_and_architecture/1.10.4-address-manager.md)):

- the domain (every site);
- the site (every subnet here);
- a subnet;
- a client class;
- a reservation's address.

A client gets the most specific: its reservation's, then its subnet's, then a class's, then the site's, then the
domain's.

```bash
sudo fabricctl ipam option show                         # the domain's and this site's, each subnet's
sudo fabricctl ipam option show subnet iot              # what a client on iot gets, and where each comes from
sudo fabricctl ipam option set site ntp-servers 10.1.10.1
sudo fabricctl ipam option set subnet iot domain-name-servers 10.1.20.1
sudo fabricctl ipam option set address 10.1.20.20 66 boot.lan        # by code: kept by its name (tftp-server-name)
sudo fabricctl ipam option remove subnet iot domain-name-servers
sudo fabricctl ipam option set domain ntp-servers 10.0.0.1          # the domain's: every site
```

- **Custom options:** a custom option needs its definition first, in the domain's set or the site's:
  1. `sudo fabricctl ipam option define site ztp-url 239 string`;
  2. `sudo fabricctl ipam option set site ztp-url http://ztp.lan/cfg`;
  3. `option undefine site ztp-url` once no option uses it.
- **Client classes:**
  - `sudo fabricctl ipam class add site uefi --test "option[93].hex == 0x0007" --boot-file ipxe.efi`;
  - `option set class uefi tftp-server-name boot.lan` (`--domain` for a class of the domain's set);
  - `class remove site uefi`.

  A subnet's own option beats a class's (Kea's order): `option show subnet <name>` marks such a class row
  "overridden".
- **0.8's words:** `org` and `--org` still work, and mean `domain` and `--domain`.
- **Who may change them:** root may change any. Anyone else needs a grant with the networks right `options`: at the
  site for its own options, or at `all` for the domain's (4.6.10.8). `--site <site>` changes another site's options.
- **What a change does:** it is checked (a name Kea does not know is refused, saying how to define it), written to
  the domain, and audited. This site's Kea takes it at once (the change applies here unless `--no-apply`); another
  site's within 30 s (its plan poll, 4.10.2.13).

## 4.10.2.11 Network boot (netboot presets)

A preset points PXE, iPXE and UEFI HTTP boot clients at a boot server you run (design:
[1.10.4.25](../volume_1_description_and_architecture/1.10.4-address-manager.md)). fabric serves no boot files.

```bash
sudo fabricctl ipam netboot on 20 --server 10.1.10.5 --bios undionly.kpxe --uefi ipxe.efi \
     --ipxe http://boot.lan/boot.ipxe               # every subnet of VLAN 20
sudo fabricctl ipam netboot on 10.1.20.20 --server 10.1.10.6 --bios kiosk.0        # one reservation
sudo fabricctl ipam netboot on lab --server 10.1.10.5 --http http://boot.lan/grubx64.efi   # UEFI HTTP boot
sudo fabricctl ipam netboot show 20                 # the preset and the classes Kea gets
sudo fabricctl ipam netboot off 20
```

- **The server:** `--server` is the boot server's address. A name works too, but some firmware reads only an
  address, and `on` warns.
- **What to boot:** give at least one of these:
  - `--bios`, `--uefi` or `--arm64`: files on the boot server's TFTP;
  - `--ipxe`: an iPXE script's URL;
  - `--http`: a UEFI HTTP boot URL.

  With iPXE binaries as the PXE files, give `--ipxe` too, or a client that has loaded iPXE is handed iPXE again
  (`on` warns).
- **A reservation's preset** replaces its subnet's for that client. A static address gets no DHCP answer, so it takes
  none.
- **Who may set one:** the same as the site's options: the networks right `options` at the site.

To check: boot a client of each kind and watch Kea's log (`sudo docker logs kea-dhcp4`) or the boot server's.

## 4.10.2.12 The 0.7 and 0.8.0 DHCP commands as aliases

Once a site's subnets live in its plan, for one release, the old `fabricctl dhcp` subnet commands still work. Each
says which `fabricctl ipam` command it stands for; move scripts to the new ones:

| Old command | Now |
|---|---|
| `fabricctl dhcp add-subnet <net> --name N [--vlan V] [--router IP] [--pool "a - b"]…` | a VLAN (when V has none; without `--vlan` the lowest free ID) and its subnet, the pools as DHCP ranges (`ipam vlan add` / `subnet add`, `range add`) |
| `fabricctl dhcp set-subnet <name> [--router IP\|none] [--notes T] [--add-pool …] [--remove-pool …]` | `ipam subnet set` and `range add\|remove`; `--name` and `--vlan` are refused (remove and add the subnet, or `ipam vlan set`) |
| `fabricctl dhcp remove-subnet <name> [--force]` | `ipam subnet remove` (`--force`: with its recorded addresses) |
| `fabricctl dhcp reserve <mac> <ip> [<hostname>]` | `ipam address add <ip> --kind reservation --mac <mac> --name <hostname>` |
| `fabricctl dhcp unreserve <mac>` | `ipam address remove` of the reservation that MAC holds |

- **Options and classes:** `fabricctl dhcp option` and `class` refuse, and name the command that makes the change:
  `fabricctl ipam option` and `ipam class` (4.10.2.10) for the global options and classes, the `ipam` subnet and
  address commands for a subnet's or a reservation's.
- **Who may:** the same as `fabricctl ipam` (4.10.2.6). Root may change any site's plan.
- **When the plan holds the subnets:** once `vars.yaml` carries no `dhcp.subnets` and the site has read its plan: after
  the upgrade's move at the first apply of 0.9.0 (4.10.2.1).

## 4.10.2.13 The plan poll

`fabric-plan-watch.timer` checks the domain every 30 s while Kea is on (design:
[1.10.4.26](../volume_1_description_and_architecture/1.10.4-address-manager.md)); a change made at another site to
this site's plan or options re-renders Kea alone and restarts it. Nothing is to be done. To see it work or check it:

```bash
systemctl list-timers fabric-plan-watch.timer       # when it last ran and runs next
systemctl status fabric-plan-watch.service          # the last run: failed when the DC, OpenBao or Kea's check refused
sudo fabricctl ipam watch                           # run it now and say what it did
```

- "an apply is needed": the change also touches DNS (a published name, a new subnet's reverse zone); run Sync now
  (4.10.2.14) or `sudo fabricctl --apply` to bring DNS in line.
- "busy": an apply was running; the next run tries again.
- "no subnet": the plan has no subnet with a DHCP range yet, so Kea is left as it is; add the subnet first, then its
  range (4.10.2.3, 4.10.2.4).
- A failed run keeps the last state, so the next run tries the same change again; fix the cause shown in the status
  (OpenBao sealed: unseal it, [4.7.1](4.7.1-openbao.md); Kea's check refusing: the option named in the message).
- At a site whose DC is read-only the poll reads that DC: a change written at the writable DC reaches it with the
  next replication, so Kea may take it a little later than 30 s.

## 4.10.2.14 Sync now

Design [1.10.4.28](../volume_1_description_and_architecture/1.10.4-address-manager.md#110428-sync-now); decision
2.1.10.29. The plan poll (4.10.2.13) brings Kea in line within 30 s of a change, but leaves DNS for the next apply.
Sync now does both at once, without an apply: after an edit to the plan (a name published in DNS, a new subnet's
reverse zone), at the site whose plan changed:

```bash
sudo fabricctl ipam sync
```

- It reads the plan, restarts Kea only if its configuration changed, brings the firewall in line when the served
  subnets changed, and, when DNS is affected, reloads BIND's zone list and the changed zones. No other service is
  restarted.
- Refused, saying why and changing nothing: while an apply is running (try again when it ends), at a site without
  DHCP, before the site's subnets moved into the plan (run an apply), or with `--site` (a sync is the site's own: run
  it there).
- If it fails part-way, it says what was done (for example Kea in line, BIND's records not): fix the cause shown and
  run it again, or run `sudo fabricctl --apply`.
- Every sync is in the audit log (`IPAM_SYNC`).
- In the console: the Sync now card on DHCP → Networks, with what the poll last found beside it (4.10.2.17).

## 4.10.2.15 Addresses in use that nobody recorded

Design [1.10.4.22](../volume_1_description_and_architecture/1.10.4-address-manager.md#110422-ping-check-and-the-scan-of-a-subnet-as-built)
and [1.10.4.36](../volume_1_description_and_architecture/1.10.4-address-manager.md#110436-scans-by-right-here-and-at-another-site);
decisions 2.1.10.13, 2.1.10.26 and 2.1.10.38.

**Ping-check** is on by itself: Kea pings an address before it offers it and skips one that answers. An address it
skipped shows as `declined` in `sudo fabricctl dhcp leases` and is not offered again for a day. To turn it off (a busy
network where 100 ms per new offer matters), set `ping_check: false` under `dhcp:` in the settings
(`sudo fabricctl`, the settings menu), then apply.

**A scan** of one subnet of this site's plan, DHCP on or off (by its name or network; at most a /22). It runs in
Kea's container, so the site needs DHCP installed. Root may always scan; anyone else needs the grants' networks
`scan` right at this site (4.6.10.8):

```bash
sudo fabricctl ipam scan iot                  # or: sudo fabricctl ipam scan 10.1.20.0/24
sudo fabricctl ipam scan iot --no-ask         # only print what it found
sudo fabricctl ipam scan iot --no-apply       # record what you say yes to, apply later
```

- It lists every address that answered, with the MAC when ARP saw it, and marks those in use but unrecorded. On a
  terminal it then asks, for each, `make 10.1.20.55 (aa:bb:cc:00:00:55) a reservation? [y/N]` (or, with no MAC,
  whether to record it as a static address) and a name (Enter for none). Yes records it in the plan and applies it,
  as `fabricctl ipam address add` would; no leaves it. Each find also prints the command that records it.
- A VLAN behind a router answers only what its gateway lets ping through, and shows no MAC.
- Refused, saying why and probing nothing: a subnet not in this site's plan (another network; another site's: scan
  it there, or ask that site, 4.10.2.16), one larger than a /22, a site without DHCP, a caller without `scan` here, a
  second scan while one runs, the same subnet again within a minute (it says how long to wait), and on a Kea image
  older than 0.9.0 ("update Kea's image": `sudo fabricctl images update kea`).
- Every scan is in the audit log (`IPAM_SCAN`, with what allowed it), and every address it recorded
  (`IPAM_ADDRESS_ADD`).
- In the console: DHCP → Networks → Scan a subnet (4.10.2.17).

## 4.10.2.16 A scan at another site

Design [1.10.4.36](../volume_1_description_and_architecture/1.10.4-address-manager.md#110436-scans-by-right-here-and-at-another-site);
decision 2.1.10.38. A scan always runs at the site whose subnet it is. From any other site, someone with `scan` at
that site (root always) asks for it:

```bash
sudo fabricctl ipam scan iot --site house2              # asks house2 to scan its subnet iot, and waits for the answer
sudo fabricctl ipam scan 10.2.20.0/24 --site house2 --no-wait   # only ask
sudo fabricctl ipam scan-requests --site house2         # house2's requests: pending, done (what answered), refused
sudo fabricctl ipam scan-requests                       # this site's
```

House2's plan poll runs it within about 30 s (one scan at a time there, the same subnet once a minute). The command
waits up to two minutes and prints the answer: every address that answered, the unrecorded first. Still pending
then, it says so; `scan-requests` shows the answer later. To record a find, use `fabricctl ipam address add ...
--site house2` (4.10.2.6).

- Refused here, saying why and writing nothing: no site named, this site itself (scan your own subnets with
  `fabricctl ipam scan <subnet>`), no `scan` right at that site, a subnet not in its plan or larger than a /22, a
  request for that subnet still pending, four requests pending there.
- Answered `refused` by house2, with why, never run: the request was not written by a fabric DC's agent account, the
  person it names does not hold `scan` there by house2's own reading of the grants, no DHCP (Kea) at house2, the
  subnet gone from its plan, an old Kea image there. Answered `expired`: house2 did not pick it up within an hour (is
  it running? `sudo systemctl status fabric-plan-watch.timer` there). Every request is removed 24 hours after it was
  made.
- If the poll at house2 cannot read or answer its requests (its DC not answering), its run fails after Kea's part,
  saying so in `systemctl status fabric-plan-watch.service`; they are tried again on the next run.
- At a site whose DC is read-only the request is written at its writable partner DC, and reaches the serving site
  with the next replication.
- In the audit log: here `IPAM_SCAN_REQUEST`; at house2 `IPAM_SCAN` (with `requested_by=`), or
  `IPAM_SCAN_REQUEST_REFUSED`.

## 4.10.2.17 The plan in the console: DHCP · Networks

Design [1.10.4.40](../volume_1_description_and_architecture/1.10.4-address-manager.md#110440-the-console-after-its-redo).
Open **DHCP → Networks** (seen with `dhcp:read`; the forms show with `dhcp:write`). Every change you make here is
**held** until you press **Apply** in the top bar, as on every console page; who may change a site's plan is still
set by the grants' networks rights (4.6.10.8), checked when you make the change and again at Apply.

- **The list:** every site of the domain with its number (pick one to show its plan), the **Sync now** card (this
  site), the scans requested at the site shown, and its VLANs, each subnet with a bar of its ranges and how much is in
  use. **Search** finds an address, a name or a MAC in the site shown; **Export (CSV)** downloads its address table.
- **Add VLAN** and **Set site number** open their forms on their own page.
- **A VLAN's page** (pick its ID): its subnets, **Change VLAN**, **Add subnet**, **Remove VLAN** (tick "with its
  subnets' recorded addresses" to remove those too).
- **A subnet's page** (pick its network): its bar and facts, its ranges, every address (recorded, leased or free),
  the options its clients get and where each comes from; **Change subnet**, **Add range**, **Remove a range**,
  **Record an address**, **Remove subnet**; **Scan this subnet** (this site) or **Scan at <site>** (another);
  **Its DHCP options**.
- **An address's page** (pick it in the table): **Change** or **Remove** a recorded address; a lease nobody recorded
  offers **Record it**, as a reservation for its device or a static address.
- **Apply:** the top bar's **Review** lists each held change in a sentence; **Apply** runs them in order, then, when
  any is this site's, brings Kea and the firewall in line once (restarting only what changed). Another site's
  changes are taken by that site's poll within 30 seconds; the site's number is never applied (it shapes
  suggestions only). A change refused at Apply stops it there and says why on the Review, the rest left pending:
  no grant at that site ("no grant gives you networks plan at lab"), a rule of the plan, or the plan changed by
  someone else since you made the change (review it and apply again).
- **Done at once, never held:** **Sync now** (4.10.2.14), **Scan now** and **Scan at <site>** (4.10.2.15,
  4.10.2.16). Each is still refused without its right, saying why.
- **Scan a subnet** (the list's actions bar) opens the scan page: pick a subnet and **Scan now**; then **Record a
  find** picks one of the addresses in use but unrecorded and holds it for Networks' Apply. Without the `scan` right
  here the page says why and offers no scan.
- A site, VLAN, subnet or address that is not there answers "Not found" (404). When this site's DC does not answer,
  the page shows this site's plan as last read and says when; changes are refused at Apply until it answers.

## 4.10.2.18 DHCP options in the console

Design [1.10.4.40](../volume_1_description_and_architecture/1.10.4-address-manager.md#110440-the-console-after-its-redo)
and [1.10.4.24](../volume_1_description_and_architecture/1.10.4-address-manager.md#110424-dhcp-options-in-the-plan-as-built).
Open **DHCP → DHCP options** (or **Its DHCP options** on a subnet's page). Its changes are held for its own **Apply**,
checked against the grants' networks `options` right at the site (at every site for the domain's set).

- **The sets:** the domain's (every site's clients) and the site's, each with its options, option definitions and
  client classes; then each subnet and reservation, linked.
- **Set an option** in the domain's set, the site's, or a class of either; **Remove an option** picks one from the
  list. **Add a client class**, **Remove a client class**, **Define an option Kea has no name for** and **Remove a
  definition** work the same way.
- **Show what a client gets at** the site, a subnet or a reservation lists every option a client there ends up with,
  where each comes from and what it replaces. On a subnet's or reservation's page you also **Set an option** or
  **Remove an option** on it, and switch **Network boot** on (a boot server and its files) or off (4.10.2.11).
- **Apply** runs the held changes, then brings this site's Kea and firewall in line once. A refusal (an unknown
  option name, bad data, no grant) stops it there and says why on the Review.

## 4.10.2.19 A location without a DC: its VLANs inside this site

A branch or an outbuilding without a DC can have its own subnet, reached through its router's DHCP relay to this
site's Kea. Its VLANs are planned in this site under a **location** (design:
[1.10.4.46](../volume_1_description_and_architecture/1.10.4-address-manager.md); decision 2.1.10.49). The location's
VLAN IDs and names may be the same as this site's own. You name a VLAN there as `<id>@<location>`.

1. On the location's router, set each network's DHCP to relay to this site's `host_ip` (4.10.2.7). If the router
   relays from its uplink or a tunnel, rather than from an address inside the subnet, record that address as the
   subnet's relay (`--relay`).
2. Add each VLAN with its network. No network is suggested at a location:

   ```bash
   sudo fabricctl ipam vlan add 10@branch --name iot --subnet 10.9.10.0/24     # its subnet is named branch-iot
   sudo fabricctl ipam vlan add 20@branch --name cams --subnet 10.9.20.0/24 --access guest
   ```

3. Every other command names the VLAN the same way: `ipam vlan set 10@branch ...`, `ipam subnet add 10@branch
   <cidr>`, `ipam range add 10@branch ...`, `ipam address add <ip> --vlan 10@branch`.
4. To move a VLAN to another location, run `sudo fabricctl ipam vlan set 10@branch --to-location shed`. Use
   `--to-location none` to move it to this DC's own location. Its subnets move with it and keep their names. A move
   onto an ID or a name the new location already has is refused, and nothing moves.
5. `sudo fabricctl ipam show` lists this DC's own VLANs first, then each location under `at <location>`. The export
   has a `location` column, its last.

In the console (DHCP · Networks), use **Add VLAN** with its **Location** field, and give the subnet. A VLAN at a
location is listed with "at <location>". Its page has a Location field, which moves it.

The location's subnets, options and names are this site's: the people with `networks:plan` at this site edit them
(1.10.4.34). The location depends on the link to this DC for DHCP, DNS and NTP. If that link may be down for longer
than a lease, set a longer `dhcp.lease_time` for the site (up to 30 days; 1.10.4.45.2).

## 4.10.2.20 A scan beyond a router

A subnet this host has no address in is reached through a router (a location's, 4.10.2.19). Its scan finds which
addresses answer, but ARP sees no MAC past the gateway. The scan says "beyond a router: addresses only" (decision
2.1.10.50).

- On a terminal, after you answer yes to record a find with no MAC, the command asks for its MAC. Type it to make
  the find a reservation, or press Enter to record a static address. A MAC that is not one is refused and nothing is
  recorded.
- The printed commands give both ways: `--kind static`, or `--kind reservation --mac <MAC>` once you know it.
- In the console's **Record a find**, type the MAC in the MAC field to make a find with none a reservation. Choosing
  a reservation with no MAC is refused and nothing is held.
